Sorting in Linear Time

Counting sort with the cumulative-count table worked cell by cell, radix sort pass by pass, bucket sort, why none of them contradicts the Ω(n log n) bound, and when each is actually usable.

Exam strategy

“Sort the following using counting sort / radix sort, showing all intermediate arrays” is the question, and it is entirely mechanical. Two things earn the marks: show the count array before and after the cumulative step, and show every pass of radix sort as a separate line. The companion theory question is “How do these algorithms beat the Ω(n log n) lower bound?” — the answer is one sentence, given below, and it is worth learning exactly.

The sentence that answers the theory question — learn it exactly

These algorithms do not contradict the Ω(n log n) lower bound, because they are not comparison sorts. The bound applies only to algorithms that determine the order by comparing elements with each other. Counting, radix and bucket sort instead use the values themselves as array indices, which is extra information the comparison model forbids. The price is that they only work on restricted inputs — small integers, fixed-width keys, or a known distribution.

1. Counting sort

The assumption and the idea Assumption: each of the n input elements is an integer in the range 0 to k.

Idea: for each element x, count how many elements are less than or equal to x. That count is x's position in the output.
The four steps 1. Create a count array C[0 … k], all zeros.
2. Count: for each element x of A, increment C[x]. Now C[i] = the number of elements equal to i.
3. Accumulate: replace C[i] by C[i] + C[i−1] for i = 1 to k. Now C[i] = the number of elements ≤ i.
4. Place: traverse A from RIGHT to LEFT. For each element x, put it at B[C[x] − 1] and decrement C[x].
Why right to left — this is the marked detail

Traversing from right to left makes counting sort STABLE. Equal elements keep their original relative order, because the rightmost duplicate is placed at the highest available position. Left-to-right traversal would reverse them. Stability is essential, because radix sort depends on it.

Analysis Counting the elements is Θ(n); building and accumulating C is Θ(k); placing is Θ(n).

When k = O(n), this is Θ(n) — linear. But if k = n², it is Θ(n²) and worse than merge sort. The whole method depends on the range being small.

2. Radix sort

The idea Sort digit by digit, starting from the LEAST significant digit (LSD radix sort). Each pass uses a stable sort — almost always counting sort.

The stability requirement is not optional. It is what preserves the ordering achieved by all the earlier, less significant passes.
Q. Sort A = [170, 45, 75, 90, 802, 24, 2, 66] by radix sort.

The largest number is 802, so d = 3 digits, and the radix is k = 10. Pad shorter numbers with leading zeros: 045, 075, 090, 024, 002.

Analysis d passes, each a counting sort costing Θ(n + k), where d is the number of digits and k the radix.

Time = Θ( d (n + k) )     Space = Θ(n + k)     Stable: YES     In place: NO

When d is a constant and k = O(n), this is Θ(n).
The subtlety examiners like

“Is radix sort really linear?” To distinguish n numbers they must be at least log2n bits wide, so d ≥ logkn, and the time becomes Θ(n logkn) — not asymptotically better than comparison sorting in the general case. It is genuinely linear only when d is fixed and small, as it is for 32-bit integers, dates or fixed-width identifiers. Say this and you have answered the deeper question.

Why LSD rather than MSD? Sorting from the most significant digit first would require sorting each bucket independently, which means recursion and bookkeeping. LSD needs no recursion at all — just d stable passes over the whole array.

3. Bucket sort

The assumption and the algorithm Assumption: the input is drawn from a uniform distribution over an interval, conventionally [0, 1).

1. Create n empty buckets.
2. Scatter: put element x into bucket ⌊n · x⌋.
3. Sort each bucket individually — usually with insertion sort, since buckets are expected to be tiny.
4. Gather: concatenate the buckets in order.
Q. Sort A = [0.78, 0.17, 0.39, 0.26, 0.72, 0.94, 0.21, 0.12, 0.23, 0.68] by bucket sort. n = 10, so bucket index = ⌊10x⌋.

Sanity check: 10 elements went in and 10 came out, and each bucket's contents lie strictly within its own interval, so concatenating in bucket order is guaranteed to be sorted.

Analysis Average case — Θ(n). With a uniform distribution the expected number of elements per bucket is 1, so the expected cost of insertion-sorting a bucket is O(1), and the total is Θ(n) for scatter + Θ(n) for the sorts + Θ(n) for gather.

Worst case — Θ(n²). If every element lands in the same bucket, that bucket must be insertion-sorted with n elements.

Space = Θ(n)    Stable: YES (if the per-bucket sort is stable)    In place: NO
The crucial contrast to state

Bucket sort's linear time is an ASSUMPTION about the input distribution, not a guarantee. Counting sort and radix sort are linear whatever the arrangement of the data, provided the range or digit count is small. That distinction is exactly what a “compare the linear-time sorts” question is after.

A worked comparison, because “which is better?” gets asked

Sorting n = 1000 numbers in the range 0 to 999999.

Counting sort: Θ(n + k) = 1000 + 1000000 ≈ 106 operations — and it needs a count array of a million entries. Terrible.

Radix sort with radix 10: d = 6, so Θ(6 × (1000 + 10)) ≈ 6060 operations. Excellent.

Merge sort: n log2n = 1000 × 10 = 10 000 operations. Competitive, and with no assumptions at all.

Conclusion: radix sort wins here, counting sort loses badly, and merge sort is a perfectly reasonable default. Counting sort is only worth using when k = O(n) — which is precisely why radix sort exists: it applies counting sort to one digit at a time, keeping k tiny.

Recall without looking

How do these sorts escape the Ω(n log n) bound?

They are not comparison sorts. The bound applies only to algorithms that determine order by comparing elements with each other; these use the values themselves as array indices, which the comparison model forbids. The price is that they only work on restricted inputs — small integers, fixed-width keys, or a known distribution.

Give the four steps of counting sort and why the last one goes right to left.

Create a count array C[0…k]; count occurrences so C[i] is the number of elements equal to i; accumulate so C[i] is the number of elements ≤ i; then traverse the input from right to left placing each x at B[C[x] − 1] and decrementing C[x]. Right to left makes it stable, which radix sort depends on.

Give counting sort's complexity and when it fails.

Time and space Θ(n + k), stable, not in place. It is linear when k = O(n), but if k is large — say n² — it is worse than merge sort and needs an enormous count array. Sorting 1000 values in the range 0 to 999999 costs about a million operations.

Describe radix sort, its complexity, and why stability is required.

Sort digit by digit from the least significant, using a stable sort — usually counting sort — at each pass. Time Θ(d(n + k)), space Θ(n + k). Stability is what preserves the ordering achieved by earlier, less significant passes; without it each pass would destroy the last. LSD avoids the recursion that MSD would need.

Is radix sort really linear?

Only when d is fixed and small. To distinguish n numbers, keys must be at least log₂n bits wide, so d ≥ log_k n and the general cost is Θ(n log_k n) — no better asymptotically than comparison sorting. It is genuinely linear for 32-bit integers, dates and fixed-width identifiers.

Describe bucket sort and state its key limitation.

Assume a uniform distribution over an interval; create n buckets; scatter x into bucket ⌊nx⌋; sort each bucket, usually with insertion sort; concatenate. Average Θ(n) because the expected bucket size is 1; worst case Θ(n²) when everything lands in one bucket. Its linear time is an assumption about the distribution, not a guarantee.

Compare the three linear-time sorts.

Counting: integers 0 to k, Θ(n + k) always, stable, breaks when k is large. Radix: fixed-width keys, Θ(d(n + k)) always, stable and must be, breaks when d is large or keys vary in width. Bucket: uniform distribution, Θ(n) average but Θ(n²) worst, stable if the inner sort is, breaks on skewed data. None is in place; counting and radix use no comparisons at all.
