1. Merge sort

Divide and conquer. Split the array in half, sort each half recursively, then merge the two sorted halves. All the work is in the merge.

The algorithm
MERGE-SORT(A, p, r)
   if (p < r) {
     q = ⌊(p + r) / 2⌋;      /* DIVIDE */
     MERGE-SORT(A, p, q);    /* CONQUER */
     MERGE-SORT(A, q+1, r);
     MERGE(A, p, q, r);      /* COMBINE — Θ(n) */
   }

2. Quick sort

Divide and conquer with the work in the DIVIDE step. Choose a pivot, partition the array so that everything smaller is on its left and everything larger on its right, then sort the two sides recursively. There is no combine step — once both sides are sorted, the array is sorted.

Lomuto partition, with the LAST element as pivot
PARTITION(A, low, high)
   pivot = A[high];
   i = low − 1;
   for (j = low; j < high; j++)
     if (A[j] ≤ pivot) { i++; swap A[i], A[j]; }
   swap A[i+1], A[high];
   return i + 1;  /* the pivot's final position */

Recurse on the left, [10, 30, 40, 50], pivot = 50. Every element is ≤ 50, so i advances with j throughout and the pivot ends at its own index. The sub-array is unchanged, and we recurse on [10, 30, 40] with pivot 40 — again already correct — then [10, 30] with pivot 30, then [10]. Left side sorted: [10, 30, 40, 50].

Recurse on the right, [90, 80], pivot = 80. j = 0: 90 > 80, so no swap; i stays at −1. Then swap A[i+1] = A[0] with the pivot: [80, 90].

Final sorted array: [10, 30, 40, 50, 70, 80, 90] ✓

Note the left side: it was already sorted, and quick sort still recursed four levels deep on it, doing n−1, n−2, … comparisons. That is the worst case in miniature — and it is exactly what the next section analyses.

The analysis — the 10-mark derivation

BEST CASE — the pivot always lands in the middle.

Each partition splits n elements into two halves of n/2, and partitioning costs Θ(n).

T(n) = 2T(n/2) + Θ(n)

Master theorem Case 2 → T(n) = Θ(n log n)

WORST CASE — the pivot is always the smallest or largest element.

The partition splits n into 0 and n − 1. Partitioning still costs Θ(n).

T(n) = T(n − 1) + T(0) + Θ(n) = T(n − 1) + Θ(n)

Solve by back-substitution:

T(n) = T(n−1) + n = T(n−2) + (n−1) + n = … = 1 + 2 + … + n = n(n+1)/2

T(n) = Θ(n²)

When does it happen? With the first or last element as pivot, on an array that is already sorted, or sorted in reverse — the most common real-world input, which is the irony of quick sort.

Also note the space: the recursion depth becomes n, so the stack space is O(n) in the worst case rather than O(log n).

AVERAGE CASE — the pivot is equally likely to be any rank.

If the pivot ends at position i, the two subproblems have sizes i and n−1−i. Averaging over all n equally likely positions:

T(n) = (1/n) Σi=0n−1 [ T(i) + T(n−1−i) ] + Θ(n)

Solving this gives T(n) ≈ 1.39 n log2 n, so

T(n) = Θ(n log n)

The intuitive argument, which earns the same marks in less time: even a permanently lopsided 9-to-1 split gives the recurrence T(n) = T(9n/10) + T(n/10) + n, whose recursion tree has every level costing n and a height of log10/9n — still Θ(n log n). Only a split that is unbalanced by a constant number of elements, rather than a constant ratio, produces n² — and that is very unlikely by chance.

The three fixes for the worst case — name them

1. Randomised quick sort: pick the pivot at random and swap it to the end. No particular input is then bad; the expected time is Θ(n log n) for every input.

2. Median-of-three: take the median of the first, middle and last elements as pivot. Cheap, and it makes sorted input the best case rather than the worst.

3. Introsort: start with quick sort and switch to heap sort if the recursion depth exceeds about 2 log n. This is what the C++ STL std::sort actually does, giving a genuine O(n log n) worst case.

3. Heap sort

The algorithm — two phases Phase 1. BUILD-MAX-HEAP(A) — O(n).
Phase 2. For i = n down to 2:
    swap A[1] and A[i] — the maximum moves to its final position;
    reduce the heap size by 1;
    MAX-HEAPIFY(A, 1) — O(log n).

The pattern to state: the sorted portion grows from the RIGHT end of the array, and it is built in increasing order because the largest remaining element is extracted each time. This is why a max-heap produces ascending order.

Analysis Phase 1: O(n).   Phase 2: (n − 1) calls to MAX-HEAPIFY, each O(log n) → O(n log n).

T(n) = O(n) + O(n log n) = Θ(n log n) — in all cases, and with O(1) auxiliary space.

The Ω(n log n) lower bound

The question: “Prove that any comparison-based sorting algorithm requires Ω(n log n) comparisons in the worst case.”
The decision-tree argument.

Step 1 — the model. A comparison sort determines the sorted order using only comparisons between elements: ai < aj, ai ≤ aj, and so on. It never inspects the values in any other way.

Step 2 — the decision tree. Represent the algorithm as a binary tree: each internal node is one comparison, with the two branches for the two outcomes; each leaf is one possible output permutation.

Step 3 — the leaves. The algorithm must be able to produce every one of the n! permutations of the input, since any of them could be the correct answer. So the tree has

at least n! reachable leaves.

Step 4 — the height. A binary tree of height h has at most 2h leaves. Therefore

2h ≥ n!  ⇒  h ≥ log2(n!)

Step 5 — Stirling's approximation. n! ≈ √(2πn) (n/e)n, so

log2(n!) = n log2n − n log2e + O(log n) = Θ(n log n)

Step 6 — the conclusion. The height of the decision tree is the number of comparisons in the worst case. Hence

Any comparison-based sort makes Ω(n log n) comparisons in the worst case. ∎

The two consequences to state:

  • Merge sort and heap sort are ASYMPTOTICALLY OPTIMAL — they achieve the bound.
  • The bound applies only to comparison sorts. Counting, radix and bucket sort escape it by not comparing elements to each other — which is exactly the subject of Lesson 14.

A simpler version of Step 5, if Stirling is not to hand: n! ≥ (n/2)n/2, so log2(n!) ≥ (n/2)log2(n/2) = Ω(n log n). That suffices for the bound.

The paradox to explain, because it is a favourite question

“If quick sort's worst case is n² and heap sort's is n log n, why is quick sort the one used in practice?”

Three reasons: its constant factor is the smallest of the three — its inner loop is extremely tight; it is in place, unlike merge sort; and it has excellent cache locality, since it works on contiguous ranges, whereas heap sort jumps all over the array. The worst case is also easy to avoid with a randomised or median-of-three pivot. Real libraries hedge with introsort.

Check yourself

1. Merge sort's worst-case time is:

The split is always exactly in half regardless of the data, so no input is worse than any other. Its real weakness is the O(n) auxiliary array.

2. Quick sort's worst case arises when:

The partition splits n into 0 and n−1, giving T(n) = T(n−1) + n = Θ(n²). The irony is that sorted input is the most common real-world case.

3. A permanently 9-to-1 unbalanced split in quick sort gives:

Every level still costs n and the height is log_{10/9}n. Only a split unbalanced by a constant number of elements, not a constant ratio, produces n².

4. Heap sort's auxiliary space is:

It sorts within the array itself. That, plus its Θ(n log n) worst case, makes it the only one of the three with both guarantees — which is why introsort falls back to it.

5. In the decision-tree lower-bound proof, the number of leaves must be at least:

Every one of the n! permutations must be a reachable output. A binary tree of height h has at most 2^h leaves, so 2^h ≥ n! and h ≥ log₂(n!) = Θ(n log n).

6. Which of these sorts is stable?

Merge sort is stable if you take from the left list on ties. Quick sort's partition swaps distant elements, and heap sort's swaps do the same, so both destroy the original order of equal keys.

7. Quick sort is preferred in practice despite its O(n²) worst case because:

The worst case is real but easy to avoid with a randomised or median-of-three pivot, and libraries hedge further with introsort, which switches to heap sort past a depth of about 2 log n.

Recall without looking

Give merge sort's recurrence, complexity and trade-offs.

T(n) = 2T(n/2) + Θ(n), Master theorem Case 2, so Θ(n log n) in every case because the split never depends on the data. It needs O(n) auxiliary space, is stable, is not in place, and is the right choice for linked lists and external sorting.

Derive quick sort's best, worst and average cases.

Best: the pivot lands in the middle, T(n) = 2T(n/2) + Θ(n) = Θ(n log n). Worst: the pivot is always smallest or largest, T(n) = T(n−1) + Θ(n) = n(n+1)/2 = Θ(n²), which happens on already sorted or reverse-sorted input with a first or last pivot. Average: T(n) = (1/n)Σ[T(i) + T(n−1−i)] + Θ(n) ≈ 1.39 n log₂n = Θ(n log n).

Name the three fixes for quick sort's worst case.

Randomised pivot selection, so no particular input is bad; median-of-three, which turns sorted input into the best case; and introsort, which switches to heap sort past a recursion depth of about 2 log n — this is what the C++ STL sort does.

Describe heap sort and its complexity.

Build a max-heap in O(n), then repeatedly swap the root with the last heap element, shrink the heap by one and heapify the root — n − 1 times at O(log n) each. Total Θ(n log n) in all cases, with O(1) auxiliary space. The sorted portion grows from the right end of the array, in ascending order.

Prove the Ω(n log n) lower bound.

Model the algorithm as a binary decision tree, each internal node a comparison and each leaf an output permutation. It must be able to produce all n! permutations, so it has at least n! leaves. A binary tree of height h has at most 2^h leaves, so 2^h ≥ n! and h ≥ log₂(n!) = Θ(n log n) by Stirling. The height is the worst-case comparison count. Merge sort and heap sort achieve this bound and so are asymptotically optimal; counting, radix and bucket sort escape it because they do not compare elements to each other.

Give the master comparison table.

Merge sort: n log n in all cases, O(n) space, stable, not in place. Quick sort: n log n best and average, n² worst, O(log n) stack, not stable, in place. Heap sort: n log n in all cases, O(1) space, not stable, in place. Insertion and bubble sort: Ω(n) best, n² otherwise, O(1) space, stable. Selection sort: n² always, O(1) space, not stable.

Why is quick sort used in practice despite its worst case?

Its constant factor is the smallest — the inner loop is very tight; it is in place, unlike merge sort; and its cache locality is excellent because it works on contiguous ranges, while heap sort jumps around the array. The worst case is easy to avoid with randomisation or median-of-three.
