Input Buffering

Why the scanner needs lookahead, the one-buffer scheme and where it breaks, buffer pairs with their two pointers and the reload algorithm, and the sentinel trick that halves the tests per character — with the arithmetic to prove it.

Exam strategy

“Explain input buffering with sentinels” is a reliable 5–10 mark question, and it has a fixed shape: state why buffering is needed, draw the two-buffer diagram with lexemeBegin and forward marked, give the code before and after sentinels, and finish with “two tests per character become one”. That last sentence is the point of the whole topic and the one students omit. The eof sentinel character and the reason N is the disk block size are the two details examiners probe.

Why buffering is needed at all

The two reasons — state both

1. Speed. The lexical analyser is the only phase that reads the source character by character, so it does the bulk of the compiler's I/O. Fetching one character at a time from disk would dominate the compiler's running time. Reading a large block at once and serving characters from memory is far cheaper.

2. Lookahead. The analyser often cannot decide what token it has until it has read one or more characters past the end of the lexeme. Seeing > it must look ahead to know whether the token is > or >=; seeing i, f it must look ahead to know whether the lexeme is the keyword if or the start of the identifier ifx. Having looked ahead, it must be able to retract — and that requires the characters to still be available.

The one-buffer scheme

The simplest idea: read N characters into a single buffer, scan from it, and when it runs out read the next N.

One buffer — and its fatal flaw
+————————————————————————+
|    E  =  M  *  C  *  *  2  …   |
+————————————————————————+
    ↑
   pointer
The problem: if a lexeme straddles the end of the buffer, reloading destroys the part already scanned. A long identifier or string literal beginning near the end of the buffer cannot be recovered. The scheme only works if no lexeme is ever longer than the buffer, which cannot be guaranteed.

Buffer pairs — the two-buffer scheme

The arrangement Use a buffer divided into two halves of N characters each, where N is the size of one disk block — typically 1024 or 4096.

Read N characters into each half with ONE system read command, not one per character. If fewer than N characters remain in the file, a special eof character marks the true end of input.

Two pointers are maintained:
    lexemeBegin — marks the start of the current lexeme, whose extent we are trying to determine.
    forward — scans ahead until a pattern match is found.

Once the lexeme is determined, forward is set past its last character, the token and attribute are returned, and then lexemeBegin is moved to the character just after the lexeme.

Here, forward crossed into the second half while scanning operator **. Because lexemeBegin is still preserved in the first half without being overwritten, the whole token boundary remains intact!

Each half is extended to hold a sentinel eof marker. The common advance path requires only ONE test: if (*forward == eof)!

The advancing code — before sentinels
if ( forward at end of first half ) {
    reload second half;
    forward = forward + 1;
}
else if ( forward at end of second half ) {
    reload first half;
    move forward to the beginning of the first half;
}
else forward = forward + 1;
The two halves are used alternately and cyclically. Count the tests: TWO per character advanced — one for each end-of-half check — even though a reload is actually needed only once every N characters. That waste is what sentinels remove.
The limitation to state

Buffer pairs work only if no lexeme is longer than N characters, since a lexeme that spans both halves would still be destroyed by a reload. In practice N is a full disk block and lexemes are short, so this never bites — but it is the honest caveat, and stating it earns a mark.

Sentinels — the improvement

The idea Extend each buffer half to hold a sentinel character at the end — a character that cannot be part of the source program. The natural choice is eof.

Now a single test if (*forward == eof) catches both end-of-half conditions, and only when that test succeeds does the code work out which case it is. The common case — an ordinary character — costs ONE test instead of two.
The advancing code — with sentinels
forward = forward + 1;
if ( *forward == eof ) {   /* the ONE test in the common path */
    if ( forward at end of first half ) {
        reload second half;
        forward = forward + 1;
    }
    else if ( forward at end of second half ) {
        reload first half;
        move forward to the beginning of the first half;
    }
    else terminate lexical analysis;  /* a real eof — the source has ended */
}
The sentence that is the point of the topic

Without sentinels, every character advance costs two tests. With sentinels it costs one, because the expensive checks are performed only when the single eof test succeeds — roughly once every N characters. The number of tests per character is halved.

And the neat bonus: the same test detects the genuine end of the file, so no separate end-of-input check is needed anywhere in the scanner.

Numerical — what sentinels actually save

Q. A source program contains 100,000 characters. The buffer half-size is N = 4096. Compare the number of end-of-buffer tests, and the number of disk reads, with and without sentinels.

Disk reads. Each reload fetches N = 4096 characters with one system read.

Reloads = ⌈100000 / 4096⌉ = ⌈24.41⌉ = 25 reads

This is the same either way — sentinels do not change how often the buffer must be refilled, only how often we check. Say so; it is the distinction the question is testing.

Tests without sentinels. Two tests per character advanced:

2 × 100000 = 200,000 tests

Tests with sentinels. One test per character, plus the two extra tests performed on each of the 25 occasions the eof test succeeds:

100000 + (2 × 25) = 100000 + 50 = 100,050 tests

Saving = 200000 − 100050 = 99,950 tests, very close to 50 %.

Sanity check: the overhead term is 50 tests against 100,000 — that is 0.05 %, which is why the saving is “essentially half” rather than exactly half. As N grows the saving approaches exactly 50 %, and that limiting statement is what the theory means by “the tests per character are halved”.

And the comparison that matters most: reading one character at a time from disk would need 100,000 system calls instead of 25. Buffering saves four orders of magnitude on I/O; sentinels then save a further factor of two on the in-memory testing. The two optimisations are independent, and a full answer names both.

Check yourself

A long identifier or string literal beginning near the end of the buffer cannot be recovered. Buffer pairs fix it by never reloading the half that still holds lexemeBegin.

2. In buffer pairs, N is normally chosen to be:

One system read fetches exactly one block, which is what makes buffering worth doing. It also means N is far larger than any realistic lexeme.

3. The two pointers maintained are:

Once the lexeme is determined, forward sits just past its last character; the token is returned, and only then does lexemeBegin move to the character after the lexeme.

4. A sentinel must be a character that:

If it could occur in the source, the test would fire spuriously. Using eof has the bonus that the same test also detects the genuine end of input.

Without them, both end-of-half conditions are tested every time. With them, a single eof test guards both, and the expensive checks run only when it succeeds — about once every N characters.

Recall without looking

Give the two reasons input buffering is needed.

Speed — the lexical analyser is the only phase reading the source character by character, so it does the bulk of the compiler's I/O, and fetching a block at a time is far cheaper than a system call per character. Lookahead — the analyser often cannot decide the token until it has read past the end of the lexeme, as with > versus >= or if versus ifx, and it must then be able to retract.

Why does the one-buffer scheme fail?

If a lexeme straddles the end of the buffer, reloading destroys the part already scanned, so a long identifier or string beginning near the end cannot be recovered. It works only if no lexeme is ever longer than the buffer, which cannot be guaranteed.

Describe the buffer-pairs scheme.

Two halves of N characters each, N being one disk block, filled by a single read command per half and used alternately and cyclically. Two pointers: lexemeBegin marks the start of the current lexeme, forward scans ahead until a pattern matches. Once found, forward sits past the last character, the token is returned, and lexemeBegin moves past the lexeme. It costs two tests per character and requires no lexeme to exceed N characters.

Explain the sentinel improvement and give the code.

Extend each half by one character holding a sentinel that cannot appear in the source — eof. Then: forward = forward + 1; if (*forward == eof) { if at end of first half, reload the second and advance; else if at end of second half, reload the first and move forward to its beginning; else terminate lexical analysis }. The common path costs one test instead of two, and the same test detects real end of input.

For 100,000 characters with N = 4096, give the reads and the tests.

Reads: ⌈100000/4096⌉ = 25, the same with or without sentinels. Tests without sentinels: 2 × 100000 = 200,000. Tests with sentinels: 100000 + 2 × 25 = 100,050. The saving is 99,950, essentially 50 %, and it approaches exactly 50 % as N grows. Reading character by character would instead need 100,000 system calls rather than 25.

Compare the four schemes.

Character-at-a-time: no buffer, one system call per character. One buffer of N: one test per character but cannot handle a lexeme spanning the boundary. Buffer pairs, 2 × N: two tests per character, handles boundary-spanning lexemes shorter than N. Buffer pairs with sentinels, 2 × (N+1): one test per character, same condition, and the same test finds real eof.
