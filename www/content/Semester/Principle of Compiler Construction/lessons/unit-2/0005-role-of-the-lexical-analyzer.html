What the lexical analyser does

The primary task The lexical analyser is the first phase of a compiler. It reads the stream of characters making up the source program, groups them into meaningful sequences called lexemes, and for each lexeme produces a token of the form

⟨ token-name, attribute-value ⟩

which it passes to the parser.

The lexical analyser operates as a subroutine of the parser, not a separate physical pass. The parser calls getNextToken() on demand, and the scanner consumes characters until the next token is found.

The process is sometimes split in two: scanning, which does the simple character-level work such as deleting comments and compacting whitespace, and lexical analysis proper, which produces the tokens. Mentioning that split is worth a mark.

Token, pattern, lexeme — the distinction that gets tested

The three definitions A TOKEN is a pair consisting of a token name and an optional attribute value. The token name is an abstract symbol representing a kind of lexical unit — a keyword, or a sequence of input characters denoting an identifier. It is what the parser works with.

A PATTERN is a description of the form that the lexemes of a token may take. For keywords it is just the sequence of characters; for identifiers and other tokens it is a more complex structure — normally a regular expression.

A LEXEME is a sequence of characters in the source program that matches the pattern for a token and is identified by the lexical analyser as an instance of that token.
The one-line test

Pattern is the RULE. Lexeme is the actual TEXT in the file. Token is the CATEGORY the parser is told about.

Or, as a sentence: “the lexeme count matches the pattern for identifiers, so the lexical analyser emits the token ⟨id, ptr⟩.” One rule, many lexemes, one token name.

Two points examiners probe. Each keyword has its own token — if and else are different tokens, not two lexemes of one “keyword” token. And all the comparison operators share one token, comparison, distinguished by an attribute — because the parser's grammar treats them identically.

Attributes of tokens

When more than one lexeme matches a pattern, the analyser must pass the parser additional information about the particular lexeme found. That extra information is the attribute value.

TokenAttribute value
IdentifierA pointer to its symbol-table entry, which holds the lexeme, its type, and where it was first seen
NumberIts numeric value, or a pointer to a constant table
Comparison operatorA code such as LT, LE, EQ, NE, GT, GE saying which operator it was
Keyword, punctuationNone needed — the token name says everything
Q. Give the token sequence, with attributes, for E = M * C ** 2

⟨id, pointer to symbol-table entry for E⟩   ⟨assign_op⟩   ⟨id, pointer to M⟩   ⟨mult_op⟩
⟨id, pointer to C⟩   ⟨exp_op⟩   ⟨number, integer value 2⟩

Seven tokens. Note that ** is one token, not two — the analyser must use the longest-match rule, which Lesson 10 formalises. Note also that =, * and ** need no attribute, while every identifier does.

Why separate lexical analysis from parsing?

Three reasons — memorise as three words 1. SIMPLICITY of design. Separating the two lets each be simplified. A parser that also had to handle whitespace and comments would be far more complex than one that deals with tokens only.

2. Compiler EFFICIENCY is improved. A separate lexical analyser lets us apply specialised techniques — particularly buffering — that serve only the lexical task. Reading characters is where most of the compiler's I/O time goes, so speeding it up matters.

3. Compiler PORTABILITY is enhanced. Input-device-specific peculiarities and character-set oddities can be confined to the lexical analyser, leaving the rest of the compiler untouched when the platform changes.
The deeper reason, if you want the extra mark

Regular expressions are enough to describe tokens, but not enough to describe syntax. Identifiers, numbers and operators form a regular language, recognisable by a finite automaton with no memory. Balanced parentheses and nested blocks are not regular — they need a stack, so they need a context-free grammar and a pushdown automaton. The split between lexical and syntax analysis is exactly the split between regular and context-free languages, and using the weaker, faster machine wherever it suffices is why the design is fast.

Token-counting numericals

The four rules that decide every counting question

1. A string literal in double quotes is ONE token, however long, and whatever is inside it — commas, spaces and %d included.

2. Every punctuation mark is a separate token — each comma, semicolon, bracket and brace counts.

3. Multi-character operators are ONE token — <=, ==, ++, &&, ** each count once, by the longest-match rule.

4. Whitespace and comments are NOT tokens. They are discarded before the parser sees anything.

Numerical 3. How many tokens are in int max(int a, int b);?

int(1)  max(2)  ((3)  int(4)  a(5)  ,(6)  int(7)  b(8)  )(9)  ;(10)

Answer: 10 tokens. Note that each occurrence of the keyword int counts separately — the question asks for the number of tokens, not the number of distinct tokens. If it asked for distinct ones the answer would be 6: int, max, (, a / b as id, ,, ), ;. Read the wording.

Numerical 4. How many tokens are in if (a >= b) count++; /* tally */?

if(1)  ((2)  a(3)  >=(4)  b(5)  )(6)  count(7)  ++(8)  ;(9)

Answer: 9 tokens.

Two traps together: >= and ++ are one token each, not two, by the longest-match rule; and the comment contributes nothing, having been stripped before tokens were produced.

Lexical errors and recovery

How little the lexical analyser can actually detect

It sees only a small part of the program, so its power to spot errors is limited. Given fi (a == f(x)) in C, it cannot tell whether fi is a misspelling of if or a genuine, undeclared function name — fi is a perfectly valid identifier, so it emits ⟨id, fi⟩ and lets the parser complain. A lexical error occurs only when no pattern matches at all — an illegal character such as @ or #, an unterminated string or comment, or an ill-formed number such as 12abc.

Recovery strategyAction
Panic modeDelete successive characters from the remaining input until the analyser can find a well-formed token. This is the simplest and most common strategy, and it may confuse the parser, but it never loops for ever
DeleteDelete one extraneous character
InsertInsert one missing character
ReplaceReplace one incorrect character by a correct one
TransposeSwap two adjacent characters

The last four are called minimal-distance or error-correction transformations: the analyser looks for the smallest number of transformations that turn the bad text into a legal one. It is elegant, but expensive, so panic mode is what real compilers use.

Check yourself

1. In count = count + 1;, the word count is:

Pattern is the rule, lexeme is the actual text in the file, token is the category reported to the parser. One pattern, many lexemes, one token name.

2. How many tokens are in printf("i = %d, &i = %x", i, &i);?

The whole quoted string is one token, so the commas, spaces and ampersand inside it are not counted. Counting them is the mistake almost everyone makes first.

3. How many tokens are in if (a >= b) count++;?

Both >= and ++ are single tokens by the longest-match rule. Splitting them into two each gives 11, which is the trap.

Recall without looking

State the primary task of the lexical analyser and its other jobs.

It reads the character stream, groups characters into lexemes, and produces a token ⟨token-name, attribute-value⟩ for each, which it passes to the parser. It also strips whitespace and comments, counts newlines so errors can be given line numbers, enters identifiers into the symbol table, and in some designs expands macros. It runs as a subroutine of the parser, called through getNextToken, not as a separate pass.

Define token, pattern and lexeme, with the one-line test.

A token is a pair of an abstract token name and an optional attribute value — the category the parser works with. A pattern is a description of the form the lexemes of a token may take, normally a regular expression — the rule. A lexeme is the actual sequence of characters in the source that matches a pattern — the text in the file.

What attribute does each kind of token carry?

Identifier: a pointer to its symbol-table entry. Number: its numeric value or a pointer to a constant table. Comparison operator: a code such as LT, LE, EQ, NE, GT or GE. Keywords and punctuation: none, because the token name says everything.

Give the three reasons for separating lexical from syntax analysis.

Simplicity of design — each phase is simpler when neither handles the other's job. Compiler efficiency — specialised buffering techniques can be applied to the character-reading task alone. Compiler portability — input-device and character-set peculiarities are confined to one phase. The deeper reason is that tokens form a regular language recognisable by a finite automaton, while syntax is context-free and needs a stack.

Give the four rules for counting tokens.

A double-quoted string literal is one token however long. Every punctuation mark counts separately. Multi-character operators such as <=, ==, ++ and ** are one token each by longest match. Whitespace and comments are not tokens at all. Also check whether the question asks for tokens or for distinct tokens.

When is something a lexical error, and what are the recovery strategies?

Only when no pattern matches at all — an illegal character, an unterminated string or comment, or a malformed number such as 12abc. A misspelling like fi for if is not a lexical error, because it is a valid identifier. Recovery: panic mode, deleting successive characters until a well-formed token appears — the simplest and most used; and the minimal-distance transformations of delete, insert, replace and transpose one character.
