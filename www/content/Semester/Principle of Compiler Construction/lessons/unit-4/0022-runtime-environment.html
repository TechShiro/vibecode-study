1. Runtime Storage Organization

During execution, the operating system allocates a continuous block of virtual memory to the compiled program, subdivided into four logical segments:

Target Machine Runtime Memory Map
Target Code / Text Segment
Fixed size, read-only machine instructions (Low Memory: 0x0000...)
Static Data Segment
Global variables and compile-time string/numeric constants
Heap (Grows Downward ↓)
Dynamically allocated data (malloc, new, dynamic objects)
↑   ——— Free Unallocated Memory Space ———   ↓
Stack (Grows Upward ↑)
Activation records / stack frames for active procedure calls (High Memory)
Why Stack and Heap Grow Toward Each Other

By placing the Stack at the highest memory addresses growing downward and the Heap at lower addresses growing upward, the compiler allows both segments to dynamically share the unused middle memory space without pre-allocating an arbitrary fixed boundary for either.

2. Activation Trees and Lifetimes

The execution of a program can be modeled as a tree of procedure invocations called an Activation Tree:

  • Each node represents an activation of a procedure.
  • The root of the tree is the activation of the main program entry point (main()).
  • Node $A$ is the parent of node $B$ if activation $A$ calls procedure $B$.
  • Children are ordered from left to right according to the chronological sequence of calls.
Worked Example: QuickSort Activation Tree 
main()
└── qsort(1, 9)
    ├── partition(1, 9)
    ├── qsort(1, 4)
    │   ├── partition(1, 4)
    │   ├── qsort(1, 2)
    │   └── qsort(4, 4)
    └── qsort(6, 9)
        └── ...

Crucial Property: Because procedure calls follow Last-In, First-Out (LIFO) nesting, the set of currently live procedure activations at any moment corresponds strictly to the path from the root to the active node in the activation tree. This guarantees that procedure storage can be managed using a runtime stack.

3. Structure of an Activation Record (Stack Frame)

An Activation Record (or stack frame) is a contiguous block of memory allocated on the runtime stack for a single execution of a procedure. It contains seven standard fields:

Field #Field NameCompiler Function & Purpose
1 Return Value Allocates space used by the called procedure to return computed results to the caller (especially for composite types not fitting into a machine register).
2 Actual Parameters Storage for arguments passed by the calling procedure to the callee.
3 Control Link (Dynamic Link) A pointer storing the base address of the caller's activation record. Used by the CPU base pointer (ebp/rbp) to unwind the stack frame upon return.
4 Access Link (Static Link) A pointer to the activation record of the procedure that statically (lexically) encloses the callee. Used to access non-local variables in languages with nested procedures (e.g. Pascal, Ada, GCC nested C).
5 Saved Machine Status Stores the program counter (return address), condition code flags, and machine registers that must be restored when the function completes.
6 Local Variables Storage for variables declared locally within the scope of this procedure invocation.
7 Temporaries Temporary memory allocated for intermediate expression evaluations that cannot fit into CPU general-purpose registers.
Exam Differentiator: Dynamic Link vs Static Link

Control Link (Dynamic Link): Points to the calling procedure at runtime. Follows the dynamic execution call stack. Unwinds on return.

Access Link (Static Link): Points to the enclosing procedure defined in the source code text. Follows static lexical scoping rules. Used to resolve non-local variable addresses.

5. Parameter Passing Mechanisms

MechanismPassing RuleCaller ImpactAliasing Sensitivity
Call by Value The caller evaluates the actual argument's r-value (data value) and copies it into the callee's parameter. None: Modifications to parameter do not affect caller's variables. None.
Call by Reference The caller passes the l-value (memory address) of the actual variable. Formal parameter becomes an alias for the actual variable. Direct & Immediate: Every assignment to formal parameter immediately alters caller's variable in real time. High: Two parameters referencing the same variable alias each other.
Call by Value-Result (Copy-Restore) Actual argument value copied in at call time. Callee operates on local copy. At procedure return, final local value is copied back to caller's argument. Deferred: Caller's variable remains unchanged until the moment the function returns. Distinct from Reference if aliasing occurs (order of copy-back matters!).
Call by Name (Algol 60) Textual substitution of argument expression into procedure body (implemented via runtime functions called thunks). Evaluated afresh every time parameter is accessed; side effects repeat. Extreme (can cause unexpected Jensen's Device behavior).
Classic Exam Problem: Parameter Passing & Aliasing Comparison

Consider the following C-like program:

int a = 1;

void test(int x, int y) {
    x = x + 1;
    y = y + a;
}

int main() {
    test(a, a);
    print(a);
}

What is printed under each parameter passing mechanism?

  • 1. Call by Value:
    $x = 1, y = 1$ are independent local copies.
    $x = 1 + 1 = 2$.
    $y = 1 + a = 1 + 1 = 2$.
    Global variable $a$ was never modified. Output: $a = 1$.
  • 2. Call by Reference:
    Both $x$ and $y$ receive the address of global variable $a$ ($x \equiv a, y \equiv a$).
    $x = x + 1 \implies a = 1 + 1 = 2$.
    $y = y + a \implies a = a + a = 2 + 2 = 4$.
    Output: $a = 4$.
  • 3. Call by Value-Result (Copy-Restore):
    At call time: copy in $x = 1, y = 1$.
    Body executes: $x = 1 + 1 = 2$.
    $y = 1 + a = 1 + 1 = 2$ (since global $a$ is still 1 during execution).
    At return time: copy back parameters to $a$ from left to right:
    $a = x = 2$, then $a = y = 2$.
    Output: $a = 2$.

6. Accessing Non-Local Data · Static Links vs The Display Mechanism (Mam's Material)

In languages that support nested procedures (such as Pascal, Ada, and modern closures in Python/JavaScript), a procedure can reference variables declared in lexically enclosing outer procedures. The runtime environment must efficiently resolve these non-local data accesses.

Lexical Nesting Depth Definition • Main program sits at nesting depth $0$ (or $1$).
• A procedure immediately declared inside procedure $p$ at depth $d$ has nesting depth $d + 1$.
• If procedure $p$ at nesting depth $n_p$ accesses variable $x$ declared at nesting depth $n_q$, the nesting depth difference is $\Delta = n_p - n_q$.

Method 1: Static Links (Access Links / Static Chain)

In this approach, each activation record contains a pointer called an access link (or static link) that points directly to the activation record of the procedure that statically (lexically) encloses it in the source text.

  • Variable Lookup: To access variable $x$ declared at nesting depth $n_q$ from depth $n_p$, the CPU follows exactly $\Delta = n_p - n_q$ static links backward: $$\text{Target Frame Address} = \underbrace{\text{static\_link}(\text{static\_link}(\dots(\text{current\_fp})\dots))}_{n_p - n_q \text{ dereferences}} + \text{offset}(x)$$
  • Limitation: Variable access takes time proportional to the nesting depth difference ($O(k)$ pointer dereferences). If procedures are deeply nested, non-local reads become sluggish.

Method 2: The Display Mechanism

The Display is an auxiliary global array of pointers, d[], maintained by the runtime environment to provide constant-time $O(1)$ access to non-local variables regardless of nesting depth.

How the Display Operates (Mam's Runtime env.pdf)

The display array is indexed by lexical nesting depth:

  • d[i] always points to the most currently active activation record at lexical nesting depth $i$.
  • Fast Variable Access ($O(1)$): When procedure $p$ accesses variable $x$ declared at lexical depth $i$ with offset $j$, the address is computed directly in one single instruction: $$\text{Address}(x) = \mathbf{d}[i] + j$$ No static links are traversed!
  • Maintenance on Procedure Call ($p$ at depth $k$ called):
    1. Save the current value of d[k] into the new activation record's "saved display entry" slot.
    2. Update d[k] to point to the new activation record.
  • Maintenance on Procedure Return:
    1. Restore d[k] from the activation record's saved display entry slot before popping the frame.

Check yourself

Retrieval practice

1. What is the fundamental difference between the Control Link and the Access Link in an activation record?

The control link (dynamic link) maintains the caller-callee call chain for stack unwinding. The access link (static link) traverses lexical scope levels to find non-local variables.

2. Why can't early programming languages like Fortran 77 that use static storage allocation support recursive procedure calls?

Static allocation binds fixed memory addresses to local variables at compile time. Recursive calls require multiple live instances of variables simultaneously, which static allocation cannot provide.

3. In Call by Value-Result (Copy-Restore), when are modifications to formal parameters reflected in the caller's actual arguments?

Value-Result acts on a local copy throughout the function body and copies the final value back to the caller's argument only when the procedure terminates.

4. Which runtime memory segment grows downward toward the heap to accommodate active procedure frames?

The runtime stack grows downward from high memory, while the heap grows upward from low memory into the shared free space.

2. Actual Parameters

4. Access Link (Static Link)

6. Local Variables
7. Temporaries.

Contrast Call by Reference and Call by Value-Result.

Call by Reference passes the variable address, causing modifications to take effect immediately in the caller. Call by Value-Result copies values in, operates on local variables, and copies values back only at return time.
