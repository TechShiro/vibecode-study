1. Transition Diagrams in Lexical Analysis

Formal Definition A transition diagram is a stylized, flowchart-like directed graph used as an intermediate specification to design and implement a lexical analyser. Its nodes represent states (conditions during scanning), and its directed edges represent transitions triggered by specific input characters.
Graphic ConventionVisual RepresentationPrecise Semantic Meaning
State Single circle with state ID: (s) Represents an intermediate condition reached while scanning a sequence of characters.
Start State Arrow labelled start pointing into a state from nowhere: → (0) The entry point where scanning begins. There is exactly one start state per token pattern.
Accepting / Final State Double concentric circles: ((2)) Indicates that a complete, valid lexeme has been recognized. Associated token is returned.
Retract Pointer An asterisk (*) placed beside an accepting double circle: ((4))* Lookahead overrun: The scanner read one character too far to verify lexeme boundary. The input buffer pointer must be moved back by one position (forward--).
Directed Edge Arrow labelled with input symbol: — c → Transition to target state if the current lookahead character matches symbol c.
other Edge labelled other Matches any input character not explicitly listed on existing edges leaving that state.
State Transition Diagram: Recognition of Relational Operators (relop)
Branch A · Initiated by <
start → (0) — < → (1)
  • — = → ((2))  &implies;  return(relop, LE)  [No retract needed]
  • — > → ((3))  &implies;  return(relop, NE)  [No retract needed]
  • — other → ((4))*  &implies;  return(relop, LT)  ← RETRACT 1 CHAR
Branch B · Initiated by =
start → (0) — = → ((5))  &implies;  return(relop, EQ)  [No retract needed]
Branch C · Initiated by >
start → (0) — > → (6)
  • — = → ((7))  &implies;  return(relop, GE)  [No retract needed]
  • — other → ((8))*  &implies;  return(relop, GT)  ← RETRACT 1 CHAR
Why the Retract Asterisk (*) is Essential

Consider scanning the code expression if (a < b):

  • The scanner reads < (moves from state 0 to state 1).
  • At state 1, it cannot immediately conclude the token is LT, because the subsequent character might be = (forming <=) or > (forming <>).
  • It reads ahead one character and sees space or b. This matches the other edge, moving to accepting state 4.
  • Because character b belongs to the next token, the scanner must push it back into the input buffer (decrementing the pointer). The asterisk * visually documents this retract action.

2. Bootstrapping and T-Diagrams

The Fundamental Chicken-and-Egg Problem

Compilers are sophisticated software systems written in high-level programming languages (e.g., C, C++, Rust). However, to compile a high-level compiler program, a compiler for that language must already exist! How was the first compiler ever compiled?

The solution is Bootstrapping: writing an initial tiny subset compiler in machine code, and systematically using each generated compiler to compile a larger, richer version of itself — metaphorically “pulling oneself up by one's own bootstraps.”

T-Diagram Notation

In 1958, H. Bratman introduced T-diagrams to represent compiler translation dependencies visually. Every compiler involves three languages:

Anatomy of a Compiler T-Diagram
Source S
Target T
Impl I
Notation: (S, T, I) or SCTI
• Left Arm (S): The Source Language the compiler accepts as input.
• Right Arm (T): The Target Language the compiler generates as output.
• Bottom Stem (I): The Implementation Language the compiler code is written in.
The Universal Composition Rule Fundamental Rule: To RUN a compiler on physical hardware $M$, its implementation language $I$ must be the machine code of $M$.

If you have a compiler (S, T, I) and an existing host compiler (I, M, M) that runs on $M$ and translates language $I$ into machine code $M$, then compiling the first with the second yields:

(S, T, I)  +  (I, M, M)  &implies;  (S, T, M)
The source and target arms remain strictly unchanged; only the implementation language transforms from I to M.

1. The Classic Two-Step Bootstrap

Exam Problem · Build a full compiler for language L on machine M starting with no tools

Step 1 — Hand-code a minimal subset compiler in machine language:
Select a small subset $S$ of language $L$ (just enough syntax to write compiler parsing routines). Hand-code a compiler for subset $S$ targeting $M$, directly in machine language $M$:

(S, M, M) — Rudimentary and tedious to code, but fully executable on machine M.

Step 2 — Write the full compiler in the subset language:
Write the compiler for the complete language $L$, targeting machine code $M$, in the comfortable subset language $S$:

(L, M, S) — Source code only; cannot run directly on M yet.

Step 3 — Compile Step 2 with Step 1:
Run $(L, M, S)$ through $(S, M, M)$ on machine $M$:

(L, M, S)  compiled by  (S, M, M)  &implies;  (L, M, M)

Outcome: You now possess a production compiler for the full language $L$, executing natively on machine $M$ and generating native machine code for $M$!

2. The Three-Step Cross-Compiler Construction

The Guaranteed Exam 10-Marker · Design of a Cross-Compiler

Problem Statement: You possess an existing, fully functioning compiler for language $L$ that executes on Machine $A$ and produces code for Machine $A$ — i.e., (L, A, A). A new machine $B$ is released. You want to generate a native compiler for $L$ that runs on Machine $B$ and produces code for Machine $B$ — i.e., (L, B, B). Construct the step-by-step T-diagram derivation.

Step 1 — Retarget the code generator for Machine B:
Take the compiler source code and modify its backend code generator so that it emits machine instructions for Machine B instead of Machine A. Because the compiler is written in language $L$, this produces:

(L, B, L) — Source L, Target B, written in L. Not runnable anywhere yet.

Step 2 — Compile on Machine A using the existing host compiler:
Feed $(L, B, L)$ through your working compiler $(L, A, A)$ on Machine A:

(L, B, L)  compiled by  (L, A, A)  &implies;  (L, B, A)

THIS IS THE CROSS-COMPILER! It runs on Machine A, but generates executable binary for Machine B.

Step 3 — Compile the compiler source again using the cross-compiler on Machine A:
Feed $(L, B, L)$ into the cross-compiler $(L, B, A)$ running on Machine A:

(L, B, L)  compiled by  (L, B, A)  &implies;  (L, B, B)

Final Step — Transfer binary to Machine B: Move the resulting binary executable $(L, B, B)$ onto Machine B. Machine B can now compile language $L$ independently without Machine A.

Sanity Check: The source arm remains L in every single step! If your source arm changes, you made an error.

Self-Hosting Compilers and Three-Stage Verification

Modern production compilers for languages like GCC, Clang, Rust (rustc), and Go are self-hosting — the compiler is written in the very language it compiles. To eliminate compiler bugs and verify determinism, they execute a Three-Stage Bootstrap:

  • Stage 1: System compiler compiles compiler source → produces compiler_stage1.
  • Stage 2: compiler_stage1 compiles compiler source → produces compiler_stage2.
  • Stage 3: compiler_stage2 compiles compiler source → produces compiler_stage3.
  • Bitwise Verification: compiler_stage2 and compiler_stage3 are compared byte-for-byte using cmp. If the binaries are identical, the compiler is proven deterministic and sound.

3. Just-In-Time (JIT) Compilation

Formal Definition Just-In-Time (JIT) compilation (also known as dynamic translation or run-time compilation) is compilation performed during program execution at run time rather than ahead of time. A JIT compiler translates intermediate bytecode into native machine instructions dynamically immediately prior to execution and caches the translated code in RAM.
System Flowchart: The Just-In-Time Compilation Lifecycle
Source Code · Prog.java / App.js
Ahead-of-Time Bytecode Translation Emits platform-neutral bytecode · Prog.class
Virtual Machine Interpreter (Tier 1) Starts executing bytecode immediately line by line
Runtime Profiler & Hot Spot Detector Monitors loop iterations & method invocation counters
JIT Compiler (Tier 2 · HotSpot / V8 TurboFan) Compiles frequently executed hot methods to native CPU code
Native Machine Code Cache (RAM) Future calls invoke native machine code directly at full CPU speed

Why JIT is Unsuitable for Hard Real-Time Systems

JIT compilation introduces dynamic compilation pauses and memory allocation spikes whenever execution crosses hot-spot thresholds. In hard real-time systems (such as automotive airbag controllers, pacemaker firmware, or aerospace flight control), execution latency must be strictly deterministic with sub-millisecond guarantees. JIT warm-up jitter makes it dangerous for hard real-time environments.

Check Yourself

1. In a lexical analyser transition diagram, an asterisk (*) beside an accepting double circle indicates that:

To determine that < was not <=, the scanner peeked at the next character. That character belongs to the subsequent token, so the buffer pointer must be retracted.

2. In the T-diagram triple (S, T, I), the components S, T, and I represent:

Left arm S = source language, right arm T = target language, bottom stem I = implementation language.

3. Compiling compiler source (L, B, L) with an existing compiler (L, A, A) running on Machine A yields:

The composition rule updates only the implementation arm from L to A. The result runs on A and emits code for B, which is the exact definition of a cross-compiler.

4. A JIT compiler achieves near-native execution speed because it:

JIT begins execution via interpretation for rapid startup, dynamically profiles loop and method executions, and compiles hot spots into cached native instructions.

Recall Without Looking

What is a transition diagram and what are its graphical conventions?

A directed graph used to specify lexical analysers. Conventions: Start state (incoming arrow from nowhere); State (single circle); Accepting/Final state (double circle); Retract pointer (asterisk * beside double circle indicating one character lookahead pushback); Edges (labelled transitions on character classes); other (matches unhandled characters).

What is bootstrapping and what problem does it resolve?

Bootstrapping is the process of constructing a compiler in the very language it compiles. It resolves the chicken-and-egg problem of needing a working compiler to compile the initial compiler, by starting with a hand-written subset compiler in machine code and iteratively compiling progressively richer versions of itself.

State the T-diagram composition rule.

(S, T, I) compiled by (I, M, M) → (S, T, M). To execute a compiler, its implementation language must match the host machine. The source and target arms remain strictly unchanged; only the implementation arm transforms.

Derive the three-step cross-compiler construction from memory.

Given (L, A, A), target is (L, B, B). Step 1: Retarget code generator, producing source (L, B, L). Step 2: Compile (L, B, L) with (L, A, A) on Machine A → produces (L, B, A), which is the cross-compiler. Step 3: Compile (L, B, L) with cross-compiler (L, B, A) on Machine A → produces (L, B, B). Move binary to Machine B.

Explain how Just-In-Time (JIT) compilation works.

Source is compiled to bytecode ahead of time. At runtime, the VM interpreter begins executing bytecode immediately. A runtime profiler monitors loop and method invocation counts. When code crosses an execution threshold (hot spot), the JIT compiler translates it to native CPU instructions and caches it in RAM for subsequent zero-overhead calls.

Compare AOT, interpretation, and JIT across key metrics.

AOT: translates prior to execution, instant startup, fastest native execution, poor binary portability, low RAM. Interpretation: translates line by line, instant startup, slowest execution, excellent portability, low RAM. JIT: translates hot spots dynamically at runtime, fast startup with warm-up, near-native speed, excellent bytecode portability, higher RAM footprint, non-deterministic timing.
