1. Why SLR is Insufficient — The Need for LR(1) Lookahead

SLR(1) parsers consult the global set $FOLLOW(A)$ to decide whether to reduce $A \to \alpha$. However, $FOLLOW(A)$ collects every terminal that can follow $A$ across the entire grammar, regardless of the current parse state.

In many valid right-sentential forms, only a strict subset of $FOLLOW(A)$ is legally allowed at a specific step. Placing reduce actions indiscriminately across all of $FOLLOW(A)$ leads to false conflicts (as proven in Lesson 15 with $S \to L = R \mid R$).

To fix this, Canonical LR (CLR) equips every item with an explicit 1-symbol lookahead context.

2. Formal Definition of an LR(1) Item

LR(1) Item Structure [A → α • β,   a]

where $A \to \alpha \beta$ is a grammar production, $\cdot$ is the dot position, and $a$ is a lookahead terminal (or the endmarker $\$$).

Semantic Meaning: The substring $\alpha$ has been matched on the stack, $\beta$ is expected next in the input, and when the complete non-terminal $A$ is reduced, the very next terminal in the input stream must be $a$.

Crucial Rule for Shifts vs Reduces

The lookahead $a$ has no effect on shift items $[A \to \alpha \cdot X \beta, a]$. The dot simply shifts across $X$ regardless of $a$. The lookahead $a$ comes into play only when the dot reaches the end $[A \to \alpha \cdot, a]$ — instructing the parser to reduce by $A \to \alpha$ strictly when the current lookahead symbol equals $a$.

3. CLR(1) Canonical Collection: CLOSURE and GOTO

Algorithm: CLR CLOSURE(I) 1. Initialize $CLOSURE(I) = I$.
2. For each item $[A \to \alpha \cdot B \beta, a] \in CLOSURE(I)$, and each production $B \to \gamma$ in the grammar, add the item:
[B → • γ,   b]   for every terminal   b ∈ FIRST(βa)
to $CLOSURE(I)$ if not already present.
3. Repeat until no more items can be added.
How to Compute FIRST(βa)

If $\beta$ does NOT derive $\epsilon$, then $FIRST(\beta a) = FIRST(\beta)$.
If $\beta$ is empty ($\beta = \epsilon$) or $\beta \Rightarrow^* \epsilon$, then the terminal $a$ itself provides the lookahead: $FIRST(\epsilon a) = \{a\}$.

Algorithm: CLR GOTO(I, X) For any grammar symbol $X$ (terminal or non-terminal):
$$GOTO(I, X) = CLOSURE(\{[A \to \alpha X \cdot \beta, a] \mid [A \to \alpha \cdot X \beta, a] \in I\})$$ The lookahead $a$ is preserved untouched as the dot steps over $X$.

5. LALR(1) Construction — Merging States with Identical Cores

Definition: Core of an LR(1) Item The core of an LR(1) item $[A \to \alpha \cdot \beta, a]$ is the production and dot position $A \to \alpha \cdot \beta$, completely ignoring the lookahead $a$.

Notice in the CLR(1) table that several pairs of states have identical sets of cores and differ only in their lookaheads:

  • States $I_3$ and $I_6$ share the core $\{C \to c \cdot C, C \to \cdot c C, C \to \cdot d\}$.
    Merge into $I_{36}$ with lookahead set $\{c, d\} \cup \{\$\} = \{c, d, \$\}$.
  • States $I_4$ and $I_7$ share the core $\{C \to d \cdot\}$.
    Merge into $I_{47}$ with lookahead set $\{c, d\} \cup \{\$\} = \{c, d, \$\}$.
  • States $I_8$ and $I_9$ share the core $\{C \to c C \cdot\}$.
    Merge into $I_{89}$ with lookahead set $\{c, d\} \cup \{\$\} = \{c, d, \$\}$.
State Count Equivalence

Merging the 10 CLR states reduces the table size to exactly 7 states: $I_0, I_1, I_2, I_{36}, I_{47}, I_5, I_{89}$.
Crucial theorem: The number of states in an LALR(1) parser is always identical to the number of states in an SLR(1) parser!

6. Conflict Behavior During LALR State Merging

Conflict CategoryCan Merging Introduce It?Mathematical Reason
Shift/Reduce Conflict NO (Never) Suppose state $I_m$ has shift on $a$ and reduce on $a$. The shift action is determined purely by the core item $[A \to \alpha \cdot a \beta]$. Since cores in the merged states are identical, both individual states already had this shift on $a$. If one individual state had a reduction on $a$, that state already possessed a Shift/Reduce conflict in CLR(1)! Merging can never create a new S/R conflict.
Reduce/Reduce Conflict YES (Possible) Suppose State $I_1$ has $[A \to \alpha \cdot, a]$ and $[B \to \beta \cdot, b]$, while State $I_2$ (same core) has $[A \to \alpha \cdot, c]$ and $[B \to \beta \cdot, a]$. Neither individual state has an R/R conflict in CLR(1). But when merged, State $I_{12}$ has both reductions active on lookahead terminal $a$ — producing a new Reduce/Reduce conflict!

Error Detection, Error Recovery & The Viable Prefix Property in LR Parsers

A central theoretical and practical triumph of bottom-up LR parsing is its precise, immediate error localization. Unlike naive parsers, an LR parser will never shift an invalid terminal onto the stack. The moment an illegal token appears in the input stream, the parser announces an error immediately.

The Viable Prefix Property Explained Verbatim (Mam's Syntax Analysis-2.pdf)

A viable prefix is defined as a prefix of a right-sentential form that can appear on the stack of a shift-reduce parser without going past the right end of the handle.

Why this matters for examiners:

  • As long as the parser's stack contains a viable prefix, there is at least one continuation of input symbols that could complete a valid rightmost derivation.
  • Canonical LR parsers possess the viable prefix property: they detect a syntax error as soon as the input token makes it impossible to form a viable prefix. No erroneous input token is ever shifted into the parser state stack!
  • LALR note: While merging states in LALR never introduces shift/reduce conflicts, it may delay error detection — an LALR parser may perform a few extra spurious reductions before detecting an error, but it still never shifts an invalid token.

Error Recovery Strategies in Bottom-Up LR Parsing

Recovery StrategyAlgorithm / ProcedurePros & Cons in Exams
1. Panic-Mode Recovery in LR When an error entry (blank) is encountered in the ACTION table:
  1. Scan down the stack from the top until a state $s$ is uncovered that possesses a valid goto entry on a major non-terminal $A$ (such as stmt or expr).
  2. Discard zero or more input tokens until a token $a$ is found that can legitimately follow $A$ ($a \in \text{FOLLOW}(A)$).
  3. Push state $\text{goto}(s, A)$ onto the stack and resume normal shift-reduce parsing.
Completely avoids infinite loops; robust and easy to implement. May discard significant input if synchronizing headers are far away.
2. Phrase-Level Recovery in LR The compiler designer fills blank slots in the ACTION table with pointers to custom error routines based on the state and symbol:
  • Routine E1 (missing operand): Push dummy id token and state, report "Operand expected".
  • Routine E2 (unbalanced parentheses): Push matching ) state, report "Unbalanced parenthesis".
  • Routine E3 (missing semicolon): Insert ; token and execute shift.
Local, user-friendly diagnostic messages; requires careful manual configuration to avoid cascading false errors.
3. Error Productions Augment the grammar itself with productions representing common programming mistakes (e.g., $E \to E \ E$ for missing operators).Permits the parser to construct standard parse trees and generate pinpoint diagnostic warnings.

Check yourself

Retrieval practice

1. When computing the CLR closure of $[A \to \alpha \cdot B \beta, a]$, what lookahead is assigned to newly generated items $[B \to \cdot \gamma, b]$?

The lookahead represents what follows B in this sentential form: $\beta$ followed by $a$. Hence, $b \in FIRST(\beta a)$.

2. An LALR(1) parser is constructed by merging states from which collection?

LALR merges CLR states that share identical cores, unioning their lookahead sets. This contracts the table back to LR(0)/SLR size while retaining precise lookahead discrimination.

3. Can merging CLR(1) states into LALR(1) introduce new Shift/Reduce conflicts?

Shifts depend solely on the core $[A \to \alpha \cdot a \beta]$. Because both merged states had the exact same core, if a Shift/Reduce conflict occurred after merging, it must have already been present in one of the individual CLR states.

4. How does the number of states in an LALR(1) parser compare to the number of states in an SLR(1) parser for any arbitrary grammar?

Both SLR(1) and LALR(1) state spaces are in 1-to-1 correspondence with the canonical sets of LR(0) cores. Therefore, their state counts are always identical.

Recall without looking

How does CLR lookahead differ from SLR?

SLR reduces on all terminals in $FOLLOW(A)$ regardless of state context. CLR reduces strictly on the terminal $a$ carried by the LR(1) item $[A \to \alpha \cdot, a]$, which was computed from $FIRST(\beta a)$ when the item was created.

Why can LALR introduce Reduce/Reduce conflicts but never Shift/Reduce?

Shifts depend strictly on the item core $[A \to \alpha \cdot a \beta]$, which is identical in both merged states. A reduce action depends on lookaheads: if two different productions reduce in the same core state with non-overlapping lookaheads in CLR, unioning their lookaheads during merge can cause their lookaheads to collide on a shared terminal, creating an R/R conflict.
