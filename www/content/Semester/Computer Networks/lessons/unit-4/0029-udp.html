UDP — User Datagram Protocol

Eight bytes of header, four fields, and almost no services — and every one of those omissions is deliberate. The header, the pseudoheader checksum, the applications, and the TCP vs UDP table that is asked every year.

Exam strategy

"Compare TCP and UDP" is the single most likely question in Unit IV — answer it as a table of 10–12 rows. "Draw the UDP header" is a 3-mark freebie: four fields, two bytes each, sixteen bytes total is wrong — it is eight. The sub-question that separates answers is "why would anyone use an unreliable protocol?", so have the applications list and the reasoning ready.

What UDP is

UDP is a connectionless, unreliable transport protocol. It adds only what the transport layer minimally must add: process-to-process addressing and optional error checking. Nothing else.

UDP providesUDP does NOT provide
Process-to-process delivery via port numbersNo connection establishment — no handshake, no setup delay
Multiplexing and demultiplexingNo acknowledgement and no retransmission
An optional checksum over the whole datagramNo sequence numbers — so no ordering and no duplicate detection
A very small, fixed 8-byte headerNo flow control — a fast sender can swamp a slow receiver
No congestion control — UDP does not slow down when the network is loaded
The sentence that answers "why use UDP at all?"

Reliability costs time, and for some traffic a late packet is worse than a lost one. In a live voice call, retransmitting a lost 20 ms of audio means it arrives after the moment it was needed — the gap is already past. Dropping it and moving on is strictly better. UDP is not "TCP without the good bits"; it is the correct choice whenever timeliness matters more than completeness.

The UDP header

UDP header — 8 bytes, four fields of 2 bytes each | Source Port (16) | Destination Port (16) |
| Total Length (16) | Checksum (16) |
FieldSizePurpose
Source port16 bitsThe port of the sending process. If the source is the client it is an ephemeral port; if the server, a well-known port.
Destination port16 bitsThe port of the receiving process.
Total length16 bitsThe length of the whole user datagram — header plus data — in bytes. Minimum 8 (header only, no data); maximum 65,535.
Checksum16 bitsError detection over the header, the data and a pseudoheader. Optional in IPv4 — all zeros means "not computed". Mandatory in IPv6.
The total-length field is technically redundant — say so

The IP header already carries the total datagram length and the header length, so the UDP data length could be derived by subtraction. The field exists anyway, so that UDP does not have to depend on the service of the IP layer — it keeps the layers independent. That reasoning is a genuine 2-mark answer.

The pseudoheader

The UDP checksum is unusual: it covers not only the UDP header and data but also a pseudoheader, a temporary structure built from fields of the IP header.

The pseudoheader — 12 bytes, not transmitted | Source IP address (32) |
| Destination IP address (32) |
| All 0s (8) | Protocol = 17 (8) | UDP total length (16) |

Why it exists: to let the receiver check that the datagram actually arrived at the right host and was meant for UDP. Without it, a corrupted IP destination address could deliver a perfectly valid-looking UDP datagram to the wrong machine, which would accept it. The pseudoheader is added for the calculation and then discarded — it is never transmitted, and the protocol field is set to 17, UDP's IP protocol number.

Worked example — UDP length arithmetic

Q. A UDP datagram has a total length field of 48. The IP datagram carrying it has a total length of 92 and a HLEN value of 5. Find (a) the UDP data length, (b) the size of the IP header, (c) whether any padding was added.

(a) UDP data = UDP total length − UDP header = 48 − 8 = 40 bytes

(b) IP header = HLEN × 4 = 5 × 4 = 20 bytes

(c) IP payload = IP total length − IP header = 92 − 20 = 72 bytes.
But the UDP datagram is only 48 bytes. 72 − 48 = 24 bytes unaccounted for.

An IP datagram carries exactly one UDP datagram, so this means the IP layer either carried 24 bytes of options that HLEN did not account for — impossible, since HLEN = 5 means no options — or the figures are inconsistent. In a well-formed datagram, IP total length − IP header must equal the UDP total length.

The check to state: IP total length = IP header + UDP total length. Here that would require 20 + 48 = 68, not 92. Spotting the inconsistency is the answer to this style of question — examiners set it deliberately.

Where UDP is actually used

ApplicationWhy UDP rather than TCP
DNS (port 53)A query and a reply are one small exchange each. A three-way handshake would triple the cost of a two-packet transaction. If a reply is lost, the resolver simply asks again.
DHCP (ports 67, 68)The client has no IP address yet, so no connection could be established anyway. It must broadcast, and TCP cannot broadcast.
Streaming audio and video, VoIPTimeliness beats completeness — a retransmitted frame arrives too late to be played. Better a small glitch than a stall.
Online gamingPosition updates are superseded by the next update. Resending a stale one is worse than useless.
TFTP (port 69)Deliberately simple, for booting diskless machines. It builds its own minimal reliability on top.
SNMP (port 161)Network management must keep working when the network is already congested — exactly when TCP would back off and stall.
RIPRouting updates are sent periodically; a lost update is replaced by the next one 30 seconds later.
Multicast and broadcastTCP cannot do either — it is inherently a one-to-one connection. Anything one-to-many must use UDP.

The general rule, worth a closing line: UDP suits processes that need a simple request-reply exchange, that have their own reliability mechanism, that are multicast, or for which speed matters more than accuracy.

The row most answers omit

TCP is a byte stream; UDP is message oriented. If an application writes 100 bytes then 200 bytes to a TCP connection, the receiver may read 300 bytes in one go, or 150 twice — TCP does not preserve the boundaries. UDP does: one send is one datagram is one receive. This has real consequences for how applications are written, and including it marks out an answer that understands the protocols rather than having memorised a list.

Check yourself

Retrieval practice

1. The UDP header is:

Source port, destination port, total length, checksum — four fields, 16 bits each, 8 bytes total. 20–60 bytes describes TCP. The pseudoheader is 12 bytes but is never transmitted.

2. The pseudoheader is included in the UDP checksum so that the receiver can verify:

It carries the IP source and destination addresses plus protocol number 17. Without it, a corrupted IP destination address could deliver an apparently valid UDP datagram to the wrong machine, which would accept it.

3. DNS uses UDP rather than TCP mainly because:

A query and a reply are one small packet each; adding a three-way handshake and teardown would triple the traffic. If a reply is lost the resolver just asks again — cheaper than maintaining a connection. (DNS does use TCP for large zone transfers.)

4. Which is true of UDP but not TCP?

TCP is inherently a one-to-one connection, so it cannot broadcast or multicast at all — anything one-to-many must use UDP. The other three options describe TCP exactly.

5. A UDP total length field contains 8. This means:

Total length covers header plus data, and the header alone is 8 bytes — so 8 means zero data. This is legal: an empty UDP datagram can be sent as a probe or keep-alive.

Recall without looking

Define UDP and list what it does and does not provide.

A connectionless, unreliable transport protocol. Provides: process-to-process delivery via ports, multiplexing/demultiplexing, an optional checksum, and an 8-byte header. Does not provide: connection establishment, acknowledgement, retransmission, sequence numbers, flow control or congestion control.

Draw the UDP header with field sizes.

Source Port (16) | Destination Port (16) | Total Length (16) | Checksum (16). Eight bytes, fixed. Total length covers header plus data: minimum 8, maximum 65,535.

Why does UDP have a length field when IP already has one?

The value could be derived from the IP header by subtraction, but the field exists so UDP does not have to depend on the service of the IP layer — it keeps the two layers independent.

What is the pseudoheader and why is it used?

A 12-byte structure of IP source address, IP destination address, all-zero byte, protocol number 17, and the UDP length, added to the checksum calculation and then discarded — never transmitted. It lets the receiver verify the datagram reached the correct host and was intended for UDP.

Give six applications of UDP and the reason for each.

DNS (handshake would cost more than the exchange); DHCP (client has no address yet and must broadcast); streaming and VoIP (timeliness beats completeness); gaming (stale updates are worthless); TFTP (deliberately simple); SNMP (must work when the network is congested); RIP (periodic updates replace lost ones); any multicast or broadcast (TCP cannot do either).

Give eight differences between TCP and UDP.

Connection-oriented vs connectionless; reliable vs unreliable; ordered vs unordered; 20–60 byte vs 8-byte header; segment vs user datagram; flow and congestion control vs neither; full error control vs optional checksum only; slower vs faster; byte stream vs message oriented; no broadcast vs broadcast and multicast supported.

Explain "TCP is a byte stream, UDP is message oriented".

TCP does not preserve the boundaries of application writes — 100 bytes then 200 bytes may be read as one 300-byte chunk. UDP does preserve them: one send is one datagram is one receive.
