TCP Flow and Error Control

The sliding window in bytes rather than frames, the window-size formula that ties flow and congestion control together, silly window syndrome with both its fixes, and the three error-control mechanisms including fast retransmit.

Exam strategy

Two questions. (1) "Explain flow control in TCP" — draw the sliding window over a byte line, define the four pointers, and give the window-size formula. (2) "What is silly window syndrome and how is it solved?" — a 5-mark question with a clean structure: the sender's version fixed by Nagle's algorithm, the receiver's version fixed by Clark's solution or delayed acknowledgement. Naming the two algorithms is where the marks are.

Flow control in TCP

Flow control balances the rate a producer creates data against the rate a consumer can absorb it. TCP separates the two concerns cleanly:

Flow controlCongestion control
ProtectsThe receiverThe network
Driven byrwnd — the receiver's advertised window, carried in the headercwnd — the congestion window, computed by the sender itself
Signalled howExplicitly, in the window size field of every segmentImplicitly, by packet loss and timeouts
The formula that ties them together Send window size = minimum ( rwnd , cwnd )
The sender obeys whichever constraint is tighter.

This single line answers "how do flow and congestion control interact?" and it is the most valuable sentence in the lesson.

The sliding window

TCP's sliding window differs from the data link layer's in three ways, and the differences are examinable:

The sender's window covers four regions of the byte stream:

The four regions 1. Bytes sent and acknowledged — may be purged from the buffer
2. Bytes sent but not yet acknowledged  ← outstanding
3. Bytes not yet sent but which may be sent now  ← usable window
4. Bytes that cannot be sent until the window moves
Window movementCauseEffect
Opens (right edge moves right)The receiver's application consumes data, freeing buffer spaceMore bytes become sendable
Closes (left edge moves right)Data is sent and acknowledgedAcknowledged bytes leave the window
Shrinks (right edge moves left)The receiver advertises a smaller windowStrongly discouraged — it can leave already-sent bytes outside the window
Worked example — the effective window

Q. A receiver advertises rwnd = 5000 bytes. The sender's congestion window is 3000 bytes, and it has already sent 1200 bytes that remain unacknowledged. How many more bytes may it send right now?

Send window = min(rwnd, cwnd) = min(5000, 3000) = 3000 bytes

Outstanding (sent, not acknowledged) = 1200 bytes

Usable window = 3000 − 1200 = 1800 bytes

Sanity check: the usable window can never be negative. If it comes out negative, either the outstanding count is wrong or the receiver shrank its window — which is exactly the situation TCP discourages.

Follow-up: if the receiver's application now reads 2000 bytes and it re-advertises rwnd = 7000, but cwnd is unchanged, the send window is still min(7000, 3000) = 3000. Opening the receiver's window does nothing while congestion control is the binding constraint — a good line to add, because it shows which limit is actually operating.

The zero-window problem and the persistence timer

If the receiver advertises rwnd = 0, the sender must stop. The receiver will send a window-update segment when space frees up — but that update is a pure acknowledgement, and pure acknowledgements are not acknowledged, so they are not retransmitted if lost. Both sides would then wait forever: a deadlock.

The fix is the persistence timer. When the sender receives a zero-window advertisement it starts this timer; on expiry it sends a probe segment of one byte, which forces the receiver to respond with its current window size. Cover this here; the timer itself returns in Lesson 34.

Silly window syndrome

The problem: segments carrying only a few bytes of data but a full 20-byte TCP header and 20-byte IP header. Sending 1 byte of data in a 41-byte packet is about 2% efficiency. It can be caused by either end.

Caused by the sender — Nagle's algorithm

An application such as TELNET generates one byte at a time. If TCP sent each one immediately, the link would fill with 41-byte packets carrying one byte each.

Nagle's algorithm 1. The sending TCP sends the first piece of data immediately, however small — even one byte.
2. After that, it waits, accumulating data in the buffer, until either an acknowledgement for the outstanding data arrives, or enough data has accumulated to fill a maximum-size segment (MSS).
3. Repeat step 2 for the rest of the transmission.

Why it is elegant, and worth stating: the algorithm is self-adjusting. On a fast network acknowledgements return quickly, so segments are sent often and latency stays low. On a slow network they return slowly, so more data accumulates and segments are larger — exactly when efficiency matters most. It adapts to the link without being told anything about it.

Caused by the receiver — Clark's solution and delayed acknowledgement

A receiving application that consumes one byte at a time frees one byte of buffer at a time, and if TCP advertises each such opening the sender responds with another one-byte segment.

FixHow it worksCost
Clark's solutionSend an acknowledgement as soon as data arrives, but advertise a window of zero until either the buffer space is half empty or there is room for a maximum-size segment.None significant — the sender is kept informed but not invited to send trivial segments.
Delayed acknowledgementDo not acknowledge immediately. The delay prevents the sender sliding its window at once, and gives the receiving application time to consume more. It also reduces traffic by acknowledging several segments at once.The sender may retransmit unnecessarily if the delay is too long, so it is bounded — typically at most 500 ms.
The three-line answer to "what is silly window syndrome?"

Segments carrying only a few bytes of data with 40 bytes of headers, wasting bandwidth. If the sender causes it (an application producing one byte at a time), Nagle's algorithm fixes it. If the receiver causes it (an application consuming one byte at a time), Clark's solution or delayed acknowledgement fixes it. Name the cause and the matching fix for each side — that structure is what the marks are for.

Error control in TCP

TCP is reliable, and it achieves that with exactly three tools:

ToolDetects / handles
ChecksumCorrupted segments. 16 bits, covering header, data and pseudoheader. Mandatory. A corrupted segment is silently discarded by the receiver, which then looks like a lost segment.
AcknowledgementConfirms arrival. Cumulative — acknowledging byte n confirms everything before it. TCP also supports selective acknowledgement (SACK) as an option.
RetransmissionRecovers lost or discarded segments. Triggered in two ways — see below.

The two retransmission triggers

Retransmission timeout (RTO)Fast retransmit
TriggerThe retransmission timer expires before the segment is acknowledgedThree duplicate acknowledgements arrive for the same byte number
Why it worksNo news at all — the segment is presumed lostLater segments are arriving (each triggering a duplicate ACK for the still-missing byte), so the network is working and one specific segment is missing
SpeedSlow — must wait out the whole timeoutFast — acts as soon as the third duplicate arrives
Effect on congestion windowTreated as severe congestion — cwnd drops to 1 MSSTreated as mild — cwnd is halved (TCP Reno)

Why three duplicates and not one? Segments can arrive out of order through the network, and a single out-of-order arrival produces one duplicate ACK without anything being lost. Waiting for three makes reordering an unlikely explanation and loss the likely one — it trades a little delay for far fewer needless retransmissions.

Two rules examiners test directly

A corrupted segment is discarded, not negatively acknowledged. TCP has no NAK. Corruption therefore looks identical to loss, and is recovered the same way.
An out-of-order segment is buffered, not discarded (unlike Go-Back-N at the data link layer). The receiver holds it and sends a duplicate ACK for the byte still missing — which is exactly what triggers fast retransmit.

Check yourself

Retrieval practice

1. The sender's window size in TCP is:

The sender must satisfy both constraints, so it obeys whichever is tighter. If cwnd is the smaller, opening the receiver's window changes nothing — congestion is the binding limit.

2. rwnd = 8000, cwnd = 4000, and 2500 bytes are outstanding. The sender may now send:

Send window = min(8000, 4000) = 4000. Usable = 4000 − 2500 = 1500. Using rwnd instead of the minimum gives 5500, which is the standard error.

3. Nagle's algorithm sends the first piece of data:

Rule 1 sends the first byte at once so interactivity is not damaged; only afterwards does it accumulate until an ACK returns or an MSS is full. That is what makes it self-adjusting — fast networks get frequent small segments, slow ones get larger ones.

4. Silly window syndrome caused by the receiving application is solved by:

Nagle fixes the sender's version. Clark's solution — acknowledge but advertise zero until the buffer is half empty or an MSS fits — fixes the receiver's, as does delaying the acknowledgement. Pairing each cause with its own fix is what the question tests.

5. Fast retransmit is triggered by:

One duplicate could simply mean a segment arrived out of order. Three makes reordering unlikely and loss likely. Note also that TCP has no NAK at all — a corrupted segment is silently discarded and looks exactly like a lost one.

6. A TCP receiver that gets an out-of-order segment will:

TCP buffers out-of-order data rather than throwing it away, and repeats the acknowledgement for the still-missing byte. Those repeated ACKs are precisely the duplicates that trigger fast retransmit.

Recall without looking

Distinguish flow control from congestion control, with the formula.

Flow control protects the receiver and is driven by rwnd, advertised explicitly in the window size field. Congestion control protects the network and is driven by cwnd, computed by the sender from loss and timeouts. Send window = min(rwnd, cwnd).

Give three differences between TCP's sliding window and the data link layer's.

TCP's counts bytes rather than frames; its size is variable, changed by the receiver segment by segment; and its acknowledgements are cumulative by byte number rather than per frame.

Name the four regions of the sender's window.

Sent and acknowledged (may be purged); sent but not yet acknowledged (outstanding); not sent but sendable now (usable window); and not sendable until the window moves.

What are window opening, closing and shrinking?

Opening — the right edge moves right as the receiving application consumes data. Closing — the left edge moves right as data is acknowledged. Shrinking — the right edge moves left because a smaller window was advertised; strongly discouraged, since it can leave already-sent bytes outside the window.

Explain the zero-window deadlock and its fix.

A receiver advertising rwnd = 0 stops the sender. The later window update is a pure acknowledgement, which is not itself acknowledged and so is not retransmitted if lost — both sides would wait forever. The persistence timer fixes it: on expiry the sender sends a one-byte probe segment forcing the receiver to report its current window.

Define silly window syndrome and name both fixes.

Segments carrying only a few bytes of data with 40 bytes of TCP and IP headers, wasting bandwidth. Sender-caused: Nagle's algorithm — send the first piece immediately, then wait for an acknowledgement or a full MSS. Receiver-caused: Clark's solution — acknowledge but advertise zero until the buffer is half empty or an MSS fits — or delayed acknowledgement, bounded at about 500 ms.

Name TCP's three error-control tools.

Checksum (mandatory, 16 bits, over header, data and pseudoheader; corrupted segments are discarded), acknowledgement (cumulative, with optional SACK), and retransmission (on RTO expiry or on three duplicate acknowledgements).

Compare timeout retransmission with fast retransmit.

Timeout: the timer expires with no news, the segment is presumed lost, and it is treated as severe congestion — cwnd drops to 1 MSS. Fast retransmit: three duplicate ACKs show later segments are arriving, so only one is missing; it acts immediately and is treated as mild congestion — cwnd is halved in TCP Reno.
