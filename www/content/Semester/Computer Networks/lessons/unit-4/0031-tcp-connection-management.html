TCP Connection Management

The three-way handshake, data transfer, the four-way termination, half-close, and the state transition diagram. The handshake diagram alone is worth drawing until you can produce it in ninety seconds.

Exam strategy

"Explain TCP connection establishment and termination with a diagram" is a 10-mark question and among the most certain in the paper. Draw the timeline diagram — two vertical lines, arrows between them, each arrow labelled with its flags, seq and ack. That diagram carries most of the marks. Then the sub-questions: why three ways and not two, and why termination needs four.

Connection establishment: the three-way handshake

The client performs an active open; the server has already performed a passive open, meaning it is listening and prepared to accept connections.

The three segments 1. Client → Server: SYN
   flags: SYN  |  seq = x (the client's random ISN)  |  no data

2. Server → Client: SYN + ACK
   flags: SYN, ACK  |  seq = y (the server's own random ISN)  |  ack = x + 1  |  no data

3. Client → Server: ACK
   flags: ACK  |  seq = x + 1  |  ack = y + 1  |  may carry data
SegmentWhat it accomplishes
SYNThe client announces its ISN and requests the connection. It consumes one sequence number although it carries no data.
SYN + ACKA single segment doing two jobs: it acknowledges the client's SYN (ack = x + 1) and announces the server's own ISN in the other direction. It also consumes one sequence number.
ACKThe client acknowledges the server's SYN. Consumes no sequence number if it carries no data — and it may carry data, which is how the first request often rides along.
Why three and not two — the sub-question

TCP is full-duplex, so both directions must be initialised. Each side has to announce its own ISN and have it acknowledged — that is four events. The handshake is three segments rather than four only because the server combines its SYN and its ACK into one segment.

A two-way handshake would also be unsafe: a delayed duplicate SYN from an old connection could arrive later and open a connection the client never asked for, with the client unable to say so. The third segment is the client's confirmation that the connection is genuinely wanted now.

SYN flooding — the attack that follows from the handshake

Worth two lines, and often asked as a security sub-question. An attacker sends a stream of SYN segments with forged (spoofed) source addresses. For each, the server allocates resources for a half-open connection and sends SYN + ACK to an address that never replies. The server's connection table fills with half-open connections, and legitimate clients are refused — a denial-of-service attack.

The defence is SYN cookies: the server does not allocate resources on the SYN. Instead it encodes the connection state into the ISN it returns, and allocates only when the third segment comes back carrying that value.

Data transfer

Once established, data flows in both directions simultaneously. Points worth stating:

  • Piggybacking — an acknowledgement travelling in the direction of the data flow rides on a data segment rather than being sent separately, saving a segment.
  • Pure acknowledgement — when there is no data to send in that direction, an ACK-only segment is sent. It consumes no sequence number.
  • Delayed acknowledgement — TCP may wait briefly before acknowledging, hoping either to piggyback on outgoing data or to acknowledge two segments at once. The delay is bounded (typically 500 ms).
  • Pushing data — the PSH flag forces both the sending TCP to transmit immediately and the receiving TCP to deliver to the application immediately, instead of buffering.
  • Urgent data — the URG flag plus the urgent pointer marks bytes to be handed to the application out of band.

Connection termination: the four-way handshake

Because TCP is full-duplex, each direction must be closed separately. That is why termination takes four segments where establishment took three.

The four segments 1. Client → Server: FIN  (flags FIN, or FIN + ACK) — "I have no more data"
2. Server → Client: ACK — acknowledges the FIN; the server may still keep sending
3. Server → Client: FIN  (flags FIN + ACK) — "now I have no more data either"
4. Client → Server: ACK — acknowledges the server's FIN; the connection closes

FIN and FIN + ACK each consume one sequence number. The final ACK does not.

Why four segments, not three

The server's ACK and its own FIN cannot always be combined, because after acknowledging the client's FIN the server may still have data to send. Only when it has finished can it send its own FIN. If the server happens to have nothing left to send, the two can be combined and the termination becomes a three-way handshake — mention this; it is the follow-up question.

Half-close

One end can close its outgoing direction while continuing to receive. Normally the client does this: it sends all its data, sends FIN to say it has finished sending, but keeps reading the server's reply until the server closes too.

The standard example: a client sends a long list of records to a server for sorting. The client must signal that the list is complete — so it half-closes — but it still needs to receive the sorted result. Data can still flow from server to client after the client's half-close; only the client's own sending direction is shut.

The state transition diagram

Named states are frequently asked individually. The important ones:

FIN-WAIT-2Its FIN has been acknowledged; now waiting for the other side's FIN

LAST-ACKThe passive side has sent its own FIN and awaits the final acknowledgement
TIME-WAITThe active closer waits 2 × MSL before fully closing
TIME-WAIT and 2 × MSL — a favourite 3-mark question

MSL is the Maximum Segment Lifetime, the longest a segment can survive in the network (commonly taken as 30 seconds, 1 minute or 2 minutes). After sending its final ACK, the closing side waits 2 × MSL before releasing the connection, for two reasons:

  1. If the final ACK is lost, the other end will resend its FIN. Staying in TIME-WAIT means there is still someone there to re-acknowledge it. Without the wait, the resent FIN would meet a closed port and provoke an RST.
  2. To let all old segments of this connection die out, so that a new connection reusing the same port pair cannot receive a stray segment from the old one.

Retrieval practice

1. In the three-way handshake, the second segment carries which flags?

The handshake is three segments rather than four precisely because the server combines its own SYN with the ACK of the client's SYN. Both directions still get initialised — that is why two segments would not be enough.

2. A client sends SYN with seq = 3000. The server's SYN+ACK will carry ack =

SYN and FIN each consume one sequence number despite carrying no data. So the next byte expected is 3001, and that is what the acknowledgement names.

3. Connection termination normally needs four segments because:

TCP is full-duplex, so both directions close independently. The server acknowledges the client's FIN first, keeps sending if it has data, then sends its own FIN. If it has nothing left, the two can combine and termination becomes three-way.

4. The TIME-WAIT state lasts 2 × MSL so that:

If the final ACK is lost, the other end resends its FIN and needs someone still listening to re-acknowledge it. The wait also ensures no stray segment from this connection can reach a new connection reusing the same port pair.

5. In a half-close:

The classic case: a client sends a list for sorting, half-closes to signal the list is complete, then keeps reading until the sorted result has arrived. Data still flows server-to-client after the client's FIN.

6. SYN flooding works by:

The server allocates state and replies SYN+ACK to an address that never answers, so half-open connections accumulate and legitimate clients are refused. SYN cookies defend against it by encoding the state in the ISN and allocating nothing until the third segment returns.

Recall without looking

Describe the three-way handshake with flags and numbers.

1. Client → Server: SYN, seq = x (client's random ISN). 2. Server → Client: SYN + ACK, seq = y (server's ISN), ack = x + 1. 3. Client → Server: ACK, seq = x + 1, ack = y + 1, and it may carry data. SYN consumes one sequence number; a pure ACK consumes none.

Why three segments rather than two?

TCP is full-duplex, so both directions must be initialised — each side announces its ISN and has it acknowledged, which is four events compressed into three segments because the server combines SYN and ACK. A two-way handshake would also let a delayed duplicate SYN from an old connection open an unwanted connection.

Describe the four-way termination.

1. Client → Server: FIN. 2. Server → Client: ACK (the server may still send data). 3. Server → Client: FIN + ACK. 4. Client → Server: ACK. FIN consumes one sequence number; the final ACK does not. If the server has no data left, steps 2 and 3 combine into a three-way close.

What is a half-close, and give an example.

One end closes its sending direction while continuing to receive. A client sends a list of records for sorting and half-closes to signal the list is complete, then keeps receiving until the sorted result arrives.

Name the main TCP states.

CLOSED, LISTEN (server passive open), SYN-SENT (client), SYN-RCVD (server), ESTABLISHED (data transfer), FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, LAST-ACK, TIME-WAIT.

Explain TIME-WAIT and 2 × MSL.

MSL is the maximum segment lifetime. The active closer waits 2 × MSL after its final ACK so that (a) if that ACK was lost and the other end resends FIN, someone is still there to re-acknowledge it, and (b) all old segments of this connection die out before a new connection can reuse the same port pair.

Define piggybacking, pure acknowledgement and delayed acknowledgement.

Piggybacking — an acknowledgement rides on an outgoing data segment instead of being sent separately. Pure acknowledgement — an ACK-only segment, sent when there is no data going that way; it consumes no sequence number. Delayed acknowledgement — TCP waits briefly (bounded, typically 500 ms) hoping to piggyback or to acknowledge two segments at once.

What is SYN flooding and how is it defended against?

An attacker sends SYNs with spoofed source addresses; the server allocates resources and replies SYN+ACK to addresses that never answer, filling its table with half-open connections and denying service to real clients. SYN cookies defend against it: the server encodes connection state into the ISN it returns and allocates resources only when the third segment comes back carrying that value.
