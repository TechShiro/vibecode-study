The transport layer on one page. Three diagrams carry this unit: the TCP header, the three-way handshake, and the congestion-window graph. If you can draw all three from memory you have most of the marks.

Where the marks are

In order of certainty: TCP vs UDP table · three-way handshake diagram · congestion control graph · TCP header · silly window syndrome · SCTP's two features.

Transport layer basics

The three deliveries Data link → hop to hop (MAC) · Network → host to host (IP) · Transport → process to process (ports)

Port = 16 bits, 0–65,535. Socket address = IP + port. A connection = the pair of socket addresses (which is how one server holds thousands of connections on port 80).

Ranges: well-known 0–1023 · registered 1024–49151 · ephemeral 49152–65535 (the client side).

Ports: FTP 20/21 · SSH 22 · TELNET 23 · SMTP 25 · DNS 53 · DHCP 67/68 · TFTP 69 · HTTP 80 · POP3 110 · IMAP4 143 · SNMP 161 · HTTPS 443.

Multiplexing = many processes → one network layer (sender). Demultiplexing = one network layer → many processes by destination port (receiver).

Flow vs congestion control

Flow control protects the RECEIVER (rwnd, advertised in the header). Congestion control protects the NETWORK (cwnd, computed by the sender). Send window = min(rwnd, cwnd).

UDP 8-byte header

UDP header — four fields, 2 bytes each | Source Port (16) | Destination Port (16) | Total Length (16) | Checksum (16) |
Total length = header + data; minimum 8, maximum 65,535

Pseudoheader (12 bytes, never transmitted): source IP, destination IP, zeros, protocol 17, UDP length. It lets the receiver check the datagram reached the right host and was meant for UDP. Checksum optional in IPv4, mandatory in IPv6.

UDP is used by: DNS, DHCP, TFTP, SNMP, RIP, VoIP, streaming, gaming — and anything multicast or broadcast, since TCP cannot do either.

The "why unreliable?" line: for real-time traffic a late packet is worse than a lost one — a retransmitted 20 ms of audio arrives after the moment it was needed.

TCP header 10 marks

20 to 60 bytes, 4 bytes per row | Source Port (16) | Destination Port (16) |
| Sequence Number (32) |
| Acknowledgement Number (32) |
| HLEN (4) | Reserved (6) | Flags (6) | Window Size (16) |
| Checksum (16) | Urgent Pointer (16) |
| Options + Padding (0–40) |
The numbering rules Sequence number = number of the FIRST byte in this segment
Acknowledgement number = number of the NEXT byte expected (cumulative)
TCP numbers bytes, not segments. ISN is random (old-segment confusion + hijacking).

Flags: URG, ACK, PSH, RST, SYN, FIN — "Unskilled Attackers Pester Real Security Folks."
URG = urgent pointer valid · ACK = ack number valid · PSH = deliver to app now · RST = abort · SYN = synchronise · FIN = finished.

SYN and FIN each consume one sequence number; a pure ACK consumes none.

HLEN in 4-byte words: 5 = 20 bytes, 15 = 60 bytes. Window size = rwnd, max 65,535 (hence the window scale option). Checksum mandatory, pseudoheader protocol 6.

Connection management 10 marks

Three-way handshake 1. C→S  SYN, seq = x
2. S→C  SYN + ACK, seq = y, ack = x+1
3. C→S  ACK, seq = x+1, ack = y+1 (may carry data)
Four-way termination 1. FIN →   2. ACK ← (server may still send)   3. FIN ←   4. ACK →

Why three, not two: TCP is full-duplex so both directions need initialising; the server combines its SYN and ACK. A two-way handshake would also let a delayed duplicate SYN open an unwanted connection.

Why four to close: each direction closes separately, and the server may still have data after acknowledging the FIN. If it has none, steps 2 and 3 combine → three-way close.

Half-close: one end stops sending but keeps receiving (client sends a list for sorting, then reads the result).

States: CLOSED, LISTEN, SYN-SENT, SYN-RCVD, ESTABLISHED, FIN-WAIT-1/2, CLOSE-WAIT, LAST-ACK, TIME-WAIT.

TIME-WAIT = 2 × MSL, for two reasons: a lost final ACK can be re-answered when the FIN is resent, and all old segments die out before the port pair is reused.

SYN flooding: spoofed SYNs fill the table with half-open connections → DoS. Fixed by SYN cookies (state encoded in the ISN, allocate only on the third segment).

Flow and error control

Silly window syndrome Segments with a few data bytes and 40 bytes of headers.
Sender-caused → Nagle's algorithm: send the first piece at once, then wait for an ACK or a full MSS.
Receiver-caused → Clark's solution (ACK but advertise zero until the buffer is half empty or an MSS fits) or delayed ACK (bounded, ~500 ms).

Window regions: sent+acked · sent-not-acked (outstanding) · usable · not sendable. Usable = min(rwnd,cwnd) − outstanding.

Zero-window deadlock → the persistence timer sends a one-byte probe.

Error control = checksum + acknowledgement + retransmission. There is no NAK — a corrupted segment is silently discarded and looks like a loss. Out-of-order segments are buffered (unlike Go-Back-N).

Fast retransmit = 3 duplicate ACKs. Why three? One duplicate could just be reordering.

Congestion control draw the graph

The three phases Slow start: cwnd = 1, +1 MSS per ACK → doubles every RTT, until cwnd = ssthresh
Congestion avoidance: +1 MSS per RTT → linear
Detection: timeout → ssthresh = cwnd/2, cwnd = 1, slow start
                 3 dup ACKs → ssthresh = cwnd/2, cwnd = cwnd/2, stay in avoidance (Reno)

AIMD = Additive Increase, Multiplicative Decrease. "Slow start" is a misnomer — the growth is exponential; only the starting point (1 MSS) is small.

Tahoe vs Reno: identical on a timeout. On 3 duplicate ACKs, Tahoe drops to 1, Reno halves and stays in congestion avoidance (fast recovery).

Trace trap: in slow start, never double past ssthresh — stop at it and switch phase. ssthresh is computed from cwnd at the moment of loss.

Sample trace (ssthresh 8, timeout at RTT 8): 1, 2, 4, 8, 9, 10, 11, 12 → timeout → ssthresh 6, cwnd 1 → 1, 2, 4, 6, 7.

The graph must show: exponential rise · dashed ssthresh line · linear rise · vertical drop · new ssthresh · the repeating sawtooth.

Timers, options, SCTP

The four timers Retransmission (RTO) · Persistence (zero-window probe) · Keepalive (~2 h idle) · TIME-WAIT (2×MSL)
RTO calculation First: RTTS = RTTM, RTTD = RTTM/2
Then: RTTS = (7/8)·old + (1/8)·RTTM  ·  RTTD = (3/4)·old + (1/4)·|RTTS − RTTM|
RTO = RTTS + 4 × RTTD  — use the NEW RTTS in the RTTD line

Karn's algorithm: after a retransmission you cannot tell which transmission an ACK answers, so exclude retransmitted segments from RTT measurement — paired with exponential backoff (double the RTO each retransmission).

Options: EOP, NOP, MSS (announced in the SYN, not negotiated, default 536), window scale (16-bit window caps at 65,535 — too small for a large bandwidth-delay product), timestamp (RTT + PAWS), SACK-permitted, SACK.

Final scan — ten minutes before you go in

  1. Transport = process to process, via ports. Socket = IP + port; a connection is the pair.
  2. Send window = min(rwnd, cwnd). rwnd protects the receiver, cwnd the network.
  3. UDP header 8 bytes, four fields. TCP header 20–60 bytes. Pseudoheader protocol 17 / 6.
  4. Seq = first byte in the segment. ACK = next byte expected. SYN and FIN consume one each.
  5. Handshake: SYN(x) → SYN+ACK(y, x+1) → ACK(x+1, y+1). Close takes four; TIME-WAIT is 2×MSL.
  6. Nagle fixes the sender's silly window; Clark or delayed ACK fixes the receiver's.
  7. Fast retransmit = 3 duplicate ACKs. TCP has no NAK; out-of-order segments are buffered.
  8. Slow start doubles per RTT; congestion avoidance adds 1 per RTT. Never double past ssthresh.
  9. Timeout → cwnd = 1. Three dup ACKs → cwnd = cwnd/2 in Reno, cwnd = 1 in Tahoe.
  10. RTO = RTTS + 4·RTTD. SCTP = multi-homing + multi-streaming + cookie handshake.
  11. Congestion Control: Open-loop (preventive: retransmission/discard policies) vs Closed-loop (reactive: backpressure, choke packet, BECN/FECN).
  12. Traffic Shaping: Leaky Bucket (strictly constant rate; drops overflow data) vs Token Bucket (bursts allowed up to capacity $C$; drops overflow tokens).
  13. QoS & Scheduling: Delay, Jitter, Reliability, Bandwidth. Weighted Fair Queuing (WFQ) prevents starvation by weighted bandwidth allocation.
