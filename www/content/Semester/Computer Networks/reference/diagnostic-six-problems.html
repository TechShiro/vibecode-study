Six Problems — a Diagnostic

Not practice. This is a measurement: six problems, one per numerical topic, each chosen so that a wrong answer fails in a specific way that names a specific gap. Work them cold, then open the solutions.

How to use this
  1. Work all six on paper first, without opening anything. Do not look at the lessons. If you get stuck, write down where you got stuck — that is data too.
  2. Then open each solution and compare, not just the final answer but every intermediate value. The intermediate values are what identify the gap.
  3. Read the diagnostic table under each solution. It maps particular wrong answers to particular misunderstandings.
  4. Tell me which ones failed and what you actually got. That is what I need to aim any drill sheet at real weaknesses instead of guesses.

Printing: the solutions are hidden when this page prints, so you can print it as a blank problem sheet.

Time: about 60–75 minutes for all six. There is no partial credit here and no marks — a wrong answer is more useful to me than a right one, so do not look anything up to rescue a question.

Dividend = 11010110110000 (14 bits).

Diagnostic

If you got…It means
A remainder with 5 bits, or 3You appended the wrong number of zeros. The rule: divisor length − 1, and the remainder must have exactly that many bits. This is the fastest self-check in the whole topic.
The right method but a different remainderAn alignment slip. The commonest cause is forgetting to XOR with 00000 when the leading bit is 0 and instead skipping straight to the next 1 — which loses a bring-down. Steps 3–6 and 8 above are all leading-zero steps; check yours has ten steps in total.
You used subtraction with borrowsCRC division is mod 2: XOR only, no borrows and no carries. If you found yourself borrowing, that is the whole problem.
Correct remainder but you appended it rather than replacing the zerosThe codeword is dataword + CRC, replacing the appended zeros — still 14 bits, not 18.
You skipped part (d)Not a knowledge gap, but a marks gap: the receiver-side check is usually worth a mark and it catches your own arithmetic errors.
Problem 2 — Hamming code  ·  solution and diagnostic

(a) Redundancy bits: 2r ≥ m + r + 1 with m = 7.
r = 3 → 8 ≥ 11 ✗  ·  r = 4 → 16 ≥ 12 ✓  →  r = 4, codeword is 11 bits.

(b) Layout. Parity at positions 1, 2, 4, 8; data 1 0 0 1 1 0 1 fills 3, 5, 6, 7, 9, 10, 11:

Position1234567891011
Bitp1p21p4001p8101

p1 covers 1,3,5,7,9,11 → data 1,0,1,1,1 → sum 4, even → p1 = 0
p2 covers 2,3,6,7,10,11 → data 1,0,1,0,1 → sum 3, odd → p2 = 1
p4 covers 4,5,6,7 → data 0,0,1 → sum 1, odd → p4 = 1
p8 covers 8,9,10,11 → data 1,0,1 → sum 2, even → p8 = 0

Codeword = 0 1 1 1 0 0 1 0 1 0 1 = 01110010101

(c) Bit 9 flips from 1 to 0: received = 01110010001

(d) Recompute each check (1 if the count of 1s is odd):

c1: positions 1,3,5,7,9,11 = 0,1,0,1,0,1 → three 1s, odd → 1
c2: positions 2,3,6,7,10,11 = 1,1,0,1,0,1 → four 1s, even → 0
c4: positions 4,5,6,7 = 1,0,0,1 → two 1s, even → 0
c8: positions 8,9,10,11 = 0,0,0,1 → one 1, odd → 1

Syndrome c8c4c2c1 = 1001 = 9 → bit 9 is in error

(e) Flip position 9 back to 1 → 01110010101. Removing positions 1, 2, 4, 8 leaves positions 3,5,6,7,9,10,11 = 1001101. ✓

Diagnostic

If you got…It means
Syndrome 9 — correctYou read it c8c4c2c1, highest check as the most significant bit. Good.
Syndrome 1001 read as 9 but you wrote bit 1, or you got syndrome 9 reversedYou read the syndrome backwards (c1c2c4c8). This is the classic Hamming error and it silently produces a plausible-looking wrong position every time.
r = 3You stopped at the first r you tried instead of testing upward. 2³ = 8 is not ≥ 7+3+1 = 11. Test r = 1, 2, 3… until the inequality holds.
Parity bits in the wrong positionsParity goes at powers of two — 1, 2, 4, 8 — counting from 1 at the left, not from 0. Data fills everything else in order.
Right positions, wrong coverageThe rule: p covers every position whose number has p's bit set. Equivalently — p1: check 1 skip 1 · p2: check 2 skip 2 · p4: check 4 skip 4 · p8: check 8 skip 8. Note p8 covers 8–11 only, because the codeword stops at 11.
You included the parity bit itself when summingWhen computing p, sum only the data positions it covers and set p to make the total even. When checking at the receiver, include the parity bit — a correct group then sums to even.

Diagnostic

If you got…It means
Blocks that overlap, or a /24 that will not fitYou allocated in the order the question listed them rather than largest first. This is the single rule that makes VLSM work, and the error is unrecoverable once made — the whole plan has to be redone.
Department A given a /25You sized on 200 ≤ 128 + something, or forgot the −2. 200 hosts needs 202 addresses minimum, so 128 is short and 256 is the smallest power of two that works.
Range for A ending at 172.16.0.254 as the broadcastYou confused the last usable host with the broadcast. Broadcast is the last address of the block (.255); last host is one below it (.254).
You thought /22 spans only 172.16.0.0–172.16.0.255The prefix falls inside the third byte. Block size there is 256 − 252 = 4, so the third byte runs 0–3 and the block is four /24s wide.
Links given a /29 or largerA router-to-router link needs exactly two addresses, and /30 is the smallest block that provides them. /29 works but wastes four addresses on every link.
Correct blocks, no verification lineNot a knowledge gap. But the sum-to-block-size check catches your own errors and is usually worth a mark — always write it.
Problem 4 — Fragmentation  ·  solution and diagnostic

(a) Data per fragment. Each fragment needs its own 20-byte header, so the payload space is 1400 − 20 = 1380 bytes.
But 1380 ÷ 8 = 172.5 — not a whole number. Round down to the nearest multiple of 8: 1376 (1376 ÷ 8 = 172 ✓).

(b) Number of fragments. Total data = 5000 − 20 = 4980 bytes.
4980 ÷ 1376 = 3.62 → 4 fragments (three full, one partial).

(c) The fragments:

Offsets: 0÷8 = 0, 1376÷8 = 172, 2752÷8 = 344, 4128÷8 = 516 — each rising by 172.
Fragment 4's data = 4980 − (3 × 1376) = 4980 − 4128 = 852.

Total bytes transmitted: 4 headers × 20 + 4980 data = 5060 bytes, against the original 5000 — 60 bytes of extra overhead. Fragmentation always costs.

Diagnostic

If you got…It means
1380 bytes per fragment, offsets 0, 172.5, …This is the trap this problem exists for. The offset field counts in 8-byte units, so every fragment except the last must carry a multiple of 8 data bytes. Round down, never up.
1400 bytes per fragmentYou forgot that each fragment carries its own 20-byte header. MTU is the limit on the whole fragment, not on its payload.
Offsets 0, 1376, 2752, 4128You reported byte positions instead of dividing by 8. The offset is measured in 8-byte units — that is what lets a 13-bit field address a 65,535-byte datagram.
Fragment 4 with MF = 1, or all four with MF = 1MF means "more fragments follow". Only the last fragment has MF = 0.
Data bytes summing to 5000You used the total length rather than the payload. Data = 5000 − 20 = 4980; the four fragment payloads must sum to 4980, not 5000.
3 fragmentsYou rounded 3.62 down. The remainder still has to travel, so always round the fragment count up — even though the fragment size rounds down. The two directions are opposite and that is easy to conflate.

Under TCP Tahoe, rounds 8–12 differ. Tahoe treats three duplicate ACKs exactly like a timeout:

ssthresh = 18/2 = 9, but cwnd = 1 and back to slow start.
RTT 8 = 1 · RTT 9 = 2 · RTT 10 = 4 · RTT 11 = 8 · RTT 12 = 9 (doubling to 16 would overshoot ssthresh 9, so cap and switch to congestion avoidance).

That divergence — Reno at 9, 10, 11, 12 versus Tahoe at 1, 2, 4, 8 — is fast recovery.

Diagnostic

If you got…It means
RTT 5 = 16 then RTT 6 = 32You doubled past ssthresh. Slow start stops at ssthresh and switches phase; it never overshoots. The same trap is set again at RTT 15, where doubling 4 would give 8 but ssthresh is 6.
RTT 15 = 8Same error, second occurrence. If you caught it at RTT 5 but not at RTT 15, the rule is not yet automatic.
RTT 8 = 1You treated the duplicate ACKs as a timeout — that is Tahoe behaviour, not Reno. Reno's whole contribution is distinguishing mild loss (later segments are arriving) from severe loss (nothing is).
ssthresh = 8 after round 7You halved the wrong value. ssthresh is computed from cwnd at the moment of loss — 18 here, not 16 (the old ssthresh) and not 17.
RTT 6 = 32 or +2 per roundCongestion avoidance adds 1 MSS per round-trip time, not per acknowledgement and not multiplicatively.
Reno and Tahoe traces identicalYou applied the same rule to both loss events. They differ only on three duplicate ACKs; on a timeout both drop to 1.
You put the drop in round 7 rather than 8A convention question, not an error, if you stated it. The loss is detected at the end of round 7, so the reduced window is what round 8 uses. Say which convention you are using and you keep the marks.
Problem 6 — RSA  ·  solution and diagnostic

(a) n = p × q = 11 × 13 = 143
(b) φ(n) = (p − 1)(q − 1) = 10 × 12 = 120
Check e: gcd(7, 120) = 1 ✓

(c) Find d with 7d ≡ 1 (mod 120).
7 × 103 = 721, and 721 = (6 × 120) + 1 = 720 + 1 ✓  →  d = 103

(d) Public key = (7, 143)  ·  Private key = (103, 143)

(e) Encrypt M = 9: C = 97 mod 143, by square and multiply.
92 = 81
94 = 812 = 6561; 6561 − (45 × 143 = 6435) = 126
7 = 4 + 2 + 1, so 97 = 94 × 92 × 91 = 126 × 81 × 9
126 × 81 = 10206; 10206 − (71 × 143 = 10153) = 53
53 × 9 = 477; 477 − (3 × 143 = 429) = 48

Ciphertext C = 48

(f) Decrypt: M = 48103 mod 143.
482 = 2304 → 2304 − (16 × 143 = 2288) = 16
484 = 162 = 256 → 256 − 143 = 113
488 = 1132 = 12769 → 12769 − (89 × 143 = 12727) = 42
4816 = 422 = 1764 → 1764 − (12 × 143 = 1716) = 48
4832 = 482 = 16  ·  4864 = 162 = 256 → 113

103 = 64 + 32 + 4 + 2 + 1, so
48103 = 113 × 16 × 113 × 16 × 48  (mod 143)
113 × 16 = 1808 → 92  |  92 × 113 = 10396 → 100  |  100 × 16 = 1600 → 27  |  27 × 48 = 1296 → 9

Decrypted M = 9 — the original plaintext, verified. ✓

Diagnostic

If you got…It means
φ(n) = 143 or used n where φ belongsYou confused n with φ(n). n = pq is the modulus used in the encryption arithmetic; φ(n) = (p−1)(q−1) is used only to find d. Mixing them makes every later step wrong.
d = 7, or no d foundYou need e × d ≡ 1 mod φ, not mod n. Try multiples of 7 until one is 1 more than a multiple of 120: 7×103 = 721 = 720 + 1.
You tried to compute 97 in full (4,782,969)It works here but will not on any larger exponent — and 48103 is a 173-digit number. Reduce mod n at every step. That is the method being tested, not the answer.
Right method, wrong CAn arithmetic slip in one of the mod reductions. Check each line by confirming the result is less than 143 — if any intermediate exceeds n, you did not reduce.
You did not decrypt to checkNot a knowledge gap, but you gave up your own error detection. If decrypting does not return 9, something upstream is wrong — and the verification is usually worth a mark.
Correct throughoutThen also be able to say why it is secure: recovering d needs φ(n), which needs p and q, which means factoring n. That is the theory half of the question.
