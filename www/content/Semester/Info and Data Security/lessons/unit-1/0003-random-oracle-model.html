The Random Oracle Model

The ideal hash function that real hash functions are measured against — how the oracle behaves, the birthday problems that follow from it, the three attacks on hash functions, and why 512-bit digests exist.

Exam strategy

A short-note or 5-mark question, almost always phrased “Explain the Random Oracle Model” or “What is an ideal hash function?” The full marks come from three things: the oracle’s three rules, the “it is a theoretical model, no real function achieves it” caveat, and the birthday attack bound 2n/2 that comes out of it. It is also the topic students skip, which makes it cheap marks.

What the model is

Introduced by Bellare and Rogaway in 1993, the Random Oracle Model (ROM) is an ideal mathematical model of a hash function. It does not describe any real algorithm. It describes the behaviour a perfect hash function would have, so that the security of a scheme can be proved against that ideal and real hash functions can be judged by how close they come.

The oracle, described exactly A random oracle is an imaginary black box holding a table of pairs (message, digest).
Given a message, it looks in the table:
• if the message is there, it returns the digest already recorded;
• if it is not, it generates a truly random n-bit digest, records the new pair, and returns it.

The three rules to state in the answer

RuleStatementConsequence
1. Deterministic / consistentThe same message always receives the same digest — the oracle never contradicts an earlier answerVerification is possible at all
2. Uniformly randomA new message receives a digest chosen uniformly at random from all 2n possible valuesThe digest reveals nothing about the message; every output is equally likely
3. No structure to exploitThe only way to learn H(M) is to query the oracle — the digest cannot be computed, guessed or shortcutEvery attack degenerates into brute-force search, so security is measured purely by the number of queries
Why the model exists at all

If the only attack is guessing, the strength of the hash can be calculated rather than guessed at. A scheme is then proved secure “in the random oracle model”, and in practice the oracle is replaced by a real hash such as SHA-512. RSA-OAEP, RSA-PSS, DSS and many key-exchange protocols are proved this way.

The limitation — state it, it is worth a mark

No real hash function is a random oracle. A real function is a fixed, published algorithm with internal structure; the oracle is an infinite random table. Canetti, Goldreich and Halevi showed in 1998 that schemes exist which are provably secure in the ROM yet insecure with every real hash function. So a ROM proof is strong evidence, not a guarantee. That caveat is the standard closing sentence of this answer.

The pigeonhole principle, restated here

The oracle assigns random n-bit digests to infinitely many messages, so collisions are certain to exist — there are 2n pigeonholes and unlimited pigeons. The model does not prevent collisions; it makes the search for one a pure counting problem. That counting problem is the birthday problem.

The birthday problems

Forouzan sets out four related questions. Each corresponds to one attack on a hash function, and the mapping is the reason this section sits in the syllabus next to the oracle.

#Birthday problemHash attack it modelsTrials needed (N = 2n possible digests)
1How many people before one of them shares your birthday?Preimage attack≈ N
2How many people before one shares the birthday of a specified person?Second preimage attack≈ N
3How many people before any two share a birthday?Collision attack (birthday attack)≈ √N = 2n/2
4Two groups — how many in each before someone in one shares with someone in the other?Meet-in-the-middle / multiple-message attack≈ √N in each group
The birthday paradox, in the one sentence examiners want

Finding a match to a particular value is far harder than finding some match among many values — in a room of only 23 people there is already a better-than-even chance that two share a birthday, though the chance any one of them shares yours is tiny. Applied to hashing: a collision costs the square root of the effort of a preimage, so an n-bit digest gives only n/2 bits of collision security.

The classic collision-attack story

Worth two lines in an answer, because it shows why collision resistance is the property that actually matters. Eve prepares two contracts — one favourable to Bob, one fraudulent — and, by varying spaces, synonyms and invisible formatting, tunes them until both have the same digest. She gets Bob to sign the harmless one. The signature, being over the digest, is equally valid on the fraudulent one, which she then produces in court. Note that Bob’s key was never broken; only the hash was.

How the digest length is chosen

The design rule that follows from the birthday bound Security against collisions = n/2 bits for an n-bit digest.
To resist an attacker able to perform 280 operations, n must be at least 160.
Hence: MD4 and MD5 at 128 bits give only 64-bit collision security — broken.
SHA-1 at 160 bits gives 80 bits — deprecated. SHA-512 and Whirlpool at 512 bits give 256.

This single line explains the whole history of Lessons 5, 6 and 7: digest lengths grew because the birthday bound halves them. If a question asks why MD5 is no longer used, this is the answer — not that the algorithm is slow or badly designed, but that 264 became reachable.

Recall without looking

Define the Random Oracle Model.

An ideal model of a hash function, introduced by Bellare and Rogaway in 1993. The oracle holds a table of message–digest pairs: a repeated message gets the digest already recorded, and a new message gets a freshly chosen uniformly random n-bit digest which is then recorded. It models the behaviour a perfect hash function would have.

State the three rules the oracle obeys.

It is consistent and deterministic — the same message always gets the same digest. Its output for a new message is uniformly random over all 2ⁿ values, revealing nothing about the message. It has no exploitable structure, so the only way to learn a digest is to query it, which makes brute force the only attack.

Why is the model used, and what is its limitation?

It lets the security of a scheme be calculated in terms of the number of oracle queries, which is how RSA-OAEP, RSA-PSS and DSS are proved secure. Its limitation is that no real hash function is a random oracle — real functions have fixed public structure — and schemes exist that are secure in the model yet insecure with any real hash, so a ROM proof is strong evidence, not a guarantee.

State the four birthday problems and the attack each models.

Someone sharing your birthday — preimage attack, effort N. Someone sharing a specified person’s birthday — second preimage attack, effort N. Any two people sharing a birthday — collision or birthday attack, effort √N. A match between two groups — meet-in-the-middle attack, about √N in each group. Here N = 2ⁿ for an n-bit digest.

Explain the birthday attack on a digital signature.

The attacker prepares two versions of a document, one harmless and one fraudulent, and varies wording or spacing until both hash to the same digest — costing only 2^(n/2) work. The victim signs the harmless version; since the signature is over the digest, it verifies equally on the fraudulent version, which the attacker then presents. The key is never broken, only the hash.

How does the birthday bound decide digest length?

An n-bit digest gives only n/2 bits of collision security, so n must be at least twice the work factor required. 128-bit MD4 and MD5 give 64 bits and are broken; 160-bit SHA-1 gives 80 and is deprecated; 512-bit SHA-512 and Whirlpool give 256 bits and are considered secure.
