Message Authentication: MAC, HMAC and CMAC

Adding a secret key to the digest so it can travel the insecure channel — the MAC and its security requirements, the nested construction HMAC with its ipad and opad, and the block-cipher construction CMAC with its two subkeys.

Exam strategy

The highest-yield lesson in Unit I — expect a full 10-mark question. The three that recur: “What is a MAC? Explain message authentication with a diagram”, “Explain HMAC with its block diagram” (the ipad/opad formula is the mark-earner), and “Differentiate HMAC and CMAC” or “MAC vs MDC vs digital signature”. What message authentication adds

A keyless digest tells the receiver the message did not change. It does not tell them who sent it. Message authentication assures the receiver of both the integrity of the message and the identity of its source, and it does so without needing a separate safe channel — because the digest itself is now protected by a secret key.

MAC — Message Authentication Code

Definition and transmission MAC = C(K, M)  —  a fixed-length tag computed from message M under shared secret key K.

The sender transmits M ‖ MAC over the insecure channel.
The receiver recomputes MAC′ = C(K, M′) on the message received and compares.
MAC′ = MAC → accept (unchanged, and from the holder of K); otherwise reject.

Also called a cryptographic checksum or a keyed hash function. Two things to say about it that examiners look for: the MAC function need not be reversible — it is a many-to-one function like a hash, not a cipher — and the message itself is sent in the clear unless confidentiality is separately arranged.

What the receiver is actually assured of

NOT non-repudiationThe key is shared — either party could have produced the tag, so the receiver cannot prove authorship to a judge. Only a digital signature can.

Security requirements of a MAC function

  • Knowing M and C(K, M) must not let an attacker construct a valid pair for any other message — the essential forgery requirement.
  • MAC values must be uniformly distributed: for a randomly chosen pair of messages, the chance of equal MACs must be 2−n for an n-bit tag.
  • The MAC must depend equally on all bits of the message, so no part can be altered freely.
  • The key space must be large enough that brute-force key search is infeasible.

Nested MAC and the road to HMAC

The obvious keyed hash — MAC = H(K ‖ M), prepending the key to the message — is insecure. Because iterated hashes chain block by block, an attacker who sees the digest of K ‖ M can extend the message and compute the digest of K ‖ M ‖ extra without knowing K. This is the length-extension attack, and it is the reason HMAC exists.

The fix is a nested MAC: hash once with the key, then hash the result again with the key. The outer hash hides the internal chaining state, so extension is impossible. HMAC is the standardised nested MAC.

HMAC — Hash-based MAC

Defined in RFC 2104, adopted by FIPS 198, and used inside IPsec, SSL/TLS and SET. Its design goal was to reuse an existing hash function as a black box, so that a broken hash can be swapped out without redesigning the MAC.

The HMAC formula — memorise this line HMAC(K, M) = H[ (K+ ⊕ opad) ‖ H[ (K+ ⊕ ipad) ‖ M ] ]

ipad = 00110110 (0x36) repeated to one block  ·  opad = 01011100 (0x5C) repeated to one block
K+ = the secret key padded with 0s on the left to the hash’s block size b
The steps, as the block diagram reads top to bottom

1. Take the secret key K. If it is shorter than the block size b, pad it on the left with zeros to get K+. If it is longer than b, hash it first and then pad that digest to b bits.

2. XOR K+ with ipad to produce the b-bit block Si.

3. Prepend Si to the message M.

4. Hash it: inner digest = H(Si ‖ M), of length n bits.

5. Pad the inner digest out to b bits.

6. XOR K+ with opad to produce So.

7. Prepend So to the padded inner digest.

8. Hash again: HMAC = H(So ‖ inner digest) — the n-bit tag.

Sizes to quote

b is the hash’s block size: 512 bits for MD5, SHA-1 and SHA-256; 1024 bits for SHA-512. n is the digest size: 128, 160, 256 or 512. The tag may be truncated to the leftmost bits (HMAC-SHA-1-96 in IPsec, for instance), which shortens the tag without weakening the key.

Why ipad and opad differ

They differ in half their bits. XORing K with two very different constants produces two pseudorandom keys from one key, so the inner and outer hashes behave independently. That is the whole reason for the two constants, and it is the standard follow-up question after “write the HMAC formula”.

Efficiency and security of HMAC

  • Only two extra block computations beyond hashing the message itself — one for Si, one for So. For long messages HMAC costs essentially the same as a plain hash.
  • Those two blocks can be precomputed and cached while the key is unchanged.
  • The security of HMAC is provably related to the security of the underlying hash: to forge an HMAC, an attacker must either find collisions in the hash while not knowing the key, or break the compression function used with a secret IV. Even MD5’s collision weakness does not directly break HMAC-MD5.
  • Any hash can be plugged in — HMAC-MD5, HMAC-SHA-1, HMAC-SHA-512.

CMAC — Cipher-based MAC

Where HMAC reuses a hash, CMAC reuses a block cipher — useful on devices that already implement AES and have no hash hardware. It is standardised in NIST SP 800-38B and uses AES or triple-DES in CBC mode.

The problem CMAC fixes

The older DAA (Data Authentication Algorithm), also called CBC-MAC, simply runs the message through CBC mode with an IV of zeros and keeps the last ciphertext block as the tag. It is secure only for messages of a fixed length. With variable-length messages an attacker who knows the tag of a one-block message X can forge the tag of the two-block message X ‖ (X ⊕ T) without the key. CMAC removes that weakness by XORing a derived subkey into the final block.

CMAC, step by step

1. Derive the subkeys. Encrypt an all-zero block: L = E(K, 0b). Then derive K1 and K2 = 2K1 by multiplication by x in the finite field GF(2b) — in practice a left shift by one bit, with a conditional XOR of a constant (0x87 for the 128-bit AES block) when the bit shifted out is 1.

2. Split the message into b-bit blocks M1…Mn.

3. Treat the last block. If it is a complete block, XOR it with K1. If it is incomplete, pad it with a 1 followed by 0s and XOR it with K2.

4. Run CBC: Ci = E(K, Ci−1 ⊕ Mi), starting from an all-zero IV.

5. Output the leftmost s bits of the final ciphertext block as the CMAC tag.

The single idea to remember: two subkeys, one for a full final block and one for a padded final block — that is what makes the length of the message unforgeable.

Check yourself

1. A MAC does not provide non-repudiation because:

Shared-key symmetry is the reason. A judge cannot tell sender from receiver, so authorship cannot be proved — that needs the asymmetry of a private key.

2. In HMAC, the key is XORed with two different constants, ipad and opad, in order to:

0x36 and 0x5C differ in half their bits, so the inner and outer hashes effectively use different keys. Padding to block size is done separately, by K⁺.

3. MAC = H(K ‖ M), with the key simply prepended, is insecure because:

The length-extension attack on Merkle–Damgård hashes. Hashing a second time with the key — the nested construction of HMAC — closes it.

4. CMAC derives two subkeys K₁ and K₂ so that:

This is exactly the weakness of plain CBC-MAC (DAA) that CMAC repairs: with variable-length messages, tags could otherwise be forged by concatenation.

5. For SHA-512, the block size b used to pad the HMAC key is:

K⁺, ipad and opad are all one *block* long, and SHA-512 processes 1024-bit blocks. Confusing block size with digest size is the classic slip here.

6. Which pairing of construction and base primitive is correct?

The H in HMAC is Hash; the C in CMAC is Cipher. That mnemonic answers most questions on this pair.

Recall without looking

Define a MAC and describe how sender and receiver use it.

A MAC is a fixed-length tag MAC = C(K, M) computed from the message under a secret key shared by the two parties. The sender transmits M along with the MAC; the receiver recomputes the MAC on the message received using the same key and compares. A match means the message is unchanged and came from the holder of the key.

What does a MAC assure the receiver of, and what does it not?

It assures integrity, source authentication, and — if a sequence number is included — correct ordering with no replay or deletion. It does not provide confidentiality, since the message travels in the clear, and it does not provide non-repudiation, because the key is shared and either party could have produced the tag.

State the security requirements of a MAC function.

Knowing a message and its MAC must not allow a valid MAC to be constructed for any other message; MAC values must be uniformly distributed, so a random pair collides with probability 2⁻ⁿ; the MAC must depend equally on all bits of the message; and the key space must be large enough to defeat brute-force search.

Write the HMAC formula and name its constants.

HMAC(K, M) = H[(K⁺ ⊕ opad) ‖ H[(K⁺ ⊕ ipad) ‖ M]], where ipad is the byte 0x36 repeated to one block, opad is 0x5C repeated to one block, and K⁺ is the key padded with zeros to the hash’s block size b — 512 bits for MD5 and SHA-1, 1024 bits for SHA-512.

Give the eight steps of HMAC.

Pad the key to block size (hashing it first if it is too long); XOR it with ipad to get S_i; prepend S_i to the message; hash to get the inner digest; pad the inner digest to block size; XOR the key with opad to get S_o; prepend S_o to the padded inner digest; hash again to get the tag.

Why is HMAC efficient, and why is it secure?

It costs only two extra block computations beyond hashing the message, and those two can be precomputed for a fixed key. Its security is provably tied to the underlying hash: forging it requires either finding collisions without knowing the key or breaking the compression function with a secret IV, so even a collision-weak hash such as MD5 does not immediately break HMAC.

Describe CMAC and the weakness of CBC-MAC that it fixes.

CMAC runs a block cipher such as AES in CBC mode over the message with a zero IV, and takes the last ciphertext block as the tag; before that, it XORs subkey K₁ into a complete final block or K₂ into a padded final block, the subkeys being derived from L = E(K, 0ᵇ) by multiplication by x in GF(2ᵇ). Plain CBC-MAC (DAA) is secure only for fixed-length messages: for variable-length messages an attacker can forge tags by concatenation, which the subkeys prevent.

Give five differences between HMAC and CMAC.

HMAC is built on a hash, CMAC on a block cipher; HMAC is a nested double hash with ipad and opad, CMAC is a CBC chain with two subkeys; HMAC’s tag is the digest size, CMAC’s the cipher block size; HMAC is standardised in RFC 2104/FIPS 198, CMAC in NIST SP 800-38B; HMAC is used in IPsec and TLS, CMAC in WPA2 and constrained devices with AES hardware.
