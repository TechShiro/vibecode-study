SSL/TLS protocol stack

SSL sits between the application layer (HTTP, FTP) and the transport layer (TCP). Four sub-protocols:

ProtocolFunction
HandshakeAuthenticate server (optionally client), negotiate cipher suite, establish session keys
Change Cipher SpecSignal: switch to negotiated keys now
AlertSend warnings and fatal errors
RecordFragment, compress, MAC, encrypt, transmit application data

TLS handshake (simplified)

  1. ClientHello: supported cipher suites, random number, TLS version.
  2. ServerHello: chosen cipher suite, random number, session ID.
  3. Server Certificate: server’s X.509 certificate (contains public key).
  4. ServerKeyExchange (if needed, e.g. DHE): server’s DH parameters.
  5. ServerHelloDone.
  6. ClientKeyExchange: pre-master secret encrypted with server’s public key (RSA) or client’s DH public value.
  7. Both derive master secret from pre-master + two randoms.
  8. ChangeCipherSpec (both sides): switch to encrypted communication.
  9. Finished (both sides): first encrypted message, verifies handshake integrity.
Key derivation Master secret = PRF(pre-master secret, "master secret", client_random + server_random)
From master secret: derive client/server write keys, client/server MAC keys, client/server IVs.

Record protocol

For each chunk of application data: Fragment → Compress → Add MAC → Encrypt → Add SSL record header → Send.

Session vs connection

Session: created by handshake, stores crypto parameters. Can span multiple connections.
Connection: a single transport link. Session resumption avoids repeating the full handshake.

1. The four SSL sub-protocols are:

Handshake negotiates. CCS signals switch. Alert reports errors. Record encrypts data.

2. The pre-master secret is encrypted with:

Client encrypts with server's public key so only the server can decrypt. From this they derive the master secret.

3. The SSL Record protocol order is:

MAC-then-encrypt in TLS 1.2. Fragment first to fit size limits.
