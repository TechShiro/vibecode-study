Four methods of public-key distribution

MethodHow it worksWeakness
1. Public announcementUser broadcasts their public key (email, website, keyserver)No authentication — anyone can post a fake key claiming to be Alice
2. Publicly available directoryA trusted authority maintains a directory mapping names to public keys; users register in personDirectory can be tampered if compromised; single point of failure
3. Public-key authority (online)The authority signs each key on request in real-time; the user contacts the authority for every communicationAuthority must be online at all times; becomes a bottleneck
4. Public-key certificates (CA)A Certificate Authority signs a certificate binding (name, public key, validity). The certificate can be verified offline using the CA’s public keyRequires trust in the CA; if CA is compromised, all certificates are suspect
Method 4 is the standard

The CA-based system is what the internet uses (X.509 certificates in TLS/SSL). The other three are listed for the exam comparison table, but certificates are the only method that scales and works offline.

X.509 certificates

An X.509 certificate contains:

  • Version (v1, v2, v3)
  • Serial number (unique per CA)
  • Signature algorithm (e.g., SHA-256 with RSA)
  • Issuer (the CA’s distinguished name)
  • Validity period (not before / not after)
  • Subject (the entity’s distinguished name)
  • Subject’s public key (algorithm + key value)
  • CA’s digital signature over all of the above
Certificate notation CA «A» = EKRCA( IDA ‖ KUA ‖ validity ‖ … )

Anyone with KUCA (the CA’s public key) can verify that the certificate is genuine.

Certificate chain (hierarchy)

If Alice’s certificate is signed by CA1 and Bob trusts CA2, they can still communicate if there is a chain: CA2 has signed CA1’s certificate, so Bob trusts CA1 transitively. This is the certificate hierarchy / chain of trust.

Certificate Revocation List (CRL)

A list published by the CA of certificates that are revoked before expiry (e.g., if the private key is compromised). The verifier must check the CRL (or use OCSP — Online Certificate Status Protocol) before accepting a certificate.

Hijacking

Man-in-the-middle (MITM) on public-key distribution

MITM attack Alice requests Bob’s public key. Mallory intercepts and sends her own public key as Bob’s.
Alice encrypts with Mallory’s key thinking it is Bob’s. Mallory decrypts, reads, re-encrypts with Bob’s real key, forwards to Bob.

Neither side detects the attack.
Defence: certificates from a trusted CA. Mallory cannot forge a certificate for Bob without the CA’s private key.

Session hijacking

An attacker takes over an established session between two authenticated parties:

  1. TCP session hijacking: attacker predicts TCP sequence numbers and injects packets after authentication is complete. The server thinks the attacker is the legitimate client.
  2. Cookie hijacking: attacker steals a session cookie (via XSS, sniffing) and uses it to impersonate the user’s session with a web server.
  3. IP spoofing: attacker forges the source IP address to appear as the legitimate client.
Attack typeWhat is exploitedDefence
MITMUnauthenticated key exchangeCertificates, authenticated DH
TCP hijackingPredictable sequence numbersRandom sequence numbers, encryption (TLS)
Cookie hijackingUnencrypted session tokensHTTPS, secure/httponly cookie flags
IP spoofingNo source authentication in IPIPSec, ingress filtering
ReplayReuse of old credentialsTimestamps, nonces, sequence numbers
The exam-ready summary

Hijacking = taking control of a session after authentication. It differs from MITM (which is during key exchange) and replay (which is reuse of old messages). The common theme: any gap between authentication and communication is exploitable. TLS closes this gap by combining authentication and encryption into one protocol.

Check yourself

Retrieval practice

1. The most secure and scalable method of public-key distribution is:

Certificates are signed by a trusted CA and can be verified offline. The other methods lack authentication or require the authority to be online.

2. An X.509 certificate is verified using:

The CA signs the certificate with its private key. Anyone with the CA’s public key can verify the signature, confirming the certificate is genuine.

3. A CRL is used to:

Certificate Revocation List = certificates that should no longer be trusted (e.g., private key compromised). Must be checked before accepting a certificate.

4. In a MITM attack on public-key distribution, the attacker:

The attacker intercepts the key exchange and substitutes their own key. They then relay messages between the parties, decrypting and re-encrypting.

5. Session hijacking differs from a replay attack in that:

Hijacking = active takeover of a current session after auth. Replay = passive reuse of recorded credentials.

6. The defence against MITM on Diffie–Hellman is:

DH gives no authentication. Signing g^a and g^b with the sender’s private key (Station-to-Station protocol) prevents substitution.

7. A certificate chain enables:

If Bob trusts CA_2 and CA_2 has signed CA_1’s certificate, Bob can transitively trust certificates issued by CA_1.

Recall without looking

Name the four methods of public-key distribution.

1. Public announcement (no auth). 2. Publicly available directory (tamper risk). 3. Online public-key authority (bottleneck). 4. Certificates from CA (standard, works offline).

What does an X.509 certificate contain?

Version, serial number, signature algorithm, issuer (CA), validity period, subject, subject’s public key, and the CA’s digital signature over all fields.

Explain session hijacking vs MITM vs replay.

MITM: intercepts during key exchange. Hijacking: takes over a live session after auth. Replay: resends old messages. All exploit gaps in authentication/freshness.

How do certificates prevent MITM?

The CA signs (name, public key). An attacker cannot forge a certificate for Bob without the CA’s private key, so substituting a fake public key is detectable.
