The key distribution problem

If two parties want to communicate with a symmetric cipher, they need a shared secret key. But how do they agree on one securely? The options are:

  1. Physical delivery — meet in person or use a courier. Does not scale.
  2. Key Distribution Centre (KDC) — a trusted third party that shares a master key with every user and generates session keys on demand.
  3. Key agreement protocol (Diffie–Hellman) — the two parties negotiate a key over an insecure channel.
  4. Public-key cryptography — encrypt the session key with the recipient’s public key (Lesson 19).

Key Distribution Centre (KDC)

Every user U shares a long-term master key KU with the KDC. When Alice wants to talk to Bob:

Basic KDC protocol 1. Alice → KDC:   “I want to talk to Bob” + nonce N1
2. KDC → Alice:   EKA( Ks ‖ IDB ‖ N1 ‖ EKB(Ks ‖ IDA) )
3. Alice → Bob:   EKB(Ks ‖ IDA)   ← this is the ticket
4. Bob decrypts with KB, obtains Ks and knows he is talking to Alice.

Needham–Schroeder protocol

An extension of the above with mutual authentication using nonces. Its weakness: if an old session key Ks is compromised, an attacker can replay the ticket (step 3) and impersonate Alice. Fix: add timestamps (Denning–Sacco modification) or use Kerberos.

Kerberos (v5)

Kerberos is a network authentication protocol based on symmetric-key cryptography and a trusted third party. It uses tickets to prove identity without sending passwords over the network.

Components

  • AS (Authentication Server) — verifies identity, issues a Ticket-Granting Ticket (TGT).
  • TGS (Ticket-Granting Server) — issues service tickets based on TGT.
  • Client — the user wanting access.
  • Application Server — the service being accessed.

The three exchanges

Exchange 1 — Authentication Service (AS) Exchange 1. Client → AS:   IDC ‖ IDTGS ‖ TS1
2. AS → Client:   EKC( KC,TGS ‖ IDTGS ‖ TS2 ‖ Lifetime ‖ TGT )
   where TGT = EKTGS( KC,TGS ‖ IDC ‖ ADC ‖ TS2 ‖ Lifetime )
Exchange 2 — Ticket-Granting Service (TGS) Exchange 3. Client → TGS:   IDV ‖ TGT ‖ AuthenticatorC
   AuthenticatorC = EKC,TGS( IDC ‖ ADC ‖ TS3 )
4. TGS → Client:   EKC,TGS( KC,V ‖ IDV ‖ TS4 ‖ TicketV )
   TicketV = EKV( KC,V ‖ IDC ‖ ADC ‖ TS4 ‖ Lifetime )
Exchange 3 — Client/Server Authentication 5. Client → V:   TicketV ‖ AuthenticatorC′
   AuthenticatorC′ = EKC,V( IDC ‖ ADC ‖ TS5 )
6. V → Client:   EKC,V( TS5 + 1 )   (for mutual authentication)
What to remember for the exam

The password is never sent over the network. The AS encrypts the response with KC = h(password). The TGT lets the client get service tickets without re-entering the password (single sign-on). Timestamps prevent replay attacks. Authenticators prove the client possesses KC,TGS or KC,V.

Symmetric-key agreement — Diffie–Hellman

Diffie–Hellman Key Exchange Public: prime p, generator g.
Alice picks private a, sends A = ga mod p.
Bob picks private b, sends B = gb mod p.
Shared secret: K = Ba mod p = Ab mod p = gab mod p.

Security rests on: the Discrete Logarithm Problem (DLP) — given ga mod p, finding a is computationally infeasible.

The man-in-the-middle attack on DH

Mallory intercepts A and B, performs separate DH with Alice and Bob, establishing KAM and KMB. Neither Alice nor Bob detects this because DH provides no authentication. Defence: authenticate the public values with digital signatures or certificates (Station-to-Station protocol).

Check yourself

Retrieval practice

1. In Kerberos, the TGT is encrypted with:

The TGT is encrypted with K_TGS so only the TGS can read it. The outer envelope is encrypted with K_C so the client can extract the session key.

2. Kerberos achieves single sign-on because:

After the initial AS exchange (where the password is used), the TGT serves as proof of identity for all subsequent TGS requests during its lifetime.

3. The Needham–Schroeder vulnerability is:

If an old K_s is compromised, the ticket E_{K_B}(K_s, ID_A) can be replayed. Adding timestamps (Denning-Sacco) or using Kerberos fixes this.

4. Diffie–Hellman is vulnerable to:

DH establishes a shared secret but does NOT authenticate the parties. An active attacker can impersonate both sides.

5. In Kerberos, an authenticator proves:

The authenticator = E_{K_session}(ID_C, timestamp). Only someone with K_session can create it, and the timestamp proves it is fresh.

6. The shared DH secret is computed as:

Alice computes B^a = (g^b)^a = g^{ab}. Bob computes A^b = (g^a)^b = g^{ab}. Same result.

7. Kerberos uses timestamps to prevent:

Timestamps ensure freshness. A replayed message has an old timestamp and is rejected. This fixes the Needham-Schroeder vulnerability.

Recall without looking

Draw the three Kerberos exchanges.

1. Client → AS: ID_C. AS → Client: E_{K_C}(K_{C,TGS}, TGT). 2. Client → TGS: TGT + Authenticator. TGS → Client: E_{K_{C,TGS}}(K_{C,V}, Ticket_V). 3. Client → V: Ticket_V + Auth. V → Client: E_{K_{C,V}}(TS+1).

Explain the DH man-in-the-middle attack.

Mallory intercepts g^a and g^b, does DH with each side separately, getting K_AM and K_MB. Neither side knows they are talking to Mallory. Fix: authenticate public values with signatures.

What is the Needham-Schroeder flaw?

Old tickets can be replayed if the session key is compromised, because there are no timestamps to prove freshness. Fix: Denning-Sacco (add timestamps) or Kerberos.

Why is the password never sent in Kerberos?

The AS encrypts the reply with K_C = h(password). Only the real user can decrypt it. The password itself never leaves the client machine.
