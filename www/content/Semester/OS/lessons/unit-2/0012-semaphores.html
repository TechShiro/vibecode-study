Semaphores

The wait and signal operations, binary and counting semaphores, the block–wakeup implementation that removes busy waiting, enforcing execution order, and the three things that still go wrong — deadlock, starvation and priority inversion.

Exam strategy

Three certainties. “What is a semaphore? Explain wait and signal” — write both operations as code, and stress that they are atomic. “Differentiate binary and counting semaphore” — a table. Semaphore value numericals — count the P's and V's, and know that a negative value is the number of blocked processes; that single fact answers most objective questions on this topic. Priority inversion, with the Mars Pathfinder story, is a reliable short note.

What a semaphore is

Definition A semaphore S is an integer variable that, apart from initialisation, is accessed only through two standard atomic operations: wait() and signal().

Dijkstra's original names, still used in exam papers, are P (from the Dutch proberen, to test) for wait, and V (verhogen, to increment) for signal.
wait(S) — also P(S), or downsignal(S) — also V(S), or up
wait(S) {
  while (S <= 0)
    ;  /* busy wait */
  S--;
} 		signal(S) {
  S++;
}
The word that carries the marks

Atomically. All modifications to the integer value of the semaphore in wait() and signal() must be executed indivisibly — when one process modifies the semaphore value, no other process may simultaneously modify it. In wait(), the testing of S and its decrement must together be uninterruptible. Without atomicity, the semaphore is itself a shared variable with a race condition, and solves nothing.

The two standard uses 1. Mutual exclusion — binary semaphore mutex, initialised to 1:
do {
  wait(mutex);
    critical section
  signal(mutex);
    remainder section
} while (true);
2. Resource counting — counting semaphore initialised to the number of instances. Each process calls wait() to claim one and signal() to release it. When the count reaches 0, all resources are in use and further callers block.

Enforcing execution order — the second use of semaphores

Semaphores also solve ordering problems, not just mutual exclusion. Suppose statement S2 in process P2 must execute only after statement S1 in process P1.

Ordering with a semaphore initialised to 0 Shared: semaphore synch = 0;

P1:   S1;   signal(synch);
P2:   wait(synch);   S2;

Because synch starts at 0, P2 cannot pass the wait until P1 has executed the signal. Initialising to 0 is the whole trick — initialising to 1 would give mutual exclusion instead.
Numerical — enforce a precedence graph with semaphores.

Q. Four statements must execute in this order: S1 first; then S2 and S3 in parallel; then S4 only after both S2 and S3 have finished. Write the semaphore solution.

Semaphores needed: one per dependency edge, all initialised to 0. The edges are S1→S2, S1→S3, S2→S4, S3→S4, so we need a, b, c, d, all 0.

P1P2P3P4
S1;
signal(a);
signal(b);		 wait(a);
S2;
signal(c);		 wait(b);
S3;
signal(d);		 wait(c);
wait(d);
S4;

Why it works: P2 and P3 both block at 0 until P1 signals both, so they start together. P4 blocks on c until S2 finishes and then on d until S3 finishes, so it starts only after both. The rule for any such question: one semaphore per arrow in the graph, all initialised to 0; signal at the tail of the arrow, wait at the head.

The implementation — removing busy waiting

The definition above still busy-waits, which wastes CPU cycles. The real implementation replaces the spin with blocking.

Semaphore with a waiting queue
typedef struct {
  int value;
  struct process *list;  /* the waiting queue */
} semaphore;

wait(semaphore *S) {
  S->value--;
  if (S->value < 0) {
    add this process to S->list;
    block();
  }
}

signal(semaphore *S) {
  S->value++;
  if (S->value <= 0) {
    remove a process P from S->list;
    wakeup(P);  /* move P to the ready queue */
  }
}
The single most useful fact in this lesson

In this implementation the semaphore value can go negative, and the magnitude of a negative value is exactly the number of processes blocked on that semaphore.

So if S = −4, then four processes are waiting. If S = 3, then three more processes may enter without blocking. Note that block() suspends the calling process and wakeup(P) moves a blocked process to the ready queue — both are ordinary OS system calls.

Semaphore value numericals

Numerical 1 — the basic count.

Q. A counting semaphore is initialised to 10. Then 6 wait (P) and 4 signal (V) operations are completed. What is the final value?

Each wait decrements by 1; each signal increments by 1.

Final = 10 − 6 + 4 = 8

Interpretation: 8 instances of the resource remain free, so 8 more processes could enter without blocking.

Numerical 2 — when the value goes negative.

Q. A counting semaphore S is initialised to 5. Twelve P operations and three V operations are then performed. What is the value of S, and how many processes are blocked?

S = 5 − 12 + 3 = −4

Four processes are blocked on S — the magnitude of the negative value is the queue length.

Sanity check: 5 initial permits plus 3 released = 8 permits ever available, against 12 requests. 12 − 8 = 4 requests unmet. The two routes agree.

Numerical 3 — how many processes are inside.

Q. Twenty processes share a resource guarded by a counting semaphore initialised to 3. If all twenty execute wait(S), what is the value of S, how many are in the critical section, and how many are blocked?

Sanity check: in the critical section plus blocked must equal the total: 3 + 17 = 20. ✓

Numerical 4 — the reverse question.

Q. A binary semaphore initialised to 1 currently has the value −3. How many processes have executed wait, and what is the state of the system?

Value = 1 − (number of waits) + (number of signals). With no signals yet completed, 1 − n = −3 gives n = 4 processes have executed wait.

State: one process is inside the critical section, and three are blocked on the semaphore's queue.

Sanity check: a binary semaphore admits exactly one process, so of the four, 1 got in and 3 wait — and |−3| = 3 matches. ✓

The trap in these questions

Some textbooks define wait so that the value never falls below 0 — the busy-wait version at the top of this lesson. Under that definition, the answer to Numerical 2 is 0, with 4 processes waiting, not −4. Always state which definition you are using in the first line of the answer; examiners accept either, and the working is identical.

What still goes wrong

1. Deadlock

Two or more processes wait indefinitely for an event that can only be caused by one of the waiting processes.

P0P1
wait(S);
wait(Q);
  …
signal(S);
signal(Q);		 wait(Q);
wait(S);
  …
signal(Q);
signal(S);

Both S and Q start at 1. If P0 executes wait(S) and P1 executes wait(Q), then P0 blocks on wait(Q) and P1 blocks on wait(S). Neither can proceed, and neither can release. The fix is to make every process acquire the semaphores in the same order.

2. Starvation — indefinite blocking

A process waits indefinitely on the semaphore queue. This happens if the queue is served in last-in first-out order: a process at the bottom may never be reached. The fix is a FIFO waiting queue.

3. Priority inversion — the short note that always appears

Priority inversion A higher-priority process is kept waiting because a lower-priority process holds a lock it needs. The situation is made far worse when a medium-priority process preempts the low-priority lock holder — the high-priority process is then blocked indirectly by a process of lower priority than itself.

The concrete case: three processes L (low), M (medium) and H (high). L acquires a resource R. H then needs R and blocks. M, which needs nothing, preempts L. H now waits on M, which has lower priority than H — the priorities have inverted.

The solution: the priority-inheritance protocol. A process holding a resource needed by a higher-priority process temporarily inherits that higher priority until it releases the resource, at which point it reverts. In the example L inherits H's priority, so M cannot preempt it, L finishes quickly, releases R, and H proceeds.

The story worth telling in one line

The Mars Pathfinder rover, 1997, kept resetting itself on the Martian surface. The cause was priority inversion in its real-time kernel. The fix — enabling priority inheritance — was uploaded from Earth. One sentence of this in an answer is worth a mark, and makes the concept memorable.

The initial value is the number of permits, so 3 get in and 17 block. The semaphore value becomes −17, and 3 + 17 = 20 checks out.

It becomes acute when a medium-priority process preempts the low-priority lock holder. The remedy is priority inheritance — the holder temporarily inherits the waiter's priority.

Signalling first raises the count instead of claiming it, so mutual exclusion is lost. Writing wait() at both ends instead causes deadlock. These usage errors are the reason monitors exist.

LIFO ordering is exactly what causes it — a process at the bottom of the stack may never be reached.

Recall without looking

Define a semaphore and write both operations.

A semaphore is an integer variable accessed, apart from initialisation, only through two standard atomic operations: wait(S), which spins while S ≤ 0 then decrements, and signal(S), which increments. Dijkstra's names are P and V. Atomicity is essential — in wait(), the test and the decrement must be indivisible.

Compare binary and counting semaphores.

A binary semaphore ranges over 0 and 1 only, is also called a mutex lock, is initialised to 1 and gives mutual exclusion for one process at a time. A counting semaphore ranges over any integers, is initialised to the number of available instances of a resource, and admits up to N processes.

How do you enforce that S₂ runs only after S₁?

Share a semaphore initialised to 0. P₁ executes S₁ then signal(synch); P₂ executes wait(synch) then S₂. For a precedence graph, use one semaphore per edge, all initialised to 0, with signal at the tail of each arrow and wait at the head.

Give the block–wakeup implementation and the meaning of a negative value.

The semaphore is a struct holding an integer value and a list of waiting processes. wait() decrements, and if the value goes below zero adds the process to the list and calls block(). signal() increments, and if the value is still ≤ 0 removes a process from the list and calls wakeup(). The magnitude of a negative value is exactly the number of blocked processes.

How do you find the number of processes inside and blocked?

Final value = initial − (number of waits) + (number of signals). If the result is negative, its magnitude is the number blocked, and the number admitted is the initial value. If positive, nobody is blocked and that many more may enter. Check that admitted plus blocked equals the total.

Show how two semaphores can deadlock, and give the fix.

P₀ does wait(S) then wait(Q); P₁ does wait(Q) then wait(S), with both semaphores at 1. If each takes its first, each blocks on the other's and neither can release. The fix is to make every process acquire semaphores in the same global order.

Define priority inversion and its solution.

A high-priority process waits because a low-priority process holds a lock it needs, and the problem worsens when a medium-priority process preempts the holder. The priority-inheritance protocol has the holder temporarily inherit the waiter's priority until it releases the resource. Mars Pathfinder in 1997 kept resetting because of this, and was fixed by enabling priority inheritance.

Name the four ways a programmer can misuse semaphores.

Swapping wait and signal, which lets several processes into the critical section; writing wait instead of signal at the exit, which deadlocks; omitting either call, which loses mutual exclusion or deadlocks; and errors that are timing-dependent and so nearly impossible to reproduce. These motivate monitors.
