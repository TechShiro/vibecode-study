Monitors

Why semaphores were not enough, the monitor construct and its automatic mutual exclusion, condition variables with wait and signal, the signal-and-wait versus signal-and-continue question, the dining-philosophers monitor, and implementing a monitor with semaphores.

Exam strategy

“What is a monitor? How does it differ from a semaphore?” is the question, and it is worth 5–10 marks. The winning line is: a monitor provides mutual exclusion automatically, so the programmer cannot forget it; a semaphore relies entirely on the programmer. Draw the schematic view — shared data, procedures, entry queue — and know that x.signal() on a condition variable with nobody waiting has no effect, which is exactly where it differs from a semaphore's signal(). The dining-philosophers monitor is the standard long answer.

Why monitors exist

Semaphores are powerful, but timing errors caused by their incorrect use are extremely hard to detect, because they only appear under particular interleavings. Recall the four failure modes from Lesson 12:

Programmer errorConsequence
signal(mutex) … wait(mutex) — the order reversedMutual exclusion violated — several processes in the critical section
wait(mutex) … wait(mutex) — signal written as waitDeadlock
wait(mutex) omittedMutual exclusion violated
signal(mutex) omittedDeadlock

Every one of these is a silent error. The compiler cannot see it. A monitor is a high-level language construct that makes these errors impossible to write.

The monitor construct

Definition A monitor is an abstract data type that encapsulates shared data together with the procedures that operate on it, and guarantees that only one process at a time can be active inside the monitor.
Syntax
monitor monitor_name
{
  /* shared variable declarations */

  function P1 ( … ) { … }
  function P2 ( … ) { … }
     …
  function Pn ( … ) { … }

  initialization_code ( … ) { … }
}

The three rules that define a monitor

  1. The shared variables are accessible only by the monitor's own procedures. A process outside the monitor cannot touch them. This is ordinary data encapsulation, and it removes the possibility of an unprotected access.
  2. Only one process may be active inside the monitor at any time. The compiler inserts the mutual exclusion — the programmer does not write it and cannot forget it.
  3. A process wanting to enter a busy monitor is placed in the monitor's entry queue.

Condition variables

The monitor construct as described is not sufficiently powerful on its own. It gives mutual exclusion, but there is no way for a process to say “I cannot proceed until some condition becomes true — let someone else in meanwhile.” That requires condition variables.

Declaration and the two operations condition x, y;

x.wait() — the process invoking it is suspended on x's queue, and releases the monitor, so another process may enter.
x.signal() — resumes exactly one process suspended on x. If no process is suspended on x, the operation has no effect whatsoever — the state of x is unchanged.
The difference from a semaphore — this is the exam's favourite distinction

A semaphore's signal() always increments the counter, so its effect is remembered: a later wait() will pass because of it.

A condition variable's x.signal() on an empty queue does nothing at all, and is forgotten. Condition variables have no stored value — they are not counters, only queues.

Signal and wait, or signal and continue?

Suppose process P executes x.signal() and process Q is suspended on x. Both cannot be active in the monitor at once, so one must give way. There are two possibilities, and naming them is worth a mark:

 Signal and waitSignal and continue
Who runs onQ resumes immediately; P waits until Q leaves the monitor or waits on another conditionP continues; Q waits until P leaves the monitor or waits on another condition
Argument forThe condition Q was waiting for is known to hold right nowP is already running, so no extra switch is needed; and it is illogical for P to wait when it has more to do
Argument againstAn extra context switch, and P is penalised for being helpfulThe condition may have changed again by the time Q runs — so Q must re-test it in a while loop, not an if
Used byHoare's original monitorsJava, C#, Pthreads condition variables — the practical choice

A third option, adopted in Concurrent Pascal, sidesteps the question: signal() must be the last statement a monitor procedure executes, so P leaves the monitor immediately and Q resumes at once.

The dining-philosophers monitor solution

This is the standard long answer, and it also completes Lesson 13's fourth remedy.

monitor DiningPhilosophers
monitor DiningPhilosophers
{
  enum { THINKING, HUNGRY, EATING } state[5];
  condition self[5];  /* one per philosopher */

  void pickup(int i) {
    state[i] = HUNGRY;
    test(i);
    if (state[i] != EATING) self[i].wait();
  }

  void putdown(int i) {
    state[i] = THINKING;
    test((i + 4) % 5);  /* left neighbour */
    test((i + 1) % 5);  /* right neighbour */
  }

  void test(int i) {
    if ( (state[(i + 4) % 5] != EATING) &&
       (state[i] == HUNGRY) &&
       (state[(i + 1) % 5] != EATING) ) {
      state[i] = EATING;
      self[i].signal();
    }
  }

  initialization_code() {
    for (int i = 0; i < 5; i++) state[i] = THINKING;
  }
}

Each philosopher must call: DiningPhilosophers.pickup(i); … eat … DiningPhilosophers.putdown(i);

PointExplanation
Why test is the heartA philosopher may move to EATING only if she is HUNGRY and neither neighbour is EATING — which means both her chopsticks are free. She takes both or neither
Why putdown tests both neighboursFinishing may have released a chopstick each neighbour was waiting for, so both must be given the chance to proceed
Why it cannot deadlockNo philosopher ever holds one chopstick while waiting for the other — hold-and-wait is broken
Why it can still starveNothing prevents a philosopher's two neighbours from alternating for ever, so that test never finds both free at the moment she is hungry. Deadlock-free is not starvation-free — end the answer with this
Why self[i].signal() is safeIf nobody is waiting on self[i], the signal simply has no effect — unlike a semaphore, it leaves nothing behind to cause an error later

Implementing a monitor using semaphores

Asked when the paper wants to test whether the two constructs are understood as equivalent in power.

The monitor's own mutual exclusion
semaphore mutex = 1;     /* one process inside the monitor */
semaphore next = 0;      /* signallers suspended here */
int next_count = 0;     /* how many are suspended on next */

/* every monitor procedure F is compiled as: */
wait(mutex);
    … body of F …
if (next_count > 0) signal(next);
else signal(mutex);
Each condition variable x, with semaphore x_sem = 0 and int x_count = 0
x.wait():
  x_count++;
  if (next_count > 0) signal(next); else signal(mutex);  /* release the monitor */
  wait(x_sem);
  x_count--;

x.signal():
  if (x_count > 0) {  /* the whole point — do nothing if nobody waits */
    next_count++;
    signal(x_sem);
    wait(next);  /* the signaller now waits — this is signal-and-wait */
    next_count--;
  }

Notice the if (x_count > 0) guard: it is precisely what makes x.signal() a no-op when nobody is waiting, which is the semantic difference from a plain semaphore.

The one-line answer

A semaphore is a mechanism the programmer must use correctly; a monitor is a construct that uses the mechanism correctly on the programmer's behalf.

Monitors in Java — worth a sentence

Every object in Java has an associated monitor lock. Declaring a method synchronized makes the compiler acquire that lock on entry and release it on exit — exactly rule 2 above. wait(), notify() and notifyAll() are the condition-variable operations, and Java uses signal and continue, which is why every Java textbook insists that wait() be called inside a while loop and never an if.

Resuming processes within a monitor

If several processes are suspended on the same condition x, which one does x.signal() resume? The simple answer is FCFS — the longest waiting. When that is not adequate, the conditional-wait construct is used:

Conditional wait x.wait(c);

where c is an integer expression evaluated when wait is executed — the priority number, stored with the suspended process. When x.signal() is executed, the process with the smallest priority number is resumed.

The standard illustration is a resource allocator whose acquire(time) operation passes the expected duration of use as the priority number, so the shortest job gets the resource first.

The limitation to name at the end

A monitor still cannot force correct use. A process may access the resource without asking, never release it, ask twice, or ask for one it already holds. The monitor guarantees only that access to the monitor's own data is correctly serialised — the protocol around it remains the programmer's responsibility.

1. The defining guarantee of a monitor is that:

The programmer never writes the mutual exclusion, so cannot forget it, reverse it or duplicate it — which is exactly the class of semaphore errors monitors were invented to remove.

2. x.signal() on a condition variable with no process suspended on x:

This is the sharpest difference from a semaphore, whose signal() always increments and is therefore remembered. A condition variable holds no value; it is only a queue.

3. Under signal-and-continue semantics, a waiting process must re-test its condition because:

That is why Java's wait() must sit inside a while loop, not an if. Under Hoare's signal-and-wait the condition is known to hold on resumption, but the signaller pays with an extra switch.

4. In the dining-philosophers monitor, test(i) sets state[i] to EATING only when:

Both chopsticks must be free, so she takes both or neither. That is what breaks hold-and-wait and makes the solution deadlock-free — though not starvation-free.

5. Why does putdown(i) call test on both neighbours?

The left neighbour is (i+4)%5 and the right is (i+1)%5. Each is given the chance to move to EATING, and test's signal is a no-op if that philosopher is not actually waiting.

6. The conditional-wait construct x.wait(c) resumes, on signal:

Without it, the default is FCFS. The resource-allocator example passes the expected duration of use as c, so the shortest job is served first.

7. Which error is possible with a semaphore but not with a monitor?

Mutual exclusion is compiler-inserted in a monitor, so it cannot be omitted. Starvation, protocol misuse and cross-monitor deadlock all remain possible — the monitor guarantees serialised access to its own data, nothing more.

Recall without looking

Define a monitor and give its three rules.

A monitor is an abstract data type encapsulating shared data with the procedures that operate on it, guaranteeing that only one process is active inside it at a time. The shared variables are accessible only through the monitor's procedures; mutual exclusion is inserted by the compiler, not the programmer; and processes wanting to enter a busy monitor queue in the entry queue.

Why were monitors invented?

Because semaphore misuse fails silently. Reversing wait and signal loses mutual exclusion; writing wait twice deadlocks; omitting wait loses mutual exclusion; omitting signal deadlocks. None of these can be detected by a compiler, and all are timing-dependent and hard to reproduce.

Define the two condition-variable operations and their key semantic.

x.wait() suspends the calling process on x's queue and releases the monitor so another process may enter. x.signal() resumes exactly one process suspended on x, and if none is suspended it has no effect at all. Condition variables hold no value; they are only queues.

Contrast signal-and-wait with signal-and-continue.

Signal-and-wait: the signalled process resumes immediately and the signaller waits — the condition is known to hold, at the cost of an extra context switch; this was Hoare's original semantics. Signal-and-continue: the signaller keeps running and the signalled process waits — no extra switch, but the condition may change again, so the waiter must re-test in a while loop. Java, C# and Pthreads use signal-and-continue.

Write the dining-philosophers monitor and explain why it is deadlock-free but not starvation-free.

State array of THINKING, HUNGRY, EATING plus one condition variable per philosopher. pickup sets HUNGRY, calls test, and waits if not EATING. putdown sets THINKING and tests both neighbours. test sets EATING and signals only if the philosopher is HUNGRY and neither neighbour is EATING. No philosopher ever holds one chopstick while waiting for the other, so hold-and-wait is broken — but the two neighbours can alternate for ever, so starvation remains possible.

Compare monitors and semaphores on six points.

A semaphore is a low-level integer with two atomic operations, requires the programmer to write mutual exclusion, encapsulates nothing, remembers a signal to an empty queue, holds a value, and is highly error-prone. A monitor is a high-level abstract data type, has automatic compiler-inserted mutual exclusion, encapsulates its shared data, ignores a signal to an empty queue, holds no value, and makes those errors unwritable — but needs language support.

What remains the programmer's responsibility even with a monitor?

The protocol around the monitor. A process may still access a resource without requesting it, never release it, request it twice, or request one it already holds. The monitor guarantees only that access to its own data is correctly serialised — and starvation and cross-monitor deadlock remain possible.
