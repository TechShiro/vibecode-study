The race condition

Definition A race condition is a situation in which several processes access and manipulate the same data concurrently, and the outcome depends on the particular order in which the accesses take place.

Recall the bounded buffer from Lesson 6. To use all N slots we add a counter, count, incremented by the producer and decremented by the consumer. Each looks like a single statement, but the compiler turns each into three machine instructions:

count++ becomescount-- becomes
register1 = count
register1 = register1 + 1
count = register1		 register2 = count
register2 = register2 − 1
count = register2
Numerical — trace an interleaving. Start with count = 5. The producer executes count++ and the consumer count--. What values can result?

The correct result is 5 — one increment and one decrement cancel. Now interleave the six instructions like this:

Final count = 4 — which is wrong. Reversing the order of steps 5 and 6 leaves count = 6 — also wrong.

So the answer to “what values can result” is 4, 5 or 6, depending purely on timing. That is the race condition, and it is why synchronisation exists.

Note carefully: the program is not buggy in any way a compiler could detect. Each process is individually correct; the fault is that the three-instruction update is not atomic.

The critical-section problem

Definition Consider n processes, each having a segment of code called its critical section, in which it changes shared variables, updates a table, writes a file and so on.

The critical-section problem is to design a protocol such that when one process is executing in its critical section, no other process is allowed to execute in its critical section.
The general structure of a process — draw this
do {
   ENTRY SECTION       /* request permission to enter */
       CRITICAL SECTION /* access the shared data */
   EXIT SECTION        /* release permission */
       REMAINDER SECTION/* everything else */
} while (true);

The three conditions — learn these verbatim

ConditionStatementWhat it prevents
1. Mutual exclusionIf process Pi is executing in its critical section, then no other process can be executing in its critical sectionData corruption — the race condition itself
2. ProgressIf no process is in its critical section and some processes wish to enter, then only those not in their remainder section may take part in deciding which enters next, and this selection cannot be postponed indefinitelyDeadlock — and a process in its remainder section blocking one that wants in
3. Bounded waitingThere exists a bound on the number of times other processes are allowed to enter their critical sections after a process has made a request and before that request is grantedStarvation
The memory hook, and how they map

M – P – B. Mutual exclusion stops corruption. Progress stops deadlock. Bounded waiting stops starvation. When a question asks “does this solution work?”, test it against all three in that order — and the answer is almost always that mutual exclusion holds while one of the other two fails.

Preemptive and non-preemptive kernels

The kernel itself has critical sections — the list of open files, memory allocation structures, process lists. A non-preemptive kernel does not allow a process running in kernel mode to be preempted, so it is free from race conditions on kernel data structures. A preemptive kernel allows it, so it must be carefully designed — but it is more responsive and more suitable for real-time programming. That trade-off is a short-note question in its own right.

Two-process software solutions

Assume two processes, P0 and P1, and write j = 1 − i for “the other process”. The exam value of these attempts is that each fails a different condition.

Attempt 1 — the turn variable (strict alternation)

Shared: int turn;
do {
  while (turn != i) ;  /* wait */
     critical section
  turn = j;
     remainder section
} while (true);
  • Mutual exclusion: satisfied. turn holds one value, so only one process can pass the loop.
  • Progress: VIOLATED. Suppose turn = 0, and P0 is in its remainder section, not interested in entering. P1 wants in but must wait for turn to become 1 — which only P0 can set. A process in its remainder section is blocking a process that wants to enter, which is exactly what progress forbids.
  • It also forces strict alternation: neither process can enter twice in a row.

Attempt 2 — the flag array

Shared: boolean flag[2] = {false, false};
do {
  flag[i] = true;
  while (flag[j]) ;  /* wait */
     critical section
  flag[i] = false;
     remainder section
} while (true);
  • Mutual exclusion: satisfied.
  • Progress: VIOLATED — by deadlock. If P0 sets flag[0] = true and is then preempted, and P1 sets flag[1] = true, both now spin for ever, each waiting for the other's flag to clear.

Peterson's solution — the exam answer

Peterson's solution combines both variables. The flag says “I want in”; the turn variable breaks the tie. That one sentence explains the whole algorithm.

Peterson's solution — two shared variables
int turn;
boolean flag[2];  /* both initially false */

/* code for process Pi, with j = 1 − i */
do {
  flag[i] = true;         /* I want to enter */
  turn = j;             /* but you go first */
  while (flag[j] && turn == j) ; /* wait */
     CRITICAL SECTION
  flag[i] = false;
     REMAINDER SECTION
} while (true);
The line students always get wrong

It is turn = j, not turn = i. Each process politely offers the turn to the other one. If both do so at nearly the same moment, the second write wins — and the process whose write lost gets in. Because only one write can be last, exactly one process proceeds.

The proof — all three conditions

ConditionArgument
Mutual exclusionPi enters only if flag[j] == false or turn == i. If both are in their critical sections, then flag[0] == flag[1] == true, so both must have found turn equal to their own index. But turn holds only one value at a time — a contradiction. Hence at most one is inside.
ProgressPi is stuck only while flag[j] && turn == j. If Pj is in its remainder section, flag[j] == false and Pi enters at once. So a disinterested process never blocks an interested one.
Bounded waitingIf Pj is also trying, then when Pj exits it sets flag[j] = false and Pi enters. If Pj immediately re-enters its entry section it sets turn = i, so Pi still enters. Pi waits at most one turn — the bound is 1.
The limitations to state — they carry marks

1. It works for two processes only. Extending it needs the bakery algorithm.

2. It uses busy waiting. The process spins in a loop, consuming CPU cycles — a spinlock.

3. It is not guaranteed to work on modern architectures, because processors and compilers reorder read and write operations that have no data dependency. If turn = j and flag[i] = true are reordered, mutual exclusion can break. It remains the right teaching algorithm, and the right exam answer, but real systems use memory barriers or hardware instructions.

Hardware solutions

Disabling interrupts

The simplest idea: on entry to a critical section, disable interrupts; on exit, enable them. With no interrupts there is no preemption, so no interleaving. Three reasons it is unacceptable in general:

  • It does not work on a multiprocessor — disabling interrupts on one CPU does not stop the others, and passing the message to every CPU is slow.
  • It is dangerous — a user process that disables interrupts and then loops hangs the machine, so it can only be a privileged operation.
  • The clock is missed, so the system's notion of time drifts.

It is still used inside the kernel, for very short critical sections on single-processor systems.

The atomic instructions

Modern hardware provides special atomic — uninterruptible — instructions. The two named in every syllabus:

test_and_set()compare_and_swap()
boolean test_and_set(boolean *target) {
  boolean rv = *target;
  *target = true;
  return rv;
}

Returns the old value; always sets true. 		int compare_and_swap(int *v, int exp, int nv) {
  int temp = *v;
  if (*v == exp) *v = nv;
  return temp;
}

Swaps only if the value is what was expected.
Mutual exclusion with test_and_set — shared boolean lock = false
do {
  while (test_and_set(&lock)) ;  /* spin while it was already true */
     critical section
  lock = false;
     remainder section
} while (true);

How it works: the first process to call it finds lock == false, so test_and_set returns false — the loop exits — and simultaneously sets lock = true. Every later caller gets true and spins. The read and the write happen as one indivisible step, so no interleaving is possible.

The catch worth stating

This simple version satisfies mutual exclusion but not bounded waiting — nothing stops the same lucky process winning the race every time while another starves. The textbook fix adds a waiting[] array so that a departing process explicitly hands the lock to the next waiter in a circular order, which makes the bound n − 1.

Mutex locks

The simplest software tool A mutex lock — from mutual exclusion — has a boolean variable available and two atomic operations:

acquire() — while (!available) ; available = false;
release() — available = true;

A process calls acquire() before its critical section and release() after it.
AdvantageDisadvantage
Simple; needs no context switch, so it is fast when the wait is shortBusy waiting — the process spins, wasting CPU cycles that another process could use

A mutex that busy-waits is called a spinlock. It is not always wrong: on a multiprocessor, where one thread can spin on one core while the lock holder runs on another, spinning can be cheaper than the two context switches a block-and-wake would cost. That is why spinlocks are used widely in real kernels. On a single processor, spinning is pure waste.

Check yourself

1. Starting from count = 5, a concurrent count++ and count-- with no synchronisation can leave count as:

Each statement compiles to three instructions — load, modify, store — and whichever store executes last determines the result. Only 4, 5 and 6 are reachable.

2. The condition violated when a process in its remainder section blocks another from entering is:

That is exactly the failure of the turn-variable solution. Mutual exclusion stops corruption; progress stops deadlock; bounded waiting stops starvation.

3. In Peterson's solution, the entry section sets:

Each process offers the turn to the other. When both do so, the last write wins and the other process gets in — which is what makes exactly one proceed.

4. Peterson's solution may fail on modern hardware because:

If the write to turn is reordered before the write to flag[i], mutual exclusion can break. Real systems use memory barriers or atomic instructions; Peterson's remains the right teaching and exam answer.

5. test_and_set() returns:

The read and the write are one indivisible step. The first caller sees false and proceeds; every later caller sees true and spins.

6. Disabling interrupts is an unacceptable general solution mainly because:

Disabling interrupts on one CPU leaves the others free to interleave, and a process that disables them and loops never gives the CPU back. It survives only inside the kernel, for very short sections.

7. A spinlock can be preferable to a blocking lock when:

Spinning on one core while the holder runs on another can be cheaper than the two context switches a block-and-wake would cost. On a single processor, spinning is pure waste.

Recall without looking

Define a race condition and trace one.

A race condition is when several processes access and manipulate shared data concurrently and the outcome depends on the order of access. With count = 5, count++ and count-- each compile to load, modify, store; interleaving them can leave 4, 5 or 6 because whichever store executes last wins. Neither process is individually incorrect — the fault is that the update is not atomic.

Give the general structure of a process with a critical section.

A loop containing an entry section that requests permission, the critical section that touches shared data, an exit section that releases permission, and a remainder section for everything else.

State the three conditions and what each prevents.

Mutual exclusion — if one process is in its critical section, no other may be — prevents data corruption. Progress — if no process is in its critical section, only processes not in their remainder section take part in choosing who enters next, and the choice cannot be postponed indefinitely — prevents deadlock. Bounded waiting — there is a bound on how many times others may enter after a process has requested and before it is granted — prevents starvation.

Why do the turn-variable and flag-array solutions fail?

Both satisfy mutual exclusion but violate progress. The turn variable forces strict alternation, so a process in its remainder section blocks the other. The flag array deadlocks: if both set their flags before either tests, both spin for ever.

Write Peterson's solution and prove mutual exclusion.

flag[i] = true; turn = j; while (flag[j] && turn == j); critical section; flag[i] = false. For mutual exclusion: a process enters only if the other's flag is false or turn equals its own index. If both were inside, both flags would be true, so both would need turn equal to their own index — impossible, since turn holds one value.

Name three limitations of Peterson's solution.

It handles only two processes; it uses busy waiting, so it is a spinlock; and it is not guaranteed correct on modern architectures, because processors and compilers may reorder independent reads and writes.

Give the code of test_and_set and explain how it enforces mutual exclusion.

It saves the target's old value, unconditionally sets the target to true, and returns the old value — all atomically. With a shared lock initialised to false, a process spins while test_and_set returns true. The first caller sees false, exits the loop and has simultaneously set the lock; everyone else spins. It satisfies mutual exclusion but not bounded waiting without an added waiting array.

Define a mutex lock and say when a spinlock is justified.

A mutex has a boolean available and two atomic operations, acquire() which spins until available then clears it, and release() which sets it. It busy-waits, making it a spinlock. Spinning is justified on a multiprocessor with short critical sections, where it costs less than the two context switches of a block-and-wake; on a single processor it is pure waste.
