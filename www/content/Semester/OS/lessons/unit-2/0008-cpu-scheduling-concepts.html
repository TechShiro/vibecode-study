Why scheduling exists at all

In a single-processor system only one process can run at a time. Multiprogramming exists to keep the CPU busy: several processes are kept in memory, and when one has to wait, the OS takes the CPU away and gives it to another. CPU scheduling is the basis of multiprogrammed operating systems. That is the opening line of any answer here.

The CPU–I/O burst cycle

Process execution consists of a cycle of CPU execution and I/O wait. A process begins with a CPU burst, followed by an I/O burst, then another CPU burst, and so on. It begins and ends with a CPU burst — the final one ends with a system request to terminate.

The observed distribution of burst lengths matters, and is worth a sentence: it is exponential or hyper-exponential, with a very large number of short CPU bursts and a small number of long ones. An I/O-bound program has many short bursts; a CPU-bound program has a few long ones. This shape is the whole justification for shortest-job-first scheduling.

Dispatch latency Dispatch latency is the time the dispatcher takes to stop one process and start another running. It should be as small as possible, because it is pure overhead — the dispatcher is invoked at every single context switch.

When scheduling decisions occur — the four situations

CPU scheduling decisions may take place when a process:

#TransitionCaused byPreemptive?
1Running → WaitingAn I/O request, or wait() for a childNo — the process gives up the CPU voluntarily
2Running → ReadyAn interrupt, typically the timer expiringYes
3Waiting → ReadyI/O completionYes — the newly ready process may deserve the CPU more
4TerminatesThe process exitsNo
The definition that follows from that table

When scheduling takes place only under 1 and 4, the scheme is non-preemptive (or cooperative) — once a process has the CPU it keeps it until it releases it by terminating or by switching to waiting. Otherwise the scheme is preemptive.

Two costs of preemption worth naming: race conditions on shared data, if a process is preempted while updating it; and the problem of a process being preempted while inside a kernel system call, which is why some kernels wait for the system call to complete before switching.

Scheduling criteria — and the formulas

CriterionDefinitionGoal
1. CPU utilisationThe percentage of time the CPU is busy. Real systems run 40 % (lightly loaded) to 90 % (heavily loaded)Maximise
2. ThroughputThe number of processes completed per unit timeMaximise
3. Turnaround timeThe total time from submission to completion — waiting to get into memory, waiting in the ready queue, executing, and doing I/OMinimise
4. Waiting timeThe total time spent waiting in the ready queue. Scheduling affects only this — it cannot change how long a burst takes or how long I/O takesMinimise
5. Response timeThe time from submission until the first response is produced — not until the output is completeMinimise
The four formulas — learn these exactly Turnaround Time (TAT) = Completion Time − Arrival Time
Waiting Time (WT) = Turnaround Time − Burst Time
Response Time (RT) = First time on CPU − Arrival Time
Average = (sum over all processes) ÷ (number of processes)

Equivalently: WT = CT − AT − BT. Both forms are accepted; the two-step form is safer under pressure.
Four traps that cost marks

1. Forgetting the arrival time. If arrival times are all 0 then TAT = CT, and many students then carry that habit into a question where arrivals differ. Always write TAT = CT − AT even when AT = 0.

2. Confusing waiting time with response time. Waiting time is the total time in the ready queue, possibly accumulated over several visits. Response time counts only until the process first gets the CPU. In non-preemptive scheduling with no idle gaps they coincide; in Round Robin they differ sharply.

3. Ignoring CPU idle time. If no process has arrived yet, the CPU is idle and the Gantt chart must show the gap. Starting the next process too early throws every subsequent number off.

4. Not stating the tie-breaking rule. When two processes have the same burst or priority, say which you chose and why — normally the one that arrived first, or the lower process number. Examiners accept either, but only if you state it.

The answer format that earns full marks

Whatever the algorithm, present it in this order every time:

  1. Name the algorithm and say whether it is preemptive.
  2. Draw the Gantt chart, with time markers under every boundary.
  3. Draw the table: Process | AT | BT | CT | TAT | WT.
  4. Show the averages as a division — write “61 / 4 = 15.25”, not just “15.25”. Partial marks live in that line.
  5. Add one sentence of comment — convoy effect, starvation risk, why this algorithm beat the other. It costs ten seconds and reliably lifts the grade.

Sanity check: the sum of the bursts is 5 + 3 + 2 = 10, and the last completion time is 10 with an arrival at 0, so the CPU was busy throughout. If your final CT exceeds the sum of the bursts, there must be an idle gap in the chart — go back and find it.

Recall without looking

Describe the CPU–I/O burst cycle and the shape of its distribution.

Process execution alternates CPU bursts with I/O bursts, beginning and ending with a CPU burst. The distribution of burst lengths is exponential or hyper-exponential — a very large number of short bursts and a small number of long ones. I/O-bound programs have many short bursts, CPU-bound programs a few long ones.

Distinguish the short-term scheduler from the dispatcher.

The scheduler is policy: it decides which ready process gets the CPU. The dispatcher is mechanism: it switches context, switches to user mode and jumps to the right location to restart the program. The time it takes is dispatch latency, and it is pure overhead.

Name the four situations in which scheduling decisions occur, and say which make a scheme preemptive.

Running to waiting (I/O request or wait for a child), running to ready (interrupt), waiting to ready (I/O completion), and termination. If scheduling occurs only in the first and fourth, the scheme is non-preemptive; otherwise it is preemptive.

Compare preemptive and non-preemptive scheduling on five points.

Non-preemptive: no timer needed, low overhead, poor response time, safe for shared data, suits batch systems, uses FCFS, SJF and non-preemptive priority. Preemptive: needs a timer, higher context-switch overhead, good bounded response time, risks race conditions so needs synchronisation, suits time-sharing and real-time, uses SRTF, preemptive priority and round robin.

Name the five scheduling criteria and say which are maximised.

CPU utilisation and throughput are maximised. Turnaround time, waiting time and response time are minimised. Real systems run at 40 to 90 % CPU utilisation.

Give the three formulas.

TAT = CT − AT. WT = TAT − BT, equivalently CT − AT − BT. RT = first time on the CPU − AT. Averages are the sums divided by the number of processes.

Name the four traps in scheduling numericals.

Forgetting to subtract the arrival time; confusing waiting time with response time; ignoring CPU idle time when no process has arrived; and failing to state the tie-breaking rule when two processes have equal burst or priority.
