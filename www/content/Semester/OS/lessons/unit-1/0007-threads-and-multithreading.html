What a thread is

Definition A thread is a basic unit of CPU utilisation. It comprises a thread ID, a program counter, a register set and a stack.

It shares with other threads of the same process: the code section, the data section, and other OS resources such as open files and signals.

A thread is also called a lightweight process (LWP); a traditional process is a heavyweight process.
Each thread has its ownAll threads of a process share
Thread IDCode (text) section
Program counterData section — globals and statics
Register setHeap
StackOpen files, signals, address space
The sentence that answers half the questions on this topic

A thread owns exactly what it needs to execute independently — PC, registers, stack — and shares everything else. That is why creating a thread is cheap, why switching between threads is cheap, and why threads need synchronisation while separate processes do not.

Single-threaded and multithreaded processes

A single-threaded process has one program counter and performs one task at a time. A multithreaded process has several program counters within the same address space, so it can perform several tasks at once.

Examples worth quoting: a web browser displays images and text in one thread while retrieving data over the network in another; a word processor runs a display thread, a keystroke thread and a background spell-checking thread; a web server creates a thread per client request rather than a process per request.

Benefits of multithreading — the four-mark list

BenefitExplanation
1. ResponsivenessAn interactive application keeps running even if part of it is blocked or performing a long operation — the browser stays usable while an image downloads
2. Resource sharingThreads share the memory and resources of their process by default, with no explicit arrangement — unlike processes, which need shared memory or message passing set up
3. EconomyAllocating memory and resources for process creation is costly; threads share them, so creating and context-switching threads is far cheaper
4. ScalabilityOn a multiprocessor architecture, threads may run in parallel on different cores. A single-threaded process can only ever use one core, however many exist

Three thread libraries to name: POSIX Pthreads (a specification, implemented at user or kernel level), Windows threads (kernel level), and Java threads (implemented using whatever the host OS provides).

Multithreading models — draw all three

The models answer one question: how are user threads mapped onto kernel threads?

1. Many-to-one

Many-to-one U   U   U   U  ← user threads
\   |   |   /
K  ← a single kernel thread

Many user threads mapped to one kernel thread. Thread management is done by the library in user space, so it is efficient.

  • Advantage: thread creation and switching are very fast — entirely in user space.
  • Disadvantage 1: a single blocking system call blocks the entire process.
  • Disadvantage 2: no true parallelism — only one thread can access the kernel at a time, so multiple cores are useless.
  • Examples: Solaris Green Threads, GNU Portable Threads. Few systems still use it.

2. One-to-one

One-to-one U    U    U    U  ← user threads
|     |     |     |
K    K    K    K  ← one kernel thread each

Each user thread gets its own kernel thread.

  • Advantage 1: more concurrency — when one thread blocks, another runs.
  • Advantage 2: true parallelism on multiprocessors.
  • Disadvantage: creating a user thread means creating a kernel thread, and the overhead of creating kernel threads can burden performance. Most implementations therefore restrict the number of threads supported.
  • Examples: Linux, Windows — that is, almost everything modern.

3. Many-to-many

Many-to-many U   U   U   U   U  ← many user threads
\   \   |   /   /
K     K     K  ← a smaller number of kernel threads

Multiplexes many user threads onto a smaller or equal number of kernel threads. The developer may create as many user threads as necessary, and the corresponding kernel threads can run in parallel.

  • Advantage: combines both benefits — no artificial limit on user threads, and real concurrency, since blocking one thread lets the kernel schedule another.
  • Disadvantage: difficult to implement; and because most systems now have many cores, the effort of limiting kernel threads has stopped being worthwhile.
  • Variant — the two-level model: like many-to-many, but it also allows a user thread to be bound to a kernel thread. Examples: IRIX, HP-UX, older Solaris.

Multicore programming

Placing several computing cores on a single chip. Two words must be kept apart:

ConcurrencyParallelism
More than one task can make progressMore than one task is executed at the same instant
Possible on a single core, by interleavingRequires multiple cores
Every parallel system is concurrentNot every concurrent system is parallel

Five challenges of multicore programming — a clean 5-mark list:

  1. Identifying tasks — finding areas that can be divided into separate, concurrent tasks.
  2. Balance — making sure the tasks do equal work of equal value, or a core will idle.
  3. Data splitting — dividing the data the tasks operate on across the cores.
  4. Data dependency — where one task depends on another's data, execution must be synchronised.
  5. Testing and debugging — far harder than for single-threaded code, since execution paths are many and timing-dependent.

Two kinds of parallelism: data parallelism distributes subsets of the same data across cores, each doing the same operation (summing halves of an array); task parallelism distributes different threads doing different operations across cores.

Numerical — Amdahl's law

Amdahl's law speed-up ≤ 1 / ( S + (1 − S) / N )

where S is the fraction of the program that is strictly serial and N is the number of processing cores.
As N → ∞, the speed-up approaches 1 / S — the hard ceiling.
Q1. An application is 75 % parallel and 25 % serial. Find the speed-up on 2 cores and on 4 cores, and the maximum possible speed-up.

Here S = 0.25 and 1 − S = 0.75.

N = 2:   speed-up = 1 / (0.25 + 0.75/2) = 1 / (0.25 + 0.375) = 1 / 0.625 = 1.6

N = 4:   speed-up = 1 / (0.25 + 0.75/4) = 1 / (0.25 + 0.1875) = 1 / 0.4375 = 2.286

N → ∞:   speed-up → 1 / S = 1 / 0.25 = 4

Reading: doubling from 2 cores to 4 gains only 0.69, and no number of cores can ever beat 4×. That ceiling is the entire lesson of Amdahl's law: the serial fraction, not the core count, sets the limit.

Q2. A program has a 5 % serial portion. What speed-up is achievable on 8 cores, and what is the theoretical maximum?

S = 0.05, N = 8.

speed-up = 1 / (0.05 + 0.95/8) = 1 / (0.05 + 0.11875) = 1 / 0.16875 = 5.926

Maximum = 1 / 0.05 = 20×

Sanity check: the speed-up must always be less than N and less than 1/S. Here 5.93 < 8 and 5.93 < 20. Both hold. If your answer ever exceeds N, you have inverted the formula.

Q3 — the reverse question. How much of a program must be parallelisable to achieve a 10× speed-up on 16 cores?

Let the parallel fraction be P, so S = 1 − P. We need

10 = 1 / ((1 − P) + P/16)  ⇒  (1 − P) + P/16 = 0.1

1 − P + 0.0625P = 0.1  ⇒  1 − 0.9375P = 0.1  ⇒  0.9375P = 0.9

P = 0.96 — the program must be 96 % parallel, leaving only 4 % serial.

Reading: a 4 % serial fraction already caps you at 25× whatever the hardware. Getting to a 10× real speed-up therefore demands near-total parallelisation — which is why writing parallel software is hard, and why the question is worth asking on an exam.

Threading issues

IssueThe problemResolution
fork() and exec() semanticsIf a thread in a multithreaded process calls fork(), does the new process duplicate all threads or only the calling one?UNIX provides both versions. If exec() is called immediately after, duplicating only the calling thread is right, since everything is about to be replaced anyway
Signal handlingWhich thread of a multithreaded process should receive a signal?Four options: deliver to the thread the signal applies to; to every thread; to certain threads; or to a designated specific thread that handles all signals. Synchronous signals (divide by zero) go to the causing thread; asynchronous ones (Ctrl-C) to any or all
Thread cancellationTerminating a thread before it finishes — the target threadAsynchronous cancellation: terminate it immediately — risks leaving shared data inconsistent and resources unfreed. Deferred cancellation: the target checks periodically at cancellation points whether it should stop — safer, and the default
Thread-local storage (TLS)A thread sometimes needs its own copy of certain data, not the shared version — a transaction ID, for instanceTLS gives each thread private data that persists across function calls. Distinguish it from local variables, which vanish when the function returns
Thread poolsCreating a thread per request is costly and unbounded — a server could be overwhelmedCreate a pool of threads at start-up that wait for work. Faster (the thread already exists) and it bounds the number of threads
Scheduler activationsIn many-to-many models, the user library and the kernel must communicateThe kernel gives the application a set of virtual processors (LWPs) and notifies it of events by upcalls, handled by an upcall handler in the library

Check yourself

1. Which of these is NOT shared between threads of the same process?

Each thread has its own thread ID, program counter, register set and stack. Everything else — code, data, heap, files, signals — is shared.

2. In the many-to-one model, a blocking system call:

The kernel sees just one schedulable entity, so it has no way to run the other user threads. That, plus the absence of real parallelism, is why the model has largely died out.

3. The main drawback of the one-to-one model is:

One-to-one is what Linux and Windows actually use. Its cost is that every user thread is a kernel object, so most implementations restrict how many you may create.

4. A program is 90 % parallel. Its maximum speed-up, on any number of cores, is:

S = 0.10, so the ceiling is 1/S = 10. On 8 cores you would get 1/(0.1 + 0.9/8) = 4.71 — still well short of the ceiling.

5. Deferred cancellation is safer than asynchronous cancellation because:

Killing a thread mid-update can leave shared structures half-written and resources unreleased. Deferred cancellation lets the thread choose a safe moment.

6. Concurrency without parallelism means:

Parallelism needs multiple cores; concurrency only needs interleaving. Every parallel system is concurrent, but not the reverse.

7. A thread pool improves on creating a thread per request because it:

The thread already exists, so there is no creation cost, and the pool size caps how many threads can ever exist — which protects the server from being overwhelmed.

Recall without looking

Define a thread, and say exactly what it owns and what it shares.

A thread is a basic unit of CPU utilisation, comprising a thread ID, program counter, register set and stack. It shares the code section, data section, heap and other OS resources such as open files and signals with the other threads of its process. It is also called a lightweight process.

Compare process and thread on six points.

Address space: separate vs shared. Creation cost: high vs low. Context switch: expensive vs cheap. Communication: needs IPC vs direct through shared variables. Isolation: strong vs none, since one thread crashing kills the process. Synchronisation: only when data is deliberately shared vs always.

Give the four benefits of multithreading.

Responsiveness — the application keeps running while part of it blocks. Resource sharing — threads share memory and resources by default. Economy — creation and context switching are far cheaper than for processes. Scalability — threads can run in parallel on multiple cores, which a single-threaded process never can.

Compare user-level and kernel-level threads.

User-level threads are managed by a library above the kernel, are very fast to create and switch, are portable, but block the whole process on a blocking call and give no true parallelism. Kernel-level threads are managed and scheduled by the OS, are slower because every operation is a system call, but block only themselves and can run in parallel on multiple cores.

Describe the three multithreading models with one advantage and one disadvantage each.

Many-to-one: efficient user-space management, but one blocking call stops the process and there is no parallelism. One-to-one: real concurrency and parallelism, but a kernel thread per user thread is costly, so the count is capped; used by Linux and Windows. Many-to-many: combines both benefits with no artificial limit, but is difficult to implement; the two-level model additionally allows binding a user thread to a kernel thread.

Distinguish concurrency from parallelism, and name the five multicore challenges.

Concurrency means several tasks make progress, possible by interleaving on one core; parallelism means they execute at the same instant, requiring multiple cores. The challenges are identifying tasks, balance, data splitting, data dependency, and testing and debugging.

State Amdahl's law and its consequence.

speed-up ≤ 1 / (S + (1 − S)/N), where S is the serial fraction and N the number of cores. As N grows without bound the speed-up approaches 1/S, so the serial fraction — not the core count — sets the ceiling. A 25 % serial program can never beat 4×.

Name the six threading issues.

fork() and exec() semantics, signal handling, thread cancellation (asynchronous vs deferred), thread-local storage, thread pools, and scheduler activations with LWPs and upcalls.
