Four reasons for allowing process cooperation — a standard 4-mark list:

  1. Information sharing. Several users may want the same piece of information, such as a shared file.
  2. Computation speed-up. A task split into subtasks running in parallel finishes sooner — but only on a machine with multiple processing cores.
  3. Modularity. Divide the system into separate processes or threads, each with one job.
  4. Convenience. Even one user works on many tasks at once — editing, printing and compiling in parallel.

The two IPC models

The fundamental split 1. Shared memory. A region of memory is established that both processes map into their address spaces. They then read and write that region as ordinary memory. The OS is involved only once, to set the region up.

2. Message passing. Processes exchange discrete messages through the kernel using send() and receive(). Every message is a system call.
 Shared memoryMessage passing
SpeedFaster — at memory speed, no kernel involvement after setupSlower — a system call per message, plus copying
Kernel involvementOnly to create the shared regionOn every send and every receive
SynchronisationThe programmer's responsibility — the processes must not write the same location at onceHandled by the OS — messages are delivered atomically
SuitsLarge volumes of data; processes on the same machineSmall amounts of data; processes on different machines, over a network
Ease of implementationHarder to program correctly — race conditions are the programmer's problemEasier — no shared state to corrupt
ConflictsPossible — needs semaphores or monitors (Unit II)None — nothing is shared

The one-line contrast

Shared memory is faster but leaves synchronisation to you; message passing is slower but the OS keeps it safe. Everything else in this lesson elaborates that sentence.

Shared memory — the producer–consumer problem

The paradigm for cooperating processes: a producer process produces items that a consumer process consumes. A compiler produces assembly code consumed by an assembler; a web server produces HTML consumed by a browser.

Buffer typeRule
Unbounded bufferNo practical limit on size. The consumer may have to wait for items, but the producer never waits
Bounded bufferFixed size. The consumer waits if the buffer is empty; the producer waits if the buffer is full
Bounded buffer — shared data
#define BUFFER_SIZE 10
item buffer[BUFFER_SIZE];
int in = 0;   /* next free position */
int out = 0;  /* first full position */
Buffer is empty when in == out. Buffer is full when ((in + 1) % BUFFER_SIZE) == out.
ProducerConsumer
item next_produced;
while (true) {
  /* produce an item */
  while (((in + 1) % BUFFER_SIZE) == out)
    ;  /* buffer full — do nothing */
  buffer[in] = next_produced;
  in = (in + 1) % BUFFER_SIZE;
} 		item next_consumed;
while (true) {
  while (in == out)
    ;  /* buffer empty — do nothing */
  next_consumed = buffer[out];
  out = (out + 1) % BUFFER_SIZE;
  /* consume the item */
}
The limitation to state — it is worth a mark

This solution can use only BUFFER_SIZE − 1 elements out of BUFFER_SIZE. One slot is deliberately wasted, because otherwise “full” and “empty” would both be in == out and could not be told apart. Using all N slots requires a counter variable — and that counter is precisely what creates a race condition, which is where Unit II begins.

Message passing

A message-passing facility provides two operations: send(message) and receive(message). If two processes want to communicate, a communication link must exist between them. Three design questions must be settled, and “discuss the issues in message passing” means exactly these three.

Question 1 — naming: direct or indirect?

 Direct communicationIndirect communication
Syntaxsend(P, msg) — send to process P
receive(Q, msg) — receive from process Q		send(A, msg) — send to mailbox A
receive(A, msg) — receive from mailbox A
Who is namedThe process, explicitlyA mailbox / port, which has a unique id
Link establishedAutomatically, between exactly one pairOnly if both processes share a mailbox
Links per pairExactly oneSeveral possible — one per shared mailbox
Number of processesExactly two per linkMany may share a mailbox
WeaknessPoor modularity — changing a process's identifier means finding and changing every reference to itMore OS machinery: mailboxes must be created, owned and deleted

Direct communication also has an asymmetric variant, in which only the sender names the receiver; the receiver's call, receive(id, msg), sets id to whichever process sent the message.

The mailbox-sharing problem: if P1, P2 and P3 all share mailbox A, and P1 sends while both P2 and P3 execute receive — who gets the message? Three solutions: allow a link between at most two processes; allow only one process at a time to execute receive; or let the system choose arbitrarily, using an algorithm such as round robin, and tell the sender who received it.

Question 2 — synchronisation: blocking or non-blocking?

OperationBlocking (synchronous)Non-blocking (asynchronous)
SendThe sender is blocked until the message is received by the receiving process or mailboxThe sender sends and immediately resumes
ReceiveThe receiver blocks until a message is availableThe receiver retrieves either a valid message or a null, and continues either way

The four combinations are all legal. When both send and receive are blocking, the pair is called a rendezvous — a term worth using, because it earns a mark on its own. Note also that with blocking send and blocking receive, the producer–consumer solution becomes trivial: no explicit buffer management is needed at all.

Question 3 — buffering: how many messages can wait?

Queue capacityBehaviourAlso called
Zero capacityThe queue holds no messages, so the sender must block until the receiver takes the messageA message system with no buffering; a rendezvous
Bounded capacityThe queue holds at most n messages. If it is not full the sender continues; if it is full the sender blocks until space appearsAutomatic buffering
Unbounded capacityThe queue is potentially infinite, so the sender never blocksAutomatic buffering

Numerical — shared memory against message passing

Q. Two processes must exchange 1 MB of data. A system call costs 2 µs, a message may carry at most 4 KB, and copying costs 0.5 µs per KB. Setting up a shared-memory region costs one system call plus 50 µs. Compare the two models.

Message passing. Number of messages = 1024 KB ÷ 4 KB = 256 messages.

Each message needs a send and a receive, so 2 system calls: 2 × 2 = 4 µs. Copying 4 KB costs 0.5 × 4 = 2 µs, and the data is copied twice — sender to kernel buffer, kernel to receiver — so 4 µs.

Cost per message = 4 + 4 = 8 µs  →  Total = 256 × 8 = 2048 µs ≈ 2.05 ms

Shared memory. Setup = 1 system call (2 µs) + 50 µs = 52 µs. After that the data is written once and read once directly, with no kernel involvement: 2 × (0.5 × 1024) = 1024 µs.

Total = 52 + 1024 = 1076 µs ≈ 1.08 ms

Shared memory is about 1.9× faster here, and the gap widens with the volume of data, because the setup cost is paid once while the per-message system-call cost is paid 256 times.

Sanity check: for a single small message the verdict reverses. One 4 KB exchange costs 8 µs by message passing but 52 + 4 = 56 µs by shared memory, because the setup dominates. That is exactly why the rule is “shared memory for bulk data, message passing for small or remote exchanges.”

Both parties wait until the exchange happens. It also corresponds exactly to the zero-capacity buffering case.

Hard-coding process names into send and receive calls is brittle. Mailboxes decouple sender from receiver, which is why indirect communication is more flexible.

5. An ordinary (anonymous) pipe requires:

Ordinary pipes are unidirectional and only work between related processes. Named pipes (FIFOs) have a file-system name and work between any processes.

Zero capacity means no message can wait anywhere, so the two must meet — a rendezvous. Bounded capacity blocks only when full; unbounded capacity never blocks the sender.

Recall without looking

Give four reasons for allowing process cooperation.

Information sharing, computation speed-up, modularity and convenience. Speed-up only helps if the machine actually has multiple processing cores.

Compare shared memory and message passing on six points.

Shared memory is faster, involves the kernel only at setup, leaves synchronisation to the programmer, suits large volumes on one machine, is harder to program, and can suffer conflicts. Message passing is slower, involves the kernel on every send and receive, has synchronisation handled by the OS, suits small amounts and machines across a network, is easier to program, and has no conflicts.

State the empty and full conditions of the bounded buffer.

Empty when in == out. Full when (in + 1) % BUFFER_SIZE == out. Only BUFFER_SIZE − 1 slots can be used, because otherwise the two conditions would be identical.

Name the three design questions of message passing.

Naming — direct (name the process) or indirect (name a mailbox or port). Synchronisation — blocking or non-blocking send and receive, with blocking-blocking called a rendezvous. Buffering — zero, bounded or unbounded capacity.

Compare direct and indirect communication.

Direct names the process explicitly, links form automatically between exactly one pair, and modularity is poor because identifiers are hard-coded. Indirect names a mailbox, requires both processes to share it, allows many processes per mailbox and several links per pair, but needs more OS machinery.

Compare ordinary and named pipes.

Ordinary pipes are unidirectional, need a parent–child relationship, have no file-system name and die with the processes. Named pipes (FIFOs) are bidirectional — half duplex on UNIX — need no relationship, have a name created by mkfifo() and persist until deleted.

Name four real IPC systems and the model each uses.

POSIX shared memory (shm_open, mmap) uses shared memory. Mach uses message passing to ports. Windows ALPC uses ports but switches to shared-memory section objects for large messages. Pipes, sockets and RPC use message passing, with sockets and RPC working across a network.
