Process vs program

Definition A process is a program in execution — an active entity, with a program counter specifying the next instruction, a set of associated resources, and its own memory image.

A program is a passive entity — a file of instructions stored on disk, an executable file.

The memory layout of a process — four sections

Process in memory (high address at top) STACK — temporary data: function parameters, return addresses, local variables. Grows downward.
↓    (free space)    ↑
HEAP — memory dynamically allocated at run time (malloc, new). Grows upward.
DATA — global and static variables
TEXT — the program code itself, and the program counter

Stack and heap grow toward each other; the OS must make sure they never overlap. Note that text and data sizes are fixed at load time, while stack and heap shrink and grow dynamically.

Process states — draw this every time

Three traps in this diagram

1. There is no arrow from WAITING to RUNNING. A process that finishes its I/O goes back to READY, not straight to the CPU — it must be dispatched again. Drawing that arrow wrongly costs the mark.

2. There is no arrow from READY to WAITING. Only a running process can request I/O.

3. Only one process is RUNNING per CPU at any instant, but many can be READY and many WAITING.

Two extra states appear when swapping is involved: suspended-ready and suspended-blocked — processes swapped out of main memory to the backing store by the medium-term scheduler. Add them only if the question mentions swapping or a seven-state model.

The Process Control Block

Definition The Process Control Block (PCB), also called the task control block, is the data structure in the operating system that represents a process. It holds all the information the OS needs about that process. It is created when the process is created and destroyed when the process terminates.
#FieldContents
1Process stateNew, ready, running, waiting or terminated
2Process number / PIDThe unique identifier of the process
3Program counterThe address of the next instruction to execute
4CPU registersAccumulators, index registers, stack pointers, general-purpose registers, condition codes — saved on interrupt so execution can resume exactly
5CPU scheduling informationPriority, pointers to scheduling queues, other scheduling parameters
6Memory management informationBase and limit registers, page tables or segment tables
7Accounting informationCPU time used, real time elapsed, time limits, account numbers, job or process numbers
8I/O status informationList of I/O devices allocated, list of open files

The PCB is the process, as far as the OS is concerned. Everything the OS knows about a process is in there, which is why saving and restoring it is the context switch.

The queueing diagram shows a process leaving the ready queue for the CPU, and then either (a) issuing an I/O request and joining a device queue, (b) creating a child and waiting for it, or (c) being removed forcibly by an interrupt — in all three cases eventually returning to the ready queue.

The point about the job mix

An I/O-bound process spends more time doing I/O than computation, in many short CPU bursts. A CPU-bound process spends more time computing, in a few very long bursts. The long-term scheduler must select a good mix of both. All-I/O-bound leaves the CPU idle; all-CPU-bound leaves the device queues empty. That sentence is a standard 3-mark answer.

Context switch

Definition A context switch is the mechanism of saving the state of the currently running process into its PCB and loading the saved state of the next process from its PCB, so that the CPU can be switched from one process to another.
  • Context-switch time is pure overhead — the system does no useful work while switching. Typical cost: a few microseconds.
  • The cost depends on hardware support: some machines have multiple register sets, so a switch is only a change of pointer.
  • A context switch is not a mode switch. A mode switch changes privilege within one process; a context switch changes which process holds the CPU. Every context switch involves mode switches, but not every mode switch is a context switch.

Operations on processes

Process creation

A process may create several new processes with a create-process system call. The creator is the parent, the new process the child; children may create further children, forming a process tree. Each process has a unique process identifier (PID). In UNIX the root of the tree is init or systemd, with PID 1.

Design questionOptions
Resource sharingParent and child share all resources; or the child shares a subset; or they share nothing
ExecutionParent and child execute concurrently; or the parent waits until the child terminates
Address spaceThe child is a duplicate of the parent (fork()); or the child has a new program loaded into it (exec())
The UNIX idiom — know the return values pid = fork();

In the child, fork() returns 0.
In the parent, fork() returns the PID of the child (a positive number).
On failure it returns −1, and no child is created.

exec() replaces the process's memory image with a new program — it does not return on success.
wait() makes the parent block until a child terminates.
exit() terminates the calling process and returns a status to the parent.

Process termination

A process terminates when it finishes and calls exit(). The parent may also terminate a child with abort(), for three reasons: the child exceeded its allocated resources; the task assigned to it is no longer required; or the parent itself is exiting and the OS does not permit orphaned children.

TermMeaning
Zombie processA process that has terminated but whose parent has not yet called wait(). Its PCB entry is kept so the exit status can be collected. Every terminated process is briefly a zombie
Orphan processA process whose parent terminated first. In UNIX it is re-parented to init, which reaps it
Cascading terminationKilling a process automatically kills all its descendants. Initiated by the OS, in systems that do not permit orphans

Numerical 1 — counting processes from fork()

The rule n successive, unconditional fork() calls produce 2n total processes — that is 2n − 1 child processes, plus the original parent.
A printf placed after all the forks therefore executes 2n times.
Q1. How many processes are created, and how many times is “Hello” printed?

main() {
  fork();
  fork();
  fork();
  printf("Hello");
}

Trace it as a doubling. Start with 1 process.

AfterProcesses alive
start1
1st fork()2
2nd fork()4
3rd fork()8

Total processes = 23 = 8. Child processes created = 8 − 1 = 7. “Hello” is printed 8 times.

Why: every existing process executes every remaining fork(), so the population doubles at each one.

Q2. A conditional fork — how many processes, and what is printed?

main() {
  if (fork() == 0) {
    fork();
    printf("A");
  } else {
    printf("B");
  }
}

Step 1. The original process P executes fork(). Two processes now exist: P and child C1.

Step 2. In P, fork() returned C1's PID, which is non-zero, so the condition is false → P takes the else branch and prints B.

Step 3. In C1, fork() returned 0, so the condition is true → C1 executes the inner fork(), creating C2. Both C1 and C2 then print A.

Answer: 3 processes in total (P, C1, C2); 2 child processes created. Output: one B and two A’s — 3 characters, in an order that is not determined.

Sanity check: the ordering of the output is non-deterministic because the processes are scheduled independently — say so, it is worth a mark.

Q3. Forks inside a loop

for (i = 0; i < 4; i++)
   fork();
printf("X");

The loop body executes fork() four times, and every process created also continues the loop from its own value of i, so it behaves exactly like four successive forks.

Total processes = 24 = 16. Children created = 15. “X” printed 16 times.

Watch for the trap version: if the code were if (fork() == 0) fork(); inside the loop, the doubling no longer applies and you must draw the tree.

Numerical 2 — context-switch overhead

Q. A system performs a context switch every 10 ms. Each context switch takes 0.1 ms. What percentage of CPU time is lost to switching? What if the switch interval is reduced to 1 ms?

Case A — 10 ms interval. Each cycle is 10 ms of useful work plus 0.1 ms of switching, so the cycle length is 10.1 ms.

Overhead = 0.1 / 10.1 = 0.00990 = 0.99 %   →   about 99 % of the CPU does useful work.

Case B — 1 ms interval. Cycle = 1 + 0.1 = 1.1 ms.

Overhead = 0.1 / 1.1 = 0.0909 = 9.09 %   →   only about 91 % is useful work.

Reading: a ten-times shorter quantum gives ten-times better responsiveness but multiplies the overhead by about nine. This is exactly the trade-off behind choosing the time quantum in round robin, which Lesson 9 works in full.

Sanity check: overhead must rise as the interval falls, and must approach 0 as the interval grows large. With a 100 ms interval it would be 0.1/100.1 = 0.0999 %, which fits the pattern.

Check yourself

1. A process that completes its I/O moves to which state?

There is no arrow from waiting to running. The process must rejoin the ready queue and be dispatched again by the short-term scheduler.

2. Which scheduler controls the degree of multiprogramming?

The long-term scheduler decides how many processes enter the ready queue. The medium-term scheduler can only reduce it, by swapping processes out.

3. In the child process, fork() returns:

Child gets 0; parent gets the child's PID; failure gives −1. Every conditional-fork numerical turns on this one fact.

4. Three successive unconditional fork() calls create how many child processes?

2³ = 8 processes exist in total, one of which is the original — so 7 children. Read the question carefully: “processes” means 8, “child processes” means 7.

5. A terminated process whose parent has not yet called wait() is called:

Zombie = dead child, parent hasn't reaped it. Orphan = live child, parent already dead — re-parented to init.

6. Which is NOT stored in the PCB?

The PCB holds metadata about the process, not the program text — the code lives in the process's own text section in memory.

7. A good long-term scheduler selects:

All-CPU-bound leaves the device queues empty; all-I/O-bound leaves the ready queue empty and the CPU idle. A mix keeps both busy.

Recall without looking

Distinguish a program from a process on five points.

A program is passive, lives on disk, is permanent, holds no resources, and one program can spawn many processes. A process is active, lives in main memory, is temporary, holds CPU, memory, files and devices, and runs one program at a time.

Name the four sections of a process in memory.

Text (the code and program counter), data (globals and statics), heap (dynamically allocated at run time, growing upward) and stack (parameters, return addresses and locals, growing downward). Text and data are fixed in size; heap and stack grow toward each other.

Draw the five-state process diagram with all transitions named.

New —admitted→ Ready —scheduler dispatch→ Running —exit→ Terminated. Running —interrupt→ Ready. Running —I/O or event wait→ Waiting. Waiting —I/O or event completion→ Ready. There is no arrow from waiting to running, and none from ready to waiting.

List the eight fields of the PCB.

Process state; process number (PID); program counter; CPU registers; CPU scheduling information such as priority; memory management information such as base and limit registers or page tables; accounting information such as CPU time used; and I/O status information such as open files and allocated devices.

Compare the three schedulers.

Long-term (job scheduler): new to ready, slowest, controls the degree of multiprogramming, mostly absent in time-sharing systems. Short-term (CPU scheduler): ready to running, fastest — every few milliseconds — and must itself be very fast because it is overhead. Medium-term (swapper): swaps processes out to backing store and back, reducing the degree of multiprogramming.

Define a context switch, and distinguish it from a mode switch.

A context switch saves the state of the running process into its PCB and loads the state of the next process from its PCB. It is pure overhead. A mode switch changes privilege level within one process; a context switch changes which process holds the CPU.

Give the return values of fork() and the process-counting rule.

fork() returns 0 in the child, the child's PID in the parent, and −1 on failure. n successive unconditional forks give 2ⁿ total processes, that is 2ⁿ − 1 children, and a printf after them all runs 2ⁿ times.

Define zombie, orphan and cascading termination.

A zombie has terminated but its parent has not yet called wait(), so its PCB entry is kept for the exit status. An orphan is still running but its parent has terminated; UNIX re-parents it to init. Cascading termination kills all descendants of a terminated process, in systems that do not allow orphans.
