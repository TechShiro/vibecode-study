1 · The One Idea

Even if an application has zero SQL injection or XSS vulnerabilities, flawed authentication and access control will allow attackers to seize administrative control. The #1 API vulnerability in the world is BOLA (Broken Object Level Authorization / IDOR): assuming that because a user is logged in, they are authorized to view any record they request. Modern security relies on cryptographically signed tokens (JWTs), robust session revocation, Multi-Factor Authentication (MFA), and secure identity delegation (OAuth 2.0 / OIDC).

2 · Insecure Direct Object References (IDOR / BOLA)

The Anatomy of an IDOR Attack

Victim logs in as user 105 and accesses their medical profile: GET /api/profile?user_id=105. Attacker modifies the request parameter to GET /api/profile?user_id=106. If the backend fails to verify whether the authenticated session user matches the requested object's owner, sensitive records of all users are dumped!

Defense: Never rely on client-supplied IDs. Derive the user context directly from the server-side authenticated session or JWT claim: WHERE user_id = current_authenticated_user_id().

3 · JSON Web Token (JWT) Security Pitfalls

A JWT consists of three base64url-encoded parts: Header.Payload.Signature. Common implementation exploits:

  • The "alg": "none" Attack: Early vulnerable JWT libraries accepted tokens where the algorithm was set to none, treating unsigned tokens as valid without verifying signatures!
  • Algorithm Confusion (RSA to HMAC): If the server expects RSA public/private key verification, but the attacker changes alg to HS256 (symmetric HMAC), the server might verify the signature using its public RSA key as the secret HMAC key, allowing anyone to forge signatures.
  • Weak HMAC Secrets: Signing tokens with simple passwords (e.g. secret, password123). Can be cracked offline in seconds using Hashcat: hashcat -m 16500 jwt.txt rockyou.txt.

4 · OAuth 2.0 with PKCE (Proof Key for Code Exchange)

OAuth 2.0 allows third-party applications to access resources on behalf of a user without seeing the user's password. The Authorization Code Grant with PKCE is the mandatory gold standard for mobile and Single Page Apps (SPAs):

Client creates Code Verifier + Code Challenge
Auth Server redirects with Authorization Code
Exchange Code + Verifier for Access Token

Why PKCE matters: PKCE prevents malicious apps from intercepting the authorization code from the OS redirect URI: only the party possessing the secret Code Verifier can exchange the code for the JWT access token.

5 · Modern Strong Authentication: FIDO2 & WebAuthn

SMS OTP and email verification codes are vulnerable to SIM-swapping, SS7 attacks, and reverse proxy phishing (Evilginx). FIDO2 / WebAuthn uses hardware security keys (YubiKey, TouchID) that perform public-key challenge-response cryptography bound to the exact browser domain origin, making phishing mathematically impossible.
