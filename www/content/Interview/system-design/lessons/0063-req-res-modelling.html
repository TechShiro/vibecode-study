Request & Response Object Modelling (DTOs)

Decoupling internal database entities from external API contracts.

↑ Back to Course Index Module O — UML & API Design

1 · The One Idea

Never expose your internal database entity classes (like Hibernate/JPA @Entity models) directly over your public REST API! If you return a UserEntity directly, you risk accidentally leaking the password_hash or internal database IDs to the public internet. Data Transfer Objects (DTOs) create a clean, intentional abstraction boundary between what is stored in the database and what is transmitted over the wire.

2 · Standard API Response Envelope Pattern

Consistent APIs wrap responses in a predictable JSON envelope:

{
  "success": true,
  "data": {
    "userId": "usr_9918",
    "name": "Alice Johnson",
    "email": "alice@example.com"
  },
  "error": null,
  "meta": {
    "timestamp": 1740000000,
    "requestId": "req_a78c1"
  }
}

3 · Consistent Error Payload Pattern (RFC 7807)

When an error occurs, provide structured, machine-readable validation details:

{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Invalid user registration payload",
    "details": [
      { "field": "email", "issue": "Must be a valid email address" },
      { "field": "password", "issue": "Password must be at least 8 characters" }
    ]
  }
}
