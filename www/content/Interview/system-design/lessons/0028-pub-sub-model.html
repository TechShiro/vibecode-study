1 · The One Idea

In traditional point-to-point queues, each message is consumed by exactly one worker. In the Pub/Sub pattern, senders (Publishers) publish events to a named channel or Topic without knowing who (if anyone) is listening. Any number of interested services (Subscribers) subscribe to that topic and each receive an independent copy of the message (Fan-out).

3 · The 3 Message Delivery Semantics

Distributed networks can crash, drop packets, or timeout. How does a message broker guarantee delivery?

Semantic Guarantee Trade-off
At-Most-Once Message is delivered 0 or 1 time. Packets may be lost, but duplicates never happen. Lowest latency; acceptable only for non-critical metrics (e.g. mouse hover tracking).
At-Least-Once Message is guaranteed to be delivered, but network retries may cause duplicate messages. The industry standard! Consumers MUST be engineered to be Idempotent.
Exactly-Once Message is guaranteed to be processed exactly once, with zero loss and zero duplicates. Heaviest overhead; requires distributed transaction logs, two-phase commit, or Kafka transactional APIs.

4 · Idempotency: The Universal Antidote to Duplicates

Because distributed systems almost always operate on At-Least-Once delivery, your consumer service will inevitably receive duplicate messages (e.g., network timeout during ACK). How do you prevent double-charging a credit card?

The Idempotency Key Pattern

Every message includes a unique idempotency_key (UUID). Before processing, the consumer checks a database or Redis: IF EXISTS(key) -> SKIP. If not, it executes the operation and records the key inside the same database transaction. Any duplicate message is recognized and ignored safely!
