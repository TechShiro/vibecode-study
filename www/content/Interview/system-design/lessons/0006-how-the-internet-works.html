How the Internet Works

Before you can design a massive distributed system, you must understand exactly what happens in the milliseconds after a user presses "Enter" in their browser.

Track goal: Master System Design for interviews — HLD + LLD. This is Lesson 6 of 66. Index

1 · The One Idea

The internet is essentially a massive web of physical cables connecting computers. To send a message (like a web page) from a server to a client, the system must translate a human-readable name into a machine IP address (DNS), establish a reliable connection (TCP), secure that connection (TLS/SSL), and finally request and transfer the data (HTTP).

2 · The Journey of a Request (Step-by-Step)

When a user types https://www.google.com into their browser, a highly orchestrated sequence of events occurs.

Step 1: DNS Resolution (Finding the Address)

Computers communicate using IP addresses (e.g., 142.250.190.46), not names. The browser needs to find the IP.

  1. Browser Cache: Checks if it already knows the IP.
  2. OS Cache: Checks the operating system's DNS cache.
  3. Resolver: Asks the ISP's DNS resolver.
  4. Root/TLD/Authoritative Servers: If nobody has it cached, the request traverses the global DNS hierarchy until the Authoritative Name Server for google.com returns the IP address.

Step 2: TCP 3-Way Handshake (Establishing the Connection)

Before sending HTTP data, the client and server must agree to talk. TCP (Transmission Control Protocol) guarantees reliable, ordered delivery.

  • SYN: Client says, "Hello, I want to talk. Here is my initial sequence number (x)."
  • SYN-ACK: Server replies, "I acknowledge (x+1). I also want to talk, here is my number (y)."
  • ACK: Client replies, "I acknowledge (y+1). Let's begin."

Step 3: TLS Handshake (Securing the Connection)

Because the URL is https:// (secure), the data must be encrypted so no one sniffing the network can read it.

  • Client and server negotiate which encryption algorithms to use.
  • Server sends its SSL Certificate (containing its Public Key).
  • Client verifies the certificate with a trusted Certificate Authority (CA).
  • They generate a symmetric "session key" used to encrypt the actual HTTP data.

Step 4: HTTP Request & Response (Transferring Data)

Now the browser sends the actual HTTP GET request over the secure TCP connection. The server processes it (hits the DB, renders HTML) and sends back an HTTP Response containing the HTML body.

Step 5: Browser Rendering

The browser parses the HTML, finds links to CSS, JS, and images, and repeats this entire process (usually reusing the existing TCP connection) to fetch those assets and paint the screen.

4 · Critical Concepts for System Design

Interviewers won't ask you to recite the TCP handshake, but they expect you to know the performance implications of how the internet works.

Latency vs Bandwidth

  • Latency: How long it takes a packet to travel from A to B (measured in ms). Constrained by the speed of light.
  • Bandwidth: How much data can be transferred per second (measured in Mbps/Gbps). Constrained by hardware limits (fiber optic cable thickness).
System Design Insight You can buy more bandwidth, but you cannot buy lower latency (you can't beat the speed of light). A request from Tokyo to New York will always take ~150ms round trip. To solve latency, you must bring the data physically closer to the user using CDNs (Content Delivery Networks) or Edge Computing.

Connection Overhead

Look at the diagram above. Setting up a secure connection requires 3 to 4 round trips (DNS, TCP, TLS) before a single byte of application data is sent! If a user is 100ms away, connection setup takes 400ms. This is why modern systems use Connection Pooling (keeping connections open) and Keep-Alive headers to reuse TCP connections for multiple HTTP requests.
