SSO & OAuth 2.0 Architecture

Enabling delegated authorization and frictionless single sign-on across the internet.

1 · The One Idea

In the early internet, if a printing website wanted to print your Flickr photos, it asked you to enter your Flickr username and password directly into the printer site — a horrifying security violation! OAuth 2.0 was created to solve Delegated Authorization: allowing a third-party app to access specific resources on your behalf without ever giving them your password. OpenID Connect (OIDC) is a thin identity layer built on top of OAuth 2.0 to provide Single Sign-On (SSO) ("Log in with Google").

2 · The 4 Roles in OAuth 2.0

  • Resource Owner: The user (You).
  • Client: The third-party application requesting access (e.g. Spotify, Canva).
  • Authorization Server: The identity provider (Google, GitHub, Okta).
  • Resource Server: The API holding the user's data (Google Drive, GitHub Repos).

3 · The Authorization Code Flow (With PKCE)

User Browser
Google Login Dialog
Returns Auth Code
Backend exchanges Code for Token
  1. User Clicks "Sign in with Google": Browser redirects to accounts.google.com/o/oauth2/v2/auth with client_id, redirect_uri, and requested scope (e.g., profile email).
  2. User Consents: Google authenticates the user and shows a consent screen: "Allow Spotify to view your profile?"
  3. Auth Code Redirect: Google redirects back to the app with a temporary Authorization Code in the URL query string (valid for 60 seconds).
  4. Back-Channel Exchange: The app backend makes a secure server-to-server POST request to Google's token endpoint with the Auth Code and client_secret.
  5. Token Delivery: Google returns an ID Token (JWT containing user profile) and an Access Token for API queries!
