Rate Limiting Algorithms & Architecture

Protecting your APIs from denial-of-service attacks, brute force abuse, and accidental traffic floods.

↑ Back to Course Index Module F — Load Balancers & Traffic Management

1 · The One Idea

A Rate Limiter controls the rate of traffic sent by a client or user to your services (e.g., "Maximum 100 requests per minute per IP"). If the request rate exceeds the limit, the limiter rejects the excess requests with HTTP status 429 Too Many Requests and a Retry-After header, ensuring system stability.

2 · The 4 Great Rate Limiting Algorithms

1. Token Bucket (Most Popular — Used by AWS & Stripe)

  • A bucket has a fixed capacity (e.g., 10 tokens) and refills with new tokens at a steady rate (e.g., 2 tokens per second).
  • Every incoming request consumes 1 token.
  • If the bucket has enough tokens, the request is allowed. If empty, the request is dropped (HTTP 429).
  • Strength: Allows short bursts of traffic (up to bucket capacity) while maintaining a strict long-term average rate.

2. Leaky Bucket

  • Requests enter a FIFO queue (bucket) of fixed size.
  • The bucket leaks (processes requests) at a strictly constant, smoothed rate regardless of incoming bursts.
  • If the queue overflows, incoming requests are dropped.
  • Strength: Eliminates bursts completely, ensuring a perfectly smooth flow of traffic to fragile downstream services.

3. Fixed Window Counter

  • Divides time into fixed windows (e.g., 12:00:00 to 12:01:00) with a max counter (e.g., 100 requests).
  • Major Flaw (Edge Burst): A user sends 100 requests at 12:00:59, and another 100 requests at 12:01:01. In a span of 2 seconds, 200 requests pass through, doubling the intended limit!

4. Sliding Window Counter

  • Blends the current window count with the previous window count weighted by elapsed time.
  • Requests = (Current Window Count) + (Previous Window Count * (1 - Percentage of Current Window Elapsed)).
  • Strength: Prevents edge boundary bursts with minimal memory footprint (only stores 2 integers per user).

3 · Distributed Rate Limiting with Redis & Lua Scripts

In a cluster with 50 API servers, local in-memory counters won't work because requests from the same user hit different servers. You store counters in a central in-memory store like Redis.

The Race Condition Trap: Reading a counter from Redis, incrementing it in backend memory, and writing it back causes race conditions under high concurrency.

Production Solution Execute the rate limiting logic inside a Redis Lua Script. Redis executes Lua scripts atomically in a single thread, guaranteeing zero race conditions and sub-millisecond execution!
