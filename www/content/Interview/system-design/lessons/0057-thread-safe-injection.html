Thread-Safe Injection & Scoped Instances

Managing shared dependencies and state safety across multi-threaded web servers.

↑ Back to Course Index Module N — Concurrency & Thread Safety

1 · The One Idea

In web frameworks like Spring Boot, NestJS, and ASP.NET Core, services are managed by a Dependency Injection (DI) Container. By default, almost all beans and services are created with Singleton Scope: a single shared instance handles requests from 500 concurrent worker threads simultaneously! If your singleton service holds even one mutable instance variable (e.g. private String currentUserId;), concurrent threads will overwrite each other's data, causing catastrophic security leaks.

2 · The Golden Rule of Singleton Services

Rule of Thumb Singleton services MUST BE 100% STATELESS OR IMMUTABLE! Never store user-specific request state in an instance variable of a singleton service. 
// DANGEROUS DISASTER: Singleton holding mutable user state
@Service
public class OrderService {
    private String currentUserId; // THREAD SAFETY BUG! Shared across all threads!

    public void processOrder(Order order, String userId) {
        this.currentUserId = userId;
        paymentGateway.charge(this.currentUserId, order.getAmount()); // Might charge wrong user!
    }
}

// CORRECT & THREAD-SAFE: State kept strictly on thread call-stack (local variables)
@Service
public class OrderService {
    public void processOrder(Order order, String userId) {
        paymentGateway.charge(userId, order.getAmount()); // Local parameter = private to thread
    }
}

3 · ThreadLocal & The Thread Pool Memory Leak Trap

ThreadLocal<T> gives each thread its own independent copy of a variable (useful for tracking current Security Context or Trace ID). However, web servers reuse worker threads from a Thread Pool. If you set a value in ThreadLocal and forget to call threadLocal.remove() in a finally block, that data leaks into the next unrelated HTTP request handled by that worker thread (or causes a JVM memory leak)!
