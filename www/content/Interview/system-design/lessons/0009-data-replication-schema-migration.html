Data Replication & Schema Migration

Making sure your data outlives a single server crash and evolves safely.

The one idea

Data replication involves keeping copies of your data across multiple servers (nodes) so that if one server goes up in flames, your system stays alive. Schema migration is the careful art of changing the structure of that data (adding/removing columns) across all those servers without taking your application offline.

Why Replicate?

  1. High Availability (HA): If the primary database dies, a replica can take over immediately (failover).
  2. Read Scalability: Instead of hammering one database with all read and write queries, you can route read queries to the replicas, freeing up the primary for writes.
  3. Geographical Proximity: You can place replicas closer to your users (e.g., one in the US, one in Europe) to reduce read latency.

Architectures

1. Master-Slave (Leader-Follower)

This is the most common pattern. One node is designated as the Leader (Master). All writes must go to the leader. The leader then ships a data log to the Followers (Slaves), which apply the updates to their own local copies. Reads can go to the leader or any follower.

2. Multi-Master (Multi-Leader)

Multiple nodes can accept writes. Used primarily for multi-datacenter deployments. If a user is in the US, they write to the US Master. If a user is in Asia, they write to the Asia Master. The masters then sync with each other.

The Catch: Conflict resolution. If two users edit the same record simultaneously on different masters, you have a collision. You need complex logic (like LWW - Last Write Wins, or custom application logic) to resolve it.

Sync vs Async Replication

How does the leader send data to the follower?

Aspect Synchronous Asynchronous
How it works Leader waits for Follower to confirm it saved the data before responding "Success" to the client. Leader writes data locally, says "Success" to client, and sends data to Follower in the background.
Latency High. Client waits for network roundtrips to all sync replicas. Low. Client gets immediate response.
Durability Perfect. If Leader dies, Follower has 100% of the data. Risky. If Leader dies before background sync, recent writes are permanently lost.
The Replication Lag Trap: In async replication, if a user updates their profile (goes to Leader) and immediately refreshes the page (reads from Follower), they might see their old profile because the Follower hasn't received the update yet. This is Replication Lag. A common fix is "Read-your-own-writes" consistency (route the user's reads to the Leader for a few seconds after a write).

Schema Migration Without Downtime

In a production system, you cannot simply run ALTER TABLE ADD COLUMN on a multi-terabyte database. It will lock the table for hours, causing total system downtime.

How to do it safely:

  1. Backward Compatibility is Mandatory: Your application code must be able to handle the old schema and the new schema simultaneously.
  2. Shadow Writes: Write to the new column/table while continuing to write to the old one.
  3. Backfill: Run a background script to copy old data into the new structure slowly, chunk by chunk, without locking the DB.
  4. Flip the switch: Once backfilled, change the application code to read from the new structure.
  5. Cleanup: Eventually drop the old column/table in a future deployment.

Tools like gh-ost (GitHub) or pt-online-schema-change are often used in MySQL to do this automatically by creating a shadow table, syncing data via replication logs, and swapping them instantaneously.
