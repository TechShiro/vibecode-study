Database Sharding

Splitting your database across completely separate database servers to achieve infinite horizontal scale.

↑ Back to Course Index Module B — Databases

1 · The One Idea

When a single database server runs out of disk space, RAM, or CPU power, buying a bigger machine (vertical scaling) quickly becomes impossibly expensive or hits physical hardware limits. Sharding solves this by breaking one giant database into multiple independent databases called shards, where each shard runs on its own separate machine and holds a unique portion of the total rows.

2 · Partitioning vs Sharding: What's the Difference?

People often mix these terms up. Here is the zero-level difference:

  • Partitioning: Dividing a table into smaller parts on the same database server (e.g., PostgreSQL table partitions stored on different disk directories of one machine).
  • Sharding: Horizontal partitioning across multiple independent physical machines or database instances across a network. Each shard has zero knowledge of the other shards (Shared-Nothing Architecture).

3 · The Shard Key: The Most Critical Decision

The Shard Key (or Partition Key) is the column used to decide which shard stores a specific record. If you pick the wrong shard key, your system will suffer from severe lag and unbalanced servers.

Attributes of a Great Shard Key:

  1. High Cardinality: Must have millions of distinct values (e.g., user_id or uuid), not something like gender or status which only has 2–5 values.
  2. Uniform Distribution: Writes and reads should spread evenly across all shards, preventing any single shard from getting overloaded.
  3. Query Alignment: Most of your application's common queries should include the shard key so the request goes directly to one shard instead of searching every shard in the cluster.

4 · Common Sharding Strategies

Strategy How it Works Pros & Cons
Range-Based Sharding Assign records based on a range of values (e.g., User IDs 1-1M on Shard 1, 1M-2M on Shard 2). Pros: Very simple to query ranges.
Cons: Severe hotspots! If new users are auto-incrementing, 100% of new writes hammer only the latest shard while older shards sit idle.
Hash-Based Sharding Apply a hash function to the key: Shard = Hash(user_id) % Number_of_Shards. Pros: Spreads data uniformly across all shards.
Cons: Resharding is painful when you add more servers, unless you use Consistent Hashing.
Directory-Based (Lookup) Sharding A central lookup service or table maps each key to its designated shard server. Pros: Extremely flexible; easy to move records or balance shards dynamically.
Cons: The lookup service is an extra network hop and a Single Point of Failure (SPOF).
Geographic Sharding Sharding by user country or region (e.g., EU users on Frankfurt servers, US users on Virginia servers). Pros: Ultra-low latency for local users; satisfies GDPR / data sovereignty laws.
Cons: Uneven shard sizes (some countries have 100x more traffic than others).

5 · The 4 Great Nightmares of Sharding

Sharding introduces significant architectural complexity. You should only shard when your database is genuinely bursting at the seams.

1. Cross-Shard Joins

In a single SQL database, JOIN operations are fast and native. When your users table is on Shard 1 and your orders table is on Shard 3, the database cannot perform an internal join. Your backend application must manually query Shard 1, query Shard 3, and stitch the records together in application memory.

2. Cross-Shard Transactions

Executing an ACID transaction across multiple shards requires distributed transaction protocols like Two-Phase Commit (2PC) or the Saga Pattern. These protocols introduce heavy network latency, lock contention, and failure points.

3. The Celebrity (Hotspot) Problem

If you shard Twitter by user_id, a typical user might write 1 tweet a week. But a celebrity account gets 50,000 comments and likes every second. The specific shard hosting that celebrity server will crash under the load, even if the other 99 shards are 95% idle.

4. Resharding & Rebalancing

When your data doubles and you need to grow from 10 shards to 20 shards, redistributing billions of rows across active production databases without downtime is one of the most challenging operations in distributed engineering.

6 · Real-World Architecture: How Instagram Sharded PostgreSQL

Early in its hypergrowth, Instagram hit scale limits on Amazon EC2. Instead of abandoning PostgreSQL for NoSQL, they sharded PostgreSQL using a custom 64-bit ID generator:

  • 41 bits: Milliseconds since custom epoch (gives 69 years of timestamps).
  • 13 bits: Shard ID (supports up to $2^{13} = 8192$ logical shards).
  • 10 bits: Auto-incrementing sequence number (allows 1024 unique IDs per millisecond per shard).

Because the Shard ID is embedded directly inside every entity's primary key, any backend service can immediately determine which shard holds a photo or comment just by bit-shifting its ID — no central lookup table required!

Architecture takeaway Sharding should be your last resort, not your first step. First optimize queries and indexes, then add read replicas, then add a caching layer (Redis). Only shard when writes exceed what a single master instance can physically write to disk.
