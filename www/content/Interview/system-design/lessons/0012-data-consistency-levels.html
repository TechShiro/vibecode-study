Data Consistency & Its Levels

When you write data to a distributed system, how quickly does everyone else see the update?

↑ Back to Course Index Module C — Consistency & Isolation

1 · The One Idea

In a single computer, when you write a variable to memory, any subsequent read immediately returns that new value. But in a distributed system with 5 database replicas across the world, writes take time to travel over network cables. Consistency models define the contract between your database and your application regarding what data a client is guaranteed to observe after a write.

2 · The Spectrum of Consistency Models

Consistency is not a binary yes/no; it exists on a spectrum from strict and slow to loose and blazing fast.

Consistency Level What It Guarantees Real-World Example
Strong Consistency (Linearizability) Once a write completes, every single client across the entire globe will immediately read the newest value. It behaves as if there is only one global copy of the data. Bank account balances, ATM withdrawals, stock trading engines.
Sequential Consistency All operations appear to execute in some sequential order that all nodes agree on, and operations from the same process follow program order. Shared memory architectures, distributed locks.
Causal Consistency Operations that are causally related (e.g., a question followed by an answer) must be seen by all nodes in the same order. Concurrent unrelated writes can be seen in different orders. Chat comments and discussion message boards (answers shouldn't appear before the question).
Read-Your-Own-Writes A single user is guaranteed to always see updates made by themselves, even if other users still see older cached data for a few seconds. Updating your profile picture on Instagram: you see your new photo immediately, while friends might see the change 5 seconds later.
Monotonic Reads If a user reads a value at time $T$, they will never subsequently read an older value from a slower replica (time will never move backward for that reader). Reading email threads: refreshed inbox will never show a vanished email.
Eventual Consistency If no new writes are made, all replicas will eventually converge and hold the exact same data. However, temporary stale reads are completely normal. YouTube view counts, Twitter follower counts, DNS propagation.

3 · Quorum Reads and Writes: The Math of Consistency

Leaderless distributed databases (like Apache Cassandra and AWS DynamoDB) let you mathematically configure your desired consistency using Quorums.

Suppose you have $N$ total replicas for a piece of data:

  • $N$ (Replication Factor): How many copies of the record exist in the cluster.
  • $W$ (Write Quorum): How many replicas must acknowledge a write before it is marked successful.
  • $R$ (Read Quorum): How many replicas must respond to a read request before returning data to the client.
The Golden Quorum Rule

If $W + R > N$, your system guarantees Strong Consistency!

Why? Because the set of nodes written to and the set of nodes read from must overlap by at least one node. That overlapping node will return the newest version timestamp, allowing the client to discard older values.

N = 3 Replicas (Node 1, Node 2, Node 3)
Write to W=2 (Node 1, Node 2)
Read from R=2 (Node 2, Node 3)
Node 2 has the latest write! (W + R = 4 > 3)

4 · Tunable Consistency Trade-offs

  • High Write Performance: Set $W = 1$, $R = N$. Writes are instant, but reads must poll all nodes.
  • High Read Performance: Set $W = N$, $R = 1$. Reads are instant from any single node, but writes are slower because every replica must acknowledge.
  • Balanced (Standard Quorum): Set $W = \lfloor N/2 floor + 1$ and $R = \lfloor N/2 floor + 1$. Tolerates node crashes while preserving strong consistency.
