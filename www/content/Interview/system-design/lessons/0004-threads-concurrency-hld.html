Threads & Concurrency (HLD Perspective)

How does a server handle 10,000 users at the same time? Understanding threading models and I/O is the key to building high-throughput systems from scratch.

1 · The One Idea

To handle multiple requests simultaneously, servers must use concurrency. Historically, this meant assigning one OS thread to every incoming request (Thread-per-Request). However, because OS threads are heavy and spend most of their time blocked on I/O (like waiting for a database), modern high-throughput systems use an Event Loop or Lightweight Threads (Goroutines/Virtual Threads) with Non-blocking I/O to handle tens of thousands of connections on a single machine.

2 · Process vs Thread

Before designing a concurrent system, you must know what executes your code.

  • Process: An isolated executing program. Has its own memory space. Heavy to create. Crashing one process doesn't crash others. (e.g., A running Node.js instance).
  • OS Thread: The smallest unit of execution managed by the OS, living inside a process. Threads in the same process share memory. Creating a thread is cheaper than a process, but still costs ~1MB of RAM and takes time.
  • Lightweight/Virtual Thread: Managed by the programming language runtime (e.g., Go's goroutines, Java 21's virtual threads, Erlang processes), not the OS. They take kilobytes of RAM and you can spawn millions of them.
Context Switching Cost When a CPU core switches from running Thread A to Thread B, it must save Thread A's state and load Thread B's state. This is called a Context Switch. If you have 10,000 OS threads on a 4-core machine, the CPU spends more time context-switching than doing actual work!

3 · Concurrency vs Parallelism

In system design, these mean different things:

ConceptDefinitionAnalogy
ConcurrencyDealing with multiple things at once (structuring the program).One barista making an espresso, frothing milk while it brews, then serving.
ParallelismDoing multiple things at exactly the same time (requires multiple cores).Two baristas, each making a separate drink at the exact same time.

You can have massive concurrency on a single-core CPU (via context switching and event loops). Parallelism strictly requires multiple CPU cores or multiple machines.

4 · The C10K Problem & I/O

In 1999, the "C10K problem" asked: How do we handle 10,000 concurrent connections on a single server?

If you use 1 OS thread per connection, 10,000 connections = 10,000 threads. That requires ~10GB of RAM just for thread stacks, and the CPU thrashes from context switching. The Thread-per-Request model fails at massive scale.

Blocking vs Non-Blocking I/O

Why do we need so many threads in the first place? Because of Blocking I/O.

  • Blocking I/O: When Thread A asks the database for data, Thread A goes to sleep (blocks) for 50ms. It does absolutely nothing while waiting. To handle another request, you must spawn Thread B.
  • Non-Blocking I/O (Async): Thread A fires the database request and immediately moves on to handle another user's request. When the database replies, an interrupt triggers a callback, and Thread A resumes the original task.

6 · How Popular Systems Handle Concurrency

When designing a system from zero, the tech stack you choose dictates your concurrency model.

TechnologyConcurrency ModelHow it scales
Java (Spring MVC), Apache Thread-per-Request A large Thread Pool (e.g., 200 threads). Great for CPU work, poor for massive I/O scale (C10K).
Node.js, Nginx, Redis Event Loop (Single-threaded) Uses non-blocking I/O (epoll/kqueue). Extremely lightweight, easily handles C10K. Bad for CPU-heavy tasks (blocks the loop).
Go (Golang) Goroutines (M:N scheduling) Maps millions of lightweight "goroutines" onto a few OS threads. Gives the easy syntax of blocking code, with the performance of async I/O.
Java 21+ (Spring Boot 3.2+) Virtual Threads (Loom) Similar to Go. Java runtime automatically translates blocking I/O calls into non-blocking OS calls, unmounting the virtual thread.
Erlang, Elixir, Akka Actor Model Millions of isolated "actors" that don't share memory, communicating strictly by message passing. Inherently thread-safe.
Interview Hack: "Don't Block the Event Loop" If you choose Node.js/Python AsyncIO for your architecture, you MUST mention that CPU-intensive tasks (like image processing or parsing massive JSON) will block the single event loop, starving all other requests. You solve this by offloading CPU work to a separate worker queue (like RabbitMQ + Python Celery).

7 · Thread Pools and Connection Pools

Creating and destroying threads (or TCP connections) is expensive. We use Pools to reuse them.

Thread Pools

Instead of new Thread() per request, a server maintains a pool of pre-warmed threads. A request arrives, borrows a thread, uses it, and returns it. If the pool is empty, requests queue up.

Connection Pools (Database)

Databases can only handle a limited number of concurrent TCP connections. If you have 10 horizontally scaled web servers, and each has 200 threads, that's 2,000 potential DB connections. The DB will crash.

Solution: Use a Database Connection Pool (like HikariCP in Java or PgBouncer for PostgreSQL). The app borrows a DB connection, runs the query, and returns it. We keep DB connections relatively low (e.g., 20-50 per server).

Ideal DB Connection Pool Size (PostgreSQL estimation):
Connections = ((Number of CPU Cores * 2) + Effective Spindle Count)

8 · Thread Safety (System Design Perspective)

At an LLD level, thread safety means locks, mutexes, and synchronized blocks. At an HLD level, thread safety means Statelessness and Distributed Locking.

  • Shared State is Evil: If Web Server A and Web Server B both read/write to the same global variable, you have a race condition.
  • Stateless Architecture: Store state externally (Redis or DB). Treat your app servers as completely disposable execution engines.
  • Distributed Locks: When two separate machines try to process the same order simultaneously, local thread locks don't work. You must use Redis (Redlock) or ZooKeeper to lock the resource across the entire cluster.

9 · Decision Framework: Which model to use?

Use Node.js / Event Loop / Async if:
  • Heavy I/O (API Gateway, Chat Server, proxying)
  • Thousands of concurrent connections (WebSockets)
  • Workloads are fast, simple database reads/writes
Use Java/C++ Thread-per-request / Multi-threading if:
  • Heavy CPU computation (video encoding, cryptography, ML inference)
  • Complex business logic where async callbacks cause "callback hell"
  • (Though Virtual Threads / Goroutines give you the best of both worlds)
