Data Partitioning

Splitting your massive dataset into manageable chunks.

↑ Back to Course Index Module B — Databases

The one idea

Replication copies the same data across multiple servers for reliability. Partitioning (or Sharding) splits a large dataset across multiple servers because the total data is too big, or the read/write volume is too high, for any single machine to handle.

Vertical vs Horizontal Partitioning

There are two primary ways to slice a massive database table.

Vertical Partitioning (Splitting by Columns) Horizontal Partitioning / Sharding (Splitting by Rows)
You split tables based on columns. For example, moving the heavy profile_picture_url and bio columns to a different server than the frequently accessed username and password columns. You split tables based on rows. E.g., Users with IDs 1 to 10,000 live on Server A. Users with IDs 10,001 to 20,000 live on Server B. Both servers have the exact same table structure (columns).
Pros: Easy to implement initially. Optimizes disk I/O because you aren't pulling heavy, unused columns into memory. Pros: Truly infinite scale. You can just keep adding servers as your user base grows.
Cons: Has a hard limit. Eventually, even the vertically sliced tables will get too many rows to fit on one machine. Cons: Extremely complex. Cross-partition joins are terribly slow or impossible. Application logic must route queries to the correct server.

How to horizontally partition (Sharding Strategies)

If you decide to split your data by rows across multiple servers, how do you decide which row goes to which server? You need a Partition Key (or Shard Key).

1. Range Partitioning

Partition based on a continuous range of the key.
Example: Data for Jan-Mar goes to Server 1. Apr-Jun goes to Server 2.
Problem: Can lead to severe uneven distribution. If your application only reads recent data (e.g., this month's logs), Server 2 will be overloaded while Server 1 sits idle.

2. Hash Partitioning

Pass the partition key (e.g., UserID) through a hash function, then modulo the number of servers (Hash(UserID) % N).
Example: UserID 50. Hash(50) = 124. 124 % 3 servers = Server 2.
Problem: What happens when you add a 4th server? The modulo changes (% 4 instead of % 3), meaning almost every single row is now mapped to a different server. You have to move massive amounts of data just to add one server. (We solve this later using Consistent Hashing).

3. Directory-Based Partitioning

Maintain a lookup table (directory) that keeps track of which server holds which data.
Example: A table saying "User 1, 4, 7 → Server A; User 2, 8 → Server B".
Problem: The directory itself becomes a single point of failure and a performance bottleneck.

The "Hot Partition" (Celebrity) Problem

Even with a perfect hashing function, some rows are just accessed way more than others.

Imagine you partition Twitter data by UserID. Taylor Swift and a random bot both have a UserID. Millions of people request Taylor Swift's profile every minute, meaning the specific server holding her data (her partition) gets completely overwhelmed, while the other servers do nothing. This is called a Hotspot.

Interview Tip - Solving the Hotspot: If an interviewer asks how to solve the celebrity problem, common answers include: 1. Caching: Put the celebrity data in Redis/Memcached in front of the database. 2. Dedicated Shard: Assign massive accounts their own dedicated database servers. 3. Randomization/Splitting: For writes, append a random number to the key (e.g., taylorswift_1, taylorswift_2) to spread her data across multiple nodes, though this makes reading it back more complex.

Trade-offs of Partitioning

  • Joins are painful: If you need to JOIN the Users table and the Orders table, but User 5 is on Server A and their Orders are on Server B, you cannot run a simple SQL JOIN. You must query both servers in your application code and stitch the data together in memory.
  • Distributed Transactions: Ensuring ACID properties across multiple servers requires complex protocols like Two-Phase Commit (2PC), which are incredibly slow and prone to failure.
