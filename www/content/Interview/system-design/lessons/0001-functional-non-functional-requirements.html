Functional & Non-Functional Requirements

Before you draw a single box or arrow, you must know what you're building and how well it needs to work — this lesson teaches you the very first step of every system design interview.

Track goal: Master System Design for interviews — HLD + LLD. This is Lesson 1 of 66. Index

1 · The One Idea

Every system design starts with a single question: "What should this system do, and how well should it do it?" The answer splits into two clean buckets:

  • Functional Requirements (FRs) — what the system does (features, behaviours, use cases)
  • Non-Functional Requirements (NFRs) — how well the system does it (performance, scalability, reliability, security…)

In an interview, the first 3–5 minutes should be spent clarifying requirements. If you jump straight into drawing boxes, the interviewer will think you don't know what you're doing. Requirements are the compass — they decide every architectural choice that follows.

Interview golden rule Never start designing without asking clarifying questions. The interviewer is testing whether you can identify ambiguity and scope the problem. A great candidate spends 3–5 minutes just on requirements.

2 · Functional Requirements — The "What"

Functional requirements define the features and behaviour of the system. They answer: "What does the user want to do?" Each FR is a concrete action or capability.

2.1 · Definition

A functional requirement describes a specific input → processing → output behaviour. If someone asks "What does the system do?", your FRs should answer completely.

2.2 · Examples by System

SystemFunctional Requirements
URL Shortener (like bit.ly)
  • Given a long URL, generate a short unique URL
  • Given a short URL, redirect to the original long URL
  • Users can optionally set custom short links
  • Links should expire after a configurable time (optional)
  • Analytics: track click counts per link
Twitter/X
  • Users can post tweets (text, images, video)
  • Users can follow/unfollow other users
  • Users see a feed of tweets from people they follow
  • Users can like, retweet, and reply to tweets
  • Users can search tweets by keyword/hashtag
WhatsApp
  • 1:1 messaging between users
  • Group messaging
  • Sent/delivered/read receipts
  • Media sharing (images, video, documents)
  • Last-seen & online status

2.3 · How to Extract FRs in an Interview

Use the actor-action framework. For each type of user (actor), list what they can do (actions):

// Actor-Action Framework
Actor: End User
  → Post a message
  → View feed
  → Search content
  → Follow/unfollow

Actor: Admin
  → Ban/suspend accounts
  → View analytics dashboard
  → Manage content moderation

Actor: System (automated)
  → Send push notifications
  → Generate recommendations
  → Archive old data
Key questions to ask the interviewer
  • "Who are the users of this system?" (end-users, admins, internal services?)
  • "What are the core features?" (don't design everything — scope it)
  • "What are the input/output for each feature?"
  • "Are there any features we should explicitly NOT build?"

3 · Non-Functional Requirements — The "How Well"

Non-functional requirements define the quality attributes of the system. They don't say what the system does — they say how well it does it. They are the constraints under which the system must operate.

3.1 · The Big Categories

There are many NFRs, but for system design interviews, these are the ones that matter most:

NFRWhat It MeansExample Target
ScalabilityHandle growth — more users, more data, more requestsSupport 100M DAU, 10K requests/sec
AvailabilitySystem is up and reachable (uptime)99.99% uptime (≈ 52 min downtime/year)
ReliabilitySystem works correctly, data isn't lostZero data loss, exactly-once processing
Latency / PerformanceHow fast responses come backP99 latency < 200ms for reads
ConsistencyAll users see the same data at the same timeStrong consistency for payments, eventual for feeds
DurabilityData survives failures (disk crash, power loss)Data persisted to at least 3 replicas
SecurityProtection from unauthorized access and attacksEncryption at rest + in transit, OAuth 2.0
Fault ToleranceSystem continues working when components failNo single point of failure, auto-failover
MaintainabilityEasy to update, debug, and operateMicroservices, CI/CD, structured logging
CostBudget constraints — cloud bills, hardwareStay within $X/month infrastructure

3.2 · The Availability Nines Table

This table comes up in almost every system design discussion. Memorize it.

Availability %Allowed Downtime/YearAllowed Downtime/MonthCommon Name
99% (two nines)3.65 days7.31 hoursBasic
99.9% (three nines)8.77 hours43.83 minutesStandard
99.99% (four nines)52.60 minutes4.38 minutesHigh Availability
99.999% (five nines)5.26 minutes26.3 secondsUltra HA (banking)
Availability = Uptime / (Uptime + Downtime) × 100%
Reality check Going from 99.9% to 99.99% is NOT 10x harder — it's 100x harder and 100x more expensive. Each additional "nine" requires exponentially more redundancy, monitoring, and engineering effort. Always ask: "How much availability does this system actually need?"

6 · Deep Dive: Each NFR Explained

6.1 · Scalability

The ability to handle increasing load. There are two dimensions:

  • Vertical Scaling (Scale Up) — bigger machine (more CPU, RAM)
  • Horizontal Scaling (Scale Out) — more machines (add servers)

In interviews, always think about:

  • How many users? (DAU/MAU)
  • How many requests per second? (QPS)
  • How much data will we store? (TB/PB)
  • What's the read:write ratio?
🏢 Real-world example
Instagram serves 2B+ MAU. Reads massively outnumber writes (~100:1). This means the architecture is heavily read-optimized: CDN for images, aggressive caching, read replicas, and pre-computed feeds.

6.2 · Availability vs Reliability

People often confuse these. Here's the difference:

  • Availability = "Is the system UP?" (can I reach it?)
  • Reliability = "Does the system give CORRECT results?" (does it work right?)

A system can be available but unreliable (it's up but returns wrong data). Or reliable but unavailable (when it's up it works perfectly, but it's down a lot). Ideally you want both.

Analogy A vending machine that is always powered on but sometimes gives you the wrong drink is available but unreliable. A vending machine that always gives the right drink but is often out of order is reliable but unavailable.

6.3 · Latency

Time from request to response. Measured in percentiles:

  • P50 (median) — 50% of requests are faster than this
  • P95 — 95% of requests are faster. This is what most teams target.
  • P99 — 99% of requests are faster. Used for critical systems.
  • P99.9 — "tail latency" — the worst cases that affect your most engaged users
Why percentiles, not averages? Averages hide outliers. If 99 requests take 10ms and 1 takes 10 seconds, the average is 109ms — looks fine! But that one user waited 10 seconds. P99 = 10s tells the real story. Amazon found that every 100ms of latency cost them 1% in sales.

6.4 · Consistency

Can all users see the same data at the same time?

  • Strong Consistency — Every read returns the most recent write. Required for banking, payments.
  • Eventual Consistency — Reads might return stale data, but will eventually catch up. Fine for social media feeds, likes count.
  • Causal Consistency — Operations that are causally related are seen in order. Good for chat apps.

We'll explore this deeply in Lesson 12.

6.5 · Durability

Once data is written, it won't be lost — even if servers crash, disks fail, or a whole data center goes down. Achieved through:

  • Replication (copies across machines/regions)
  • Write-Ahead Logs (WAL)
  • Backups (periodic snapshots)

6.6 · Fault Tolerance

The system continues operating when parts fail. Key strategies:

  • Redundancy — no single point of failure
  • Replication — data copied across nodes
  • Failover — automatic switch to backup
  • Graceful degradation — offer reduced functionality instead of complete failure
🏢 Real-world example
Netflix uses Chaos Monkey to randomly kill servers in production. If the system can survive random failures during normal operation, it can survive real outages. This is called Chaos Engineering.

7 · Worked Example: Design a URL Shortener — Requirements Phase

Let's walk through exactly what you'd say in the first 3–5 minutes of this interview:

Step 1: Clarifying Questions

You → Interviewer:
"What's the main use case — is this for internal use or public-facing like bit.ly?"
"How many URLs do we expect to shorten per day?"
"What's the expected read:write ratio?"
"Should short URLs expire?"
"Do we need analytics (click tracking)?"
"Should users be authenticated, or is it open?"

Step 2: Functional Requirements (agreed with interviewer)

// Functional Requirements
FR1: Given a long URL → generate a unique short URL
FR2: Given a short URL → redirect (301/302) to the original URL
FR3: Optional: users can create custom aliases
FR4: Optional: links can have expiration dates
FR5: Optional: analytics dashboard (click count, referrer, geo)

Step 3: Non-Functional Requirements (agreed with interviewer)

// Non-Functional Requirements
NFR1: Scale — 100M new URLs/day, 10:1 read:write ratio → 1B redirects/day
NFR2: Latency — redirect should be < 50ms (P99)
NFR3: Availability — 99.99% (URL shortener must always work)
NFR4: Durability — shortened URLs should never be lost
NFR5: Consistency — eventual consistency is fine (a 1-second delay to propagate a new URL is acceptable)
NFR6: URL length — short URL should be ≤ 7 characters after domain

Step 4: Back-of-Envelope Estimation

// Quick math
Writes: 100M URLs/day = ~1,200 writes/sec
Reads:  1B redirects/day = ~12,000 reads/sec (10:1 ratio)
Storage: 100M × 365 days × 5 years = 182.5B URLs
         Each URL ≈ 500 bytes → 182.5B × 500B ≈ 91 TB
         Need: DB that can handle ~100 TB, heavy reads
This is the template Every system design interview follows this flow: clarify → FRs → NFRs → estimate → then design. Master this template and you'll never freeze in an interview.

8 · How NFRs Drive Architecture Decisions

This is the key insight: NFRs determine your architecture, not FRs. The same feature set can be built in wildly different architectures depending on the NFRs.

If the NFR says…Then the architecture needs…
High read throughput (100K+ QPS)Caching layer (Redis), read replicas, CDN
Low latency (< 50ms)In-memory cache, edge servers, no heavy DB joins
High availability (99.99%)Multiple regions, auto-failover, no SPOF
Strong consistencySynchronous replication, consensus protocol (Raft/Paxos)
Eventual consistency is fineAsync replication, message queues, simpler architecture
Handle huge data (PB scale)Sharding, partitioning, distributed storage (HDFS/S3)
High write throughputWrite-ahead log, batching, message queue buffer
Must be secureEncryption, auth, rate limiting, WAF, audit logs
The Architecture Connection Think of FRs as "what rooms does the house need?" and NFRs as "should the house survive an earthquake?" The same rooms can be built with wood (cheap, fine for low-risk areas) or reinforced concrete (expensive, needed for earthquake zones). The NFRs determine the building material — i.e., your architecture.

11 · Edge Cases & Gotchas

  • Don't over-scope FRs. An interviewer says "design Twitter" — they don't want DMs, Spaces, ads, and bookmarks. Pick 3–5 core features.
  • Don't ignore NFRs. If you never mention scalability or availability, the interviewer will prompt you — and you've lost initiative.
  • NFRs conflict. Consistency vs Availability (CAP theorem), Latency vs Accuracy. Acknowledge the trade-off and justify your choice.
  • Don't guess numbers. Ask the interviewer: "Should we assume 1M DAU or 100M DAU?" They'll either give you a number or say "whatever you think is reasonable."
  • Extended requirements. If the interviewer says "what else would you add?", suggest: monitoring/logging, rate limiting, analytics, A/B testing.
