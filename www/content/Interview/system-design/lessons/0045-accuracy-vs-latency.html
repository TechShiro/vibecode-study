Accuracy vs Latency: Probabilistic Data Structures

How massive scale systems count billions of items in microseconds using 12 KB of memory.

↑ Back to Course Index Module K — System Design Trade-offs

1 · The One Idea

If you ask an engineer to count the number of unique visitors (cardinality) who visited YouTube today, their first instinct is: SELECT COUNT(DISTINCT user_id). But when you have 2 billion unique visitors, storing 2 billion 64-bit IDs in a Hash Set requires 16 Gigabytes of RAM per day! When exact precision is unnecessary (a human doesn't care if a video has 4,200,100 views vs 4,200,000 views), Probabilistic Data Structures trade 1% of mathematical accuracy for a 99.9% reduction in memory and sub-millisecond latency.

2 · The 3 Legendary Probabilistic Structures

1. HyperLogLog (HLL) — Unique Element Counting (Cardinality)

  • Problem: How many unique users visited Reddit today?
  • How it works: Hashes each incoming user ID into a binary string. Observes the maximum number of consecutive leading zeroes in the binary hash. By probability theory, observing $k$ leading zeroes implies approximately $2^k$ unique items!
  • The Miracle: Redis PFADD and PFCOUNT can estimate the unique cardinality of billions of items with a standard error of 0.81% using only 12 KB of RAM!

2. Count-Min Sketch — Frequency Tracking

  • Problem: How many times has the hashtag #WorldCup been tweeted today across 500 million tweets?
  • How it works: A 2D array of counters with $d$ hash functions. Each incoming word increments $d$ counters. When queried, returns the minimum value among those counters. Guarantees it will never underestimate frequency, with a tightly bounded overestimation rate.

3. Heavy Hitters (Top-K) Algorithm

  • Combines Count-Min Sketch with a Min-Heap to continuously track the top 100 trending hashtags or highest-spending customers in a real-time data stream without storing the full history.
