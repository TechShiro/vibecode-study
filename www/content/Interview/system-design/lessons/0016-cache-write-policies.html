Cache Write Policies

Deciding how and when data flows between your cache and your database during write operations.

↑ Back to Course Index Module D — Caching

1 · The One Idea

Whenever an update occurs (e.g., a user changes their username), you have two distinct storage systems holding that value: the in-memory cache and the persistent database. If you don't update them in a coordinated manner, your system will suffer from data inconsistency (readers seeing stale, outdated data). Cache Write Policies dictate the exact choreography of writes.

2 · The 4 Major Write Patterns

1. Cache-Aside (Lazy Loading) — The Industry Standard

The application directly manages both the cache and the database.

  • Reads: App checks cache. If hit, return. If miss, app reads DB, stores in cache, and returns.
  • Writes: App writes directly to the DB, and then evicts (deletes) the key from the cache. (The next read will repopulate it fresh).
  • Why delete instead of update cache? Updating cache directly can cause race conditions between concurrent writes. Deleting the key is safe and idempotent!

2. Write-Through

The application treats the cache as the main data store. When a write occurs, the application writes to the cache, and the cache synchronously writes to the database before acknowledging success.

Pros: Data in cache is never stale.
Cons: High write latency because every write must wait for both cache and disk write.

3. Write-Behind (Write-Back)

The application writes only to the cache, which acknowledges success immediately. The cache then asynchronously batches and writes the data to the database in the background (e.g., every 10 seconds).

Pros: Insanely fast write speeds; absorbs massive spikes of write traffic.
Cons: Risk of data loss! If the cache server crashes or loses power before flushing dirty pages to the database, recent writes vanish forever.

4. Write-Around

The application writes directly to the database, completely bypassing the cache. Only subsequent reads (if configured as cache-aside) will pull the data into the cache.

Pros: Prevents the cache from being flooded with data that is written once and never read again (e.g., real-time audit logs).
Cons: A read immediately following a write results in a cache miss.

3 · Comparison Table

Strategy Write Latency Data Loss Risk Best Used For
Cache-Aside Medium None General purpose web applications (User profiles, catalogues).
Write-Through Highest (waits for DB) None Systems where stale reads cannot be tolerated (e-commerce orders).
Write-Behind Lowest (instant in RAM) High (if cache crashes) High-frequency write systems (IoT telemetry, video view counters, game state).
Write-Around Medium (hits DB) None Write-heavy data that is rarely read immediately (e.g., log dumps).
