WebSockets & Real-Time Communication

Building low-latency, two-way interactive connections for chat, trading, and collaboration apps.

↑ Back to Course Index Module E — Networking

1 · The One Idea

Standard HTTP is strictly unidirectional: the client asks, the server answers, and the connection closes. If a friend sends you a WhatsApp message, the server cannot push it to your phone under plain HTTP without your phone constantly asking "Any new messages?" every second (polling). WebSockets establish a single, persistent, bidirectional (full-duplex) TCP connection where either the client or the server can push data at any microsecond with virtually zero header overhead.

2 · How a WebSocket Connection Starts: The Upgrade Handshake

WebSockets are designed to work seamlessly through standard firewalls and HTTP ports (80/443). They start as a regular HTTP request with special upgrade headers:

GET /chat HTTP/1.1
Host: chat.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

The server replies with HTTP status 101 Switching Protocols:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

From that exact moment onward, HTTP is discarded! The TCP socket remains wide open, exchanging lightweight binary/text frames with only 2–10 bytes of frame overhead (compared to 1,000+ bytes of HTTP headers).

3 · The Distributed WebSocket Problem: Scaling Across Multiple Servers

In a production system with 1 million users, you have 10 backend WebSocket servers behind a load balancer.

The problem: User Alice is connected to WebSocket Server 1. User Bob is connected to WebSocket Server 3. When Alice sends a message to Bob, Server 1 has no open socket to Bob! How does Server 1 deliver the message to Server 3?

Alice → Server 1
Redis Pub/Sub or Kafka
Server 3 → Bob
Architecture Solution Connect all WebSocket servers to a distributed message broker (like Redis Pub/Sub). When Server 1 receives Alice's message for Bob, it publishes to channel user:bob:messages. Server 3 is subscribed to that channel, receives the payload, and writes it directly into Bob's active WebSocket connection!
