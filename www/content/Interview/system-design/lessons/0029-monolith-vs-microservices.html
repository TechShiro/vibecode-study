Monolith vs Microservices Architecture

Understanding why systems evolve from single codebases to distributed microservice fleets.

↑ Back to Course Index Module H — Microservices Architecture

1 · The One Idea

A Monolith packages all business capabilities (auth, billing, catalogue, shipping) into a single unified application and shared database. A Microservices Architecture decomposes the application into small, autonomous, independently deployable services that communicate over network protocols (HTTP/REST or gRPC) and own their private databases. Microservices do not solve technical problems — they solve organizational scaling problems.

2 · Monolith vs Microservices Comparison

Aspect Monolithic Architecture Microservices Architecture
Development & Deployment Single repository, simple local setup, one-click build and deploy. Fast for small teams. Dozens of repos, complex CI/CD pipelines, container orchestration (Docker/K8s) required.
Data Consistency Native ACID database transactions across all tables. Easy relational JOINs. Distributed transactions (Saga pattern), eventual consistency, data duplication across services.
Debugging & Tracing Stack trace points directly to the failing line of code in the monolith process. Requires distributed tracing (OpenTelemetry, Jaeger) to track requests jumping across 15 network hops.
Fault Isolation A single memory leak or unhandled exception in one feature can crash the entire application for all users. If Recommendation Service crashes, the user can still browse and purchase items (graceful degradation).
Team Scaling Merge conflicts, long release queues when 200+ engineers touch the same codebase. Autonomous teams (Two-Pizza Teams) own, deploy, and scale their service independently (Conway's Law).

3 · Conway's Law & When to Break a Monolith

Conway's Law

"Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations."

Never start a startup with microservices! Start with a clean, modular monolith. Only migrate to microservices when:

  1. Your engineering team exceeds 50–100 developers and deployments are constantly bottlenecked.
  2. Different subdomains have radically different scaling profiles (e.g., video transcoding needs 1,000 GPU instances, while user auth needs 2 small CPU instances).
