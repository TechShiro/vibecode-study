Back-of-the-Envelope Capacity Estimation

The cheat codes and mental math to estimate hardware, storage, and throughput in 2 minutes.

↑ Back to Course Index Bonus HLD Fundamentals

1 · The One Idea

In system design, you cannot design an architecture until you understand its scale. Designing a system for 10 requests per second is completely different from designing for 1,000,000 requests per second. Back-of-the-Envelope Estimation is quick napkin math used to determine your system's Queries Per Second (QPS), Storage capacity requirements over 5 years, and Network Bandwidth consumption.

2 · The Powers of Two & Time Constants (Memorize These!)

  • $2^{10} pprox 1,000$ (One Thousand / 1 KB)
  • $2^{20} pprox 1,000,000$ (One Million / 1 MB)
  • $2^{30} pprox 1,000,000,000$ (One Billion / 1 GB)
  • $2^{40} pprox 1,000,000,000,000$ (One Trillion / 1 TB)
  • $2^{50} pprox 1 ext{ Petabyte (PB)}$
The Magic Daily Seconds Number

1 Day = $24 imes 60 imes 60 = \mathbf{86,400 ext{ seconds}} pprox \mathbf{100,000 ext{ seconds}}$ for quick mental math!

3 · Step-by-Step Worked Example: Designing Twitter (X)

Given Assumptions: 300 million Daily Active Users (DAU). Each user posts 2 tweets/day on average. 10% of tweets include media (images/videos).

Step 1: Calculate Write QPS

  • Total Tweets per day: $300 ext{M} imes 2 = 600 ext{ Million tweets/day}$.
  • Average Write QPS: $ rac{600,000,000}{100,000 ext{ seconds}} = \mathbf{6,000 ext{ tweets/second}}$.
  • Peak Write QPS (usually $2 imes$ average): $6,000 imes 2 = \mathbf{12,000 ext{ QPS}}$.

Step 2: Calculate Read QPS

  • Users browse feeds way more than they post! Assume a 10:1 read-to-write ratio.
  • Average Read QPS: $6,000 imes 10 = \mathbf{60,000 ext{ QPS}}$.
  • Peak Read QPS: $120,000 ext{ QPS}$.

Step 3: Storage Estimation (5 Years)

  • Assume text tweet record: tweet_id (8B) + user_id (8B) + text (280B) + metadata = ~500 Bytes.
  • Daily text storage: $600 ext{M} imes 500 ext{B} = 300 ext{ GB/day}$.
  • Media storage: 10% of 600M = 60M photos/videos per day. Assume average media size 200 KB: $60 ext{M} imes 200 ext{ KB} = \mathbf{12 ext{ TB/day}}$!
  • 5-Year Total Storage: $12.3 ext{ TB/day} imes 365 imes 5 pprox \mathbf{22.4 ext{ Petabytes}}$! (This immediately tells you that you MUST store media on distributed object storage like AWS S3, not a SQL database).
