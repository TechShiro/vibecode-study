The SOLID Principles: Clean Code Architecture

The five timeless design principles that make software maintainable, extensible, and robust.

↑ Back to Course Index Module L — OOP Foundations

1 · The One Idea

Introduced by Robert C. Martin (Uncle Bob), SOLID is the foundational mnemonic representing the five core design guidelines for writing maintainable object-oriented software. Software designed with SOLID is modular, easy to test with mock objects, and gracefully accommodates new features without breaking existing code.

2 · The 5 Principles Broken Down

1. S — Single Responsibility Principle (SRP)

"A class should have one, and only one, reason to change."

  • Violation: An OrderService class that calculates tax, inserts orders into SQL, and formats/sends customer emails. If email formatting changes, you risk breaking SQL logic!
  • Fix: Split into three focused classes: OrderRepository (SQL persistence), TaxCalculator (pricing math), and EmailNotificationService (communication).

2. O — Open/Closed Principle (OCP)

"Software entities should be open for extension, but closed for modification."

  • You should be able to add new functionality (e.g., adding Bitcoin payments) without modifying existing, tested, working classes.
  • Achieved through polymorphism: declare a PaymentMethod interface. To add Bitcoin, create BitcoinPayment implements PaymentMethod without editing a single line in CheckoutService!

3. L — Liskov Substitution Principle (LSP)

"Subtypes must be substitutable for their base types without altering program correctness."

  • The Classic Violation: Square extends Rectangle. When someone calls rectangle.setWidth(5); rectangle.setHeight(10);, a square forces width and height to be equal, violating the caller's expectations!
  • If a subclass throws UnsupportedOperationException or does nothing for an inherited method, LSP is violated.

4. I — Interface Segregation Principle (ISP)

"Clients should not be forced to depend on interfaces they do not use."

  • Violation: A giant "fat" interface Worker with code(), eat(), sleep(), and chargeBattery(). A RobotWorker is forced to implement dummy eat() and sleep() methods.
  • Fix: Break into lean, cohesive interfaces: Workable, Feedable, Rechargeable.

5. D — Dependency Inversion Principle (DIP)

"High-level modules should not depend on low-level modules. Both should depend on abstractions."

  • Violation: UserService directly instantiates MySQLDatabase db = new MySQLDatabase();. The business logic is now married to MySQL forever!
  • Fix: UserService depends on interface Database. The concrete implementation (MySQL, Postgres, Mongo) is injected at runtime via Dependency Injection (Spring/Guice).
