Migration to Microservices: The Strangler Fig

How to incrementally replace a giant legacy monolith without rewriting the world from scratch.

↑ Back to Course Index Module H — Microservices Architecture

1 · The One Idea

The "Big Bang Rewrite" (stopping all feature development for 18 months to rebuild the entire system as microservices from scratch) is the single most infamous way software projects fail. By the time the rewrite finishes, business requirements have shifted and the new system has 1,000 unforeseen bugs. The proven industry method is the Strangler Fig Pattern: gradually carving off small features one by one until the monolith naturally withers away.

2 · The Strangler Fig Architecture

API Gateway / Reverse Proxy
Monolith (90% legacy routes)
Route /users/*
New User Microservice (10% traffic)
  1. Place a Proxy at the Front: Put an API Gateway (like Envoy or Nginx) in front of the existing monolith.
  2. Carve Out a Vertical Slice: Pick one clean, bounded domain (e.g. Notification Service or User Profile). Build it as a standalone microservice with its own database.
  3. Divert Traffic: Update the proxy route: send /notifications/* to the new microservice; keep all other traffic flowing to the monolith.
  4. Repeat: Carve out the next domain (Payments, Inventory, Orders). Over months, the monolith shrinks until it can be safely decommissioned!

3 · The Hard Part: Database Migration

Migrating code is easy; migrating active production databases with millions of users is where data corruption happens. Use the Dual-Write & CDC Strategy:

  • Step 1 (Dual Write): Application writes to both the legacy database and the new microservice database.
  • Step 2 (Change Data Capture / CDC): Use a tool like Debezium on PostgreSQL/MySQL replication logs to stream past historical rows to the new database.
  • Step 3 (Reconciliation & Dark Launch): Run background batch scripts comparing both databases to verify 100% data fidelity. Direct reads to the new service while keeping writes dual.
  • Step 4 (Cutover): Cut all write traffic to the new service and sever the legacy database connection.
