Locking Mechanisms & Deadlock Prevention

Controlling concurrent access to critical sections in memory and databases.

↑ Back to Course Index Module N — Concurrency & Thread Safety

1 · The One Idea

When two threads attempt to update the same memory location or database row concurrently (e.g. reserving the last flight seat), without synchronization both can read seat as free and both sell it (double booking). Locking Mechanisms enforce mutual exclusion, allowing only one thread at a time to execute a Critical Section of code.

2 · In-Memory Locking in Java

Locking Mechanism How It Works When to Use
synchronized keyword Intrinsic monitor lock on an object. Automatically acquired and released by JVM. Simple critical sections. Easy to write, zero risk of forgetting to unlock.
ReentrantLock Explicit lock object. Supports timed tryLock (tryLock(500, ms)), interruptible locks, and fairness policies. When you need to avoid deadlocks by bailing out if lock isn't available immediately.
ReentrantReadWriteLock Allows unlimited concurrent readers as long as no writer is active. Only 1 writer can acquire exclusive lock. Read-heavy data structures (95% reads, 5% writes). Multiplies throughput.
StampedLock Provides Optimistic Reading. Reader doesn't acquire an actual lock; validates a version stamp afterward! Ultra-high-performance concurrent cache lookups (Java 8+).

3 · Database Locking: Optimistic vs Pessimistic

  • Pessimistic Locking: SELECT * FROM seats WHERE id = 1 FOR UPDATE;. The database row is physically locked at the SQL level. Safe, but locks out other transactions.
  • Optimistic Locking: Every row has a version column: UPDATE seats SET booked = true, version = version + 1 WHERE id = 1 AND version = 5;. If another transaction changed the version to 6 in the meantime, the update returns 0 affected rows and the application retries. Zero database lock contention!

4 · The 4 Coffman Deadlock Conditions

A Deadlock occurs when Thread 1 holds Lock A and waits for Lock B, while Thread 2 holds Lock B and waits for Lock A. A deadlock can ONLY occur if all 4 conditions hold simultaneously:

  1. Mutual Exclusion: Resource is non-shareable.
  2. Hold and Wait: Thread holds a resource while requesting another.
  3. No Preemption: Resources cannot be forcibly taken away.
  4. Circular Wait: Thread A waits for B, B waits for C, C waits for A.
Deadlock Cure To prevent deadlocks forever: Break Circular Wait by enforcing a strict global lock acquisition order! Always acquire Lock A before Lock B everywhere in your codebase.
