Database Isolation Levels

How databases prevent concurrent transactions from destroying each other's data.

↑ Back to Course Index Module C — Consistency & Isolation

1 · The One Idea

In ACID transactions, the "I" stands for Isolation. In an ideal world, every transaction would run in total isolation, as if it were the only transaction executing in the entire database. But achieving perfect isolation requires aggressive locking that grinds database throughput to a halt. Databases therefore provide Isolation Levels, allowing engineers to balance data safety against concurrency speed.

2 · The 4 Concurrency Anomalies (Nightmares)

To understand isolation levels, you must first meet the four bugs that occur when transactions collide:

1. Dirty Read

Transaction A modifies a row but hasn't committed yet. Transaction B reads that uncommitted row. Transaction A then crashes and rolls back. Transaction B is now operating on data that never officially existed!

2. Non-Repeatable Read (Fuzzy Read)

Transaction A reads a row (e.g., User balance = $100). Meanwhile, Transaction B updates that balance to $50 and commits. Transaction A reads the same row again in the same transaction and gets $50. Reading the exact same row gave two different results!

3. Phantom Read

Transaction A queries a range of rows (e.g., SELECT * FROM orders WHERE user_id = 5) and gets 3 rows. Meanwhile, Transaction B inserts a new 4th order for User 5 and commits. Transaction A re-executes the query and suddenly sees a "phantom" 4th row appear out of nowhere.

4. Write Skew

Two transactions read overlapping data, verify a business rule independently, and make writes that together violate the rule. Example: A hospital requires at least 1 doctor on call. Doctor A and Doctor B both request leave at the exact same second. Both transactions see 2 doctors active, both approve their respective leave, and the hospital is left with 0 doctors!

4 · How Modern Databases Do It Fast: MVCC

In older databases, reading a row locked out writers, and writing a row locked out readers. Modern relational engines use Multi-Version Concurrency Control (MVCC).

  • Whenever a row is updated, the database does not overwrite the old data in place. Instead, it creates a new version of the row with a transaction timestamp.
  • When a transaction starts, it reads a frozen snapshot of the database matching its start time.
  • The Golden Rule of MVCC: Readers never block writers, and writers never block readers!
Production takeaway 90% of real-world applications run on Read Committed or Repeatable Read. Avoid Serializable unless you are handling ledger transactions where write skew would cause direct monetary loss.
