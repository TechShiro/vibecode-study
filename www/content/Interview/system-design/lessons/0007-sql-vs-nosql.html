SQL vs NoSQL Databases

The most frequent architectural decision you will make. Picking the wrong database paradigm will doom your system's scaling potential or cripple your data integrity.

Track goal: Master System Design for interviews — HLD + LLD. This is Lesson 7 of 66. Index

1 · The One Idea

SQL (Relational) databases are built for strict schema, strong data integrity (ACID), and complex relationships via JOINs, but they are historically hard to scale horizontally. NoSQL (Non-Relational) databases sacrifice complex querying and strict schemas to achieve extreme horizontal scalability, high performance, and flexible data models.

2 · SQL (Relational Databases)

Data is stored in highly structured Tables (rows and columns). Relationships between tables are enforced via Foreign Keys.

  • Examples: PostgreSQL, MySQL, Oracle, SQL Server.
  • ACID Guarantees:
    • Atomicity: All parts of a transaction succeed, or it all rolls back.
    • Consistency: Data must adhere to all constraints/schemas.
    • Isolation: Concurrent transactions don't interfere with each other.
    • Durability: Once committed, data survives crashes.
  • Best for: Financial systems, inventory, systems where data relationships are complex and data integrity is non-negotiable.

3 · The 4 Families of NoSQL

NoSQL is not one thing—it is a blanket term for four entirely different database paradigms.

TypeHow it stores dataExamplesBest Used For
Key-Value A hash map (dictionary). Unique key points to a blob of data. Redis, Memcached, DynamoDB Caching, session storage, shopping carts, leaderboards. Extreme read/write speed.
Document JSON/BSON objects. Each document can have a completely different structure. MongoDB, Couchbase Content management, user profiles, product catalogs. Great when schema changes rapidly.
Column-Family Stores data by columns rather than rows. Highly optimized for massive write throughput across distributed nodes. Cassandra, HBase Time-series data, IoT sensor data, massive logging (e.g., Discord messages, Netflix viewing history).
Graph Nodes (entities) and Edges (relationships). Highly optimized for traversing deep connections. Neo4j, Amazon Neptune Social networks (friends of friends), recommendation engines, fraud detection.

4 · Mental Models: SQL vs Document vs Graph

5 · Scaling: The Real Reason NoSQL Exists

The core motivation behind the NoSQL movement in the 2000s (led by Google and Amazon) wasn't just "we hate schemas." It was Horizontal Scalability.

  • SQL scaling: To scale an RDBMS, you traditionally buy a bigger server (Vertical Scaling). Sharding SQL across multiple machines is notoriously difficult because you break foreign keys and JOINs across shards.
  • NoSQL scaling: Built from day one to be distributed across hundreds of cheap commodity servers (Horizontal Scaling). Because data is typically denormalized (e.g., self-contained JSON documents), a node can return the entire document without talking to other nodes.

6 · Decision Framework

ScenarioWinnerWhy
Financial Ledger / PaymentsSQLACID guarantees are strictly required. Cannot risk inconsistent reads or partial writes.
E-Commerce Product CatalogNoSQL (Document)A TV has different attributes (screen size) than a T-shirt (size, color). Rigid schemas fail here; JSON shines.
Real-time LeaderboardNoSQL (Key-Value)Requires extreme in-memory read/write speeds (Redis Sorted Sets).
Uber/Lyft Ride TrackingNoSQL (Column/KV)Massive influx of GPS coordinates per second. Cassandra handles heavy writes perfectly.
Social Network Friend SuggestionsNoSQL (Graph)Finding "friends of friends of friends" in SQL requires multiple expensive JOINs. Graph DBs do this instantly.
Default / Starting a new projectSQL (PostgreSQL)Postgres is incredibly powerful. It now supports JSONB, effectively giving you NoSQL features inside a relational engine. Always start SQL unless you have massive scale needs.

7 · System Design Interview Angle

In a system design interview, database selection is a major scoring point. Follow this playbook:

  1. Default to Postgres/MySQL. Say: "I will use PostgreSQL because the data is highly structured, requires ACID compliance, and easily handles our projected load."
  2. Pivot to NoSQL only with justification. "However, for the chat message storage, we expect 100,000 writes per second. Relational databases will bottleneck here, so I will use a Wide-Column NoSQL database like Cassandra which handles massive write throughput effortlessly."
  3. Mention Denormalization. If you pick NoSQL, explicitly state that you are giving up JOINs and will denormalize the data (store redundant copies of data so it can be fetched in one query).
