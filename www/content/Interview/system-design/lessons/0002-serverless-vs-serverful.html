Serverless vs Serverful Architecture

There are still servers in "serverless" — you just don't manage them. Understanding when to hand control to the cloud vs keeping your own fleet is a critical system design skill.

Track goal: Master System Design for interviews — HLD + LLD. This is Lesson 2 of 66. Index

1 · The One Idea

In serverful architecture, you provision, manage, and pay for servers whether they're busy or idle. In serverless, the cloud provider dynamically allocates compute per request — you write code, they run it, and you pay only for what you use. The trade-off is control vs convenience.

Interview one-liner "Serverless abstracts infrastructure entirely — I write a function, deploy it, and the cloud handles scaling, patching, and availability. The trade-off is I lose control over the runtime environment, face cold-start latency, and risk vendor lock-in."

2 · Serverful Architecture — The Traditional Way

This is what most engineers learn first. You have actual servers (physical or virtual) that you manage:

  • Virtual Machines (VMs) — EC2 instances, GCE VMs, Azure VMs
  • Containers — Docker containers on ECS, EKS, GKE
  • Bare Metal — physical servers in your own data center

You choose the OS, install software, configure networking, handle security patches, set up auto-scaling rules, and monitor health. The servers run 24/7 — even if nobody is sending requests at 3 AM.

How a request flows (serverful)

Client → DNS → Load Balancer → Web Server (always running)
                                    ↓
                             Application Code
                                    ↓
                               Database

The web server is always on, waiting for requests. You pay whether it's handling 0 or 10,000 req/sec.

Characteristics

  • Full control over OS, runtime, dependencies, networking
  • You handle scaling (manual or auto-scaling groups)
  • You handle patching, monitoring, failover
  • Pay for uptime, not usage — servers cost money 24/7
  • Can run any workload: long-running processes, WebSockets, stateful services

3 · Serverless Architecture

Serverless is a cloud execution model where the provider runs your code on demand. You don't provision or manage servers. There are two flavours:

You write a single function, upload it, and the cloud runs it when triggered. Each invocation is isolated.

3.2 · BaaS — Backend as a Service

BaaS provides pre-built backend services you use via SDKs/APIs instead of building yourself:

ServiceWhat It Provides
FirebaseAuth, Firestore DB, Storage, Hosting, Cloud Messaging
SupabaseAuth, PostgreSQL DB, Storage, Realtime subscriptions

With BaaS, you don't write backend code for auth, database, or file storage — you use the provider's managed service. Combined with FaaS for custom logic, you can build entire applications without managing a single server.

4 · How Serverless Works Under the Hood

When you invoke a Lambda function, here's what happens behind the scenes:

  1. Request arrives at API Gateway / event source (S3, SQS, HTTP, etc.)
  2. Lambda service checks: is there a warm container for this function?
  3. If YES (warm start) → route request to existing container. Latency: ~1–5 ms overhead.
  4. If NO (cold start) → spin up a new container:
    • Download your code package
    • Initialize the runtime (JVM, Node.js, Python interpreter)
    • Run your initialization code (static blocks, global variables)
    • Then execute the handler
    • Cold start latency: 100ms–5+ seconds depending on language & package size
  5. Container stays warm for ~5–15 minutes after last invocation (provider-dependent)
  6. If no requests come, container is destroyed — resources freed
The Cold Start Problem Cold starts are serverless's biggest pain point. Java/C# are worst (~1–5 sec) because JVM/.NET startup is heavy. Node.js/Python are best (~100–300ms). Mitigation strategies:
  • Provisioned concurrency — keep N containers always warm (AWS Lambda feature, costs money)
  • Keep-warm pings — CloudWatch scheduled event every 5 min to prevent container death
  • Smaller packages — reduce deployment size = faster download = faster cold start
  • Use lighter runtimes — Node.js/Python/Go instead of Java for latency-sensitive functions
  • GraalVM native image — compile Java ahead-of-time to eliminate JVM startup

5 · Architecture Comparison

6 · Pricing: Pay-Per-Use vs Always-On

Serverless Pricing (AWS Lambda example)

  • $0.20 per 1 million invocations
  • $0.0000166667 per GB-second of compute time
  • Free tier: 1M invocations + 400,000 GB-seconds per month

Serverful Pricing (EC2 example)

  • t3.medium (2 vCPU, 4 GB): ~$30/month (always on)
  • m5.large (2 vCPU, 8 GB): ~$70/month
  • Pays 24/7 whether serving 0 or 10K requests

When is serverless cheaper?

ScenarioCheaper OptionWhy
Sporadic traffic (few requests/day)ServerlessPay only when invoked; idle = $0
Bursty traffic (spikes then quiet)ServerlessScales to spike, scales to zero
Steady high traffic (1000+ req/sec 24/7)ServerfulPer-invocation cost adds up; reserved instances are cheaper
MVP / PrototypeServerlessNo infra setup, free tier covers most usage
Long-running jobs (>15 min)ServerfulLambda has execution time limits
The crossover point At roughly 1–2 million requests per day with consistent load, serverful (with reserved instances) often becomes cheaper than Lambda. Below that, serverless almost always wins on cost.

7 · Scaling Behaviour

Serverless auto-scales to zero and to thousands instantly. You don't configure anything.

  • AWS Lambda: up to 1,000 concurrent executions by default (can request increase to 10K+)
  • Each invocation runs in its own container — instant horizontal scaling
  • Scale to zero: when no requests come, you pay nothing

Serverful requires you to configure scaling:

  • Auto Scaling Groups (AWS), Managed Instance Groups (GCP)
  • Define min/max instances, scaling policies (CPU > 70% → add instance)
  • Scaling takes minutes (boot VM, pull image, health check)
  • You usually keep minimum instances running → baseline cost

8 · Statelessness Constraint

Serverless functions must be stateless. Each invocation may run on a different container. You cannot store data in memory or local filesystem and expect it to be there on the next call.

Where to put state instead:

  • Database — DynamoDB, RDS, Firestore
  • Cache — ElastiCache (Redis/Memcached)
  • Object Storage — S3, GCS
  • Session Store — Redis, DynamoDB
Gotcha: /tmp is ephemeral Lambda gives you a /tmp directory (512 MB), but it's only available within the same warm container. If the container is recycled, /tmp is gone. Never rely on it for persistent data.

10 · Vendor Lock-In

Serverless ties you to a provider's ecosystem. Your Lambda function uses DynamoDB, S3, SQS, API Gateway — all AWS. Moving to GCP means rewriting everything.

Mitigation strategies:

  • Serverless Framework / SAM — abstraction layers that can target multiple providers
  • Knative — run serverless workloads on Kubernetes (any cloud)
  • OpenFaaS — open-source FaaS framework
  • Keep business logic portable — put core logic in pure functions, provider-specific code in thin adapters

13 · Real-World Examples

🏢 Netflix
Uses AWS Lambda for media encoding pipeline. When a new movie is uploaded, Lambda functions are triggered to encode it into 1,200+ different formats/resolutions. Sporadic, massively parallel — perfect serverless use case.
🏢 Coca-Cola
Migrated their vending machine payment processing to serverless. Requests are sporadic (someone buys a Coke), and they eliminated the cost of idle servers. Estimated 65% cost reduction.
🏢 Slack
Slack's core messaging is serverful — persistent WebSocket connections for real-time chat. But they use Lambda for auxiliary tasks: image resizing, link previews, search indexing.

14 · Hybrid Architectures

Most real production systems are hybrid — not purely serverless or serverful.

  • Core API → serverful (ECS/K8s) for consistent latency and WebSocket support
  • Image processing → serverless (Lambda triggered by S3 upload)
  • Scheduled jobs → serverless (CloudWatch → Lambda)
  • Webhook handlers → serverless (API Gateway → Lambda)
  • ML inference → serverful (GPU instances)
Interview pro tip In a system design interview, don't say "everything is serverless" or "everything is serverful." Show maturity by using each where it fits. Say: "For the core chat service I'd use a containerized server because we need WebSocket connections. But for image thumbnailing, I'd use a Lambda triggered by S3 uploads — it's event-driven and bursty."

15 · Edge Computing & Serverless

A newer serverless variant runs functions at the edge — close to users worldwide:

  • Cloudflare Workers — runs on 300+ edge locations, <50ms cold start (uses V8 isolates, not containers)
  • AWS Lambda@Edge — runs Lambda at CloudFront edge locations
  • Vercel Edge Functions — used for Next.js middleware
  • Deno Deploy — edge-first serverless platform

Use case: A/B testing, auth checks, URL rewrites, personalization — logic that should run close to the user for minimal latency.

16 · Interview Angle

When should you bring up serverless in a system design interview?

  • Event-driven pipelines — "When a user uploads a photo, a Lambda function generates thumbnails"
  • Webhook/callback handlers — "Third-party webhooks trigger a Lambda to process the event"
  • Cron/scheduled tasks — "A scheduled Lambda runs nightly analytics"
  • Low/variable traffic APIs — "This admin API gets 10 requests/day, Lambda is perfect"

When should you NOT suggest serverless?

  • Real-time chat / gaming (need persistent connections)
  • Core high-traffic API (steady 10K+ QPS → serverful is cheaper)
  • ML training (needs GPU, runs for hours)
  • Anything requiring strict <10ms latency guarantee
