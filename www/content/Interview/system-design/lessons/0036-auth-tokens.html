Authentication Tokens: Session Cookies vs JWTs

Architecting secure, stateless authentication for web, mobile, and microservices.

↑ Back to Course Index Module J — Security

1 · The One Idea

HTTP is fundamentally stateless: each incoming request knows nothing about past requests. To remember that a user logged in, systems historically used Stateful Sessions (storing session IDs in server memory/database). In modern distributed systems with millions of mobile and API clients, we use Stateless JSON Web Tokens (JWT): the user's identity and permissions are cryptographically signed directly inside the token string, allowing any microservice to verify authentication instantly without querying a central database!

2 · Stateful Sessions vs Stateless JWTs

Aspect Stateful Session Cookies Stateless JWT (JSON Web Token)
Where state lives On the server (Redis cluster or database table). Client receives a random session ID string. Entirely in the token payload carried by the client. Server stores zero session state.
Verification Cost Requires a database/Redis lookup on every single HTTP request across all microservices. $0$ database calls! Verified cryptographically in CPU memory via public key or secret signature.
Revocation / Logout Trivial: Delete the session key from Redis. User is instantly logged out everywhere. Hard: Once issued, a JWT is valid until its expiration timestamp unless you maintain a revocation blacklist.

3 · The Anatomy of a JWT

A JWT consists of three base64url-encoded parts separated by dots: header.payload.signature

  1. Header: Algorithmic metadata (e.g. {"alg": "RS256", "typ": "JWT"}).
  2. Payload: Claims data (e.g. {"sub": "user_42", "role": "admin", "exp": 1740000000}). Warning: Not encrypted! Anyone can read this; never store credit cards or passwords in a JWT.
  3. Signature: Computed hash of Header + Payload signed by the server's private key. If an attacker modifies the payload to say "role": "superadmin", the cryptographic signature fails immediately!

4 · The Production Architecture: Access + Refresh Tokens

Best Practice Architecture
  • Access Token (Short-Lived: 10–15 minutes): Stored in memory; passed in Authorization: Bearer <token> header on every API call. Because it expires in minutes, a stolen token's blast radius is tiny.
  • Refresh Token (Long-Lived: 30 days): Stored securely in an HttpOnly, Secure, SameSite=Strict cookie. When the access token expires, client hits POST /auth/refresh to receive a fresh access token. Refresh tokens are tracked in Redis so they can be instantly revoked on user password reset or stolen phone!
