API Versioning & Backward Compatibility

Evolving backend APIs gracefully without stranding older mobile and web clients.

↑ Back to Course Index Module O — UML & API Design

1 · The One Idea

Unlike web apps where users refresh their browser to receive updated JavaScript, mobile users can keep an old app version on their smartphones for 3 years without updating. If you rename an API field from firstName to given_name, thousands of older mobile apps will crash immediately. API Versioning & Compatibility strategies ensure existing clients continue operating smoothly while new clients take advantage of new features.

2 · The 3 Common Versioning Strategies

Strategy Example Pros & Cons
URI Path Versioning (Most Popular) https://api.example.com/v1/users
https://api.example.com/v2/users		 Pros: Explicit, easy to test in browser, easy for API Gateway routing.
Cons: Pollutes URL namespace.
Header Versioning GET /users
Header: X-API-Version: 2		 Pros: Keeps URIs clean and pristine.
Cons: Harder to explore in browser; easy for clients to omit.
Content Negotiation (Accept Header) Accept: application/vnd.company.v2+json Pros: Strict REST purist standard.
Cons: Complex to configure and document.

3 · Postel's Law (The Robustness Principle)

Postel's Law "Be conservative in what you send, be liberal in what you accept."
  • When receiving: Ignore unknown JSON fields from newer clients (never crash on unexpected attributes).
  • When sending: Add new fields freely, but never delete or rename existing fields without a formal multi-month deprecation lifecycle!
