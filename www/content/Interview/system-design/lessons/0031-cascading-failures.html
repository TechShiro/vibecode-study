Cascading Failures & System Resilience

Preventing a minor failure in one dependency from pulling down your entire distributed architecture.

↑ Back to Course Index Module H — Microservices Architecture

1 · The One Idea

In a microservice chain (Service A → Service B → Service C), if Service C becomes slow, Service B's worker threads block waiting for C to reply. Soon, Service B runs out of threads and stops responding to Service A. Service A's threads block and crash. Within minutes, a minor hiccup in a non-critical analytics service has triggered a Cascading Failure that knocks out checkout and authentication across the entire company.

2 · The 4 Resilience Patterns

1. Circuit Breaker Pattern (Netflix Hystrix / Resilience4j)

Acts exactly like an electrical circuit breaker in your house: stops sending traffic to a failing downstream service before it causes a fire.

  • Closed (Normal): Requests pass through. If failure rate exceeds threshold (e.g. 50% errors over 10s), the breaker trips OPEN.
  • Open (Tripped): Breaker immediately fails fast without making any network call. Returns an instant fallback response (e.g. cached recommendations).
  • Half-Open (Testing): After a sleep window (e.g. 30s), breaker lets a few test requests pass. If they succeed, it returns to Closed. If they fail, it remains Open.

2. Bulkhead Pattern (Ship Hull Compartments)

Ships divide their hulls into watertight bulkheads so if one compartment floods, the ship stays afloat. In software, isolate thread pools and connection pools per dependency so that an outage in the "Reviews Service" cannot exhaust the thread pool dedicated to the "Payment Service".

3. Timeouts (Never Wait Forever)

Never make a network call without an explicit timeout! Default to aggressive timeouts (e.g., 500ms). A fast failure is 100x better than a slow hang.

4. Exponential Backoff with Jitter

When retrying a failed network call, do not hammer the server immediately. Double the wait time after each attempt: $100 ext{ms} o 200 ext{ms} o 400 ext{ms} o 800 ext{ms}$.

Why Jitter is Vital If 10,000 clients fail at the same moment and all retry at exactly 1.00s and 2.00s, they hit the recovering server in waves of synchronized shock (thundering herd). Adding random jitter (e.g., $ ext{sleep} = 2^k + ext{random}(0, 100 ext{ms})$) smooths retries into an even distribution.
