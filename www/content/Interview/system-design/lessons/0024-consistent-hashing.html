Consistent Hashing

The elegant algorithm that allows distributed caches and databases to scale dynamically without data storms.

What is CONSISTENT HASHING and Where is it used? — Gaurav Sen A step-by-step whiteboard breakdown of the hash ring and virtual nodes.

1 · The One Idea

In standard distributed caching, you map keys to $N$ servers using modulo: server = Hash(key) % N. But if 1 server crashes, the denominator changes from $N$ to $N-1$. Every single key now hashes to a completely different server! Almost 100% of your cached data is instantaneously missed, and your database dies in a thundering herd. Consistent Hashing solves this: when a server is added or removed, only $1/N$ of the total keys need to be remapped on average!

2 · How the Hash Ring Works

  1. The Circular Ring: Imagine a circle where angles range from $0$ to $2^{32}-1$ (the output range of a 32-bit hash function like MD5 or MurmurHash).
  2. Placing Servers on the Ring: Hash each server's IP address or hostname. Plot the resulting integer on the ring (e.g., Server A at 100, Server B at 500, Server C at 800).
  3. Placing Data Keys on the Ring: When storing user:42, hash the key to get its position on the ring (e.g., position 250).
  4. Routing Rule (Clockwise Traversal): To find which server holds a key, walk clockwise along the ring until you bump into the very first server! (Key 250 walks clockwise and lands on Server B at 500).

3 · Adding and Removing Servers

  • Removing Server B: Only keys between Server A and Server B fall forward onto Server C. Keys on Server A and C remain 100% untouched!
  • Adding a new Server D: Only keys between its predecessor and Server D are relocated to Server D.

4 · The Hotspot Problem and Virtual Nodes (Vnodes)

Basic consistent hashing has a flaw: random placement of 3 physical servers can lead to uneven arcs on the ring (e.g., Server A covers 80% of the ring while B and C cover 10% each).

The Solution: Virtual Nodes (Vnodes):

  • Instead of placing Server A once, place 200 virtual instances of Server A across the ring (Server_A#1, Server_A#2, ..., Server_A#200).
  • Do the same for Server B and C.
  • Now the ring is finely interleaved with hundreds of points per physical machine. The distribution of data becomes mathematically near-perfect!
  • If Server A crashes, its load is evenly shared across Server B and Server C rather than crushing a single neighbor.

5 · Real-World Implementations

  • Amazon DynamoDB & Apache Cassandra: Partition tokens on a hash ring to manage distributed storage.
  • Discord & Akamai CDN: Route user WebSocket connections and HTTP caching to edge nodes.
