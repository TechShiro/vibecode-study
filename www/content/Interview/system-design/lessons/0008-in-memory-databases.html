In-Memory Databases

Lightning-fast data access when disk I/O is too slow.

↑ Back to Course Index Module B — Databases

The one idea

An in-memory database keeps the entire dataset in RAM rather than relying on slower spinning disks or SSDs for primary storage. By bypassing disk I/O, it delivers sub-millisecond read and write latency, making it the perfect choice for caching, session management, leaderboards, and real-time analytics.

Why do we need them?

Traditional RDBMS (like PostgreSQL) or NoSQL databases (like Cassandra) store data on disk to ensure it survives a power loss. However, disk access—even on fast NVMe SSDs—is orders of magnitude slower than RAM (microseconds vs. nanoseconds). When an application needs to serve millions of reads per second, or needs to calculate real-time metrics without delay, hitting the disk for every request creates a massive bottleneck.

Interview Tip: When designing a system, use an in-memory database whenever you hear "low latency," "leaderboard," "user sessions," or "caching."

Redis vs Memcached

When we talk about in-memory databases, two giants dominate the conversation: Redis and Memcached.

Feature Memcached Redis
Data Structures Strings only (Key-Value) Strings, Hashes, Lists, Sets, Sorted Sets, Bitmaps, HyperLogLog, Geospatial
Architecture Multi-threaded (uses multiple cores well) Single-threaded (event loop, very fast but bound to 1 core per instance)
Persistence None. Data is lost on restart. Yes. RDB (snapshots) and AOF (append-only file).
Replication No built-in replication. Yes. Supports Master-Slave replication, Sentinel for HA, and Cluster mode.
Use Case Simple, raw object caching (e.g., HTML fragments). Advanced caching, session store, pub/sub, queues, counters.

Data Structures in Redis

Unlike Memcached, Redis is a "data structure server." This means you can offload computational complexity from your application servers directly into Redis.

  • Strings: Standard key-value cache (e.g., caching a serialized JSON object).
  • Hashes: Perfect for storing objects like user profiles (field-value pairs).
  • Lists: Linked lists. Great for simple message queues or "latest N items" feeds.
  • Sets: Unordered collections of unique elements. Good for "who voted for this" or tag clouds.
  • Sorted Sets (ZSET): Sets ordered by a score. The undisputed king of building Leaderboards and rate limiters.
  • Bitmaps: Bit-level operations. Ideal for tracking daily active users (DAU) across millions of users in very little memory.
  • HyperLogLog: Probabilistic data structure for counting unique items (e.g., unique IP visits) with a tiny memory footprint.

How does Redis survive crashes? (Persistence)

RAM is volatile. If the server loses power, RAM is wiped. Redis solves this by asynchronously syncing data to disk using two main methods:

RDB (Redis Database)

Takes point-in-time snapshots of your dataset at specified intervals (e.g., every 5 minutes).

Pros: Compact file, fast restarts, minimal performance impact on the main thread (forks a child process).

Cons: You will lose data modified since the last snapshot if a crash occurs.

AOF (Append Only File)

Logs every write operation received by the server. These operations are replayed on startup.

Pros: Much higher durability. Can be configured to sync to disk every second (losing max 1 sec of data).

Cons: Larger file size than RDB, slightly slower writes depending on sync policy.

Note: Most production systems use a combination of both for optimal durability and backup capability.

Real-World Examples

  • Twitter/X: Uses Redis heavily for delivering the home timeline. When a user tweets, it is fanned out to the Redis list (timeline) of all their followers.
  • Gaming Leaderboards: Almost all live-service games use Redis Sorted Sets (ZADD, ZREVRANGE) to maintain global leaderboards in real-time.
  • E-commerce (Amazon): Shopping carts and user session data are kept in an in-memory DB so that even if an app server dies, the user's cart is not lost and is retrieved instantly.

Trade-offs & Constraints

  • Cost: RAM is expensive. You cannot store terabytes of cold data in Redis without astronomical AWS/GCP bills.
  • Dataset Size: In Redis, the entire dataset must fit in memory. If you run out of memory, Redis either stops accepting writes or starts evicting older keys (based on your eviction policy, like LRU).
  • Single-Threaded Bottleneck (Redis): Since Redis is single-threaded, a slow command (like KEYS * on a huge dataset) will block all other clients. Always use SCAN instead.
