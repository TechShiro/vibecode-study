Access Control Models & Policy Engines

Architecting fine-grained permissions, roles, and rules at enterprise scale.

↑ Back to Course Index Module J — Security

1 · The One Idea

Authentication answers: "Who are you?". Authorization answers: "What are you allowed to do?". If an e-commerce customer changes their URL from /invoices/100 to /invoices/101 and can view someone else's bill, the system suffers from Broken Object Level Authorization (BOLA). Access Control Models provide structured rules and evaluation engines to govern every single entity read and write.

2 · The 3 Core Permission Models

Model How It Works Best Used For
ACL (Access Control List) Each resource object attaches a list of specific users and their direct rights (e.g., File doc.pdf: Alice=Read, Bob=Write). File systems (Linux/Windows), Google Drive file sharing permissions.
RBAC (Role-Based Access Control) Permissions are assigned to Roles (e.g., Admin, Editor, Viewer). Users are assigned one or more roles. 90% of SaaS web applications (e.g., Jira, Slack, GitHub organization permissions).
ABAC (Attribute-Based Access Control) Evaluates dynamic attributes of the Subject (department), Resource (classification), Action (delete), and Environment (IP address, time of day). Banks, healthcare, defense: e.g., "Allow doctor to view patient records ONLY if doctor is on active shift AND connecting from hospital Wi-Fi."

3 · Modern Policy as Code: Open Policy Agent (OPA)

Instead of hardcoding if (user.role == 'admin') throughout 50 microservice codebases, enterprise architectures decouple policy evaluation using dedicated policy engines like OPA or AWS Cedar. Services send a JSON query to the policy engine, which evaluates rules written in declarative policy code (Rego) and returns an instant allow: true/false decision!
