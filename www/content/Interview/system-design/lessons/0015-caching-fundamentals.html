Caching Fundamentals

How to make your read latency 100x faster by storing frequently used data in ultra-fast RAM.

↑ Back to Course Index Module D — Caching

1 · The One Idea

Reading data from a hard drive or SSD takes milliseconds. Reading data from RAM (memory) takes nanoseconds to microseconds — roughly 100 to 1,000 times faster. A Cache is a temporary, high-speed in-memory storage layer positioned in front of your database to intercept read queries and return responses instantly without hitting slow disk storage.

2 · Cache Hit vs Cache Miss

  • Cache Hit: The requested key is found in cache memory. Returned immediately in < 2ms.
  • Cache Miss: The key is not in cache. The backend must query the database, write the result into cache for future requests, and return it to the client.
  • Cache Hit Ratio: Hits / (Hits + Misses). A healthy system typically aims for > 90% hit ratio.

3 · Redis vs Memcached: Which to Choose?

Feature Redis Memcached
Data Structures Rich: Strings, Lists, Sets, Sorted Sets (ZSet), Hashes, Bitmaps, HyperLogLog, Geospatial. Pure Simple Key-Value strings only.
Thread Model Single-threaded event loop (ultra predictable, no locking overhead). Multi-threaded (scales well across many CPU cores for raw string throughput).
Persistence to Disk Yes: RDB snapshots and AOF (Append-Only File) logging. No: Pure volatile RAM. Crashes wipe all data.
Replication & HA Native Master-Replica replication, Redis Sentinel, Redis Cluster. None built-in; must be managed by the client application.
Verdict Default choice for 95% of modern system designs. Great only for ultra-simple, massive multi-core string caching clusters.

4 · The 3 Big Cache Failure Modes

Caching introduces specific operational hazards that every engineer must prepare for:

1. Cache Penetration

Clients repeatedly query for non-existent keys (e.g., hacker querying user ID -99999). The cache misses every time, and every single request hammers the database directly.

Solution: Use a Bloom Filter in front of the cache to instantly check if the key exists, or cache the null value with a short 60-second TTL.

2. Cache Breakdown (Hotspot Invalidated)

A super-popular key (e.g., World Cup final score) expires its TTL. In that exact millisecond, 50,000 concurrent requests miss the cache and all hit the database simultaneously.

Solution: Use a distributed mutex lock (e.g., Redis SETNX) so only 1 worker queries the database while the rest wait.

3. Cache Avalanche

Thousands of cached keys were created at the same time with the exact same 1-hour TTL. Exactly 1 hour later, all keys expire together, instantly drowning the database in queries.

Solution: Add random jitter to your TTLs (e.g., TTL = 3600 + random(0, 300) seconds) so expirations are scattered evenly over time.
