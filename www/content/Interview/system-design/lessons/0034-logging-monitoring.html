Logging & Monitoring: The 3 Pillars of Observability

Turning a distributed black box into an open window of actionable telemetry.

↑ Back to Course Index Module I — Monitoring & Logging

1 · The One Idea

In a distributed system with 100 microservices running on 500 servers, you cannot simply SSH into a machine and read a local text file. When an error strikes, you need centralized Observability to answer three questions instantly: What broke? Where did it break? Why did it break? Observability rests on three foundational pillars: Metrics, Logs, and Traces.

2 · The 3 Pillars of Observability

Pillar What It Is Tools & Example
1. Metrics
(Aggregated Numbers)		 Numeric measurements recorded over time intervals (Time-Series data). Ultra lightweight to store and query. Tells you THAT a problem exists. Prometheus, Grafana, Datadog.
Example: http_requests_total, CPU usage 92%, P99 latency 450ms.
2. Logs
(Timestamped Events)		 Discrete event records with rich contextual metadata. Tells you WHY a specific failure occurred. ELK Stack (Elasticsearch, Logstash, Kibana), Loki.
Example: JSON structured log: {"timestamp": "...", "error": "NullPointerException at line 42", "user_id": 99}.
3. Distributed Traces
(Request Journeys)		 Tracks a single incoming request across its complete lifecycle as it hops through 12 microservices and databases. OpenTelemetry, Jaeger, Zipkin.
Every request receives a unique Trace-ID and propagating Span-IDs. Shows waterfall latency per service.

3 · The RED Method for Services

Engineered by Tom Wilkie, the RED Method defines the 3 essential metrics to track for every microservice:

  • Rate: The number of requests per second (QPS/RPS) your service is handling.
  • Errors: The number of failed requests (e.g. HTTP 5xx status codes) per second.
  • Duration: How long requests take to complete (latency percentiles: P50, P90, P99).

4 · The USE Method for Hardware Infrastructure

Created by Brendan Gregg for monitoring raw hardware resources (CPU, Memory, Disk, Network):

  • Utilization: Percentage of time the resource was busy (e.g., CPU at 85%).
  • Saturation: Extra work queued waiting for the resource (e.g., Linux load average or run-queue length).
  • Errors: Count of error events (e.g., disk I/O device errors, network packet drops).
