Containerization: Docker & Kubernetes

Standardizing application packaging and automated planetary orchestration.

↑ Back to Course Index Module H — Microservices Architecture

1 · The One Idea

Before containers, deploying software was plagued by the classic excuse: "It works on my machine!" because development laptops and production servers had mismatched OS libraries and Python/Java runtimes. Docker Containers package application code, dependencies, runtimes, and system libraries into an immutable, portable artifact that runs identically on any cloud or OS. Kubernetes (K8s) is the container orchestrator that automates deployment, scaling, health self-healing, and networking for thousands of containers across a cluster.

2 · Containers vs Virtual Machines (VMs)

Aspect Virtual Machines (VMware, EC2) Containers (Docker)
Architecture Runs a complete Guest OS on top of a Hypervisor. Heavy disk space (GBs) and high RAM overhead. Shares the host OS Linux kernel; isolates processes using Linux namespaces and cgroups. Lightweight (MBs).
Startup Time Minutes (must boot an entire operating system). Milliseconds to seconds (starts like a native OS process).
Density Tens of VMs per physical host server. Hundreds of containers per physical host server.

3 · The Core Kubernetes Concepts (Zero-Level Guide)

  • Pod: The smallest deployable unit in K8s. Wraps one or more tightly-coupled containers sharing the same network IP and storage volume.
  • Deployment: Defines the desired state (e.g., "Always keep 5 replicas of the Auth Pod running"). K8s automatically performs zero-downtime rolling updates.
  • Service: A persistent virtual IP and internal load balancer that routes traffic to active Pods (since Pods are ephemeral and constantly die/restart with new IPs).
  • Ingress: The external gateway routing public internet HTTP/HTTPS traffic to internal K8s Services.

4 · Service Mesh (Istio / Envoy)

When you have 500 microservices communicating, managing TLS encryption, retries, and distributed tracing inside every application codebase becomes unmaintainable.

A Service Mesh injects a lightweight Sidecar Proxy (Envoy) alongside every Pod. All service-to-service communication flows through the sidecar proxies, offloading mutual TLS (mTLS), circuit breaking, and telemetry out of the application code entirely!
