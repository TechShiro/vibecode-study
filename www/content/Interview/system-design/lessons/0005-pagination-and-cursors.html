Pagination & Cursors

Whenever an interviewer asks you to "design a feed" or "return a list of users," you absolutely must bring up pagination. Returning 10 million rows in one JSON response is how servers crash.

Track goal: Master System Design for interviews — HLD + LLD. This is Lesson 5 of 66. Index

1 · The One Idea

To fetch large datasets, APIs break the data into smaller chunks (pages). There are two main strategies: Offset-based pagination (skip $X$ items, take $Y$) which is easy but scales horribly, and Cursor-based (Keyset) pagination (give me $Y$ items *after* this specific marker) which is complex but scales infinitely. At FAANG scale, you almost exclusively use cursors.

2 · Offset-Based Pagination

The most common and intuitive approach. The client tells the server: "Skip the first 100 items, and give me the next 20."

How it works (API & SQL)

// API Request: Give me page 6 (assuming 20 items per page)
GET /api/users?page=6&limit=20

// Backend calculates: offset = (page - 1) * limit = (6 - 1) * 20 = 100

// SQL Query sent to Database
SELECT * FROM users 
ORDER BY created_at DESC 
LIMIT 20 OFFSET 100;

The Problems (Why it fails at scale)

  1. Performance Degradation: OFFSET 1000000 LIMIT 20 does not magically jump to the millionth row. The database must scan, load, and discard 1,000,000 rows just to give you the 20 you want. As the offset grows, the query gets slower (O(N)).
  2. Data Drift (The Missing/Duplicate Item Bug):
    • Imagine you are on Page 1 (items 1-10).
    • While you read, someone deletes item 2.
    • Item 11 shifts into the 10th spot.
    • You click "Page 2" (skip 10, take 10). You miss item 11 completely!
    • Conversely, if an item is inserted at the top, items shift down, and you will see duplicates across pages.

3 · Cursor-Based Pagination (Keyset)

Instead of saying "skip $X$ items," the client says: "Give me the next 20 items that come after the last item I saw." The marker of that last item is the Cursor.

How it works (API & SQL)

The cursor is usually a unique, sequential column (like a Timestamp, Auto-incrementing ID, or UUID v7).

// API Request: Client sends the ID of the last item from the previous page
GET /api/users?cursor=9876&limit=20

// SQL Query sent to Database
SELECT * FROM users 
WHERE id < 9876       // Assuming descending order
ORDER BY id DESC 
LIMIT 20;

Why it succeeds at scale

  1. O(1) Performance: If id is indexed, the database instantly jumps to id = 9876 using a B-Tree index, and grabs the next 20 rows. It doesn't matter if it's the 1st page or the 10,000th page; it's exactly as fast.
  2. No Data Drift: Since you anchor to a specific row, inserts or deletes happening above or below your cursor do not shift your position. You never miss items or see duplicates.
The Non-Unique Sort Key Gotcha If you sort by a non-unique column (like first_name or likes_count), you can't use it directly as a cursor, because multiple rows might have "50 likes".
Solution: Combine it with a unique tie-breaker. Sort by (likes_count, id), and make your cursor a combination of both: WHERE (likes_count, id) < (50, 9876).

6 · Opaque Page Tokens

If you expose an internal DB ID as a cursor (e.g., ?cursor=9876), clients might start relying on that ID format, or try to guess the next ID. Furthermore, if you change your backend database, the cursor format might break.

Solution: The server Base64-encodes the cursor into an Opaque Token. 

// Client requests first page
GET /api/tweets

// Server responds:
{
  "data": [...],
  "next_page_token": "ZXlKMGFXMWxjM1JoYlhB"  // Base64 string
}

// Client fetches next page:
GET /api/tweets?page_token=ZXlKMGFXMWxjM1JoYlhB

The client treats it as a random string. The server decodes it to extract the ID, Timestamp, or whatever internal sorting mechanism it uses.

7 · How different Databases handle Pagination

  • SQL (Postgres, MySQL): Uses LIMIT/OFFSET (bad) or WHERE col > val (good).
  • MongoDB: Has .skip(X).limit(Y). Skip has the exact same performance problems as SQL OFFSET. Use range queries instead: db.col.find({_id: {$gt: last_id}}).limit(20).
  • DynamoDB (AWS): Doesn't support offset at all. Forces you to do it right. Provides an ExclusiveStartKey in responses, which you pass back to get the next page.
  • Elasticsearch: Default from/size fails past 10,000 results to protect memory. You must use search_after (cursor) for deep pagination.

8 · The "Total Pages" Problem

If you use numbered pages, your UI usually says "Showing 1-20 of 1,234,567 results". To get that number, the backend must run SELECT COUNT(*) FROM users;.

Count is slow! In modern relational databases (especially Postgres/MVCC), COUNT(*) is surprisingly slow on large tables because it has to do a full table scan to verify row visibility.

Solutions:
  • Drop the total count completely (use Infinite Scroll).
  • Use estimated counts (e.g., reading metadata from Postgres stats tables).
  • Cache the total count in Redis and update it asynchronously.

9 · System Design Interview Angle

If the prompt is "Design Twitter / Instagram / News Feed":

  • Never suggest Offset Pagination. It immediately signals you haven't built large-scale apps.
  • State clearly: "We will use cursor-based pagination utilizing a page_token. The cursor will be the Tweet ID (if it's a timestamp-based ID like Snowflake) or a compound key of (timestamp, tweet_id) to ensure strict ordering and O(1) index lookups."
  • Mention that cursor pagination perfectly matches the Infinite Scroll UX pattern that modern feeds use.
