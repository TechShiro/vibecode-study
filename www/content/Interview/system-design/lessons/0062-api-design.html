RESTful API Design Principles

Designing intuitive, developer-friendly, and standardized HTTP interfaces.

1 · The One Idea

A poorly designed API uses verbs in URLs (e.g. POST /getUserDetails, POST /delete_item) and returns HTTP 200 OK even when requests crash with database errors. A professional RESTful API models endpoints as Resource Nouns in plural form and leverages standard HTTP Verbs and semantic HTTP Status Codes to express intentions cleanly.

2 · Standard HTTP Verbs & Idempotency

HTTP Verb Action Idempotent? Safe?
GETFetch resource(s)YesYes (Read-only)
POSTCreate new resourceNo (Multiple POSTs create duplicates)No
PUTReplace/overwrite complete resourceYes (Calling 5 times leaves same state)No
PATCHPartial update (modify 1 field)Generally NoNo
DELETERemove resourceYes (Calling once or 10 times = deleted)No

3 · Semantic HTTP Status Codes to Memorize

  • 200 OK: Standard success.
  • 201 Created: Resource successfully created (returned after POST with Location header).
  • 204 No Content: Success, but response body is intentionally empty (common after DELETE).
  • 400 Bad Request: Client sent invalid JSON or syntax errors.
  • 401 Unauthorized: Missing or invalid authentication token (who are you?).
  • 403 Forbidden: Authenticated, but lacking permission to touch this resource.
  • 404 Not Found: Resource does not exist.
  • 409 Conflict: State conflict (e.g. duplicate username registration).
  • 422 Unprocessable Entity: Valid JSON syntax, but violates business validation rules (e.g. age < 0).
  • 429 Too Many Requests: Rate limit exceeded.
  • 500 Internal Server Error: Unhandled exception on backend server.
  • 503 Service Unavailable: Server overloaded or undergoing maintenance.
