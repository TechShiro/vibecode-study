API Gateway & Service Discovery Architecture

How dynamic cloud instances find and communicate with each other automatically.

↑ Back to Course Index Bonus HLD Fundamentals

1 · The One Idea

In modern cloud environments (Kubernetes, AWS Auto Scaling), servers are ephemeral: containers crash, autoscalers spin up 50 new instances during traffic surges, and IP addresses change every 10 minutes. Microservice A cannot hardcode an IP address like 192.168.1.50 to talk to Microservice B. Service Discovery is the dynamic phonebook (Service Registry) that keeps track of active IPs, ports, and health statuses of every service in the cluster.

2 · Client-Side vs Server-Side Discovery

Pattern How It Works Pros & Cons
Client-Side Discovery
(Netflix Eureka / Ribbon)		 Client queries the Service Registry (Eureka) directly, caches the list of live server IPs, and runs an internal load balancing algorithm in client code. Pros: Zero intermediate network hops; fast.
Cons: Couples discovery library to application language (needs Java/Go/Node SDKs).
Server-Side Discovery
(Kubernetes DNS / AWS ALB)		 Client simply sends a request to a fixed DNS name (e.g. http://payment-service). A proxy/load balancer queries the registry and forwards the request. Pros: Language agnostic; 100% transparent to developer.
Cons: One extra network hop through the proxy.

3 · The API Gateway as Central Entrypoint

The API Gateway acts as the unified reverse proxy front door for all public traffic, performing SSL termination, authentication token checks, rate limiting, and service discovery routing before forwarding requests to internal private microservices.
