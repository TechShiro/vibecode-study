Horizontal vs Vertical Scaling

Every system will eventually need to handle more load — the question is whether you make your machine bigger or add more machines. This lesson teaches you the most fundamental scaling decision in system design.

Track goal: Master System Design for interviews — HLD + LLD. This is Lesson 3 of 66. Index

1 · The One Idea

When your system can't handle the load, you have exactly two options: Vertical Scaling (Scale Up) — get a bigger machine, or Horizontal Scaling (Scale Out) — get more machines. Vertical is simpler but has hard limits; horizontal is complex but scales infinitely. Almost every large-scale system ultimately goes horizontal.

2 · Vertical Scaling (Scale Up)

Add more power to your existing machine: more CPU cores, more RAM, faster SSDs, better network card.

How it works

  • Upgrade from t3.medium (2 vCPU, 4 GB) to m5.4xlarge (16 vCPU, 64 GB)
  • Or add more RAM sticks / swap to NVMe SSD on bare metal
  • Your application code doesn't change — same single server, just more powerful

Advantages

  • Simple — no code changes, no distributed systems complexity
  • No data consistency issues — single source of truth on one machine
  • Lower operational overhead — one server to monitor, patch, back up
  • Inter-process communication is fast — everything is local, no network calls

Disadvantages

  • Hardware limits — the biggest AWS instance (u-24tb1.metal) has 448 vCPUs and 24 TB RAM. That's the ceiling.
  • Single point of failure — if that one machine dies, everything is down
  • Exponential cost — 2x resources ≠ 2x cost. Often 3–4x cost for 2x performance
  • Downtime during upgrade — usually need to stop the server to resize (though live migration exists in some cloud providers)
🏢 Real-world example
Stack Overflow famously runs on just a few very powerful servers. As of 2024, their entire site (serving 100M+ monthly visitors) runs on ~9 web servers and 4 SQL Server instances. They scale vertically with high-end hardware. It works because their architecture is read-heavy and heavily cached.

3 · Horizontal Scaling (Scale Out)

Add more machines (nodes) to your fleet. Distribute the load across them using a load balancer.

How it works

  • Instead of one powerful server, run 10 (or 100, or 1000) smaller servers
  • A load balancer distributes incoming requests across servers
  • Each server runs the same application code (stateless)
  • Add more servers when load increases, remove when it decreases

Advantages

  • Theoretically unlimited — just add more machines (no hardware ceiling)
  • Fault tolerant — if one server dies, others continue serving
  • Linear cost — 2x servers ≈ 2x cost (much more predictable)
  • No downtime for scaling — add/remove servers without interrupting service
  • Geographic distribution — put servers close to users worldwide

Disadvantages

  • Complexity — need load balancers, service discovery, health checks
  • Data consistency — data must be shared/replicated across nodes
  • Stateless requirement — application must not store state locally (or use external state store)
  • Network overhead — inter-service communication is slower than in-process calls
  • More operational burden — monitoring, deploying, and debugging across many machines

6 · Stateful vs Stateless — Why Horizontal Needs Statelessness

Horizontal scaling requires your application to be stateless. A stateless server doesn't store any user-specific data locally — every request can be handled by any server.

The problem with state

// STATEFUL server — stores user session in-memory
Map<String, UserSession> sessions = new HashMap<>();

void handleLogin(Request req) {
    sessions.put(req.getSessionId(), new UserSession(req.getUser()));
    // Session lives in THIS server's memory only!
}

void handleRequest(Request req) {
    UserSession s = sessions.get(req.getSessionId());
    // If load balancer sends this to a DIFFERENT server → session not found → broken!
}

Solutions

ApproachHow It WorksTrade-off
External session store Store sessions in Redis/Memcached — all servers read from it Extra hop to Redis on every request (~1ms). Best approach.
Sticky sessions Load balancer always routes same user to same server (via cookie/IP) If that server dies, user loses session. Uneven load distribution.
Client-side sessions Store session data in a JWT/cookie — server is truly stateless Token size limits. Can't revoke easily. Works for simple auth.
Database sessions Store sessions in the main DB Slower than Redis. Adds load to DB. Not recommended for high traffic.
Interview best answer "I'd make the app servers stateless and store sessions in Redis. This way any server can handle any request, scaling is simple, and if a server dies we don't lose user sessions."

7 · Database Scaling — The Hard Part

Application servers are easy to scale horizontally (stateless + load balancer). Databases are hard because they hold state.

Vertical database scaling

  • Give your DB server more RAM → more data cached in memory → faster queries
  • Faster CPU → faster query processing
  • Faster SSD → faster disk I/O
  • Works well up to a point — MySQL on a beefy machine can handle millions of rows easily

Horizontal database scaling

StrategyHowUse Case
Read Replicas One master (writes) + N replicas (reads). Replicas get async copies of data. Read-heavy workloads (10:1 read:write)
Sharding Split data across multiple DB instances by key (user_id % N) When data is too large for one machine
Partitioning Split tables within the same DB (range, hash, list) Large tables that need to be split for performance
Which databases scale how?
  • MySQL / PostgreSQL — traditionally vertical; horizontal via read replicas + sharding (harder to set up)
  • MongoDB — built-in sharding, horizontal-native
  • Cassandra / DynamoDB — designed for horizontal scaling from day one
  • Redis — Redis Cluster for horizontal scaling

8 · Auto-Scaling

Auto-scaling automatically adjusts the number of servers based on load metrics.

AWS Auto Scaling Group

// Auto Scaling Policy (conceptual)
MinInstances: 2          // always keep at least 2 running
MaxInstances: 20         // never exceed 20
DesiredCapacity: 4       // start with 4

ScaleOutPolicy:
  Metric: CPUUtilization
  Threshold: > 70%       // add instance when CPU > 70%
  Cooldown: 300 seconds  // wait 5 min before scaling again

ScaleInPolicy:
  Metric: CPUUtilization
  Threshold: < 30%       // remove instance when CPU < 30%

Kubernetes Horizontal Pod Autoscaler (HPA)

// K8s HPA — scale pods based on CPU
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 2
  maxReplicas: 50
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

9 · Elasticity vs Scalability

People use these interchangeably, but they're different:

ConceptDefinitionExample
Scalability The ability to handle increased load by adding resources "Our system can scale to 1M users" — it's architecturally capable
Elasticity The ability to automatically scale up AND down based on demand "Our system scales up during Black Friday, scales down at night" — it's dynamic

Scalability is a property. Elasticity is a behaviour. A system can be scalable (add servers manually) but not elastic (doesn't auto-scale). Cloud auto-scaling gives you both.

10 · The Scale Cube (AKF Scale Cube)

The AKF Scale Cube is a model for scaling systems across three axes:

AxisStrategyExample
X-axis Horizontal duplication — clone the entire app behind a load balancer 10 identical web servers
Y-axis Functional decomposition — split by feature/service (microservices) Separate auth service, payment service, search service
Z-axis Data partitioning — split by data (sharding) Users A-M on shard 1, N-Z on shard 2
Interview power move Mentioning the Scale Cube in an interview shows deep understanding. Say: "We can scale on all three axes — X-axis by adding more app server replicas, Y-axis by decomposing into microservices, and Z-axis by sharding the database."

11 · Real-World Scaling Examples

🏢 Netflix
Runs thousands of EC2 instances across multiple AWS regions. Horizontally scaled everything — app servers, caching (EVCache), data layer (Cassandra). Can serve 200M+ subscribers globally with automatic failover between regions.
🏢 YouTube
Started as a single MySQL server (vertical). As traffic exploded, they moved to: read replicas → Vitess (MySQL sharding framework) → eventually horizontal scaling across thousands of shards. A textbook progression from vertical to horizontal.
🏢 Instagram
At launch (2010): 1 Django server + 1 PostgreSQL instance. Scaled vertically for the first year. Then moved to horizontal: multiple app servers, PostgreSQL read replicas, Redis cache, Cassandra for feed storage. Now handles 2B+ users.

12 · Decision Framework

SituationRecommendationReasoning
Small app, <10K usersVertical firstSimple, cheap, no complexity needed yet
Growing app, 10K–1M usersStart horizontal for app, vertical for DBApp is easy to scale out; DB can still handle it vertically
Large app, 1M+ usersHorizontal for everythingMust distribute load, add replicas, shard DB
Read-heavy workloadHorizontal with read replicas + cacheDistribute reads across many nodes
Write-heavy workloadHorizontal with shardingDistribute writes across partitions
Need fault toleranceHorizontal (mandatory)Single machine = single point of failure
Budget-constrained startupVertical first, plan for horizontalDon't over-engineer early; optimize cost
The pragmatic answer In interviews, the best answer is usually: "Start vertical for simplicity, then scale horizontally as traffic grows. Make the application stateless from day one so horizontal scaling is easy when you need it." This shows practical thinking, not just textbook knowledge.

13 · Common Interview Questions

Q: "How would you scale this system to handle 10x more traffic?"

Answer framework:

  1. First: is the bottleneck CPU, memory, I/O, or network?
  2. Application tier → add more app servers (horizontal) behind a load balancer
  3. Database reads → add read replicas + caching layer (Redis)
  4. Database writes → shard the database by a partition key
  5. Static content → use a CDN
  6. Mention auto-scaling for handling traffic spikes

Q: "What problems arise when you scale horizontally?"

  • Data consistency across nodes
  • Distributed transactions become complex
  • Service discovery and health checking
  • Session management (must be external)
  • Debugging is harder (which server had the bug?)
  • Network partitions (CAP theorem comes into play)
