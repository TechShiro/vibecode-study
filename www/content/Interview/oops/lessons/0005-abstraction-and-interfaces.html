Abstraction & Interfaces

Show people a clean dashboard. Hide the engine. Java gives you two tools for this promise: abstract classes and interfaces.

Track goal: Master OOPS for interviews — from zero. This is Lesson 5 of 8. Index

1 · The one idea

Abstraction means showing only what the user needs, and hiding how it works. Think of a car dashboard. You get a steering wheel, two pedals, and a fuel gauge. That is all you need to drive. Under the hood there are hundreds of moving parts — pistons, injectors, a gearbox. You never see them. You don't need to.

In code, abstraction means you design a class by asking one question: "What should the outside world see?" Everything else gets hidden. Java lets you write down the "what" without the "how" using abstract classes and interfaces. This lesson covers both, and when to pick which.

Why interviewers love this "Abstraction vs encapsulation" and "interface vs abstract class" are two of the most-asked OOPS questions in Indian SDE intern interviews. Both sound similar, so a crisp answer instantly separates you from candidates who memorized definitions.

2 · Abstraction vs encapsulation — the classic confusion

Both "hide" something. That's why people mix them up. But they hide different things, for different reasons.

  • Abstraction hides complexity. It is a design decision: "the driver only gets a steering wheel and pedals."
  • Encapsulation hides data. It is an implementation decision: "the bonnet is locked, so nobody can reach in and yank a wire."

Back to the car. The dashboard is abstraction — a simple interface over a complex machine. The locked bonnet is encapsulation — protection, so the internals can't be touched or corrupted from outside. Abstraction is about the view. Encapsulation is about the guard.

One concrete example that shows both at once:

class Car {
    private int fuel = 50;              // ENCAPSULATION: data is private, guarded

    public void drive() {               // ABSTRACTION: one simple button for the user
        igniteEngine();
        injectFuel();
        System.out.println("Vroom!");
    }

    public int getFuel() {              // controlled read access — still encapsulation
        return fuel;
    }

    private void igniteEngine() { /* complex wiring hidden here */ }
    private void injectFuel()   { fuel--; }  // only the class itself may change fuel
}

// The user's whole world:
Car c = new Car();
c.drive();                              // they never see ignition or injection

The caller sees drive() and getFuel(). That tiny public surface is the abstraction. The private keyword on fuel, igniteEngine(), and injectFuel() is the encapsulation that enforces it.

Interview one-liner "Abstraction hides complexity at the design level — deciding what to expose. Encapsulation hides data at the implementation level — bundling data with methods and guarding it with access modifiers. Abstraction is achieved with abstract classes and interfaces; encapsulation with private fields plus getters/setters."

3 · Abstract classes: a half-built template

Sometimes a parent class knows part of the answer but not all of it. Think of an exam paper: the questions are printed (fixed), but the answer boxes are blank — you must fill them. An abstract class is exactly that: some methods have bodies, and some are blank boxes marked abstract. 

abstract class Shape {
    String name;                        // abstract classes CAN have fields...
    Shape(String name) {                // ...and constructors (called via super())
        this.name = name;
    }

    abstract double area();             // blank box: NO body. Child MUST fill it.

    void describe() {                   // shared, fully-written behavior
        System.out.println(name + " has area " + area());
    }
}

class Circle extends Shape {
    double r;
    Circle(double r) { super("Circle"); this.r = r; }

    @Override
    double area() { return Math.PI * r * r; }  // the blank box, filled
}

The rules, in plain words:

  • You cannot do new Shape("x"). An abstract class is an incomplete template — Java refuses to build an incomplete object.
  • One abstract method is enough to force the whole class to be declared abstract.
  • A child must implement every abstract method — or declare itself abstract too and pass the job down.
  • Abstract classes can hold fields, constructors, and normal methods. That's their superpower: shared state + shared code + blanks to fill.
Common trap "Abstract classes can't have constructors" — false. They can, and children call them with super(...). You just can't call new on the abstract class itself. Interviewers use this to catch rote learners.

4 · Interfaces: a pure contract

An interface is a signed contract with no work done yet. Think of a wall socket standard: the standard says "two pins, this shape, 230 volts." It doesn't build any device. Any company can make a fan, a charger, or a fridge — as long as the plug fits, it works with every socket. 

interface Payable {
    double calculatePay();              // implicitly public abstract — no body
}

interface Notifiable {
    void notify(String msg);
}

// A class can sign MANY contracts at once:
class Employee implements Payable, Notifiable {
    @Override
    public double calculatePay() { return 50000; }

    @Override
    public void notify(String msg) { System.out.println("Mail: " + msg); }
}

// Now any code that needs "something payable" accepts an Employee:
Payable p = new Employee();
System.out.println(p.calculatePay());

Notice the magic word: implements, and it takes a comma-separated list. A Java class can extend only one class, but implement many interfaces. Why is multiple allowed here but not for classes? Because classic interfaces carry no fields, no state — just promises. Two promises can't clash the way two inherited copies of a field would. (The one edge case — two interfaces with the same default method — is handled next, and the full diamond-problem story is in Lesson 7.)

5 · Default and static interface methods (Java 8+)

Originally, interfaces were 100% blank. Java 8 relaxed this for one practical reason: if you add a new method to an interface that a thousand classes already implement, all thousand break. A default method ships a fallback body so old implementers keep compiling. 

interface Payable {
    double calculatePay();

    default double yearlyPay() {        // has a body — implementers inherit it for free
        return calculatePay() * 12;     // can call the abstract method
    }

    static double minimumWage() {       // utility that belongs to the interface itself
        return 15000;
    }
}

// Usage:
Payable p = new Employee();
p.yearlyPay();                          // default: called on an instance
Payable.minimumWage();                  // static: called on the INTERFACE name only
  • default — an instance method with a body. Implementers may override it or just use it.
  • static — a helper owned by the interface. Called as Payable.minimumWage(), never through an object, and never inherited by implementers.
Real-world proof Java 8 added sort, forEach, and stream-related defaults to List and Collection without breaking twenty years of existing code. That's the whole reason default methods exist — a great detail to drop in an interview.

6 · Interface vs abstract class — the decision table

This table is the model answer for "how is an interface different from an abstract class?" Memorize the first column, understand the rest.

FeatureAbstract classInterface
Fields / stateYes — any instance fieldsOnly public static final constants
ConstructorsYes (invoked via super())No — never instantiated, nothing to construct
How many can a class take?Extend exactly oneImplement many
Method bodiesAny mix of abstract + concreteAbstract by default; default/static may have bodies
Member access levelsAny: private, protected, public...Methods are effectively public
Relationship it modelsis-a with shared code ("a Circle is a Shape")can-do capability ("an Employee is Payable")
Keywordextendsimplements
The 5-second decision rule Related classes sharing code and fields → abstract class. Unrelated classes sharing only a capability (Comparable, Runnable, Payable) → interface. Need both? Extend one abstract class and implement interfaces — Java allows the combo.

7 · C++ dictionary corner: virtual vs pure virtual

Your senior's notes are C++-flavored, and interviewers often ask in C++ terms. Here is the translation — Lesson 7 does the full dictionary; this is the slice that belongs to abstraction.

C++ termMeaning in C++Java equivalent
virtual functionHas a body; a derived class may override it; the call is resolved at runtimeEvery normal (non-static, non-final, non-private) Java method — no keyword needed
pure virtual functionDeclared with no body at all; a derived class must implement itAn abstract method
Abstract classAny class with ≥ 1 pure virtual functionA class marked abstract (the keyword is explicit)
Class with all functions pure virtual"Interface-style" class — C++ has no interface keywordLiterally an interface

In words: in C++ a method must be explicitly marked virtual to get runtime dispatch, and a pure virtual method is a virtual method declared with no body at all — derived classes are forced to implement it. You never need to write that; you only need to show the same two ideas in Java: 

abstract class Shape {
    abstract double area();          // = C++'s PURE VIRTUAL: no body, children MUST implement

    void describe() {                // = C++'s VIRTUAL: body provided, children MAY override —
        System.out.println("shape"); // every normal Java instance method already works this way
    }
}
Say it in the interview "A virtual function has an implementation that derived classes may override; a pure virtual function has none and must be overridden — it's what makes a C++ class abstract. In Java, all instance methods behave like virtual functions by default, and a pure virtual function corresponds to an abstract method."

8 · Interview questions this lesson answers

Quoted from your senior's Top-25 list, with 2-line model answers.

  • Q6. "Can you explain abstraction vs encapsulation with an example?"
    Abstraction hides complexity by exposing only what's needed (a car's drive() hides ignition and fuel injection); encapsulation hides data by bundling it with methods and marking it private (the fuel field only changes through the class's own methods).
  • Q7. "What is an interface and how is it different from an abstract class?"
    An interface is a pure contract — no state, no constructors, all methods effectively public, and a class may implement many. An abstract class is a partial implementation — fields, constructors, mixed concrete/abstract methods, but a class extends only one.
  • Q22. "Difference between virtual function and pure virtual function."
    Virtual: has a body, derived classes may override, dispatched at runtime. Pure virtual: declared with no body, must be overridden, makes the class abstract. Java mapping: normal instance methods are virtual by default; pure virtual = abstract method.
