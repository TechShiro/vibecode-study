1 · The One Idea

Before Java 5 introduced Generics, collections stored raw Object references. Developers had to manually cast every retrieval: String s = (String) list.get(0);. A single mismatched type crashed in production with ClassCastException. Generics shift type verification from runtime to compile time, guaranteeing type safety before your code ever runs.

2 · Under the Hood: Type Erasure

To preserve backward compatibility with legacy Java 1.4 bytecodes, Java implements generics via Type Erasure:

  • During compilation, the compiler replaces all type parameters (like <T>) with their bounded type (e.g. Object or Comparable).
  • The compiler automatically inserts synthetic type-casts at call sites.
  • At runtime, generic types DO NOT EXIST! List<String> and List<Integer> are the exact same compiled class: List.class!
  • Why new T[] fails: Because at runtime, the JVM has no idea what T is and cannot allocate array memory!

3 · Wildcards & Joshua Bloch's PECS Rule

Is List<Integer> a subclass of List<Number>? NO! Generics are invariant: you cannot pass a List<Integer> to a method expecting List<Number> because the method could write a Double into your Integer list!

To write flexible APIs, use Bounded Wildcards governed by Joshua Bloch's legendary rule:

The PECS Rule

Producer Extends, Consumer Super

  • Producer Extends (? extends T): If your method reads/produces elements of type T from a collection, use <? extends T>. (You can read T, but you cannot write anything except null!).
  • Consumer Super (? super T): If your method writes/consumes elements of type T into a collection, use <? super T>. (You can safely add T, but reads only return Object!).
// Copies from src (Producer) into dest (Consumer)
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T item : src) {
        dest.add(item); // Safe! Dest accepts T or any supertype of T
    }
}
