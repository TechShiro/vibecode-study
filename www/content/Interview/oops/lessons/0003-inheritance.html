Inheritance

Write the common stuff once in a parent class, and let child classes get it for free — plus the rules Java enforces when parents and children disagree.

Track goal: Master OOPS for interviews — from zero. This is Lesson 3 of 8. Index

1 · The one idea

Inheritance lets a class acquire the fields and methods of another class. The child (subclass) gets everything reusable from the parent (superclass), then adds or adjusts what makes it special. Analogy: you inherit your family surname, house rules, and property — you didn't write them, but they're yours — and you still add your own personality on top. The relationship it models is "is-a": a Dog is an Animal.

2 · extends — code reuse in action

Suppose you're building a payroll system. Every employee has a name and base salary; managers additionally have a bonus. Without inheritance you'd copy-paste the shared fields into both classes — and every future fix would need doing twice. With inheritance, write the common part once: 

class Employee {                          // PARENT (superclass / base class)
    protected String name;                // protected: children may use it (Lesson 2)
    protected double baseSalary;

    Employee(String name, double baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }
    double salary() { return baseSalary; }
    void introduce() { System.out.println("I am " + name); }
}

class Manager extends Employee {          // CHILD: gets name, baseSalary, introduce() FREE
    private double bonus;                 // ...and adds its own extras

    Manager(String name, double baseSalary, double bonus) {
        super(name, baseSalary);          // hand the shared setup to the parent
        this.bonus = bonus;
    }
    @Override
    double salary() { return baseSalary + bonus; }  // ...and adjusts behaviour
}

Manager m = new Manager("Krish", 50000, 10000);
m.introduce();                            // inherited — never written in Manager
System.out.println(m.salary());           // 60000 — the overridden version

That's the whole sales pitch: common code lives in one place. Fix a bug in introduce() once, and every subclass is fixed.

One thing children never inherit access to private members of the parent. A private field technically exists inside the child object, but the child's code cannot touch it directly — it must go through the parent's getters/setters or protected members. Encapsulation still applies inside a family.

3 · super and constructor chaining — parent runs first

When a child object is born, Java builds it inside-out: parent part first, then child part. Analogy: you can't build the first floor of a house before the ground floor exists. So every child constructor begins — explicitly or invisibly — by running a parent constructor.

The keyword super means "my parent." It has two jobs:

  • super(...) — call a parent constructor. Must be the first line of the child constructor.
  • super.method() / super.field — reach the parent's version when the child has overridden or shadowed it.
class A {
    A() { System.out.println("A constructor"); }
}
class B extends A {
    B() {
        // invisible super(); inserted here by the compiler
        System.out.println("B constructor");
    }
}
class C extends B {
    C() { System.out.println("C constructor"); }
}

new C();

Trace what actually happens — this exact "what gets printed?" question is an interview staple:

new C() → C's constructor starts, but first line is an implicit super() → jump to B B's constructor starts, first line is an implicit super() → jump to A A has no parent to wait for (except Object) → prints "A constructor" back in B → prints "B constructor" back in C → prints "C constructor" Output order: A, B, C — top of the family tree finishes first
The no-arg-constructor trap The invisible super() calls the parent's no-argument constructor. If the parent only has a parameterized constructor (like Employee(String, double)), the child must call super(args...) explicitly on line one — otherwise it won't compile. This is why Manager above starts with super(name, baseSalary).

4 · Method overriding and @Override

Overriding = the child re-defines a method it inherited, with the same name and same parameters, to change the behaviour. Manager.salary() above overrides Employee.salary(). Analogy: the family recipe book says how to make chai; you keep the recipe's name but brew it your own way.

The @Override annotation is optional but always write it: it asks the compiler to verify you're really overriding. Typo the name (salery()) or the parameters, and instead of silently creating a useless new method, the compiler shouts. Free bug insurance.

Rules the compiler enforces on an override (know these — they get quizzed):

  • Same method name and parameter list as the parent's version.
  • Access can widen, never narrow: a protected parent method can become public, not private.
  • final methods cannot be overridden (Lesson 2's final at work); private and constructors are never inherited, so never overridden.

5 · Method hiding vs overriding — the static twist

What if the method is static? Static members belong to the class, not to objects (Lesson 1) — and only instance methods get the "child version wins" treatment. If a child declares a static method with the same signature as the parent's static method, it doesn't override it — it hides it. Which one runs is decided by the type of the reference variable, at compile time — not by the actual object. 

class Parent {
    static void greet()   { System.out.println("static: Parent"); }
    void speak()          { System.out.println("instance: Parent"); }
}
class Child extends Parent {
    static void greet()   { System.out.println("static: Child"); }   // HIDES
    @Override
    void speak()          { System.out.println("instance: Child"); } // OVERRIDES
}

Parent p = new Child();     // reference type: Parent, actual object: Child
p.speak();                  // "instance: Child"  — object decides (overriding)
p.greet();                  // "static: Parent"   — reference type decides (hiding)
Overriding (instance methods)Hiding (static methods)

Memory hook Objects override, classes hide. Static methods never "belong" to an object, so the object can never get a vote — the variable's declared type picks the method. (Lesson 4 explains the runtime machinery that makes instance methods different.)

6 · Types of inheritance — and the one Java bans

Interviewers expect the five shapes by name. Picture family trees:

TypeShapeIn Java?
SingleB extends AYes
MultilevelC extends B extends A (grandchild chain)Yes
HierarchicalB and C both extend A (one parent, many children)Yes
MultipleC extends A and B (two parents)No for classes — yes via interfaces
HybridAny mix of the above (often contains a multiple part)Only with interfaces in the mix

Why does Java ban multiple class inheritance? The diamond problem, in one breath: if class C extends both A and B, and both define a method show(), which one does C inherit? The ambiguity has no clean answer, so Java's designers banned two parents for classes outright: extends takes exactly one class. Interfaces escape the problem (they carry contracts, not state) — the full story, including Java 8 default methods, comes in Lesson 7.

7 · is-a vs has-a — when to inherit at all

Two ways for classes to relate, and interviewers love asking you to tell them apart:

  • is-a (inheritance). A Dog is an Animal → class Dog extends Animal. The child is a specialised kind of the parent.
  • has-a (composition). A Car has an Engine → the Car keeps an Engine as a field. One object is built out of others.
class Engine { void start() { } }

class Car {
    private Engine engine = new Engine();  // HAS-A: Engine is a field, not a parent
    void start() { engine.start(); }       // Car delegates work to its part
}
// class Car extends Engine { }  ← wrong! A car is NOT a kind of engine

How to choose — apply the sentence test, then the substitution test:

  • Say it out loud. "Car is an Engine" sounds absurd; "Car has an Engine" sounds right. Trust the grammar.
  • Substitution: anywhere the parent is expected, could you honestly hand over the child? A Dog can stand in wherever an Animal is wanted — genuine is-a. An Engine can't stand in for a Car.
  • Do you want reuse of behaviour only? Prefer has-a. Inheritance couples you to the parent's internals forever; composition lets you swap the part (a new Engine) without touching Car's family tree.
The design mantra "Favour composition over inheritance" — use is-a only when the relationship is truly "specialised kind of," and reach for has-a for mere code reuse. Dropping this line (with the Car/Engine example) is an easy interview win. Related follow-up — composition vs aggregation (Q15) — is covered in Lesson 6.

8 · Interview questions this lesson answers

From your senior's Top-25 list:

  • Q1. "What are the main principles of OOPS?" (the Inheritance part)
    Inheritance lets a subclass acquire the fields and methods of a superclass via extends, modelling an is-a relationship. It gives code reuse (shared code lives once in the parent) and enables polymorphism through overriding.
  • Q9. "What is method hiding vs method overriding?"
    Overriding applies to instance methods: the actual object's version runs, chosen at runtime. Hiding applies to static methods with the same signature: the reference type's version runs, chosen at compile time — no polymorphism.
  • Q11. "What are the different types of inheritance (single, multiple, multilevel, hybrid, hierarchical)?"
    Single (one parent), multilevel (grandparent chain), hierarchical (one parent, many children), multiple (two+ parents — banned for Java classes due to the diamond problem, allowed via interfaces), and hybrid (a combination, possible in Java only using interfaces).
  • Q14. "Difference between is-a and has-a relationship."
    is-a = inheritance (Dog extends Animal): the child is a kind of the parent and can substitute for it. has-a = composition (Car holds an Engine field): one object is built from others. Prefer has-a for plain reuse — composition over inheritance.
