Encapsulation and Access Modifiers

Your data needs a bodyguard. Encapsulation is how a class says "nobody touches my fields except through my door."

Track goal: Master OOPS for interviews — from zero. This is Lesson 2 of 8. Index

1 · The one idea

Encapsulation = wrapping data and the methods that use it into one unit, then hiding the data from outsiders. Outsiders interact only through public methods — the class's official "front door." That door can validate, log, or refuse — so the object can guarantee its data is never garbage. This is the first of the four OOP pillars, and the one you already half-built in Lesson 1.

2 · The capsule analogy

Think of a medicine capsule. Inside is powder — several chemicals mixed in an exact ratio. The capsule shell does two jobs: it bundles the chemicals into one unit, and it protects you from touching them directly. You never handle the powder; you swallow the capsule whole.

A well-designed class is a capsule. Fields are the powder (hidden inside). Public methods are the shell (the only safe way to interact). Another everyday version: an ATM. You have a clean interface — insert card, type PIN, get cash. You cannot reach into the machine and grab notes from the tray. The machine's inner state is protected; your only access is through controlled operations.

Encapsulation has two halves — say both Half 1: bundling data + methods in a class. Half 2: data hiding — making fields private so the bundle can't be bypassed. Many candidates say only "data hiding" and lose the completeness point. Bundle first, then hide.

3 · Private fields + getters/setters — and the WHY

Here's the pattern. First, the unprotected version and how it goes wrong:

class Person {
    public int age;          // anyone can write anything...
}

Person p = new Person();
p.age = -5;                  // nonsense — and Java happily allows it

No one can stop that assignment, because the field itself is the door. Now the encapsulated version: make the field private, and offer methods as the only door: 

class Person {
    private int age;                     // hidden — no direct access from outside

    public int getAge() {                // GETTER: controlled read
        return age;
    }

    public void setAge(int age) {        // SETTER: controlled write
        if (age < 0 || age > 130) {      // the bodyguard checks IDs
            throw new IllegalArgumentException("Invalid age: " + age);
        }
        this.age = age;
    }
}

Person p = new Person();
p.setAge(25);       // fine
p.setAge(-5);       // rejected — exception, data stays valid
// p.age = -5;      // won't even compile: age is private

Why bother with this ceremony? Four concrete wins:

  • Validation. setAge(-5) can be rejected. With a public field, it can't.
  • Read-only or write-only data. Provide a getter but no setter → outsiders can read but never change it (an account number, for example).
  • Freedom to change internals. Tomorrow you might store birth date instead of age and compute age in getAge(). Callers never notice — the door looks the same.
  • One place to debug. If the balance is ever wrong, the bug must be inside the class's own methods. With public fields, the whole codebase is a suspect.
"Getters/setters everywhere" is NOT the point If you blindly add a public getter and setter for every field, you've built a public field with extra steps. The point is control: add a setter only if outsiders truly need to change that field, and put rules in it. Saying this in an interview shows real understanding, not memorisation.

4 · Access modifiers — the four visibility levels

Java gives you four dials for "who can see this member," from most open to most locked: public → protected → default (no keyword, aka package-private) → private. Analogy — your house: the front lawn is visible to everyone (public); some rooms are open to family and their children even after they move to another city (protected — includes subclasses); the living room is for people inside your gated society (default — same package); your diary is yours alone (private).

ModifierSame classSame packageSubclass (other package)Everywhere
publicYesYesYesYes
protectedYesYesYesNo
default (no keyword)YesYesNoNo
privateYesNoNoNo
 
package bank;

public class Account {
    private double balance;          // only Account's own methods
    protected String branchCode;     // Account + same package + subclasses anywhere
    String internalNote;             // default: same package only
    public void deposit(double a) {} // everyone
}
The two rows people forget (1) Default is a real level — no keyword means "package-private," not public. (2) protected = default + subclasses. It's the inheritance-friendly level: a subclass in a different package can still see it. You'll use it in Lesson 3.
Rule of thumb Fields: private by default, always. Methods: public only for the class's official API, private for internal helpers. Start locked; open up only with a reason. Interviewers love hearing "principle of least privilege."

5 · final — the "no changes" keyword

final means "this cannot change" — but what can't change depends on where you put it. One keyword, three uses:

Used onMeaningEveryday analogy
final variable/fieldAssign once, never reassignInk on your birth certificate
final methodSubclasses cannot override itA rule head office won't let branches modify
final classNobody can extend (subclass) itA sealed product — no third-party modifications
 
final double PI = 3.14159;       // PI = 3; → compile error

class Account {
    final String accountNo;       // set once (here or in constructor), fixed forever
    Account(String no) { this.accountNo = no; }
    final void audit() { }        // subclasses may use it, may not override it
}

final class SecureToken { }       // class Fake extends SecureToken → compile error
final reference ≠ frozen object final List<Integer> list = new ArrayList<>(); — you cannot repoint list to another list, but list.add(5) is perfectly legal. final freezes the reference (the address slip from Lesson 1), not the object it points to. This distinction is a favourite follow-up question.

Real example you already know: String is a final class in Java — you cannot extend it. Why would the JDK do that? That brings us to immutability.

6 · A first taste of immutability

An immutable object never changes after construction. No setters, no way in. Want a "different" value? You create a new object. Analogy: a printed photograph — you can't edit it; you take a new photo. Java's String works exactly like this: s.toUpperCase() doesn't change s, it returns a brand-new string.

The classic recipe (know these steps by heart):

final class Money {                       // 1. final class — no subclass can add mutability
    private final int amount;             // 2. private final fields — hidden AND fixed
    private final String currency;

    Money(int amount, String currency) {  // 3. set everything in the constructor
        this.amount = amount;
        this.currency = currency;
    }

    int getAmount() { return amount; }    // 4. getters only — NO setters
    String getCurrency() { return currency; }

    Money add(int extra) {                // 5. "changes" return a NEW object
        return new Money(this.amount + extra, this.currency);
    }
}

Why is this worth the trouble? Immutable objects are impossible to corrupt — no validation needed after birth — and safe to share across threads or hand out from getters without fear someone mutates your internals. Encapsulation taken to its logical extreme: don't just guard the data, make change impossible. Lesson 6 (SOLID & design) builds on this.

7 · Interview questions this lesson answers

From your senior's Top-25 list:

  • Q1. "What are the main principles of OOPS?" (the Encapsulation part)
    Encapsulation is bundling data with the methods that operate on it, and hiding the data behind private so all access goes through controlled public methods. It protects object state (e.g. rejecting setAge(-5)) and lets internals change without breaking callers.
  • Q6. "Can you explain abstraction vs encapsulation with an example?" (the encapsulation half — abstraction arrives in Lesson 5)
    Encapsulation is about protecting HOW data is stored: a Person hides its private int age and validates writes via setAge. (Abstraction, in contrast, is about exposing only WHAT something does — hold this thought for Lesson 5.)
  • Q10. "What are access specifiers (public, private, protected)?"
    They control member visibility. Java has four: public (everywhere), protected (package + subclasses), default/package-private (package only), private (declaring class only). Best practice: private fields, public methods only for the intended API.
