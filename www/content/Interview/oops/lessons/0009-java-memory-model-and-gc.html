Java Memory Model, Object Lifecycle & Garbage Collection

Where objects actually live in physical RAM, how the JVM reclaims memory, and preventing memory leaks.

1 · The One Idea

In languages like C and C++, you manually allocate memory with malloc() and must manually free it with free() or delete. Forgetting causes memory leaks; freeing twice causes crashes. In Java, objects are created on the JVM Heap, and the Garbage Collector (GC) automatically scans and frees objects that are no longer reachable from any active GC Root (thread stack frames, static variables, JNI references).

2 · Stack vs Heap Memory

Aspect Thread Call Stack JVM Heap Memory
What is stored Primitive local variables (int x = 5), method parameters, and references (pointers) to heap objects. All actual object instances (new User(), new String(), arrays).
Thread Access Private to each thread. Thread-safe by default. Shared across all threads. Requires synchronization for mutable state!
Lifecycle Push and popped instantaneously with method execution (zero GC overhead). Managed and cleaned asynchronously by the Garbage Collector.

3 · Generational Garbage Collection: Why Most Objects Die Young

JVM engineers discovered the Weak Generational Hypothesis: Over 95% of all objects allocated in a software program become unreachable within milliseconds of creation (e.g. temporary loop variables, short-lived DTOs).

Young Gen: Eden Space
Survivor S0 / S1
Old / Tenured Generation
  • Eden Space: Where brand-new objects are born. When full, a blazing fast Minor GC runs, copying surviving objects into Survivor space.
  • Survivor Spaces (S0 / S1): Surviving objects bounce between S0 and S1 with an age counter.
  • Old (Tenured) Generation: Objects that survive 15 Minor GC cycles (tenuring threshold) are promoted here (e.g. database connection pools, Spring singleton beans). Cleaned by Major / Full GC (more expensive).

4 · The 4 Reference Types in Java

  • Strong Reference (Default): User u = new User();. As long as u is reachable, GC will NEVER collect it, throwing OutOfMemoryError instead.
  • Soft Reference (SoftReference<T>): GC only reclaims these when the JVM is desperately running out of memory. Ideal for memory-sensitive in-memory image caches.
  • Weak Reference (WeakReference<T>): GC reclaims these on the very next GC cycle, regardless of memory availability! Powers WeakHashMap (keys automatically disappear when no longer referenced elsewhere).
  • Phantom Reference (PhantomReference<T>): Enqueued when an object is physically finalized; used for custom native cleanup instead of deprecated finalize().
