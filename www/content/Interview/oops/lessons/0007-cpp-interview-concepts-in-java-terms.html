1 · The one idea

Your senior's study material — and many interviewers' question banks — are written in C++. That's fine. You don't need to write C++ — you need to answer these questions in words and show the Java equivalent. Every C++ OOPS concept has a clean Java answer: either Java does it automatically, does it differently, or deliberately removed it. Saying which of the three and why is a stronger answer than any memorized C++ definition. 2 · Virtual functions — and why every Java method already is one

Recall from Lesson 4: when a parent-type variable holds a child object, which method runs? C++ makes you choose the behavior per method. Java chose one behavior for the whole language.

  • C++ default: the variable's type decides, at compile time (static binding). You must write virtual to make the object's real type decide at runtime.
  • Java: the object's real type always decides. Every instance method behaves like a C++ virtual function, no keyword needed.

MCQ 8 from your senior's set is the classic C++ trap: a base class and a derived class both define show(), but the method is not marked virtual. A base-typed pointer holding a derived object calls show() — and C++ prints "Base", because without the virtual marker the pointer's declared type wins at compile time. That trap doesn't translate to Java, which is exactly the point: 

// The same shape in Java — no keyword needed anywhere:
class Base    { void show() { System.out.println("Base"); } }
class Derived extends Base { @Override void show() { System.out.println("Derived"); } }

Base b = new Derived();
b.show();                           // prints "Derived" — object's real type ALWAYS wins
// (in C++ this exact code shape would print "Base" unless show() were marked virtual)

Exceptions — the three Java method kinds that are not dynamically dispatched: static (belongs to the class; hidden, not overridden), final (overriding banned), and private (invisible to subclasses). Everything else: virtual.

How dynamic dispatch works inside (the vtable)

Interviewers follow up with "but how does the runtime know?" Analogy: a franchise restaurant chain. Head office publishes a menu format ("item #3: Today's Special"), and each branch keeps its own menu card with its own recipe at slot #3. You order "item #3"; whichever branch you're standing in, their card decides the dish.

  • Each class gets a hidden table of method addresses — the vtable (Java: part of the class metadata; the JVM does the same job).
  • Every object carries a hidden pointer to its own class's table.
  • A call like b.show() compiles to: "follow the object's table pointer, jump to the show slot." An overriding class simply put a different address in that slot.
Q13 model answer "Each class has a virtual table mapping method slots to implementations; each object holds a pointer to its class's table. A virtual call is resolved by looking up the slot at runtime through the object's table — so the object's actual type, not the reference type, picks the method. Java's JVM does this for all instance methods by default (and JIT-optimizes it)."

3 · Virtual destructor — the C++ question with a one-line Java answer

The C++ problem (senior's MCQ 25), in words: in C++ you destroy objects by hand, and each class can have a destructor — cleanup code that runs at that moment. If you destroy a derived object through a base-class pointer and the base destructor is not marked virtual, only the base half gets cleaned up — the derived class's destructor never runs, leaking whatever it owned. Marking the base destructor virtual makes the destruction dispatch to the real type, so the derived cleanup runs first, then the base's. 

// Java: the question dissolves — there are no destructors and no manual delete.
Base b = new Derived();
b = null;   // GC always knows the object's REAL type — the whole Derived is freed. Always.

// For non-memory cleanup (files, sockets), Java's answer is try-with-resources:
try (FileReader fr = new FileReader("data.txt")) {
    // use fr ...
}   // fr.close() runs HERE, guaranteed — predictable cleanup without any destructor

Interview answer: "A virtual destructor ensures that deleting a derived object through a base pointer runs the derived destructor too. Java has no destructors at all — the garbage collector frees the entire object knowing its real type, so this whole class of bug can't happen. For non-memory resources, Java uses try-with-resources."

4 · Why can't a constructor be virtual?

This one is asked constantly (Q8, and MCQ 12: "virtual constructor" is the fake option among constructor types). The reasoning is a chicken-and-egg problem:

  • Virtual dispatch needs an existing object — the lookup goes through the object's hidden table pointer.
  • A constructor's job is to create that object. Before it runs, there is no object, no table pointer — nothing to dispatch through.
  • Also, to construct anything you must name the exact class (new Derived()). "Pick the constructor by the object's runtime type" is circular — the runtime type is what you're creating.

Analogy: virtual dispatch is asking a person "which branch's menu do you follow?" — you can't ask that question to a person who hasn't been born yet.

The related Java trap — overridable calls in constructors Java constructors aren't virtual either (they're not inherited, not overridden). But a constructor can call a virtual method — and that call DOES dispatch to the child's override, before the child's fields are initialized: 
class Base  { Base() { greet(); }  void greet() { } }
class Child extends Base {
    String name = "Krish";
    @Override void greet() { System.out.println(name.length()); } // NPE! name is still null
}
new Child();  // Base() runs first (MCQ 26/27: base constructs before derived) → boom
Rule of thumb: never call overridable methods from a constructor. If you need polymorphic creation, use a factory method — that's the standard "workaround" answer.

5 · friend class / friend function — and Java's nearest equivalents

In C++, class A can declare class B as its friend — "B is my trusted friend; it may read my private members." Both a class and a standalone function can be named as friends (senior's MCQ 14: "both a and b"). Use case: two tightly coupled classes, e.g. a LinkedList and its Iterator, where the iterator must walk private node pointers without exposing them to the world.

Java deliberately has no friend. Its two nearest tools:

// 1. PACKAGE-PRIVATE (no modifier): visible to every class in the SAME package.
//    "Friendship" at folder level — put the trusted classes together.
class Engine {
    int rpm;                            // no modifier → package-private
}
class Dashboard {                       // same package → can read engine.rpm directly
    void show(Engine e) { System.out.println(e.rpm); }
}

// 2. NESTED CLASS: an inner class sees the outer class's privates — friendship by containment.
class LinkedList {
    private Node head;
    private static class Node { int val; Node next; }

    class Iterator {                    // inner class: full access to private head
        Node cur = head;
    }
}

Interview answer: "friend grants another class or function access to my privates — useful for tightly coupled pairs like a container and its iterator. Java dropped it as a hole in encapsulation; instead you use package-private access for same-package trust, or nested classes — exactly how java.util collections implement their iterators."

6 · Operator overloading — how C++ does it, why Java said no

C++ lets you redefine what operators mean for your types, using its operator keyword (MCQ 28): you write a specially named method for a symbol, and after that, putting a plus sign between two of your objects runs your code. You can only re-teach existing operators for user-defined types — you cannot invent brand-new operators or change precedence (MCQ 20). 

// Java — no operator overloading. You write a named method instead:
class Complex {
    final double re, im;
    Complex(double re, double im) { this.re = re; this.im = im; }

    Complex add(Complex o) {            // the honest name for what '+' would hide
        return new Complex(re + o.re, im + o.im);
    }
}
Complex c = a.add(b);                   // same power, explicit name

// Real JDK example: BigInteger x = a.add(b).multiply(two);

Why did Java remove it? Readability and predictability. When a + b can run arbitrary hidden code, every plus sign becomes a puzzle — does it add, concatenate, merge, or fire a network call? Java's designers decided a.add(b) says what it does. The one built-in exception: + is overloaded by the language for String concatenation ("age: " + 21) — the language may, you may not.

7 · The diamond problem — two solutions, one diagram

Multiple inheritance's famous failure. B and C both extend A; D extends both B and C. Now D asks for something from A — via which side? And does D contain one copy of A's fields, or two?

How C++ solves it: virtual inheritance. B and C each mark their inheritance from A as virtual, which tells the compiler "share ONE copy of A" instead of duplicating it. It works, but it's fiddly and easy to forget.

How Java solves it: in two layers.

  • Layer 1 — ban it for classes. A Java class extends exactly one class. No two paths to a field, ever. Multiple inheritance of state is simply illegal (this is also why "hybrid inheritance" via classes doesn't exist in Java).
  • Layer 2 — tame it for interfaces. Interfaces have no fields, so only behavior can clash — via default methods. When it does, Java refuses to guess:
interface B { default String hello() { return "from B"; } }
interface C { default String hello() { return "from C"; } }

class D implements B, C {
    // Without this override: COMPILE ERROR —
    // "class D inherits unrelated defaults for hello() from types B and C"
    @Override
    public String hello() {
        return B.super.hello();         // explicitly choose a side (or write your own)
    }
}
Q12 model answer "In the diamond, D inherits A through two paths — ambiguous methods and possibly duplicated fields. C++ fixes it with virtual inheritance so only one shared A subobject exists. Java prevents it: single inheritance for classes, and if two interface default methods collide, the compiler forces the class to override and pick explicitly with InterfaceName.super.method()."

8 · Object slicing — and why Java can't have it

The C++ setup (Q16), in words: C++ variables can hold objects by value — the variable IS the object's bytes. Assign a derived object into a base-typed variable there, and the assignment copies the object into a base-sized box: only the base part fits, and the derived-specific fields are sliced off and lost — the copy then behaves as a plain base object. Like forwarding a 5-page report through a 1-page fax machine: pages 2–5 silently gone. 

// Java — the same assignment copies an ADDRESS, never the object's bytes:
Derived d = new Derived();
Base b = d;                 // copies the REFERENCE (the address), never the object
                            // one whole Derived object on the heap; b just points at it
b.show();                   // still prints "Derived" — nothing was lost

Interview answer: "Slicing happens when a derived object is copied by value into a base-typed variable — the derived part is cut off. Java variables never hold objects by value, only references; assignment copies the reference and the full object stays intact on the heap. So object slicing is impossible in Java."

10 · Interview questions this lesson answers

Quoted from your senior's Top-25 list, with 2-line model answers.

  • Q8. "Can a constructor be virtual? Why or why not?"
    No. Virtual dispatch works through an existing object's vtable pointer, but the constructor runs before the object fully exists — and creation must name an exact class anyway. Use a factory method for polymorphic creation.
  • Q12. "What is the diamond problem in multiple inheritance and how is it solved?"
    D inherits A via both B and C — ambiguity plus duplicated state. C++: virtual inheritance shares one A. Java: single class inheritance, and clashing interface defaults are a compile error until you override and choose.
  • Q13. "How does dynamic dispatch (virtual functions) work internally?"
    Each class has a table of method addresses (vtable); each object points to its class's table. Calls look up the method slot at runtime, so the object's real type wins. Java does this for all instance methods automatically.
  • Q16. "What is object slicing?"
    Copying a derived object by value into a base variable chops off the derived part (C++). Impossible in Java: assignment copies references, never object contents.
  • Q18. "Can you explain friend class/function (in C++) and its use case?"
    A friend may access a class's private members — used for tightly coupled pairs like container + iterator. Java's substitutes: package-private access and nested classes.
  • Q24. "What is operator overloading? Give an example."
    C++: redefine operators for your own types — after writing the special method for plus, adding two Complex objects runs your code. Java omits it for readability (methods like BigInteger.add()); only the language itself overloads + for Strings.
