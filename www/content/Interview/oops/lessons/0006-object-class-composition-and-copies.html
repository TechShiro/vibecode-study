The Object Class, Composition & Copies

How objects are compared, connected to other objects, duplicated, and finally cleaned up — the life story of a Java object.

Track goal: Master OOPS for interviews — from zero. This is Lesson 6 of 8. Index

1 · The one idea

Every Java class you write secretly has a parent: java.lang.Object. Even if you never type extends, you get it for free. Object defines what every object can do: describe itself (toString), compare itself (equals, hashCode), and be cleaned up by the garbage collector.

This lesson follows an object through its life: how it's compared, how it relates to other objects (association, aggregation, composition), how it's copied (and the famous shallow-copy bug), why some objects refuse to change at all (immutability), and how it dies (garbage collection — and why Java has no destructor).

2 · The Object class: toString, equals, hashCode

Start with the question that trips everyone: when are two objects "the same"?

  • == asks: are these the same object in memory? (Same house address.)
  • equals() should ask: do these have the same value? (Same person, even if the address on file differs.)

Analogy: two photocopies of your Aadhaar card. == says "different sheets of paper" — false. A sensible equals() says "same person" — true. But Object's default equals() just does ==. If you want value comparison, you must override it. 

class Employee {
    String id;
    Employee(String id) { this.id = id; }

    @Override
    public String toString() {          // default would print Employee@1b6d3586 — useless
        return "Employee(" + id + ")";
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;               // same object? done
        if (!(o instanceof Employee)) return false;
        return id.equals(((Employee) o).id);      // same VALUE = equal
    }
    // hashCode intentionally missing... watch what breaks below
}

The contract — and how HashMap breaks without it

The rule Java asks you to keep: if two objects are equals(), they must return the same hashCode(). Why? Because HashMap and HashSet work like a library with numbered shelves:

  • hashCode() tells the map which shelf (bucket) to look at.
  • equals() then finds the exact book on that shelf.

Override equals but not hashCode, and two "equal" employees hash to different shelves. The map searches the wrong shelf and finds nothing: 

Map<Employee, Integer> salary = new HashMap<>();
salary.put(new Employee("E42"), 50000);

Integer s = salary.get(new Employee("E42"));  // a NEW but equal key
System.out.println(s);                        // null !!  wrong shelf, book never found
put(E42-a): E42-a.hashCode() → default (memory-based) → shelf 17 → stored there get(E42-b): E42-b.hashCode() → a DIFFERENT default hash → shelf 92 map searches shelf 92 → empty → returns null (equals() was never even called) fix: override hashCode() → both keys hash to the same shelf → equals() finds the entry 
@Override
public int hashCode() {
    return id.hashCode();               // built from the SAME fields equals() uses
}
// or for multiple fields:  return Objects.hash(id, name);
The rule to say out loud Override equals() and hashCode() together, always, using the same fields — or neither. Equal objects must have equal hash codes. (The reverse is not required: two unequal objects may share a hash code — that's just a "collision", and equals() sorts it out on the shelf.)

3 · How objects relate: association, aggregation, composition

Objects rarely live alone — a Team has Players, an Order has a Customer. "Has-a" comes in three strengths. The test is always: what happens to the part when the whole dies?

  • Association — "knows about." A doctor treats a patient. Both live completely independent lives.
  • Aggregation — weak has-a. A team has players. Delete the team; the players still exist and can join another team.
  • Composition — strong has-a. A house has rooms. Demolish the house; the rooms are gone. The part cannot exist without the whole.

UML draws the strength of the bond on the "whole" end of the line:

Association:   Doctor ────────────> Patient      (plain arrow: just "uses / knows")
Aggregation:   Team   ◇───────────> Player       (hollow diamond: has, but doesn't own)
Composition:   House  ◆───────────> Room         (filled diamond: owns; part dies with whole)

In Java, the difference shows up in who creates the part and who holds the only reference:

// ASSOCIATION — Doctor merely uses a Patient passed in; keeps no ownership
class Doctor {
    void treat(Patient p) { /* uses p, doesn't store or own it */ }
}

// AGGREGATION — Team receives ALREADY-EXISTING players from outside
class Team {
    private List<Player> players;
    Team(List<Player> players) {        // created elsewhere → they outlive the team
        this.players = players;
    }
}

// COMPOSITION — House builds its OWN rooms; nobody outside holds them
class House {
    private final List<Room> rooms = new ArrayList<>();
    House() {
        rooms.add(new Room("kitchen"));  // born inside the house...
        rooms.add(new Room("bedroom"));  // ...die with the house (no outside refs)
    }
}
is-a vs has-a in one breath is-a = inheritance (Circle extends Shape — a circle IS a shape). has-a = one object holds a reference to another (a car HAS an engine) — and association, aggregation, and composition are just three strengths of has-a. Interviewers love: "when would you prefer composition over inheritance?" Answer: almost always when there's no true is-a — composition is more flexible and doesn't leak the parent's internals.

4 · Shallow copy vs deep copy — the bug demo

Copying an object sounds trivial until the object contains another object. Then:

  • Shallow copy: copy the outer box, but inner references still point to the same inner objects. Like forwarding someone a shared Google Doc link — you both edit one document.
  • Deep copy: copy the outer box and fresh copies of everything inside. Like sending an attachment — each person edits their own file.

Here is the classic bug, with a Team holding a List:

class Team {
    String name;
    List<String> players;

    Team(String name, List<String> players) {
        this.name = name;
        this.players = players;
    }

    // SHALLOW copy "constructor" — looks innocent, hides a landmine
    Team shallowCopy() {
        return new Team(this.name, this.players);   // SAME list object shared!
    }

    // DEEP copy — a brand-new list with the same contents
    Team deepCopy() {
        return new Team(this.name, new ArrayList<>(this.players));
    }
}

Team a = new Team("Riders", new ArrayList<>(List.of("Virat", "Rohit")));
Team b = a.shallowCopy();

b.players.add("Dhoni");                 // I only touched the COPY...
System.out.println(a.players);          // [Virat, Rohit, Dhoni] — original corrupted!

Team c = a.deepCopy();
c.players.add("Bumrah");
System.out.println(a.players);          // [Virat, Rohit, Dhoni] — safe this time

Why did the original change? Because a.players and b.players are two variables holding one shared list. Shallow copy duplicated the reference, not the list.

Where this bites in real interviews Java's built-in clone() is shallow by default, and new ArrayList<>(old) deep-copies only one level — if the list holds mutable objects, the copies still share those inner objects. A true deep copy must copy every mutable level. Model answer: "shallow copies references; deep copies the objects behind them, recursively."

5 · Immutability — why String never changes

An immutable object can never change after construction. Like a printed train ticket: need a different seat? You get a new ticket; the old one is never edited. Every String method that "changes" it — toUpperCase(), concat() — actually returns a brand-new String.

Why did Java make String immutable? Four interview-ready reasons:

  • Safe sharing / string pool. Java stores literals in a common pool: String s1 = "hi"; String s2 = "hi"; point to one object. Only safe because nobody can modify it under the other's feet.
  • Safe HashMap keys. If a key mutated after insertion, its hashCode would change and the entry would be lost on the wrong shelf (Section 2's bug — forever).
  • Security. File paths, URLs, class names travel as Strings. If callers could mutate one after a security check, they could swap the target post-check.
  • Thread safety for free. No changes → no race conditions → share across threads with zero locks.

The recipe for your own immutable class (memorize the four moves):

final class Money {                     // 1. final class — nobody can subclass and mutate
    private final int amount;           // 2. private final fields — set once, in the constructor
    private final List<String> tags;

    Money(int amount, List<String> tags) {
        this.amount = amount;
        this.tags = new ArrayList<>(tags);   // 3. defensive copy IN — caller can't mutate later
    }

    // 4. no setters; getters return copies of anything mutable
    List<String> getTags() { return new ArrayList<>(tags); }   // defensive copy OUT
    Money add(int x) { return new Money(amount + x, tags); }    // "changes" return NEW objects
}

6 · Garbage collection — why Java has no destructor

In C++, you write a destructor — a special method (named after the class, with a tilde in front) that runs automatically when the object is destroyed, because you manage memory there: every object you create must later be freed by hand. Forget one → memory leak.

Java made a different deal. The garbage collector (GC) is like the cleanup crew in a food court: you don't wash your own tray; when you walk away and no one is using it, the crew collects it — on their schedule. The GC periodically finds objects no reference can reach and frees them automatically. 

void demo() {
    Team t = new Team("Riders", new ArrayList<>());
    t = null;               // the object is now unreachable...
}                           // ...GC will reclaim it eventually — YOU never free memory

So the honest interview answer to "constructor and destructor?":

  • Constructor: special method, same name as class, no return type, runs at new to initialize the object. Java has these, fully.
  • Destructor: Java doesn't have one, because GC owns deallocation and runs at an unpredictable time — so "run my cleanup at destruction" can't be promised. (finalize() tried, was unreliable, and is now deprecated/removed.)
  • For non-memory resources (files, sockets, DB connections) Java uses AutoCloseable + try-with-resources: cleanup at a predictable point — end of the block — instead of at destruction.
try (FileReader fr = new FileReader("data.txt")) {
    // use fr ...
}   // fr.close() runs HERE, guaranteed — even if an exception was thrown.
    // This is Java's disciplined replacement for destructor-style cleanup.
Bonus depth (Q21 preview) Where do objects live? Objects on the heap (shared, GC-managed); local variables and references on the stack (per-method, freed instantly on return). Team t = new Team(...) → t is a stack reference pointing to a heap object. GC only patrols the heap.

7 · Interview questions this lesson answers

Quoted from your senior's Top-25 list, with 2-line model answers.

  • Q3. "What is constructor and destructor?" (destructor half)
    A constructor initializes an object at new. Java has no destructor — the garbage collector frees unreachable objects automatically at an unpredictable time; for files/sockets, use AutoCloseable with try-with-resources instead.
  • Q14. "Difference between is-a and has-a relationship."
    is-a = inheritance: Circle extends Shape. has-a = one object holds a reference to another: a Car has an Engine. Prefer has-a (composition) unless the subclass truly IS a special kind of the parent.
  • Q15. "Explain composition vs aggregation."
    Both are has-a. Aggregation is weak ownership — parts arrive from outside and outlive the whole (Team–Players). Composition is strong ownership — the whole creates its parts and they die with it (House–Rooms).
  • Q17. "Difference between deep copy and shallow copy."
    Shallow copies the object but shares its inner references — mutate the copy's list, the original changes too. Deep copies every mutable level, giving fully independent objects. Java's clone() is shallow by default.
