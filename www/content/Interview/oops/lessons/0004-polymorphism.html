Polymorphism

One name, many forms: call speak() on an Animal and get a bark, a meow, or a moo — decided by the actual object, not by your variable's type.

Track goal: Master OOPS for interviews — from zero. This is Lesson 4 of 8. Index

1 · The one idea

Polymorphism ("many forms") means one method name can behave differently depending on context. Java gives you two flavours: at compile time, the same name with different parameter lists (overloading); at runtime, the same call landing on different subclass versions (overriding + dynamic dispatch). The second flavour is the superpower: code written against a parent type automatically does the right thing for every child type — even children written years later.

2 · The animal analogy

Tell a group of animals "speak!" You give one command, but the dog barks, the cat meows, the cow moos. You didn't need a separate command per animal — each one responds in its own form. That's polymorphism: same instruction, different behaviour, chosen by who receives it. 

class Animal {
    void speak() { System.out.println("..."); }
}
class Dog extends Animal {
    @Override void speak() { System.out.println("Woof!"); }
}
class Cat extends Animal {
    @Override void speak() { System.out.println("Meow!"); }
}

Animal[] zoo = { new Dog(), new Cat(), new Dog() };
for (Animal a : zoo) a.speak();   // Woof! Meow! Woof! — ONE line handles every species

Look at that loop. It only knows about Animal, yet each element speaks in its own voice. Add a Cow class tomorrow — the loop doesn't change. This is why polymorphism matters: old code can run new code without being edited.

3 · Two kinds: compile-time vs runtime

Compile-time polymorphism = method overloading. Same method name, different parameter lists, in the same class. The compiler picks the version by looking at the arguments you pass — the decision is locked in before the program ever runs. (Also called static binding or early binding.) 

class Calculator {
    int    add(int a, int b)        { return a + b; }        // version 1
    double add(double a, double b)  { return a + b; }        // version 2
    int    add(int a, int b, int c) { return a + b + c; }    // version 3
}
calc.add(2, 3);        // compiler sees (int, int) → version 1. Decided at compile time.
calc.add(2.0, 3.0);    // (double, double) → version 2
Return type alone can't overload int get() and double get() in one class won't compile. The compiler picks overloads by the parameter list only — at the call site x.get() it would have no way to choose. Small question, frequently asked.

Runtime polymorphism = method overriding (Lesson 3) + dynamic dispatch. The child redefines the parent's method with the same signature, and the JVM — at runtime — runs the version belonging to the actual object, whatever the variable's declared type says. (Also called dynamic binding or late binding.)

4 · Upcasting — Animal a = new Dog()

Storing a child object in a parent-type variable is called upcasting. It's always safe and needs no cast syntax, because every Dog is an Animal (Lesson 3's is-a test). Analogy: pinning a generic "Animal" name-badge on a dog. The badge changes what people ask of it — not what it is. 

Animal a = new Dog();    // upcast: Dog object, Animal badge

a.speak();               // OK — Animal declares speak(); the DOG's version runs: "Woof!"
// a.fetch();            // COMPILE ERROR — the Animal badge doesn't list fetch()

The two rules of an upcast reference — memorise them as a pair:

  • What you may CALL is fixed by the reference type (compile time). Only methods declared in Animal are callable through a.
  • Which version RUNS is fixed by the actual object (runtime). If Dog overrode it, Dog's version runs.
Why would anyone upcast? Generality. A method feed(Animal a) accepts every species, present and future. A List<Animal> can hold a whole zoo. Write code once against the parent; every child slots in. Upcasting is not a trick — it's the normal way polymorphic code is written.

5 · Dynamic dispatch — how the JVM picks, with vtables

So a.speak() runs Dog's version even though a is declared Animal. How does the JVM know? The classic answer: virtual method tables (vtables).

Think of a restaurant menu. Each class keeps a menu — a table listing its methods and where their code lives. A subclass starts with a photocopy of its parent's menu, then pastes its own code address over any slot it overrides and appends new items at the end. Every object carries a small hidden pointer to its class's menu. 

// what a.speak() really does, conceptually:
// 1. follow a → the object on the heap
// 2. follow the object's hidden class pointer → the ACTUAL class's vtable (Dog's)
// 3. look up the "speak" slot → Dog pasted its own address there
// 4. jump to that code → "Woof!"

Now the earlier rules explain themselves. The reference type limits which slots you may name (the compiler checks Animal's menu has a speak line at all). The actual object supplies which table is consulted — Dog's — so an overridden slot holds Dog's code. And static, private, and final methods skip the table entirely (nothing could override them), which is precisely why static methods are "hidden, not overridden" (Lesson 3).

If the interviewer says "virtual functions" That's C++ vocabulary: there, only methods marked virtual get vtable dispatch. In Java, every non-static, non-private, non-final method is virtual by default. Say that sentence — it directly answers "how does dynamic dispatch work internally" across both languages.

6 · Downcasting and instanceof

Upcasting's opposite: convincing the compiler a parent-typed reference really points to a specific child, so you can call child-only methods. This is downcasting, it needs an explicit cast, and it's the risky direction — if you're wrong about what the object is, the JVM throws ClassCastException at runtime. 

Animal a = new Dog();

Dog d = (Dog) a;         // downcast — OK, the object really is a Dog
d.fetch();               // now fetch() is callable

Animal x = new Cat();
Dog oops = (Dog) x;      // compiles!  ...but throws ClassCastException at runtime

The safe pattern: check before you cast with instanceof.

if (a instanceof Dog) {          // "is the actual object a Dog?"
    Dog d = (Dog) a;
    d.fetch();
}
// modern Java (16+) pattern matching does both in one step:
if (a instanceof Dog d) d.fetch();
Needing lots of downcasts is a design smell If your code is full of instanceof chains ("if Dog do this, if Cat do that"), you're doing the JVM's job by hand. Usually the fix is to push that behaviour into the classes as an overridden method and let dynamic dispatch choose. Mention this and you sound like someone who has designed real systems.

7 · Covariant return types — a quick nicety

An override must keep the same signature — but since Java 5, the return type may narrow to a subtype. That's called a covariant return type. It saves callers a downcast: 

class AnimalShelter {
    Animal adopt() { return new Animal(); }
}
class DogShelter extends AnimalShelter {
    @Override
    Dog adopt() { return new Dog(); }   // returns Dog, not Animal — legal since Java 5
}

Dog d = new DogShelter().adopt();       // no cast needed — the override promised a Dog

It's safe because every Dog is an Animal — anyone who expected an Animal back still gets one. Parameters get no such freedom: change a parameter type and you've created an overload, not an override (one more reason to always write @Override).

8 · Interview questions this lesson answers

From your senior's Top-25 list:

  • Q4. "Difference between compile-time polymorphism and runtime polymorphism."
    Compile-time = overloading: the compiler picks among same-named methods by parameter types, before the program runs (static binding). Runtime = overriding: the JVM picks the actual object's version at the moment of the call (dynamic binding), which needs inheritance.
  • Q5. "What is the difference between overloading and overriding?"
    Overloading: same name, different parameter lists, usually in one class, resolved at compile time; no inheritance needed. Overriding: same signature redefined in a subclass, resolved at runtime by the actual object; requires inheritance, powers polymorphic code like Animal a = new Dog(); a.speak().
  • Q13. "How does dynamic dispatch (virtual functions) work internally?"
    Each class has a vtable mapping method slots to code; a subclass copies its parent's table and overwrites the slots it overrides. Every object holds a pointer to its class's table, so a.speak() follows object → class table → slot — the actual object's version always wins. In Java all non-static, non-private, non-final methods are virtual by default; in C++ only methods marked virtual.
