Exception Handling Architecture & Anti-Patterns

Designing clean error hierarchies and avoiding catastrophic production debugging traps.

↑ Back to Course Index Advanced OOP Internals

1 · The One Idea

Exceptions in OOP are not just debugging logs — they are a formal architectural mechanism to signal that a method cannot fulfill its promised contract. Poor exception handling (swallowing errors, returning null, or catch-all logging) produces phantom production bugs where failures are masked until data corruption occurs hours later.

2 · The Java Throwable Hierarchy

Throwable
Error (OutOfMemory, StackOverflow) - Never Catch!
Exception
Checked Exception (IOException, SQLException)
RuntimeException / Unchecked (NullPointer, IllegalState)

3 · The 4 Deadly Exception Anti-Patterns

  1. Swallowing Exceptions (The Black Hole): catch (Exception e) {}. The error is completely erased from history. Never do this!
  2. Log and Re-throw: catch (Exception e) { log.error(e); throw e; }. In a 5-layer call stack, this dumps 5 duplicate error traces into your logs for a single failure!
  3. Catching Throwable or Error: Catches OutOfMemoryError or ThreadDeath, leaving the JVM in an undefined, corrupted zombie state.
  4. Losing the Cause: catch (SQLException e) { throw new ServiceException("Failed"); }. The original root cause stack trace is wiped out! Always pass e as the cause: new ServiceException("Failed", e);!

4 · Try-With-Resources & AutoCloseable

// Automatically closes file stream even if an exception strikes!
try (BufferedReader reader = new BufferedReader(new FileReader("config.json"))) {
    return reader.readLine();
} // reader.close() invoked automatically by JVM!
