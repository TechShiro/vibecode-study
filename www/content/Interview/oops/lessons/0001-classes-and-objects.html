Classes and Objects

You've been writing classes in Java for a while — now find out what a class actually is, and why the whole OOP idea exists in the first place.

Track goal: Master OOPS for interviews — from zero. This is Lesson 1 of 8. Index

1 · The one idea

A program is really just two things: data and functions that work on that data. Old-style (procedural) code keeps them in separate piles, and you must remember which function goes with which data. OOP's one big move is to glue related data and functions into a single unit — a class. Everything else in this course (encapsulation, inheritance, polymorphism) is just a consequence of that glue.

2 · Why OOP? The mess it fixes

Imagine you are writing a tiny banking app without classes. You need to track many accounts: each account has a holder name and a balance. The procedural way is parallel arrays plus loose functions: 

// PROCEDURAL STYLE — data and functions live apart
String[] names    = new String[100];
double[] balances = new double[100];

static void deposit(double[] balances, int i, double amt) {
    balances[i] += amt;              // hope 'i' is the right account!
}
static void withdraw(double[] balances, int i, double amt) {
    balances[i] -= amt;              // nothing stops balance going negative
}

This works... until it doesn't. Three problems creep in fast:

  • Data and behaviour are strangers. Nothing in the code says deposit belongs to accounts. Any function anywhere can poke balances[i] directly.
  • No protection. One typo — balances[i] = -999 — and your data is corrupt. There is no gatekeeper.
  • Scaling hurts. Add a new field (say, account type)? You must add another parallel array and update every function that touches accounts.

Now the same thing, the OOP way:

// OOP STYLE — data + behaviour glued into one unit
class Account {
    String holder;                   // data (fields) live INSIDE
    double balance;

    void deposit(double amt) {       // behaviour (methods) live with the data
        if (amt > 0) balance += amt; // the class guards its own data
    }
    void withdraw(double amt) {
        if (amt > 0 && amt <= balance) balance -= amt;
    }
}

Each Account object carries its own name and balance, and the only sensible way to change a balance is through the account's own methods. The data has a bodyguard now.

Interview one-liner "Procedural programming organises code around functions; OOP organises it around data. OOP bundles data with the functions allowed to touch it, which gives us protection (encapsulation), reuse (inheritance), and flexibility (polymorphism) — things procedural code can't give cleanly."

3 · Class vs object — blueprint vs house

A class is a blueprint. An object is a house built from that blueprint. The blueprint of a house describes rooms and doors, but you cannot live in a blueprint. You build actual houses from it — and each house has its own paint colour, its own furniture, its own address.

Same in Java. class Account is the design on paper. new Account() builds a real one in memory. You can build a hundred houses from one blueprint; you can create a hundred objects from one class, and each keeps its own copy of the fields. 

Account a1 = new Account();   // house #1
Account a2 = new Account();   // house #2 — totally separate
a1.balance = 500;
a2.balance = 900;             // changing a2 never touches a1

4 · Fields and methods

Inside a class you get two kinds of members. Fields (also called instance variables or attributes) are the data each object remembers — holder, balance. Methods are the actions an object can perform — deposit, withdraw. Together they answer the two design questions: what does this thing know? and what can this thing do?

Vocabulary sync You'll hear synonyms in interviews: fields = instance variables = attributes = properties; methods = member functions = behaviour. Also, "instance" is just a fancy word for object — "a1 is an instance of Account" means a1 is an object built from that class.

5 · Constructors — the setup crew

A constructor is a special method that runs once, automatically, at the moment an object is born with new. Its job: put the new object into a valid starting state. Analogy: when you check into a hotel room, housekeeping has already prepared it — bed made, towels ready. The constructor is housekeeping for objects.

Rules that make it "special": its name is exactly the class name, and it has no return type (not even void).

class Account {
    String holder;
    double balance;

    // 1) DEFAULT-STYLE (no-argument) constructor
    Account() {
        this.holder = "unknown";
        this.balance = 0;
    }

    // 2) PARAMETERIZED constructor — caller supplies starting values
    Account(String holder, double balance) {
        this.holder = holder;
        this.balance = balance;
    }

    // 3) COPY-CONSTRUCTOR idea — build a new object from an existing one
    Account(Account other) {
        this.holder = other.holder;
        this.balance = other.balance;
    }
}

Account a = new Account();                  // runs #1
Account b = new Account("Krish", 1000);     // runs #2
Account c = new Account(b);                 // runs #3 — a fresh clone of b

Notice #1, #2 and #3 have the same name but different parameter lists. That's constructor overloading — several setup recipes, and Java picks the one matching your arguments. (This is your first taste of overloading; Lesson 4 makes it a big deal.)

The disappearing default constructor If you write no constructor at all, Java quietly gifts you an empty no-arg one. But the moment you write any constructor yourself, that gift is withdrawn — new Account() stops compiling unless you also write the no-arg version. Classic interview gotcha.
"...and destructor?" C++ has destructors — code that runs when an object dies, to free memory. Java has no destructors, because the Garbage Collector automatically reclaims objects nobody refers to anymore. If asked: mention C++ destructors, then say Java replaces them with GC.

6 · The this keyword

Inside a method, this means "the object I was called on." Analogy: in a classroom of students, when one student says "my bag," everyone knows they mean their own bag — not their neighbour's. this is an object saying "my."

Its most common job is breaking a name tie between a parameter and a field:

Account(String holder, double balance) {
    this.holder = holder;    // this.holder = the FIELD; holder = the PARAMETER
    this.balance = balance;  // without 'this.' you'd assign the parameter to itself
}

Bonus use: this(...) as the first line of a constructor calls a sibling constructor — handy to avoid repeating setup code across overloaded constructors.

7 · new and memory — stack vs heap

Where does an object actually live? Java splits memory into two areas. The stack is a small, fast scratchpad — each method call gets a frame holding its local variables, and the frame vanishes when the method returns. The heap is a big open warehouse where every object created by new is stored, and it outlives any single method call.

The key sentence: objects live on the heap; your variable holds only a reference — a small "address slip" on the stack pointing into the warehouse. 

Account a1 = new Account("Krish", 500);
Account a2 = a1;          // copies the ADDRESS SLIP, not the object!
a2.balance = 999;
System.out.println(a1.balance);  // prints 999 — both slips point to ONE object

Quick contrast to keep in your head:

StackHeap
Local variables, method parameters, referencesAll objects and arrays created with new
Freed automatically when the method returnsFreed by the Garbage Collector when no reference points to it
Small, fast, per-threadBig, shared by all threads
Overflows on deep recursion (StackOverflowError)Fills with too many objects (OutOfMemoryError)
"Primitives on stack, objects on heap" — say it carefully A primitive local variable (int x = 5;) sits on the stack. But a primitive field inside an object (like balance) lives on the heap, inside its object. Location depends on where the variable is declared, not just its type.

8 · Static vs instance members

An instance member belongs to each object separately — every account has its own balance. A static member belongs to the class itself — one shared copy, no matter how many objects exist. Analogy: in an apartment building, every flat has its own kitchen (instance), but there is one shared lift for the whole building (static). 

class Account {
    double balance;                    // instance: one per object
    static int totalAccounts = 0;      // static: ONE copy for the whole class

    Account() {
        totalAccounts++;               // every birth bumps the shared counter
    }

    double getBalance() { return balance; }        // instance method: needs an object
    static int getTotal() { return totalAccounts; } // static method: no object needed
}

new Account(); new Account(); new Account();
System.out.println(Account.getTotal());  // 3 — called on the CLASS, not an object

Why is main static? Because when the program starts, no objects exist yet. The JVM needs an entry point it can call on the class directly, without constructing anything first. Great answer to have ready — it shows you understand static deeply, not just as a keyword you copy.

9 · Interview questions this lesson answers

From your senior's Top-25 list:

  • Q25. "Why do we need OOPS when we already have procedural programming?"
    Procedural code separates data from the functions that use it, so nothing protects the data and large codebases become tangled. OOP bundles data with its behaviour (classes), enabling protection, reuse, and modelling real-world entities — which scales far better.
  • Q2. "Difference between class and object."
    A class is a blueprint written once in code; an object is a runtime instance built from it with new. One class, many objects — each with its own copy of the fields.
  • Q3. "What is constructor and destructor?" (constructor half)
    A constructor is a special method (same name as the class, no return type) that runs automatically on new to initialise the object; it can be overloaded. Java has no destructor — the Garbage Collector frees unreachable objects instead.
  • Q21. "How are objects stored in memory (stack vs heap)?"
    All objects live on the heap; variables hold references, and local variables/references live in stack frames. Copying a reference copies the address, not the object; unreferenced heap objects are garbage-collected.
  • Q19. "What is the difference between static methods and instance methods?"
    Instance methods belong to an object, are called on it, and can use this and instance fields. Static methods belong to the class, are called without any object, and can only touch static state directly.
