2 · SOLID — five sentences, five tiny examples

S — Single Responsibility: one class, one job

A class should have only one reason to change. A Swiss-army knife breaks in three ways; a kitchen knife in one.

// BAD: three unrelated jobs — any change to printing, saving, or math touches this class
class Report { double calculate() {...} void printPDF() {...} void saveToDB() {...} }

// GOOD: one job each — a DB change now touches only ReportRepository
class Report          { double calculate() {...} }
class ReportPrinter   { void printPDF(Report r) {...} }
class ReportRepository{ void save(Report r) {...} }

O — Open/Closed: open for extension, closed for modification

Add new behavior by adding new classes, not by editing tested old code. Like a power strip: plug in a new device; don't rewire the wall.

// BAD: every new shape means editing (and re-risking) this if-chain
double area(Object s) {
    if (s instanceof Circle) {...} else if (s instanceof Square) {...}  // grows forever
}

// GOOD: new shape = new class. area() never changes again.
interface Shape { double area(); }
class Circle implements Shape { public double area() {...} }
class Square implements Shape { public double area() {...} }   // added, nothing modified

L — Liskov Substitution: a child must work anywhere its parent works

If code expects a Bird, handing it any subclass must not break it. A substitute teacher must actually teach the class, not cancel it.

// BAD: Penguin IS-A Bird by keyword, but breaks the parent's promise
class Bird    { void fly() {...} }
class Penguin extends Bird {
    @Override void fly() { throw new UnsupportedOperationException(); } // callers crash
}

// GOOD: model the promise correctly — only FlyingBird promises fly()
class Bird {}
class FlyingBird extends Bird { void fly() {...} }
class Penguin    extends Bird { void swim() {...} }   // no broken promise anywhere

I — Interface Segregation: many small interfaces beat one fat one

Don't force a class to implement methods it can't use. Order à la carte; don't make everyone buy the full thali.

// BAD: Robot is forced to fake eat()
interface Worker { void work(); void eat(); }
class Robot implements Worker { public void work() {...} public void eat() { /* ??? */ } }

// GOOD: split by capability; implement only what's true
interface Workable { void work(); }
interface Eatable  { void eat(); }
class Human implements Workable, Eatable {...}
class Robot implements Workable {...}                  // no fake methods

D — Dependency Inversion: depend on abstractions, not concrete classes

High-level code should talk to an interface, and receive the concrete thing from outside. Appliances plug into a socket; they're not hardwired into the wall.

// BAD: welded to MySQL — switching DBs or testing means editing this class
class UserService { private MySQLDatabase db = new MySQLDatabase(); }

// GOOD: depends on the interface; any Database can be injected (real, Postgres, fake-for-tests)
interface Database { void save(String data); }
class UserService {
    private final Database db;
    UserService(Database db) { this.db = db; }         // dependency injection
}
Q20 in one breath "SOLID: Single responsibility — one reason to change. Open/closed — extend, don't modify. Liskov — subclasses must honor the parent's promises. Interface segregation — small, focused interfaces. Dependency inversion — depend on abstractions and inject the concretes. Together they keep code changeable without ripple effects."

4 · Rapid-fire: all 25 questions

Compact model answers — 2 to 4 lines each, exactly the density an interviewer wants first. Deep dives live in the lessons noted.

Basic Concepts (Q1–Q10)

  • Q1. "What are the main principles of OOPS?" — Encapsulation: bundle data + methods, guard with private. Abstraction: expose only what's needed. Inheritance: child reuses and extends a parent. Polymorphism: one call, many behaviors — overloading (compile time), overriding (runtime).
  • Q2. "Difference between class and object." — Class = blueprint (fields and methods); object = a concrete instance with real values. One class, many objects: Car vs new Car().
  • Q3. "What is constructor and destructor?" — Constructor: class-named, no return type, runs at new to initialize state. Destructor: C++ cleanup at destruction; Java has none — GC frees unreachable objects, try-with-resources handles files/sockets. (Lesson 6.)
  • Q4. "Difference between compile-time polymorphism and runtime polymorphism." — Compile time = overloading: same name, different parameter lists, resolved by the compiler. Runtime = overriding: the object's real type picks the version via dynamic dispatch. (Lesson 4.)
  • Q5. "What is the difference between overloading and overriding?" — Overloading: same class, same name, different signatures — a convenience, bound at compile time. Overriding: child class, same signature, new behavior — bound at runtime; the heart of polymorphism.
  • Q6. "Can you explain abstraction vs encapsulation with an example?" — Abstraction hides complexity: car.drive() hides ignition and injection. Encapsulation hides data: private int fuel changes only through the class's own methods. "What to show" vs "how to guard". (Lesson 5.)
  • Q7. "What is an interface and how is it different from an abstract class?" — Interface: pure contract, no state or constructors, implement many. Abstract class: fields, constructors, mixed methods, extend one. Shared code among relatives → abstract class; a capability → interface. (Lesson 5.)
  • Q8. "Can a constructor be virtual? Why or why not?" — No. Virtual dispatch needs an existing object's vtable pointer; the constructor runs before the object exists, and creation must name an exact class. Use factory methods instead. (Lesson 7.)
  • Q9. "What is method hiding vs method overriding?" — Overriding: instance methods, dispatched by runtime type. Hiding: static methods with the same signature — resolved by the reference type at compile time, no polymorphism.
  • Q10. "What are access specifiers (public, private, protected)?" — private: same class. Package-private (Java default): same package. protected: package + subclasses. public: everywhere. C++ contrast: class members default to private; C++ protected has no package part.

Inheritance & Polymorphism (Q11–Q15)

  • Q11. "What are the different types of inheritance?" — Single (A→B), multilevel (A→B→C), hierarchical (A→B, A→C), multiple (B,C→D), hybrid (a mix). Java supports the first three with classes; multiple/hybrid only via interfaces — dodging the diamond problem.
  • Q12. "What is the diamond problem in multiple inheritance and how is it solved?" — D inherits A via both B and C: ambiguity, duplicated state. C++: virtual inheritance shares one A. Java: single class inheritance; clashing interface defaults are a compile error until you override and pick via B.super.method(). (Lesson 7.)
  • Q13. "How does dynamic dispatch (virtual functions) work internally?" — Each class holds a vtable of method addresses; each object points to its class's table. A call looks up the method slot at runtime, so the real type wins. Java does this for all instance methods. (Lesson 7.)
  • Q14. "Difference between is-a and has-a relationship." — is-a = inheritance (Circle extends Shape); has-a = holding a reference (Car has an Engine). Prefer has-a/composition unless the subtype genuinely IS the parent and honors its promises (Liskov). (Lesson 6.)
  • Q15. "Explain composition vs aggregation." — Both has-a; the test is lifetime. Aggregation: parts arrive from outside and outlive the whole (Team–Players, hollow diamond). Composition: the whole creates its parts and they die with it (House–Rooms, filled diamond). (Lesson 6.)

Advanced Concepts (Q16–Q20)

  • Q16. "What is object slicing?" — In C++, copying a derived object by value into a base-typed variable chops off the derived part. Impossible in Java: assignment copies a reference, and the whole object survives on the heap. (Lesson 7.)
  • Q17. "Difference between deep copy and shallow copy." — Shallow: copy the object, share its inner references — mutate the copy's list and the original changes. Deep: copy every mutable level for full independence. Java's clone() is shallow by default. (Lesson 6.)
  • Q18. "Can you explain friend class/function (in C++) and its use case?" — A friend can access another class's privates; classic use: container + iterator. Java dropped it — use package-private access or nested classes (how JDK iterators work). (Lesson 7.)
  • Q19. "What is the difference between static methods and instance methods?" — Static: class-owned, called on the class name, no this, not overridable (only hidden). Instance: object-owned, has this, dynamically dispatched.
  • Q20. "What is the SOLID principle in OOPS?" — Five principles that keep code loosely coupled and extension-friendly (Section 2). Give the one-breath answer, then a bad→good example — the if-chain vs polymorphism one lands best.

Memory & Design (Q21–Q25)

  • Q21. "How are objects stored in memory (stack vs heap)?" — Objects live on the heap (shared, GC-managed); locals and references live on the stack (per call, freed on return). Team t = new Team(): t on the stack points to a Team on the heap.
  • Q22. "Difference between virtual function and pure virtual function." — Virtual: has a body, may be overridden, runtime dispatched. Pure virtual: declared with no body at all, must be overridden, makes the class abstract. Java: instance methods are virtual by default; pure virtual = abstract method. (Lesson 5.)
  • Q23. "What is abstract factory design pattern (or any common OOPS design pattern)?" — Safest pick: Factory Method — a creator returns objects via a common interface (Shape s = ShapeFactory.create("circle")), so callers never new concretes. Also name Singleton and Strategy. Deep dive: LLD track.
  • Q24. "What is operator overloading? Give an example." — C++: redefine operators for your own types, e.g. teach plus to add two Complex objects so the plus sign runs your code. Java omitted it for readability; write a.add(b) (BigInteger style). Only the language overloads + for Strings. (Lesson 7.)
  • Q25. "Why do we need OOPS when we already have procedural programming?" — Procedural code shares mutable data among free functions; at scale, anything can corrupt anything. OOPS bundles data with its guardian methods, models the domain directly, and allows extension without modifying tested code. Scale, safety, change-friendliness.
