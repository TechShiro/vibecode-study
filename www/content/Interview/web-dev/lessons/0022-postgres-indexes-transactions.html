PostgreSQL: Indexes, Transactions & JSONB

Lesson 21 taught you to talk to Postgres — this one teaches you how Postgres thinks: why some queries are 1000× faster than others, how money never vanishes mid-transfer, and the one security bug every interviewer asks about.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 22 of 24. Index

1 · How a query actually runs

When you hit Enter on a SELECT, Postgres doesn't just "look at the table". Your SQL goes through a pipeline:

  • Parser — checks the syntax and turns your text into a tree. (Like javac parsing your Java source.)
  • Planner / optimizer — the interesting part. There are usually many ways to execute the same query: scan the whole table, use an index, join in one order or another. The planner estimates the cost of each strategy using statistics it keeps about your data (row counts, value distributions) and picks the cheapest plan.
  • Executor — actually runs the chosen plan and streams rows back to you.

This is the key mental shift of this lesson: SQL says what you want, the planner decides how to get it. Your job as a developer is to give the planner good options — and the main way you do that is with indexes.

Interview one-liner "SQL is declarative — I describe the result, and the query planner picks an execution strategy based on table statistics. Indexes don't change what a query returns; they change what strategies are available, which can turn a full table scan into a direct lookup."

2 · Indexes — the phone book

Imagine a phone book with 1,000,000 entries in random order, and you're asked to find "Krish Sharma". Your only option is to read every single entry — on average 500,000 checks. That's a sequential scan, and it's exactly what Postgres does when you filter on a column with no index.

A real phone book is sorted by name, so you can flip to the middle, see you're too far, flip again — and land on the entry in about 20 steps instead of 500,000. That's binary search, and an index gives Postgres the same power: a separate, sorted structure that maps column values to row locations.

The default index type is a B-tree — a balanced, wide tree kept sorted at all times. Lookups, range scans (BETWEEN, <, >) and sorted reads are all O(log n). With a branching factor in the hundreds, a B-tree over millions of rows is only 3–4 levels deep: a handful of page reads instead of scanning everything.

Java parallel A table with no index is an ArrayList you search with a for-loop — O(n). A B-tree index is like a TreeMap kept alongside it — O(log n) lookups and sorted iteration, which is why one index can serve WHERE, range filters, and ORDER BY. (Why not a HashMap? Hash indexes exist in Postgres, but they can only answer = — no ranges, no ordering — so B-tree is the default.)

Creating one is a single statement. Using the users/posts schema from Lesson 21:

-- posts(id, user_id, title, body, created_at) from Lesson 21
CREATE INDEX idx_posts_user_id ON posts (user_id);

-- naming convention: idx_<table>_<columns> — future-you will thank you
DROP INDEX idx_posts_user_id;   -- removing one is just as easy

When does an index help? When a column appears in:

  • WHERE — WHERE user_id = 7 becomes a direct lookup instead of a scan.
  • JOIN ... ON — join columns are looked up once per row of the other table; without an index that's a scan per row. Foreign key columns are the #1 thing to index — Postgres does NOT index them automatically.
  • ORDER BY — the index is already sorted, so Postgres can skip the sort step entirely (huge for ORDER BY created_at DESC LIMIT 10 feeds).

Why not index everything, then? Because indexes are not free:

  • Writes get slower. Every INSERT/UPDATE/DELETE must also update every index on the table. Five indexes ≈ six writes per insert.
  • Disk space. Each index is a full extra copy of the indexed columns plus tree overhead.
  • The planner may ignore it anyway. If a filter matches most of the table (say WHERE is_active = true and 95% of rows are active), a sequential scan is genuinely cheaper — one pass beats a million tree lookups.
Rule of thumb Index the columns you search, join, and sort by — in practice: every foreign key, plus whatever your WHERE clauses actually filter on. Don't index tiny tables, rarely-queried columns, or columns where almost every row matches the filter.

3 · Composite indexes, unique indexes, and the freebies

An index can cover multiple columns. Order matters enormously: 

CREATE INDEX idx_posts_user_created ON posts (user_id, created_at);

Think of it as a phone book sorted by last name, then first name. You can find all "Sharma"s fast (first column alone), and all "Sharma, Krish"s fast (both columns). But finding everyone named "Krish" regardless of surname? Useless — you're back to scanning, because first names are scattered across the whole book.

That's the leftmost-prefix rule: a composite index on (a, b) accelerates queries filtering on a, or on a AND b — but not on b alone. So WHERE user_id = 7 AND created_at > '2026-01-01' flies, while WHERE created_at > '2026-01-01' by itself ignores this index and needs its own.

A unique index is an index that also enforces a rule — no two rows may share a value:

CREATE UNIQUE INDEX idx_users_email ON users (email);
-- equivalent effect to the UNIQUE constraint you wrote in Lesson 21:
-- ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE (email);
The freebies Postgres automatically creates a unique index for every PRIMARY KEY and every UNIQUE constraint — that's literally how it enforces them (to reject a duplicate fast, it needs a fast lookup). So WHERE id = 5 is always indexed for free. What is never automatic: indexes on foreign key columns. Add those yourself.

4 · EXPLAIN — watching the planner think

Don't guess whether an index is used — ask. EXPLAIN shows the plan without running the query; EXPLAIN ANALYZE runs it and shows real timings. Let's see the before/after with enough rows to matter (generate_series is Postgres's built-in row factory — great for experiments): 

-- seed a play table with 1 million rows
CREATE TABLE bench (
  id    integer PRIMARY KEY,
  label text NOT NULL
);
INSERT INTO bench (id, label)
SELECT n, 'row-' || n FROM generate_series(1, 1000000) AS n;

-- BEFORE: filter on the un-indexed column
EXPLAIN ANALYZE SELECT * FROM bench WHERE label = 'row-777777';
-- output (abridged) — read the first word of the node:
Seq Scan on bench  (cost=0.00..17906.00 rows=1 width=14)
                   (actual time=41.3..78.9 ms rows=1)
  Filter: (label = 'row-777777')
  Rows Removed by Filter: 999999    -- read a million rows to keep ONE
-- AFTER: add the index, run the same query
CREATE INDEX idx_bench_label ON bench (label);
EXPLAIN ANALYZE SELECT * FROM bench WHERE label = 'row-777777';

Index Scan using idx_bench_label on bench
                   (cost=0.42..8.44 rows=1 width=14)
                   (actual time=0.031..0.033 ms rows=1)
  Index Cond: (label = 'row-777777')

78 ms → 0.03 ms, roughly 2000× faster, from one line of SQL. Reading plans in depth is a career-long skill, but for now you need exactly two words:

  • Seq Scan — "I read the entire table." Fine for small tables or match-everything filters; a red flag on big tables with selective filters.
  • Index Scan — "I walked the B-tree straight to the rows." What you want for selective lookups. (Cousins you'll meet: Index Only Scan — even better, answer came from the index alone; Bitmap Index Scan — index used in bulk mode for medium-sized result sets.)
Gotcha EXPLAIN ANALYZE actually executes the statement. Harmless for SELECT — but EXPLAIN ANALYZE DELETE FROM users really deletes. Wrap risky ones in a transaction: BEGIN; EXPLAIN ANALYZE ...; ROLLBACK; — which is a perfect segue.

5 · Transactions — the bank transfer

You're moving ₹500 from account A to account B. That's two updates: 

UPDATE accounts SET balance = balance - 500 WHERE id = 'A';
-- ⚡ power cut / server crash / app exception happens HERE
UPDATE accounts SET balance = balance + 500 WHERE id = 'B';

If the world stops between the two statements, ₹500 has vanished: A was debited, B was never credited. No amount of careful application code fixes this — the crash can always land between any two statements. The fix has to come from the database: a transaction groups statements into a single all-or-nothing unit. 

BEGIN;                                                    -- start the unit
UPDATE accounts SET balance = balance - 500 WHERE id = 'A';
UPDATE accounts SET balance = balance + 500 WHERE id = 'B';
COMMIT;                                                   -- make BOTH permanent, atomically

-- if anything goes wrong before COMMIT (error, crash, or you change your mind):
ROLLBACK;                                                 -- undo everything since BEGIN

If the server crashes mid-transaction, Postgres rolls the whole thing back on restart. The outside world only ever sees "transfer fully happened" or "transfer never happened" — never the half-done state.

The guarantees transactions give you are the interview staple ACID. Learn these four properly — this is a top-5 backend interview question:

  • A — Atomicity. All statements in the transaction apply, or none do. No partial transfers. (COMMIT/ROLLBACK is the mechanism.)
  • C — Consistency. A transaction moves the database from one valid state to another — all constraints (CHECK balance >= 0, foreign keys, uniqueness) hold before and after. If a statement would break a rule, the transaction fails rather than corrupting data.
  • I — Isolation. Concurrent transactions don't trample each other; each behaves as if it had the database (mostly) to itself. "Mostly" is tunable — that's Section 6.
  • D — Durability. Once COMMIT returns, the data survives crashes and power loss — Postgres writes to a write-ahead log (WAL) on disk before acknowledging the commit.
Java parallel Isolation is the database's answer to the same problem synchronized solves in Java: interleaved access to shared state. But a JVM lock protects one object inside one process; a transaction protects arbitrary rows across many clients, survives crashes, and lets you tune how much interleaving is acceptable instead of serializing everything.
Gotcha Every single statement you've ever run in psql was already a transaction — Postgres auto-wraps each standalone statement in its own tiny BEGIN/COMMIT. Explicit BEGIN is only needed to make multiple statements atomic together.

6 · Concurrency anomalies and isolation levels

Perfect isolation is easy — run transactions one at a time. It's also uselessly slow. So databases allow controlled interleaving, and the SQL standard names the three weird things ("anomalies") that interleaving can cause:

  • Dirty read — transaction B reads data that A has written but not committed. If A rolls back, B acted on data that never existed.
  • Non-repeatable read — B reads a row, A commits an update to it, B reads the same row again and gets a different value within one transaction.
  • Phantom read — B runs SELECT COUNT(*) WHERE ..., A commits an INSERT matching that filter, B re-runs the query and new "phantom" rows have appeared.

Isolation levels are how much protection you buy, trading strictness for concurrency:

Isolation levelDirty readNon-repeatable readPhantom readNotes
READ UNCOMMITTEDprevented*possiblepossible*In Postgres this level silently behaves as READ COMMITTED — dirty reads are never possible in Postgres
READ COMMITTED (Postgres default)preventedpossiblepossibleEach statement sees only committed data as of its start
REPEATABLE READpreventedpreventedprevented†Whole transaction sees one frozen snapshot; †Postgres's MVCC snapshot also stops phantoms here, stricter than the standard requires
SERIALIZABLEpreventedpreventedpreventedResult is as if transactions ran one-by-one; conflicting transactions abort with a serialization error — retry them
 
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- per-transaction opt-in
SELECT balance FROM accounts WHERE id = 'A';       -- 1000
-- ...another session commits an update to A here...
SELECT balance FROM accounts WHERE id = 'A';       -- STILL 1000: frozen snapshot
COMMIT;
Interview one-liner "Postgres defaults to READ COMMITTED: no dirty reads, but values can change between statements. For read-modify-write logic like inventory or balances I either lock rows with SELECT ... FOR UPDATE or raise the level to SERIALIZABLE and retry on conflict. Postgres uses MVCC — readers get snapshots instead of blocking writers — so even its stricter levels stay fast."

7 · Locks — a glance

MVCC means readers never block writers and writers never block readers. But two writers touching the same row must queue: the second UPDATE waits until the first transaction commits or rolls back. That's an automatic row lock.

Sometimes you want to lock before writing — the classic read-check-write race: 

BEGIN;
-- lock the row NOW so nobody else can change it under us
SELECT balance FROM accounts WHERE id = 'A' FOR UPDATE;
-- app code checks: balance >= 500? then:
UPDATE accounts SET balance = balance - 500 WHERE id = 'A';
COMMIT;   -- lock released

Without FOR UPDATE, two concurrent withdrawals could both read balance = 600, both decide "600 ≥ 500, go ahead", and drive the account negative. With it, the second transaction waits at the SELECT until the first commits, then sees the updated balance of 100 and refuses.

The classic failure mode: transaction 1 locks row A then wants B; transaction 2 locks B then wants A. Both wait forever — a deadlock, exactly like two Java threads acquiring locks in opposite order. Postgres detects the cycle after a moment, kills one transaction with a deadlock error, and lets the other proceed. Prevention is the same discipline as in Java: always acquire locks in a consistent order (e.g., lock accounts by ascending id).

8 · Views and materialized views

A view is a saved query that behaves like a read-only table — a named lens over your data: 

CREATE VIEW post_stats AS
SELECT u.username,
       COUNT(p.id)        AS post_count,
       MAX(p.created_at)  AS last_post_at
FROM users u
LEFT JOIN posts p ON p.user_id = u.id
GROUP BY u.username;

SELECT * FROM post_stats WHERE post_count > 10;   -- like a table!

Views store no data — each query against the view re-runs the underlying SQL. They're for DRY (write the gnarly join once), for clean interfaces, and for hiding columns (grant an analyst access to a view without the password_hash column).

A materialized view does store the result — a cached snapshot you refresh on your schedule: 

CREATE MATERIALIZED VIEW daily_signups AS
SELECT created_at::date AS day, COUNT(*) FROM users GROUP BY 1;

REFRESH MATERIALIZED VIEW daily_signups;   -- re-run + re-store (e.g. nightly cron)

Perfect for expensive dashboard aggregates where "data as of last night" is acceptable. The trade: reads are instant, but the data is stale until the next refresh.

9 · JSONB — a document store inside your tables

Sometimes part of your data genuinely has no fixed shape. User preferences, third-party API payloads, per-product attributes (a phone has RAM, a shirt has size). Modeling every possible key as a column is madness. Postgres's answer: a jsonb column — binary-stored, indexable JSON. 

CREATE TABLE events (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind    text NOT NULL,
  payload jsonb NOT NULL DEFAULT '{}'
);

INSERT INTO events (kind, payload) VALUES
('signup', '{"plan": "free", "referrer": "google", "utm": {"campaign": "july"}}'),
('signup', '{"plan": "pro",  "referrer": "friend"}');

Two extraction operators, and the difference bites everyone once:

SELECT payload -> 'plan'  FROM events;   -- "pro"  → returns JSONB (note the quotes)
SELECT payload ->> 'plan' FROM events;   -- pro    → returns TEXT — use for comparisons

-- filter on a JSON field (->> gives text, so compare with text)
SELECT * FROM events WHERE payload ->> 'plan' = 'pro';

-- drill into nested objects: -> to navigate, ->> for the last hop
SELECT payload -> 'utm' ->> 'campaign' FROM events;      -- july

-- @> containment: "does the JSON contain this sub-document?"
SELECT * FROM events WHERE payload @> '{"plan": "pro"}';

B-trees can't index arbitrary keys inside a document — for that Postgres has GIN (Generalized Inverted Index), which indexes every key/value inside the JSON, making @> queries fast: 

CREATE INDEX idx_events_payload ON events USING GIN (payload);
Gotcha JSONB is a tool, not an escape hatch from schema design. If a field is present on every row, has a known type, needs a foreign key, or is central to your queries — make it a real column. Real columns get types, constraints, and better statistics for the planner. Reach for JSONB only for genuinely variable, schema-less parts of a row. "We put everything in one JSONB column" is a NoSQL cosplay that loses the R in relational.

10 · UUID vs serial primary keys

Lesson 21 used auto-incrementing integer keys. The alternative is a uuid — a random 128-bit identifier:

CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),   -- built-in since PG 13
  total numeric(10,2) NOT NULL
);
serial / identity (int)uuid
Size4–8 bytes — smaller table & indexes16 bytes
GenerationDatabase counter — needs a DB round-tripAnywhere — app, client, offline — no coordination
Guessability/users/42 leaks "you have ~42 users"; adjacent ids are enumerableUnguessable — safe to expose in URLs

Multi-service / shardingCounters collide across databasesGlobally unique by construction

Sensible default: integers for internal tables, UUIDs for anything exposed publicly (or wherever ids must be generated outside the database). Both are common; being able to argue the tradeoffs is what interviews want.

11 · Talking to Postgres from Node — and the injection attack

Time to connect the Express skills from Lessons 18–19 to a real database. The standard driver is the pg package (a.k.a. node-postgres): 

npm install pg
// db.js
const { Pool } = require('pg');

const pool = new Pool({
  host: 'localhost',
  port: 5432,
  database: 'blog',
  user: 'postgres',
  password: process.env.PGPASSWORD,   // never hardcode — env vars (Lesson 19)
  max: 10,                            // at most 10 open connections
});

module.exports = pool;

Why a Pool? Opening a Postgres connection is expensive — a TCP handshake, authentication, and a dedicated server process on the Postgres side. Doing that per request would crush your throughput, and Postgres caps total connections (default 100). A pool opens a handful of connections once and lends them out per query, like a library lending books instead of printing a new copy per reader. (Java parallel: exactly what HikariCP does for JDBC.) 

// routes/posts.js — async/await from Lesson 7, Express from Lesson 18
const pool = require('../db');

app.get('/api/posts/:id', async (req, res, next) => {
  try {
    const { rows } = await pool.query(
      'SELECT id, title, body FROM posts WHERE id = $1',   // $1 = placeholder
      [req.params.id]                                      // values array
    );
    if (rows.length === 0) return res.status(404).json({ error: 'Not found' });
    res.json(rows[0]);
  } catch (err) { next(err); }
});

Those $1, $2, ... placeholders are not a style choice. To see why, look at the version every beginner writes first — and which interviewers will show you and ask "what's wrong here?": 

// ❌ VULNERABLE — user input concatenated straight into SQL
app.get('/api/users', async (req, res) => {
  const sql = "SELECT id, username FROM users WHERE username = '"
            + req.query.name + "'";
  const { rows } = await pool.query(sql);
  res.json(rows);
});

Looks fine with ?name=krish. Now watch an attacker choose the input:

-- attacker requests:  /api/users?name=' OR '1'='1
-- your string-glue produces:
SELECT id, username FROM users WHERE username = '' OR '1'='1'
-- '1'='1' is always true → WHERE matches EVERY row → entire users table leaked

-- attacker requests:  /api/users?name='; DROP TABLE users; --
SELECT id, username FROM users WHERE username = ''; DROP TABLE users; --'
-- second statement DROPS YOUR TABLE; -- comments out the trailing quote

That's SQL injection — for over a decade the #1 vulnerability class on the web, and it has destroyed real companies. The root cause: the database can't tell where your code ends and the attacker's data begins, because you mixed them into one string.

Parameterized queries kill it completely. With $1, the SQL text and the values travel to Postgres separately. Postgres compiles the query first, then slots values in as pure data — a value can never be reinterpreted as SQL, no matter what it contains: 

// ✅ SAFE — the attack string is just a weird username that matches nothing
const { rows } = await pool.query(
  'SELECT id, username FROM users WHERE username = $1',
  [req.query.name]     // even "'; DROP TABLE users; --" is inert data here
);
Interview one-liner "SQL injection happens when untrusted input is concatenated into query text, letting data be executed as SQL. The fix is parameterized queries — the query shape and the values are sent separately, so input can never change the query's structure. Escaping by hand is fragile; parameterization is the correct fix, and ORMs use it under the hood."

And the bank transfer from Section 5, done properly from Node — one dedicated connection for the whole transaction:

async function transfer(fromId, toId, amount) {
  const client = await pool.connect();      // checkout ONE connection —
  try {                                     // a transaction must stay on it
    await client.query('BEGIN');
    await client.query(
      'UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromId]);
    await client.query(
      'UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId]);
    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK');         // any failure → undo both
    throw err;
  } finally {
    client.release();                       // ALWAYS return it to the pool
  }
}

12 · Migrations — schema changes as code

Your schema will change: new columns, new tables, new indexes. The amateur move is running ALTER TABLE by hand in a psql prompt on the production server. Why that fails:

  • Your laptop's DB, your teammate's DB, and production silently drift apart — "works on my machine" but the deploy explodes.
  • There's no history — nobody knows what changed, when, or why, and there's no way to recreate the schema from scratch.
  • Hand-typed DDL on prod at 11pm is how tables get dropped.

The fix is migrations: every schema change is a small, numbered SQL file committed to git, and a tool applies — in order — exactly the ones a given database hasn't seen yet (tracked in a bookkeeping table): 

migrations/
  0001_create_users.sql        -- CREATE TABLE users (...);
  0002_create_posts.sql        -- CREATE TABLE posts (...);
  0003_add_posts_user_idx.sql  -- CREATE INDEX idx_posts_user_id ...;
  0004_users_add_bio.sql       -- ALTER TABLE users ADD COLUMN bio text;

Schema history becomes reviewable in pull requests, reproducible on any machine, and automatable in deploys — the same philosophy as git itself: changes as versioned, ordered diffs. You won't write a migration runner by hand: in Lesson 23, Drizzle will generate these SQL files from a TypeScript schema and run them for you — now you'll know exactly what it's doing and why.

13 · Interview questions this lesson answers

  • "What is an index and when would you add one?"
    A separate sorted structure (B-tree by default) mapping column values to rows, turning O(n) scans into O(log n) lookups. Add on columns used in WHERE, JOIN (especially foreign keys — not auto-indexed), and ORDER BY. Cost: slower writes and extra disk, so don't index blindly. Verify with EXPLAIN ANALYZE: Seq Scan → Index Scan.
  • "Explain ACID."
    Atomicity — all-or-nothing statement groups via COMMIT/ROLLBACK. Consistency — constraints hold before and after every transaction. Isolation — concurrent transactions don't see each other's intermediate states, tunable by isolation level. Durability — committed data survives crashes via the write-ahead log.
  • "What isolation levels exist, and what's the Postgres default?"
    READ COMMITTED (default: no dirty reads, but non-repeatable and phantom reads possible), REPEATABLE READ (frozen snapshot — in Postgres this also prevents phantoms), SERIALIZABLE (as-if-sequential; conflicting transactions abort and retry). Postgres never allows dirty reads — READ UNCOMMITTED is silently upgraded.
  • "How does SQL injection work and how do you prevent it?"
    Concatenating user input into query text lets input like ' OR '1'='1 or '; DROP TABLE ...-- change the query's structure. Prevention: parameterized queries ($1 placeholders) — SQL and values are transmitted separately so values can never execute as SQL. ORMs do this by default.
  • "Composite index on (a, b) — which queries can use it?"
    Leftmost-prefix rule: filters on a, or a AND b — not b alone, just as a last-name-then-first-name phone book can't find people by first name.
  • "Why use a connection pool?"
    Connections are expensive (handshake, auth, a server process each) and Postgres caps them. A pool reuses a fixed set of warm connections across requests — same idea as HikariCP in Java.
  • "When would you use JSONB vs normal columns?"
    JSONB for genuinely variable, schema-less fragments (preferences, third-party payloads), indexed with GIN for containment queries. Fixed, always-present, constrained, or frequently-joined data belongs in real columns.
