PostgreSQL: SQL Fundamentals

Every API you've built so far forgets everything on restart — today your data finally gets a permanent, queryable, rule-enforcing home.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 21 of 24. Index

1 · Why a database at all?

In the Express lessons you stored notes and users in a plain JavaScript array: const users = []. It worked for learning, but think about what happens in real life. Four problems kill the in-memory (or "just write a JSON file") approach, and each one is a reason databases exist:

  • Persistence. Restart the server — deploy, crash, laptop reboot — and the array is gone. A file survives restarts, but…
  • Concurrency. Two requests hit your API at the same moment. Both read the JSON file, both modify their copy, both write it back — one write silently overwrites the other. This is a lost update, and files have no defence against it. A database serialises and coordinates concurrent writers safely.
  • Integrity. Nothing stops your array from holding two users with the same email, a post whose authorId points at a deleted user, or a price of -50. In a database you declare these rules once (UNIQUE, FOREIGN KEY, CHECK) and the database refuses bad data from any code path — even a buggy one.
  • Querying. "Top 10 users by post count in the last 30 days" against an array means writing loops, sorts and grouping by hand, loading everything into memory first. SQL expresses that in four lines, and the database answers it without shipping a million rows to Node — using indexes to touch only what's needed.
Interview one-liner "A database gives you four things application memory and flat files can't: durable storage that survives crashes, safe concurrent access from many clients, enforced data integrity via constraints, and a declarative query language that answers complex questions efficiently."

2 · The relational model — tables, rows, columns

A relational database organises data into tables. Start with the Excel analogy: a table is a sheet, each row is one record (one user, one post), each column is one attribute (email, title, created date). Simple.

Then go beyond Excel, because the differences are the whole point:

  • Every column has a fixed type. An integer column can never hold "hello". Excel lets any cell hold anything; a database is more like a Java class — int age; is int forever.
  • Rows have no inherent order. A table is a set of rows. If you want order, you ask for it with ORDER BY.
  • Tables reference each other. A post row stores the id of its author, not a copy of the author. The database can enforce that this reference is always valid. Excel has nothing like this.
  • You talk to it in SQL — a declarative language where you say what you want, and the database's planner decides how to fetch it.
Java parallel A table is roughly a class (class User { long id; String email; }), a row is an object, and a column is a field. The mismatch between "rows in tables" and "objects in memory" is called the object-relational impedance mismatch — ORMs like Drizzle (Lesson 23) exist to bridge it.

3 · The database landscape — and why PostgreSQL

Before picking one, know the map. Databases split into two big families. Relational (SQL) databases store data in tables with a fixed schema and speak SQL — Postgres, MySQL, SQLite, SQL Server, Oracle. NoSQL databases drop the table model for something else: documents (MongoDB stores JSON-like objects), key-value (Redis — an in-memory cache, blazing fast, usually a sidekick rather than the main database), wide-column (Cassandra) and graph (Neo4j).

DatabaseTypeWhere you'll meet it
PostgreSQLRelational#1 in developer surveys; default for new products and startups; what this track uses
MySQLRelationalThe long-time web workhorse (LAMP, WordPress); huge legacy + current install base
MongoDBNoSQL (document)The most popular NoSQL DB; the "M" in MERN; flexible-schema JSON documents
Oracle / SQL ServerRelationalBig enterprise, banks, government — by revenue Oracle still leads the industry
SQLiteRelational (embedded)A single-file DB inside apps and phones — no server at all
RedisKey-value (in-memory)Caching, sessions, queues — alongside a primary DB, not instead of one
Interview one-liner "Relational databases like Postgres or MySQL are the default: strict schema, joins, ACID transactions. I'd reach for a document store like MongoDB when the data is naturally document-shaped or the schema changes fast, and add Redis as a cache in front of either. For anything with money, relationships, or integrity rules — relational wins."
Gotcha "NoSQL is faster" is a myth worth killing in interviews. Each is fast at what it's shaped for: MongoDB reads a whole document in one hop but joins poorly; Postgres joins effortlessly and, with jsonb (Lesson 22), can store documents too. Choose by data shape and integrity needs, not by hype.

Within the relational family, we use PostgreSQL ("Postgres") because it is the modern default choice:

  • Open-source and free, with three decades of engineering behind it — no licence tiers, no vendor lock-in.
  • Feature-rich: real data types (arrays, jsonb, uuid), full-text search, window functions, strict standards compliance. Things that are extensions elsewhere are built in.
  • Strict by default. Postgres rejects invalid data loudly instead of silently coercing it (older MySQL was infamous for quietly truncating strings).
  • The ecosystem default: Neon, Supabase, RDS, Railway — every modern hosting platform leads with Postgres, and Drizzle/Prisma treat it as the first-class target.

Everything you learn here is 90% portable SQL anyway — switching databases later is mostly relearning edge cases, not the language.

4 · Getting it running

Two good options — pick one:

-- Option A: Docker (recommended — clean, disposable, one line)
docker run --name pg -e POSTGRES_PASSWORD=secret -p 5432:5432 -d postgres:16

-- then open an interactive SQL shell inside it:
docker exec -it pg psql -U postgres

Option B: the official installer for Windows — it installs the server as a service plus pgAdmin (a GUI) and the psql command-line client. Default port is 5432; default superuser is postgres.

psql is where you'll live in this lesson. The commands starting with a backslash are psql meta-commands (client-side helpers), not SQL:

\l          -- list all databases on this server
CREATE DATABASE devlog;   -- real SQL: make a database (note the ; — SQL statements end with one)
\c devlog   -- connect to (switch into) database devlog
\dt         -- list tables in the current database
\d users    -- describe table 'users': columns, types, constraints, indexes
\q          -- quit psql

If you prefer clicking, pgAdmin (bundled) or TablePlus give you a GUI with a query editor and table browser — useful for inspecting data, but learn the SQL first; the GUI just runs SQL for you.

6 · Data types — choose deliberately

Unlike JavaScript, every column commits to a type up front. The ones you'll actually use:

TypeUse forNotes

serial / bigserialAuto-incrementing idShorthand: integer + auto-sequence. Modern preferred spelling: bigint GENERATED ALWAYS AS IDENTITY.
numeric(p,s)Money, exact decimalsExact arithmetic, like Java's BigDecimal.

7 · CREATE TABLE — structure plus rules

Here is our running example for the rest of the lesson (and the track): a mini blog with users, posts, and tags. Constraints are the star — each one is a rule the database enforces forever, no matter which app, script, or careless intern writes the data: 

CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                                  -- PRIMARY KEY = NOT NULL + UNIQUE + the row's official identity
  email       text NOT NULL UNIQUE,   -- must exist, no duplicates across the table
  name        text NOT NULL,
  age         integer CHECK (age >= 13),          -- arbitrary rule; NULL age is still allowed
  created_at  timestamptz NOT NULL DEFAULT now()  -- filled in automatically if omitted
);

CREATE TABLE posts (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  author_id   bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
                                  -- FOREIGN KEY: must match an existing users.id;
                                  -- deleting a user auto-deletes their posts
  title       text NOT NULL,
  body        text NOT NULL DEFAULT '',
  published   boolean NOT NULL DEFAULT FALSE,
  created_at  timestamptz NOT NULL DEFAULT now()
);

The constraint vocabulary, spelled out:

  • PRIMARY KEY — the column that uniquely identifies each row. Every table should have one; almost always a generated id.
  • NOT NULL — the column must have a value. NULL means "unknown/absent", and it is the SQL cousin of Java's null — with even sharper edges (see WHERE below).
  • UNIQUE — no two rows may share this value (two NULLs are allowed — NULL isn't equal to anything, even itself).
  • DEFAULT — value used when the INSERT doesn't supply one.
  • CHECK — any boolean condition rows must satisfy.
  • FOREIGN KEY / REFERENCES — this value must exist as a key in another table. The referential-integrity option matters: ON DELETE CASCADE (delete children with the parent — posts die with their user), ON DELETE SET NULL (orphan the child gracefully — needs a nullable column), or the default NO ACTION/RESTRICT (refuse to delete a referenced parent).
Interview one-liner "Constraints push data-integrity rules from application code into the database, where they're enforced for every writer. A foreign key guarantees you can never have a post pointing at a user that doesn't exist — the app can't forget the check, because the check isn't in the app."

Structure changes later? ALTER and DROP:

ALTER TABLE posts ADD COLUMN views integer NOT NULL DEFAULT 0;
ALTER TABLE posts RENAME COLUMN body TO content;
ALTER TABLE posts DROP COLUMN views;
ALTER TABLE users ALTER COLUMN name SET DEFAULT 'anonymous';

DROP TABLE posts;              -- deletes the table AND all its data, no undo
DROP TABLE IF EXISTS posts;    -- no error if it's already gone

8 · INSERT and SELECT — writing and reading rows

-- single row; unlisted columns take their DEFAULT (id, created_at, published)
INSERT INTO users (email, name, age) VALUES ('krish@dev.io', 'Krish', 21);

-- multi-row insert: one statement, several rows — much faster than a loop
INSERT INTO users (email, name, age) VALUES
  ('asha@dev.io',  'Asha',  22),
  ('ravi@dev.io',  'Ravi',  25),
  ('meera@dev.io', 'Meera', NULL);

-- RETURNING hands back the row you just wrote — no second query needed.
-- This is how your API will get the generated id to send in the 201 response.
INSERT INTO posts (author_id, title, body, published)
VALUES (1, 'Hello Postgres', 'First post!', TRUE)
RETURNING id, created_at;

Reading is SELECT. Its clauses always appear in the same order — memorise the skeleton:

SELECT ...columns... FROM table
WHERE ...filter rows...
GROUP BY ... HAVING ...
ORDER BY ... LIMIT ... OFFSET ...;
SELECT * FROM users;                       -- every column, every row (debugging only)
SELECT name, email FROM users;             -- pick columns — in APIs, always list them
SELECT name AS display_name FROM users;    -- alias: rename in the result
SELECT DISTINCT age FROM users;            -- de-duplicated values

9 · WHERE, ORDER BY, LIMIT — filtering and shaping

SELECT * FROM users WHERE age >= 21;                 -- =, <> (not equal), <, >, <=, >=
SELECT * FROM users WHERE age >= 21 AND age < 30;    -- AND / OR / NOT, parentheses to group
SELECT * FROM users WHERE age BETWEEN 21 AND 29;     -- inclusive both ends
SELECT * FROM users WHERE name IN ('Asha', 'Ravi');  -- membership in a list
SELECT * FROM users WHERE email LIKE '%@dev.io';     -- pattern: % = any chars, _ = one char
SELECT * FROM users WHERE name ILIKE 'kri%';         -- ILIKE = case-insensitive (Postgres)
SELECT * FROM users WHERE age IS NULL;               -- NULL check needs IS, never =
Gotcha — NULL breaks = WHERE age = NULL returns zero rows, silently. Any comparison with NULL evaluates to unknown — not true, not false — and WHERE only keeps rows where the condition is true. Use IS NULL / IS NOT NULL. This trips up nearly everyone once. 
-- ORDER BY: sort the result (remember: tables themselves are unordered sets)
SELECT name, age FROM users ORDER BY age DESC, name ASC;   -- tie-break with a 2nd key

-- LIMIT/OFFSET: pagination — page 3 with 10 per page:
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10 OFFSET 20;

This LIMIT/OFFSET pattern is exactly what backs the ?page=3&limit=10 query params from your Express lessons. (Large OFFSETs get slow — the database still walks past the skipped rows; keyset pagination fixes that, a story for the System Design track.)

10 · UPDATE and DELETE — with a horror story

UPDATE posts
SET title = 'Hello PostgreSQL', published = TRUE
WHERE id = 1;                       -- WHERE picks which rows change

UPDATE posts SET views = views + 1 WHERE id = 7;   -- read-modify-write in ONE atomic statement

DELETE FROM posts WHERE id = 1;
DELETE FROM posts WHERE published = FALSE AND created_at < now() - interval '1 year';
The forgot-the-WHERE horror story UPDATE users SET email = 'x@x.com'; — no WHERE. Every user in production now has the same email. Same with DELETE FROM users; — the table is empty. SQL does exactly what you said, instantly, to all rows. Working habits that save careers: run a SELECT with the same WHERE first to see what you'll hit; and in a manual session, wrap risky statements in BEGIN; ... ROLLBACK; (transactions — Lesson 22) so you can undo.

11 · Aggregates, GROUP BY and HAVING

Aggregates collapse many rows into one number:

SELECT COUNT(*) FROM posts;                    -- how many rows
SELECT COUNT(age) FROM users;                  -- counts only NON-NULL ages — subtle!
SELECT AVG(age), MIN(age), MAX(age) FROM users;
SELECT SUM(views) FROM posts WHERE published;

GROUP BY makes aggregates per-bucket instead of per-table: "split the rows into groups by this column, then aggregate each group." 

-- posts per author:
SELECT author_id, COUNT(*) AS post_count
FROM posts
GROUP BY author_id;

-- only authors with 5+ posts — HAVING filters GROUPS (WHERE filters rows, and
-- runs BEFORE grouping; HAVING runs AFTER, so it can see the aggregate):
SELECT author_id, COUNT(*) AS post_count
FROM posts
WHERE published = TRUE
GROUP BY author_id
HAVING COUNT(*) >= 5
ORDER BY post_count DESC;
The classic GROUP BY error SELECT author_id, title, COUNT(*) FROM posts GROUP BY author_id; → "column "posts.title" must appear in the GROUP BY clause or be used in an aggregate function." Why: each result row represents a whole group of posts — which single title would it show? Ambiguous, so Postgres refuses. Every selected column must be either in the GROUP BY or wrapped in an aggregate. Interviewers love asking why this errors.

12 · Modeling relationships — 1:1, 1:N, M:N

Real data is connected. Three shapes cover everything:

  • One-to-one (1:1) — a user has one profile. Give profiles.user_id a foreign key that is also UNIQUE (unique FK = at most one profile per user). Used to split rarely-needed or private columns out of a hot table.
  • One-to-many (1:N) — a user has many posts; each post has one author. The many side carries the foreign key: posts.author_id. This is the most common shape by far.
  • Many-to-many (M:N) — a post has many tags; a tag belongs to many posts. Neither table can hold the other's id (which one of many would it store?). The fix is a third table — a junction (join) table — where each row is one link:
CREATE TABLE tags (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL UNIQUE
);

CREATE TABLE post_tags (
  post_id  bigint NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  tag_id   bigint NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)   -- composite PK: the same link can't exist twice
);

-- 'tag post 3 with tag 2' is just an insert:
INSERT INTO post_tags (post_id, tag_id) VALUES (3, 2);

13 · JOINs — reading across tables

Splitting data into tables is only useful if you can put it back together. A JOIN pairs rows from two tables using a condition — almost always foreign key = primary key. Picture two circles of a Venn diagram: users on the left, posts on the right, matches in the overlap. Our running example: 

-- users: (1 Krish) (2 Asha) (3 Ravi — has written no posts)
-- posts: ('Hello' author 1) ('SQL 101' author 2) ('Draft' author 2)

-- INNER JOIN: only pairs that MATCH. Ravi vanishes (no posts).
SELECT u.name, p.title
FROM users u
INNER JOIN posts p ON p.author_id = u.id;
--   Krish | Hello
--   Asha  | SQL 101
--   Asha  | Draft

-- LEFT JOIN: every LEFT row survives; missing right side becomes NULLs.
SELECT u.name, p.title
FROM users u
LEFT JOIN posts p ON p.author_id = u.id;
--   Krish | Hello
--   Asha  | SQL 101
--   Asha  | Draft
--   Ravi  | NULL      ← kept! This is how you find users with no posts:

SELECT u.name FROM users u
LEFT JOIN posts p ON p.author_id = u.id
WHERE p.id IS NULL;                        -- classic interview query
  • RIGHT JOIN — mirror image: every right row survives. Rarely written; people swap the table order and use LEFT.
  • FULL JOIN — every row from both sides; non-matches padded with NULLs on the missing side.
  • CROSS JOIN — every row paired with every row (m × n, no condition). Rare; useful for generating combinations.
  • Self-join — a table joined to itself, e.g. an employees table where manager_id REFERENCES employees(id):
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;  -- two aliases, one table

-- and the M:N read — posts with their tags takes TWO joins through the junction:
SELECT p.title, t.name AS tag
FROM posts p
JOIN post_tags pt ON pt.post_id = p.id
JOIN tags t       ON t.id = pt.tag_id;
JOIN typeRows you getTypical use
INNER JOINOnly matching pairs from both tables"Posts with their authors"
LEFT JOINAll left rows; NULLs where right has no match"All users, with posts if any" / find-the-missing
RIGHT JOINAll right rows; NULLs where left has no matchMirror of LEFT — usually rewritten as LEFT
FULL JOINAll rows from both; NULL-padded non-matchesReconciling two datasets
CROSS JOINEvery combination (m × n)Generating pairs/grids

14 · Subqueries and CTEs — queries inside queries

-- subquery with IN: authors of published posts
SELECT name FROM users
WHERE id IN (SELECT author_id FROM posts WHERE published = TRUE);

-- scalar subquery: one value used inline — users older than average
SELECT name, age FROM users
WHERE age > (SELECT AVG(age) FROM users);

-- correlated subquery (glance): the inner query references the outer row,
-- so it conceptually re-runs per row — powerful but often slower than a join
SELECT u.name,
  (SELECT COUNT(*) FROM posts p WHERE p.author_id = u.id) AS post_count
FROM users u;

A CTE (Common Table Expression, the WITH clause) names an intermediate result so big queries read top-to-bottom instead of inside-out:

WITH author_counts AS (
  SELECT author_id, COUNT(*) AS post_count
  FROM posts GROUP BY author_id
)
SELECT u.name, ac.post_count
FROM author_counts ac
JOIN users u ON u.id = ac.author_id
WHERE ac.post_count >= 2;

15 · Normalization — 1NF, 2NF, 3NF in five minutes

Normalization is the discipline behind "split data into related tables". The enemy is redundancy: the same fact stored in many rows drifts out of sync (update one copy, forget the others — an update anomaly). Start with a denormalized mess: 

-- ONE table for everything (bad):
-- orders(id, customer_name, customer_email, product_names, total)
--   1 | Krish | krish@dev.io | 'keyboard,mouse' | 2500
--   2 | Krish | krish@d.io   | 'monitor'        | 9000   ← email drifted!
  • 1NF — atomic values. No lists inside a cell. 'keyboard,mouse' is unqueryable — you can't join or index inside a string. Fix: one row per order-item (an order_items table).
  • 2NF — no partial dependency. With a composite key like (order_id, product_id), every non-key column must depend on the whole key. A product_name column there depends only on product_id — move it to a products table.
  • 3NF — no transitive dependency. Non-key columns must depend on the key directly. customer_email depends on the customer, not the order — move customer fields to a customers table and keep customer_id in orders.
-- normalized: each fact lives in exactly ONE place
customers(id, name, email)
products(id, name, price)
orders(id, customer_id → customers, created_at)
order_items(order_id → orders, product_id → products, qty)
Interview one-liner "Normalize until every fact is stored exactly once: atomic values (1NF), non-key columns depending on the whole key (2NF), and on nothing but the key (3NF). Denormalize later only as a measured performance tradeoff — accepting redundancy for read speed." A cheap mnemonic for 2NF/3NF: every column depends on the key (1NF), the whole key (2NF), and nothing but the key (3NF).

16 · Interview questions this lesson answers

  • "What's the difference between WHERE and HAVING?"
    WHERE filters individual rows before grouping, so it can't use aggregates; HAVING filters groups after GROUP BY, so it can (HAVING COUNT(*) >= 5).
  • "Explain the types of JOINs."
    INNER returns only matching pairs; LEFT keeps all left rows padding misses with NULLs (RIGHT is its mirror); FULL keeps all rows from both sides; CROSS is every combination. A self-join joins a table to itself via aliases for hierarchical data.
  • "What is a primary key vs a foreign key vs a unique constraint?"
    A primary key uniquely identifies each row (NOT NULL + UNIQUE, one per table). A foreign key makes a column reference another table's key, and the database rejects values that don't exist there. UNIQUE forbids duplicates but allows NULLs and can appear on many columns.
  • "How do you model a many-to-many relationship?"
    With a junction table holding two foreign keys — e.g. post_tags(post_id, tag_id) with a composite primary key. Each row is one link; M:N becomes two 1:N relationships.
  • "What is normalization? Explain 1NF/2NF/3NF."
    Organising tables to remove redundancy and update anomalies: 1NF atomic values, 2NF no non-key column depending on part of a composite key, 3NF no non-key column depending on another non-key column — "the key, the whole key, and nothing but the key."
  • "Why did SELECT with GROUP BY throw 'column must appear in GROUP BY'?"
    Because each output row represents a whole group; a column that's neither grouped nor aggregated has no single defined value for that group, so Postgres refuses the ambiguity.
  • "Why store money in NUMERIC and time in timestamptz?"
    Floats are binary approximations that accumulate rounding errors; NUMERIC is exact like BigDecimal. Plain timestamp records a wall-clock time with no zone, which breaks across time zones and DST; timestamptz stores an absolute UTC instant.
