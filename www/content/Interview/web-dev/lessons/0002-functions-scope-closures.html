Functions, Scope & Closures

In Java, methods live inside classes and behave. In JS, functions are free-roaming values — you can pass them, return them, and make them remember things. That last trick powers everything from React hooks to Express middleware.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 2 of 24. Index

1 · Three ways to write a function

Java gives you one way to define behavior: a method inside a class. JS gives you three syntaxes, and the differences between them are real, testable behavior — not style. 

// 1) FUNCTION DECLARATION — a standalone statement starting with 'function'
function add(a, b) {
  return a + b;
}

// 2) FUNCTION EXPRESSION — a function used as a VALUE, assigned to a variable
const subtract = function (a, b) {
  return a - b;
};

// 3) ARROW FUNCTION (ES6) — compact expression syntax
const multiply = (a, b) => a * b;        // one expression? it's auto-returned
const square   = n => n * n;             // one parameter? parens optional
const greet    = () => "hi";             // zero parameters? empty parens required
const divide   = (a, b) => {             // need multiple statements? add braces…
  if (b === 0) throw new Error("÷0");
  return a / b;                          // …and then 'return' is on you again
};

The first behavioral difference: hoisting. Declarations are hoisted whole — body and all — so you can call them before their line. Expressions live in variables, and variables follow Lesson 1's rules:

add(2, 3);       // 5 — declaration was fully hoisted, this works
subtract(5, 2);  // ReferenceError — 'subtract' is a const, still in its TDZ

function add(a, b) { return a + b; }
const subtract = function (a, b) { return a - b; };

The second difference — the big one — is this. Arrow functions don't get their own this; they borrow it from the surrounding scope. That single fact fixes a decade of JS bugs, and it deserves its own stage: Lesson 3 covers it in depth. For now: arrows are perfect for short callbacks, and you should not use them as object methods until you've seen why.

2 · Parameters: defaults, rest, and the arguments object

Java overloads methods to handle different argument counts. JS doesn't have overloading at all — a function has one definition, and callers may pass too few or too many arguments without any error. Missing parameters are simply undefined; extras are ignored. The tools below exist to manage that flexibility. 

// DEFAULT PARAMETERS — used when the argument is undefined (missing counts)
function connect(host, port = 5432, retries = 3) {
  return `${host}:${port} (retries ${retries})`;
}
connect("db.local");             // "db.local:5432 (retries 3)"
connect("db.local", 8080);       // "db.local:8080 (retries 3)"
connect("db.local", undefined, 5); // default kicks in for port: "db.local:5432 (retries 5)"
connect("db.local", null, 5);    // null is a VALUE, default does NOT kick in: "db.local:null…"

// REST PARAMETER — gathers "all remaining arguments" into a real array
function sum(...nums) {          // nums is a genuine array: map/filter/reduce all work
  let total = 0;
  for (const n of nums) total += n;
  return total;
}
sum(1, 2, 3, 4);                 // 10 — this is JS's varargs, like Java's int... nums

// THE OLD WAY: 'arguments' — an array-LIKE object available in non-arrow functions
function legacySum() {
  let total = 0;
  for (let i = 0; i < arguments.length; i++) total += arguments[i];
  return total;                  // works, but arguments has no map/filter, and
}                                // arrow functions don't have it at all. Prefer ...rest.
Java parallel Rest parameters are Java varargs: function sum(...nums) ≈ int sum(int... nums), same last-position-only rule. Default parameters replace the overload pattern — where Java writes connect(String h) delegating to connect(String h, int p), JS writes one function with port = 5432.

3 · Functions are values — first-class citizens

Here is the sentence that separates JS thinking from Java thinking: a function is just a value, like 42 or "hello". It can be stored in a variable, put in an array, passed as an argument, and returned from another function. Java only approximated this in Java 8 with lambdas and Function<T,R> — in JS it has been the core design since day one. 

const shout = function (s) { return s.toUpperCase() + "!"; };

const ops = [shout, s => s.length, s => s.split("").reverse().join("")];
ops[0]("hey");                  // "HEY!" — grabbed from an array and called

function applyTwice(fn, value) { // takes a function as a parameter…
  return fn(fn(value));
}
applyTwice(shout, "go");        // "GO!!"

function makeMultiplier(factor) {
  return x => x * factor;       // …and returns a brand-new function
}
const triple = makeMultiplier(3);
triple(7);                      // 21

Two vocabulary words fall straight out of this, and interviewers use both:

  • A callback is a function you hand to other code so it can call you back at the right moment — when a button is clicked, when data arrives, for each array element. shout passed into applyTwice is a callback.
  • A higher-order function (HOF) is any function that takes a function as an argument or returns one. applyTwice and makeMultiplier both qualify — as do map, filter, and reduce, the HOFs you'll use daily from Lesson 4 onward.
// The HOFs you'll actually live in (full treatment in Lesson 4):
[1, 2, 3, 4].map(n => n * 2)        // [2, 4, 6, 8]   — transform each element
[1, 2, 3, 4].filter(n => n % 2 === 0) // [2, 4]        — keep matching elements
setTimeout(() => console.log("later"), 1000) // run my callback after ~1s
Java parallel Java 8's list.stream().map(n -> n * 2) and button.addActionListener(e -> ...) are the same idea — but under the hood Java wraps each lambda in a functional-interface object. JS needs no wrapper: the function is the value. No Function<T,R>, no @FunctionalInterface, no ceremony.

4 · IIFE — the historical oddity worth knowing

You will meet this pattern in older code and in interviews: the IIFE (Immediately Invoked Function Expression, pronounced "iffy") — a function defined and called in the same breath: 

(function () {
  var secret = "hidden";        // trapped inside — invisible to the outside world
  console.log("runs once, immediately");
})();                            // ← the () at the end calls it right now

// console.log(secret);  → ReferenceError. Mission accomplished.

Why did this exist? Before 2015, JS had only var (function-scoped — no block scope) and no module system: every script dumped its variables into the shared global scope, and two scripts using the same name silently clobbered each other. The only way to create a private scope was… a function. So developers wrapped whole files in one. The wrapping parentheses force the function keyword to be parsed as an expression (statements can't be immediately invoked; expressions can).

Today, block scope (let/const + {}) and ES modules (Lesson 8) solve the privacy problem properly, so you'll rarely write an IIFE — but you must recognize it, explain why it existed, and you'll see its ghost in every bundled JS file you ever open in DevTools.

5 · Lexical scope and the scope chain

Lesson 1 introduced the rule: inner scopes can see outer names. Now the precise mechanism, because closures depend on it. When code uses a name, the engine resolves it by walking the scope chain: current scope → enclosing scope → … → global. And critically, "enclosing" is decided by where the function is written in the source code — not where or by whom it is called. That's what lexical (= "of the text") scope means. 

const region = "global";

function outer() {
  const region = "outer";
  function inner() {
    console.log(region);   // which one? walk outward from where inner is WRITTEN:
  }                        // inner's scope → outer's scope (found! "outer") → global
  return inner;
}

const fn = outer();
fn();                      // "outer" — even though we CALL it out here in global,
                           // its birth location decides what it sees. Forever.

Nearest match wins — the inner region shadows the global one, exactly like a Java local shadowing a field. The chain is fixed at the moment the function is created, like a birth certificate listing its home address. Calling the function later, from anywhere, doesn't change its home. Hold that thought — it's the entire secret of the next section.

6 · Closures — functions with a backpack

Now the headline concept of this lesson, and one of the top-three JS interview topics of all time.

A closure is a function bundled together with the variables from its birth scope. When a function is created inside another function, it keeps a live link to the outer function's variables — and that link survives even after the outer function has returned. Analogy: the inner function leaves home carrying a backpack holding every outer variable it uses. Wherever it travels, the backpack goes too. 

function makeCounter() {
  let count = 0;              // a local — should die when makeCounter returns…
  return function () {
    count++;                  // …but the inner function still holds it
    return count;
  };
}

const counter = makeCounter(); // makeCounter has now RETURNED. count lives on.
counter();  // 1
counter();  // 2
counter();  // 3 — the backpack persists between calls

const other = makeCounter();   // a fresh call → a fresh scope → a FRESH backpack
other();    // 1 — completely independent of counter's count

Why doesn't count die? In Lesson 1's terms: locals live in a scope object, and scope objects are garbage-collected when nothing references them. The returned inner function references its birth scope — so the GC must keep that scope alive. A closure is simply a scope kept alive by a surviving function.

Use 1 — private state. Notice what just happened: count is impossible to touch except through the returned function. That's encapsulation — Java's private keyword — achieved with no class at all:

function createAccount(opening) {
  let balance = opening;               // effectively 'private double balance'
  return {
    deposit(amt)  { if (amt > 0) balance += amt; return balance; },
    withdraw(amt) { if (amt > 0 && amt <= balance) balance -= amt; return balance; },
    getBalance()  { return balance; }
  };                                   // three methods sharing ONE backpack
}

const acc = createAccount(1000);
acc.deposit(500);      // 1500
acc.balance;           // undefined — no such property; the real balance is unreachable
acc.withdraw(99999);   // 1500 — the guard logic cannot be bypassed
Java parallel This is a class with a private field, written without a class. createAccount plays constructor; the closure variables play private fields; the returned object's functions play public methods. Java's inner classes capture outer variables too — but only final/effectively-final ones. JS closures capture the live variable itself, mutation included — strictly more powerful.

Use 2 — the classic loop pitfall (a guaranteed interview question):

// BUG: prints 3, 3, 3 — not 0, 1, 2
for (var i = 0; i < 3; i++) {
  setTimeout(function () { console.log(i); }, 100);
}

Why? var is function-scoped, so all three iterations share one variable i — all three callbacks carry the same backpack containing the same i. The callbacks run after the loop finishes (timers wait, Lesson 6), by which time i is 3. Closures capture variables, not values. 

// FIX: let is block-scoped — each iteration gets a FRESH i in a fresh backpack
for (let i = 0; i < 3; i++) {
  setTimeout(function () { console.log(i); }, 100);   // 0, 1, 2 ✓
}

// The pre-2015 fix, for history: an IIFE forcing a per-iteration copy
for (var i = 0; i < 3; i++) {
  (function (j) {                                      // j is a fresh local per pass
    setTimeout(function () { console.log(j); }, 100);  // 0, 1, 2 ✓
  })(i);
}

Use 3 — why this concept owns the rest of the track. Closures aren't an exam curiosity; they are the load-bearing wall of everything ahead:

  • React hooks (Lesson 12): useState works because your component function closes over its state; the notorious "stale closure" bug is exactly the var-in-loop pitfall wearing a React costume.
  • Express middleware (Lesson 18): rateLimit({ max: 100 }) returns a handler that closes over your config — that's makeMultiplier at industrial scale.
  • Debounce, throttle, memoize (Lesson 10): each is ~10 lines of closure keeping private timers/caches.
  • Event handlers & callbacks everywhere: any callback that uses a variable from where it was written is using a closure. You'll write hundreds without noticing.
Interview one-liner "A closure is a function that retains access to its lexical scope's variables even after the outer function has returned. The engine keeps that scope alive because the inner function references it. It gives JS private state and is how React hooks, middleware factories, and debounce/memoize all work. Key subtlety: closures capture variables, not values — hence the var-in-loop bug and its let fix."

7 · Pure functions and side effects

Last concept — a small one with a big future. A pure function satisfies two conditions: (1) same inputs → same output, always; (2) no side effects — it doesn't modify anything outside itself (no mutating shared objects, no writing globals, no I/O, no console.log in the strict sense). 

// PURE — same in, same out; touches nothing outside
function circleArea(r) { return Math.PI * r * r; }
function withTax(price, rate) { return price * (1 + rate); }

// IMPURE — depends on / modifies the outside world
let total = 0;
function addToTotal(x) { total += x; return total; }  // mutates a global
function now() { return Date.now(); }                 // different output each call

// SUBTLY IMPURE — mutates its argument (the caller's object! Lesson 1 §9)
function addItemBad(cart, item) {
  cart.push(item);              // caller's array modified — side effect
  return cart;
}
// PURE version — build a new array, leave the input untouched
function addItem(cart, item) {
  return [...cart, item];       // spread copies; full story in Lesson 4
}

Why care? Pure functions are trivially testable (no setup, no mocks), safe to cache, and safe to run in any order. React is built on this contract — components are expected to be pure functions of their props, and Redux reducers must be pure. When React (Lesson 11) says "don't mutate state," it's this section talking. Real programs need side effects (saving to a DB is the job) — the discipline is to push them to the edges and keep the core logic pure.

8 · Interview questions this lesson answers

  • Q. "What's the difference between a function declaration and a function expression?"
    A declaration (function f() {} as a statement) is hoisted with its body, so it's callable anywhere in its scope. An expression (const f = function () {}) is a value assigned to a variable, so it follows variable rules — calling it before the assignment throws (TDZ with const/let).
  • Q. "What is a closure? Give a practical use."
    A function plus its preserved lexical scope: inner functions keep live access to outer variables even after the outer function returns, because the engine keeps that scope alive. Uses: private state (counter/account factories), function factories and middleware configuration, debounce/throttle/memoize, React hooks.
  • Q. "Why does for (var i...) with setTimeout print the final value three times, and what fixes it?"
    var is function-scoped, so every callback closes over the one shared i; by the time the timers fire the loop has finished and i is 3. let creates a fresh binding per iteration, so each callback captures its own value. Pre-ES6, an IIFE passing i as a parameter achieved the same.
  • Q. "What is a higher-order function? A callback?"
    A HOF takes and/or returns functions — possible because JS functions are first-class values. A callback is a function passed to other code to be invoked later (event handlers, map's argument, timer functions).
  • Q. "Rest parameter vs the arguments object?"
    ...rest is a true array holding the remaining arguments and works everywhere including arrows. arguments is a legacy array-like object (no array methods), absent in arrow functions. Always prefer rest.
  • Q. "What is an IIFE and why was it used?"
    A function expression invoked immediately: (function(){...})(). Pre-ES6 it was the only way to create private scope and avoid polluting the shared global namespace. Block scope and ES modules have replaced it.
  • Q. "What makes a function pure, and why does it matter?"
    Deterministic output from inputs alone, and zero side effects (including not mutating arguments). Pure functions are easy to test, cache, and reason about — React components and Redux reducers are required to be pure.
