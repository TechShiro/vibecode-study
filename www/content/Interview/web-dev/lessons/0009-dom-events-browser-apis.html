DOM, Events & Browser APIs

Your JavaScript finally touches the page — select, change and build elements, react to clicks and keys, and ship a real todo app by the end.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 9 of 24. Index

1 · What the DOM is — and your scaffold for this lesson

When the browser reads an HTML file, it doesn't keep it as text. It builds a tree of objects in memory — one node per tag, nested exactly as the tags nest. That live tree is the DOM (Document Object Model), and JS reaches it through one global object: document. Change the tree, and the browser instantly repaints the screen. The DOM is not JavaScript — it's a browser API that JS can call, which is why Node.js has no document.

Java parallel If you've touched XML DOM parsers or Swing, it's the same idea: a tree of node objects with an API to query and mutate it, plus listeners for user events. document is your root handle, like Swing's JFrame — except the "components" were declared in HTML and the browser built them for you.

Per this track's rule you are not learning to author HTML/CSS. Here is the one fixed scaffold for the whole lesson — save it as index.html, put all JS in app.js, and never edit the HTML again: 

<!DOCTYPE html>
<html>
<body>
  <h1 id="title">My App</h1>
  <form id="todo-form">
    <input id="todo-input" placeholder="What to do?" />
    <button type="submit">Add</button>
  </form>
  <div>
    <button class="filter" data-filter="all">All</button>
    <button class="filter" data-filter="active">Active</button>
    <button class="filter" data-filter="done">Done</button>
  </div>
  <ul id="todo-list"></ul>
  <p id="status"></p>
  <script src="app.js"></script>   <!-- at the END of body: elements exist by now -->
</body>
</html>

2 · Selecting elements

The modern API is two methods that accept CSS selectors — #id, .class, tag, and combinations: 

const title = document.querySelector("#title");        // FIRST match, or null
const firstFilter = document.querySelector(".filter"); // first element with class
const filters = document.querySelectorAll(".filter");  // ALL matches → a NodeList

// Older family — still fine, you'll see them in code everywhere:
document.getElementById("title");          // by id, no '#' — fastest, very common
document.getElementsByClassName("filter"); // LIVE collection (updates as DOM changes)

// NodeList is array-LIKE: it has forEach, but not map/filter.
filters.forEach(btn => console.log(btn.dataset.filter));   // ok
const arr = [...filters];                  // spread → real array when you need map()
arr.map(b => b.textContent);
Gotcha querySelector returns null when nothing matches — and the resulting Cannot read properties of null is the most common DOM error in existence. Usual causes: a typo in the selector, or the script ran before the element existed (script tag in <head> without defer). Fix: script at end of body, or listen for DOMContentLoaded (section 5).

3 · Reading and changing elements

const title = document.querySelector("#title");

// TEXT — textContent treats everything as plain text. Safe.
title.textContent = "Todo App";
title.textContent = "<b>hi</b>";     // literally shows "<b>hi</b>" — not bold

// HTML — innerHTML PARSES the string as markup. Powerful and dangerous.
title.innerHTML = "<em>Todo</em> App"; // renders real italic element

// FORM VALUES — inputs use .value, not textContent
const input = document.querySelector("#todo-input");
console.log(input.value);            // whatever the user typed, always a STRING
input.value = "";                    // clear the box

// CLASSES — classList, never string-mash className
title.classList.add("highlight");
title.classList.remove("highlight");
title.classList.toggle("dark");      // on↔off; returns true if now present
title.classList.contains("dark");    // boolean check

// INLINE STYLE — CSS property names become camelCase
title.style.color = "tomato";
title.style.backgroundColor = "black";   // background-color → backgroundColor
// prefer classList + a CSS class over style for anything reusable

// ATTRIBUTES and data-*
input.setAttribute("maxlength", "50");
input.getAttribute("placeholder");       // "What to do?"
const btn = document.querySelector(".filter");
console.log(btn.dataset.filter);         // "all" — data-filter → dataset.filter
btn.dataset.count = "3";                 // writes attribute data-count="3"
Gotcha — innerHTML and XSS Never feed user-supplied text into innerHTML. If a user types <img src=x onerror="stealCookies()"> as their "todo" and you innerHTML it, their code runs in your page — that's XSS (cross-site scripting), a top real-world vulnerability and a standard interview question. Rule: user data → textContent (renders inert text); innerHTML only for markup you wrote.

4 · Creating, inserting, removing

// build a <li><span>Buy milk</span><button>✕</button></li> from scratch
const li = document.createElement("li");       // exists in memory, NOT on page yet
li.dataset.id = "42";

const span = document.createElement("span");
span.textContent = "Buy milk";                 // safe even if text came from a user

const del = document.createElement("button");
del.textContent = "✕";
del.className = "delete";

li.append(span, del);                          // append accepts multiple nodes/strings
document.querySelector("#todo-list").append(li);  // NOW it's on the page

// other insert points:
// parent.prepend(node)      — as first child
// node.before(x) / after(x) — as sibling

li.remove();                                   // gone from the page
document.querySelector("#todo-list").replaceChildren();  // nuke all children

This create → configure → append dance is exactly what React automates: you'll describe what the list should look like, and React performs these calls for you. Doing it by hand first is what makes React make sense.

5 · Events — reacting to the user

Every node is an event emitter. You register a callback with addEventListener(type, handler) — same idea as Swing's addActionListener, and your first daily-life use of Lesson 6's macrotask queue: the browser detects the click, queues your handler, the event loop runs it. 

const btn = document.querySelector(".filter");

function onClick(event) {
  console.log(event.type);            // "click"
  console.log(event.target);          // the element actually clicked (could be a child!)
  console.log(event.currentTarget);   // the element the LISTENER is attached to
}
btn.addEventListener("click", onClick);
btn.removeEventListener("click", onClick);  // must be the SAME function reference —
// removeEventListener("click", () => {...}) removes NOTHING (new function ≠ old one).
// Closures lesson paying rent: anonymous arrows can't be unregistered.

// The events you'll use constantly:
input.addEventListener("input",  e => console.log("every keystroke:", e.target.value));
input.addEventListener("keydown", e => { if (e.key === "Enter") console.log("enter!"); });
form.addEventListener("submit", e => { /* section 7 */ });
document.addEventListener("DOMContentLoaded", () => {
  // fires when the HTML is fully parsed — safe to query anything.
  // Needed if your script loads in <head>; unnecessary with script-at-end-of-body.
});

6 · Bubbling, capturing & event delegation

Click a <span> inside a <li> inside a <ul> — who gets the event? Everyone, in order. The event travels down from document to the target (capturing phase — rarely used), then back up to document (bubbling phase — where listeners fire by default). So a listener on the <ul> hears clicks on every <li> inside it, present or future. 

list.addEventListener("click", e => {
  // e.target        = the deepest element clicked (span? button? li?)
  // e.currentTarget = list (where this listener lives)
  e.stopPropagation();     // stop the journey here — ancestors won't hear it (rarely needed)
});
// third arg { capture: true } would fire on the way DOWN instead — niche.

Bubbling enables the single most important DOM pattern: event delegation. Problem: a todo list where items are added and removed constantly. Attaching a listener to every item is wasteful, and items created later have no listener at all. Solution: one listener on the stable parent, using e.target to work out what was actually clicked: 

const list = document.querySelector("#todo-list");

list.addEventListener("click", (e) => {
  const deleteBtn = e.target.closest("button.delete");  // climbs from target upward,
  if (deleteBtn) {                                      // null if click wasn't on/inside one
    deleteBtn.closest("li").remove();
    return;
  }
  const item = e.target.closest("li");
  if (item) item.classList.toggle("done");              // any other click on a li → toggle
});
// ONE listener. Works for items that don't exist yet. This is delegation.
Interview one-liner "Event delegation: attach one listener to a common ancestor and use the bubbled event's target to identify the actual element. It saves memory and — crucially — automatically covers elements added to the container later. Frameworks like React delegate under the hood."

7 · Forms — preventDefault and validation

A form's default submit behaviour is a full page reload (a leftover from the pre-JS web) — which destroys your app state. Step one of every JS-handled form: e.preventDefault(). 

const form  = document.querySelector("#todo-form");
const input = document.querySelector("#todo-input");
const status = document.querySelector("#status");

form.addEventListener("submit", (e) => {
  e.preventDefault();                  // STOP the reload. Line one, always.

  const text = input.value.trim();     // basic validation
  if (text === "") {
    status.textContent = "Please type something first.";
    return;
  }
  if (text.length > 50) {
    status.textContent = "Keep it under 50 characters.";
    return;
  }

  status.textContent = "";
  addTodo(text);                       // your logic
  input.value = "";                    // clear and refocus for rapid entry
  input.focus();
});
// Listening to "submit" on the FORM (not "click" on the button) is the right way:
// it also catches Enter pressed inside the input, for free.

Note the pairing: preventDefault() cancels the browser's built-in action (submit reload, link navigation) but the event still bubbles; stopPropagation() stops the journey but the default action still happens. Different jobs, both on the event object.

8 · Browser storage — localStorage & friends

Refresh the page and every variable dies. localStorage is a tiny per-site key-value store (~5 MB) that survives refreshes, tab closes, even reboots. sessionStorage is the same API but dies with the tab. Both store strings only — hence the universal JSON round-trip pattern (Lesson 5's JSON.stringify/parse): 

localStorage.setItem("theme", "dark");      // write a string
localStorage.getItem("theme");              // "dark" — or null if absent
localStorage.removeItem("theme");
localStorage.clear();                       // wipe this site's storage

// THE pattern: objects/arrays go through JSON
const todos = [{ id: 1, text: "learn DOM", done: false }];
localStorage.setItem("todos", JSON.stringify(todos));           // object → string

const saved = JSON.parse(localStorage.getItem("todos") ?? "[]"); // string → object,
// with ?? "[]" as the first-visit fallback (getItem returned null)

localStorage.setItem("count", 5);
typeof localStorage.getItem("count");       // "string"! Numbers come back as strings —
Number(localStorage.getItem("count"));      // convert explicitly.

Cookies, in one paragraph: an older, tiny (~4 KB) storage mechanism whose defining feature is that cookies are automatically sent to the server with every HTTP request. That makes them the vehicle for login sessions (the server sets a session cookie; the browser presents it on each request) — and irrelevant for general client-side data, where localStorage wins. You'll work with cookies properly in the Express auth lesson (19).

location & history, at a glance: location.href is the current URL (assign to it to navigate away), with parts like location.pathname and query params readable via new URLSearchParams(location.search). history.back() is the back button; history.pushState() changes the URL without reloading — the trick single-page-app routers (React Router, Lesson 13) are built on.

9 · Errors done properly — throw, custom errors, strict mode

Straight from your Java instincts, with JS twists:

// throw + try/catch/finally — semantics you already know
function getTodo(list, id) {
  const t = list.find(t => t.id === id);
  if (!t) throw new Error(`no todo with id ${id}`);   // throw Error OBJECTS,
  return t;                    // not strings — you want .message and .stack
}

// custom errors — subclass Error, branch with instanceof (like Java catch types)
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";     // shows up in logs instead of "Error"
    this.field = field;                // carry structured data
  }
}

try {
  throw new ValidationError("too long", "title");
} catch (err) {
  if (err instanceof ValidationError) console.log(`fix field: ${err.field}`);
  else throw err;                      // not mine — rethrow (JS has ONE catch,
}                                      // no multi-catch: instanceof + rethrow instead

// finally quirk worth a glance: a RETURN inside finally silently OVERRIDES
// the try block's return AND swallows in-flight exceptions. Never return from finally.
function sneaky() {
  try { return 1; } finally { return 2; }   // returns 2. Yes really.
}

Strict mode. 'use strict'; at the top of a file or function switches off JS's most forgiving (read: bug-hiding) behaviours: assigning to an undeclared variable becomes an error instead of silently creating a global; writing to read-only properties throws instead of failing silently; this in a plain function call is undefined instead of the global object; duplicate parameter names are rejected. You rarely type it today because ES modules and class bodies are automatically strict — but "what does strict mode change?" remains a stock interview question. 

"use strict";
count = 5;         // ReferenceError. Without strict mode: silently creates
                   // a GLOBAL variable — the classic typo-eats-your-data bug.

10 · Capstone — a complete todo app

Everything above, wired together: state as a plain array, one render function, delegation for clicks, a form for input, filters via dataset, persistence via localStorage. This exact app is a common machine-coding round question. Uses the section 1 scaffold — this is the entire app.js: 

"use strict";

// ---------- state ----------
// ONE source of truth: an array of {id, text, done}. The DOM is merely a
// PICTURE of this array — we change state, then redraw. (React's core idea, by hand.)
let todos  = JSON.parse(localStorage.getItem("todos") ?? "[]");
let filter = "all";                       // "all" | "active" | "done"

// ---------- elements ----------
const form   = document.querySelector("#todo-form");
const input  = document.querySelector("#todo-input");
const list   = document.querySelector("#todo-list");
const status = document.querySelector("#status");

// ---------- persistence ----------
function save() {
  localStorage.setItem("todos", JSON.stringify(todos));   // JSON round-trip
}

// ---------- render: state → DOM ----------
function render() {
  list.replaceChildren();                 // wipe and redraw (simple > clever, for now)

  const visible = todos.filter(t =>
    filter === "all"    ? true  :
    filter === "active" ? !t.done :
    t.done);

  for (const todo of visible) {
    const li = document.createElement("li");
    li.dataset.id = todo.id;              // the id rides on the element for delegation

    const span = document.createElement("span");
    span.textContent = todo.text;         // textContent: user input stays inert (no XSS)
    if (todo.done) span.style.textDecoration = "line-through";

    const del = document.createElement("button");
    del.textContent = "✕";
    del.className = "delete";

    li.append(span, del);
    list.append(li);
  }

  const left = todos.filter(t => !t.done).length;
  status.textContent = `${left} item(s) left · showing: ${filter}`;
}

// ---------- add (form submit) ----------
form.addEventListener("submit", (e) => {
  e.preventDefault();                     // no page reload
  const text = input.value.trim();
  if (!text) return;                      // validation: ignore empty

  todos.push({ id: Date.now(), text, done: false });  // timestamp as a cheap unique id
  save();
  render();
  input.value = "";
  input.focus();
});

// ---------- toggle + delete: ONE delegated listener ----------
list.addEventListener("click", (e) => {
  const li = e.target.closest("li");
  if (!li) return;                        // click on the empty ul itself
  const id = Number(li.dataset.id);       // dataset values are strings!

  if (e.target.closest("button.delete")) {
    todos = todos.filter(t => t.id !== id);        // delete: keep everyone else
  } else {
    const todo = todos.find(t => t.id === id);     // toggle
    todo.done = !todo.done;
  }
  save();
  render();                               // state changed → redraw. Every action ends here.
});

// ---------- filters: delegation again, via data-filter ----------
document.addEventListener("click", (e) => {
  const btn = e.target.closest("button.filter");
  if (!btn) return;
  filter = btn.dataset.filter;            // "all" / "active" / "done" from the HTML
  render();
});

render();                                 // first paint from whatever localStorage had

Read the shape, not just the lines — it's the architecture every UI framework formalises:

  • State lives in data (the array), never scraped back out of the DOM;
  • render() is the only writer — one function turns state into pixels;
  • every event handler does: mutate state → save → render. Nothing else touches the page.

When React arrives in Lesson 11, its pitch is exactly: "you write render(), we'll call it at the right times and diff the DOM efficiently." You've now earned that sentence.

12 · Interview questions this lesson answers

  • "What is the DOM?"
    An in-memory tree of node objects the browser builds from HTML, exposed to JS through document. JS queries and mutates the tree; the browser re-renders to match. It's a browser API, not part of the JS language — hence no DOM in Node.
  • "Event bubbling vs capturing? target vs currentTarget?"
    An event travels document → target (capturing), then target → document (bubbling); listeners default to the bubbling phase. target is the element actually interacted with; currentTarget is the element the listener is attached to — they differ exactly when the event bubbled up.
  • "What is event delegation and why use it?"
    One listener on a stable ancestor handles events for all descendants via e.target. Fewer listeners (memory), and elements added later are covered automatically — essential for dynamic lists.
  • "preventDefault vs stopPropagation?"
    preventDefault cancels the browser's default action (form submit reload, link navigation) but the event still bubbles. stopPropagation halts the bubbling journey but the default action still runs. Independent switches.
  • "textContent vs innerHTML?"
    textContent reads/writes plain text — markup is shown literally, so it's safe for user input. innerHTML parses the string as HTML — powerful for trusted markup, but with user data it's an XSS hole.
  • "localStorage vs sessionStorage vs cookies?"
    localStorage: ~5 MB, persists indefinitely, JS-only. sessionStorage: same API, per-tab lifetime. Cookies: ~4 KB, auto-sent to the server on every request — which is why they carry sessions, and why you don't use them for general client data.
  • "What does strict mode do?"
    Turns silent failures into errors: undeclared assignments throw (no accidental globals), writes to read-only properties throw, this is undefined in plain function calls, duplicate params are rejected. Modules and classes are strict automatically.
