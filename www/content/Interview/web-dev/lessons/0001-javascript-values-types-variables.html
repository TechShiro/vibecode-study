Values, Types & Variables

You know Java's strict, compiler-checked world — now meet a language that decides types at runtime, and learn exactly where that freedom bites and how interviewers test it.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 1 of 24. Index

1 · What JavaScript is, and how it actually runs

Java's story: you write .java files, javac compiles them to bytecode, and the JVM runs that bytecode anywhere. JavaScript's story is different: there is no separate compile step you run. You hand raw source code to an engine, and the engine parses, compiles, and executes it in one continuous motion, at runtime.

The engine you'll meet most is V8 (Google's, written in C++). It lives inside Chrome and inside Node.js. Firefox has SpiderMonkey, Safari has JavaScriptCore — all implement the same language standard, called ECMAScript ("ES"). When people say "ES6" or "ES2015+", they mean the big 2015 upgrade that gave us let, const, classes, arrow functions, and most of modern JS.

Modern engines are not slow interpreters. They use JIT (just-in-time) compilation — exactly the trick the JVM uses: start by interpreting quickly, watch which functions run hot, then compile those to optimized machine code on the fly. So "JS is interpreted" is an outdated line; the honest sentence is "JS is JIT-compiled by its engine, like Java bytecode is JIT-compiled by the JVM."

Where can that engine live? Two homes matter to us:

Browser (Chrome, Firefox…)Node.js
EngineV8 (Chrome), SpiderMonkey (Firefox)…V8
Extra powers added around the engineDOM (the page), fetch, alert, browser storageFile system, network servers, processes (fs, http…)

Interview one-liner "JavaScript is a language defined by the ECMAScript standard; an engine like V8 JIT-compiles it. The browser and Node.js are two different host environments wrapping the same engine — the browser adds the DOM, Node adds file and network APIs. The language itself has neither."

To follow along: install Node, save code in a file like play.js, and run node play.js — or just press F12 in Chrome and type into the Console. Both work for everything in Module A.

2 · Dynamic typing — the big mental shift from Java

In Java, variables have types: int x can never hold a String, and the compiler enforces it before the program ever runs. In JavaScript, values have types; variables don't. A variable is just a label that can be stuck onto any value: 

let x = 42;        // x currently labels a number
x = "hello";       // now a string — perfectly legal, no error
x = true;          // now a boolean
x = { name: "Krish" };  // now an object

This is dynamic typing: type checks happen at runtime, on the value itself. Java's approach is static typing: checks happen at compile time, on the variable. The trade: JS lets you move fast and write less ceremony, but type mistakes that Java's compiler would catch on day one surface in JS as runtime bugs on day thirty. (TypeScript, which we meet in the NestJS lesson, bolts Java-style static checking back on top of JS — now you know why it exists.)

Java parallel Think of every JS variable as being declared Object x in Java — it can reference anything — except JS also skips the casts and lets primitives flow through the same variables. The flexibility is real, and so is the loss of compile-time safety.

3 · The 7 primitives vs objects

Every JS value is either a primitive or an object. There are exactly seven primitive types — interviewers love asking you to list them:

PrimitiveExampleJava's nearest relativeNotes
string"hi", 'hi', `hi`StringImmutable, like Java's. No separate char type — a char is a string of length 1.
number42, 3.14, -0, NaNdoubleONE number type. No int/long/float split — everything is a 64-bit IEEE 754 double.
booleantrue, falsebooleanSame idea.
undefinedundefined(no equivalent)"No value was ever assigned." The default for uninitialized variables and missing things.
nullnullnull"Intentionally empty" — a value you assign to say "nothing here, on purpose."
symbolSymbol("id")(no equivalent)Guaranteed-unique identifier, used for special object keys. Details in Lesson 5.
bigint123nBigIntegerArbitrary-precision integers, for numbers beyond 253. Details in Lesson 5.

Everything else is an object — plain objects, arrays, functions, dates, regexes. Yes, arrays and functions are objects (we'll exploit that heavily in Lessons 2–4). The dividing line matters because primitives and objects behave differently when copied and compared — section 9 below. 

let s = "text";              // primitive: string
let n = 3.14;                // primitive: number
let nothingYet;              // primitive: undefined (declared, never assigned)
let cleared = null;          // primitive: null (deliberately empty)
let user = { name: "Krish" };// object
let list = [1, 2, 3];        // object (arrays are objects)
let f = function () {};      // object (functions are objects too)
undefined vs null — the interview classic undefined means "the language never got a value here" (unassigned variable, missing function argument, absent object property). null means "a programmer deliberately wrote 'nothing' here." Java only has the second concept. Rule of thumb: you read undefined, you write null.

4 · var, let, const — and why var is banished

JS has three ways to declare a variable, and the differences are a guaranteed interview topic because var (the original, pre-2015 keyword) has genuinely broken behavior that let/const fixed.

varletconst
ScopeFunction (ignores { } blocks!)Block { }, like JavaBlock { }, like Java
Redeclare in same scopeAllowed (silently!)SyntaxErrorSyntaxError
ReassignYesYesNo — TypeError
Use before declarationGives undefined (hoisted & auto-initialized)ReferenceError (TDZ)ReferenceError (TDZ)
VerdictLegacy — never write itWhen you must reassignDefault choice

Watch var ignore a block, which Java would never allow:

if (true) {
  var a = 1;     // var doesn't respect the block…
  let b = 2;     // let does, exactly like a Java local
}
console.log(a);  // 1 — leaked out of the if-block!
console.log(b);  // ReferenceError: b is not defined — Java-like, sane

One subtlety about const: it makes the binding constant, not the value. Like a Java final reference, you can't re-point it, but you can mutate the object it points to: 

const arr = [1, 2];
arr.push(3);       // fine — mutating the object the label points to
arr = [9, 9];      // TypeError — re-pointing the label is what's banned
Java parallel const ≈ final in Java: final List<Integer> list = new ArrayList<>() lets you list.add(3) but not list = otherList. Same rule, same reasoning: the variable is frozen, the object isn't. For a truly frozen object you'd need Object.freeze(obj) (Lesson 3).

5 · Hoisting and the Temporal Dead Zone

Before executing your code, the engine does a quick first pass over each scope and registers every declaration it finds. This is hoisting — it's as if declarations were moved to the top of their scope. The interview-grade detail is that var and let/const are hoisted differently:

  • var x is hoisted and initialized to undefined — so reading it early silently gives undefined.
  • let/const are hoisted but left uninitialized — the zone from the top of the scope until the declaration line is the Temporal Dead Zone (TDZ), and touching the variable there throws a ReferenceError.
console.log(a);  // undefined — var was hoisted and pre-set (silent, dangerous)
var a = 5;

console.log(b);  // ReferenceError — b exists but is in its TDZ (loud, safe)
let b = 5;

Why "temporal" (about time) and not "spatial" (about position)? Because what matters is whether the declaration has executed yet, not where the access sits in the file: 

function demo() {
  const read = () => value;  // written ABOVE the declaration — fine…
  let value = 10;
  return read();             // …because by the time this RUNS, the TDZ is over → 10
}
Interview one-liner "All declarations are hoisted. var is initialized to undefined during hoisting, so early access yields undefined. let/const are hoisted uninitialized, so early access throws — that window is the temporal dead zone. TDZ turns a silent bug into an immediate error, which is why it exists."

6 · Global, function, and block scope

Scope = the region of code where a name is visible. JS has three levels: 

let planet = "Earth";            // GLOBAL scope — visible everywhere below

function mission() {             // FUNCTION scope starts
  let crew = 4;                  // visible only inside mission()
  if (crew > 2) {                // BLOCK scope starts
    let status = "go";           // visible only inside this if-block
    console.log(planet, crew, status);  // inner scopes see outer names
  }
  // console.log(status);  → ReferenceError, block-scoped
}
// console.log(crew);      → ReferenceError, function-scoped

Inner scopes can read outer names; outer scopes can never see in. That nesting chain — each scope linking to the one that contains it in the source code — is called lexical scope, and it is the entire foundation of closures in Lesson 2.

One trap Java protects you from and JS doesn't: assigning to a name you never declared (outside strict mode) silently creates a global. score = 10 with no let pollutes the global object. Always declare; strict mode and modules (Lesson 8) make this an error, which is what you want.

7 · Type coercion, == vs ===, and truthy/falsy

Java refuses to compare an int with a String. JS, when types don't match, will convert one value to another type automatically and press on. That's implicit coercion, and it's the source of JS's most famous "wat" moments — and of a whole genre of interview questions.

Explicit conversion — you asking for it — is fine and normal:

Number("42")     // 42        string → number, on purpose
String(42)       // "42"      number → string
Boolean("")      // false     anything → boolean
Number("42px")   // NaN       not fully numeric → NaN (parseInt("42px") → 42; Lesson 5)

Implicit coercion — the engine deciding for you — is where care is needed:

"5" + 1     // "51"  — + with any string means CONCATENATE; 1 becomes "1"
"5" - 1     // 4     — minus is numbers-only, so "5" becomes 5
"5" * "2"   // 10    — same: both coerced to numbers
1 + true    // 2     — true coerces to 1
"" + 10     // "10"  — the old-school number→string trick

Now the headline act. JS has two equality operators. === (strict equality) compares type AND value, no conversions — behave like it's the only one. == (loose equality) first coerces the operands toward a common type, producing the classic weirdness: 

5 === "5"          // false — different types, end of story
5 == "5"           // true  — "5" is coerced to 5 first
0 == false         // true  — false coerces to 0
"" == 0            // true  — "" coerces to 0
null == undefined  // true  — special rule: these two match each other…
null == 0          // false — …but null matches NOTHING else
NaN == NaN         // false — NaN never equals anything, even itself (§8)
[] == false        // true  — [] → "" → 0, and false → 0. Yes, really.
Java parallel — but flipped! Careful: in Java, == on objects compares references and .equals() compares content — the danger there is == being too strict. In JS the danger is reversed: == is too loose. The safe habit in both worlds is the same: JS → always ===; Java → .equals() for objects. (JS === on two objects still compares references, like Java's == — Lesson 3.)

Related: wherever JS expects a boolean (an if condition, !, &&), it coerces the value. Values that coerce to false are falsy — and there are exactly 8 of them. Memorize this list; everything else is truthy: 

// THE 8 FALSY VALUES — everything not on this list is truthy
false        // the boolean itself
0            // zero
-0           // negative zero (a real, distinct value in IEEE 754)
0n           // BigInt zero
""           // empty string
null
undefined
NaN

// Frequent surprises — these are all TRUTHY:
if ("false") { }  // runs! non-empty string
if ([]) { }       // runs! an array is an object, all objects are truthy
if ({}) { }       // runs! same reason
if ("0") { }      // runs! non-empty string

This enables idioms you'll see everywhere: if (username) {...} means "if it's not empty/null/undefined," and !!value is the shorthand for converting anything to a real boolean.

Last syntax upgrade for this section — template literals, backtick strings with ${} holes. This is JS's answer to Java's String.format / +-chains, and it's what you should always use: 

const name = "Krish", cgpa = 6.78;
const msg = `Student ${name} has CGPA ${cgpa + 0.5} next sem?`;
// any expression works inside ${...}; multi-line strings work too:
const html = `<div>
  <p>${name}</p>
</div>`;

8 · typeof, its famous bug, and NaN

typeof is an operator that returns a value's type as a string — your runtime replacement for Java's compile-time knowledge:

typeof "hi"        // "string"
typeof 42          // "number"
typeof true        // "boolean"
typeof undefined   // "undefined"
typeof 10n         // "bigint"
typeof Symbol()    // "symbol"
typeof {}          // "object"
typeof []          // "object"  — arrays don't get their own answer; use Array.isArray()
typeof function(){} // "function" — the one object subtype with a special answer
typeof null        // "object"  ← THE FAMOUS BUG

typeof null === "object" is a mistake from JavaScript's very first implementation in 1995 (null's internal type tag looked like an object's). It can never be fixed — too much existing code depends on it — so it's frozen into the language and into interview question banks. To actually test for null: x === null.

NaN ("Not-a-Number") is what numeric operations return when they can't produce a meaningful number: 0/0, Number("abc"), Math.sqrt(-1). Two things to know cold: 

typeof NaN         // "number" — ironically, Not-a-Number IS of type number
NaN === NaN        // false — NaN is the only value not equal to itself (IEEE 754 rule)

// So how do you test for it?
Number.isNaN(NaN)     // true  — the correct tool: no coercion, exact check
Number.isNaN("abc")   // false — a string is not NaN, correctly
isNaN("abc")          // true?! — the OLD global isNaN coerces first ("abc"→NaN). Avoid it.
x !== x               // the cheeky interview trick: true ONLY when x is NaN
Gotcha Java's Double.NaN behaves identically (Double.NaN == Double.NaN is false there too) — both languages follow the IEEE 754 floating-point standard. If an interviewer springs "why isn't NaN equal to itself?", the answer is: the floating-point standard defines it that way, so that a failed computation can never accidentally compare equal to another failed computation.

9 · How values are copied — the "pass by value" truth

Here's the model that explains 90% of beginner JS bugs, and it should feel familiar from Java. Primitives are copied by value; objects are copied by reference-value — the variable holds an "address slip" pointing at the object on the heap, and copying the variable copies the slip, not the object: 

// PRIMITIVES: independent copies
let a = 10;
let b = a;         // b gets its own 10
b = 99;
console.log(a);    // 10 — untouched

// OBJECTS: copied address slip, ONE object
let u1 = { name: "Krish" };
let u2 = u1;       // u2 gets a copy of the ARROW, not the object
u2.name = "Kumar";
console.log(u1.name);  // "Kumar" — both slips point at the same heap object

Function calls follow the exact same rule — arguments are copies of what the variable holds:

function change(obj) {
  obj.name = "changed";   // follows the slip → mutates the SHARED object: caller sees it
  obj = { name: "new" };  // re-points the LOCAL copy of the slip: caller does NOT see it
}
let user = { name: "Krish" };
change(user);
console.log(user.name);   // "changed" — mutation leaked out, reassignment didn't

So is JS "pass by reference"? No — and neither is Java. Both are strictly pass-by-value; it's just that for objects, the value being passed is a reference. The litmus test: if reassigning the parameter inside the function (obj = ...) were visible to the caller, you'd have true pass-by-reference (like C++'s &). It isn't, in either language.

Interview one-liner "JavaScript is always pass-by-value. For primitives the value is the data itself; for objects the value is a reference, so mutations through the parameter are visible to the caller but reassigning the parameter is not. Java works exactly the same way."

10 · Interview questions this lesson answers

  • Q. "Is JavaScript compiled or interpreted?"
    Neither label fits cleanly: modern engines like V8 JIT-compile JS at runtime — parse, interpret hot-start, then compile hot paths to machine code, much like the JVM does with bytecode. There's just no separate compile step for the developer.
  • Q. "Difference between let, const and var?"
    var is function-scoped, allows redeclaration, and hoists initialized to undefined. let/const are block-scoped, forbid redeclaration, and hoist uninitialized (TDZ → ReferenceError on early use). const additionally forbids reassignment of the binding (not mutation of the object). Default to const, use let when reassigning, never var.
  • Q. "What is hoisting? What is the temporal dead zone?"
    During scope setup the engine registers all declarations before running code. var is also auto-initialized to undefined; let/const are registered but uninitialized, and the region before their declaration line executes is the TDZ, where any access throws. TDZ exists to make use-before-declare a loud error instead of a silent undefined.
  • Q. "Difference between == and ===?"
    === compares type and value with no conversion. == coerces operands to a common type first, giving surprises like 0 == "" being true. Special case worth citing: null == undefined is true, but neither loosely equals anything else. Always use ===.
  • Q. "What are the falsy values in JavaScript?"
    Exactly eight: false, 0, -0, 0n, "", null, undefined, NaN. Everything else — including "0", "false", [], and {} — is truthy.
  • Q. "What's the difference between null and undefined?"
    undefined = the language's "no value was assigned" (uninitialized variable, missing property/argument). null = the programmer's deliberate "empty". Bonus points: typeof null is "object" — a historical bug — while typeof undefined is "undefined".
  • Q. "Is JavaScript pass-by-value or pass-by-reference?"
    Pass-by-value, always. For objects the copied value is a reference, so callees can mutate the shared object but cannot re-point the caller's variable. Same as Java.
