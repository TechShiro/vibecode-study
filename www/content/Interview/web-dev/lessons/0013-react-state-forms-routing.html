Components you can build — now learn where state should live, how real forms work, and how one HTML page pretends to be a whole website.

1 · Lifting state up

Data flows down; so when two sibling components need the same data, neither can own it — a sibling can't pass props sideways. The rule: state lives in the closest common ancestor of everyone who needs it. The ancestor passes the value down to readers and a setter function down to writers.

Worked example — a search box and a results list, siblings under App:

function SearchBar({ query, onQueryChange }) {      // WRITER: gets value + setter
  return <input value={query} onChange={e => onQueryChange(e.target.value)} />;
}

function ResultsList({ products, query }) {         // READER: gets what it needs
  const visible = products.filter(p =>
    p.name.toLowerCase().includes(query.toLowerCase()));
  return <ul>{visible.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

function App() {
  const [query, setQuery] = useState('');           // state at the COMMON ANCESTOR
  return (
    <>
      <SearchBar query={query} onQueryChange={setQuery} />
      <ResultsList products={PRODUCTS} query={query} />
    </>
  );
}

Typing flows: input event → onQueryChange → setQuery in App → App re-renders → both children get the new query. One source of truth, two views of it. Reverse question is just as useful: if only SearchBar needed the text, push the state down into it — state as low as possible, as high as necessary.

2 · Derived state — compute, don't store

Notice visible above is a plain const computed during render — not state. If a value can be calculated from existing props/state, calculating it is always correct; storing a second copy invites the two copies to disagree. The classic anti-pattern is mirroring a prop into state: 

// ✘ ANTI-PATTERN: copying a prop into state
function Profile({ user }) {
  const [name, setName] = useState(user.name);   // initializer runs ONCE (mount)
  // parent later passes a new user → this state keeps the OLD name forever
}

// ✔ Just use the prop; derive during render
function Profile({ user }) {
  const displayName = user.name.toUpperCase();   // recomputed each render — always fresh
}
Interview one-liner "State should hold the minimal source of truth; everything computable from it is derived during render. Mirroring props into state is a bug because useState's initializer runs only on mount — later prop changes never reach the copy. If it's expensive to compute, wrap it in useMemo, don't promote it to state."

3 · Controlled vs uncontrolled inputs

An <input> has its own internal value in the DOM (that's how plain HTML forms work). React gives you a choice about who owns that value:

  • Uncontrolled: the DOM owns it; you peek when needed via a ref. Less code, less power.
  • Controlled: React state owns it. You set value={state} and update state onChange — the input displays state and only state. Now the current text is available every render: live validation, disabling submit, character counters, formatting-as-you-type.
// UNCONTROLLED — DOM owns the value; read it at submit time
function Uncontrolled() {
  const nameRef = useRef(null);
  const submit = e => { e.preventDefault(); console.log(nameRef.current.value); };
  return <form onSubmit={submit}><input ref={nameRef} defaultValue="Krish" /></form>;
}

// CONTROLLED — state owns the value; every keystroke round-trips through React
function Controlled() {
  const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />;
}

Each input type has its controlled wiring — note which prop carries the value:

<input value={text} onChange={e => setText(e.target.value)} />

<textarea value={bio} onChange={e => setBio(e.target.value)} />
                     // value prop, NOT children like in HTML

<select value={branch} onChange={e => setBranch(e.target.value)}>
  <option value="cse">CSE</option>
  <option value="it">IT</option>
</select>            // value on the SELECT, not `selected` on an option

<input type="checkbox" checked={agree}   // checkboxes use CHECKED (boolean)
       onChange={e => setAgree(e.target.checked)} />

<input type="radio" name="mode" value="dark"
       checked={mode === 'dark'}         // radio: checked = comparison
       onChange={e => setMode(e.target.value)} />

Gotcha: the frozen input <input value={name} /> with no onChange = an input you cannot type into. React re-renders it back to name after every keystroke. That's not a bug — it's the controlled contract: the DOM shows state and only state. React warns in the console and suggests defaultValue or readOnly if that's what you meant.

4 · A real form: multi-field state, validation, submit

Ten fields should not mean ten useState calls. Use one state object plus one handler keyed by the input's name attribute — computed property names from lesson 3 doing real work: 

function SignupForm() {
  const [form, setForm] = useState({ email: '', password: '', branch: 'cse', agree: false });
  const [errors, setErrors]       = useState({});
  const [submitting, setSubmitting] = useState(false);

  function handleChange(e) {
    const { name, type, value, checked } = e.target;
    setForm(f => ({
      ...f,                                          // keep the other fields (immutable update)
      [name]: type === 'checkbox' ? checked : value  // computed key = input's name
    }));
  }

  function validate(f) {
    const errs = {};
    if (!/^\S+@\S+\.\S+$/.test(f.email)) errs.email    = 'Enter a valid email';
    if (f.password.length < 8)           errs.password = 'Minimum 8 characters';
    if (!f.agree)                        errs.agree    = 'You must accept the terms';
    return errs;
  }

  async function handleSubmit(e) {
    e.preventDefault();                    // SPA: no full-page POST reload
    const errs = validate(form);
    setErrors(errs);
    if (Object.keys(errs).length > 0) return;
    setSubmitting(true);
    try {
      const res = await fetch('/api/signup', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(form),
      });
      if (!res.ok) throw new Error('Signup failed');
    } catch (err) {
      setErrors({ submit: err.message });
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <input name="email" type="email" value={form.email} onChange={handleChange} />
      {errors.email && <p className="error">{errors.email}</p>}

      <input name="password" type="password" value={form.password} onChange={handleChange} />
      {errors.password && <p className="error">{errors.password}</p>}

      <select name="branch" value={form.branch} onChange={handleChange}>
        <option value="cse">CSE</option><option value="it">IT</option>
      </select>

      <label>
        <input name="agree" type="checkbox" checked={form.agree} onChange={handleChange} />
        I accept the terms
      </label>
      {errors.agree && <p className="error">{errors.agree}</p>}

      <button disabled={submitting}>{submitting ? 'Creating…' : 'Sign up'}</button>
    </form>
  );
}

One handler serves every field; adding a field is one input plus one initial value. (In production apps you'll meet react-hook-form + zod, which package these patterns — but interviewers ask for exactly this hand-rolled version.)

5 · Prop drilling → Context, and its performance tax

From lesson 12: Context solves prop drilling — relay components passing props they never use. But it has a cost worth knowing precisely: when the provider's value changes, every consumer under it re-renders, whether it cares about the changed part or not. Two standard mitigations: 

// ✘ SMELL 1: one mega-context — theme change re-renders cart consumers too
<AppContext.Provider value={{ theme, user, cart, setTheme, setCart }}>

// ✔ FIX 1: split by change-frequency — consumers subscribe to what they need
<ThemeContext.Provider value={theme}>
  <UserContext.Provider value={user}>
    <CartContext.Provider value={cart}>…

// ✘ SMELL 2: fresh object literal as value — NEW reference every render of App,
// so ALL consumers re-render whenever App re-renders for ANY reason
<UserContext.Provider value={{ user, logout }}>

// ✔ FIX 2: memoize the value object (lesson 12's referential equality)
const userValue = useMemo(() => ({ user, logout }), [user, logout]);
<UserContext.Provider value={userValue}>

6 · Global state — Redux Toolkit and Zustand

The idea both share: move state out of the component tree into a store; components subscribe to just the slice they read, and re-render only when that slice changes — the precision Context lacks.

Redux is lesson 12's reducer pattern made global: one store, pure reducers, dispatched actions, plus dev-tools that time-travel through every action. Modern Redux is written with Redux Toolkit (RTK) — the old hand-written action-type constants and switch statements are legacy: 

npm i @reduxjs/toolkit react-redux
// store.js
import { configureStore, createSlice } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {                              // "mutating" style is SAFE here:
    added(state, action) {                 // RTK's Immer records these mutations
      state.items.push(action.payload);    // and produces an immutable copy
    },
    removed(state, action) {
      state.items = state.items.filter(i => i.id !== action.payload);
    },
  },
});

export const { added, removed } = cartSlice.actions;  // auto-generated creators
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

// main.jsx — provide the store like a context
<Provider store={store}><App /></Provider>

// Any component, any depth:
import { useSelector, useDispatch } from 'react-redux';
function CartButton({ product }) {
  const count    = useSelector(s => s.cart.items.length);  // re-renders ONLY if this changes
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(added(product))}>Add ({count})</button>;
}

Zustand gets you the same subscription precision with a fraction of the ceremony — a store is one function call, no provider needed: 

npm i zustand
import { create } from 'zustand';

const useCart = create((set) => ({
  items: [],
  add:    (p)  => set(s => ({ items: [...s.items, p] })),
  remove: (id) => set(s => ({ items: s.items.filter(i => i.id !== id) })),
}));

function CartButton({ product }) {
  const count = useCart(s => s.items.length);   // selector = subscribe to a slice
  const add   = useCart(s => s.add);
  return <button onClick={() => add(product)}>Add ({count})</button>;
}

Honest answer for interviews "Do you need Redux?" — often no. Start with local state; lift it when shared; context for low-churn globals; a store (Zustand, or RTK for big teams) when many components share fast-changing state. Saying the escalation ladder out loud beats name-dropping libraries.

7 · Server state vs client state — TanStack Query

Everything so far is client state — data your app owns (form text, open modal, cart). Data that lives on a server is different in kind: it can be stale the moment it arrives, others can change it, and you must handle caching, refetching, deduplication, and loading/error states. Your lesson-12 useFetch handles almost none of that. TanStack Query (React Query) is the standard tool for server state: 

npm i @tanstack/react-query
import { QueryClient, QueryClientProvider, useQuery } from '@tanstack/react-query';

const qc = new QueryClient();
// main.jsx: <QueryClientProvider client={qc}><App /></QueryClientProvider>

function Todos() {
  const { data, isPending, error } = useQuery({
    queryKey: ['todos'],                                   // cache key (like a Map key)
    queryFn: () => fetch('/api/todos').then(r => r.json()),
  });

  if (isPending) return <p>Loading…</p>;
  if (error)     return <p>Error: {error.message}</p>;
  return <ul>{data.map(t => <li key={t.id}>{t.title}</li>)}</ul>;
}

What you get over useEffect-fetch: a cache keyed by queryKey (two components asking for ['todos'] = one request, shared result); instant cached data on revisit with background refetch (stale-while-revalidate); automatic retries, deduplication, and refetch-on-window-focus; and useMutation with cache invalidation for writes. Rule of thumb worth quoting: server data belongs in a query cache, not in useState/Redux.

8 · React Router — many "pages", one page

An SPA never reloads, but users still expect URLs: bookmarkable, shareable, back-button-friendly. A router maps the URL to components, using the browser's History API to change the address bar without a page load. React Router v6+: 

npm i react-router-dom
import { createBrowserRouter, RouterProvider, Link, NavLink,
         Outlet, useParams, useNavigate } from 'react-router-dom';

function Layout() {                    // shared shell for all child routes
  return (
    <>
      <nav>
        <NavLink to="/">Home</NavLink>          {/* NavLink knows when it's active */}
        <NavLink to="/products">Products</NavLink>
      </nav>
      <Outlet />                       {/* ← the matched child route renders HERE */}
    </>
  );
}

function ProductPage() {
  const { id } = useParams();          // "/products/42" → id = "42" (a STRING)
  const navigate = useNavigate();      // imperative nav (after submit/login)
  const del = async () => { await api.remove(id); navigate('/products'); };
  return <><h1>Product {id}</h1><button onClick={del}>Delete</button></>;
}

const router = createBrowserRouter([
  {
    path: '/',
    element: <Layout />,
    children: [                                    // NESTED routes → render in Outlet
      { index: true,           element: <Home /> },        // matches "/" exactly
      { path: 'products',      element: <ProductList /> },
      { path: 'products/:id',  element: <ProductPage /> }, // :id = dynamic segment
      { path: '*',             element: <NotFound /> },    // 404 catch-all
    ],
  },
]);

export default function App() {
  return <RouterProvider router={router} />;
}

(The older JSX style — <BrowserRouter><Routes><Route path="/" element={...} /> — still works and appears in many codebases; createBrowserRouter is the recommended v6.4+ API and unlocks loaders/actions.) Key pieces: Link/NavLink instead of <a href> — they call preventDefault() and push History state instead of reloading; useParams reads dynamic segments; useNavigate navigates from code; nested routes + Outlet give persistent layouts (nav stays mounted while the page below swaps); path: '*' is your 404.

Gotcha: SPA routing vs real page loads A plain <a href="/products"> inside an SPA triggers a full page load — the entire JS bundle re-downloads, and all in-memory state (Redux store, form fields, everything) is wiped. Link only rewrites the URL and re-renders. Related deploy gotcha: refreshing the browser at /products/42 asks the server for that path — the server must be configured to return index.html for every route, or refreshes 404.

9 · Interview questions this lesson answers

  • "Two sibling components need the same data — what do you do?"
    Lift the state to their closest common ancestor; pass the value down to readers and a callback down to writers. State should live as low as possible but as high as necessary.
  • "Controlled vs uncontrolled components?"
    Controlled: React state is the single source of truth — value + onChange; enables live validation and dependent UI. Uncontrolled: the DOM owns the value; read via ref (defaultValue for initials). Default to controlled; file inputs are always uncontrolled.
  • "Why is copying props into state an anti-pattern?"
    The useState initializer runs only on mount, so later prop updates never reach the copy — two diverging sources of truth. Derive during render instead (useMemo if expensive).
  • "Context vs Redux?"
    Context is a transport, not a manager: any value change re-renders all consumers, and there's no update protocol or tooling. Stores (RTK/Zustand) hold state outside the tree with per-selector subscriptions, middleware, and devtools. Use context for low-churn globals; a store for shared fast-changing state.
  • "Why TanStack Query over fetching in useEffect?"
    Server state needs caching, deduplication, background refresh, retries, and invalidation-on-mutation — Query provides them keyed by queryKey. useEffect-fetch re-downloads on every mount and shares nothing between components.
  • "How does client-side routing work without reloads?"
    The router intercepts navigation, uses the History API (pushState) to change the URL, and swaps matched components. The server must serve index.html for all routes so deep links and refreshes work.
