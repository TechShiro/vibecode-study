React: Components, JSX, Props & State

In lesson 9 you hand-synced the DOM with your data and it hurt — React's entire job is to make that pain disappear with one idea: UI = f(state).

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 11 of 24. Index

1 · The problem React solves

Think back to your lesson-9 todo app. Your data was an array of todos. Your UI was a bunch of <li> elements. And your code's real job was keeping those two in sync by hand: 

// Lesson 9 style — IMPERATIVE: you describe every DOM surgery step
function addTodo(text) {
  todos.push({ text, done: false });      // 1. update the data
  const li = document.createElement('li'); // 2. now update the DOM to match...
  li.textContent = text;
  li.addEventListener('click', () => { /* toggle logic + classList surgery */ });
  list.appendChild(li);                    // 3. ...and hope you didn't miss a spot
}
function deleteTodo(i) {
  todos.splice(i, 1);
  list.children[i].remove();               // indexes must stay aligned FOREVER
  updateCounter();                         // oh right, the counter too
  toggleEmptyMessage();                    // oh right, the empty-state too
}

Every state change forces you to remember every place in the DOM that depends on it. With 3 features that's annoying; with 30 features it's a bug factory. The classes of bug are always the same: stale UI (data changed, screen didn't), double updates, and index drift between your array and the DOM children.

React's fix is radical: stop mutating the DOM yourself. Instead, write a function that answers one question — "given the current state, what should the UI look like?" — and let React figure out the minimal DOM surgery. 

// React style — DECLARATIVE: describe the END RESULT, not the steps
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map(t => <li key={t.id}>{t.text}</li>)}
    </ul>
  );      // change `todos`, and React re-runs this and patches the DOM diff
}

Interview one-liner "React is a library for building UIs declaratively: you express the UI as a function of state (UI = f(state)), and when state changes React re-renders that function and efficiently updates only the parts of the real DOM that changed. This removes the manual DOM-synchronisation bugs of imperative code."

2 · What's an SPA?

Traditional websites do a full page load per URL: every click asks the server for a whole new HTML document. A Single-Page Application loads one HTML shell plus a JavaScript bundle, and from then on JavaScript swaps content in and out of the page — navigation, forms, everything — talking to servers only for data (JSON via fetch, lesson 7), not for new pages. Result: app-like snappiness (Gmail, Twitter), at the cost of a bigger initial JS download and some SEO work (which Next.js solves in Module C). React is the most popular way to build the UI layer of an SPA.

3 · Setup with Vite

You met Vite as a dev server + bundler in lesson 8. It's also the standard way to start a React project:

npm create vite@latest my-app    # pick: React, then JavaScript
cd my-app
npm install                      # pulls react + react-dom (see package.json)
npm run dev                      # dev server at http://localhost:5173, hot reload

The anatomy that matters:

my-app/
├─ index.html          // the ONE html page of your SPA; has <div id="root"></div>
├─ package.json        // deps: react, react-dom; scripts: dev/build/preview
├─ vite.config.js      // tells Vite to transform JSX via the React plugin
└─ src/
   ├─ main.jsx         // entry point — mounts React into #root
   └─ App.jsx          // your top-level component
// src/main.jsx — the bridge between the real DOM and React-land
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root'))   // claim the #root div (lesson 9 API!)
  .render(<App />);                           // hand React the top component; it owns everything inside
Two packages, on purpose react is the core (components, hooks, the diffing model) and is platform-agnostic; react-dom is the renderer that targets the browser DOM. React Native swaps in a different renderer and keeps the same core — a nice separation-of-concerns point for interviews.

4 · JSX — HTML-looking function calls

JSX is not HTML and browsers can't run it. It's syntax sugar that Vite compiles into plain JavaScript function calls before the browser ever sees it: 

// What you write:
const el = <h1 className="title">Hello</h1>;

// What it compiles to (conceptually — React.createElement in the classic transform):
const el = React.createElement('h1', { className: 'title' }, 'Hello');

// Which just returns a plain JS object describing the UI (a "React element"):
{ type: 'h1', props: { className: 'title', children: 'Hello' } }

That object is cheap — no DOM involved. React collects these description objects and later decides what real DOM to build. This is why you can put JSX in variables, return it from functions, and pass it around: it's just data.

The rules, and why each exists:

  • One parent element per return. A function returns one value; createElement calls produce one object. Two siblings = two objects = illegal return. Wrap in a <div>, or in a fragment <>...</> which groups children without adding a DOM node.
  • className, not class; htmlFor, not for. JSX attributes become JS object keys, and class/for are reserved words in JS. Attributes are camelCase in general: onClick, tabIndex, readOnly.
  • {expression} embeds any JS expression. Braces are an escape hatch back into JS: {user.name}, {2 + 2}, {items.length}, {cond ? a : b}. Not statements — no if, no for inside braces (they don't produce values).
  • Every tag must close. <br />, <img />, <input /> — XML rules, because the compiler needs unambiguous trees.
  • Comments are JS comments inside braces: {/* like this */}.
function Profile() {
  const user = { name: 'Krish', college: 'NSUT', year: 3 };
  return (
    <>  {/* fragment: two siblings, zero extra DOM nodes */}
      <h2 className="name">{user.name}</h2>
      <p>{user.college} · year {user.year + 1} soon</p>
      <img src={user.avatarUrl} alt="avatar" />
    </>
  );
}
Java parallel A component returning JSX is like a toString() for UI: a pure description of "what I look like right now", produced fresh on demand. Nobody hand-edits the string returned by toString() — and in React, nobody hand-edits the DOM.

5 · Conditional rendering

Since JSX is expressions, conditionals use expression tools you already know from Module A:

function Inbox({ user, messages }) {
  // 1) EARLY RETURN — cleanest for "whole component differs"
  if (!user) return <p>Please log in.</p>;

  return (
    <div>
      {/* 2) TERNARY — choose between two pieces of UI */}
      {messages.length > 0 ? <MessageList msgs={messages} /> : <p>Inbox zero!</p>}

      {/* 3) && — render-or-nothing (lesson 1: short-circuit) */}
      {user.isAdmin && <AdminPanel />}

      {/* null / false / undefined render as NOTHING — that's why && works */}
    </div>
  );
}
Gotcha: the rendered 0 {messages.length && <List />} renders a literal 0 on screen when the array is empty! From lesson 1: && returns the first falsy value, and while false renders as nothing, the number 0 renders as "0". Fix: make the left side a real boolean — {messages.length > 0 && ...} — or use a ternary with null. A favourite React interview trick question.

6 · Rendering lists — map and keys

No for loops in JSX; you transform data into elements with .map() (lesson 4), because map is an expression that produces an array of elements — and JSX happily renders arrays: 

const todos = [
  { id: 'a1', text: 'Revise closures', done: true  },
  { id: 'b2', text: 'Build todo app',  done: false },
];

function TodoList() {
  return (
    <ul>
      {todos.map(t => (
        <li key={t.id}>{t.text}</li>   // key: a stable identity for THIS item
      ))}
    </ul>
  );
}

Why keys? When the list changes, React must match old elements to new ones to update the DOM minimally and to know which component's state belongs to which item. Keys are the name tags it matches by. Without them React falls back to matching by position — fine for static lists, wrong the moment you insert, delete, or reorder.

Gotcha: index as key todos.map((t, i) => <li key={i}>...) — the index IS the position, so "match by key" degrades into "match by position". Delete item 0 and every remaining item's key shifts by one: React thinks each item became its neighbour, so any per-item state (an input's text, a checkbox) stays at the old position and now sits next to the wrong data. Use a stable id from your data (t.id, a DB id, crypto.randomUUID() assigned at creation). Index is acceptable only for lists that never reorder/insert/delete. (Lesson 14 demos the bug.)

7 · Components, props & one-way data flow

A component is a function that takes an object of inputs (props) and returns JSX. Its name must start with a capital letter — that's how the compiler tells <App /> (call your function) apart from <div /> (build a DOM tag). Components compose exactly like functions calling functions: 

// A component is literally: props in, JSX out
function Badge({ label, color = 'gray' }) {   // destructuring + default (lessons 2, 4)
  return <span className={'badge ' + color}>{label}</span>;
}

function Card({ title, children, onClose }) { // children + a function prop
  return (
    <div className="card">
      <h3>{title} <Badge label="new" color="green" /></h3>
      {children}                              // whatever the caller nested inside
      <button onClick={onClose}>×</button>
    </div>
  );
}

// Usage — attributes become the props object; nested JSX becomes props.children
<Card title="Hello" onClose={() => console.log('closed')}>
  <p>This paragraph arrives as props.children.</p>
</Card>
// ≈ Card({ title: 'Hello', onClose: fn, children: <p>...</p> })

Three rules that keep React apps sane:

  • Props are read-only. A component must never mutate its props — same input, same output, like a pure function. If a child needs to change something, the parent passes down a function and the child calls it (that's onClose above). Java parallel: props are final constructor parameters; you don't reassign them, you ask the owner to change.
  • Data flows one way: down. Parents pass props to children. There's no "child writes to parent's variables". This makes bugs traceable — data has one owner and one direction.
  • children is just a prop — the JSX you nest between the tags. It's how you build wrapper components (cards, layouts, modals) that don't care what goes inside them.

8 · State — memory that survives re-renders

Props come from outside; state is a component's own memory that can change over time. A local variable won't do — the component function re-runs on every render, resetting locals. You need a value that (a) survives re-runs and (b) tells React "re-render me" when it changes. That's useState: 

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);   // array destructuring (lesson 4)
  // count    → current value for THIS render
  // setCount → asks React to store a new value AND re-render

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

Four things about state that trip everyone up:

// (1) setState does NOT change `count` immediately — it schedules a re-render
function handleClick() {
  setCount(count + 1);
  console.log(count);        // still the OLD value! count is a const in this run
}

// (2) updates are BATCHED — three calls, but count was 0 in all three expressions
setCount(count + 1);  // 0 + 1
setCount(count + 1);  // 0 + 1 again
setCount(count + 1);  // 0 + 1 again → final count: 1, one re-render

// (3) FUNCTIONAL UPDATE — "compute from the latest value", fixes (2)
setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);  // → 3. Use this whenever new state depends on old state.

(4) Objects and arrays in state must be replaced, never mutated. React decides whether to re-render by comparing old vs new state with Object.is — effectively a reference check (lesson 3!). Mutate the same object and the reference is unchanged, so React sees "same state, nothing to do": 

const [user, setUser]   = useState({ name: 'Krish', year: 3 });
const [todos, setTodos] = useState([]);

user.year = 4; setUser(user);              // BUG: same reference → no re-render

setUser({ ...user, year: 4 });             // ✔ new object via spread (lesson 4)

// The array patterns you'll use daily (all NON-mutating — lesson 4 table):
setTodos([...todos, newTodo]);                              // add
setTodos(todos.filter(t => t.id !== id));                   // delete
setTodos(todos.map(t =>                                     // update one
  t.id === id ? { ...t, done: !t.done } : t
));
// NEVER: todos.push(x), todos.splice(i,1), t.done = true  — mutations

9 · Events in React

Event handling looks like lesson 9 but with three differences: names are camelCase props (onClick, onChange, onSubmit); you pass a function reference, not a string; and the e you receive is a SyntheticEvent — React's cross-browser wrapper with the same interface (e.target, e.preventDefault()) as the native event (e.nativeEvent if you ever need the raw one). React actually attaches one real listener at the root and delegates — the pattern you hand-built in lesson 9, industrialised. 

<button onClick={handleClick}>ok</button>          // ✔ pass the function itself
<button onClick={handleClick()}>bad</button>       // ✘ CALLS it during render!
<button onClick={() => remove(t.id)}>del</button>  // ✔ need args? wrap in an arrow

<form onSubmit={e => { e.preventDefault(); save(); }}>  // stop the full-page reload

10 · Build it: counter → todo app

Everything above, in one runnable component. Replace App.jsx in a fresh Vite project with this:

import { useState } from 'react';

// Child component: pure — renders one todo, reports events UP via function props
function TodoItem({ todo, onToggle, onDelete }) {
  return (
    <li style={{ textDecoration: todo.done ? 'line-through' : 'none' }}>
      <input
        type="checkbox"
        checked={todo.done}
        onChange={() => onToggle(todo.id)}   // child ASKS, parent changes
      />
      {todo.text}
      <button onClick={() => onDelete(todo.id)}>✕</button>
    </li>
  );
}

export default function App() {
  const [todos, setTodos] = useState([]);   // the single source of truth
  const [text, setText]   = useState('');   // the input box's current value

  function addTodo(e) {
    e.preventDefault();
    if (!text.trim()) return;
    setTodos(ts => [...ts, { id: crypto.randomUUID(), text, done: false }]);
    setText('');                            // clear the box
  }
  const toggle = id =>
    setTodos(ts => ts.map(t => t.id === id ? { ...t, done: !t.done } : t));
  const remove = id =>
    setTodos(ts => ts.filter(t => t.id !== id));

  const remaining = todos.filter(t => !t.done).length;  // DERIVED — not state!

  return (
    <main>
      <h1>Todos ({remaining} left)</h1>
      <form onSubmit={addTodo}>
        <input value={text} onChange={e => setText(e.target.value)} />
        <button>Add</button>
      </form>
      {todos.length === 0
        ? <p>Nothing yet — add one!</p>
        : <ul>
            {todos.map(t => (
              <TodoItem key={t.id} todo={t} onToggle={toggle} onDelete={remove} />
            ))}
          </ul>}
    </main>
  );
}

Compare with the lesson-9 version: there is zero DOM manipulation code. No createElement, no appendChild, no counter-updating, no empty-message toggling. Every feature is "update the array immutably" — the counter, empty message, strikethrough, and list all follow, because they're all computed from todos during render. That's UI = f(state), earned.

Note the derived value remaining is calculated during render, not stored with useState. If you can compute it from existing state, don't make it state — duplicated state drifts out of sync. Lesson 13 turns this into a rule.

11 · Interview questions this lesson answers

  • "What is React and why use it over vanilla JS?"
    A declarative UI library: you describe UI as a function of state, and React syncs the real DOM efficiently on state changes. It removes manual DOM-sync bugs, gives reusable components, and scales to large apps.
  • "What is JSX? Is it HTML?"
    No — it's syntax sugar compiled to function calls (React.createElement-style) that return plain JS objects describing the UI. That's why it needs a build step, uses className, and embeds JS with braces.
  • "Props vs state?"
    Props are read-only inputs passed by the parent; state is the component's own mutable-over-time memory managed via useState. Both changing triggers a re-render; only the component itself sets its state.
  • "Why are keys needed in lists? Why is index a bad key?"
    Keys give list items stable identity so React can match old and new items across renders and preserve their state and DOM. Index equals position, so inserts/deletes/reorders shift keys and attach state to the wrong items.
  • "Why does console.log after setState show the old value?"
    The setter doesn't reassign the variable; it schedules a re-render. The current run keeps its snapshot of state. Batching also merges multiple setter calls — use functional updates when new state depends on old.
  • "Why must state be updated immutably?"
    React compares old and new state with Object.is (a reference check for objects). Mutating in place keeps the same reference, so React can't detect the change and skips the re-render.
