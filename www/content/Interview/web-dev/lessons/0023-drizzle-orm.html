Drizzle ORM: Schema, Migrations & Queries

Your SQL knowledge from Lessons 21–22 stays — Drizzle just teaches TypeScript to read it, so column typos die at compile time instead of 2 a.m. in production.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 23 of 24. Index

1 · The gap: SQL strings are invisible to TypeScript

In Lesson 22 you talked to Postgres from Node with the pg package and parameterized queries. That's correct and safe — but look at it through TypeScript's eyes: 

// Lesson 22 style — raw pg. Safe from injection, but...
const result = await pool.query(
  'SELECT id, usernme, email FROM users WHERE id = $1',  // typo: "usernme"
  [42]
);
const user = result.rows[0];      // type: any — TS has no idea what's inside
console.log(user.username.length); // compiles fine, EXPLODES at runtime

Three separate problems hide in those five lines:

  • The SQL is a string. To TypeScript it's just text. The typo usernme compiles happily and fails only when the query actually runs — maybe in production, on the one code path you didn't test.
  • No autocomplete. The editor can't suggest column names, because it can't see your database. You keep a mental copy of the schema and hope it's in sync.
  • Results are any. result.rows is untyped. Rename a column in the database and every query that reads the old name still compiles. The type system — the whole reason you learned TS in Lesson 20 — is switched off exactly where bugs are most expensive.
Java parallel Same story as raw JDBC: resultSet.getString("usernme") compiles and throws at runtime. Java's answer was Hibernate/JPA — mapped entity classes that the compiler can check. Tonight you meet the TypeScript generation's answer, which learned from Hibernate's mistakes.

2 · The options ladder: driver → query builder → ORM

There are three rungs between you and Postgres, each trading control for safety and convenience:

  1. Raw driver (pg) — you write SQL strings, you map rows by hand. Full control, zero help.
  2. Query builder — you compose SQL from functions (select().from().where()). The structure is checked, but often not the columns.
  3. ORM (Object-Relational Mapper) — a two-way translator: tables ↔ objects, SQL queries ↔ method calls. It knows your schema, so it can type your queries and your results.

The classic ORM promise: "never write SQL again." The classic ORM disease, which Java devs know from Hibernate: it's a leaky abstraction. Heavy ORMs generate SQL you can't predict, hide performance cliffs, and invite the N+1 problem — you fetch 100 users in one query, then the ORM lazily fires 100 more queries to fetch each user's posts. The database does 101 round trips where 1 join would do. Sooner or later you end up reading the generated SQL anyway — so the SQL knowledge from Lessons 21–22 was never optional.

Interview one-liner "An ORM maps tables to objects and queries to typed function calls. The tradeoff is abstraction leak: you gain type safety and productivity but can lose sight of the actual SQL — which is how N+1 query problems happen. That's why I like Drizzle: it's a thin, typed layer where each call maps to one predictable SQL statement."

3 · Why Drizzle (and an honest look at Prisma)

Drizzle sits deliberately on rung 2.5 — a typed query builder with ORM conveniences. Its pitch:

  • SQL-transparent. db.select().from(users).where(eq(users.id, 1)) — you can read the SQL right through it. "If you know SQL, you know Drizzle" is the actual slogan.
  • Fully typed. The schema lives in TypeScript, so queries and results are checked against it with zero code generation step.
  • Lightweight. A small library, no separate query engine process, minimal cold-start cost — which is why it's the favourite in serverless environments (Vercel, edge functions).

The other big name is Prisma — you'll see it in many job posts, so know both honestly:

Prisma in practice — enough to read (and pass an interview on) a Prisma codebase

Since half the job posts mention Prisma, here is the same "users and posts" world in Prisma, end to end. The workflow has three moving parts: a schema file in Prisma's own language, a generate step that builds a typed client, and that client as your query API. 

// prisma/schema.prisma — Prisma's own schema language (NOT TypeScript)
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

generator client {
  provider = "prisma-client-js"     // what `prisma generate` builds
}

model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  name  String?                     // ? = nullable
  posts Post[]                      // 1:N relation — a User has many Posts
}

model Post {
  id        Int      @id @default(autoincrement())
  title     String
  published Boolean  @default(false)
  author    User     @relation(fields: [authorId], references: [id])
  authorId  Int                     // the actual FK column
  createdAt DateTime @default(now())
}

The lifecycle after every schema change (compare with Drizzle's in section 7):

# 1. write/edit schema.prisma
npx prisma migrate dev --name add-posts   # diffs schema → writes SQL migration → applies it
npx prisma generate                        # (re)builds the typed client into node_modules
# prisma db push  = quick prototyping, no migration files (like drizzle-kit push)
# prisma studio   = a GUI to browse your tables in the browser

Querying — object-shaped instead of SQL-shaped:

import { PrismaClient } from '@prisma/client'
const prisma = new PrismaClient()

// CREATE — nested write creates the user AND a post in one call
const user = await prisma.user.create({
  data: {
    email: 'krish@example.com',
    name: 'Krish',
    posts: { create: [{ title: 'Hello Prisma' }] },
  },
})

// READ — where / orderBy / take map to WHERE / ORDER BY / LIMIT
const published = await prisma.post.findMany({
  where: { published: true, title: { contains: 'drizzle' } },
  orderBy: { createdAt: 'desc' },
  take: 10,
  include: { author: true },        // JOIN-ish: nests the related User — Prisma's N+1 killer,
})                                  // same job as Drizzle's `with:` in section 10

// UPDATE and DELETE
await prisma.post.update({ where: { id: 1 }, data: { published: true } })
await prisma.post.delete({ where: { id: 1 } })

// TRANSACTION — same bank-transfer shape as section 11
await prisma.$transaction(async (tx) => {
  await tx.account.update({ where: { id: 1 }, data: { balance: { decrement: 500 } } })
  await tx.account.update({ where: { id: 2 }, data: { balance: { increment: 500 } } })
})
Interview one-liner "I've used Drizzle, and I can read Prisma. The mental map: schema.prisma + generate ≈ Drizzle's TS schema with inference; migrate dev ≈ drizzle-kit generate + migrate; findMany({ include }) ≈ the relational query API's with. Same concepts, different dialect — the transferable skill is knowing what SQL you expect underneath."

4 · Setup: three packages and two files

Drizzle for Postgres needs the ORM, the driver you already know, and a CLI dev tool:

npm install drizzle-orm pg          # the ORM + the node-postgres driver from Lesson 22
npm install -D drizzle-kit @types/pg # CLI for migrations + TS types for pg (dev-only)

File 1 — drizzle.config.ts at the project root. This configures the CLI, not your app: where the schema lives, where migration files go, how to reach the database.

import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema: './src/db/schema.ts',      // where your tables are defined
  out: './drizzle',                  // generated migration .sql files land here
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,  // e.g. postgres://user:pass@localhost:5432/devlog
  },
});

File 2 — src/db/index.ts, the client your app imports. Note it's the same Pool from Lesson 22 — Drizzle wraps the driver, it doesn't replace it:

import { Pool } from 'pg';
import { drizzle } from 'drizzle-orm/node-postgres';
import * as schema from './schema';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// passing the schema unlocks the relational query API (section 10)
export const db = drizzle(pool, { schema });
TS rust? Recap pointer Everything here uses TypeScript from Lesson 20's primer — interfaces, generics, inference, ! non-null assertion. If any syntax looks alien, skim that primer again before continuing; Drizzle is 90% "TypeScript doing its inference thing."

5 · Schema in TypeScript

Here is the users/posts schema from Lesson 21 rebuilt as code. Each pgTable call mirrors a CREATE TABLE — same constraints, new spelling: 

// src/db/schema.ts
import {
  pgTable, serial, integer, text, varchar, boolean,
  timestamp, uuid, jsonb, pgEnum, index, uniqueIndex,
} from 'drizzle-orm/pg-core';

// CREATE TYPE role AS ENUM ('user', 'admin');
export const roleEnum = pgEnum('role', ['user', 'admin']);

export const users = pgTable('users', {
  id: serial('id').primaryKey(),                       // SERIAL PRIMARY KEY
  username: varchar('username', { length: 50 }).notNull().unique(),
  email: text('email').notNull().unique(),
  role: roleEnum('role').notNull().default('user'),
  isActive: boolean('is_active').notNull().default(true),
  profile: jsonb('profile'),                           // flexible extras — Lesson 22 rules apply
  createdAt: timestamp('created_at', { withTimezone: true })  // timestamptz — always
    .notNull().defaultNow(),
});

export const posts = pgTable('posts', {
  id: uuid('id').primaryKey().defaultRandom(),         // uuid PK this time, for contrast
  title: varchar('title', { length: 200 }).notNull(),
  body: text('body').notNull(),
  authorId: integer('author_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),  // FK + ON DELETE CASCADE
  publishedAt: timestamp('published_at', { withTimezone: true }),  // nullable = draft
}, (table) => [
  index('posts_author_idx').on(table.authorId),        // CREATE INDEX — FK columns, Lesson 22!
]);

Mapping table, SQL ↔ Drizzle:

Gotcha Two names per column: the TS property (isActive, camelCase, what your code uses) and the SQL column name ('is_active', snake_case, what Postgres stores). Drizzle translates between them. Mixing them up — writing is_active in a query — is a compile error, which is exactly the point.

6 · The payoff: $inferSelect and $inferInsert

Because the schema is TypeScript, Drizzle can hand you the row types for free — no interface written by hand, no codegen: 

export type User = typeof users.$inferSelect;
// { id: number; username: string; email: string; role: 'user' | 'admin';
//   isActive: boolean; profile: unknown; createdAt: Date }

export type NewUser = typeof users.$inferInsert;
// id, createdAt, role, isActive become OPTIONAL — they have defaults.
// username and email stay REQUIRED — notNull with no default.

Now the Lesson-22 horror scene replays with a different ending:

const u = await db.select().from(users);  // u: User[] — automatically
console.log(u[0].usernme);
// ^ TS error: Property 'usernme' does not exist on type 'User'.
//   Did you mean 'username'? — caught BEFORE the code ever runs

And it's alive: add a column to pgTable and every query in the codebase that's now wrong turns red in the editor. Your schema and your types cannot drift apart, because they are the same file.

Interview one-liner "Drizzle's schema is TypeScript, so row types are inferred — $inferSelect for reads, $inferInsert for writes, with defaulted columns optional on insert. A column typo or a schema change becomes a compile error instead of a runtime crash."

7 · Migrations: generate vs push

Lesson 22 ended on migrations as a concept: schema changes as versioned files, replayable in order on any database. drizzle-kit makes that real. The professional workflow: 

npx drizzle-kit generate   # diff schema.ts vs previous snapshot → writes ./drizzle/0001_xyz.sql
npx drizzle-kit migrate    # run pending .sql files against DATABASE_URL, record them as applied

The generated file is plain SQL you can read — and you should read it before applying, every time:

-- drizzle/0000_flat_wolverine.sql (generated)
CREATE TYPE "role" AS ENUM('user', 'admin');
CREATE TABLE "users" (
  "id" serial PRIMARY KEY NOT NULL,
  "username" varchar(50) NOT NULL,
  "email" text NOT NULL,
  ...
  CONSTRAINT "users_username_unique" UNIQUE("username")
);

The shortcut, npx drizzle-kit push, skips files entirely and syncs the live database to match schema.ts right now. Faster for toy projects — but there's no history, no review step, and no replayable record for teammates or production.

generate + migratepush
Produces SQL files?Yes — versioned, reviewable, committed to gitNo — applies changes directly
History/replayable?Yes, in order, on any environmentNo
Best forReal projects, teams, productionSolo prototyping, throwaway experiments
Gotcha Migration files are append-only history. Never edit an already-applied migration to "fix" it — change schema.ts and generate a new migration. Editing history breaks every database that already ran the old version. (Same rule as never rewriting pushed git commits.)

8 · Queries: CRUD, typed end to end

Every operator is an imported function — that's how the type checking reaches inside your WHERE:

import { eq, ne, gt, lt, like, ilike, inArray, and, or, desc, count } from 'drizzle-orm';
import { db } from './db';
import { users, posts } from './db/schema';

INSERT — with multi-row and RETURNING, just like Lesson 21:

// INSERT INTO users (username, email) VALUES ($1, $2) RETURNING *
const [krish] = await db.insert(users)
  .values({ username: 'krish', email: 'krish@nsut.ac.in' })  // NewUser — checked!
  .returning();                    // without this, inserts return nothing useful

await db.insert(users).values([   // multi-row: pass an array
  { username: 'asha', email: 'asha@example.com' },
  { username: 'ravi', email: 'ravi@example.com', role: 'admin' },
]);

SELECT — read the SQL through it:

// SELECT * FROM users WHERE role = 'admin' AND is_active = true
// ORDER BY created_at DESC LIMIT 10 OFFSET 0
const admins = await db.select().from(users)
  .where(and(eq(users.role, 'admin'), eq(users.isActive, true)))
  .orderBy(desc(users.createdAt))
  .limit(10).offset(0);

// partial select — SELECT id, username FROM users; result type shrinks to match
const names = await db.select({ id: users.id, username: users.username }).from(users);

// more operators, mapping straight to Lesson 21 WHERE clauses
await db.select().from(users).where(ilike(users.email, '%@nsut.ac.in'));  // ILIKE
await db.select().from(users).where(inArray(users.id, [1, 2, 3]));        // IN (…)
await db.select().from(posts).where(gt(posts.publishedAt, new Date('2026-01-01')));

UPDATE / DELETE / COUNT:

// UPDATE users SET is_active = false WHERE id = $1 RETURNING *
const [updated] = await db.update(users)
  .set({ isActive: false })
  .where(eq(users.id, krish.id))
  .returning();

// DELETE FROM posts WHERE author_id = $1
await db.delete(posts).where(eq(posts.authorId, krish.id));

// SELECT count(*) FROM users
const [{ value: total }] = await db.select({ value: count() }).from(users);
Gotcha Just like raw SQL, db.update(...) and db.delete(...) with no .where() hit every row. Drizzle won't stop you — the Lesson 21 forgot-the-WHERE horror story is alive and well one abstraction level up. And under the hood every one of these calls becomes a parameterized $1, $2 query, so the SQL-injection door from Lesson 22 stays closed by default.

9 · Joins and the nested result shape

leftJoin works exactly like Lesson 21's LEFT JOIN, with one surprise in the result shape: instead of one flat row, you get one object per table, and the right side is null where the join found no match — the typed version of the NULL-padded row: 

// SELECT * FROM users LEFT JOIN posts ON posts.author_id = users.id
const rows = await db.select().from(users)
  .leftJoin(posts, eq(posts.authorId, users.id));

// rows: Array<{ users: User; posts: Post | null }>
for (const row of rows) {
  console.log(row.users.username, row.posts?.title ?? '(no posts yet)');
}

One row per user-post pair, so a user with three posts appears three times — same as raw SQL. Grouping pairs into "user with posts array" is your job... or the next section's.

10 · The relational query API — killing N+1 boilerplate

For the everyday "give me users with their posts, nested" case, Drizzle has a second API. First declare how tables relate (this is metadata for queries — the real FK lives in the table definition): 

// at the bottom of schema.ts
import { relations } from 'drizzle-orm';

export const usersRelations = relations(users, ({ many }) => ({
  posts: many(posts),                // one user → many posts
}));

export const postsRelations = relations(posts, ({ one }) => ({
  author: one(users, {               // each post → one user
    fields: [posts.authorId],
    references: [users.id],
  }),
}));

Then — remember we passed { schema } to drizzle() in section 4 — query nested data in one call:

const activeUsers = await db.query.users.findMany({
  where: (u, { eq }) => eq(u.isActive, true),
  columns: { id: true, username: true },     // only these user columns
  with: {
    posts: {                                 // nest each user's posts inside
      columns: { id: true, title: true },
      limit: 5,
    },
  },
});
// type: Array<{ id: number; username: string;
//               posts: Array<{ id: string; title: string }> }>

Why this matters: the naive hand-rolled version is the N+1 bug — fetch N users, then loop and fire one posts query per user. Drizzle compiles with into a single SQL statement, so you get the nested shape your React components want, at one-round-trip cost, with full types.

Interview one-liner "N+1 is when an ORM fetches a list in 1 query, then lazily fires N more for each item's relations. The fix is eager loading — a join or a nested-select API like Drizzle's with — so it's one round trip instead of N+1."

11 · Transactions in Drizzle

The Lesson 22 bank transfer — two updates that must both happen or neither — translates directly. db.transaction runs your callback between BEGIN and COMMIT; any thrown error triggers ROLLBACK automatically: 

await db.transaction(async (tx) => {          // BEGIN
  // inside, use tx exactly like db — same API, same types
  const [from] = await tx.update(accounts)
    .set({ balance: sql`${accounts.balance} - 500` })
    .where(eq(accounts.id, 1))
    .returning();

  if (from.balance < 0) {
    throw new Error('insufficient funds');    // → ROLLBACK, nothing saved
  }

  await tx.update(accounts)
    .set({ balance: sql`${accounts.balance} + 500` })
    .where(eq(accounts.id, 2));
});                                            // callback returns → COMMIT
Gotcha Use tx, not db, for every query inside the callback. A db.update(...) inside the transaction body runs on a different pooled connection, outside the transaction — it commits even when the transaction rolls back. Classic, painful, silent bug. (That sql template tag is Drizzle's escape hatch for raw SQL fragments — still parameterized, still safe.)

12 · Wiring it in: Express and Next.js

Express — in Lesson 18 your service layer held an in-memory array. That was the point of layering: only the service changes, routes and controllers don't notice: 

// services/posts.service.ts — before: const posts = []; now:
import { db } from '../db';
import { posts } from '../db/schema';
import { eq } from 'drizzle-orm';

export const postsService = {
  findAll: () => db.select().from(posts),
  findOne: async (id: string) => {
    const [post] = await db.select().from(posts).where(eq(posts.id, id));
    return post ?? null;                    // controller turns null into 404, as before
  },
  create: async (data: typeof posts.$inferInsert) => {
    const [created] = await db.insert(posts).values(data).returning();
    return created;
  },
};

Next.js — server components (Lesson 15) run on the server, so they can query the database directly, no API route in between. Mutations go in a server action (Lesson 16) that revalidates: 

// app/posts/page.tsx — a server component; async and DB access are fine here
import { db } from '@/db';

export default async function PostsPage() {
  const allPosts = await db.query.posts.findMany({
    with: { author: { columns: { username: true } } },
  });
  return (
    <ul>
      {allPosts.map((p) => (
        <li key={p.id}>{p.title} — {p.author.username}</li>
      ))}
    </ul>
  );
}
// app/posts/actions.ts — a server action for the mutation
'use server';
import { revalidatePath } from 'next/cache';
import { db } from '@/db';
import { posts } from '@/db/schema';

export async function createPost(formData: FormData) {
  await db.insert(posts).values({
    title: String(formData.get('title')),
    body: String(formData.get('body')),
    authorId: 1,                          // real app: from the session (Lesson 19)
  });
  revalidatePath('/posts');               // refresh the cached listing
}

That is the whole track connected: React renders, Next.js decides where, Drizzle types the query, Postgres stores the truth. Lesson 24 assembles exactly this into one small complete app.

13 · Interview questions this lesson answers

  • "What is an ORM and what are its tradeoffs?"
    An ORM maps database tables to objects and SQL to typed function calls, giving type safety, autocomplete, and less boilerplate. Tradeoffs: it's a leaky abstraction — generated SQL can be inefficient or surprising (N+1 queries), and you still need SQL knowledge to debug it. Thin, SQL-transparent ORMs like Drizzle minimize the leak.
  • "What is the N+1 query problem?"
    Fetching a list with 1 query, then triggering N additional queries — one per item — for related data. Fixed with eager loading: a join, or a nested-relations API (Drizzle's with) that compiles to a single statement.
  • "Drizzle vs Prisma — how do you choose?"
    Prisma: schema in its own DSL, a generate step, object-style queries, heavier client. Drizzle: schema in plain TS with instant inference, SQL-shaped queries, thin and serverless-friendly. Both mainstream; I pick Drizzle when I want to see the SQL and keep the runtime light.
  • "How do migrations work in your project?"
    Schema changes are edits to schema.ts; drizzle-kit generate diffs that against the last snapshot and emits a versioned SQL file, which is reviewed, committed, and applied with migrate in each environment. push exists for prototyping but keeps no history.
  • "How does Drizzle prevent SQL injection?"
    Every query compiles to a parameterized statement — values travel as $1, $2 parameters, never concatenated into SQL text. Even the raw sql template tag parameterizes its interpolations.
  • "How do you run a transaction in an ORM?"
    db.transaction(async (tx) => ...) — the callback runs inside BEGIN/COMMIT; a thrown error rolls back. All queries inside must go through tx so they share the transaction's connection.
