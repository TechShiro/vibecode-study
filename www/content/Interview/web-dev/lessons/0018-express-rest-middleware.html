Express: REST APIs & Middleware

Last lesson you built an HTTP server with your bare hands — now meet the framework that turns those 60 lines of routing pain into 6, and the one concept (middleware) that powers every Node backend you'll ever touch.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 18 of 24. Index

1 · From raw http to Express — what exactly does it abstract?

In Lesson 17 you wrote this kind of thing with the core http module: 

// Lesson 17 flashback — raw http server. Every server is ONE giant callback.
import http from "node:http";

const server = http.createServer((req, res) => {
  // 1. Routing by hand: if-else on method + URL string parsing
  if (req.method === "GET" && req.url === "/notes") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify([{ id: 1, text: "hi" }]));
  } else if (req.method === "POST" && req.url === "/notes") {
    // 2. Body parsing by hand: collect stream chunks, join, JSON.parse, try/catch
    let body = "";
    req.on("data", chunk => body += chunk);
    req.on("end", () => { /* parse, validate, respond... */ });
  } else {
    res.writeHead(404); res.end("Not found");
  }
});
server.listen(3000);

That works, but three chores repeat in every route and grow ugly fast:

  • Routing — matching method + URL, extracting /notes/42-style params with regex.
  • Parsing — reading the body stream, parsing JSON, parsing the query string.
  • Chaining cross-cutting logic — logging, auth, error handling that must run for many routes without copy-paste.

Express is a thin layer over http.createServer that industrialises exactly these three things. It is not a different server — under the hood the same req and res objects from Lesson 17 flow through, just decorated with helper methods. That's why understanding raw http first was worth it: nothing Express does is magic to you now.

Java parallel Raw http is like writing a server on bare java.net.ServerSocket / com.sun.net.httpserver. Express is roughly the Servlet API + a routing layer — comparable to Spark Java or a very stripped-down Spring MVC. It gives you routing and request/response conveniences but no opinions about architecture (NestJS, Lesson 20, adds the Spring-style opinions).

Compare with Lesson 17: no manual writeHead, no if-else ladder. app.listen literally calls http.createServer(app).listen(...) for you — app itself is a valid request handler function.

3 · Routing: methods, params, queries, and the req/res API

app.get("/notes", handler);        // read collection
app.post("/notes", handler);       // create
app.get("/notes/:id", handler);    // :id is a PATH PARAM — matches /notes/42, /notes/abc
app.put("/notes/:id", handler);    // full replace
app.patch("/notes/:id", handler);  // partial update
app.delete("/notes/:id", handler); // delete

Path params identify a resource; query strings tweak how you read it (filters, sorting, paging):

// GET /notes/42?fields=text  →  params and query are pre-parsed objects
app.get("/notes/:id", (req, res) => {
  req.params.id;      // "42" — ALWAYS a string, convert with Number() yourself
  req.query.fields;   // "text"  (Lesson 17 made you parse this with URLSearchParams)
});

// GET /notes?done=true&sort=createdAt&page=2
app.get("/notes", (req, res) => {
  const { done, sort, page = "1" } = req.query;  // destructuring + default, Lesson 4 style
});

The response helpers you'll use daily:

res.send("text or html or Buffer");        // guesses Content-Type
res.json({ ok: true });                    // JSON.stringify + Content-Type: application/json
res.status(201).json(newNote);             // chainable — set code, then body
res.sendStatus(204);                       // status + standard text, no body
res.set("X-Request-Id", "abc");            // response header
req.get("Authorization");                  // read a request header (case-insensitive)
res.redirect(301, "/v2/notes");            // Location header + status
Gotcha Sending a response does not stop your function. After res.json(...), code keeps running — and a second res.send throws "Cannot set headers after they are sent" (you met the reason in Lesson 17: headers go out first on the wire, and the stream is finished). Habit: return res.status(404).json(...) — the return is for control flow, Express ignores the return value.

4 · REST, done properly

REST (REpresentational State Transfer) is not a library — it's a set of conventions for using HTTP the way it was designed. The core idea: your API exposes resources (nouns: notes, users, orders), and the HTTP verb carries the action. You never write /getNotes or /deleteNote?id=5 — the verb is already in the request line.

VerbMeaningIdempotent?Typical success
GETRead; never changes state (safe)Yes200 with body
POSTCreate a new resource / trigger an actionNo — repeat = duplicate201 + Location header
PUTReplace the whole resource at that URLYes — same body twice = same state200 or 204
PATCHPartial update (only sent fields change)Usually yes in practice, not guaranteed200
DELETERemove the resourceYes — deleting twice leaves same state204, no body

Idempotency — the interview word — means doing it N times has the same effect as doing it once. It matters because networks fail: if a client times out and retries, retrying a PUT or DELETE is harmless, but retrying a POST can create two orders. That's why payment APIs make you send an "idempotency key" with POSTs.

Interview one-liner "PUT replaces the entire resource and is idempotent; PATCH modifies part of it. GET is safe (no side effects) and idempotent; POST is neither, which is why browsers warn you before re-submitting a form."

Status codes that actually matter

CodeNameWhen to use it
200OKSuccessful GET/PUT/PATCH with a response body
201CreatedSuccessful POST; ideally include the new resource + Location header
204No ContentSuccess, nothing to say — typical for DELETE
301Moved PermanentlyResource lives at a new URL forever; browsers cache it
400Bad RequestMalformed request — broken JSON, missing required field
401UnauthorizedMisnamed — really "unauthenticated": who are you? No/invalid credentials
403ForbiddenI know who you are, and you're still not allowed (authorization failure)
404Not FoundNo such resource (also used to hide resources you can't reveal exist)
409ConflictState clash — e.g. registering an email that already exists
422Unprocessable EntitySyntax fine, semantics wrong — validation failures (many teams use 400 instead; pick one, be consistent)
500Internal Server ErrorYour bug. Never leak stack traces to clients

URL design + versioning glance

GET    /api/v1/notes            // plural nouns, lowercase, hyphens if multiword
GET    /api/v1/notes/42
GET    /api/v1/users/7/notes    // nesting shows ownership — keep it max 2 levels
GET    /api/v1/notes?done=true&page=2&limit=20   // filtering/paging = query, not path

// BAD: verbs in URLs, singular/plural chaos
POST   /api/createNote
GET    /api/note_list

The /v1/ prefix is URL versioning — the most common scheme. When you must break the contract (rename fields, change shapes), you ship /v2/ alongside and let old clients keep working. Alternatives (header-based, media-type versioning) exist; know they exist, use URL versioning in projects.

5 · Middleware — THE core concept

Everything in Express is middleware. A middleware is just a function with the signature (req, res, next). Express keeps an ordered list of them; each request walks the list top to bottom. Each function can: (a) do work (log, parse, attach data to req), then call next() to pass the baton; or (b) end the story by sending a response; or (c) call next(err) to jump to error handling.

Mental model: an assembly line — or, closer to home, exactly the Servlet Filter chain from Java: doFilter(request, response, chain) where you call chain.doFilter(...) to continue. Same pattern, same "order matters" rule, same use cases (auth, logging, compression). 

// A logger middleware — runs for EVERY request because of app.use
function logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next();                                   // forget this and the request HANGS forever
}

// A timer — shows the trick of hooking the response 'finish' event
function timer(req, res, next) {
  const start = Date.now();
  res.on("finish", () => {                  // res is a stream (Lesson 17!) — it emits events
    console.log(`  → ${res.statusCode} in ${Date.now() - start}ms`);
  });
  next();
}

app.use(logger);          // ORDER MATTERS: these run in registration order
app.use(timer);
app.use(express.json());  // built-in: parses JSON bodies into req.body

app.get("/notes", (req, res) => res.json(notes));  // a route handler is just the LAST middleware
Gotcha Register express.json() after your routes and req.body is undefined inside them — the pipeline already reached the route before the parser existed in its path. "Middleware order bug" is the single most common beginner Express bug, and a favourite debugging interview question.

The built-ins you actually use

  • express.json() — reads the body stream, JSON.parses it, sets req.body. (This is the chore you did by hand in Lesson 17.)
  • express.urlencoded({ extended: true }) — parses classic HTML form posts (a=1&b=2).
  • express.static("public") — serves files from a folder (images, a built React app) with correct MIME types and caching headers.

Route-level and third-party middleware

// Route-level: runs only for this route — perfect for auth on specific endpoints
function requireAuth(req, res, next) {
  if (!req.get("Authorization")) return res.status(401).json({ error: "Login required" });
  next();
}
app.delete("/notes/:id", requireAuth, deleteNote);   // any number of middlewares before the handler

// Mount-path: runs only for URLs starting with /admin
app.use("/admin", requireAuth);

// Third-party: npm install morgan cors
import morgan from "morgan";
import cors from "cors";
app.use(morgan("dev"));    // battle-tested request logger (more in Lesson 19)
app.use(cors());           // cross-origin headers (explained properly in Lesson 19)
Interview one-liner "Middleware is a function (req, res, next) in a pipeline. Each one can transform the request, end the response, or pass control with next(); next(err) skips ahead to error-handling middleware. Order of registration is order of execution — it's Chain of Responsibility, the same pattern as Java's servlet filters."

6 · express.Router — modular routes

One file with 40 app.get(...) calls doesn't scale. A Router is a mini-app: it has its own middleware and routes, and you mount it at a prefix. 

// src/routes/notes.routes.js
import { Router } from "express";
const router = Router();

router.get("/", listNotes);        // paths are RELATIVE to the mount point
router.post("/", createNote);
router.get("/:id", getNote);

export default router;

// server.js
import notesRouter from "./src/routes/notes.routes.js";
app.use("/api/v1/notes", notesRouter);   // router.get("/") now serves GET /api/v1/notes

7 · Project structure — routes / controllers / services

This is the layered architecture you already know from Java, with different hats:

LayerJobJava / Spring equivalent
RouteMap URL + verb → controller function; attach route middleware@RequestMapping annotations / web.xml
ControllerHTTP translation only: pull data from req, call service, pick status code, send response@RestController
ServiceBusiness logic, knows nothing about HTTP — pure functions on data@Service
Data layerTalks to the DB (arrives in Lessons 21–23)@Repository / DAO

Why keep controllers thin? Because business logic buried in a controller is welded to Express — you can't unit-test it without faking req/res, can't reuse it from a CLI script or a cron job, and can't swap Express for Nest later. A service that takes plain arguments and returns plain values is trivially testable. Exactly the reason Spring separates @RestController from @Service.

8 · Error handling — the 4-arg middleware

Express treats a middleware with four parameters — (err, req, res, next) — as an error handler. Arity is the signal; the names don't matter, the count does. Whenever any middleware calls next(err) or a synchronous handler throws, Express skips every normal middleware and jumps to the first 4-arg one. That gives you a single centralized place to convert errors into HTTP responses — the equivalent of Spring's @ControllerAdvice + @ExceptionHandler. 

// src/middleware/error.js
export class ApiError extends Error {            // custom error carrying a status (Lesson 9 custom errors)
  constructor(status, message) {
    super(message);
    this.status = status;
  }
}

export function notFound(req, res, next) {       // 404 catcher: mounted AFTER all routes,
  next(new ApiError(404, `No route: ${req.method} ${req.originalUrl}`));  // reached only if nothing matched
}

export function errorHandler(err, req, res, next) {   // FOUR args = error middleware
  const status = err.status ?? 500;
  if (status >= 500) console.error(err);         // log real bugs server-side...
  res.status(status).json({                      // ...but never leak stack traces to the client
    error: status >= 500 ? "Internal server error" : err.message,
  });
}

The async trap

In Express 4, a rejected promise inside an async handler is not caught — the request hangs and the error escapes. Two fixes: 

// Fix 1 (Express 4): a tiny wrapper that forwards rejections to next()
const asyncWrap = (fn) => (req, res, next) => fn(req, res, next).catch(next);

app.get("/notes/:id", asyncWrap(async (req, res) => {
  const note = await notesService.getById(req.params.id);   // throws ApiError(404) if missing
  res.json(note);
}));

// Fix 2: Express 5 (now the default on npm) catches async rejections automatically —
// a thrown/rejected error in an async handler goes straight to your error middleware.
Gotcha Mount order for the endgame is fixed: all routes → notFound → errorHandler. Put errorHandler before the routes and it never sees their errors; forget notFound and unknown URLs get Express's default HTML error page instead of your JSON.

9 · Validation — never trust input

Everything in req.body, req.params, req.query comes from a stranger's keyboard (or a script). Types are wrong, fields are missing, extra fields smuggle in. Validating at the boundary — before the service runs — is non-negotiable in real APIs. The modern choice is zod: you declare a schema, and it both validates and strips unknown fields. (express-validator is the older chain-style alternative.) 

npm install zod
// src/middleware/validate.js — a reusable schema-checking middleware FACTORY
export const validate = (schema) => (req, res, next) => {
  const result = schema.safeParse(req.body);     // safeParse never throws — returns a result object
  if (!result.success) {
    return res.status(422).json({
      error: "Validation failed",
      details: result.error.issues.map(i => `${i.path.join(".")}: ${i.message}`),
    });
  }
  req.body = result.data;                        // parsed + cleaned: unknown keys removed, defaults applied
  next();
};

// src/schemas/notes.schema.js
import { z } from "zod";
export const createNoteSchema = z.object({
  text: z.string().min(1).max(500),
  done: z.boolean().default(false),
});

// wire it: router.post("/", validate(createNoteSchema), createNote);

11 · Capstone: a full in-memory notes CRUD API

Every file, wired together. This exact shape is what you'll rebuild in NestJS in Lesson 20, line-by-line comparable.

// ── src/services/notes.service.js — pure logic, zero HTTP knowledge
import { ApiError } from "../middleware/error.js";

let notes = [{ id: 1, text: "Learn Express", done: false }];
let nextId = 2;

export const notesService = {
  list()          { return notes; },
  getById(id) {
    const note = notes.find(n => n.id === id);
    if (!note) throw new ApiError(404, `Note ${id} not found`);
    return note;
  },
  create(data)    {
    const note = { id: nextId++, ...data };
    notes.push(note);
    return note;
  },
  update(id, data) {                       // PATCH semantics: merge only sent fields
    const note = this.getById(id);         // reuse → 404 for free
    Object.assign(note, data);
    return note;
  },
  remove(id) {
    this.getById(id);
    notes = notes.filter(n => n.id !== id);
  },
};
// ── src/controllers/notes.controller.js — HTTP translation only, stays THIN
import { notesService } from "../services/notes.service.js";
import { ApiError } from "../middleware/error.js";

const parseId = (raw) => {
  const id = Number(raw);
  if (!Number.isInteger(id) || id <= 0) throw new ApiError(400, "id must be a positive integer");
  return id;
};

export const listNotes  = (req, res) => res.json(notesService.list());
export const getNote    = (req, res) => res.json(notesService.getById(parseId(req.params.id)));
export const createNote = (req, res) =>
  res.status(201).json(notesService.create(req.body));            // 201 for creation
export const updateNote = (req, res) =>
  res.json(notesService.update(parseId(req.params.id), req.body));
export const deleteNote = (req, res) => {
  notesService.remove(parseId(req.params.id));
  res.sendStatus(204);                                            // 204: success, no body
};
// ── src/routes/notes.routes.js
import { Router } from "express";
import { listNotes, getNote, createNote, updateNote, deleteNote } from "../controllers/notes.controller.js";
import { validate } from "../middleware/validate.js";
import { createNoteSchema, updateNoteSchema } from "../schemas/notes.schema.js";

const router = Router();
router.get("/", listNotes);
router.post("/", validate(createNoteSchema), createNote);
router.get("/:id", getNote);
router.patch("/:id", validate(updateNoteSchema), updateNote);
router.delete("/:id", deleteNote);
export default router;

// updateNoteSchema (add to notes.schema.js): all fields optional for PATCH
// export const updateNoteSchema = createNoteSchema.partial();
// ── server.js — composition root: everything mounts here, in the right ORDER
import express from "express";
import morgan from "morgan";
import notesRouter from "./src/routes/notes.routes.js";
import { notFound, errorHandler } from "./src/middleware/error.js";

const app = express();

app.use(morgan("dev"));                    // 1. logging first — sees everything
app.use(express.json());                   // 2. body parsing before any route needs req.body

app.use("/api/v1/notes", notesRouter);     // 3. feature routes

app.use(notFound);                         // 4. nothing matched → 404
app.use(errorHandler);                     // 5. all errors funnel here — LAST

app.listen(3000, () => console.log("API on http://localhost:3000"));

12 · Interview questions this lesson answers

  • "What is middleware in Express?"
    A function (req, res, next) in an ordered pipeline that every request flows through. It can modify req/res, end the response, or call next() to continue (or next(err) to reach error handlers). Registration order is execution order. Used for parsing, logging, auth, CORS — it's the Chain of Responsibility pattern.
  • "PUT vs PATCH vs POST?"
    POST creates (not idempotent), PUT replaces the whole resource at a known URL (idempotent), PATCH partially updates. Idempotent = repeating the request leaves the same final state, which makes retries safe.
  • "401 vs 403?"
    401 Unauthorized = not authenticated (we don't know who you are / bad token). 403 Forbidden = authenticated but not allowed (we know exactly who you are, and the answer is still no).
  • "How does Express error handling work?"
    A middleware with four parameters (err, req, res, next) is an error handler. next(err) or a throw skips all normal middleware and jumps there. Centralize it last in the stack; in Express 4, async errors need a wrapper that .catch(next)es (Express 5 forwards async rejections automatically).
  • "Why separate controllers from services?"
    Controllers translate HTTP ↔ function calls; services hold business logic with no HTTP knowledge. That makes logic unit-testable without mocking req/res, reusable outside HTTP, and framework-swappable — the same reason Spring separates @RestController from @Service.
  • "What does express.json() do and why does its position matter?"
    It's built-in middleware that reads the request body stream, parses JSON, and sets req.body. It must be registered before any route that reads req.body, because the pipeline runs in order.
