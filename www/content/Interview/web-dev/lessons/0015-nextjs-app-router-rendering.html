Next.js: App Router & Rendering Models

Your React app grows a server — and suddenly SEO, fast first paint, secret keys, and routing all come for free. The catch: you must learn where the server ends and the client begins.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 15 of 24. Index

1 · The wall your Vite SPA hits

Everything you built in Module B is a Single-Page Application: Vite serves one nearly empty HTML file, the browser downloads a JavaScript bundle, and React builds the whole page in the browser. That works — until four real-world problems show up: 

<!-- what a crawler (or a slow phone) receives from a Vite SPA -->
<!DOCTYPE html>
<html>
  <body>
    <div id="root"></div>   <!-- empty. All content arrives later, via JS -->
    <script src="/assets/index-abc123.js"></script>
  </body>
</html>
  • SEO. Search crawlers and link previews (WhatsApp, LinkedIn) see that empty div. Your product pages may never rank; shared links show no title or image.
  • First paint. The user stares at a blank screen until the bundle downloads, parses, and runs — brutal on slow networks.
  • No server code. Where do you put your database password or Stripe secret key? Not in the bundle — everything you ship to the browser is public. A SPA forces you to build and host a separate backend just to hide secrets.
  • Hand-rolled routing. React Router works, but you configured every route, every code-split, every 404 by hand. Conventions beat configuration at scale.
Java parallel Plain React is like the Servlet API: powerful primitives, zero opinions — you wire everything yourself. Next.js is React's Spring Boot: a framework layered on the library that adds routing conventions, a server, build tooling, and production defaults, so you write features instead of plumbing.

2 · What Next.js actually is

Next.js is a full-stack React framework. It runs your React components in two places: on a Node.js server (to produce real HTML before the browser sees anything) and in the browser (to make the page interactive). On top of that it bundles in:

  • File-based routing — folders and files are your routes.
  • Server-side rendering — real HTML on first load → SEO and fast first paint solved.
  • Server code in the same repo — data fetching, secrets, even API endpoints live beside your components.
  • Built-in optimization — images, fonts, code-splitting, caching, all by default.

Since Next 13, the recommended way to build is the App Router (the app/ directory). The older Pages Router (pages/) still exists in many codebases — Lesson 16 gives you the interview-level mapping. Everything in this lesson is App Router, Next 14/15 era.

4 · File conventions: page, layout, loading, error

In the App Router, folders define URL segments, and special file names give each segment behaviour. A folder becomes a real page only when it contains a page.js.

FileRoleNotes
page.jsThe UI for this route — makes the segment publicly reachableExactly one per route
layout.jsShared shell wrapping this segment and all childrenPersists across navigation — does not re-render or lose state
loading.jsInstant fallback shown while the page's data loadsIt's an automatic Suspense boundary (Lesson 14 déjà vu)
error.jsError boundary for this segmentMust be a Client Component; receives error and reset
not-found.jsUI for 404s in this segmentTriggered by notFound() or unmatched URLs
template.jsLike layout, but remounts on every navigationRare — use for enter animations or per-page reset
route.jsAPI endpoint instead of a pageLesson 16
 
// app/layout.js — the ROOT layout. Required. Owns <html> and <body>.
export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>
        <nav>My Site</nav>
        {children}          {/* the current page renders here */}
      </body>
    </html>
  );
}

// app/page.js — the "/" route
export default function Home() {
  return <h1>Hello from the server</h1>;
}

Layouts nest. app/dashboard/layout.js wraps everything under /dashboard, inside the root layout. Crucially, when you navigate from /dashboard/sales to /dashboard/users, the dashboard layout does not remount — a sidebar's scroll position, an open dropdown, any useState inside the layout: all preserved. Only the changing page swaps. (A template.js in the same spot would remount — that's the whole difference.) 

// app/dashboard/error.js — catches render/data errors below it
'use client';                              // error boundaries need client-side JS

export default function Error({ error, reset }) {
  return (
    <div>
      <h2>Something broke: {error.message}</h2>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}

5 · Routing: dynamic segments, catch-alls, groups, navigation

app/
├── blog/
│   ├── page.js              // /blog
│   └── [id]/
│       └── page.js          // /blog/42  → params.id === "42"
├── docs/
│   └── [...slug]/
│       └── page.js          // /docs/a/b/c → params.slug === ["a","b","c"]
├── (marketing)/             // route GROUP — organizes files, invisible in URL
│   ├── about/page.js        // /about  (NOT /marketing/about)
│   └── pricing/page.js      // /pricing — can share a (marketing)/layout.js
// app/blog/[id]/page.js — dynamic segment value arrives via params
export default async function BlogPost({ params }) {
  const { id } = await params;   // Next 15: params is a Promise (Next 14: plain object)
  return <h1>Post #{id}</h1>;
}

Navigation has two faces — declarative links and imperative hooks:

import Link from 'next/link';

<Link href="/blog/42">Read post 42</Link>
// renders a real <a>, but intercepts the click: client-side transition,
// no full page reload. Next also PREFETCHES linked routes in the viewport.

// imperative navigation — client components only
'use client';
import { useRouter, usePathname } from 'next/navigation';

function LogoutButton() {
  const router = useRouter();
  const pathname = usePathname();          // current URL path, e.g. "/dashboard"
  return <button onClick={() => router.push('/login')}>Logout</button>;
}
Gotcha Import from next/navigation, not next/router — the latter is the old Pages Router API and throws in the App Router. And useRouter/usePathname are hooks, so they only work in Client Components — which brings us to the heart of this lesson.

6 · Server Components vs Client Components — the core idea

This is the App Router concept, and the #1 Next.js interview topic. In the App Router, every component is a Server Component by default. It runs on the server (at build time or per request), produces HTML plus a compact description of the UI, and — here's the kicker — its code is never shipped to the browser. Zero bundle cost.

A Client Component is one you opt into with the 'use client' directive at the top of the file. It is server-rendered to HTML once for fast first paint, then its JS is shipped and it hydrates — React attaches event listeners and state so it becomes interactive. "Client" doesn't mean "renders only in the browser"; it means "also ships JS to the browser". 

// SERVER component (default — no directive). Can be async! Can touch secrets!
import { db } from '@/lib/db';

export default async function ProductList() {
  const products = await db.query('SELECT * FROM products');  // direct DB access
  return (
    <ul>
      {products.map(p => <li key={p.id}>{p.name} — ₹{p.price}</li>)}
    </ul>
  );
}

// CLIENT component — needs state and click handlers
'use client';
import { useState } from 'react';

export default function AddToCart({ productId }) {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>In cart: {count}</button>;
}
CapabilityServer ComponentClient Component
Fetch data with async/await in the bodyYes — components can be asyncNo (use effects/libraries)
Read secrets, env vars, filesystem, databaseYes — code never reaches the browserNever — everything shipped is public
useState / useEffect / any hookNoYes
Event handlers (onClick, onChange)NoYes
Browser APIs (window, localStorage)NoYes (after hydration)
JS shipped to the browserNoneIts bundle + everything it imports
Interview one-liner "In the App Router, components are server-first: they render on the server and ship no JS. You add 'use client' only where you need interactivity — state, effects, events, browser APIs. Server components can be async and safely touch databases and secrets; client components hydrate in the browser and carry bundle cost. The skill is pushing 'use client' as far down the tree as possible."

7 · Where the boundary goes — composition & serialization

'use client' marks a boundary, not just one file. Everything a client component imports becomes part of the client bundle too. So the strategy is: keep pages and layouts as server components, and carve out small interactive leaves — a search box, a like button, a theme toggle — as client components.

One composition trick every interviewer loves: a client component can render server components — as long as they're passed in as children (or any prop), not imported. The server renders them first and hands the finished result through the "slot": 

// ClientTabs.js — client shell with a server-rendered slot
'use client';
import { useState } from 'react';

export default function ClientTabs({ children }) {
  const [open, setOpen] = useState(true);
  return (
    <div>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      {open && children}   {/* server-rendered content passes through untouched */}
    </div>
  );
}

// app/page.js — SERVER component composes them
import ClientTabs from './ClientTabs';
import ProductList from './ProductList';   // server component with DB access

export default function Page() {
  return (
    <ClientTabs>
      <ProductList />      {/* rendered on the server, slotted into the client shell */}
    </ClientTabs>
  );
}
Gotcha — props must cross a wire Props passed from a server component to a client component travel over the network as part of the RSC payload, so they must be serializable: plain objects, arrays, strings, numbers, booleans are fine; functions, class instances, DB handles are not. Passing onClick={someFn} from a server component to a client component is a build error. (The one blessed exception: Server Actions — Lesson 16.)
Java parallel Think of the server/client boundary like a remote call in a Java system: whatever crosses it must be serializable, exactly like objects crossing RMI or a REST boundary must map to JSON. A Connection object can't go over the wire in Java; a DB handle can't go into a client component's props in Next.

You need to…Use
Fetch data, render lists/articles, read env secrets, query the DBServer Component

Use localStorage, geolocation, media APIs, useRouterClient Component

9 · Metadata API — SEO, finally solved

Remember problem #1 from section 1? Because Next renders on the server, it can put real <title> and <meta> tags in the HTML before any crawler arrives. Two flavours: 

// STATIC metadata — export a plain object from a page or layout
export const metadata = {
  title: 'Qhess — Quantum Chess',
  description: 'Chess, but every piece is in superposition.',
};

// DYNAMIC metadata — computed per request from params
export async function generateMetadata({ params }) {
  const { id } = await params;
  const post = await getPost(id);
  return {
    title: post.title,                       // /blog/42 gets ITS OWN title
    description: post.summary,
    openGraph: { images: [post.coverUrl] },  // the WhatsApp/LinkedIn preview card
  };
}

Titles from nested layouts and pages merge (a layout can define title: { template: '%s | Qhess' } and each page fills the %s). This is why SEO matters for placements too: "how do you make a React app SEO-friendly?" is a stock interview question, and "server-side rendering + the Metadata API" is the modern answer.

10 · next/image and next/font, briefly

import Image from 'next/image';
import { Inter } from 'next/font/google';

const inter = Inter({ subsets: ['latin'] });

<Image src="/hero.png" alt="Board" width={800} height={400} />
  • next/image replaces <img>: it resizes and serves modern formats (WebP/AVIF) on demand, lazy-loads offscreen images, and requires width/height so the layout never jumps while loading (no layout shift).
  • next/font downloads the font at build time and self-hosts it — no request to Google at runtime, no flash of unstyled text, better privacy.

Name-drop both when asked "what does Next optimize for you?" — images, fonts, code-splitting per route, and prefetching of <Link>s.

11 · Interview questions this lesson answers

  • Q. "Why use Next.js over plain React?"
    Plain React (Vite SPA) ships an empty HTML page and renders in the browser: bad SEO, slow first paint, no place for server code or secrets, hand-rolled routing. Next adds server rendering, file-based routing, server-side data access, and built-in optimization — a full-stack framework on top of the React library.
  • Q. "Server Components vs Client Components?"
    Server components are the default: they render on the server, can be async and touch databases/secrets, and ship zero JS. Client components opt in with 'use client' for state, effects, events, and browser APIs; they're server-rendered once, then hydrate. Push 'use client' to the leaves.
  • Q. "What does 'use client' actually mark?"
    A module-level boundary. That file and everything it imports joins the client bundle. Props crossing into it must be serializable — no functions or class instances (Server Actions excepted).
  • Q. "Can a client component contain a server component?"
    Not by importing it — that would drag it into the client bundle. But yes via composition: a server component passes an already-rendered server component into the client component as children.
  • Q. "layout vs template?"
    Both wrap child routes. A layout persists across navigation (state, scroll survive); a template remounts on every navigation. Default to layouts; templates are for per-page resets/animations.
  • Q. "How is SEO handled in Next?"
    Server rendering delivers full HTML to crawlers, and the Metadata API (metadata object or generateMetadata) sets per-route titles, descriptions, and Open Graph tags.
