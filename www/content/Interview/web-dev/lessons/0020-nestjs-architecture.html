NestJS: Modules, DI & the Request Pipeline

Express gave you total freedom; Nest takes some back and hands you Spring Boot for Node in exchange — for a Java developer, this is the framework where everything suddenly feels like home.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 20 of 24. Index

1 · A compact TypeScript primer — enough to read Nest

Nest is TypeScript-first, and so is Drizzle in Lesson 23 — so ten minutes here pays twice. TypeScript = JavaScript + a static type layer that is erased at compile time: tsc type-checks, then emits plain JS. Nothing about the runtime changes; you already know the runtime. For your Java brain: it's the compile-time safety of javac bolted onto the JS you learned in Lessons 1–10 — but structural ("has the right shape") rather than nominal ("declared as the right class"). 

// Type annotations — after the name, unlike Java's before
let title: string = "Qhess";
let count: number = 3;                // one number type — no int/double split
let tags: string[] = ["chess", "quantum"];
let maybe: string | null = null;      // UNION types — no Java equivalent; like Optional but built into the type

// Functions: parameter types + return type. ? marks optional params.
function clamp(x: number, max: number, min?: number): number {
  return Math.min(max, Math.max(min ?? 0, x));
}

// Interfaces describe SHAPES (like Java interfaces, but no class needs to 'implements' them —
// any object with matching members qualifies: structural typing, "duck typing checked at compile time")
interface Note {
  id: number;
  text: string;
  done: boolean;
}
const n: Note = { id: 1, text: "hi", done: false };  // ✓ shape matches

// Generics — same idea and even similar syntax as Java's <T>
function firstOrNull<T>(arr: T[]): T | null {
  return arr.length ? arr[0] : null;
}
const x = firstOrNull<Note>([n]);     // x: Note | null — usually inferred, no need to write <Note>

// Enums — a glance; Nest code prefers union-of-literals, which does the same job lighter
enum Role { User = "user", Admin = "admin" }
type RoleLite = "user" | "admin";

Decorators — the syntax Nest is built on

A decorator — @Something() above a class, method, property, or parameter — is just a function that receives the thing it decorates and may register metadata about it or wrap it. If it looks exactly like Java annotations, that's the point: @Controller() plays the role of @RestController. One real difference: Java annotations are passive metadata read via reflection; TS decorators are functions that execute when the class is defined. 

function Logged(target: any, key: string, desc: PropertyDescriptor) {
  const original = desc.value;                    // the method being decorated
  desc.value = function (...args: any[]) {        // replace it with a wrapper
    console.log(`calling ${key}`);
    return original.apply(this, args);
  };
}

class Greeter {
  @Logged                                          // applied once, at class-definition time
  hello(name: string) { return `hi ${name}`; }
}
Java parallel Annotation-driven frameworks translate one-to-one: @Component→@Injectable(), @RestController→@Controller(), @GetMapping→@Get(), @RequestBody→@Body(), @PathVariable→@Param(). When Nest code looks foreign, ask "what would this be in Spring?" — the answer is almost always right.

2 · Why Nest exists

Express is deliberately unopinionated: it gives you routing and middleware and no answer to "where does code go, how do classes get their dependencies, how do we test this?" Every Express team invents its own architecture — you hand-built one in Lesson 18 (routes/controllers/services), and you also hand-wired every dependency yourself. On a 10-person team, five private conventions collide.

NestJS ships the opinions: an Angular/Spring-style architecture on top of Express (or Fastify) with modules for organization, a dependency-injection container for wiring, first-class TypeScript, and dedicated slots (pipes/guards/interceptors/filters) for every cross-cutting concern. If Express is a bag of excellent parts, Nest is Spring Boot: the parts pre-arranged, opinionated, and test-friendly.

4 · Building blocks: modules, controllers, providers

Modules — the unit of organization

import { Module } from "@nestjs/common";

@Module({
  imports: [],                    // other modules whose EXPORTS we want to use
  controllers: [NotesController], // HTTP endpoints owned by this module
  providers: [NotesService],      // injectable classes the container should instantiate
  exports: [NotesService],        // what other modules may inject — everything else is PRIVATE
})
export class NotesModule {}

Every Nest app is a graph of modules with AppModule at the root. Providers are encapsulated: UsersModule can inject NotesService only if NotesModule exports it and UsersModule imports NotesModule. That's enforced architecture — Java packages plus JPMS-style explicit exports, per feature.

Controllers — routing via decorators

import { Controller, Get, Post, Body, Param, Query } from "@nestjs/common";

@Controller("notes")                         // base path: /notes
export class NotesController {
  constructor(private readonly notesService: NotesService) {}  // DI — next section

  @Get()                                     // GET /notes
  list(@Query("done") done?: string) {       // @Query pulls from the query string
    return this.notesService.list();         // return a value — Nest serializes to JSON, sets 200
  }

  @Get(":id")                                // GET /notes/42
  getOne(@Param("id") id: string) {
    return this.notesService.getById(Number(id));
  }

  @Post()                                    // POST /notes → Nest defaults POST to 201 automatically
  create(@Body() dto: CreateNoteDto) {
    return this.notesService.create(dto);
  }
}

Note the shift from Express: no req/res in sight. Parameter decorators (@Body(), @Param(), @Query()) extract exactly what you declare, and returning a value replaces res.json(...). Handlers become plain, easily-tested methods — exactly Spring MVC's @RequestBody/@PathVariable model.

Providers — anything injectable

import { Injectable, NotFoundException } from "@nestjs/common";

@Injectable()                                // marks the class as container-managed — Spring's @Service/@Component
export class NotesService {
  private notes = [{ id: 1, text: "Learn Nest", done: false }];

  getById(id: number) {
    const note = this.notes.find(n => n.id === id);
    if (!note) throw new NotFoundException(`Note ${id} not found`);  // → 404, see filters
    return note;
  }
}

5 · Dependency injection, deeply

In Lesson 18 your controller imported its service directly — the controller chose and constructed its own dependency. Inversion of Control flips that: classes only declare what they need (in the constructor), and a container — Nest's IoC container, same job as Spring's ApplicationContext — builds the object graph and hands each class its dependencies. "Don't call us, we'll call you." 

constructor(private readonly notesService: NotesService) {}
// TS shorthand: declares the field AND assigns it. The TYPE ANNOTATION is the lookup token —
// decorator metadata lets Nest read "NotesService" at runtime and inject the singleton instance.

What actually happens at bootstrap:

  • Nest walks the module graph and collects every class listed in providers.
  • For each, it inspects constructor parameter types, resolves those first (recursively), then instantiates — by default one singleton per provider, like Spring's default bean scope.
  • Circular or missing dependencies fail loudly at startup — wiring bugs die before the first request.

Why does DI matter for testing? Because the class never hard-codes new NotesService(), tests can hand it a fake: 

// notes.controller.spec.ts — swap the real provider for a stub, zero HTTP involved
const moduleRef = await Test.createTestingModule({
  controllers: [NotesController],
  providers: [{
    provide: NotesService,                             // the token...
    useValue: { list: () => [{ id: 1, text: "fake", done: false }] },  // ...bound to a mock
  }],
}).compile();

const controller = moduleRef.get(NotesController);
expect(controller.list()).toHaveLength(1);             // pure unit test — no server, no real service

6 · DTOs, ValidationPipe & pipes in general

A DTO (data-transfer object — the term is straight from Java) is a class that defines a request body's shape, with validation rules as decorators from class-validator: 

npm i class-validator class-transformer
// src/notes/dto/create-note.dto.ts — Bean Validation vibes: @NotBlank/@Size → @IsString/@Length
import { IsString, Length, IsBoolean, IsOptional } from "class-validator";

export class CreateNoteDto {
  @IsString()
  @Length(1, 500)
  text: string;

  @IsOptional()
  @IsBoolean()
  done?: boolean;
}

// update DTO: same fields, all optional — PartialType does it in one line
// export class UpdateNoteDto extends PartialType(CreateNoteDto) {}   (from @nestjs/mapped-types)
// main.ts — one global pipe replaces Lesson 18's hand-written zod middleware
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,             // strip properties not declared in the DTO (mass-assignment defence)
  forbidNonWhitelisted: true,  // ...or reject the request outright when extras appear
  transform: true,             // convert payloads into real DTO class instances (+ type coercion)
}));
// invalid body → automatic 400 with per-field messages. You wrote this by hand last lesson.

Generalizing: a pipe is a class that transforms or validates a handler's input just before the handler runs. ValidationPipe is one; ParseIntPipe is the other everyday one: 

@Get(":id")
getOne(@Param("id", ParseIntPipe) id: number) {   // "42" → 42; "abc" → automatic 400 Bad Request
  return this.notesService.getById(id);           // Lesson 18's parseId() helper, now declarative
}

7 · Guards — where auth lives

A guard answers one boolean question before the handler runs: may this request proceed? It implements CanActivate — this is Nest's slot for the JWT check you wrote as requireAuth middleware in Lesson 19, and the direct cousin of a Spring Security filter + @PreAuthorize. 

import { Injectable, CanActivate, ExecutionContext, UnauthorizedException } from "@nestjs/common";
import * as jwt from "jsonwebtoken";

@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest();       // the underlying Express req
    const token = req.headers.authorization?.replace("Bearer ", "");
    if (!token) throw new UnauthorizedException();          // → 401
    try {
      req.user = jwt.verify(token, process.env.JWT_SECRET!); // attach identity, like Lesson 19
      return true;                                          // true = proceed; false/throw = blocked
    } catch {
      throw new UnauthorizedException("Invalid or expired token");
    }
  }
}

@UseGuards(AuthGuard)          // per-handler, per-controller, or global — role guards read
@Get("secret")                 // custom @Roles() decorator metadata via Reflector, same slot
secret() { return "vip"; }

8 · Interceptors — around the handler

An interceptor wraps the handler like an around-advice in Spring AOP: code before, code after, and the power to transform the response. Classic uses: timing/logging, mapping every response into an envelope, caching. 

import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from "@nestjs/common";
import { map, tap } from "rxjs/operators";

@Injectable()
export class TimingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler) {
    const start = Date.now();                       // BEFORE the handler
    return next.handle().pipe(                      // handle() runs the rest of the pipeline
      tap(() => console.log(`took ${Date.now() - start}ms`)),   // AFTER
      map(data => ({ data, timestamp: Date.now() })),           // reshape every response body
    );
  }
}
// (next.handle() returns an RxJS Observable — think "a Promise with operators"; tap/map is all you need here)

9 · Exception filters — centralized errors

Nest ships HttpException subclasses — NotFoundException, UnauthorizedException, ConflictException… Throw them anywhere (service included) and the built-in global filter converts them to proper JSON responses; unrecognized errors become a safe 500. This replaces Lesson 18's hand-written ApiError + 4-arg error middleware, and mirrors Spring's @ControllerAdvice. A custom filter lets you own the format: 

import { Catch, ExceptionFilter, ArgumentsHost, HttpException } from "@nestjs/common";

@Catch(HttpException)                          // which exception types this filter handles
export class ApiExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    res.status(exception.getStatus()).json({
      error: exception.message,
      at: new Date().toISOString(),            // your envelope, your rules
    });
  }
}
// app.useGlobalFilters(new ApiExceptionFilter());

10 · Middleware in Nest — and how it differs

Express-style (req, res, next) middleware still exists in Nest, but it's demoted: it runs before routing, knows nothing about which handler will run, and can't use execution context metadata. Use it only for raw HTTP concerns (request logging, compression, helmet); use guards/pipes/interceptors for anything route-aware. Configuration happens in a module: 

export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(LoggerMiddleware).forRoutes("*");   // or specific paths/methods
  }
}

11 · THE interview question: the full request lifecycle

Every request walks a fixed pipeline. Memorize the order — Nest interviews ask it almost every time: 

  Request
    │
    ▼
  1. MIDDLEWARE            // raw req/res work, before routing (logging, helmet)
    │
    ▼
  2. GUARDS                // may you enter? auth/roles → 401/403 stop here
    │
    ▼
  3. INTERCEPTORS (pre)    // wrap begins — start timers, open spans
    │
    ▼
  4. PIPES                 // validate + transform the handler's inputs (DTOs, ParseIntPipe)
    │
    ▼
  5. HANDLER → SERVICE     // your controller method calls business logic
    │
    ▼
  6. INTERCEPTORS (post)   // wrap ends — stop timers, map/reshape the response
    │
    ▼
  7. EXCEPTION FILTERS     // only on a thrown exception, from ANY stage → error response
    │
    ▼
  Response

Walk one request through it: POST /notes with a JWT and {"text":"hi","hacker":"x"}:

  • Middleware logs POST /notes.
  • AuthGuard verifies the JWT, attaches req.user. Bad token? UnauthorizedException → straight to the filter, 401, stages 3–6 never run.
  • TimingInterceptor starts its stopwatch, calls next.handle().
  • ValidationPipe checks the body against CreateNoteDto, strips hacker (whitelist).
  • Handler runs, service creates the note, returns it.
  • Interceptor (post) logs the elapsed time, wraps the body in its envelope. Response: 201.
Interview one-liner "Middleware → guards → interceptors (pre) → pipes → handler → interceptors (post) → exception filters. Sanity check: it's need-order — you can't authorize before raw processing, can't validate input for a handler you're not allowed to reach, and errors from any stage short-circuit into the filters."

13 · The notes CRUD in Nest — compare with Lesson 18 line-by-line

Same resource you built in Express. Four files, generated by nest g resource notes in real life:

// ── src/notes/dto/create-note.dto.ts  (≙ Lesson 18's zod schema)
export class CreateNoteDto {
  @IsString() @Length(1, 500) text: string;
  @IsOptional() @IsBoolean() done?: boolean;
}
export class UpdateNoteDto extends PartialType(CreateNoteDto) {}

// ── src/notes/notes.service.ts  (≙ notes.service.js — logic is nearly identical)
@Injectable()
export class NotesService {
  private notes: Note[] = [{ id: 1, text: "Learn Nest", done: false }];
  private nextId = 2;

  list() { return this.notes; }
  getById(id: number) {
    const note = this.notes.find(n => n.id === id);
    if (!note) throw new NotFoundException(`Note ${id} not found`);  // was: throw new ApiError(404,...)
    return note;
  }
  create(dto: CreateNoteDto) {
    const note = { id: this.nextId++, done: false, ...dto };
    this.notes.push(note);
    return note;
  }
  update(id: number, dto: UpdateNoteDto) { return Object.assign(this.getById(id), dto); }
  remove(id: number) { this.getById(id); this.notes = this.notes.filter(n => n.id !== id); }
}

// ── src/notes/notes.controller.ts  (≙ routes file + controller file COMBINED — decorators route)
@Controller("notes")
export class NotesController {
  constructor(private readonly notesService: NotesService) {}   // was: import { notesService }

  @Get()    list() { return this.notesService.list(); }
  @Get(":id")  getOne(@Param("id", ParseIntPipe) id: number) { return this.notesService.getById(id); }
  @Post()   create(@Body() dto: CreateNoteDto) { return this.notesService.create(dto); }  // 201 auto
  @Patch(":id") update(@Param("id", ParseIntPipe) id: number, @Body() dto: UpdateNoteDto) {
    return this.notesService.update(id, dto);
  }
  @Delete(":id") @HttpCode(204)
  remove(@Param("id", ParseIntPipe) id: number) { this.notesService.remove(id); }

// ── src/notes/notes.module.ts  (≙ the app.use("/api/v1/notes", router) wiring)
@Module({ controllers: [NotesController], providers: [NotesService] })
export class NotesModule {}   // imported into AppModule; global prefix: app.setGlobalPrefix("api/v1")

What vanished from the Express version: manual body parsing setup, the zod middleware, parseId, the ApiError class, the 4-arg error handler, the 404 catcher, the asyncWrap — all replaced by framework slots. What appeared: classes, decorators, and one module file. That's the trade in miniature.

15 · Interview questions this lesson answers

  • "What is dependency injection and why does Nest use it?"
    Classes declare dependencies in their constructors; the IoC container instantiates and wires them (singletons by default). Benefits: decoupling, one obvious wiring mechanism, and testability — tests substitute providers via the container instead of monkey-patching imports. Same design as Spring's ApplicationContext.
  • "Explain the Nest request lifecycle."
    Middleware → guards → interceptors (pre) → pipes → handler → interceptors (post) → exception filters. Guards gate access, pipes validate/transform input, interceptors wrap around, filters catch anything thrown at any stage.
  • "Guard vs middleware vs interceptor vs pipe — when which?"
    Middleware: raw pre-routing req/res work (logging, helmet). Guard: boolean access decision (auth/roles). Pipe: validate/transform handler inputs (DTO validation, ParseIntPipe). Interceptor: around-logic — timing, response mapping, caching. Filter: exception → HTTP response.
  • "What does a decorator actually do?"
    It's a function applied to a class/method/property/parameter at definition time; it can attach metadata or wrap behavior. Nest's decorators mostly record metadata the framework reads to build routing and injection — like Java annotations, except decorators are executable functions rather than passive markers.
  • "What does ValidationPipe({ whitelist: true }) protect against?"
    Mass assignment: extra fields not declared in the DTO are stripped (or rejected with forbidNonWhitelisted), so a client can't smuggle role: "admin" into a create-user body.
  • "Why can't module B use a provider from module A?"
    Providers are module-scoped: A must list it in exports, and B must list A in imports. Encapsulation at the architecture level, enforced by the framework.
