React Performance & Internals

Pop the hood: what actually happens between setState and pixels — and the handful of tools that make slow React apps fast.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 14 of 24. Index

1 · What happens on setState — render phase, commit phase

You call setCount(1). Between that call and pixels changing, React runs two distinct phases:

  • Render phase: React calls your component function (and affected children). The output is a tree of those cheap element-description objects from lesson 11 — the virtual DOM. React then diffs this new tree against the previous one (reconciliation). No real DOM is touched. This phase must be pure — which is exactly why side effects are banned from render.
  • Commit phase: React applies the computed minimal set of changes to the real DOM ("change this text node, add that attribute, remove that li"), then runs effects (useLayoutEffect before paint, useEffect after).

Why bother with the middle-man tree? Because real DOM operations are the expensive part — each mutation can trigger style/layout work in the browser. Diffing plain JS objects is cheap. React spends cheap CPU comparing descriptions so it can spend expensive DOM operations only on what truly changed. The virtual DOM isn't "faster than the DOM" — it's a strategy for doing less DOM.

2 · Reconciliation — the diffing rules

A perfect tree-diff is O(n³); React gets O(n) with two blunt heuristics you must know:

  • Rule 1 — different type ⇒ tear down. If a position's element type changes (<div> → <span>, or <Sidebar /> → <Chat />), React doesn't look inside. It unmounts the whole old subtree — destroying its DOM and all its state — and mounts the new one fresh.
  • Rule 2 — same type ⇒ update in place. Same tag/component at the same position: React keeps the DOM node and the component's state, patches changed attributes/props, and recurses into children.
  • Lists — match by key. Among siblings, keys tell React which old child is which new child, so a reorder becomes "move these nodes" instead of "rewrite every one".

The reorder bug from lesson 11, now explainable end-to-end. Each row has its own state (an input):

function Row({ name }) {
  const [note, setNote] = useState('');            // per-row state
  return <li>{name}: <input value={note} onChange={e => setNote(e.target.value)} /></li>;
}

// key={i}: keys are 0,1,2. Type "boss" into Alice's input, then sort the array.
{people.map((p, i) => <Row key={i} name={p.name} />)}
// After sorting, position 0 STILL has key 0 → React says "same component,
// new name prop" → state `note`="boss" stays at position 0… under the wrong person.

// key={p.id}: React matches rows by identity, MOVES the DOM nodes,
// and "boss" travels with Alice wherever she sorts to. ✔
Fiber, honestly Since React 16, each element in the work-in-progress tree is a fiber — a plain JS object holding the component, its state, and links to parent/child/sibling. The point of the rewrite: rendering became a linked list of small work units instead of one deep recursion, so React can pause rendering, let urgent things (typing) run, and resume or discard the work — the foundation for the concurrent features in section 9. Commit is still synchronous. In an interview, one paragraph at this level is exactly enough.

3 · What actually triggers a re-render

Interview favourite, widely misunderstood. A component re-renders when:

  • Its own state changes (setter stores a value that fails Object.is vs the old one — same value = render skipped).
  • Its parent re-renders. By default React re-renders all children of a rendering component, whether their props changed or not.
  • A context it consumes changes value, or a subscribed external store slice changes (lesson 13).

Note what's missing: "its props changed" is not a trigger. Props can't change on their own — they're arguments computed by the parent's render. Prop changes and child re-renders are both consequences of the parent rendering. The default is: parent renders ⇒ children render, props or no props.

And usually — that's fine. A re-render is a cheap function call producing cheap objects; the expensive DOM part only happens for actual diffs. Re-renders are a problem only when they're expensive (heavy computation, huge lists) and frequent. Which brings us to the golden rule:

Measure first Open React DevTools → Profiler tab → record → interact → stop. Flame graph shows what rendered, how long it took, and why ("why did this render?" in settings). Optimize the slow thing it shows you — not the thing you guessed. Premature memo-everywhere adds comparison overhead and complexity for zero user-visible gain.

4 · React.memo — skipping unchanged children

React.memo(Component) wraps a component so that when its parent re-renders, React first shallow-compares old and new props; if every prop is Object.is-equal, the re-render is skipped and the previous output reused. 

const ProductRow = React.memo(function ProductRow({ product, onBuy }) {
  // expensive row: renders charts, formats prices…
  return <li onClick={() => onBuy(product.id)}>{product.name}</li>;
});

// Optional escape hatch: custom comparator (return true = "equal, skip render")
const Chart = React.memo(ChartImpl,
  (prev, next) => prev.points.length === next.points.length);

Why memo silently breaks — the referential-equality trap from lesson 12, now with teeth:

function ProductList({ products }) {
  const [query, setQuery] = useState('');
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {products.map(p => (
        <ProductRow
          key={p.id}
          product={p}
          onBuy={(id) => buy(id)}         // ✘ NEW function object every keystroke
          style={{ margin: 4 }}           // ✘ NEW object every keystroke
        />                                // shallow compare fails → memo useless
      ))}
    </>
  );
}

// ✔ Pair memo with stable references:
const onBuy = useCallback((id) => buy(id), []);
const rowStyle = useMemo(() => ({ margin: 4 }), []);

That's the real relationship: memo is the optimization; useCallback/useMemo exist largely to keep memo (and deps arrays) from being defeated by fresh references. Memoize the child, then stabilize the props you pass it — doing only one half is wasted effort.

5 · Huge lists — windowing

10,000 rows means 10,000 DOM nodes — slow no matter how memoized. Windowing (virtualization) renders only the ~20 rows in the viewport plus a small buffer, absolutely positioned inside a tall scroll container, recycling rows as you scroll. Libraries: react-window, @tanstack/react-virtual. Know the concept and a library name — implementing it by hand isn't expected at this level: 

import { FixedSizeList } from 'react-window';

<FixedSizeList height={400} itemCount={items.length} itemSize={32} width="100%">
  {({ index, style }) => (
    <div style={style}>{items[index].name}</div>   // only ~15 of these exist at once
  )}
</FixedSizeList>

6 · Code splitting — React.lazy + Suspense

By default your whole app ships as one bundle: the admin dashboard's chart library downloads before the login page can render. Code splitting cuts the bundle along dynamic import() lines (lesson 8) — the chunk downloads only when first rendered. React.lazy makes a component out of a dynamic import; Suspense declares what to show while any lazy child below it is still loading: 

import { lazy, Suspense } from 'react';

const AdminPanel = lazy(() => import('./AdminPanel.jsx'));  // separate chunk

function App() {
  return (
    <Suspense fallback={<Spinner />}>    {/* shown until the chunk arrives */}
      {isAdmin && <AdminPanel />}
    </Suspense>
  );
}

The highest-value cut is route-level — each page a chunk, so users download only the page they visit: 

const Home     = lazy(() => import('./pages/Home.jsx'));
const Products = lazy(() => import('./pages/Products.jsx'));

const router = createBrowserRouter([{
  path: '/', element: <Layout />,        // Layout renders <Suspense><Outlet/></Suspense>
  children: [
    { index: true,      element: <Home /> },
    { path: 'products', element: <Products /> },
  ],
}]);

7 · Error boundaries & portals

An uncaught error during rendering unmounts your entire app — white screen. An error boundary is a component that catches render-phase errors in its subtree and shows a fallback instead. Quirk you must know: there is no hook for this — it requires a class component with componentDidCatch / getDerivedStateFromError, one of the two remaining legitimate uses of classes: 

class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError(err) { return { hasError: true }; }  // switch to fallback
  componentDidCatch(err, info) { logToServer(err, info); }             // report it
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

// In practice everyone uses the library instead:
import { ErrorBoundary } from 'react-error-boundary';
<ErrorBoundary fallback={<p>Something broke.</p>}>
  <Profile />
</ErrorBoundary>

What they don't catch: errors in event handlers (use try/catch — the app isn't rendering then), async code and rejected promises, server-side rendering, and errors thrown in the boundary itself. Place boundaries at meaningful seams (per route, per widget) so one crashed widget doesn't kill the page.

Portals solve a different escape problem: a modal defined deep in the tree gets clipped by an ancestor's overflow: hidden or stacking context. createPortal(jsx, domNode) renders the DOM elsewhere (e.g. document.body) while keeping the component in its normal React position — context still reaches it, and events still bubble through the React tree, not the DOM tree: 

import { createPortal } from 'react-dom';

function Modal({ children, onClose }) {
  return createPortal(
    <div className="backdrop" onClick={onClose}>
      <div className="modal" onClick={e => e.stopPropagation()}>{children}</div>
    </div>,
    document.body                       // DOM parent: body. React parent: unchanged.
  );
}

StrictMode recap (lesson 12): a dev-only wrapper that double-invokes renders and effect setup/cleanup to expose impure renders and leaky effects, and warns on deprecated APIs. Zero effect in production builds. Leave it on.

8 · Concurrent React — useTransition & useDeferredValue

The Fiber payoff. Problem: one keystroke updates both a text input (must feel instant) and a filtered 10,000-row list (slow to render). Bundled together, the list render blocks the input — typing lags. Concurrent React lets you mark the heavy update as non-urgent: React renders it in the background, keeps showing the old list, and abandons that work if a newer keystroke arrives. 

import { useState, useTransition, useDeferredValue } from 'react';

// Option A — useTransition: YOU mark the slow state update
function FilterableList({ items }) {
  const [query, setQuery]   = useState('');   // urgent — drives the input
  const [filter, setFilter] = useState('');   // non-urgent — drives the big list
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value);                       // applied immediately
    startTransition(() => setFilter(e.target.value)); // interruptible, low priority
  }

  const visible = items.filter(i => i.name.includes(filter));
  return (
    <>
      <input value={query} onChange={handleChange} />
      {isPending && <span>Updating…</span>}
      <ul>{visible.map(i => <li key={i.id}>{i.name}</li>)}</ul>
    </>
  );
}

// Option B — useDeferredValue: mark the VALUE as allowed to lag
function FilterableList2({ items }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);   // trails behind during fast typing
  const visible = useMemo(
    () => items.filter(i => i.name.includes(deferredQuery)),
    [items, deferredQuery]
  );
  return <><input value={query} onChange={e => setQuery(e.target.value)} />
           <ul>{visible.map(i => <li key={i.id}>{i.name}</li>)}</ul></>;
}

Use useTransition when you own the state update; useDeferredValue when you only receive a value (e.g. a prop). Neither is debouncing — no fixed delay; the work starts immediately but yields to urgent updates and can be discarded mid-render.

9 · Class components — legacy trivia for reading old code

Before hooks (React 16.8, 2019), stateful components were ES6 classes extending React.Component — state in this.state, updates via this.setState() (which merges, unlike useState's replace), side effects in lifecycle methods, and the classic bug of forgetting to .bind(this) on handlers (lesson 3's this rules biting for real). You'll meet them in older codebases and interview questions, not in new code: 

class Counter extends React.Component {
  state = { count: 0 };
  componentDidMount()  { document.title = 'mounted'; }   // lifecycle method
  handleClick = () => this.setState({ count: this.state.count + 1 });
  render() {                                             // the only required method
    return <button onClick={this.handleClick}>{this.state.count}</button>;
  }
}

Interview one-liner "Hooks replaced classes because they let you group code by concern instead of splitting one concern across three lifecycle methods, they made stateful logic reusable via custom hooks (no HOC/render-prop wrappers), and they eliminated the this-binding bugs. Classes remain only for error boundaries and legacy code."

10 · Interview questions this lesson answers

  • "Explain the virtual DOM. Is it faster than the real DOM?"
    A tree of plain JS objects describing the UI. It isn't intrinsically faster — touching it does nothing. Its value: React diffs the cheap description trees to compute a minimal set of real-DOM mutations, avoiding expensive unnecessary DOM work and manual sync bugs.
  • "What is reconciliation?"
    React's O(n) diff between the previous and next element trees: different element type ⇒ unmount the subtree (state destroyed) and remount; same type ⇒ keep the DOM node and state, patch changed props, recurse; among siblings, keys match items by identity so reorders become moves.
  • "When does a component re-render? Do prop changes trigger it?"
    Own state change (Object.is-different), parent re-render (children re-render by default), consumed context value change, or a subscribed store slice change. Props changing is a consequence of the parent rendering, not an independent trigger; React.memo is what adds a props check.
  • "React.memo vs useMemo?"
    React.memo wraps a component and skips its re-render when props are shallow-equal; useMemo caches a value inside a component across renders. They pair: memo on the child, useMemo/useCallback in the parent so object and function props keep stable references and the shallow compare can succeed.
  • "What do error boundaries not catch?"
    Event-handler errors, async/promise rejections, SSR errors, and their own errors. They catch render-phase errors of descendants; they must be class components (componentDidCatch / getDerivedStateFromError) — no hook exists.
  • "useTransition vs debouncing?"
    Debounce delays the work by a fixed timer; a transition starts rendering immediately but at low priority — interruptible and abandonable when urgent updates (typing) arrive, with no artificial delay when the app is idle.
  • "Controlled vs uncontrolled?" (recap)
    Controlled: React state owns the input's value (value + onChange); uncontrolled: the DOM owns it, read via ref. Controlled enables live validation/dependent UI at the cost of a render per keystroke.
