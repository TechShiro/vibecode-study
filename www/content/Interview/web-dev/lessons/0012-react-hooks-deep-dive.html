React Hooks Deep Dive

Hooks look like magic until you remember lesson 2: they're closures plus an array — after this lesson you'll predict every stale-value bug before it happens.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 12 of 24. Index

1 · The render mental model

Burn this in: a component is a function that React calls again on every state change. Each call is a render. Within one render, props and state are ordinary consts — a frozen snapshot. They never change mid-render; instead, a state change causes a new call with new snapshots. Any function you define during a render (handlers, effect callbacks) closes over that render's snapshot — straight from lesson 2's closures. 

function Counter() {
  const [count, setCount] = useState(0);

  function handleAlert() {
    setTimeout(() => alert(count), 3000);  // closes over THIS render's count
  }
  return <button onClick={handleAlert}>Alert {count}</button>;
}
// Click when count=0, then quickly click +1 three times.
// The alert says 0 — the timeout's closure captured render #1's snapshot.

So here's the puzzle hooks solve: if the whole function re-runs, local variables reset every time. Where does state actually live? Answer: outside your function, in a per-component list that React maintains. useState doesn't "create a variable" — it reads slot N of that list and hands you the current value plus a setter wired to that slot. Conceptually: 

// Simplified sketch of what React does (not real source, right idea)
let hooks = [];      // one list PER component instance, owned by React
let i = 0;           // cursor reset to 0 before every render

function useState(initial) {
  const slot = i++;                          // this call = slot number `slot`
  if (hooks[slot] === undefined) hooks[slot] = initial;
  const setState = (v) => {                  // a CLOSURE over `slot` (lesson 2!)
    hooks[slot] = typeof v === 'function' ? v(hooks[slot]) : v;
    rerender();                              // call the component function again
  };
  return [hooks[slot], setState];
}

Note what identifies a piece of state: its call position. First useState call = slot 0, second = slot 1. No names, no keys — just order. That single design decision explains the next section.

2 · The rules of hooks — and the real reason for them

  • Rule 1: only call hooks at the top level — never inside if, loops, or nested functions.
  • Rule 2: only call hooks from React function components or from custom hooks (functions named useSomething) — because only there does React have a hooks list ready.

Why rule 1? Because slots are matched by call order. Make a hook conditional and the order shifts between renders:

function Broken({ loggedIn }) {
  if (loggedIn) {
    const [name, setName] = useState('');   // render A: slot 0 … render B: gone!
  }
  const [count, setCount] = useState(0);    // render A: slot 1 … render B: slot 0
  // After loggedIn flips, `count` reads the slot that used to hold `name`.
  // React detects the order change and throws instead of corrupting state.
}
Interview one-liner "Hooks must be called unconditionally at the top level because React identifies each hook by its call order within the component, not by name. A conditional hook shifts the order between renders, so hook calls would read the wrong state slots. Need conditional state? Move the hook into a child component and render the child conditionally."

3 · useState, the deep cut

Lazy initializer. useState(expensiveFn()) runs the expensive call on every render (the argument is evaluated before useState is even called), even though the result is only used once. Pass the function itself and React calls it only on the first render:

const [data, setData] = useState(readHugeLocalStorage());   // runs EVERY render ✘
const [data, setData] = useState(() => readHugeLocalStorage()); // runs ONCE ✔

The stale-closure pitfall. A long-lived callback keeps the snapshot it was born with:

useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);        // ✘ closure captured count = 0 forever → 1, 1, 1…
  }, 1000);
  return () => clearInterval(id);
}, []);                          // effect ran once; its closure never refreshes

// ✔ Functional update: don't READ the stale snapshot — ask React for the latest
setCount(c => c + 1);            // 1, 2, 3, … works from any old closure

4 · useEffect — talking to the world outside

Rendering must be pure: props/state in, JSX out, no side trips. But real apps need side effects — fetching data, timers, subscriptions, touching document.title, logging. "Effect" means exactly that: work that reaches outside the render. useEffect is React's designated place for it, and its timing is the point: the callback runs after React has committed the render to the DOM — so effects never block painting, and the DOM they see is up to date. 

useEffect(() => {
  document.title = `${unread} unread`;   // the effect
  return () => { /* cleanup */ };        // optional cleanup function
}, [unread]);                            // dependency array

The dependency array is a contract — "re-run this effect when any of these values changes (Object.is comparison)":

Second argumentEffect runsTypical use
omittedAfter every renderRare — usually a mistake
[]After the first render onlyOne-time setup: subscribe, initial fetch
[a, b]After the first render, and after any render where a or b changedRe-fetch when an id changes, re-subscribe on channel change

Cleanup is the returned function. React calls it before the effect runs again and when the component unmounts — so every setup is paired with exactly one teardown, and nothing leaks: 

useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', onResize);         // setup
  return () => window.removeEventListener('resize', onResize);  // teardown
}, []);
// Same pattern for: clearInterval, socket.close(), subscription.unsubscribe()

Fetching in an effect — with the race-condition guard. Suppose the user flips between profiles fast: two fetches are in flight, and the older one might resolve last, overwriting fresh data with stale data. Guard with a flag, or abort the outdated request (AbortController, lesson 7):

useEffect(() => {
  const ctrl = new AbortController();
  let ignore = false;                       // belt AND suspenders shown; either works

  async function load() {
    try {
      const res = await fetch(`/api/users/${userId}`, { signal: ctrl.signal });
      if (!res.ok) throw new Error(res.status);
      const data = await res.json();
      if (!ignore) setUser(data);           // stale render's effect won't set state
    } catch (err) {
      if (err.name !== 'AbortError') setError(err);
    }
  }
  load();

  return () => {        // userId changed (or unmount) → this run is now stale
    ignore = true;
    ctrl.abort();       // actually cancel the network request
  };
}, [userId]);           // new userId → cleanup old, run again
Gotcha: the two infinite loops (1) setState with no deps: effect sets state → re-render → effect runs again → sets state → … Fix: add a proper dependency array. (2) Object/array/function deps: useEffect(fn, [{ id }]) — a fresh object literal is created every render, Object.is says it changed every time, so the effect loops even with a deps array. Depend on primitives ([id]) or memoize the object (section 6).
StrictMode double-invoke In development, <StrictMode> (Vite includes it in main.jsx) mounts every component twice: effect → cleanup → effect. Not a bug — it's a stress test proving your cleanup truly undoes your setup (if a subscription doubles or a fetch races, your effect was leaky). Production runs everything once. Don't "fix" it by removing StrictMode; fix the effect.

5 · useRef — the box that doesn't re-render

useRef(x) returns one stable object { current: x } that survives re-renders — like state — but mutating .current does not trigger a re-render. Two jobs: 

// JOB 1: grab a real DOM node (React's replacement for querySelector)
function SearchBox() {
  const inputRef = useRef(null);
  useEffect(() => { inputRef.current.focus(); }, []);  // after mount, DOM exists
  return <input ref={inputRef} />;   // React fills .current with the node
}

// JOB 2: a mutable instance variable (timer ids, previous values, flags)
function Stopwatch() {
  const timerId = useRef(null);            // changing this must NOT re-render
  const [ticks, setTicks] = useState(0);   // changing this MUST re-render

  const start = () => {
    timerId.current = setInterval(() => setTicks(t => t + 1), 1000);
  };
  const stop = () => clearInterval(timerId.current);
  return <><p>{ticks}s</p><button onClick={start}>▶</button><button onClick={stop}>⏸</button></>;
}

6 · useMemo & useCallback — referential equality tools

The root problem, once more: every render re-creates objects, arrays, and functions defined in the component body. New reference each time. Anything that compares by reference — effect deps, React.memo children (lesson 14), context values — sees "changed!" every render. Two hooks cache across renders: 

const sorted = useMemo(
  () => [...products].sort(byPrice),   // expensive OR needs a stable reference
  [products]                           // recompute only when products changes
);

const handleSelect = useCallback(
  (id) => setSelected(id),
  []                                   // same function object across renders
);
// useCallback(fn, deps) ≡ useMemo(() => fn, deps) — memoizing the function ITSELF

When they matter: genuinely expensive computations; values used in dependency arrays; props passed to React.memo-wrapped children; context values. When they're noise: wrapping every variable "for performance". Each memo costs memory and a deps comparison per render — cheap code re-running is often cheaper than memoizing it. Measure first (lesson 14), and remember this is memoization from lesson 10 with a cache size of one.

7 · useContext — skipping the prop relay

Props flow one level at a time; a theme or current-user object needed six levels down means six components relaying a prop they don't use (prop drilling). Context is a broadcast channel: a provider above, direct consumers below. 

import { createContext, useContext, useState } from 'react';

const ThemeContext = createContext('light');        // 1. create (module scope)

function App() {
  const [theme, setTheme] = useState('dark');
  return (
    <ThemeContext.Provider value={theme}>          {/* 2. provide */}
      <Page />                                     {/* any depth of nesting */}
    </ThemeContext.Provider>
  );
}

function DeepButton() {
  const theme = useContext(ThemeContext);           // 3. consume — no props needed
  return <button className={theme}>Save</button>;
}

What re-renders? When the provider's value changes (Object.is again), every component that calls useContext(ThemeContext) re-renders — consumers only, but all consumers, whether they use the changed part or not. That's the performance caveat lesson 13 digs into. Use context for low-churn global-ish data: theme, auth user, locale.

8 · useReducer — the state machine hook

When one piece of state is updated in five different ways from five different places, scattered setter logic gets messy. useReducer centralises it: all transitions live in one pure function (state, action) => newState, and components just dispatch actions describing what happened. Java parallel: a state machine's single transition(currentState, event) method — or a tiny switch-based interpreter — instead of setters sprinkled everywhere. 

import { useReducer } from 'react';

function todosReducer(state, action) {        // PURE: no mutation, no fetch
  switch (action.type) {
    case 'add':
      return [...state, { id: crypto.randomUUID(), text: action.text, done: false }];
    case 'toggle':
      return state.map(t => t.id === action.id ? { ...t, done: !t.done } : t);
    case 'delete':
      return state.filter(t => t.id !== action.id);
    default:
      throw new Error('Unknown action: ' + action.type);
  }
}

function TodoApp() {
  const [todos, dispatch] = useReducer(todosReducer, []);
  return (
    <>
      <button onClick={() => dispatch({ type: 'add', text: 'learn reducers' })}>Add</button>
      {todos.map(t => (
        <li key={t.id} onClick={() => dispatch({ type: 'toggle', id: t.id })}>
          {t.text}
        </li>
      ))}
    </>
  );
}

useState vs useReducer: useState for independent simple values; useReducer when the next state depends on structured transitions, several fields update together, or you want the update logic testable in isolation (a reducer is a plain function — unit test it with no React at all). Bonus: dispatch is stable across renders — safe in dependency arrays, no useCallback needed. This exact pattern scales up into Redux (lesson 13).

9 · Custom hooks — your own reusable state logic

A custom hook is just a function named useSomething that calls other hooks. That's the entire feature — no registration, no API. Because each call gets its own hook slots, two components using the same custom hook share logic, not state. This is how you extract and reuse stateful behaviour: 

// 1) useFetch — the section-4 pattern, packaged
function useFetch(url) {
  const [data, setData]       = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError]     = useState(null);

  useEffect(() => {
    const ctrl = new AbortController();
    setLoading(true);
    fetch(url, { signal: ctrl.signal })
      .then(res => { if (!res.ok) throw new Error(res.status); return res.json(); })
      .then(setData)
      .catch(err => { if (err.name !== 'AbortError') setError(err); })
      .finally(() => setLoading(false));
    return () => ctrl.abort();
  }, [url]);

  return { data, loading, error };
}
// Usage: const { data, loading, error } = useFetch('/api/todos');

// 2) useLocalStorage — useState that survives refresh (lesson 9's localStorage)
function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {          // lazy init — read disk once
    const stored = localStorage.getItem(key);
    return stored !== null ? JSON.parse(stored) : initial;
  });
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value)); // sync on every change
  }, [key, value]);
  return [value, setValue];                           // same shape as useState!
}

// 3) useDebounce — lesson 10's debounce, hook-ified (type fast, fetch once)
function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // each keystroke cancels the previous timer
  }, [value, delay]);
  return debounced;
}
// const results = useFetch('/api/search?q=' + useDebounce(query));
Interview one-liner "A custom hook is a plain function starting with use that composes built-in hooks. It shares stateful logic, not state — every component calling it gets independent state slots. It's the modern replacement for the HOC and render-props patterns of class-era React."

10 · Honourable mentions

useLayoutEffect — same API as useEffect but fires synchronously after DOM mutation, before the browser paints. Use only when you must measure or adjust layout without a visible flicker (e.g. positioning a tooltip). Default to useEffect. useId — generates stable unique ids for accessibility wiring (<label htmlFor={id}> + <input id={id}>), safe across server and client rendering — do not use it for list keys.

11 · Interview questions this lesson answers

  • "Why can't hooks be called conditionally?"
    React stores hook state in a list indexed by call order per component. A conditional call shifts every later hook's index between renders, so reads would hit the wrong slots. The rules of hooks keep the order identical every render.
  • "Explain the useEffect dependency array."
    It lists every reactive value the effect reads. React re-runs the effect after renders where any dep changed by Object.is; [] means run once after mount; omitted means after every render. Cleanup runs before each re-run and on unmount.
  • "What is a stale closure in React?"
    A long-lived callback (timer, subscription, effect from an old render) that captured old props/state via closure and keeps reading them. Fixes: functional updates, correct dependency arrays, or a ref for the latest value.
  • "useEffect vs useLayoutEffect?"
    useEffect runs asynchronously after paint (non-blocking, default); useLayoutEffect runs synchronously after DOM mutations but before paint — for measuring/adjusting layout to avoid flicker.
  • "useMemo vs useCallback?"
    useMemo caches a computed value; useCallback caches the function itself — useCallback(fn, deps) equals useMemo(() => fn, deps). Both exist to preserve referential equality across renders and to skip expensive recomputation.
  • "Why does my effect run twice in development?"
    StrictMode intentionally mounts components twice in dev to expose effects whose cleanup doesn't fully undo their setup. Production runs once. The fix is a correct cleanup function, not removing StrictMode.
  • "When useReducer over useState?"
    When updates are structured transitions on complex state, multiple sub-values change together, or update logic should be centralised and unit-testable as a pure function. Also, dispatch is stable, easing deps.
