Objects, this, Prototypes & Classes

JS does OOP without needing classes at all — objects link to other objects, and this is decided at call time, not compile time. Learn the real machinery, and ES6 class becomes pleasant sugar instead of mysterious magic.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 3 of 24. Index

1 · Object literals — objects without classes

The Java reflex: to get an object, first write a class, then new it. JS deletes step one. An object literal conjures an object directly — a bag of key–value pairs (called properties), no blueprint required: 

const student = {
  name: "Krish",              // property: key "name", value "Krish"
  cgpa: 6.78,
  "current college": "NSUT",  // keys with spaces need quotes
  subjects: ["OOPS", "DBMS"], // values can be anything — arrays, objects…
  greet: function () {        // …including functions: that makes a METHOD
    return "Hi, I'm " + this.name;
  },
  describe() {                // METHOD SHORTHAND (ES6) — same thing, less typing
    return `${this.name}, CGPA ${this.cgpa}`;
  }
};

Reading and writing properties — two syntaxes with one crucial difference:

student.name              // DOT — key written literally in code. Use by default.
student["current college"] // BRACKET — required for keys with spaces/odd characters…

const key = "cgpa";
student[key]              // …and for DYNAMIC keys: bracket evaluates the expression → 6.78
student.key               // undefined! dot looks for a key literally called "key"

student.year = 3;         // assigning to a missing key CREATES it — no class to forbid it
delete student.year;      // and delete removes it. Objects are open bags, not fixed shapes.
student.hostel            // undefined — missing properties don't throw, they yield undefined

Two more ES6 conveniences you'll see in every codebase:

const name = "Krish", cgpa = 6.78;
const s1 = { name, cgpa };            // PROPERTY SHORTHAND: { name: name, cgpa: cgpa }

const field = "sem" + 6;
const s2 = { [field]: "ongoing" };    // COMPUTED PROPERTY: key built from an expression
s2.sem6                               // "ongoing"
Java parallel The closest Java feel is a HashMap<String, Object> that can also hold methods — plus dot-syntax access. Property keys are strings (or Symbols, Lesson 5); even obj[1] becomes obj["1"]. Remember from Lesson 1: variables hold references to objects, so === on two objects compares identity, never content — {a:1} === {a:1} is false, exactly like Java's == on two distinct instances.

2 · Getters, setters, and the Object.* toolkit

Getters/setters let a property run code when read or written — Java's getX()/setX() discipline, but invisible at the call site:

const account = {
  balance: 1000,
  get summary() {                       // computed on every READ
    return `Balance: ₹${this.balance}`;
  },
  set deposit(amt) {                    // runs on WRITE — can validate
    if (amt > 0) this.balance += amt;
  }
};
account.summary;        // "Balance: ₹1000" — no parentheses; looks like a field
account.deposit = 500;  // assignment triggers the setter
account.balance;        // 1500

And the static Object.* helpers you'll use constantly:

const user = { name: "Krish", year: 3 };

Object.keys(user)     // ["name", "year"]           — like Java's map.keySet()
Object.values(user)   // ["Krish", 3]               — map.values()
Object.entries(user)  // [["name","Krish"],["year",3]] — map.entrySet(); great with for..of:
for (const [k, v] of Object.entries(user)) console.log(k, v);

Object.assign({}, user, { year: 4 })  // merge right-to-left into a new object
                                      // → { name: "Krish", year: 4 } (spread {...} does this better — Lesson 4)

Object.freeze(user);  // NOW the object itself is immutable (const only froze the binding)
user.year = 4;        // silently ignored (throws in strict mode)
Object.isFrozen(user) // true. Note: freeze is SHALLOW — nested objects stay mutable.

Three ways to ask "does this property exist?" — they differ, and section 5 explains why:

"name" in user                    // true — checks own AND inherited properties
user.hasOwnProperty("name")       // true — checks OWN properties only
user.name !== undefined           // true — but lies if the value is literally undefined

user?.address?.city               // OPTIONAL CHAINING teaser: undefined instead of a
                                  // TypeError when a link is missing. Full story in Lesson 5.

3 · this — decided at call time, not write time

Here is the single biggest mental-model difference from Java in this whole module. In Java, this inside a method always means "the instance the method belongs to" — settled forever by the class definition. In JS, functions are free-floating values (Lesson 2), so a function doesn't belong to anyone. this is determined by HOW the function is called, freshly, on every call. Four rules, checked in order of priority:

Rule (highest priority first)Call looks likethis is…
1 · new bindingnew Fn()The freshly created object (§6)
2 · Explicit bindingfn.call(x) / fn.apply(x) / fn.bind(x)Exactly x — you chose it (§4)
3 · Implicit bindingobj.fn()The object before the dot: obj
4 · Default bindingfn() — bare callundefined in strict mode / modules; the global object in old sloppy mode
 
function whoAmI() { return this?.name ?? "nobody"; }

const alice = { name: "Alice", whoAmI };   // same function, attached to an object
const bob   = { name: "Bob",   whoAmI };

whoAmI();          // "nobody"  — rule 4: bare call, no receiver
alice.whoAmI();    // "Alice"   — rule 3: alice is before the dot
bob.whoAmI();      // "Bob"     — rule 3: same function, different this!
whoAmI.call(alice);// "Alice"   — rule 2: this forced explicitly

The lost-this bug — the classic that every JS interviewer owns a copy of. Detach a method from its object and rule 3 evaporates:

const timer = {
  seconds: 0,
  tick() { this.seconds++; console.log(this.seconds); }
};

timer.tick();              // 1 — fine: called through the dot

const t = timer.tick;      // extracting the method = taking the bare function value
t();                       // TypeError: this is undefined — the dot is gone, rule 4 applies

setTimeout(timer.tick, 1000);  // SAME BUG — setTimeout receives the bare function
                               // and later calls it with no receiver

Three standard fixes — know all three:

setTimeout(() => timer.tick(), 1000);       // 1) wrap: the dot-call survives inside
setTimeout(timer.tick.bind(timer), 1000);   // 2) bind: permanently glue this (§4)
// 3) define tick as an arrow in a class field — next paragraph explains why that works

Arrow functions — the fifth "rule" that isn't a rule. Arrows have no this of their own. Any this inside an arrow is resolved like an ordinary variable — walked up the lexical scope chain (Lesson 2 §5) to the enclosing function. Written where this is your object, the arrow keeps it forever: 

const stopwatch = {
  seconds: 0,
  start() {                                  // regular method: this = stopwatch (rule 3)
    setInterval(() => {
      this.seconds++;                        // arrow has no this → uses start()'s this ✓
    }, 1000);
  }
};

// The flip side — NEVER use an arrow AS a method:
const broken = {
  name: "X",
  greet: () => `Hi ${this.name}`   // this is NOT broken — it's the outer scope's this!
};
broken.greet();                    // "Hi undefined" — rule 3 can't rescue an arrow
Interview one-liner "this is bound at call time by four rules — new, explicit (call/apply/bind), implicit (the object before the dot), default (undefined in strict mode) — in that priority order. Arrow functions opt out entirely and inherit this lexically from where they're written. So: arrows for callbacks, regular functions for methods."

4 · call, apply, bind

Every function carries these three methods (functions are objects — they can have methods!). All three set this explicitly:

function introduce(greeting, punct) {
  return `${greeting}, I'm ${this.name}${punct}`;
}
const krish = { name: "Krish" };

introduce.call(krish, "Hello", "!");     // CALL:  invoke now, args one by one → "Hello, I'm Krish!"
introduce.apply(krish, ["Hello", "!"]);  // APPLY: invoke now, args as an Array → same result

const boundIntro = introduce.bind(krish);// BIND:  invoke NOTHING — returns a NEW function
boundIntro("Yo", "?");                   // with this glued to krish forever → "Yo, I'm Krish?"

const yoIntro = introduce.bind(krish, "Yo");  // bind can also pre-fill arguments
yoIntro("!");                            // "Yo, I'm Krish!" — this is PARTIAL APPLICATION

Mnemonic: Call = Commas, Apply = Array, Bind = Bring back later. A bound function's this cannot be re-overridden by call/apply or the dot — only new outranks it. In practice you'll mostly use bind (fixing the lost-this bug), and spread syntax (Lesson 4) has largely replaced apply.

5 · Prototypes — JS inheritance without classes

Java inheritance copies a mental model of classes extending classes, checked at compile time. JS's native model is different and simpler: every object has a hidden link to another object — its prototype. When you read obj.something and obj doesn't have it, the engine follows the link and looks there. Not found? Follow that object's link. This continues until the chain ends at null. That walk is the prototype chain — inheritance by delegation ("I don't know this, ask my prototype"), resolved at runtime. 

const animal = {
  eats: true,
  describe() { return `eats: ${this.eats}, barks: ${this.barks ?? false}`; }
};

const dog = Object.create(animal);  // new empty object whose prototype IS animal
dog.barks = true;                   // own property, lives on dog itself

dog.barks       // true  — found on dog directly (own property)
dog.eats        // true  — not on dog → walk the chain → found on animal
dog.describe()  // "eats: true, barks: true" — method found on animal, BUT
                // this = dog (rule 3: dog is before the dot). Inherited methods
                // always operate on the calling object. That's the whole trick.

Object.getPrototypeOf(dog) === animal        // true — the official way to see the link
dog.__proto__ === animal                     // true — the legacy accessor (avoid writing it)

"eats" in dog                // true  — 'in' walks the chain (§2's difference, explained)
dog.hasOwnProperty("eats")   // false — hasOwnProperty checks only dog's own bag

dog.eats = false;   // WRITING never touches the prototype — this creates an OWN 'eats'
animal.eats         // true — unchanged; dog's own property now SHADOWS it (like overriding)

Where do chains end? Object literals link to Object.prototype — the source of hasOwnProperty, toString, and friends that every object mysteriously "has." Its own prototype is null: end of the line. Arrays link to Array.prototype (home of map/filter) which links to Object.prototype. One shared object holding the methods — that's why ten thousand arrays don't carry ten thousand copies of map.

Java parallel The chain-walk is Java's virtual method dispatch made visible: Java looks up an overridden method through the class hierarchy at runtime; JS walks the prototype chain at runtime. Object.prototype plays the role of java.lang.Object — the ancestor everyone eventually reaches. Difference: JS links objects to objects and you can re-point or extend them while the program runs; Java's hierarchy is frozen at compile time.

6 · Constructor functions and what new really does

Before 2015, JS faked "classes" with plain functions used in a special way — and this is still what runs underneath modern class syntax, so you must know it. A constructor function is any function you invoke with new (capitalized by convention): 

function Account(holder, balance) {
  this.holder = holder;       // per-object data goes on 'this'
  this.balance = balance;
}
// shared methods go on Account.prototype — ONE copy for all instances:
Account.prototype.deposit = function (amt) {
  if (amt > 0) this.balance += amt;
};

const a1 = new Account("Krish", 1000);
a1.deposit(500);
a1.balance                       // 1500
a1.hasOwnProperty("holder")      // true  — own data
a1.hasOwnProperty("deposit")     // false — found via the chain, on Account.prototype

What new Account("Krish", 1000) does, step by step — a top-tier interview answer:

  • 1. Creates a fresh empty object.
  • 2. Sets that object's hidden prototype link to Account.prototype.
  • 3. Calls Account with this bound to the new object (binding rule #1).
  • 4. Returns the new object automatically (unless the function explicitly returns some other object — a quirk, rarely used).

Now the naming confusion that fails candidates, untangled. prototype vs __proto__ are two different things:

Fn.prototypeobj.__proto__
Exists onFunctions onlyEvery object (legacy accessor)
What it isThe object that instances made by new Fn() will link to — a template for future childrenThe actual hidden link of this object — who it delegates to right now
Proper API—Object.getPrototypeOf(obj)
Relationshipnew Fn() makes: instance.__proto__ === Fn.prototype

And instanceof is simply a chain search: a1 instanceof Account asks "does Account.prototype appear anywhere in a1's prototype chain?" — so it stays true for subclasses, exactly like Java's instanceof.

7 · ES6 classes — the sugar, and the truth

ES6 gave JS a class syntax that finally looks like home. Everything from §6, rewritten:

class Account {
  #pin;                              // PRIVATE field (the # is part of the name!)
  static bankName = "NSUT Bank";     // STATIC: one copy on the class itself

  constructor(holder, balance, pin) {
    this.holder = holder;
    this.balance = balance;
    this.#pin = pin;
  }

  deposit(amt) {                     // method → goes on Account.prototype (shared)
    if (amt > 0) this.balance += amt;
    return this;
  }
  checkPin(guess) { return guess === this.#pin; }

  get summary() { return `${this.holder}: ₹${this.balance}`; }  // getter, as in §2

  static compare(x, y) {             // static method: Account.compare(a, b)
    return x.balance - y.balance;
  }
}

class SavingsAccount extends Account {          // inheritance
  constructor(holder, balance, pin, rate) {
    super(holder, balance, pin);                // MUST call super() before using this
    this.rate = rate;
  }
  addInterest() { this.balance *= 1 + this.rate; }
  deposit(amt) {                                // override
    super.deposit(amt);                         // super.method() calls the parent version
    console.log("saved!");
    return this;
  }
}

const s = new SavingsAccount("Krish", 1000, 1234, 0.05);
s.deposit(500).addInterest();       // method chaining via 'return this'
s.summary                            // "Krish: ₹1575"
s.#pin                               // SyntaxError — truly private, enforced by the language
s instanceof SavingsAccount          // true
s instanceof Account                 // true — chain search walks up, like Java

The truth interviewers want you to say out loud: class is (almost entirely) syntactic sugar over §6. typeof Account is "function". Methods land on Account.prototype. extends wires SavingsAccount.prototype's link to Account.prototype — method lookup is still the same chain walk. No new inheritance model was added in ES6; only new clothes. (The sugar isn't zero-calorie: classes must be called with new, their bodies run in strict mode, and #private fields are genuinely new — but the machinery is prototypes.)

Gotcha Class methods are NOT auto-bound — the lost-this bug from §3 applies fully: const d = s.deposit; d(500) throws. Fixes: this.deposit = this.deposit.bind(this) in the constructor, or declare it as an arrow class field — deposit = (amt) => { this.balance += amt; } — which captures this lexically per instance. You'll meet this exact pattern again in React class components' history.

8 · Interview questions this lesson answers

  • Q. "How does this work in JavaScript?"
    Bound per call, by priority: new → the fresh object; explicit call/apply/bind → the object you pass; implicit → the object before the dot; default → undefined in strict mode (global object in sloppy mode). Arrows have no own this — they inherit it lexically. Contrast with Java, where this is fixed to the instance.
  • Q. "Difference between call, apply, and bind?"
    All set this explicitly. call(thisArg, a, b) invokes immediately with comma args; apply(thisArg, [a, b]) invokes immediately with an array; bind(thisArg) invokes nothing — it returns a permanently-bound new function, optionally with pre-filled arguments.
  • Q. "What is the prototype chain?"
    Every object holds a hidden link to a prototype object. Failed property lookups walk link by link until found or the chain ends at null. Shared methods live once on a prototype (e.g. map on Array.prototype); inherited methods still run with this = the calling object. Writes never climb the chain — they create shadowing own properties.
  • Q. "__proto__ vs prototype?"
    obj.__proto__ (properly Object.getPrototypeOf(obj)) is the object's actual link. Fn.prototype exists only on functions and is the object future new Fn() instances will link to. They meet in: new Fn().__proto__ === Fn.prototype.
  • Q. "What does the new keyword do?"
    Four steps: create an empty object; link it to the constructor's .prototype; run the constructor with this = that object; return the object (unless the constructor returns a different object explicitly).
  • Q. "Are ES6 classes real classes?"
    They're primarily syntax sugar over constructor functions and prototypes — methods go on the prototype, extends wires a prototype chain, instanceof is a chain search. Genuinely new: mandatory new, always-strict bodies, and #private fields with language-enforced privacy.
  • Q. "Why does passing obj.method as a callback lose this, and how do you fix it?"
    Extracting the method passes the bare function; when called without a receiver, implicit binding is gone and this is undefined. Fix with a wrapper arrow (() => obj.method()), with obj.method.bind(obj), or by defining the method as an arrow class field.
