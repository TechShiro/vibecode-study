1 · The four rendering strategies

"When is the HTML for this page produced?" — every rendering strategy is just a different answer to that single question. Nail these four definitions; they are asked in nearly every frontend interview.

  • CSR — Client-Side Rendering. HTML is produced in the browser, by JavaScript, after the bundle loads. Your Vite SPA from Module B. Fast to navigate once loaded; bad SEO, slow first paint.
  • SSR — Server-Side Rendering (dynamic). HTML is produced on the server, per request. Always fresh, can be personalized (cookies, user session) — but every visit pays a server round-trip.
  • SSG — Static Site Generation. HTML is produced once, at build time (npm run build) and served from a CDN. Fastest possible delivery; content is frozen until the next deploy.
  • ISR — Incremental Static Regeneration. SSG with an expiry: the static page is re-generated in the background after a revalidate window (or on demand). Static speed, near-fresh data, no rebuilds.

Java parallel SSR is a JSP/Thymeleaf page rendered per request. SSG is like pre-generating all pages into static HTML at build time and putting them behind a CDN. ISR is that plus a cache TTL — think of a cached Spring response with maxAge, regenerated lazily after expiry.

2 · How Next chooses — static by default, dynamic on demand

In the App Router you don't pick a strategy from a menu — Next infers it per route. The rule: a route is static (SSG) by default. It becomes dynamic (SSR) the moment it uses something that can only be known at request time:

  • cookies() or headers() from next/headers — reading the request means you need a request.
  • Reading searchParams in a page (?q=chess varies per request).
  • A fetch with cache: 'no-store' — you demanded fresh data every time.
  • Forcing it: export const dynamic = 'force-dynamic' at the top of the file.

Add revalidate to a static route and you have ISR. Run npm run build and Next prints a symbol per route — ○ static, ƒ dynamic — so you can see what it inferred. 

// this page just became DYNAMIC — cookies() needs a live request
import { cookies } from 'next/headers';

export default async function Cart() {
  const cartId = (await cookies()).get('cartId')?.value;
  const items = await getCart(cartId);
  return <CartView items={items} />;
}

// this page is ISR — static, regenerated at most every 60 seconds
export const revalidate = 60;

export default async function News() {
  const stories = await getStories();
  return <StoryList stories={stories} />;
}

3 · Fetching data in Server Components

Lesson 15's superpower, now in full: server components can be async and just… await. No useEffect, no loading-state boilerplate, no exposing your API keys. And Next extends the standard fetch with caching controls: 

export default async function Repos() {
  // 1) cached indefinitely — this data becomes part of the static page
  const a = await fetch('https://api.github.com/users/krish/repos',
                        { cache: 'force-cache' });

  // 2) never cached — fresh every request (and makes the route dynamic)
  const b = await fetch('https://api.example.com/live-scores',
                        { cache: 'no-store' });

  // 3) ISR per-request-source: cache, but refetch after 3600s
  const c = await fetch('https://api.example.com/prices',
                        { next: { revalidate: 3600 } });

  // 4) tagged — so a mutation can surgically invalidate it later
  const d = await fetch('https://api.example.com/posts',
                        { next: { tags: ['posts'] } });   // revalidateTag('posts')

  const repos = await a.json();
  return <ul>{repos.map(r => <li key={r.id}>{r.name}</li>)}</ul>;
}
Gotcha — version drift In Next 13/14, fetch in server components was cached (force-cache) by default; Next 15 flipped the default to uncached — you now opt in to caching. Interviewers may hold either mental model, so say the safe version: "static routes cache by default, and per-fetch you control it with cache / next.revalidate; the fetch default changed in Next 15."

Request memoization: within a single render pass, identical fetch(url) calls are automatically deduplicated. So your layout, page, and a nested component can each call getUser() without three network hits — one request, shared result. That's why Next has no "pass data down from a special loader function" requirement: fetch where you need it.

4 · Route Handlers — when you actually need an API

Server components cover your own pages. But sometimes the caller isn't your page: a mobile app, a webhook from Stripe, a third-party consuming JSON. For that, a route.js file turns a folder into an HTTP endpoint: 

// app/api/posts/route.js  →  /api/posts
import { NextResponse } from 'next/server';

export async function GET(request) {
  const q = request.nextUrl.searchParams.get('q');   // request is a NextRequest
  const posts = await db.searchPosts(q);
  return NextResponse.json(posts);                   // JSON + status 200
}

export async function POST(request) {
  const body = await request.json();
  if (!body.title) {
    return NextResponse.json({ error: 'title required' }, { status: 400 });
  }
  const post = await db.createPost(body);
  return NextResponse.json(post, { status: 201 });
}

Export one function per HTTP method (GET, POST, PUT, DELETE…). NextRequest extends the web-standard Request (you met fetch's Request/Response in Lesson 7) with helpers like nextUrl and cookies; NextResponse adds json(), redirect(), and cookie setting. A folder can have page.js or route.js, never both — one URL, one meaning.

5 · Server Actions — mutations without writing an API

Reads are solved. Now writes: the classic flow is "build a POST endpoint, fetch it from a form handler, manage loading and errors by hand". Server Actions collapse that. A function marked 'use server' can be passed directly to a form — Next generates the endpoint, the wiring, and the plumbing: 

// app/actions.js
'use server';                              // every export here is a Server Action
import { revalidatePath } from 'next/cache';

export async function createPost(formData) {
  const title = formData.get('title');     // standard FormData API
  await db.insertPost({ title });          // runs ON THE SERVER — DB, secrets, fine
  revalidatePath('/posts');                // purge cached /posts so it shows the new row
}

// app/posts/new/page.js — a SERVER component with a working form
import { createPost } from '../../actions';

export default function NewPost() {
  return (
    <form action={createPost}>            {/* the function IS the endpoint */}
      <input name="title" />
      <button type="submit">Create</button>
    </form>
  );
}

Three details worth saying out loud in an interview:

  • Progressive enhancement. Because it's a real <form action>, submission works even before JS loads (or with JS disabled) — the browser posts, the server acts. JS just upgrades the experience.
  • Pending and result state come from hooks (in client components): useFormStatus() gives { pending } for a "Saving…" button; useActionState(action, initial) tracks the action's returned state, e.g. validation errors.
  • Cache revalidation. After a mutation, call revalidatePath('/posts') or revalidateTag('posts') so cached pages/fetches refresh — mutation and cache invalidation live side by side.

6 · middleware.js — the gatekeeper

One file at the project root, running before matched requests reach any route — ideal for auth redirects, locale detection, and header rewrites. It runs on every matched request, so keep it tiny. 

// middleware.js (project root, next to app/)
import { NextResponse } from 'next/server';

export function middleware(request) {
  const token = request.cookies.get('session')?.value;
  if (!token) {
    // not logged in → bounce to /login before the page even renders
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next();              // let the request through
}

export const config = {
  matcher: ['/dashboard/:path*', '/settings/:path*'],  // only guard these
};

7 · Environment variables — the one prefix rule

# .env.local  (gitignored)
DATABASE_URL=postgres://user:secret@host/db     # server-only. NEVER reaches the browser
NEXT_PUBLIC_ANALYTICS_ID=UA-1234                # inlined into the client bundle = PUBLIC

The rule: process.env.X works anywhere on the server; only variables prefixed NEXT_PUBLIC_ are baked into client-side code. This is a hard compile-time line — misnaming DATABASE_URL to NEXT_PUBLIC_DATABASE_URL would ship your DB password to every visitor. The prefix is a promise: "I know this becomes public."

8 · Streaming — loading.js is Suspense

Lesson 14 gave you <Suspense>; Next wires it into routing. A loading.js file automatically wraps its sibling page.js in a Suspense boundary: the server streams the layout and fallback immediately, then streams the page's HTML when its data resolves. For finer grain, place your own boundaries so slow sections don't block fast ones: 

import { Suspense } from 'react';

export default function Dashboard() {
  return (
    <>
      <Header />                              {/* renders instantly */}
      <Suspense fallback={<Skeleton />}>
        <SlowSalesChart />                    {/* async server component — streams in later */}
      </Suspense>
    </>
  );
}

This is SSR without the classic SSR weakness ("slowest query blocks the whole page"): the shell arrives fast, slow parts pop in — one HTTP response, progressively written.

9 · Deployment in three sentences

  • Vercel (Next's maker): git push → automatic build and deploy, static routes to a CDN, dynamic routes/actions to serverless functions, preview URLs per pull request. The zero-config path.
  • Self-host: next build then next start gives a plain Node server — run it on any VPS/EC2 behind nginx, or use output: 'standalone' in the config for a minimal Docker-friendly bundle.
  • Know for interviews: a Next app is not just static files — dynamic rendering, actions, and route handlers need a Node runtime (or a platform that emulates one).

10 · The Pages Router — one honest section

Before Next 13, every Next app used the pages/ directory, and most companies still run such code. No server components there: every component is client-side, and the server side lives in special exported functions. You need name recognition, not mastery: 

// pages/posts/[id].js — Pages Router style (older codebases)
export async function getServerSideProps({ params }) {   // SSR: runs per request
  const post = await getPost(params.id);
  return { props: { post } };                            // handed to the component
}

export async function getStaticProps() { ... }           // SSG: runs at build time
export async function getStaticPaths() { ... }           // which [id]s to pre-build

export default function Post({ post }) {                 // always a client-style component
  return <h1>{post.title}</h1>;
}

11 · Interview questions this lesson answers

  • Q. "Explain CSR vs SSR vs SSG vs ISR."
    Where/when HTML is produced: in the browser after JS loads (CSR); on the server per request (SSR); once at build time (SSG); at build time with timed background regeneration (ISR). Choose by freshness and personalization needs — static wherever possible, dynamic where necessary.
  • Q. "How does Next decide if a route is static or dynamic?"
    Static by default. Using request-time information — cookies(), headers(), searchParams, a no-store fetch — or dynamic = 'force-dynamic' flips it to per-request rendering. revalidate turns static into ISR.
  • Q. "Server Actions vs API routes — when each?"
    Server Actions for my own UI's mutations: a 'use server' function bound to a form, with built-in wiring, pending state via useFormStatus, and revalidatePath after writing. Route handlers when an external HTTP client exists: webhooks, mobile apps, public APIs.
  • Q. "How do you fetch data in the App Router?"
    await fetch() (or query the DB directly) inside async server components. Caching is per-fetch: force-cache, no-store, or next: { revalidate, tags }; identical fetches in one render are memoized, so components fetch independently without duplicate requests.
  • Q. "What is middleware in Next?"
    A root-level function running before matched requests — redirects, auth checks, header tweaks — scoped by a matcher, returning NextResponse.next() or a redirect/rewrite.
  • Q. "You see getServerSideProps in a codebase — what is it?"
    Pages Router SSR: a per-request server function whose returned props feed the page component. In the App Router the same need is met by an async server component using request-time APIs.
