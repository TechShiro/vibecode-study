MySQL, MongoDB & Mongoose

You know Postgres deeply — now meet the other two databases every interviewer assumes you've seen, and learn to defend any choice with a straight face.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is the Bonus Lesson (after 24). Index

1 · Why this lesson exists

Lessons 21–23 made you dangerous with PostgreSQL and Drizzle. But the industry's top three databases are PostgreSQL, MySQL, and MongoDB — and interviews love two things: "have you seen X?" and, more dangerously, "why did you use X and not Y?". The second question is a trap for people who picked their stack by tutorial. After this lesson you'll answer it like someone who chose deliberately.

Good news: 90% of your Postgres knowledge transfers to MySQL directly, and your JS object skills make MongoDB feel almost native. This lesson is about the differences, not starting over.

2 · MySQL — the other relational giant

MySQL is a relational SQL database, like Postgres. Same tables, same joins, same ACID transactions, same SELECT / INSERT / UPDATE / DELETE. It powered the early web (the "M" in the LAMP stack — Linux, Apache, MySQL, PHP), runs WordPress and countless older systems, and is still everywhere. If a company started before ~2015, odds are good there's MySQL inside.

Everything from Lesson 21 works with small dialect changes. The differences that actually bite:

const pool = mysql.createPool({ host: 'localhost', user: 'root', database: 'app' })

Interview one-liner "MySQL and Postgres are siblings — same relational model, same SQL core. Postgres has the richer type system (jsonb, arrays, uuid) and stricter defaults, which is why it's the default for new projects; MySQL has the enormous installed base, so you meet it in existing systems. I'd never rewrite a healthy MySQL app to Postgres — but I'd start a new one on Postgres."

3 · MongoDB — documents instead of tables

MongoDB throws out tables entirely. It stores documents — JSON-like objects (internally BSON, "binary JSON") — inside collections. No fixed schema: two documents in the same collection can have different fields. The vocabulary maps like this:

Relational (Postgres/MySQL)MongoDB
DatabaseDatabase
TableCollection
RowDocument (a BSON object)
ColumnField (per-document, not enforced)
Primary key id_id (auto ObjectId)
JOINEmbedding, or $lookup in aggregation (limited)
SQLQuery objects: { age: { $gt: 18 } }

CRUD feels like handing JS objects straight to the database — that JSON affinity is why Mongo grew up with Node (the MERN stack: Mongo, Express, React, Node):

// CREATE
await db.collection('users').insertOne({ name: 'Krish', age: 20, skills: ['js', 'java'] })

// READ — query operators: $gt $gte $lt $in $ne $regex ...
await db.collection('users').find({ age: { $gt: 18 }, skills: 'js' })   // matches inside arrays too
        .sort({ name: 1 }).limit(10).toArray()

// UPDATE — $set changes fields, $push appends to arrays, $inc increments
await db.collection('users').updateOne({ name: 'Krish' }, { $set: { age: 21 }, $push: { skills: 'sql' } })

// DELETE
await db.collection('users').deleteOne({ name: 'Krish' })

The big design question — embed or reference? Relational modeling splits data into tables and joins them back. Document modeling asks: does this data live inside the parent document, or in its own collection with an id pointing across? 

// EMBEDDING — comments live inside the post document. One read gets everything.
{ _id: 1, title: 'Hello', comments: [ { by: 'Asha', text: 'Nice!' }, { by: 'Ravi', text: '+1' } ] }

// REFERENCING — comments in their own collection, pointing at the post (like a FK).
{ _id: 55, postId: 1, by: 'Asha', text: 'Nice!' }
  • Embed when the child is only ever read with the parent, and the list is bounded (comments on a post, line items on an order).
  • Reference when the child is shared, queried independently, or unbounded (users referenced by many posts; logs that grow forever — documents have a 16 MB cap).

Also good to name-drop: the aggregation pipeline (Mongo's GROUP BY — [{ $match: ... }, { $group: ... }, { $sort: ... }], stages like array methods chained on the server), indexes (same B-tree idea as Lesson 22 — createIndex({ email: 1 }), unique indexes, compound indexes; everything you learned about when indexes help transfers directly), and that Mongo has had multi-document transactions since 4.0 — though needing them often is a hint your data wanted to be relational.

Gotcha "Schemaless" does not mean "schema-free" — it means the schema lives in your application code instead of the database. The database will happily accept { nmae: 'typo' }. That's exactly the hole Mongoose plugs.

4 · Mongoose — the ODM that gives Mongo a schema back

Mongoose is to MongoDB what Drizzle/Prisma are to Postgres — with one vocabulary twist: since Mongo stores documents, not relations, Mongoose is an ODM (Object-Document Mapper), not an ORM. Same job: define your data's shape in code, get validation, types, and a nicer query API. 

import mongoose from 'mongoose'
await mongoose.connect(process.env.MONGO_URL)

// 1. Schema — the shape and rules Mongo itself never enforced
const userSchema = new mongoose.Schema({
  name:  { type: String, required: true, trim: true },
  email: { type: String, required: true, unique: true, lowercase: true },
  age:   { type: Number, min: 0 },
  posts: [{ type: mongoose.Schema.Types.ObjectId, ref: 'Post' }]  // reference (like a FK)
}, { timestamps: true })                                          // auto createdAt/updatedAt

// 2. Model — the class you query with (collection becomes 'users', auto-pluralized)
const User = mongoose.model('User', userSchema)

// 3. CRUD — validation runs automatically on save
const u = await User.create({ name: 'Krish', email: 'K@X.dev' })  // email stored lowercased
await User.find({ age: { $gte: 18 } }).sort('name').limit(10)     // same operators as raw Mongo
await User.updateOne({ _id: u._id }, { $set: { age: 21 } })
await User.deleteOne({ _id: u._id })

// populate() — Mongoose's answer to joins / Drizzle's `with` / Prisma's `include`:
const withPosts = await User.findById(u._id).populate('posts')    // swaps ObjectIds for real docs

Two more Mongoose features interviewers ask about: middleware/hooks (userSchema.pre('save', ...) — the classic use is hashing a password with bcrypt before saving, tying into Lesson 19) and methods/statics (attach user.checkPassword() to documents, User.findByEmail() to the model — very OOPS, very Java-friendly).

Interview one-liner "Mongoose is an ODM — it maps JS objects to MongoDB documents and, crucially, re-introduces a schema with validation at the application layer, because MongoDB itself won't enforce one. Schema, Model, then CRUD; populate() resolves references the way an ORM resolves relations."

5 · The "why this and not that" drill

This is the section to reread before any interview. The pattern for every answer: name the tradeoff, pick a side for YOUR use case, respect the other option. Never trash-talk a technology — it makes you sound like a tutorial, not an engineer.

Q. Why PostgreSQL and not MySQL?
"Both are excellent relational databases and most apps would work on either. I chose Postgres for its richer type system — jsonb for flexible fields, real uuid, arrays — its stricter defaults, and because the modern hosting ecosystem (Neon, Supabase, RDS) and ORMs treat it as the first-class target. If I joined a MySQL shop, nearly everything transfers."

Q. Why would anyone still pick MySQL then?
"Existing systems and team experience. MySQL runs a huge share of the web, MySQL 8 closed most feature gaps (CTEs, window functions), and migrating a healthy database is rarely worth it. New greenfield project — Postgres; existing MySQL infrastructure — MySQL, happily."

Q. Why SQL (Postgres) and not MongoDB for your project?
"My data is relational — users, notes, tags with relationships and integrity rules — and I want the database to enforce those with foreign keys and transactions. Joins are natural in SQL. Mongo would make me either duplicate data or fake joins in application code, and I'd lose schema enforcement."

Q. Then when IS MongoDB the right call?
"Document-shaped data read as a unit — a product catalog where every item has different attributes, CMS content, event payloads — especially with a rapidly evolving schema. One document read replaces a five-way join, and horizontal scaling via sharding is built into its design. Also: prototyping speed with Node, since documents are basically JS objects."

Q. Postgres has JSONB — doesn't that make MongoDB pointless?
"It covers a lot of Mongo's ground — I'd use a jsonb column for a flexible corner of an otherwise relational model, and that's usually enough. Mongo still wins when the entire model is documents and you want its sharding story, its aggregation pipeline, and a schema-flexible workflow end to end — not just one flexible column."

Q. Why an ORM/ODM at all — why not raw SQL everywhere?
"Type safety, validation, and productivity: the compiler catches a renamed column at build time instead of a runtime 500. The cost is a leaky abstraction — N+1 queries, unpredictable SQL in heavy ORMs — so I picked a thin one (Drizzle) where each call maps to predictable SQL, and I can always drop to raw SQL for the hot path."

Q. Why Drizzle and not Prisma?
"Both are solid. Drizzle: schema in plain TypeScript with instant inference, no codegen step, SQL-transparent queries, tiny runtime — great for serverless. Prisma: more batteries (Studio, mature migrate tooling) and a friendlier API if the team doesn't think in SQL. I value seeing the SQL through the API, so Drizzle — but I can read a Prisma codebase fine, the concepts map one-to-one."

Q. Why Mongoose if MongoDB is schemaless — isn't that contradictory?
"It's the point, actually: Mongo's flexibility is a feature at the database layer and a liability at the app layer. Mongoose lets ME decide where the strictness lives — validation, defaults, hooks in code — while keeping Mongo's storage flexibility. Schemaless databases still have schemas; the only question is whether anything enforces them."

Q. ORM vs ODM — difference?
"Same idea, different target: an ORM maps objects to relational tables (Drizzle, Prisma, Hibernate), an ODM maps objects to documents (Mongoose). ODMs don't need joins or table migrations; ORMs don't need runtime schema enforcement because the database already has one."

Q. Why not Redis as your database — it's the fastest, right?
"Redis is in-memory key-value — perfect as a cache, session store, or queue in front of a primary database, but it's not designed to be the durable source of truth: no relational queries, and memory is the capacity limit. Fast at its job; its job isn't primary storage."

6 · Interview questions this lesson answers

  • "What are the most used databases in industry?"
    PostgreSQL (developer-survey #1, default for new work), MySQL (largest web install base), MongoDB (leading NoSQL/document store) — with Oracle/SQL Server in enterprise, SQLite embedded, Redis as the standard cache.
  • "What is the difference between SQL and NoSQL databases?"
    SQL: fixed schema, tables, joins, ACID — integrity enforced by the database. NoSQL (documents/key-value/wide-column/graph): flexible schema, data shaped for its access pattern, horizontal scaling emphasized. Choose by data shape and integrity needs.
  • "What is MongoDB's _id?"
    Every document gets an _id, by default an ObjectId — 12 bytes encoding timestamp + random + counter, generated client-side, globally unique without a central sequence.
  • "Embedding vs referencing in MongoDB?"
    Embed bounded, always-read-together children inside the parent (one read, atomic updates); reference shared or unbounded data across collections (16 MB document cap, independent querying).
  • "What is Mongoose and why use it?"
    An ODM for MongoDB: schemas with validation/defaults/hooks at the app layer, models for querying, populate() for references — restoring the guarantees Mongo deliberately doesn't enforce.
  • "What is the difference between an ORM and an ODM?"
    ORM ↔ relational tables (Drizzle/Prisma/Hibernate); ODM ↔ documents (Mongoose). Same object-mapping idea, different storage model underneath.
