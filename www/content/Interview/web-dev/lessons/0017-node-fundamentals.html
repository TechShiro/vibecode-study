Node.js Fundamentals

We leave the browser. Same JavaScript, new powers — files, sockets, processes — and a server model that handles ten thousand connections on a single thread.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 17 of 24. Index

1 · Leaving the browser: what Node actually is

Everything before Module C ran your JS inside a browser tab. Next.js quietly ran some of it "on the server" — and that server was Node.js. This module opens the box. Backend Module D starts here: Node this lesson, Express next, so you feel exactly what Express saves you from.

Node.js is a JavaScript runtime built on V8 and libuv. Unpack that:

  • V8 — Chrome's JavaScript engine, ripped out of the browser. It compiles and runs your JS, fast. Same language, same semantics you learned in Module A.
  • libuv — a C library giving JS what browsers never allowed: files, network sockets, DNS, child processes — all through an asynchronous, non-blocking API, plus the event loop that schedules it all and a small thread pool for the few operations (like file IO) that can't be async at the OS level.
  • Node's own APIs — fs, http, path, process… glue exposing libuv's powers to your JS.
Java parallel V8 is to JS what the JVM is to bytecode: the execution engine. Node = engine + standard library + runtime services, so "Node is to JavaScript roughly what the JDK is to Java" is a fair one-liner. The deep difference is the concurrency model — coming in section 3.

3 · Why Node for servers — one thread vs a thread per request

The classic Java servlet model: each incoming request gets a thread from a pool. The thread runs your code, and when it queries the DB it blocks — sits idle holding ~1MB of stack — until the result returns. 10,000 concurrent requests? 10,000 mostly-sleeping threads, heavy memory, costly context switches.

Node's model: one thread runs all your JS, and every IO operation is non-blocking. "Read this socket — call me back when data arrives." While the DB thinks, the thread serves other requests. Ten thousand waiting connections are just ten thousand cheap callbacks in a queue, not ten thousand threads. 

// The restaurant analogy:
// Java (classic): one waiter PER TABLE; each waits at the kitchen till the dish is ready.
// Node: ONE waiter for the room; drops orders at the kitchen, keeps circulating,
//       delivers each dish when the kitchen dings the bell (the callback).

Honesty section — say this in interviews and you'll stand out:

  • IO-bound work (APIs, chat, streaming, proxies — mostly waiting on DB/network/disk): Node shines.
  • CPU-bound work (video encoding, heavy crypto, big number-crunching): Node suffers — a long computation blocks the one thread, freezing every other request. Use worker threads (section 12) or a different runtime for that.
  • Modern Java has async NIO/virtual threads too — Node's edge is that non-blocking is the default and only style, plus one language across the whole stack.
Interview one-liner "Node runs JavaScript on one thread with an event loop; all IO is non-blocking, so instead of a thread per request it multiplexes thousands of connections over one thread. Great for IO-bound servers; wrong for CPU-bound work unless you offload to worker threads."

4 · Running code, process, and the REPL

node                      # no args → REPL: an interactive JS prompt, like jshell
node app.js hello 42      # run a script with two arguments
// app.js — process is your window into the OS
console.log(process.argv);        // ['/path/node', '/path/app.js', 'hello', '42']
console.log(process.argv[2]);     // 'hello' — real args start at index 2

console.log(process.env.PORT);    // environment variables (config & secrets live here)
console.log(process.cwd());       // directory node was LAUNCHED from (not the file's dir!)
console.log(process.platform);    // 'win32', 'linux', 'darwin'

if (!process.env.PORT) {
  console.error('PORT is required');
  process.exit(1);                // nonzero = failure, same convention as System.exit
}

5 · Modules in Node — CJS vs ESM in 30 seconds

Full story in Lesson 8; the Node-specific recap: Node's historical system is CommonJS (require/module.exports, synchronous). Modern ESM (import/export) works when you set "type": "module" in package.json (or name files .mjs). 

// CJS (default in a bare project)          // ESM (with "type": "module")
const fs = require('fs');                    import fs from 'node:fs';
module.exports = { helper };                 export { helper };

This track uses ESM. The node: prefix (node:fs, node:path) explicitly marks core modules — modern style, avoids clashes with npm packages.

6 · path — stop concatenating strings

import path from 'node:path';

// WRONG: dir + '/' + file → breaks on Windows (\), duplicate slashes, '..' issues
// RIGHT:
path.join('logs', 'app', 'today.log');    // 'logs/app/today.log' (or \ on Windows)
path.resolve('logs', 'today.log');        // ABSOLUTE path from cwd: 'C:\Dev\skills\logs\today.log'
path.basename('/a/b/report.pdf');         // 'report.pdf'
path.extname('report.pdf');               // '.pdf'
path.dirname('/a/b/report.pdf');          // '/a/b'

// the classic pattern: paths relative to THIS FILE, not the launch dir
const dataFile = path.join(import.meta.dirname, 'data', 'users.json');

join glues segments with the right separator; resolve builds an absolute path. Use them because your code must survive Windows vs Linux and being launched from any directory — this is Java's Path.of()/Paths.get() lesson all over again.

7 · fs — three generations of the same read

The file-system module is a live museum of async style evolution — and a perfect interview demo: 

import fs from 'node:fs';
import fsp from 'node:fs/promises';

// GEN 1 — synchronous: BLOCKS the one thread. Fine in scripts, poison in servers.
const text1 = fs.readFileSync('notes.txt', 'utf8');

// GEN 2 — error-first callback: non-blocking, but nesting breeds callback hell
fs.readFile('notes.txt', 'utf8', (err, text2) => {
  if (err) return console.error('failed:', err.message);   // error ALWAYS first arg
  console.log(text2);
});

// GEN 3 — fs/promises + async/await: non-blocking AND readable. Use this.
const text3 = await fsp.readFile('notes.txt', 'utf8');
await fsp.writeFile('out.txt', text3.toUpperCase());
await fsp.mkdir('logs', { recursive: true });
Gotcha Forget the 'utf8' encoding and readFile hands you a Buffer (raw bytes — section 11), not a string. And never call *Sync functions while serving requests: one slow disk read freezes every connected client, because there is only one JS thread.

os in one glance: os.cpus().length (core count — used for clustering), os.totalmem(), os.homedir(), os.tmpdir().

8 · Events — EventEmitter

Browser JS had addEventListener; Node's equivalent backbone is EventEmitter — the observer pattern as a base class (think Swing listeners / a tiny pub-sub). Streams, servers, sockets: almost everything in Node is an emitter. 

import { EventEmitter } from 'node:events';

const orders = new EventEmitter();

orders.on('placed', (id) => console.log(`email receipt for ${id}`));   // subscribe
orders.on('placed', (id) => console.log(`update stock for ${id}`));    // many listeners OK
orders.once('first-sale', () => console.log('🎉 celebrate — runs once, then unsubscribes'));

orders.emit('placed', 'ord_42');       // fires both listeners, synchronously, in order
orders.emit('first-sale');
orders.emit('first-sale');             // nothing — once() already detached

// the special 'error' event: emitted with NO listener attached → Node CRASHES the process
orders.on('error', (err) => console.error('handled:', err.message));

Remember this shape — Express's app.on(...), stream events, and WebSocket handling all reuse it.

9 · http — a server with no framework

Now the payoff. Node's core http module can serve real traffic — and hand-rolling routing and body parsing once will make you grateful for Express next lesson. 

// server.js — run: node server.js  → http://localhost:3000
import http from 'node:http';

const notes = [{ id: 1, text: 'learn node' }];

const server = http.createServer((req, res) => {
  // EVERY request lands in this one function. Routing = if/else on url+method.

  if (req.method === 'GET' && req.url === '/api/notes') {
    res.writeHead(200, { 'Content-Type': 'application/json' });  // status + headers
    res.end(JSON.stringify(notes));                              // body, then close

  } else if (req.method === 'POST' && req.url === '/api/notes') {
    // the body arrives in CHUNKS (it's a stream!) — collect, then parse
    let raw = '';
    req.on('data', (chunk) => raw += chunk);
    req.on('end', () => {
      try {
        const { text } = JSON.parse(raw);
        const note = { id: notes.length + 1, text };
        notes.push(note);
        res.writeHead(201, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify(note));
      } catch {
        res.writeHead(400, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({ error: 'invalid JSON' }));
      }
    });

  } else {
    res.writeHead(404, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ error: 'not found' }));
  }
});

server.listen(3000, () => console.log('listening on :3000'));

Feel the pain points: manual if/else routing, manual chunk-collecting and JSON parsing, headers written by hand, no URL parameters, no middleware. Express (Lesson 18) is a thin layer that fixes exactly this list — nothing magical, just this code factored well.

10 · Streams and pipes — why not read the whole file?

readFile loads the entire file into memory. For a 4GB video that's a crash; for many concurrent downloads it's death by RAM. A stream processes data chunk by chunk — constant memory no matter the file size: 

import fs from 'node:fs';
import http from 'node:http';

http.createServer((req, res) => {
  // stream a huge file: read a chunk → send a chunk → repeat. RAM stays flat.
  const file = fs.createReadStream('big-video.mp4');   // Readable stream
  file.pipe(res);                                      // res is a Writable stream!
  file.on('error', () => { res.writeHead(404); res.end(); });
}).listen(3000);

pipe connects a Readable to a Writable — Unix pipes, in JS — and handles backpressure: if the client reads slowly, reading from disk pauses instead of buffering gigabytes. Chunk size is tuned by highWaterMark (default 64KB for file streams) — know the term, not the tuning. Four stream types for the record: Readable, Writable, Duplex (both, e.g. sockets), Transform (modifies data in flight, e.g. gzip). You already met streams disguised: req in section 9 is a Readable, res a Writable.

11 · Buffers — bytes, not strings

const buf = Buffer.from('नमस्ते', 'utf8');  // raw bytes of the UTF-8 encoding
console.log(buf.length);                    // 18 bytes — NOT 6 characters!
console.log(buf.toString('utf8'));          // back to 'नमस्ते'
console.log(buf.toString('base64'));        // encode for transport

A Buffer is Node's container for binary data — fixed-size raw memory, like Java's byte[]. File chunks, sockets, crypto all speak Buffer; an encoding ('utf8', 'base64', 'hex') is the translation rule between bytes and text. This is why un-encoded readFile returns a Buffer: Node won't guess your encoding.

12 · The Node event loop — interview depth

Lesson 6 gave you the browser loop (call stack, microtasks, macrotasks). Node's loop (in libuv) is the same idea with named phases cycling in order:

  • timers — run due setTimeout/setInterval callbacks
  • pending callbacks — leftover system-level callbacks
  • poll — the workhorse: wait for and process IO events (sockets, file callbacks)
  • check — run setImmediate callbacks
  • close callbacks — e.g. socket.on('close')

Between every callback, two express queues jump the line: process.nextTick (highest priority, Node-specific) and then microtasks (promise .then/await continuations). The classic questions: 

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('tick'));
console.log('sync');

// sync → tick → promise → then timeout/immediate
// (timeout vs immediate order is nondeterministic in main script;
//  INSIDE an IO callback, setImmediate always beats setTimeout(0) —
//  check phase comes right after poll, timers must wait for the next loop)
APIRunsQueue
process.nextTick(fn)Before anything else, right after current codenextTick queue (Node-only)
Promise.then / awaitAfter nextTick, before any phase continuesMicrotask queue
setTimeout(fn, 0)Timers phase of a later loop iterationMacrotask (timers)
setImmediate(fn)Check phase, right after poll/IOMacrotask (check)
Gotcha Recursive process.nextTick can starve the event loop — the tick queue drains fully before IO gets a turn, so a self-scheduling tick blocks the server as surely as an infinite while loop. That's why docs say "use setImmediate for 'run this soon', nextTick only for 'finish this before anything else observes my state'."

13 · Scaling glance: cluster & worker_threads

cluster: one JS thread uses one CPU core — on an 8-core box, 7 idle. The cluster module forks one Node process per core, all sharing the same port with the OS load-balancing connections. Process managers like PM2 do this for you; it's the standard answer to "how does Node use multiple cores?"

worker_threads: real threads within one process, each with its own event loop, passing messages instead of sharing state. The answer to "what about CPU-bound work?": push the heavy computation (image resize, big parse) into a worker so the main loop stays free to serve requests. Cluster = scale requests across cores; workers = keep computation off the main thread.

14 · Dev loop: npm scripts, nodemon, watch mode

// package.json
{
  "type": "module",
  "scripts": {
    "start": "node server.js",
    "dev": "node --watch server.js"     // auto-restart on save (Node 18.11+)
  }
}

Restarting by hand after every edit gets old in minutes. node --watch (built-in) or the classic nodemon (npx nodemon server.js) restarts the process on file change — Node's answer to Vite's hot reload, at process granularity. Convention: npm run dev = watching dev server, npm start = plain production start.

15 · Error-first callbacks — and why promises won

You saw the shape in section 7: every classic Node async API calls back as (err, result) — error first, always, so no one could forget failure handling. It worked, but composition was misery: each step nests one level deeper (callback hell), errors must be manually forwarded at every layer, and try/catch can't cross a callback boundary. Promises won because they made async values first-class — returnable, chainable, aggregatable (Promise.all) — and async/await restored straight-line code with real try/catch. Legacy callback APIs convert via util.promisify, and modern core modules ship promise versions (fs/promises) natively. Full story: Lessons 6–7.

16 · Interview questions this lesson answers

  • Q. "What is Node.js?"
    A JavaScript runtime outside the browser: V8 executes the JS, libuv provides the event loop and non-blocking IO (files, sockets), and Node's core modules (fs, http, path…) expose system capabilities browsers sandbox away.
  • Q. "Single-threaded Node vs multi-threaded Java servers?"
    Classic Java blocks a pooled thread per request during IO; Node multiplexes all requests on one thread with non-blocking IO and callbacks. Fewer resources for IO-bound loads; CPU-bound work blocks Node's only thread, so it goes to worker threads. (libuv also keeps an internal thread pool for file IO/crypto — "single-threaded" means your JS, not the whole process.)
  • Q. "setTimeout(fn, 0) vs setImmediate vs process.nextTick?"
    nextTick runs first — before microtasks, before any phase continues. Promise callbacks next. setTimeout runs in the timers phase; setImmediate in the check phase. Inside an IO callback setImmediate fires before setTimeout(0), because check follows poll directly.
  • Q. "Why streams over readFile?"
    readFile buffers the entire file in memory; a stream processes fixed-size chunks (highWaterMark), so a 4GB file serves in constant memory. pipe() connects readable to writable and manages backpressure when the consumer is slower than the producer.
  • Q. "What is a Buffer?"
    Node's raw binary container — like Java's byte[]. Streams, sockets, and un-encoded file reads produce Buffers; an encoding like utf8 or base64 converts between bytes and strings.
  • Q. "What is an error-first callback?"
    Node's classic async convention: callback(err, result) with the error as first argument, forcing explicit handling. Superseded in practice by promises/async-await, which compose and support try/catch.
  • Q. "How does Node use multiple CPU cores?"
    cluster (or PM2) forks one process per core sharing a port for request throughput; worker_threads offload CPU-heavy jobs from the main event loop within a process.
