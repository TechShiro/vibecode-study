async/await, fetch & Friends

Promise chains taught you the machine — now learn the syntax that makes async code read like normal code, and use it to talk to real servers.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 7 of 24. Index

1 · async functions — promises in disguise

Mark a function async and two things become true. First: it always returns a promise, no matter what you write. Return a plain value? It arrives wrapped in a fulfilled promise. Throw? The returned promise rejects. There is no way for an async function to hand back a raw value — callers always get the "food token" from last lesson. 

async function getAnswer() {
  return 42;                       // looks like returning a number...
}
const p = getAnswer();
console.log(p);                    // Promise { 42 } — NOT 42
p.then(v => console.log(v));       // 42

async function boom() {
  throw new Error("nope");         // throw → the promise REJECTS
}
boom().catch(e => console.log(e.message));   // "nope"

Second: inside an async function you may use await — the whole point.

2 · What await actually does

await somePromise pauses the async function — not the thread, not the page, not other code — until the promise settles. If fulfilled, await evaluates to the value. If rejected, await throws the reason, right there at that line, like a normal Java exception. 

async function main() {
  console.log("before");
  const user = await readUserP(7);   // function suspends HERE; thread moves on
  console.log("after:", user.name);  // resumes later, when the promise fulfills
}
main();
console.log("this prints BEFORE 'after' — main() paused, script continued");

Tie this back to Lesson 6: at each await, the function's remaining code is packaged up as a promise reaction — effectively a hidden .then — and the function returns control immediately. When the awaited promise settles, the continuation is queued on the microtask queue and the function resumes from where it stopped. async/await is pure syntax sugar over promise chains; the event-loop rules you drilled last lesson are unchanged. 

// Proof that await = microtask (classic interview drill)
async function f() {
  console.log("1");
  await null;                    // even awaiting a non-promise yields to microtasks
  console.log("3");              // resumes as a microtask
}
f();
console.log("2");
// Output: 1, 2, 3 — everything after 'await' behaves like a .then callback
Java parallel await feels like Java's future.get() — but get() blocks the thread. await suspends only the current function and frees the one JS thread to run other work. The closest Java relative is virtual threads / Kotlin coroutines' suspend: cheap suspension, no OS thread held hostage.
Interview one-liner "await unwraps a promise: it suspends the enclosing async function until the promise settles, yielding the thread; on fulfillment it returns the value, on rejection it throws. The continuation resumes via the microtask queue — it's syntactic sugar over .then."

3 · try/catch/finally with await

Because a rejected await throws, async error handling is just Java-style try/catch — this is the big readability win over .catch() chains: 

async function loadProfile(id) {
  try {
    const user   = await readUserP(id);       // any of these rejecting
    const orders = await readOrdersP(user.id);// jumps straight to catch
    return { user, orders };
  } catch (err) {                             // one catch for every step — like the
    console.error("profile failed:", err.message); // single .catch at chain end
    return null;                              // recover with a fallback value
  } finally {
    hideSpinner();                            // runs on success AND failure
  }
}

Where should you catch? Rule of thumb: catch at the level that can actually do something — show a message, retry, substitute a default. Low-level helpers should usually just await and let errors bubble up (rethrow behaviour is automatic), exactly like you don't wrap every Java method body in try/catch.

Gotcha — the forgotten await try { readUserP(-1); } catch (e) { ... } catches nothing. Without await, the function returns a promise that rejects later, long after the try block exited — you get an "Unhandled promise rejection" in the console instead. The same trap bites return inside try: prefer return await doWork() inside a try block so the rejection is caught here, not in your caller.

4 · Sequential vs parallel — the accidental-serial mistake

Each await is a full stop: nothing after it starts until it finishes. Perfect when step B needs step A's result. Wasteful when the steps are independent — and this is the most common real-world async performance bug: 

// ACCIDENTALLY SERIAL — ~600 ms total (300 + 300)
async function slow() {
  const user  = await fetchUser(1);    // wait 300 ms...
  const posts = await fetchPosts(1);   // ...THEN wait another 300 ms
  return { user, posts };              // but posts never needed user!
}

// PARALLEL — ~300 ms total: start both, then await both
async function fast() {
  const userP  = fetchUser(1);         // fires the request, no await yet
  const postsP = fetchPosts(1);        // second request already in flight
  const [user, posts] = await Promise.all([userP, postsP]);
  return { user, posts };
}

The pattern: start every independent operation first (call the functions, collect promises), then await them together with Promise.all. Use sequential awaits only when there is a real data dependency. Interviewers love asking you to spot and fix the serial version.

5 · Top-level await

Historically await only worked inside async functions, forcing the awkward (async () => { ... })() wrapper. Modern ES modules (Lesson 8) allow await directly at the top level of a module — the module simply finishes loading when the promise settles. It works in module scripts and modern Node; it does not work in classic non-module <script> tags or old-style CommonJS files. 

// config.js — an ES module
const res = await fetch("/api/config");     // legal at module top level
export const config = await res.json();     // importers wait until this settles

6 · Error-handling patterns worth stealing

Two small helpers you'll see in real codebases (and can name-drop in interviews):

// Pattern 1: Go-style [error, data] wrapper — no try/catch pyramid
async function safe(promise) {
  try {
    const data = await promise;
    return [null, data];
  } catch (err) {
    return [err, null];
  }
}

const [err, user] = await safe(fetchUser(1));
if (err) console.error("handled inline:", err.message);
else     console.log(user.name);

// Pattern 2: retry with delay — awaits make loops trivially readable
const delay = (ms) => new Promise(res => setTimeout(res, ms));

async function retry(fn, attempts = 3) {
  for (let i = 1; i <= attempts; i++) {
    try {
      return await fn();                 // success → return immediately
    } catch (err) {
      if (i === attempts) throw err;     // out of attempts → give up
      await delay(500 * i);              // backoff: 500, 1000, ... ms
    }
  }
}
// Try writing retry with raw .then chains — the loop alone is a nightmare.
// This readability of loops + conditionals is WHY async/await exists.

7 · fetch — talking to servers

fetch(url) is the built-in browser (and modern Node) API for HTTP requests — the successor to the ancient XMLHttpRequest. It returns a promise for a Response object. Two-step ritual: first the promise for the response headers, then a second promise to read the body: 

async function getUser(username) {
  const res = await fetch(`https://api.github.com/users/${username}`);

  // STEP 1: check res.ok — fetch does NOT reject on 404/500!
  if (!res.ok) {
    throw new Error(`HTTP ${res.status} ${res.statusText}`);
  }

  // STEP 2: read the body — .json() parses it; ALSO returns a promise
  const data = await res.json();
  return data;
}
Gotcha — the 404 that "succeeds" fetch only rejects on network failure (no connection, DNS failure, CORS block, abort). A 404 or 500 is, to fetch, a perfectly successful conversation with the server — the promise fulfills. You must check res.ok (true for status 200–299) or res.status yourself. Forgetting this check is the single most common fetch bug and a guaranteed interview question.

Useful bits of the Response object:

  • res.status / res.statusText — e.g. 200 "OK", 404 "Not Found";
  • res.ok — shorthand for status in 200–299;
  • res.headers.get("content-type") — response headers;
  • res.json(), res.text(), res.blob() — body readers, each returns a promise, and the body can be read only once.

8 · POST — sending JSON

The second argument to fetch is an options object: method, headers, body. To send JSON you must do three things yourself — stringify the body, declare the content type, and parse the reply: 

async function createTodo(todo) {
  const res = await fetch("https://jsonplaceholder.typicode.com/todos", {
    method: "POST",                                // default is GET
    headers: { "Content-Type": "application/json" }, // tell server what we send
    body: JSON.stringify(todo),                    // body must be a STRING (or FormData…)
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();                               // server echoes the created object
}

const created = await createTodo({ title: "learn fetch", completed: false });
console.log(created.id);           // server-assigned id

Same shape for PUT (replace), PATCH (partial update), DELETE (often no body). You'll design the server side of these verbs in the Express lessons — for now you're the client.

9 · AbortController — timeouts and cancellation

A promise, once made, cannot be "un-made" — but the underlying request can be cancelled. AbortController is the standard cancel switch: create one, pass its signal to fetch, and calling abort() makes the fetch promise reject with an AbortError. 

// Timeout: give the server 3 seconds, then hang up
async function fetchWithTimeout(url, ms = 3000) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), ms);   // pull the plug after ms
  try {
    const res = await fetch(url, { signal: ctrl.signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (err) {
    if (err.name === "AbortError") throw new Error(`timed out after ${ms}ms`);
    throw err;                                        // other errors pass through
  } finally {
    clearTimeout(timer);            // success or failure, disarm the timer
  }
}

The other classic use: a search box firing a request per keystroke — abort the previous request when a new one starts, so a slow old response can't overwrite fresh results. React's data libraries do this for you, but interviewers ask how it works underneath: AbortController is the answer.

10 · Timer patterns — setTimeout, setInterval, polling

You met setTimeout conceptually in Lesson 6; here's the practical toolkit:

// One-shot, cancellable
const id = setTimeout(() => console.log("fires once"), 1000);
clearTimeout(id);                       // cancelled — never fires

// Repeating — and why recursive setTimeout often beats setInterval
const iv = setInterval(() => console.log("tick"), 1000);
clearInterval(iv);
// setInterval fires on a fixed schedule even if the previous tick's work
// (e.g. a slow fetch) hasn't finished — ticks can pile up. Recursive
// setTimeout schedules the NEXT tick only after the current one completes:

async function poll(url, ms) {
  const res  = await fetch(url);
  const data = await res.json();
  console.log("status:", data.status);
  if (data.status !== "done") {
    setTimeout(() => poll(url, ms), ms);   // re-arm AFTER this round finished
  }
}
// Or the fully-await version with the delay() helper from section 6:
async function pollLoop(url, ms) {
  while (true) {
    const data = await (await fetch(url)).json();
    if (data.status === "done") return data;
    await delay(ms);                        // readable, no callback in sight
  }
}

11 · Mini-project — GitHub profile card

Everything combined: parallel fetches, res.ok checks, timeout, error handling, and a sprinkle of DOM output (fully explained in Lesson 9 — today just read it as "put text on the page"). Paste this into the browser console on any page, or save with a minimal scaffold: 

// Scaffold if you want a page: <div id="card"></div><script src="app.js"></script>
async function getJSON(url) {                       // small reusable helper
  const res = await fetchWithTimeout(url, 5000);    // from section 9 — returns parsed JSON
  return res;
}

async function showProfile(username) {
  try {
    // two INDEPENDENT calls → start together, await together (section 4!)
    const [user, repos] = await Promise.all([
      getJSON(`https://api.github.com/users/${username}`),
      getJSON(`https://api.github.com/users/${username}/repos?sort=updated&per_page=3`),
    ]);

    const top = repos.map(r => `${r.name} (★${r.stargazers_count})`).join(", ");
    const summary =
      `${user.name ?? user.login} — ${user.public_repos} repos, ` +
      `${user.followers} followers. Recent: ${top}`;

    console.log(summary);
    const card = document.querySelector("#card");   // null in the bare console — that's fine
    if (card) card.textContent = summary;
  } catch (err) {
    console.error("could not load profile:", err.message);
    // err.message is "HTTP 404 Not Found" for a bad username,
    // "timed out after 5000ms" on a dead network — both paths covered.
  }
}

showProfile("torvalds");
Why this little app matters This is the exact skeleton of every frontend data flow you'll ever write: build URL → fetch with timeout → check ok → parse JSON → transform → render → catch and show errors. React (Lesson 11+) changes where this code lives, not what it does.

13 · Interview questions this lesson answers

  • "What does the async keyword do?"
    Makes the function always return a promise (values get wrapped, throws become rejections) and enables await inside it. It changes the function's contract, not its scheduling — the body still starts synchronously until the first await.
  • "What does await do? Does it block?"
    It suspends only the enclosing async function until the promise settles, returning the value or throwing the rejection. The thread is not blocked — other code, events and rendering continue. The continuation resumes via the microtask queue.
  • "How do you run async operations in parallel with async/await?"
    Start them all first (collect the promises), then await Promise.all([...]). Writing await before each call serialises them — the classic accidental-serial mistake.
  • "Why doesn't fetch reject on a 404?"
    fetch's promise reflects the network conversation, not HTTP semantics. Any response received — even 500 — is fulfillment; only network-level failures (offline, DNS, CORS, abort) reject. You must check res.ok/res.status yourself.
  • "How do you cancel or time out a fetch?"
    Pass an AbortController's signal in the options and call controller.abort() — from a setTimeout for timeouts, or when a newer request supersedes an old one. The fetch promise rejects with an AbortError.
  • "setTimeout vs setInterval for repeated async work?"
    setInterval fires on a fixed clock even if the previous run hasn't finished, so slow work can overlap/pile up. Recursive setTimeout (or an await delay() loop) schedules the next run only after the current one completes — safer for polling.
