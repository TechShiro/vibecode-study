Modules, npm & Tooling

How JavaScript went from copy-pasted script tags to a real ecosystem — imports, packages, and the build tools every project you'll ever join relies on.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 8 of 24. Index

1 · The mess before modules

Java has had packages and import since day one — every class lives in a namespace, and the compiler wires dependencies. Early JavaScript had nothing. You "structured" a project as a stack of script tags: 

<script src="utils.js"></script>
<script src="cart.js"></script>   <!-- must come AFTER utils.js, or crash -->
<script src="app.js"></script>    <!-- must come last... good luck at 40 files -->

Every top-level variable in every file landed in one shared global scope. Two consequences:

  • Global-scope pollution. utils.js defines var format = ...; three weeks later report.js also defines format — and silently overwrites the first. No error, just wrong behaviour somewhere far away. Imagine Java where every class's fields were static fields on one giant class shared by the whole program.
  • Ordering pain. Dependencies existed only in your head. Reorder the script tags and things explode with undefined is not a function. Nothing declared "cart.js needs utils.js".

A module system fixes both: each file gets its own scope (nothing leaks unless exported), and each file declares what it needs (imports), so load order is computed, not hand-maintained. JS ended up with two module systems — CommonJS (Node's original, 2009) and ES Modules (the official standard, 2015) — and you will meet both.

2 · ES Modules (ESM) — the standard

An ES module is any file using import/export. In the browser you opt in with <script type="module" src="app.js">; in Node with the .mjs extension or "type": "module" in package.json. Two kinds of exports: 

// ---- math.js — NAMED exports: a module can have many ----
export const PI = 3.14159;
export function area(r) { return PI * r * r; }

function helper() { }              // NOT exported → invisible outside this file.
                                   // That's encapsulation — like package-private in Java.

// alternative style: declare first, export a list at the bottom
export { PI as CIRCLE_PI };        // can rename on the way out

// ---- logger.js — DEFAULT export: at most ONE per module ----
export default function log(msg) { console.log(`[app] ${msg}`); }
// "this module basically IS one thing" → default. A grab-bag of utils → named.

And every import form you'll encounter in real code:

// named — braces, names must match the export (destructuring-LIKE, not destructuring)
import { PI, area } from "./math.js";

// named + rename — dodge a name clash
import { area as circleArea } from "./math.js";

// namespace — everything under one object, like a Java static import of a class
import * as math from "./math.js";
math.area(2);

// default — NO braces, and YOU pick the local name
import log from "./logger.js";
import whateverIWant from "./logger.js";   // same function — name is yours

// default + named together (you'll see this constantly with React)
import React, { useState } from "react";

// side-effect only — run the module, import nothing (polyfills, global CSS)
import "./setup.js";

// re-export — barrel files (index.js) that gather a folder's public API
export { area } from "./math.js";
export * from "./strings.js";
Gotcha import { log } from "./logger.js" fails if log was a default export — braces mean named. The reverse mistake (no braces for a named export) imports undefined-ish errors too. When an import mysteriously arrives as undefined, check default-vs-named first. It is the most common beginner module bug.

Dynamic import is the escape hatch when a static top-of-file import won't do — import("path") is a function-like call, available anywhere, returning a promise for the module's namespace object: 

button.addEventListener("click", async () => {
  const { drawChart } = await import("./charts.js");  // loaded ONLY when clicked
  drawChart();
});
// This is how "lazy loading" / code-splitting works — heavy code ships
// only to users who need it. React.lazy (Lesson 14) is built on this.

3 · CommonJS (CJS) — Node's original system

Before the standard existed, Node.js invented its own: require() to import, module.exports to export. Millions of packages and most Node tutorials still use it, so you must read it fluently: 

// math.js — CommonJS exports
const PI = 3.14159;
function area(r) { return PI * r * r; }
module.exports = { PI, area };        // export an object with both
// or single-value style:  module.exports = area;

// app.js — CommonJS imports
const { PI, area } = require("./math.js");   // THIS one is real destructuring
const math = require("./math.js");           // or grab the whole object

Where you'll meet each: browsers understand only ESM. Modern frontend code and modern Node are ESM. Older Node codebases, many npm packages, and most config files you'll copy-paste (module.exports = {...}) are CJS. NestJS (Lesson 20) compiles TypeScript to CJS by default. Both work; ESM is the direction of travel.

Interview one-liner "ESM is static — the dependency graph is known before any code runs, which enables tree-shaking and live bindings, and it supports top-level await. CommonJS is dynamic and synchronous — require is just a function returning a copied exports object. Browsers only speak ESM; Node speaks both."

5 · npm — the package manager

npm is Java's Maven Central + the mvn tool in one: a public registry of ~3 million packages, and a CLI that installs them and records what you depend on. The record lives in package.json — your project's pom.xml: 

{
  "name": "qhess-web",
  "version": "0.1.0",
  "type": "module",                      // .js files are ESM
  "scripts": {                           // runnable commands — see below
    "dev": "vite",
    "build": "vite build",
    "lint": "eslint ."
  },
  "dependencies": {                      // needed AT RUNTIME, ships to production
    "express": "^4.19.2"
  },
  "devDependencies": {                   // needed only while DEVELOPING/BUILDING
    "vite": "^5.2.0",                    // bundler, eslint, test runner, typescript…
    "eslint": "^9.0.0"
  }
}

The commands you'll actually type:

npm init -y                 # create a package.json
npm install express         # add runtime dep (writes to dependencies)
npm install -D vite         # add dev-only dep (-D → devDependencies)
npm install                 # fresh clone? install EVERYTHING listed
npm run dev                 # run a script from "scripts"
npx cowsay "hi"             # run a package's CLI without permanent install

npm scripts are the project's command palette — like Maven goals. npm run build runs whatever the "build" script says, with node_modules/.bin on the PATH, so locally-installed CLIs work. Convention: every JS repo you clone answers to npm install then npm run dev. npx runs a package binary directly (downloading it temporarily if needed) — that's why setup docs say things like npx create-vite@latest.

6 · Semver and the lockfile

Versions follow semantic versioning: MAJOR.MINOR.PATCH = 4.19.2.

  • MAJOR — breaking changes: upgrading may require code changes;
  • MINOR — new features, backwards-compatible;
  • PATCH — bug fixes only.

The prefix in package.json says how far npm may drift when installing:

SpecMeaningAcceptsRejects
^4.19.2same MAJOR (the npm default)4.19.3, 4.20.05.0.0
~4.19.2same MINOR — patches only4.19.94.20.0
4.19.2exactly this version4.19.2anything else

Ranges create a reproducibility problem: ^4.19.2 could give teammates different versions on different days. The fix is package-lock.json — an auto-generated file recording the exact resolved version (and integrity hash) of every package and every package's packages. Commit it. With a lockfile present, npm install (and its stricter CI cousin npm ci) reproduces the identical tree everywhere. package.json states your intent ("any 4.x"), the lockfile records the outcome ("4.19.2, hash sha512-…").

And node_modules — the folder npm installs into — is famously huge because it holds your dependencies' dependencies' dependencies, flattened onto disk. It is disposable and machine-specific: never commit it (.gitignore it), never email it; npm install rebuilds it from the lockfile anytime. Delete-and-reinstall is the JS equivalent of "turn it off and on again", and it works surprisingly often.

Java parallel package.json ≈ pom.xml dependencies; package-lock.json ≈ Gradle's lockfile / effective resolved versions; node_modules ≈ the local ~/.m2 cache, except copied into every project — which is why it's gigabytes across your machine. devDependencies ≈ Maven's test/provided-scope idea: needed to build, absent at runtime.

7 · Tooling — what actually happens to your code

Between "code I write" and "code the browser runs" sits a pipeline. Java has one too — javac, JAR packaging, maybe ProGuard — you just met it in one tool. JS grew each stage separately, so job posts name-drop them all. Here's the honest map:

  • Dev server — serves your files locally at localhost:5173, auto-reloading the browser when you save (hot module replacement, HMR). This is why npm run dev is the first command of every workday.
  • Bundler — follows your import graph and combines hundreds of modules into a few optimised files for production, so the browser doesn't make 500 tiny requests. It also lets you import npm packages and non-JS assets (CSS, images) as modules.
  • Transpiler (Babel & friends) — rewrites modern syntax into older syntax for old browsers, source-to-source: e.g. optional chaining a?.b becomes an a == null ? undefined : a.b check. Like compiling Java 21 source so it runs on a Java 8 JVM. Also how TypeScript and JSX become plain JS.
  • Minifier — shrinks output: strips whitespace/comments, renames calculateTotal to t. Purely for download size; behaviour unchanged.
  • Tree-shaking — dead-code elimination powered by ESM's static imports: import one function from lodash, ship one function, not the library. This is a headline reason ESM beats CJS for frontend code.
  • Source maps — generated .map files that let DevTools show your original readable code while the browser actually runs the minified bundle. Why your debugger isn't gibberish.

Vite is the modern default that wraps all of the above: instant dev server (it serves native ESM in dev, bundling only for production builds) plus an optimised production pipeline. It's what you'll use for React. webpack was the previous-generation bundler that did the same job with heavy configuration — you'll meet it in older codebases and interview questions ("what does a bundler do?"), rarely in new projects. One command scaffolds a working setup: 

npm create vite@latest my-app     # pick a template (vanilla / react / react-ts)
cd my-app
npm install
npm run dev                       # → http://localhost:5173 with hot reload
npm run build                     # → dist/ folder of minified, tree-shaken files

8 · ESLint & Prettier — the code police and the code stylist

Two tools, two different jobs, always mentioned together, endlessly confused:

  • ESLint finds problems: unused variables, using a variable before definition, == where you meant ===, missing await. It's static analysis — the closest thing dynamic JS has to javac's compile errors plus SpotBugs. Rules are configurable; frameworks ship recommended sets.
  • Prettier enforces formatting: quotes, semicolons, line width, indentation. It doesn't judge your logic — it rewrites layout so the whole team's code looks identical and style debates die in code review.
npm install -D eslint prettier
npx eslint .              # report problems (many are auto-fixable with --fix)
npx prettier --write .    # reformat every file in place
# In real teams both run automatically: on save (editor) and on commit (hooks/CI).

9 · A short, honest TypeScript teaser

TypeScript = JavaScript + a static type layer, transpiled to plain JS before running. Everything you've learned is valid TS; TS adds the compile-time checking your Java instincts miss: 

// TypeScript
function area(r: number): number {        // param + return types, Java-style
  return Math.PI * r * r;
}
area("5");                                // ✗ compile error BEFORE running —
                                          // plain JS would happily coerce and misbehave

interface User { id: number; name: string; email?: string }   // shape types; ? = optional
const u: User = { id: 1, name: "Krish" };

The honest part: types vanish at runtime (no runtime checks — it's not Java's JVM verification), there's a learning curve around its type system, and small scripts don't need it. But every serious codebase you'll touch professionally uses it, and in this track NestJS (Lesson 20) and Drizzle (Lesson 23) are TypeScript-first — you'll get a proper primer there. For now, when you see : number or interface in docs, you can read it.

10 · Interview questions this lesson answers

  • "Why do we need modules in JavaScript?"
    Without them every file shares one global scope — name collisions overwrite silently — and dependency order is maintained by hand via script-tag order. Modules give per-file scope with explicit exports/imports, so encapsulation is real and load order is derived from the declared dependency graph.
  • "Difference between ESM and CommonJS?"
    ESM: standard import/export, static (analyzable before execution → tree-shaking), live read-only bindings, async loading with top-level await, works in browsers. CJS: require/module.exports, dynamic and synchronous, exports copied at require time, Node-only.
  • "Default export vs named export?"
    Named: many per module, imported with braces and matching names (renameable via as). Default: at most one per module, imported without braces under any local name. Mixing up braces is the classic "my import is undefined" bug.
  • "What do ^ and ~ mean in package.json? What is package-lock.json for?"
    ^ allows minor+patch updates within the major version; ~ allows patch updates only; a bare version pins exactly. The lockfile records the exact resolved version of the entire dependency tree so every machine and CI installs identical code — commit it.
  • "dependencies vs devDependencies?"
    dependencies are required at runtime and installed in production; devDependencies (bundler, linter, test tools, TypeScript) are needed only to develop and build, and production installs can skip them.
  • "What does a bundler do? What is tree-shaking?"
    A bundler follows the import graph and combines modules into optimised files, transpiling and minifying along the way. Tree-shaking is dead-code elimination — possible because ESM imports are static, so unused exports are provably unreachable and get dropped from the bundle.
  • "ESLint vs Prettier?"
    ESLint is static analysis for correctness problems (unused vars, suspicious patterns); Prettier is an opinionated formatter for layout. Lint catches bugs, Prettier ends style arguments; teams run both automatically.
