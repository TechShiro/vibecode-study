The Event Loop, Callbacks & Promises

JavaScript has one thread and never waits — this lesson explains how that's even possible, and it's the single most-asked JS interview topic.

Track goal: Full-stack web dev — JS → React/Next → Express/Nest → Postgres/Drizzle. This is Lesson 6 of 24. Index

1 · One thread, no waiting — the puzzle

In Java, when you need to do two things at once — download a file and keep the UI responsive — you spawn a Thread (or use an ExecutorService). Java's answer to concurrency is more threads.

JavaScript's answer is stranger: your code runs on exactly one thread. One call stack. One thing executing at any instant. And yet a browser tab fetches data, runs timers, and reacts to clicks all "at the same time" without freezing. How?

The trick: JS itself never does the slow work. It delegates slow work (network, timers, disk) to the host environment — the browser or Node.js — which does have background machinery. JS just says "do this, and when you're done, hand me a function to run." That function is a callback, and the machinery that feeds finished callbacks back onto the one thread is the event loop.

Java parallel Think of a single-threaded ExecutorService processing a task queue, where blocking I/O is never done on that thread — it's handed to NIO/OS machinery that later submits a new task to the queue with the result. That's essentially the JS runtime. (Node.js literally works this way: one JS thread + a C library called libuv doing async I/O underneath.)

2 · Blocking vs non-blocking

A blocking call sits on the thread until it finishes. In Java that's fine — other threads keep running. In JS it's a disaster: block the one thread and everything stops — no clicks, no rendering, no timers. The page is frozen. 

// BLOCKING (never do this) — a busy-wait "sleep"
function sleepBadly(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) { }   // spins on the ONE thread; page frozen for ms
}

// NON-BLOCKING — delegate to the host, come back later
setTimeout(() => console.log("2 seconds passed"), 2000);
console.log("this prints IMMEDIATELY — we did not wait");

setTimeout doesn't pause anything. It registers a timer with the host ("call me back in 2000 ms") and returns instantly. The one thread moves on. This is why nearly every slow API in JS is asynchronous: it takes a callback (or returns a promise) instead of making you wait.

Interview one-liner "JavaScript is single-threaded and non-blocking: slow operations are delegated to the host environment, and their callbacks are queued and executed later by the event loop. Concurrency in JS is achieved by scheduling, not by threads."

3 · The runtime picture — four moving parts

Everything about async JS reduces to four components. Learn this diagram cold — you will be asked to explain it.

  • Call stack — where JS actually executes, one frame per function call, exactly like the JVM stack. Only one stack: single-threaded.
  • Web APIs / host — the browser's (or Node's) machinery: timers, network (fetch), DOM events. This is where the "waiting" happens, off the JS thread.
  • Macrotask queue (a.k.a. callback queue / task queue) — finished host work parks its callback here: setTimeout/setInterval callbacks, click handlers, I/O callbacks.
  • Microtask queue — a separate, higher-priority queue for promise reactions (.then/.catch/.finally) and queueMicrotask().

The event loop algorithm, in plain words — this is the answer interviewers want:

// pseudo-code of the event loop
while (true) {
  run synchronous code until the call stack is empty;
  while (microtaskQueue is not empty)      // drain COMPLETELY,
      run next microtask;                  // even ones added mid-drain
  take ONE task from the macrotask queue and run it;
  (browser may render here);
}

4 · The truth about setTimeout(fn, 0)

setTimeout(fn, 0) does not run fn immediately, and not even "after 0 ms". It means: "put fn in the macrotask queue as soon as possible." It still must wait for (1) all current synchronous code to finish, and (2) the entire microtask queue to drain. The delay is a minimum, never a guarantee — if the stack is busy for 3 seconds, your "0 ms" callback runs after 3 seconds. 

console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");
// A, C, B — always. Zero delay ≠ immediate; it means "next macrotask turn".

5 · Output-ordering drills — the classic interview question

Rule of thumb: sync first, then all microtasks, then macrotasks. Predict before you read the answer.

// Drill 1 — the canonical one
console.log("1");
setTimeout(() => console.log("2"), 0);          // macrotask
Promise.resolve().then(() => console.log("3")); // microtask
console.log("4");
// Output: 1, 4, 3, 2
// sync (1,4) → microtasks (3) → macrotasks (2)
// Drill 2 — microtasks chain before the timer fires
setTimeout(() => console.log("timeout"), 0);
Promise.resolve()
  .then(() => console.log("then 1"))
  .then(() => console.log("then 2"));   // added DURING the drain — still runs first
console.log("sync");
// Output: sync, then 1, then 2, timeout
// The microtask queue is drained completely, even tasks queued mid-drain.
// Drill 3 — mixed nesting
console.log("start");
setTimeout(() => {
  console.log("timer");
  Promise.resolve().then(() => console.log("micro inside timer"));
}, 0);
Promise.resolve().then(() => {
  console.log("micro");
  setTimeout(() => console.log("timer inside micro"), 0);
});
console.log("end");
// Output: start, end, micro, timer, micro inside timer, timer inside micro
// After EACH macrotask, microtasks drain again — so "micro inside timer"
// beats the second timer even though both were queued around the same time.
Gotcha "Promise code is async" is only half-true. The executor function you pass to new Promise(...) runs synchronously, immediately. Only the .then reactions are deferred to the microtask queue. new Promise(() => console.log("now")) prints before the next line of your script even runs its console.log.

6 · Callbacks — the original async tool

A callback is just a function you hand to someone else to call later — you've met this idea with Comparator or Runnable in Java. For async work, Node.js standardised the error-first callback convention: the callback's first parameter is the error (or null), the second is the result. Why? Because with async code you can't try/catch around the call site — by the time the failure happens, your call has long returned. The error must travel inside the callback. 

// Error-first convention: callback(err, result)
function readUser(id, callback) {
  setTimeout(() => {                         // pretend this is a DB call
    if (id <= 0) callback(new Error("bad id"));      // failure path
    else callback(null, { id, name: "Krish" });      // success: err is null
  }, 300);
}

readUser(7, (err, user) => {
  if (err) { console.error("failed:", err.message); return; }  // ALWAYS check first
  console.log("got", user.name);
});

Callbacks work — until steps depend on each other. Fetch a user, then their orders, then the first order's invoice. Each step nests inside the previous callback, and each needs its own error check: 

// CALLBACK HELL / pyramid of doom — grows rightward, error handling everywhere
readUser(7, (err, user) => {
  if (err) return handle(err);
  readOrders(user.id, (err, orders) => {
    if (err) return handle(err);
    readInvoice(orders[0].id, (err, invoice) => {
      if (err) return handle(err);
      sendEmail(user.email, invoice, (err) => {
        if (err) return handle(err);
        console.log("done!");        // four levels deep for FOUR steps
      });
    });
  });
});

Three real problems, not just ugliness:

  • Rightward drift — sequential logic reads diagonally instead of top-to-bottom.
  • Repeated error plumbing — every level re-checks err; forget once and failures vanish silently.
  • Inversion of control — you hand your function to their code and must trust it calls you exactly once, not zero or five times. Promises fix precisely this with a guarantee.

7 · Promises — a receipt for a future value

A Promise is an object representing a value that isn't ready yet. Analogy: order at a food counter and get a token. The token is not the food — it's a claim on future food. You can hold it, pass it around, and register what should happen when your number is called (food arrives) or the kitchen fails (order cancelled).

A promise is always in exactly one of three states, and the transition is one-way and permanent:

  • pending — work in progress, no value yet;
  • fulfilled — done, has a value (delivered to .then);
  • rejected — failed, has a reason, usually an Error (delivered to .catch).

Once settled (fulfilled or rejected) a promise never changes again — call resolve twice and the second call is silently ignored. That's the fix for the "did they call my callback twice?" trust problem. 

// Creating a promise: the EXECUTOR runs synchronously, right now.
const p = new Promise((resolve, reject) => {
  setTimeout(() => {
    const ok = Math.random() > 0.3;
    if (ok) resolve("🍜 order ready");     // → fulfilled
    else    reject(new Error("kitchen fire")); // → rejected
  }, 500);
});

p.then(value => console.log("got:", value))     // success handler
 .catch(err  => console.error("oops:", err.message)) // failure handler
 .finally(() => console.log("either way: cleanup")); // runs on BOTH paths, gets no value
Java parallel A Promise is JS's CompletableFuture. then ≈ thenApply, catch ≈ exceptionally, finally ≈ whenComplete, Promise.all ≈ CompletableFuture.allOf. Big difference: JS promise reactions always run on the same single thread, via the microtask queue — there is no thread pool to configure.

8 · Chaining — the part people get wrong

.then() returns a new promise, whose fate depends on what your handler returns. This is the whole engine of chaining, and the #1 source of promise bugs. Three cases: 

fetchNumber()                       // promise of 7
  .then(n => n * 2)                 // CASE 1: return a plain value → next then gets 14
  .then(n => fetchSquare(n))        // CASE 2: return a PROMISE → chain WAITS for it,
                                    //         next then gets its resolved value (196)
  .then(sq => { throw new Error("nope"); })  // CASE 3: throw → next .catch gets it
  .catch(err => console.error(err.message));

Case 2 is the magic: returning a promise from .then makes the chain pause until it settles, then flattens the result — you never get a promise-of-a-promise. Sequential async steps become a flat, top-to-bottom pipeline. Callback hell, rewritten: 

readUser(7)
  .then(user   => readOrders(user.id))     // each step RETURNS the next promise
  .then(orders => readInvoice(orders[0].id))
  .then(invoice => sendEmail(invoice))
  .then(()     => console.log("done!"))
  .catch(err   => handle(err));            // ONE catch handles a failure at ANY step

Error propagation: a rejection skips every following .then and falls through to the nearest .catch — exactly like a Java exception skipping statements until a catch block. And .catch itself returns a promise: if your catch handler returns normally, the chain is "healed" and continues fulfilled — like a caught Java exception letting the method carry on.

Gotcha — the two classic chaining mistakes 1. Forgetting to return. .then(user => { readOrders(user.id); }) — no return, so the chain does NOT wait; the next .then runs immediately with undefined, and errors from readOrders escape the chain entirely. 2. Nesting instead of chaining. Calling .then inside another .then handler recreates the pyramid of doom with promises. Always return the inner promise and keep the chain flat.

9 · Promise.resolve and Promise.reject

Shortcuts for making already-settled promises — handy for tests, caches, and normalising APIs:

Promise.resolve(42).then(v => console.log(v));       // 42 (on a microtask)
Promise.reject(new Error("no")).catch(e => console.log(e.message));

// Real use: a cache that returns the SAME shape either way
const cache = new Map();
function getUser(id) {
  if (cache.has(id)) return Promise.resolve(cache.get(id)); // instant, but still a promise
  return fetchUser(id).then(u => { cache.set(id, u); return u; });
}
// Callers always do getUser(1).then(...) — cached or not. Consistent contract.

Bonus: Promise.resolve(somePromise) returns that promise unchanged — useful for wrapping a "promise or plain value" input into a guaranteed promise.

10 · Combinators — running promises together

Four static methods take an array of promises and combine them. Knowing which to pick when is a favourite interview question.

const p1 = fetchUser(1);        // pretend: 300 ms
const p2 = fetchUser(2);        // pretend: 500 ms
const p3 = fetchUser(3);        // pretend: fails at 100 ms

// all — everything must succeed; results in the SAME ORDER as input
Promise.all([p1, p2])
  .then(([u1, u2]) => console.log(u1, u2))   // waits ~500 ms (the slowest)
  .catch(err => console.error(err));         // FAIL-FAST: first rejection rejects all

// allSettled — never rejects; reports every outcome
Promise.allSettled([p1, p3]).then(results => {
  // [ {status:"fulfilled", value:...}, {status:"rejected", reason:...} ]
  for (const r of results)
    console.log(r.status === "fulfilled" ? r.value : r.reason);
});

// race — settles like the FIRST to settle, success OR failure
Promise.race([p1, p3]).catch(e => console.log("p3 lost the race by failing first"));

// any — first SUCCESS wins; ignores rejections unless ALL reject
Promise.any([p3, p1]).then(u => console.log("first success:", u));
// if every promise rejects → rejects with an AggregateError holding all reasons
CombinatorResolves whenRejects whenUse case
Promise.allALL fulfill (array of values, input order)ANY rejects (fail-fast)Parallel fetches where every result is required — e.g. user + posts + settings for one page
Promise.allSettledALL settle (array of {status, value/reason})NeverBatch jobs where partial failure is fine — e.g. send 50 emails, report which failed
Promise.raceFIRST settles fulfilledFIRST settles rejectedTimeouts: race the real work against a timer that rejects

// The classic race pattern: a timeout for any promise
function withTimeout(promise, ms) {
  const timer = new Promise((_, reject) =>
    setTimeout(() => reject(new Error(`timed out after ${ms}ms`)), ms));
  return Promise.race([promise, timer]);
}
withTimeout(fetchUser(1), 2000)
  .then(u => console.log(u))
  .catch(e => console.error(e.message));

11 · Promisifying a callback API

Old callback-style APIs and modern promise chains don't mix well, so you'll often wrap the old style in a promise once, then enjoy chains (and next lesson, await) forever. The pattern: return a new Promise, and inside the executor, translate callback outcomes into resolve/reject. 

// Before: error-first callback API
function readUser(id, cb) { /* calls cb(err, user) as in section 6 */ }

// After: promisified wrapper
function readUserP(id) {
  return new Promise((resolve, reject) => {
    readUser(id, (err, user) => {
      if (err) reject(err);       // error-first arg → rejection
      else resolve(user);         // result arg → fulfillment
    });
  });
}

// A generic promisify — works on ANY fn whose last arg is an error-first callback
function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) => {
      fn(...args, (err, result) => err ? reject(err) : resolve(result));
    });
}
const readUserP2 = promisify(readUser);
readUserP2(7).then(u => console.log(u.name)).catch(console.error);
// Node.js ships this exact helper as util.promisify.
Interview one-liner "Promisifying means wrapping a callback-based API in a function that returns a Promise: the executor calls the original API and maps its error-first callback to reject/resolve. Node provides util.promisify for exactly this."

12 · Interview questions this lesson answers

  • "Explain the event loop."
    JS runs on one call stack. Slow operations are delegated to host APIs; their callbacks are queued — promise reactions in the microtask queue, timers/events in the macrotask queue. When the stack empties, the event loop drains all microtasks, then runs one macrotask, then repeats. That's why .then callbacks always beat setTimeout(…, 0).
  • "Is JavaScript single-threaded? Then how is it asynchronous?"
    Yes — one thread executes JS. Asynchrony comes from the host environment doing the waiting (timers, network) off-thread and scheduling callbacks back onto the single thread via the event loop. Concurrency by scheduling, not by parallel JS threads.
  • "What are the states of a Promise?"
    Pending, fulfilled (with a value), rejected (with a reason). The transition from pending happens once and is permanent — a settled promise never changes, and extra resolve/reject calls are ignored.
  • "Difference between Promise.all and Promise.allSettled?"
    all is fail-fast: one rejection rejects the whole thing; use it when every result is required. allSettled never rejects — it waits for everything and reports each outcome with status/value/reason; use it for batches where partial failure is acceptable.
  • "What is callback hell and how do promises solve it?"
    Deeply nested callbacks for sequential async steps, with error checks repeated at every level. Promise chaining flattens the steps into a top-to-bottom pipeline where each .then returns the next promise, and a single .catch handles a failure from any step.
  • "Does setTimeout(fn, 0) run immediately?"
    No. It queues fn as a macrotask, which runs only after all current synchronous code finishes and the microtask queue fully drains. The delay is a minimum, not a promise.
