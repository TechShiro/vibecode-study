1 · Authentication vs authorization — the bouncer analogy

Two different questions, constantly confused:

  • Authentication (authn) — who are you? The club bouncer checking your ID at the door.
  • Authorization (authz) — what are you allowed to do? Inside the club, your wristband decides whether you get into the VIP area.

They even map to different status codes from Lesson 18: failing authentication → 401 (we don't know who you are); failing authorization → 403 (we know exactly who you are, and no). Every auth system is these two steps: first establish identity, then check permissions.

2 · The core problem: HTTP is stateless

From Lesson 17 you know each HTTP request is an independent envelope — the server keeps no memory between requests. So after a successful login, how does request #2 prove it's still you? You can't send the password every time. Two industry answers exist, and "compare them" is a guaranteed interview question.

Answer A — sessions + cookies (state on the server)

On login, the server creates a record — a session — in its memory or a store (Redis, Postgres), and hands the browser only the record's random ID inside a cookie. Browsers automatically re-attach cookies to every subsequent request to that site, so each request carries the claim ticket; the server looks the session up and knows who you are. 

// sketch with express-session (npm i express-session)
import session from "express-session";

app.use(session({
  secret: process.env.SESSION_SECRET,   // signs the cookie so clients can't forge IDs
  resave: false,
  saveUninitialized: false,
  cookie: { httpOnly: true, sameSite: "lax", secure: true },  // secure = HTTPS only
}));

app.post("/login", (req, res) => {
  // ...verify credentials, then:
  req.session.userId = user.id;         // stored SERVER-side; browser gets only the session ID
  res.json({ ok: true });
});

app.get("/me", (req, res) => {
  if (!req.session.userId) return res.sendStatus(401);
  res.json({ userId: req.session.userId });
});

Answer B — JWT (state inside the token)

A JSON Web Token flips the design: the server stores nothing. On login it issues a token that itself contains the identity claims, cryptographically signed so it can't be altered. The client sends it back on each request (usually Authorization: Bearer <token>); the server just verifies the signature — no lookup needed. 

// A JWT is three base64url parts joined by dots:  header.payload.signature
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOjcsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzUzNTUwMDAwfQ . 4x7T...

// decoded header:   { "alg": "HS256", "typ": "JWT" }        — which algorithm signed it
// decoded payload:  { "sub": 7, "role": "user", "exp": ... } — the CLAIMS (sub = subject = user id)
// signature: HMAC-SHA256( header + "." + payload, SECRET )   — proves nobody tampered
Gotcha Signing is not encryption. The payload is only base64-encoded — anyone can decode and read it (paste any JWT into jwt.io). The signature guarantees integrity (untampered) and authenticity (issued by whoever holds the secret), never secrecy. So: no passwords, no sensitive data in a JWT payload. Ever.

Tokens carry an exp (expiry) claim — keep access tokens short-lived (say 15 min). The refresh-token idea: alongside the short access token, issue a long-lived refresh token stored extra-safely (httpOnly cookie, revocable server-side); when the access token expires, the client silently exchanges the refresh token for a fresh one. Short window if stolen, no constant re-logins.

Where does the client keep the token?

  • localStorage — easy to use from JS, survives tabs... and is readable by any JS on the page. One successful XSS injection and the token is stolen.
  • httpOnly cookie — JavaScript cannot read it at all (immune to XSS theft), auto-sent by the browser. Trade-off: auto-sending is exactly what CSRF exploits, so pair it with SameSite (section 8).

Interview one-liner "Sessions keep state on the server and give the client a claim-ticket cookie — easy revocation, but scaling needs a shared store. JWTs keep signed state on the client — stateless and scale-friendly, but revocation before expiry is hard. Signed ≠ encrypted: JWT payloads are readable by anyone."

3 · Passwords — hash, never encrypt, never store

Rule zero: never store plaintext passwords. But also: never encrypt them. Encryption is two-way — whoever holds the key can decrypt every password, so a leaked key = every account burned. Hashing is one-way: you can compute hash(password) but not invert it. At login you hash the attempt and compare hashes; nobody, including you, can recover the original.

Plain fast hashes (SHA-256) are still wrong for passwords — attackers brute-force billions per second on GPUs. bcrypt fixes this with two weapons:

  • Salt — a random string mixed into each hash, stored inside the output. Two users with the password hello123 get totally different hashes, and precomputed "rainbow tables" become useless.
  • Cost rounds — bcrypt is deliberately slow, and the cost is tunable: rounds 10 ≈ 2¹⁰ internal iterations, each +1 doubles the time. Milliseconds per login for you; centuries per dictionary for an attacker.
Java parallel This is exactly Spring Security's BCryptPasswordEncoder — encode() ↔ bcrypt.hash(), matches() ↔ bcrypt.compare(). Same algorithm, same salted $2b$10$... output format.

4 · The full register + login flow

npm install bcrypt jsonwebtoken
// src/services/auth.service.js
import bcrypt from "bcrypt";
import jwt from "jsonwebtoken";
import { ApiError } from "../middleware/error.js";

const users = [];        // in-memory for now — becomes a Postgres table in Lesson 21
let nextId = 1;

export const authService = {
  async register({ email, password }) {
    if (users.some(u => u.email === email))
      throw new ApiError(409, "Email already registered");        // 409 Conflict, Lesson 18

    const passwordHash = await bcrypt.hash(password, 10);         // 10 = cost rounds; salt auto-generated
    const user = { id: nextId++, email, passwordHash, role: "user" };
    users.push(user);
    return { id: user.id, email: user.email };                    // NEVER return the hash
  },

  async login({ email, password }) {
    const user = users.find(u => u.email === email);
    // same message for wrong email and wrong password — don't leak which emails exist
    if (!user) throw new ApiError(401, "Invalid credentials");

    const ok = await bcrypt.compare(password, user.passwordHash); // re-hash attempt with stored salt, compare
    if (!ok) throw new ApiError(401, "Invalid credentials");

    const token = jwt.sign(
      { sub: user.id, role: user.role },                          // claims — public, remember!
      process.env.JWT_SECRET,                                     // from .env, section 9
      { expiresIn: "15m" }
    );
    return { token };
  },
};

// routes (with zod validation from Lesson 18):
//   router.post("/register", validate(credentialsSchema), registerController)  → 201
//   router.post("/login",    validate(credentialsSchema), loginController)     → 200 { token }

5 · Auth middleware + role-based authorization

Protection is just middleware from Lesson 18: verify the token, attach the identity to req, and let the pipeline continue — or stop it with 401/403. 

// src/middleware/auth.js
import jwt from "jsonwebtoken";
import { ApiError } from "./error.js";

export function requireAuth(req, res, next) {
  const header = req.get("Authorization") ?? "";        // "Bearer eyJhbGci..."
  const token = header.startsWith("Bearer ") ? header.slice(7) : null;
  if (!token) return next(new ApiError(401, "Missing token"));

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET); // throws if forged OR expired
    req.user = { id: payload.sub, role: payload.role };        // downstream handlers just read req.user
    next();
  } catch {
    next(new ApiError(401, "Invalid or expired token"));
  }
}

// Authorization: a middleware FACTORY — takes allowed roles, returns middleware
export const requireRole = (...roles) => (req, res, next) => {
  if (!req.user) return next(new ApiError(401, "Not authenticated"));
  if (!roles.includes(req.user.role))
    return next(new ApiError(403, "Insufficient permissions"));  // 403: known, but not allowed
  next();
};

// usage — note the ORDER: authenticate first, then authorize
router.get("/notes", requireAuth, listNotes);                        // any logged-in user
router.delete("/users/:id", requireAuth, requireRole("admin"), deleteUser); // admins only
Spring parallel requireAuth is Spring Security's JWT filter in the filter chain; requireRole("admin") is @PreAuthorize("hasRole('ADMIN')"); req.user plays the role of the SecurityContext principal.

6 · CORS — the classic interview topic, explained properly

Browsers enforce the same-origin policy: JavaScript on origin A (scheme + host + port, e.g. http://localhost:5173 — your React dev server) may not read responses from origin B (http://localhost:3000 — your API) unless B explicitly opts in. Why? Because your browser attaches your cookies to requests automatically — without this rule, evil.com's scripts could call your bank's API as you and read the response.

Three facts that untangle every CORS confusion:

  • It's a browser rule. curl, Postman, and server-to-server calls never see CORS errors.
  • The request usually reaches the server fine — the browser blocks JS from reading the response. (For state-changing requests, preflight blocks sending too.)
  • The server opts in via response headers — Access-Control-Allow-Origin and friends. The fix always lives on the server, not in your fetch call.

For "non-simple" requests (e.g. Content-Type: application/json, custom headers, PUT/DELETE) the browser first sends a preflight: an OPTIONS request asking "may I send POST with these headers?" Only if the server answers with permitting headers does the real request go out. 

npm install cors
import cors from "cors";

app.use(cors({
  origin: "http://localhost:5173",   // exact allowed origin(s); "*" = anyone (fine for public read-only APIs,
                                     // but incompatible with credentials)
  credentials: true,                 // allow cookies/Authorization across origins — requires an exact origin
}));
// the package answers preflights and sets Access-Control-Allow-* headers for you

7 · Security essentials — the armour checklist

helmet — sane security headers

import helmet from "helmet";
app.use(helmet());   // one line, ~a dozen protective response headers
  • Content-Security-Policy — whitelists where scripts/styles may load from (blunts XSS).
  • Strict-Transport-Security — tells browsers "HTTPS only from now on".
  • X-Content-Type-Options: nosniff — stops browsers guessing (and mis-executing) content types.
  • Hides X-Powered-By: Express — no free recon for attackers.

Rate limiting

import rateLimit from "express-rate-limit";

app.use("/api/auth/login", rateLimit({
  windowMs: 15 * 60 * 1000,   // 15-minute window
  limit: 10,                  // max 10 attempts per IP → then 429 Too Many Requests
}));
// stops brute-forcing passwords and blunts cheap DoS; login/OTP routes get the strictest limits

Input sanitization & the injection idea

The injection family of attacks is one idea wearing many masks: user input gets interpreted as code/commands instead of data. String-concatenated SQL → SQL injection (in depth with the fix — parameterized queries — in Lesson 22). User text echoed into HTML → XSS. Input passed to a shell → command injection. The defence is always the same shape: validate at the boundary (your zod middleware from Lesson 18 already strips unknown fields and enforces types) and use APIs that keep data and code separate — parameterized queries, escaped output — rather than gluing strings.

Secrets with dotenv

# .env  — real secrets, NEVER committed (add .env to .gitignore immediately)
JWT_SECRET=change-me-to-64-random-chars
PORT=3000

# .env.example — committed: names only, no values, so teammates know what to set
import "dotenv/config";        // first import in server.js: loads .env into process.env
// (Node 20+: `node --env-file=.env server.js` does it with zero deps)
const secret = process.env.JWT_SECRET;

A secret committed once lives in git history forever — treat it as leaked and rotate it.

8 · File uploads with multer, in brief

JSON can't carry files; browsers send them as multipart/form-data, which express.json() ignores. multer is the middleware that parses it: 

import multer from "multer";
const upload = multer({
  dest: "uploads/",
  limits: { fileSize: 5 * 1024 * 1024 },     // always cap size — uploads are a DoS vector
});

app.post("/avatar", requireAuth, upload.single("avatar"), (req, res) => {
  // req.file = { path, mimetype, size, originalname... }; other form fields land in req.body
  res.status(201).json({ path: req.file.path });
});
// validate mimetype server-side; in production files go to S3-style storage, not local disk

9 · Logging — morgan, and why logs matter

app.use(morgan(process.env.NODE_ENV === "production" ? "combined" : "dev"));
// dev:      "POST /login 401 12.3ms" — short + colored, for your terminal
// combined: Apache-style with IP, timestamp, user-agent — machine-parseable for prod

Logs are how you answer "what happened at 3 a.m.?" — debugging in production, spotting attacks (1000 failed logins from one IP), and audit trails. No logs = flying blind. Bigger apps graduate to structured JSON loggers (pino, winston); the habit starts here.

10 · Testing glance — jest + supertest

supertest fires real HTTP requests at your app object in-process — no port, no running server. This is the JS equivalent of Spring's MockMvc. One structural change: export app separately from listen. 

// app.js exports the app; server.js just does: app.listen(PORT)

// __tests__/auth.test.js   (npm i -D jest supertest)
import request from "supertest";
import app from "../app.js";

describe("auth", () => {
  test("register → login → access a protected route", async () => {
    await request(app)
      .post("/api/auth/register")
      .send({ email: "k@test.dev", password: "secret123" })
      .expect(201);

    const res = await request(app)
      .post("/api/auth/login")
      .send({ email: "k@test.dev", password: "secret123" })
      .expect(200);

    await request(app)
      .get("/api/v1/notes")
      .set("Authorization", `Bearer ${res.body.token}`)   // attach the JWT
      .expect(200);
  });

  test("wrong password → 401", async () => {
    await request(app).post("/api/auth/login")
      .send({ email: "k@test.dev", password: "nope" })
      .expect(401);
  });
});

11 · When REST isn't enough — WebSockets & socket.io

HTTP is request → response: the server can never speak first. For chat, live notifications, multiplayer (hello, Qhess) that's fatal — you'd be stuck polling on a timer. A WebSocket starts as an HTTP request that upgrades into a persistent two-way TCP connection; after that, either side pushes messages any time. socket.io wraps it with auto-reconnection, rooms, and fallbacks: 

// server (npm i socket.io) — attaches to the same http server as Express
import { createServer } from "node:http";
import { Server } from "socket.io";

const httpServer = createServer(app);
const io = new Server(httpServer, { cors: { origin: "http://localhost:5173" } });

io.on("connection", (socket) => {              // EventEmitter pattern from Lesson 17
  socket.on("chat", (msg) => {
    io.emit("chat", msg);                      // broadcast to EVERY connected client — server pushes!
  });
});
httpServer.listen(3000);

// browser client
const socket = io("http://localhost:3000");
socket.emit("chat", "hello room");
socket.on("chat", (msg) => render(msg));

Rule of thumb: REST for resources and CRUD; WebSockets only for genuinely realtime, server-initiated streams.

12 · Production notes

  • NODE_ENV=production — Express skips dev niceties (and hides error details); many libraries key off it. Your code can too: verbose logs in dev, terse in prod.
  • Process manager (PM2 / systemd / containers) — Node is one process; an uncaught crash kills the whole server. pm2 start server.js -i max auto-restarts on crash and runs one instance per CPU core in cluster mode (Lesson 17: one thread per process — this is how Node uses 8 cores).
  • Reverse proxy (nginx / Caddy) — sits in front of Node: terminates HTTPS, serves static files, load-balances across instances, absorbs slow clients. Node apps rarely face the internet naked. (Set app.set("trust proxy", 1) so req.ip and rate limiting see real client IPs.)

13 · Interview questions this lesson answers

  • "Authentication vs authorization?"
    Authentication establishes identity (who are you → 401 on failure); authorization checks permissions (what may you do → 403 on failure). Authn always comes first.
  • "Sessions vs JWT — which and why?"
    Sessions: server-side state + cookie ID; instant revocation, but scaling needs a shared store, and cookies are browser-centric. JWT: signed claims on the client; stateless and great for SPAs/mobile/microservices, but revocation before expiry needs a denylist. Mitigate with short-lived access tokens + refresh tokens.
  • "Is a JWT encrypted? What does the signature give you?"
    No — the payload is readable base64. The signature gives integrity and authenticity: it proves the token was issued by the secret-holder and hasn't been modified. Never put sensitive data in the payload.
  • "How do you store passwords?"
    bcrypt-hash them (salted, tunable cost) and compare hashes at login. Not plaintext, not encrypted (keys leak), not fast hashes like SHA-256 (GPU brute-force). Salting kills rainbow tables; cost rounds make guessing expensive.
  • "Explain CORS. Why does my fetch fail but Postman works?"
    The browser's same-origin policy blocks JS from reading cross-origin responses unless the server sends Access-Control-Allow-Origin; non-simple requests trigger an OPTIONS preflight first. Postman isn't a browser, so no CORS. The fix is server-side headers (the cors middleware).
  • "What is CSRF and how does SameSite help?"
    A malicious site triggers a request to your API and the browser auto-attaches the victim's cookie. SameSite=Lax/Strict stops the browser attaching cookies on cross-site requests, killing the trick; header-borne JWTs are inherently immune since attackers can't set headers cross-origin.
  • "How would you protect a login endpoint?"
    Rate limiting per IP, bcrypt with decent cost, identical error messages for unknown email vs wrong password, input validation, helmet headers, HTTPS everywhere, and logging of failed attempts.
