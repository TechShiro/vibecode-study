2 · A request's life — "user clicks Save Note"

Interviewers love this question because it exposes whether you actually understand your stack or just scaffolded it. Narrate it top-down, layer by layer, down and back up. Here is the full journey for the capstone app you're about to build:

  1. Browser: the user types into a controlled <textarea> in a client component and hits Save. The <form action={createNote}> fires — no hand-written fetch; Next serializes the FormData and POSTs it to the server (works even before JS hydrates).
  2. Network: an HTTPS POST carries the form data plus a header identifying which server action to invoke.
  3. Next.js server: the 'use server' function createNote runs in Node. It never trusts the client — it re-validates the input (empty title? too long?) exactly as your Express middleware did in Lesson 18.
  4. Drizzle: db.insert(notes).values({...}) compiles to INSERT INTO notes (title, body) VALUES ($1, $2) — parameterized, so the injection attack from Lesson 22 is dead on arrival.
  5. pg Pool: an already-open TCP connection is borrowed from the pool (no per-request handshake), the query and parameters go over the wire.
  6. Postgres: planner picks a plan, constraints are checked (NOT NULL, FK), the row is written ACID-safely (WAL first, so a crash can't half-save it), and RETURNING sends the new row back.
  7. Back up — revalidate: the action calls revalidatePath('/'), marking the cached page stale. Next re-runs the server component, which SELECTs the fresh list.
  8. Browser again: the response carries the updated RSC payload; React reconciles it into the DOM — the diffing from Lesson 14 — and the new note appears without a full page reload.
Gotcha The most common failure in this narration: saying "the frontend saves it to the database." The browser never talks to Postgres. Credentials live only in server env vars; the client sends intent, the server decides. If you blur that boundary, the interviewer hears "doesn't get security."

3 · The capstone: DevLog — a notes app you can build in a weekend

DevLog is a personal dev journal: list notes, add a note, delete a note. Deliberately small — every file below is short enough to type, yet it exercises the entire stack: schema, migrations, server components, server actions, a client component, validation, and revalidation. Build it, deploy it, put it on the resume.

Project layout (create with npx create-next-app@latest devlog, TypeScript + App Router):

src/db/schema.ts — the whole data model:

import { pgTable, serial, text, timestamp } from 'drizzle-orm/pg-core';

export const notes = pgTable('notes', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  body: text('body').notNull().default(''),
  createdAt: timestamp('created_at', { withTimezone: true })  // timestamptz, always
    .notNull()
    .defaultNow(),
});

// the type-inference payoff from Lesson 23:
export type Note = typeof notes.$inferSelect;   // { id, title, body, createdAt }
export type NewNote = typeof notes.$inferInsert;

src/db/index.ts — one pool, one client, reused everywhere:

import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import * as schema from './schema';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// pass schema so db.query.notes.* (relational API) is typed too
export const db = drizzle(pool, { schema });

drizzle.config.ts and the migration commands:

export default defineConfig({
  schema: './src/db/schema.ts',
  out: './drizzle',
  dialect: 'postgresql',

src/app/actions.ts — the mutations, with server-side validation:

'use server';

import { db } from '@/db';
import { notes } from '@/db/schema';
import { eq } from 'drizzle-orm';
import { revalidatePath } from 'next/cache';

export async function createNote(formData: FormData) {
  const title = String(formData.get('title') ?? '').trim();
  const body  = String(formData.get('body') ?? '').trim();

  // validate on the SERVER — the client can be bypassed with curl
  if (!title || title.length > 120) {
    return { error: 'Title is required (max 120 chars).' };
  }

  await db.insert(notes).values({ title, body });
  revalidatePath('/');            // stale-mark the list page → fresh SELECT
  return { error: null };
}

export async function deleteNote(id: number) {
  await db.delete(notes).where(eq(notes.id, id));   // DELETE ... WHERE id = $1
  revalidatePath('/');
}

src/app/page.tsx — a server component reads the database directly (no API hop, no useEffect-fetch dance):

import { db } from '@/db';
import { notes } from '@/db/schema';
import { desc } from 'drizzle-orm';
import { NoteForm } from '@/components/note-form';
import { deleteNote } from './actions';

export default async function Home() {
  // runs on the server; SQL: SELECT ... ORDER BY created_at DESC
  const all = await db.select().from(notes).orderBy(desc(notes.createdAt));

  return (
    <main>
      <h1>DevLog</h1>
      <NoteForm />
      <ul>
        {all.map((n) => (
          <li key={n.id}>                       {/* keys — Lesson 11 */}
            <strong>{n.title}</strong> — {n.body}
            <form action={deleteNote.bind(null, n.id)}>
              <button>delete</button>
            </form>
          </li>
        ))}
      </ul>
    </main>
  );
}

src/components/note-form.tsx — the only client component, because it needs interactivity (pending state, showing errors):

'use client';

import { useState, useTransition } from 'react';
import { createNote } from '@/app/actions';

export function NoteForm() {
  const [error, setError] = useState<string | null>(null);
  const [pending, startTransition] = useTransition();

  return (
    <form
      action={(formData) =>
        startTransition(async () => {
          const res = await createNote(formData);   // calls the server action
          setError(res.error);
        })
      }
    >
      <input name="title" placeholder="Title" required maxLength={120} />
      <textarea name="body" placeholder="What did you learn today?" />
      <button disabled={pending}>{pending ? 'Saving…' : 'Save note'}</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
Why so little client code? This is the App Router philosophy from Lessons 15–16 paying off: the default is server components (data lives there anyway), and you opt into 'use client' only where you need state or events. The result: less JS shipped, no loading-spinner-then-fetch waterfall, and the database is one await away.
Stretch goals (pick one, not all) Add an updatedAt column and an edit form; add a tags text[] or a proper M:N tags table from Lesson 21; add auth (roll the JWT flow from Lesson 19 as a route handler, or drop in an auth library). One well-finished stretch beats three half-done ones.

4 · Same backend, Express/Nest flavour — and when you'd split

Everything in actions.ts is transport-agnostic logic: validate → Drizzle call → respond. In Lesson 18 you'd have written it as an Express route; in Lesson 20, as a Nest controller + service. Side by side: 

// EXPRESS (Lesson 18 style) — swap the in-memory array for Drizzle
app.post('/api/notes', async (req, res, next) => {
  try {
    const { title, body } = req.body;
    if (!title || title.length > 120)
      return res.status(400).json({ error: 'Title required (max 120)' });
    const [note] = await db.insert(notes).values({ title, body }).returning();
    res.status(201).json(note);        // 201 Created — Lesson 18 status codes
  } catch (err) { next(err); }         // central error middleware handles it
});

// NESTJS (Lesson 20 style) — same logic, DI-shaped
@Controller('notes')
export class NotesController {
  constructor(private readonly notesService: NotesService) {}   // DI

  @Post()
  create(@Body() dto: CreateNoteDto) {   // ValidationPipe enforces the DTO
    return this.notesService.create(dto);      // service wraps Drizzle
  }
}

Interview one-liner "I kept the API inside Next because there's a single web client — server actions give me typed, CSRF-protected mutations with zero API boilerplate. The moment a mobile app or a second consumer appears, I'd extract the service layer behind an Express or Nest REST API; the Drizzle calls move unchanged because the logic never lived in the transport layer."

5 · Deployment reality — Vercel + managed Postgres

Localhost is not a project; a URL is. The standard budget-friendly path:

  1. Database: create a free Postgres on Neon or Supabase (both are managed Postgres — same SQL you learned, someone else does backups/patches; Neon adds serverless scale-to-zero and branching). Copy the connection string.
  2. App: push the repo to GitHub, import it in Vercel. Vercel detects Next.js, builds, and deploys — server components and actions run as serverless functions.
  3. Env vars: set DATABASE_URL in Vercel's dashboard. It exists only on the server — exactly why the browser can never touch Postgres. (Anything you deliberately expose to the client needs the NEXT_PUBLIC_ prefix; a DB URL never qualifies.)
  4. Migrations: run them against the production DB as a deliberate step — locally with the prod URL, or as a CI/predeploy step: npx drizzle-kit migrate. Never auto-run push against prod: migrations are your reviewed, versioned history (Lesson 22's whole argument).
# .env.local (dev)  — and the same var set in Vercel for prod
DATABASE_URL=postgres://user:pass@ep-xyz.neon.tech/devlog?sslmode=require

# deploy checklist
git push                      # Vercel auto-builds on push
npx drizzle-kit migrate       # apply schema to the prod database
Gotcha Serverless functions can spawn many instances, and each opens DB connections — a plain pg Pool can exhaust Postgres's connection limit. Managed providers solve this with a built-in pooler (Neon's pooled connection string, Supabase's pgbouncer port). Use the pooled URL in serverless environments. Knowing this one wrinkle sounds very senior in interviews.

7 · Whole-track rapid-fire — 25 questions, crisp answers

Cover the answer, read the question aloud, answer in two sentences, then compare. Anything shaky — the lesson number is your jump-back link.

JavaScript (L1–10)

  • 1. What is a closure? A function bundled with the lexical scope it was created in, so it can read/write those variables even after the outer function returned. Powers private state, callbacks, debounce/memoize. (L2)
  • 2. Explain the event loop. JS is single-threaded; async work is handed to the platform, and finished callbacks queue up. The loop runs the stack empty, then drains all microtasks (promises), then one macrotask (timers, I/O) — which is why Promise.then beats setTimeout(0). (L6)
  • 3. == vs ===? == coerces types before comparing ('5' == 5 is true); === compares type and value. Default to ===; the only popular exception is x == null to catch null and undefined together. (L1)
  • 4. What is a Promise, and states? An object representing a future value: pending → fulfilled or rejected, settled exactly once. then/catch/finally chain; async/await is syntax over it. (L6–7)
  • 5. var vs let vs const? var is function-scoped and hoisted as undefined; let/const are block-scoped with a temporal dead zone; const forbids reassignment (not mutation of the object it points to). (L1)
  • 6. Debounce vs throttle? Debounce fires once after the events stop for N ms (search box); throttle fires at most once per N ms while events continue (scroll handler). Both are closures over a timer. (L10)

React (L11–14)

  • 7. What problem does the Virtual DOM solve? Real DOM writes are slow; React re-renders a cheap JS tree, diffs it against the previous one (reconciliation), and applies only the minimal DOM patches. (L14)
  • 8. Why do list keys matter? Keys let the differ match old and new children by identity, preserving state and DOM. Index-as-key breaks on reorder/insert — state sticks to the wrong row. Use a stable id. (L11)
  • 9. What does the useEffect dependency array do? The effect re-runs after renders where any listed dependency changed; [] means run once on mount; omitting it means every render. Stale closures and missing deps are the classic bug pair. (L12)
  • 10. Controlled vs uncontrolled inputs? Controlled: React state is the single source of truth (value + onChange) — enables instant validation. Uncontrolled: the DOM holds the value, read via ref when needed. (L13)
  • 11. What actually triggers a re-render? A state update (with a new value/reference) in the component, or a parent re-rendering. Props changing is a consequence of the parent rendering; memo is the opt-out when props are equal. (L14)

Next.js (L15–16)

  • 12. SSR vs SSG vs ISR? SSR renders per request (always fresh, slower); SSG renders at build (fastest, can go stale); ISR is SSG plus timed/on-demand regeneration — revalidatePath is on-demand ISR. (L16)
  • 13. Server vs client components? Server components render on the server only — can await the DB, ship no JS, but no hooks/events. Client components ('use client') hydrate in the browser for interactivity. Default server, opt into client at the leaves. (L15)
  • 14. What is a server action? A 'use server' function callable from forms/components; Next turns the call into a POST to your own server. Validate inside it — it is a public endpoint. (L16)

Node / Express / Nest (L17–20)

  • 15. How is Node concurrent on one thread? Non-blocking I/O: libuv hands file/network work to the OS, the event loop keeps serving other requests, callbacks run when I/O completes. Great for I/O-bound APIs; CPU-bound work blocks everyone (worker threads exist for that). (L17)
  • 16. What is Express middleware? Functions (req, res, next) in a pipeline — each can read/modify the request, respond, or pass on with next(). Logging, body parsing, auth, and the 4-arg error handler are all middleware. (L18)
  • 17. JWT vs sessions? Sessions store state server-side, cookie holds an id — easy revocation, needs a shared store to scale. JWTs are self-contained signed tokens — stateless and multi-service friendly, but revocation is hard and they must expire short. (L19)
  • 18. What is CORS? A browser rule: cross-origin responses are blocked unless the server opts in via Access-Control-Allow-Origin (preflight OPTIONS for non-simple requests). It's a browser protection — curl ignores it. (L19)
  • 19. Status codes for: created / bad input / no token / wrong role / missing? 201, 400, 401 (unauthenticated), 403 (unauthorized), 404. Server fault = 5xx. (L18–19)
  • 20. What is dependency injection in Nest? Classes declare constructor dependencies; Nest's container instantiates and supplies them (default singletons). Decouples classes and makes testing trivial — pass a mock instead. Guards → interceptors → pipes → handler → filters is the request pipeline. (L20)

SQL / Drizzle (L21–23)

  • 21. INNER vs LEFT JOIN? INNER keeps only matching rows from both sides; LEFT keeps every left row, padding missing right columns with NULL — "users and their posts, including users with none." (L21)
  • 22. What is an index and its cost? A B-tree side structure that turns scans into O(log n) lookups on WHERE/JOIN/ORDER BY columns. Cost: every write also updates the index, plus disk space — index deliberately, verify with EXPLAIN ANALYZE. (L22)
  • 23. Spell out ACID. Atomicity (all or nothing), Consistency (constraints hold before and after), Isolation (concurrent transactions don't see each other's partial work), Durability (committed survives a crash, via the WAL). (L22)
  • 24. How do you prevent SQL injection? Never concatenate user input into SQL; use parameterized queries ($1) so input is data, never code. ORMs like Drizzle parameterize by default — ' OR 1=1 -- becomes a harmless literal. (L22)
  • 25. What is the N+1 problem, and migrations vs push? N+1: one query for a list, then one per row for its relations — fix with a join or Drizzle's with: relational query. Migrations are versioned, reviewable SQL history (generate + migrate); push just syncs the schema — prototyping only. (L23)
Java parallel — your secret weapon You came into this track from Java, and it maps: DI in Nest is Spring's DI; Drizzle's schema-in-code is JPA entities without the annotation magic; the pg Pool is HikariCP; ACID and isolation levels are identical theory. Saying "this is Spring's dependency injection, same idea" in an interview shows transferable understanding — exactly what off-campus screeners look for.

8 · Interview questions this lesson answers

  • Q. "Walk me through your project."
    Stack sentence first (§1 one-liner), then the Save-Note lifecycle from §2 top-down: client form → server action validates → Drizzle emits parameterized SQL → pooled connection → Postgres commits → revalidate → RSC re-renders → React reconciles. End with one decision you'd defend and one thing you'd improve.
  • Q. "Why did you choose this stack?"
    Next.js: one codebase for UI and API with server rendering. Postgres: relational data wants constraints, joins, and transactions — plus free managed hosting. Drizzle: type safety over the SQL I already understand, with versioned migrations. Each answer names a benefit I used, not a buzzword.
  • Q. "How would you support a mobile app tomorrow?"
    Extract the service layer behind a separate Express/Nest REST API with JWT auth and CORS; the Drizzle-backed logic moves unchanged because it never depended on the transport (§4's table is the tradeoff answer).
  • Q. "How does your app go from code to production?"
    Git push → Vercel builds and deploys the Next app as serverless functions; DATABASE_URL is a server-side env var pointing at managed Postgres (Neon) through a pooled connection; schema changes ship as drizzle-kit migrations run as a deliberate deploy step.
  • Q. "Where does validation live and why?"
    Client-side for UX (instant feedback), but authoritative validation is server-side in the action/route, because any client can be bypassed with curl. Constraints in Postgres (NOT NULL, CHECK, FK) are the final safety net.
