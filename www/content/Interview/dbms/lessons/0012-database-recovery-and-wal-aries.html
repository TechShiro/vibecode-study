Database Crash Recovery & ARIES Algorithm

How databases recover from catastrophic crashes without losing a single committed transaction using WAL and ARIES.

← Back to Course IndexModule C – Transactions & Concurrency

1 · The One Idea

Writing dirty database pages directly to disk on every single UPDATE is impossibly slow (thousands of random I/O operations per second). To achieve high performance, modern databases cache pages in RAM (the Buffer Pool) and write modifications out asynchronously. But what happens if the power cord is yanked out while dirty pages reside only in RAM? The DBMS guarantees Durability via the Write-Ahead Logging (WAL) protocol and the ARIES recovery algorithm.

2 · Buffer Pool Management: STEAL vs NO-STEAL, FORCE vs NO-FORCE

PolicyDefinitionImpact on Recovery
STEAL The DBMS can write uncommitted dirty pages to disk to free up buffer pool memory for other transactions. Requires UNDO logging (to roll back uncommitted changes if crash occurs).
NO-STEAL The buffer manager NEVER writes a page to disk until the transaction has committed. No undo needed, but buffer memory can exhaust on large transactions.
FORCE All pages updated by a transaction MUST be flushed to disk before COMMIT returns. No REDO needed, but causes massive random disk write bottlenecks.
NO-FORCE Transaction can commit as soon as its WAL records are flushed; dirty data pages stay in RAM. Maximum performance! Requires REDO logging during crash recovery.

Every high-performance database (Postgres, MySQL InnoDB, Oracle, SQL Server) implements STEAL + NO-FORCE.

3 · The Write-Ahead Logging (WAL) Protocol

The Fundamental WAL Rule

Before a dirty data page can be written from RAM to non-volatile disk storage, all log records describing the updates on that page MUST already be written and flushed to durable disk storage (PageLSN ≤ FlushedLSN).

Log records are strictly sequential (append-only), converting random data modifications into high-speed sequential disk I/O.

4 · Log Sequence Numbers (LSN) & Checkpointing

  • LSN (Log Sequence Number): Monotonically increasing 64-bit integer assigned to every log record.
  • PageLSN: Header field stored in every physical data page indicating the LSN of the latest update applied to that page.
  • Fuzzy Checkpointing: Periodically, the DBMS writes a checkpoint record containing the Dirty Page Table (DPT) (list of dirty pages in RAM and their RecLSN - first unwritten log LSN) and the Active Transaction Table (TT). This avoids scanning gigabytes of historic logs during crash recovery.

5 · The ARIES Algorithm (3 Recovery Phases)

Developed by C. Mohan at IBM, ARIES (Algorithms for Recovery and Isolation Exploiting Semantics) executes in 3 sequential phases upon database restart:

Phase 1: Analysis Phase (Scan Forward)
Phase 2: Redo Phase ("Repeating History")
Phase 3: Undo Phase (Rollback Losers)
1

Analysis Phase

Scans the log forward starting from the last checkpoint record to the end of the log. Identifies which transactions were active at crash time (the Losers) and reconstructs the Dirty Page Table (DPT) and Transaction Table.

2

Redo Phase ("Repeating History")

Finds the smallest RecLSN in the DPT and scans forward to the end of the log, reapplying ALL logged updates (even those of aborted transactions) to restore the exact buffer cache state at the moment of the crash.

3

Undo Phase

Scans backward from crash point, reversing the operations of all active Loser transactions. As operations are undone, ARIES writes Compensation Log Records (CLRs) so that if another crash occurs during recovery, the undo work is never repeated!
