1 · The One Idea

When you run SELECT u.name, o.total FROM users u JOIN orders o ON u.id = o.user_id WHERE u.country = 'IN';, the database does not naively run nested loops. It is a compiler! The DBMS translates the declarative SQL query into an Abstract Syntax Tree (AST), applies mathematical rewrite rules (Logical Optimization), computes estimated disk I/O and CPU costs for hundreds of physical permutations (Cost-Based Physical Optimization), and streams results through an iterator tree (the Volcano Model).

3 · Logical Optimization: Rule-Based Transformations

The logical optimizer applies relational algebra equivalence theorems to simplify queries without needing table data statistics:

  • Predicate Pushdown (Filter Early): Pushes WHERE filters down before joins: σcountry='IN'(Users ⋈ Orders) becomes (σcountry='IN'(Users)) ⋈ Orders. This reduces the number of rows entering the expensive join by 99%!
  • Projection Pushdown: Drops unneeded columns as early as possible to minimize memory buffer usage.
  • Constant Folding & Dead Branch Elimination: E.g., simplifying 1 + 1 to 2, or eliminating WHERE 1 = 0.

4 · Physical Join Algorithms Compared

Join AlgorithmComplexityHow It WorksBest When
Nested Loop Join $O(M imes N)$ For each outer tuple, scan every inner tuple. Outer table is tiny (< 100 rows) and no indexes exist.
Index Nested Loop Join $O(M imes \log N)$ For each outer tuple, perform a B+ tree index lookup into the inner table. Inner table has a clustered or secondary index on the join column.
Sort-Merge Join $O(M \log M + N \log N)$ Sort both relations on join key, then scan both concurrently like merging two sorted arrays. Both inputs are already sorted (e.g. from an index) or join condition is range-based.
Grace Hash Join $O(M + N)$ Hash build the smaller table into an in-memory hash table; probe it sequentially with the larger table. Large tables, unsorted data, equality join conditions (=).

5 · The Volcano Iterator Execution Model

Introduced by Goetz Graefe, the Volcano Iterator Model executes queries pipelined tuple-at-a-time. Every execution operator (Scan, Filter, Join, Sort, Aggregate) implements a uniform interface:

  • open(): Initializes operator state and allocates memory buffers.
  • next(): Pulls and returns the single next tuple matching the criteria, or EOF.
  • close(): Cleans up and frees memory.

Benefit: Results can stream immediately to the client without materializing gigabytes of intermediate relations in RAM!

  • Seq Scan / Table Scan: Scans every single block of the table sequentially. High cost if table is large.
  • Index Scan: Traverses the B+ Tree to find matching leaf nodes, then performs random I/O lookups into table pages.
  • Bitmap Index Scan + Bitmap Heap Scan: First collects matching page offsets into an in-memory bitmap, sorts them physically, and reads table blocks sequentially to eliminate random disk seek latency.
