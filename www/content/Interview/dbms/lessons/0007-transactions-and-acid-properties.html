Transactions & ACID Properties

The mathematical contract that guarantees reliable concurrent database modifications.

← Back to Course IndexModule C – Transactions & Concurrency

1 · The One Idea

A Transaction is a logical unit of database processing that includes one or more database access operations (read, write, insert, delete). Consider transferring $500 from Account A to Account B:

BEGIN TRANSACTION;
  READ(A);
  A := A - 500;
  WRITE(A);
  -- If power dies or system crashes HERE, money vanished into thin air!
  READ(B);
  B := B + 500;
  WRITE(B);
COMMIT;

Without transaction guarantees, computer crashes and network drops would cause financial ruin. The DBMS solves this via the ACID contract.

3 · The ACID Properties Mechanistically Explained

A

Atomicity (All-or-Nothing)

Either ALL operations of the transaction complete successfully, or NONE take effect. If failure strikes midway, the DBMS Recovery Manager rolls back all partial changes using Undo Logs to restore the pre-transaction state.

C

Consistency (State Invariant)

The transaction transforms the database from one valid state satisfying all integrity constraints (primary keys, foreign keys, CHECK (balance >= 0)) to another valid state. The total sum of money (A + B) must remain invariant before and after transfer.

I

Isolation (Concurrency Abstraction)

Intermediate states of a running transaction are invisible to concurrently executing transactions. Managed by the Concurrency Control Manager via Locks (2PL) or Multi-Version Concurrency Control (MVCC).

D

Durability (Persistence Guarantee)

Once a transaction commits, its updates persist permanently even if the server crashes, suffers kernel panic, or loses power one millisecond later. Guaranteed via Write-Ahead Logging (WAL) and synchronous disk flushing (fsync).
