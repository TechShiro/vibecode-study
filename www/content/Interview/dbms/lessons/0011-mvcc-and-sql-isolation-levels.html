Why modern databases achieve high read throughput without blocking writes: PostgreSQL and MySQL MVCC internals.

1 · The One Idea

Traditional Two-Phase Locking suffers from a severe performance flaw: readers block writers, and writers block readers. If a report query takes 30 seconds to scan a million rows, all updates to those rows are frozen. Modern engines (PostgreSQL, MySQL InnoDB, Oracle) solve this via Multi-Version Concurrency Control (MVCC): readers never block writers, and writers never block readers.

2 · ANSI SQL-92 Isolation Levels & Phenomena

The SQL standard defines 4 isolation levels based on three concurrency phenomena:

  • Dirty Read (G1): T1 modifies a row without committing; T2 reads that uncommitted value; T1 aborts. T2 saw phantom data that never legally existed!
  • Non-Repeatable Read (G2): T1 reads a row; T2 modifies or deletes that row and commits; T1 re-reads the row and sees changed values.
  • Phantom Read (A3): T1 queries a range: SELECT * WHERE age > 30 (returns 5 rows); T2 inserts a new 35-year-old employee and commits; T1 repeats the range query and sees 6 rows!

3 · MVCC Internal Architecture

Instead of overwriting rows in place, the database creates multiple historical versions of the same row:

  • PostgreSQL: Appends hidden system columns to every row:
    • xmin: Transaction ID that created / inserted this row version.
    • xmax: Transaction ID that deleted or superseded this row version (0 if current).
  • MySQL InnoDB: Uses hidden fields DB_TRX_ID and DB_ROLL_PTR pointing into the Undo Log. When a row is updated, the previous version is reconstructed on-the-fly by traversing the undo rollback segment.

The Read View Snapshot

When a transaction begins a read query under MVCC, the DBMS captures a Read View containing: {low_limit_id, high_limit_id, active_trx_ids}. Any row created by a transaction that committed before the snapshot is visible. Any row created by an active or uncommitted transaction is invisible (the engine traverses the undo chain to find the version that was committed before the query started).

4 · Read Committed vs Repeatable Read in MVCC

RC

Read Committed

A fresh Read View snapshot is created at the start of each individual SQL statement. If another transaction commits between two statements inside the same transaction, changes become visible immediately.

RR

Repeatable Read

A single Read View snapshot is created at the start of the first read query in the transaction and preserved throughout the entire transaction duration. Every query sees the identical historical frozen snapshot.

5 · The Write Skew Anomaly in Snapshot Isolation

Why Snapshot Isolation ≠ Full Serializability

Consider the Doctors on Call problem: Constraint is "At least one doctor must be on call". Doctors Alice and Bob are both on call. Simultaneously:

  • Alice queries: "Is someone else on call?" (Yes, Bob). Alice checks out and commits.
  • Bob queries: "Is someone else on call?" (Yes, Alice). Bob checks out and commits.

Under Repeatable Read / Snapshot Isolation, neither doctor updated the other's row, so no write conflict was triggered! Both commit, leaving ZERO doctors on call! True Serializable Isolation catches this via Serializable Snapshot Isolation (SSI) by tracking read-write dependency cycles.
