Schedules, Serializability & Precedence Graphs

How database engines mathematically prove whether an interleaved schedule is correct.

← Back to Course IndexModule C – Transactions & Concurrency

1 · The One Idea

To maximize CPU utilization and throughput, databases interleave the operations of multiple transactions. A Schedule (or History) is the chronological order of execution of concurrent operations. If transactions execute sequentially one after another (a Serial Schedule), correctness is guaranteed, but performance is terrible. The gold standard of concurrent execution is Serializability: an interleaved concurrent schedule is correct if and only if it produces the exact same final state as some serial schedule.

2 · Conflicting Operations

Two consecutive operations Ii and Ij in a schedule are in conflict if and only if all three conditions hold:

  1. They belong to different transactions (Ti ≠ Tj).
  2. They access the exact same data item Q.
  3. At least one of the operations is a WRITE (W(Q)).

Read-Read (R1(A), R2(A)) is NEVER a conflict. Conflicts arise from Read-Write (R1(A), W2(A)), Write-Read (W1(A), R2(A)), and Write-Write (W1(A), W2(A)).

3 · Conflict Serializability & Precedence Graphs

A schedule S is Conflict Serializable if it can be transformed into a serial schedule by repeatedly swapping non-conflicting adjacent operations.

Algorithm: Testing Conflict Serializability via Precedence Graph

  1. Create a node for each active transaction in the schedule: T1, T2, ..., Tn.
  2. Draw a directed edge Ti → Tj if Ti executes an operation that conflicts with an operation executed later by Tj:
    • Ti executes R(A) and later Tj executes W(A)
    • Ti executes W(A) and later Tj executes R(A)
    • Ti executes W(A) and later Tj executes W(A)
  3. Result: If the Precedence Graph has NO CYCLES, the schedule is Conflict Serializable! The equivalent serial schedule order is obtained via Topological Sort.
  4. If there is a cycle (e.g. T1 → T2 → T1), the schedule is NOT conflict serializable and must be rejected.

4 · View Serializability & Blind Writes

A schedule is View Serializable if it is view-equivalent to some serial schedule (same initial reads, same final writes, same read-from dependencies). Every conflict serializable schedule is view serializable. The converse is false: schedules with Blind Writes (writing a value without reading it first) can be view serializable without being conflict serializable. However, testing view serializability is NP-Complete, so real database engines only enforce conflict serializability.

5 · Schedule Safety Hierarchy (Cascadeless & Strict)

Schedule ClassFormal DefinitionWhy It Matters
Recoverable Schedule If Tj reads data written by Ti, then Ti must commit before Tj commits. Prevents dirty reads leading to impossible recovery (if Ti aborts after Tj committed).
Cascadeless Schedule (ACA) Every transaction reads ONLY data committed by prior transactions (Ti commits before Tj reads). Avoids Cascading Rollbacks, where aborting 1 transaction forces aborting 50 other dependent transactions.
Strict Schedule No transaction can read OR write a data item until the prior transaction that wrote to it has committed or aborted. Simplifies recovery to simple pre-image restoration; used by all production engines.
