The mathematics, node splitting, merging, and range queries of B+ Trees.

1 · The One Idea

Why do databases use B+ Trees instead of in-memory balanced binary search trees (AVL Trees, Red-Black Trees)? Because disks transfer data in blocks (4KB–16KB). A binary tree has a fanout of 2; searching 10,000,000 rows requires traversing a tree of height ~24, incurring 24 random disk reads (unacceptably slow). A B+ Tree matches node size to disk page size, achieving a fanout of hundreds or thousands of keys per node. The height is reduced to 3 or 4 levels, meaning any row among billions of records is retrieved in at most 3–4 page lookups.

3 · Structural Invariants of B+ Trees

A B+ Tree of order m adheres to strict mathematical invariants:

  • Every node contains at most m - 1 search keys and m children pointers.
  • Every internal node (except root) has at least ⌈m/2⌉ children.
  • The root node has at least 2 children if it is not a leaf.
  • All leaf nodes are at the exact same depth (perfect height balance).

4 · B-Tree vs B+ Tree Architectural Comparison

PropertyStandard B-TreeB+ Tree
Key & Record StorageKeys and data records stored in both internal nodes and leaf nodes.Internal nodes store ONLY routing keys; ALL data records reside exclusively in leaf nodes.
Node FanoutLower (data records consume space in internal nodes).Significantly higher (internal nodes fit hundreds of routing keys).
Range QueriesSlow; requires in-order tree traversal jumping up and down levels.Blazing fast; all leaves are linked together in a doubly linked list (sequential scan).
Tree HeightTaller for same data volume.Shorter (typically 3 to 4 levels).

5 · Insertion & Node Splitting Mechanism

  1. Traverse down from root to locate the target leaf node.
  2. Insert the key in sorted order into the leaf node.
  3. Overflow Check: If leaf node now has m keys (exceeds m - 1 capacity):
    • Split the leaf into two leaves, each holding half the keys.
    • Copy up the middle key into the parent internal node.
    • Maintain leaf linked list pointers (prev and next).
  4. If the parent internal node overflows:
    • Split the internal node.
    • Push up (move, not copy) the middle key to the grandparent node.
  5. If root splits, create a new root with 2 children. Tree height increases by 1 at the root.

6 · Deletion & Balancing (Borrowing vs Merging)

  1. Locate the target leaf node and remove the key.
  2. Underflow Check: If keys drop below ⌈m/2⌉ - 1:
    • Borrow (Redistribution): If an immediate left or right sibling has spare keys (more than minimum), borrow a key and adjust the parent's routing key.
    • Merge: If siblings are also at minimum capacity, merge the node with a sibling and pull down/remove the separator key from the parent.
  3. If the root node loses all keys, delete it; its single child becomes the new root. Tree height shrinks by 1.
