Indexing Foundations: Clustered vs Secondary

Accelerating queries from O(N) full table scans to O(log N) tree lookups.

← Back to Course IndexModule D – Storage & Indexing

1 · The One Idea

Without an index, finding a specific row in a 50,000,000-row table requires reading every single page from disk (a Full Table Scan / Sequential Scan) taking tens of seconds. An Index is an auxiliary data structure (typically a B+ Tree) that stores search keys in sorted order along with pointers to the actual data records, reducing lookup latency to just 3–4 disk page reads.

2 · Clustered (Primary) vs Secondary (Unclustered) Index

1

Clustered Index

The physical table rows are sorted and stored directly inside the leaf nodes of the index tree. Because physical disk records can only be ordered in one way, a table can have EXACTLY ONE clustered index (usually the Primary Key, e.g. in MySQL InnoDB).

2

Secondary (Unclustered) Index

Stored as an independent B+ Tree structure. The leaf nodes do NOT contain full data rows; they store the indexed column value and a pointer back to the row (either a physical Row ID / TID or the table's Primary Key value).

3 · The Double-Lookup Penalty (Bookmark Lookup)

In MySQL InnoDB, when you execute a query using a secondary index:

SELECT * FROM users WHERE email = 'alice@example.com';
  1. The DBMS traverses the secondary index tree on email to locate the leaf node.
  2. The leaf node yields the primary key value: user_id = 4289.
  3. The DBMS must now execute a second B+ Tree search on the Clustered Index using user_id = 4289 to fetch the remaining columns (name, address, created_at).

This second traversal is called a Bookmark Lookup or Clustered Index Lookup.

4 · Covering Index & Index-Only Scans

Optimization: The Covering Index

If all columns requested by a SQL query exist directly inside the index tree itself, the database performs an Index-Only Scan, bypassing the clustered table lookup entirely!

CREATE INDEX idx_user_covering ON users (email, first_name, last_name);
-- This query NEVER touches the main table data pages!
SELECT first_name, last_name FROM users WHERE email = 'alice@example.com';

5 · Composite Indexes & The Leftmost Prefix Rule

When an index spans multiple columns: CREATE INDEX idx_geo ON places (country, state, city);

  • The index is sorted by country first; for identical countries, by state; for identical states, by city.
  • Leftmost Prefix Rule:
    • WHERE country = 'US' → USES INDEX
    • WHERE country = 'US' AND state = 'CA' → USES INDEX
    • WHERE state = 'CA' → CANNOT USE INDEX (skips leading prefix)
    • WHERE city = 'San Jose' → CANNOT USE INDEX

6 · Dense vs Sparse Indexes

TypeStructurePros & Cons
Dense IndexAn index record appears for every single search key in the table.Faster lookup, but takes significantly more disk storage memory.
Sparse IndexAn index record appears only for each page/block of the table.Much smaller memory footprint, but requires scanning within the block.
