Hash Indexing & Log-Structured Merge (LSM) Trees

From memory hash tables to write-optimized append-only LSM trees used in RocksDB and Cassandra.

← Back to Course IndexModule D – Storage & Indexing

1 · The One Idea

While B+ Trees are the versatile default for relational databases, they are not universally optimal. For exact equality lookups (WHERE id = 500), Hash Indexes provide constant $O(1)$ time. For write-heavy workloads (ingesting hundreds of thousands of events per second), B+ Trees suffer from Write Amplification due to random page updates. In modern systems, Log-Structured Merge (LSM) Trees turn random disk writes into high-speed append-only sequential writes.

2 · Dynamic Hashing: Extendible Hashing

Static hashing fails when data grows beyond initial bucket allocations (buckets overflow into long linked lists). Extendible Hashing dynamically grows and shrinks without reorganizing the entire table:

  • Uses a central Directory of pointers to data buckets.
  • Global Depth (d): The number of hash bits used by the directory (directory size = $2^d$).
  • Local Depth (p): The number of hash bits distinguishing items inside an individual bucket ($p \le d$).
  • When a bucket overflows:
    • If p < d: Only that single bucket splits into two; its local depth increases to p + 1. Directory pointers are remapped. No directory resize!
    • If p == d: The directory doubles in size ($d$ increases by 1), and the bucket splits.

The Fatal Limitation of Hash Indexes

Hash functions destroy ordering. A Hash Index is COMPLETELY USELESS for range queries (WHERE age BETWEEN 20 AND 30), prefix matching (LIKE 'San%'), or sorting (ORDER BY created_at). Use Hash indexes only for unique key equality lookups.

3 · Log-Structured Merge (LSM) Tree Architecture

Pioneered by O'Neil in 1996 and popularized by Google Bigtable, RocksDB, and Apache Cassandra, LSM Trees achieve peak write throughput by deferring disk updates:

Write → WAL (Disk) + MemTable (RAM)
Flush to SSTable Level 0 (Disk)
Compaction → Level 1 → Level 2
1

MemTable (RAM)

All writes, updates, and deletes are written to an append-only Write-Ahead Log (WAL) on disk for durability, then inserted into an in-memory sorted data structure (SkipList or Red-Black Tree) called the MemTable. Writes are instantaneous!

2

SSTable (Disk)

When the MemTable reaches size limit (e.g. 64MB), it is flushed to disk as an immutable Sorted String Table (SSTable). Keys inside an SSTable are sorted. SSTables are never modified in place.

3

Compaction

Background worker threads merge multiple overlapping SSTables into new sorted SSTables, discarding tombstoned (deleted) records and obsolete overwritten versions (Leveled or Size-Tiered compaction).

4 · Bloom Filters: Accelerating LSM Reads

Because keys are spread across multiple SSTables on disk, searching for a non-existent key in an LSM tree could require reading every SSTable file from disk! LSM engines solve this using an in-memory Bloom Filter for each SSTable:

  • A space-efficient probabilistic data structure based on multiple hash functions and a bit array.
  • Returns either: "Definitely NOT in this SSTable" (100% true, eliminates disk read) or "Might be in this SSTable".
