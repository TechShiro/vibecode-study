1 · The One Idea

Before writing a single line of SQL (CREATE TABLE), system designers build an Entity-Relationship (ER) Model. An ER model is a top-down diagrammatic representation of business reality. Once perfected, a set of mathematically rigorous mapping algorithms translates entities, attributes, and relationships directly into relational tables with primary keys, foreign keys, and junction tables.

2 · Core ER Primitives

ComponentVisual Symbol (Chen Notation)Definition & Example
Strong EntityRectangleAn object with independent existence (e.g., Student, Course). Has a distinct Primary Key.
Weak EntityDouble RectangleCannot exist without an identifying parent entity. Has no full primary key, only a partial key (discriminator). E.g., Dependent belonging to an Employee.
AttributeEllipseA property describing an entity (e.g., student_name). Underlined ellipse = Primary Key.
Multivalued AttributeDouble EllipseAn attribute holding multiple values for a single entity (e.g., phone_numbers).
Composite AttributeHierarchical EllipsesCan be subdivided into atomic parts (e.g., Address → Street, City, Zip).
Derived AttributeDashed EllipseComputed dynamically from other attributes (e.g., Age derived from DateOfBirth).
RelationshipDiamondAn association among entities (e.g., Enrolls_In). Double Diamond for weak entity identifying relationships.

3 · Cardinality and Participation Constraints

  • Cardinality Ratios:
    • One-to-One (1:1): E.g., Citizen has one Passport; Passport belongs to one Citizen.
    • One-to-Many (1:N): E.g., Department employs many Employees; each Employee works in one Department.
    • Many-to-Many (M:N): E.g., Student enrolls in many Courses; Course has many enrolled Students.
  • Participation Constraints:
    • Total Participation (Mandatory): Every entity in the set must participate in the relationship (represented by a double line). E.g., every Loan must belong to a Customer.
    • Partial Participation (Optional): Some entities may not participate (single line). E.g., not every Employee manages a Department.

4 · ER to Relational Schema Mapping Rules

To convert an ER diagram into relational SQL schemas without loss of information:

Rule 1: Strong Entity Mapping

Each strong entity becomes a relation (table). All simple attributes become columns. The ER key becomes the Primary Key. Composite attributes are flattened into atomic columns.

Rule 2: Weak Entity Mapping

Create a relation. Include all simple attributes. Include the Primary Key of the identifying strong entity as a Foreign Key. The Primary Key of the weak relation is the combination: {Parent_PK, Partial_Key}.

Rule 3: 1:N Relationship Mapping

Do NOT create a separate table. Place the Primary Key of the "1" side as a Foreign Key inside the relation of the "N" (many) side. E.g., put dept_id in the Employee table.

Rule 4: M:N Relationship Mapping (Junction Table)

You MUST create a separate associative / junction table. The primary key of the junction table is the composite of the primary keys of both participating entities: {student_id, course_id}, plus any descriptive attributes of the relationship (e.g. enrollment_date, grade).

Rule 5: Multivalued Attribute Mapping

Create a dedicated table containing: {parent_pk, attribute_value} with composite primary key over both columns. E.g., EmployeePhones(emp_id, phone_number).
