Deadlock Handling in Databases

How database engines dynamically detect and preempt mutual blocking among transactions.

← Back to Course IndexModule C – Transactions & Concurrency

1 · The One Idea

Under lock-based protocols (like Strict 2PL), transactions hold acquired locks while requesting additional locks held by competitors. When a cyclic wait condition arises (T1 holds row A waiting for row B, while T2 holds row B waiting for row A), neither can proceed. This is a Database Deadlock. Unlike operating systems which may hang indefinitely, DBMS engines are designed to dynamically detect deadlocks, abort a victim transaction, and roll it back cleanly.

2 · Wait-For Graph (WFG) & Cycle Detection

The DBMS Lock Manager maintains a directed graph called the Wait-For Graph (WFG):

  • Nodes represent active transactions (T1, T2, ..., Tn).
  • A directed edge Ti → Tj exists if Ti is currently blocked waiting for a lock held by Tj.

Deadlock Theorem

A deadlock exists in the database system if and only if the Wait-For Graph contains a directed cycle (e.g., T1 → T2 → T3 → T1). A background engine thread periodically executes a cycle-detection algorithm (Depth-First Search / Tarjan's algorithm) to find cycles.

3 · Deadlock Recovery: Victim Selection

Once a cycle is detected, the DBMS must break the cycle by aborting one of the participating transactions (the Victim). How is the victim chosen?

  • Rollback Cost: Abort the transaction that has modified the fewest rows (minimizing undo log replay).
  • Age / Timestamp: Abort the youngest transaction to allow older, long-running batch transactions to complete.
  • Lock Count: Abort the transaction holding the fewest locks.
  • Starvation Prevention: If a victim is aborted and restarted with a fresh timestamp, it might repeatedly be selected as victim. The DBMS avoids starvation by preserving the transaction's original birth timestamp upon retry.

4 · Deadlock Prevention: Timestamp Schemes

Rather than detecting deadlocks after they happen, databases can preemptively prevent cycles from ever forming using monotonic transaction timestamps (TS(Ti) = system clock when transaction started):

SchemeMechanism (Older Ti requests lock held by Younger Tj)Mechanism (Younger Tj requests lock held by Older Ti)Preemptive?
Wait-Die (Non-preemptive) Ti WAITS (Older is allowed to wait for younger). Tj DIES (Younger is aborted, rolled back, and restarted). No; transactions die on lock request.
Wound-Wait (Preemptive) Ti WOUNDS Tj (Older preempts and aborts younger transaction Tj immediately). Tj WAITS (Younger is allowed to wait for older). Yes; older violently preempts younger.

5 · Lock Timeout (The Practical Industry Solution)

While WFG cycle detection is exact, maintaining global WFGs across distributed nodes is expensive. In production systems (e.g., MySQL InnoDB innodb_lock_wait_timeout=50), the database sets a timeout threshold. If a transaction waits for a lock longer than 50 seconds, the DBMS assumes deadlock, aborts the transaction, and throws: ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction.
