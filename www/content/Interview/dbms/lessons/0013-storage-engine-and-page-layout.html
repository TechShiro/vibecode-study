Storage Engine Architecture & Slotted Pages

How database bytes are physically organized on disk and loaded into memory pages.

← Back to Course IndexModule D – Storage & Indexing

1 · The One Idea

Operating systems read and write to disk in 4KB blocks. Database engines organize persistent tables into fixed-size units called Pages (or Blocks) — typically 8KB in PostgreSQL and 16KB in MySQL InnoDB. When a query accesses a single row, the entire page containing that row is transferred from persistent disk/NVMe into the DBMS Buffer Pool in RAM. How bytes are arranged inside that page determines storage efficiency, tuple search speed, and update fragmentation.

2 · The Slotted Page Architecture

If rows were stored in a simple contiguous array, deleting row 2 or updating row 3 with a longer string would require shifting thousands of bytes and updating external pointers everywhere. The universal industry solution is the Slotted Page Architecture:

Page Header (LSN, Slot Count)
Slot Array (Grows ↓)
Free Space (Middle)
Tuple Records (Grows ↑)
  • Header: Stores PageLSN, total number of slots, and pointer to the start of free space.
  • Slot Array: Located at the top of the page, growing downwards. Each slot entry is small (4 bytes) and contains: {byte_offset_of_tuple, tuple_length}.
  • Tuple Storage: Located at the bottom of the page, growing upwards. Contains the actual row bytes.
  • Free Space Gap: Sits in the middle between the slot array and tuple records. The page is full when the slot array meets the tuple storage.

Why Slotted Pages Are Brilliant (Indirection / RID)

A tuple's physical address is its Record ID (RID) or Tuple ID (TID / ctid): (Page_ID, Slot_Number). If row 4 is updated and grows, it can be moved anywhere inside the page. Only its entry in the slot array is updated with the new byte offset! The external index pointer (Page 42, Slot 3) remains 100% valid. No index rebuild is required!

3 · Anatomy of a Tuple Record

Inside the raw bytes of a single tuple:

  • Tuple Header: Visibility metadata (xmin, xmax in Postgres), number of columns, NULL bitmap (1 bit per column indicating if value is NULL, avoiding storing null bytes).
  • Fixed-Length Columns: INT, BIGINT, FLOAT, TIMESTAMP stored at fixed known byte offsets.
  • Variable-Length Columns: VARCHAR, TEXT, BLOB. The header contains length offsets pointing to the variable byte payloads at the end of the record.
  • TOAST (The Oversized-Attribute Storage Technique): If a single column exceeds page size (e.g. 5MB image or text), PostgreSQL breaks it into compressed chunks stored out-of-line in a secondary TOAST table.
