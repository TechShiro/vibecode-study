Concurrency Control & Two-Phase Locking (2PL)

Preventing race conditions, dirty reads, and lost updates using formal locking mechanisms.

1 · The One Idea

To automatically prevent non-serializable interleavings without requiring human analysis of execution traces, database engines use Lock-Based Protocols. A lock is a hardware-enforced permission slip. If every transaction obeys the Two-Phase Locking (2PL) rule, the resulting schedule is guaranteed to be conflict serializable.

2 · Shared (S) vs Exclusive (X) Locks

S

Shared Lock (Read Lock)

Acquired prior to reading data: LOCK-S(Q). Multiple concurrent transactions can hold shared locks on the same item simultaneously.

X

Exclusive Lock (Write Lock)

Acquired prior to modifying data: LOCK-X(Q). Only ONE transaction can hold an exclusive lock. No other transaction may read or write the item.

3 · The Two-Phase Locking (2PL) Protocol

Under 2PL, a transaction must execute in two distinct consecutive phases:

Phase 1: Growing Phase (Locks Acquired)
Lock Point (Maximum Locks Held)
Phase 2: Shrinking Phase (Locks Released)

The Core 2PL Invariant: Once a transaction releases a single lock, it enters the shrinking phase and CAN NEVER ACQUIRE ANY NEW LOCKS.

5 · Multiple Granularity Locking (MGL) & Intention Locks

Locking row-by-row for a query that scans a 10,000,000-row table produces massive locking overhead. Locking the entire database freezes all other users. DBMS uses an ancestor-tree hierarchy (Database → Table → Page → Row) with Intention Locks:

  • Intention Shared (IS): Indicates that explicit shared locks will be acquired on lower-level descendants.
  • Intention Exclusive (IX): Indicates that explicit exclusive locks will be acquired on lower-level descendants.
  • Shared with Intention Exclusive (SIX): Reading the entire table, but selectively updating certain specific rows.

To lock a row in X mode, a transaction must first acquire IX on the Database, IX on the Table, and IX on the Page!
