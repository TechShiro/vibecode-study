Fixed-Size Windows

Stop re-summing k elements from scratch — reuse the previous window's work by adding one element on the right and removing one on the left.

Mission link: "best subarray/substring of length k" is one of the most common OA warm-ups at big tech — and the same add/remove idea scales up to the hardest window problems. This is Lesson 1 of the 3-lesson sliding-window track. Mission

1 · The one idea

Say you need the maximum sum of any subarray of length k. The naive move — the one you'd write from your 100-LeetCode instincts — is a double loop: for each start index i, sum nums[i..i+k-1]. That's O(n·k), and for n = 10⁵, k = 10⁴ it's dead on arrival. But look at two adjacent windows: [i..i+k-1] and [i+1..i+k] share k−1 elements. Their sums differ by exactly one element entering and one leaving. So keep a running sum and update it in O(1): sum += nums[r] − nums[r−k]. Every element enters the window once and leaves once → O(n) total. That's the entire pattern: a window of constant width gliding across the array, maintained incrementally instead of recomputed.

Recognition trigger The problem fixes the window length for you: "subarray/substring of size k", "of length k", "any k consecutive elements", "every window of size k". If k is given as input, the window never grows or shrinks — it only slides. (If instead the problem says "longest/shortest such that…", the window size is unknown → that's Lesson 2.)

2 · Core template

Two phases: build the first window of k elements, then slide — for each new right element, evict the element k positions back and re-evaluate the answer. Worked example: Max Sum Subarray of size K (the classic warm-up; LC 643 is this plus a division). 

// Maximum sum of any contiguous subarray of length k.
int maxSumFixed(int[] nums, int k) {
    long sum = 0;
    for (int i = 0; i < k; i++) sum += nums[i];   // phase 1: build first window [0..k-1]
    long best = sum;
    for (int r = k; r < nums.length; r++) {        // phase 2: slide right edge to r
        sum += nums[r];                            // add the entering element
        sum -= nums[r - k];                        // remove the leaving element (left edge)
        best = Math.max(best, sum);                // window is now [r-k+1 .. r]
    }
    return (int) best;
}

Time O(n) — one pass, O(1) work per step. Space O(1) (or O(Σ) when the window state is a frequency table over an alphabet Σ).

Dry run — nums = [2, 1, 5, 1, 3, 2], k = 3

build: sum(2,1,5) = 8 → best = 8, window [0..2] r=3: +1 −2 → sum = 7, window [1,5,1] → best stays 8 r=4: +3 −1 → sum = 9, window [5,1,3] → best = 9 r=5: +2 −5 → sum = 6, window [1,3,2] → best stays 9 answer 9 — computed with 1 add + 1 subtract per slide, never a re-sum
The window is state, not indices The indices are trivial — left edge is always r − k + 1. What you actually maintain is the window's summary state: a running sum here, a frequency map for anagram problems, a deque for max (Lesson 3). Everything in this track is "choose the right state + update it in O(1) per slide."

Case: Maximum Average Subarray I (LC 643)

A one-line twist on the core: the average of a fixed-length window is maximized exactly where the sum is — k is constant — so never divide inside the loop (and dodge floating-point drift while you're at it). 

double findMaxAverage(int[] nums, int k) {
    long sum = 0;
    for (int i = 0; i < k; i++) sum += nums[i];
    long best = sum;
    for (int r = k; r < nums.length; r++) {
        sum += nums[r] - nums[r - k];
        best = Math.max(best, sum);
    }
    return (double) best / k;      // divide ONCE, at the very end
}

Case: Maximum Points You Can Obtain from Cards (LC 1423) — the inverted window

Take exactly k cards, each from the front or back of the row, maximizing the total. The taken cards look like "some prefix + some suffix" — two disconnected pieces, which no single window covers. Flip the lens: whatever you take, what remains is one contiguous middle block of size n − k. Maximizing the ends = minimizing that middle window. Suddenly it's the core template with min instead of max. 

int maxScore(int[] cardPoints, int k) {
    int n = cardPoints.length;
    long total = 0;
    for (int x : cardPoints) total += x;
    int w = n - k;                              // size of the UNTAKEN middle window
    if (w == 0) return (int) total;             // taking everything — no middle exists
    long sum = 0;
    for (int i = 0; i < w; i++) sum += cardPoints[i];
    long minMid = sum;
    for (int r = w; r < n; r++) {
        sum += cardPoints[r] - cardPoints[r - w];
        minMid = Math.min(minMid, sum);         // cheapest middle to leave behind
    }
    return (int) (total - minMid);              // ends = total − middle
}
The inversion trick generalizes Whenever the chosen elements are "both ends" or "everything except a contiguous block," slide a window over the complement. It converts a two-ended choice into one clean fixed window. Same move solves LC 1658 (Minimum Operations to Reduce X to Zero: longest middle window summing to total−x).

Case: Permutation in String (LC 567) — frequency-count window

"Does s2 contain a permutation of s1?" A permutation of s1 is any window of length |s1| whose character counts equal s1's. So the window state is a 26-slot frequency array, updated by ++ on entry and −− on exit. To evaluate in O(1) instead of comparing 26 slots each slide, keep matches = how many of the 26 letters currently agree, and adjust it only for the two letters that changed. 

boolean checkInclusion(String s1, String s2) {
    int k = s1.length();
    if (k > s2.length()) return false;
    int[] need = new int[26], win = new int[26];
    for (int i = 0; i < k; i++) {               // build target counts + first window
        need[s1.charAt(i) - 'a']++;
        win[s2.charAt(i) - 'a']++;
    }
    int matches = 0;
    for (int c = 0; c < 26; c++) if (win[c] == need[c]) matches++;
    if (matches == 26) return true;
    for (int r = k; r < s2.length(); r++) {
        int in = s2.charAt(r) - 'a';            // letter entering on the right
        if (win[in] == need[in]) matches--;     // it WAS in agreement; about to break it
        win[in]++;
        if (win[in] == need[in]) matches++;
        int out = s2.charAt(r - k) - 'a';       // letter leaving on the left
        if (win[out] == need[out]) matches--;
        win[out]--;
        if (win[out] == need[out]) matches++;
        if (matches == 26) return true;         // all 26 letters agree ⇒ permutation found
    }
    return false;
}

Case: Find All Anagrams in a String (LC 438)

Identical machinery to 567 — an anagram is a permutation — but instead of returning at the first hit, record every window start where all counts agree. One extra subtlety: the first window is itself a candidate, so check before you start sliding. 

List<Integer> findAnagrams(String s, String p) {
    List<Integer> res = new ArrayList<>();
    int k = p.length();
    if (k > s.length()) return res;
    int[] need = new int[26], win = new int[26];
    for (int i = 0; i < k; i++) {
        need[p.charAt(i) - 'a']++;
        win[s.charAt(i) - 'a']++;
    }
    int matches = 0;
    for (int c = 0; c < 26; c++) if (win[c] == need[c]) matches++;
    if (matches == 26) res.add(0);              // don't forget window [0..k-1] itself
    for (int r = k; r < s.length(); r++) {
        int in = s.charAt(r) - 'a';
        if (win[in] == need[in]) matches--;
        win[in]++;
        if (win[in] == need[in]) matches++;
        int out = s.charAt(r - k) - 'a';
        if (win[out] == need[out]) matches--;
        win[out]--;
        if (win[out] == need[out]) matches++;
        if (matches == 26) res.add(r - k + 1);  // current window starts at r-k+1
    }
    return res;
}
The matches-counter order matters Always do the dance in this order: check-if-equal → decrement matches → mutate count → check-if-equal → increment matches. Mutating first loses the "was it in agreement before?" information, and your matches drifts silently. (Simpler but slower alternative: Arrays.equals(win, need) each slide — O(26n), still accepted, and a fine first version under interview pressure.)

4 · Edge-case checklist

  • k > n. The first-window build loop walks off the array. Guard up front (567/438: return false/empty; 1423: w == 0 means take everything).
  • k == n. Exactly one window — the slide loop body never runs, so the answer must already be correct after the build phase. Set best before the loop, not inside it.
  • Negative numbers. Fixed windows don't care (unlike some variable-window sum tricks in Lesson 2) — the add/remove arithmetic is sign-agnostic. But initialize best to the first window's sum, never to 0.
  • Overflow. 10⁵ elements × values up to 10⁴ exceeds nothing, but 10⁵ × 10⁹ busts int. Accumulate window sums in long by reflex.
  • The leaving index is r − k, not r − k + 1 and not l++ of some separately tracked variable you forgot to move. Derive it: window is [r−k+1 .. r], so the element that just fell out is r − k.
  • Report starts, not ends. LC 438 wants start indices: r − k + 1. Off-by-one here passes small tests and fails hidden ones.
