Counting Windows & the Monotonic Deque

Two power-ups: count how many subarrays satisfy a condition (not just the longest one), and answer "max of every window" without rescanning.

Mission link: Sliding Window Maximum (LC 239) and "count the subarrays with…" questions are hard-round differentiators — the atMost trick in particular separates template-memorizers from pattern-thinkers. This is Lesson 3 of the 3-lesson sliding-window track. Mission

1 · The one idea

Lesson 2 found the best window. Now two new asks. First: counting. "How many subarrays have at most K distinct?" has a lovely closed form: after each expand-and-shrink, the window [l..r] is the largest valid window ending at r — so every suffix of it ([l..r], [l+1..r], …, [r..r]) is also valid (shrinking can't break an "at most" condition). That's r − l + 1 new subarrays per step; sum them. And "exactly K" — which isn't monotone and breaks the shrink logic — factors as atMost(K) − atMost(K−1). Second: windowed max. A running sum updates in O(1), but a running max doesn't — when the max leaves, what's next? Keep a monotonic deque of indices whose values decrease front-to-back: the front is always the current max, and each element is pushed and popped at most once → O(n).

Recognition trigger Counting: "how many / count the subarrays such that…" — especially with "exactly K", "less than K", "at most K". Deque: the window's summary is a max or min (not a sum/count): "maximum of each window of size k", "longest subarray where max − min ≤ limit". If evicting an element can invalidate your cached aggregate, you need the deque, not a single variable.

2 · Core template — count with atMost, subtract for exactly

// Subarrays with K Different Integers (LC 992):
// exactly-K is not monotone → count it as atMost(K) − atMost(K−1).
int subarraysWithKDistinct(int[] nums, int k) {
    return atMost(nums, k) - atMost(nums, k - 1);
}

// #subarrays with AT MOST k distinct values — Lesson 2's shrink loop + one counting line.
int atMost(int[] nums, int k) {
    int[] count = new int[nums.length + 1];  // values are 1..n per constraints
    int distinct = 0, l = 0, total = 0;
    for (int r = 0; r < nums.length; r++) {
        if (count[nums[r]]++ == 0) distinct++;
        while (distinct > k) {               // same shrink as LC 340
            if (--count[nums[l]] == 0) distinct--;
            l++;
        }
        total += r - l + 1;                  // every valid window ENDING at r: [l..r],[l+1..r],…,[r..r]
    }
    return total;
}

Time O(n) per atMost pass — two passes for exactly-K. Space O(n) for the count array (O(Σ) in general).

Why r − l + 1 counts correctly

nums = [1,2,1,2,3], k = 2 (atMost pass) r=0: window [1] → +1 window ending at 0 r=1: [1,2] → +2 ([1,2],[2]) r=2: [1,2,1] → +3 r=3: [1,2,1,2] → +4 r=4: '3' makes 3 distinct → shrink to l=3 ([2,3]) → +2 ([2,3],[3]) atMost(2)=12, atMost(1)=5 → exactly-2 = 7

Each end-index r is counted once, and no window is counted twice — every subarray has exactly one right end. The subtraction then peels off the windows with ≤ K−1 distinct, leaving exactly K.

Case: Subarray Product Less Than K (LC 713)

"Product of all elements < k" is already monotone (all values ≥ 1, so shrinking only reduces the product) and already an "at most"-style condition — so it's a single counting pass, no subtraction. This is the purest possible rep of the counting line. 

int numSubarrayProductLessThanK(int[] nums, int k) {
    if (k <= 1) return 0;                    // product ≥ 1 always, so nothing beats k ≤ 1
    long prod = 1;
    int l = 0, total = 0;
    for (int r = 0; r < nums.length; r++) {
        prod *= nums[r];                     // expand
        while (prod >= k) {                  // shrink until product < k again
            prod /= nums[l];                 // exact: we multiplied these very factors in
            l++;
        }
        total += r - l + 1;                  // windows ending at r with product < k
    }
    return total;
}
Two 713 traps (1) k ≤ 1: every element is ≥ 1, so no window qualifies, but without the guard the shrink loop can push l past r and divide out elements that aren't there. (2) Products overflow int fast — up to 1000… — use long (safe here because the window shrinks before the product exceeds k·1000).

Case: Sliding Window Maximum (LC 239) — the monotonic deque

Report the max of every window of size k. The pain point: when the current max slides out of the window, a plain variable can't tell you the runner-up. Fix: keep a deque of indices whose values are strictly decreasing front-to-back. Invariants: the front is the max of the current window; anything smaller than an entering element is popped from the back, because an element that is both older and smaller than the newcomer can never be a future window's max — the newcomer dominates it for its entire remaining lifetime. 

int[] maxSlidingWindow(int[] nums, int k) {
    int n = nums.length;
    int[] res = new int[n - k + 1];
    Deque<Integer> dq = new ArrayDeque<>();  // indices; values decrease front → back
    for (int r = 0; r < n; r++) {
        if (!dq.isEmpty() && dq.peekFirst() <= r - k)
            dq.pollFirst();                  // front left the window [r-k+1 .. r] → evict by INDEX
        while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[r])
            dq.pollLast();                   // older AND ≤ newcomer → never a max again
        dq.offerLast(r);                     // newcomer takes its place at the back
        if (r >= k - 1)
            res[r - k + 1] = nums[dq.peekFirst()]; // front = max of the full window
    }
    return res;
}

Time O(n) — each index enters and leaves the deque at most once. Space O(k) for the deque.

Dry run — nums = [1, 3, -1, -3, 5], k = 3

r=0: push 0 → dq=[0(1)] r=1: 3 ≥ 1 → pop 0, push 1 → dq=[1(3)] r=2: -1 < 3 → push → dq=[1(3), 2(-1)] → window full: max 3 r=3: -3 < -1 → push → dq=[1(3), 2(-1), 3(-3)] → max 3 r=4: front index 1 ≤ 4−3 → evict; 5 beats -3, -1 → pop both; push 4 → dq=[4(5)] → max 5 result [3, 3, 5] — the deque held the max AND the line of succession
Why indices, and why ≤ on the back-pop Store indices — you need them to detect the front expiring (dq.peekFirst() ≤ r−k); values alone can't tell age, and duplicates would be ambiguous. Popping on ≤ (not just <) keeps only the newest copy of equal values, which is fine (same max) and keeps the deque lean. Flip every comparison and the same structure gives sliding-window minimum — the pair of a max-deque + min-deque solves LC 1438 (max − min ≤ limit).

5 · Edge-case checklist

  • atMost(0) and k−1 = 0. The subtraction calls atMost(k−1); make sure it returns 0 gracefully for k−1 = 0 (an empty-window count), not a crash or negative.
  • Overflow in counts. n = 10⁵ gives up to n(n+1)/2 ≈ 5·10⁹ subarrays — if constraints allow that, total must be long. (992/713 fit in int; say why out loud.)
  • Deque stores indices, evicts by index. Evicting the front by comparing values is the classic 239 bug — duplicates make it wrong.
  • Emit only from r ≥ k−1 in 239: the first k−1 iterations are still building the first window.
  • 713's k ≤ 1 guard and exact division on shrink — division is only safe because you divide out exactly the factors you multiplied in, in order.
  • Monotonicity audit before counting. The r − l + 1 line assumes every sub-window of a valid window (same right end) is valid. True for "at most K distinct" and "product < K with positives"; false for "sum = K with negatives" — that's prefix-sum territory.
  • ArrayDeque, not LinkedList/Stack — idiomatic and faster in Java; and remember peekFirst/pollFirst vs peekLast/pollLast — mixing ends corrupts the invariant silently.
