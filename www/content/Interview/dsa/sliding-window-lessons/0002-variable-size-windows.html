Variable-Size Windows

When the problem asks for the longest or shortest window satisfying a condition, the width itself is the unknown — grow greedily, shrink only when forced.

Mission link: Longest Substring Without Repeating Characters (LC 3) is among the most-asked interview questions in existence, and Minimum Window Substring (LC 76) is a big-tech onsite staple. This is Lesson 2 of the 3-lesson sliding-window track. Mission

1 · The one idea

Take LC 3: longest substring with no repeated character. Naive: try every substring — O(n²) pairs, each checked for duplicates. The window insight: define an invariant ("no character appears twice") and notice it's monotone — if a window violates it, every wider window containing it violates it too. So march the right edge r forward one step at a time; whenever adding s[r] breaks the invariant, advance the left edge l just far enough to restore it. Both pointers only move forward, each at most n steps → O(n). You are implicitly considering all O(n²) windows, but skipping every one that provably can't beat what you've seen.

Recognition trigger "Longest / shortest / smallest subarray or substring such that…" with a condition like "at most k distinct", "no repeats", "contains all of…", "sum ≥ target". The window size is the answer, not an input. Key requirement: the condition must be monotone under growing/shrinking — otherwise shrinking can't be greedy and the pattern breaks (e.g. exactly-k conditions need Lesson 3's trick).

2 · Core template

Memorize this shape — every problem in this lesson is an instance. For-loop expands r; an inner while shrinks l while the window is invalid; then record the (now valid) window. 

// Longest Substring Without Repeating Characters (LC 3).
int lengthOfLongestSubstring(String s) {
    int[] count = new int[128];              // window state: freq of each ASCII char
    int l = 0, best = 0;
    for (int r = 0; r < s.length(); r++) {
        count[s.charAt(r)]++;                // EXPAND: bring s[r] into the window
        while (count[s.charAt(r)] > 1) {     // SHRINK while invariant broken (a repeat exists)
            count[s.charAt(l)]--;            // evict s[l] and advance left edge
            l++;
        }
        best = Math.max(best, r - l + 1);    // RECORD: window [l..r] is valid here
    }
    return best;
}

Time O(n) — r advances n times and l advances at most n times in total across all inner-loop iterations (amortized). Space O(Σ) for the frequency state (128 here).

Dry run — s = "pwwkew"

r=0 'p': window "p" valid → best 1 r=1 'w': "pw" valid → best 2 r=2 'w': "pww" has repeat → shrink: drop 'p', drop 'w' → l=2, window "w" → best stays 2 r=3 'k': "wk" valid → best 2 r=4 'e': "wke" valid → best 3 r=5 'w': "wkew" repeat → shrink: drop 'w' → l=3, window "kew" → best 3 answer 3 ("wke" / "kew") — l never moved backward
Longest vs shortest — where you record Longest-valid problems (LC 3, 340, 904, 424): shrink while invalid, record after the while, when the window is valid again. Shortest-valid problems (LC 76, 209): flip it — shrink while the window is still valid (trying to make it tighter), and record inside the while, just before each shrink step. Same two pointers, opposite squeeze.

Case: Longest Substring with At Most K Distinct Characters (LC 340)

Invariant: "≤ k distinct characters in the window." Track a count map plus a running distinct; a character entering from 0 increments it, a character leaving to 0 decrements it. This one template is the parent of a whole family — memorize it and 904 is free. 

int lengthOfLongestSubstringKDistinct(String s, int k) {
    if (k == 0) return 0;                    // zero distinct allowed ⇒ empty window only
    int[] count = new int[128];
    int distinct = 0, l = 0, best = 0;
    for (int r = 0; r < s.length(); r++) {
        if (count[s.charAt(r)]++ == 0) distinct++;  // new species enters
        while (distinct > k) {               // too many kinds → shrink
            if (--count[s.charAt(l)] == 0) distinct--;
            l++;
        }
        best = Math.max(best, r - l + 1);
    }
    return best;
}

Case: Fruit Into Baskets (LC 904)

The story: two baskets, each holds one fruit type, pick a contiguous run of trees. Decode the costume and it's literally "longest subarray with at most 2 distinct values" — LC 340 with k = 2 and a HashMap because values aren't chars. 

int totalFruit(int[] fruits) {
    Map<Integer, Integer> count = new HashMap<>();
    int l = 0, best = 0;
    for (int r = 0; r < fruits.length; r++) {
        count.merge(fruits[r], 1, Integer::sum);
        while (count.size() > 2) {           // third fruit type → shrink
            int c = count.merge(fruits[l], -1, Integer::sum);
            if (c == 0) count.remove(fruits[l]);  // remove dead keys so size() is honest
            l++;
        }
        best = Math.max(best, r - l + 1);
    }
    return best;
}
Dead keys lie about distinct counts With a HashMap, a count that reaches 0 must be removed — otherwise map.size() overcounts distinct values and you shrink forever. With an int array (LC 340 above), track distinct explicitly instead.

Case: Longest Repeating Character Replacement (LC 424)

Longest window that can be made all-one-letter with at most k replacements. Reframe the condition: a window is fixable iff windowLen − maxFreqInWindow ≤ k (change everything that isn't the majority letter). Twist: when a char leaves, recomputing the true max frequency costs O(26) — but you can skip it. Let maxFreq be a historical max that only ever grows. The window then never shrinks below the best size found so far; it slides at its record width until a genuinely better maxFreq appears. A stale maxFreq can make the window "illegally" large for its current contents, but never larger than some valid window seen earlier — so the final answer is still exact. 

int characterReplacement(String s, int k) {
    int[] count = new int[26];
    int maxFreq = 0, l = 0, best = 0;
    for (int r = 0; r < s.length(); r++) {
        maxFreq = Math.max(maxFreq, ++count[s.charAt(r) - 'A']); // historical max — never decreased
        if (r - l + 1 - maxFreq > k) {       // too many chars would need replacing
            count[s.charAt(l) - 'A']--;      // note: if, not while — shrink exactly one step
            l++;                             // window slides at constant (record) width
        }
        best = Math.max(best, r - l + 1);
    }
    return best;
}

The if (instead of while) works because each expand grows the window by exactly 1, so at most 1 shrink step restores the record width. If the never-shrinking-below-record argument feels slippery in an interview, using while plus an O(26) recompute of maxFreq is also correct and still O(26·n).

Case: Minimum Window Substring (LC 76) — the boss problem

Shortest window of s containing every character of t with multiplicity. This is the shrink-while-valid flavor: expand until the window covers t, then squeeze from the left as long as coverage survives, recording each size before a squeeze. State: need (t's counts), win (window's counts), and formed = how many distinct required chars are currently at full quota — so validity is the O(1) check formed == required. 

String minWindow(String s, String t) {
    if (t.length() > s.length()) return "";
    int[] need = new int[128], win = new int[128];
    int required = 0;                        // distinct chars t needs
    for (char c : t.toCharArray()) if (need[c]++ == 0) required++;
    int formed = 0, l = 0;
    int bestLen = Integer.MAX_VALUE, bestStart = 0;
    for (int r = 0; r < s.length(); r++) {
        char c = s.charAt(r);
        win[c]++;                            // EXPAND
        if (need[c] > 0 && win[c] == need[c]) formed++; // c just reached quota
        while (formed == required) {         // window covers t → SHRINK while it still does
            if (r - l + 1 < bestLen) {       // RECORD before shrinking
                bestLen = r - l + 1;
                bestStart = l;
            }
            char d = s.charAt(l);
            win[d]--;
            if (need[d] > 0 && win[d] < need[d]) formed--; // d dropped below quota → invalid
            l++;
        }
    }
    return bestLen == Integer.MAX_VALUE ? "" : s.substring(bestStart, bestStart + bestLen);
}

Time O(|s| + |t|). Space O(128). Notice it's Lesson 1's need/have frequency idea (LC 567) welded onto this lesson's shrink loop — the two tracks compose.

The three classic LC 76 bugs (1) formed counts distinct chars at quota, not total matched characters — increment only on win[c] == need[c], exactly once per char reaching quota. (2) Extra copies are fine: win[c] > need[c] keeps the window valid; only dropping below quota decrements formed. (3) Record the best inside the while — after it exits, the window is invalid and one char short.

4 · Edge-case checklist

  • Empty inputs / t longer than s (LC 76): answer ""; guard before the loop.
  • k = 0 (LC 340): at most zero distinct means the answer is 0 — the generic loop can mishandle it; special-case it.
  • Answer of "no valid window": distinguish "never found" (bestLen still MAX_VALUE → return "") from a legitimate size-0/size-1 answer.
  • Record at the right moment. Longest: after the shrink-while. Shortest: inside the shrink-while. Swapping these is the #1 template transcription error.
  • l can catch up to r+1. A window can legitimately empty out (e.g. LC 340 with k=0-like states). r − l + 1 = 0 then — make sure that doesn't corrupt best.
  • Monotonicity check before you commit. "Shortest subarray with sum ≥ k" works with this template only when all numbers are positive; with negatives, growing a window can shrink its sum and the greedy shrink is unsound (LC 862 needs a deque instead). Say this out loud in interviews — it's a strong signal.
  • charAt in hot loops: fine on LeetCode, but s.toCharArray() once up front is a cheap constant-factor win and avoids repeated bounds checks.
