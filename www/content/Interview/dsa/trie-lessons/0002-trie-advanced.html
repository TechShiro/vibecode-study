Trie Advanced — Word Search II & Maximum XOR

Two famous hard problems, one shared insight: walk the trie and something else (a grid, the bits of a number) in lockstep, and prune the instant the trie says "no word goes this way."

Mission link: Word Search II is a classic big-tech hard, and the binary-trie trick behind Maximum XOR is the standard tool for a whole family of XOR problems. Lesson 2 of 2 in the trie track. Mission

1 · The one idea

Lesson 1 walked the trie along a query string. The advanced move is to walk it along something you're exploring: each step of a grid DFS or each bit of an integer advances a matching trie pointer. The trie then acts as an oracle — "does any dictionary word continue with this letter?" / "does any number have this bit here?" — and the moment it says no, you cut the entire branch. Searching for a thousand words costs one traversal, not a thousand.

Recognition trigger Many words, one search space: "find all dictionary words in this grid/stream" → build a trie of the words, DFS the space with a trie pointer riding along. Maximize XOR / find best XOR partner → binary trie over the bits, greedy from the most significant bit down.

2 · Core template A — Word Search II (LC 212): trie + grid DFS

Running LC 79's word-search DFS once per word is O(words × grid-DFS) — too slow. Instead, insert all words into one trie and DFS the grid once from every cell, moving the trie pointer with each step. Store the full word on its terminal node (instead of a bare isEnd) so emitting a match needs no path reconstruction. 

class Solution {
    static class TrieNode {
        TrieNode[] children = new TrieNode[26];
        String word = null;            // non-null ⇒ a whole word ends here (replaces isEnd + rebuild)
    }
    List<String> result = new ArrayList<>();

    public List<String> findWords(char[][] board, String[] words) {
        TrieNode root = new TrieNode();
        for (String w : words) {       // build the trie of ALL words
            TrieNode cur = root;
            for (char c : w.toCharArray()) {
                int i = c - 'a';
                if (cur.children[i] == null) cur.children[i] = new TrieNode();
                cur = cur.children[i];
            }
            cur.word = w;
        }
        for (int r = 0; r < board.length; r++)
            for (int c = 0; c < board[0].length; c++)
                dfs(board, r, c, root); // one multi-word DFS per start cell
        return result;
    }

    void dfs(char[][] b, int r, int c, TrieNode parent) {
        if (r < 0 || r >= b.length || c < 0 || c >= b[0].length) return;
        char ch = b[r][c];
        if (ch == '#') return;                    // visited on the current path
        TrieNode node = parent.children[ch - 'a'];
        if (node == null) return;                 // THE PRUNE: no word continues this way
        if (node.word != null) {
            result.add(node.word);                // found a whole word
            node.word = null;                     // dedupe: never report it twice
        }
        b[r][c] = '#';                            // mark visited (O(1) space vs a visited[][])
        dfs(b, r + 1, c, node); dfs(b, r - 1, c, node);
        dfs(b, r, c + 1, node); dfs(b, r, c - 1, node);
        b[r][c] = ch;                             // un-choose (backtracking)

        if (node.word == null && isLeaf(node))    // PRUNE HARDER: node is spent —
            parent.children[ch - 'a'] = null;     // delete it so future DFS stops one step earlier
    }
    boolean isLeaf(TrieNode n) {
        for (TrieNode c : n.children) if (c != null) return false;
        return true;
    }
}

Time O(total word chars) to build + O(M·N·4·3L−1) worst-case DFS (L = longest word; each step after the first has ≤ 3 unvisited neighbors) — but the two prunes make it fast in practice. Space O(total word chars) for the trie + O(L) recursion.

Why the node-deletion prune matters Once a word is reported, its trie path is dead weight — every later DFS that wanders down it does useless work. When a node has no word and no children left, unlink it from its parent; the deletion cascades upward as parents empty out in turn (each level's check happens as its own recursive call returns). On LeetCode's adversarial tests this prune is the difference between accepted and TLE.
Two classic 212 bugs (1) Duplicate results: a word reachable from two cells gets added twice — null out node.word at the moment you report it (cheaper than a result Set). (2) Un-mark on the way out: forgetting b[r][c] = ch after the four recursive calls poisons every later path through that cell. Choose → explore → un-choose, always.

3 · Core template B — Maximum XOR of Two Numbers (LC 421): binary trie

XOR is maximized bit by bit from the top: a 1 in bit 30 beats 1s in all lower bits combined (230 > 230 − 1). So treat each number as a 31-bit string (bit 30 → bit 0; LC constrains inputs to non-negative ints, so bit 31 is 0) and insert into a binary trie — children [0] and [1]. For each number, walk down greedily choosing the opposite bit whenever that branch exists; the path you walk is the best possible partner for that number. 

class Solution {
    static class Node { Node[] next = new Node[2]; } // binary trie: alphabet {0,1}

    public int findMaximumXOR(int[] nums) {
        Node root = new Node();
        int best = 0;
        for (int x : nums) {
            Node ins = root, qry = root;
            int xorWithBest = 0;
            for (int b = 30; b >= 0; b--) {      // MSB first — high bits dominate
                int bit = (x >> b) & 1;
                // -- insert x's bit path --
                if (ins.next[bit] == null) ins.next[bit] = new Node();
                ins = ins.next[bit];
                // -- query best partner: prefer the OPPOSITE bit --
                int want = 1 - bit;
                if (qry.next[want] != null) {
                    xorWithBest |= (1 << b);     // opposite exists ⇒ this XOR bit is 1
                    qry = qry.next[want];
                } else {
                    qry = qry.next[bit];         // forced to match ⇒ this XOR bit is 0
                }
            }
            best = Math.max(best, xorWithBest);  // best partner for x among numbers seen so far
        }
        return best;                             // insert-then-query same loop: every pair is tried once
    }
}

Time O(n · 31) — each number does one 31-step insert and one 31-step query. Space O(n · 31) nodes worst case. Compare O(n²) brute force.

Worked example — dry run

nums = [3, 10, 5], using 4 bits for readability: 3 = 0011, 10 = 1010, 5 = 0101.

insert 3 (0011); query: trie has only 3 → XOR 3^3 = 0. best = 0 insert 10 (1010); query 10: want 0→have, want 1→have, want 0→have, want 1→have → partner 0011 = 3 → 10^3 = 9 (1001). best = 9 insert 5 (0101); query 5: want 1(bit3)→have (10's path), want 0→forced 0... walks to 1010 → 5^10 = 15 (1111). best = 15 answer: 15 — the greedy found the complementary pair (0101, 1010) without checking all pairs
Why greedy-by-bit is safe Suppose at bit b you can take the opposite branch but don't. The best you can then earn from bits b−1…0 is 2b − 1 — strictly less than the 2b you gave up. So taking the opposite bit whenever possible is never wrong. The same argument powers every "maximize a number bit by bit" greedy.

Both cores are the same template with a different alphabet: 26 letters over grid steps, 2 bits over bit positions. If an interviewer swaps in a new search space (a word stream, a DNA alphabet, 32-bit keys), you change the children array size and the step rule — nothing else.

5 · Edge-case checklist

  • Duplicate words in the result (212): the same word found via two paths — set node.word = null when reporting.
  • Restore the cell (212): b[r][c] = ch after the four DFS calls, or later searches are corrupted.
  • A cell may not be reused within one path, but may be reused across different words — which is exactly what mark/unmark gives you.
  • One word is a prefix of another (212) ("app", "apple"): report at the interior node and keep descending — don't return early, and don't delete a node that still has children.
  • Bit width (421): bits 30→0 for non-negative ints. Include negatives (bit 31 = sign) and you must go 31→0 — know which your input allows.
  • Single-element array (421): the insert-then-query order makes the first query pair x with itself → XOR 0, the right answer for n = 1. Query-before-insert on an empty trie would NPE instead.
  • Forced branch (421): when the opposite child is missing you must follow the matching child — it always exists, because at least one full path (the one you just inserted) reaches the bottom.
