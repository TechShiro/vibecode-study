Prefix Sum Track · Lesson 1 of 2 · range sums & counting subarrays

Prefix Sums + the HashMap Family

Pay O(n) once up front, and every "sum of a[i..j]" becomes a single subtraction — then add a HashMap and count subarrays-with-a-property in one pass.

Mission link: "subarray sum equals k" and its disguises (equal 0s/1s, divisible by k) are OA staples at Amazon, Meta, and Google — and the naive O(n²) loop times out on purpose. This is Lesson 1 of the 2-lesson prefix-sum track. Mission

1 · The one idea

You already know the naive way to sum a[i..j]: loop from i to j. One query costs O(n); answering many queries — or checking every subarray — costs O(n²). The fix: precompute a running total array P where P[k] = sum of the first k elements (P[0] = 0, P[k+1] = P[k] + a[k]). Then any range sum is a subtraction: 

sum(i..j) = P[j+1] - P[i]   // "total up to j" minus "total before i"

Think of a car's odometer: distance driven between two towns = reading at the second town minus reading at the first. You never re-drive the road. Every subarray sum is a difference of two prefix values — that single sentence powers this whole track.

Recognition trigger "Range sum" with many queries on an immutable array; or any question about subarrays — "count subarrays with sum k", "longest subarray with equal 0s and 1s", "sum divisible by k". The moment a subarray property can be rewritten as P[j] − P[i] satisfies X, you fix j and ask a HashMap "how many earlier i work?" — one pass, O(n).

2 · Core template

Core A — the prefix array (Range Sum Query, LC 303)

class NumArray {
    private final int[] P;                 // P[k] = a[0] + ... + a[k-1]; P[0] = 0
    public NumArray(int[] a) {
        P = new int[a.length + 1];         // length n+1 — the extra slot is the empty prefix
        for (int k = 0; k < a.length; k++)
            P[k + 1] = P[k] + a[k];        // each prefix extends the previous by one element
    }
    public int sumRange(int i, int j) {    // inclusive [i, j]
        return P[j + 1] - P[i];            // odometer subtraction — O(1) per query
    }
}

Time O(n) build, O(1) per query. Space O(n). Use long for P when sums can overflow int.

Core B — prefix + HashMap of counts (Subarray Sum Equals K, LC 560)

Count subarrays summing to k. Naive: try all O(n²) pairs. Rewrite with prefixes: subarray (i..j] sums to k ⇔ P[j] − P[i] = k ⇔ P[i] = P[j] − k. So sweep left to right maintaining the running prefix; at each position ask: how many earlier prefixes equal prefix − k? A HashMap from prefix-value → count answers in O(1). 

int subarraySum(int[] a, int k) {
    Map<Integer, Integer> count = new HashMap<>();
    count.put(0, 1);                       // THE crucial line — the empty prefix P[0]=0 (see below)
    int prefix = 0, ans = 0;
    for (int x : a) {
        prefix += x;                       // prefix = P[j] after including x
        ans += count.getOrDefault(prefix - k, 0); // each earlier i with P[i]=prefix-k gives one subarray
        count.merge(prefix, 1, Integer::sum);     // record AFTER counting (a subarray needs length ≥ 1)
    }
    return ans;
}

Time O(n). Space O(n). Works with negatives — which is exactly why sliding window can't solve 560.

Why count.put(0, 1) — the classic bug The map stores prefixes you've already passed. Before reading any element you have already "seen" one prefix: P[0] = 0, the empty prefix. Without it, any subarray that starts at index 0 is silently missed: for a = [3], k = 3, at j = 0 you look up prefix − k = 0 — the answer must come from the pre-seeded 0. Forgetting this line makes you fail exactly the test cases where the whole array (or any front-anchored slice) is an answer. Index-variant of the same idea: seed map.put(0, -1) ("prefix 0 occurs at index −1").
a = [1, 2, 1, 2, 1], k = 3   map = {0:1}, prefix = 0, ans = 0 x=1 → prefix=1; need 1−3=−2 → 0 hits; map {0:1, 1:1} x=2 → prefix=3; need 0 → 1 hit (empty prefix! subarray [1,2]); ans=1; map {…, 3:1} x=1 → prefix=4; need 1 → 1 hit ([2,1]); ans=2; map {…, 4:1} x=2 → prefix=6; need 3 → 1 hit ([1,2] middle); ans=3; map {…, 6:1} x=1 → prefix=7; need 4 → 1 hit ([2,1] tail); ans=4 answer 4 — and the first hit only existed because of put(0,1)

3 · All the cases

The whole family is one template with two dials: what you store (count vs first index) and what key you use (raw prefix vs transformed prefix).

CaseProblemWhat changes
Range sum, many queriesLC 303Plain prefix array; P[j+1] − P[i]. No map needed.
Count subarrays, sum = kLC 560Map prefix → count; seed {0:1}; look up prefix − k.
Longest subarray, equal 0s/1sLC 525Treat 0 as −1; map prefix → first index; seed {0:−1}; look up same prefix.
Count subarrays, sum % k == 0LC 974Key is prefix mod k, normalized non-negative; look up the same remainder.

Case: Contiguous Array — longest with equal 0s and 1s (LC 525)

Trick 1: replace every 0 with −1; now "equal 0s and 1s" becomes "sum = 0", i.e. P[j] = P[i] — the same prefix value seen twice brackets a balanced subarray. Trick 2: you want the longest, so store each prefix's first index (never overwrite) and take j − firstIndex. 

int findMaxLength(int[] a) {
    Map<Integer, Integer> first = new HashMap<>();
    first.put(0, -1);                      // empty prefix "occurs" just before index 0
    int prefix = 0, best = 0;
    for (int j = 0; j < a.length; j++) {
        prefix += (a[j] == 1) ? 1 : -1;    // 0 counts as −1 → balance = 0 means equal
        if (first.containsKey(prefix))
            best = Math.max(best, j - first.get(prefix)); // same value seen before → balanced span
        else
            first.put(prefix, j);          // keep the EARLIEST index — longest span later
    }
    return best;
}

Case: Subarray Sums Divisible by K (LC 974) — the negative-mod trap

P[j] − P[i] ≡ 0 (mod k) ⇔ P[j] and P[i] have the same remainder. Count pairs of equal remainders on the fly. But Java's % keeps the sign of the dividend: -1 % 5 == -1, not 4. Two mathematically-equal remainders then land in different map buckets and you undercount. Always normalize. 

int subarraysDivByK(int[] a, int k) {
    Map<Integer, Integer> count = new HashMap<>();
    count.put(0, 1);                       // empty prefix has remainder 0
    int prefix = 0, ans = 0;
    for (int x : a) {
        prefix += x;
        int r = ((prefix % k) + k) % k;    // TRAP: -1 % 5 == -1 in Java → normalize to [0, k)
        ans += count.getOrDefault(r, 0);   // pair with every earlier equal remainder
        count.merge(r, 1, Integer::sum);
    }
    return ans;
}

Case: Continuous Subarray Sum — length ≥ 2, multiple of k (LC 523)

Same remainder idea, but the answer is a boolean and the subarray needs length ≥ 2. So store the remainder's first index and check the gap. (A multiple of k includes 0, so a run of zeros of length ≥ 2 qualifies — the index logic handles it automatically.) 

boolean checkSubarraySum(int[] a, int k) {
    Map<Integer, Integer> first = new HashMap<>();
    first.put(0, -1);                      // remainder 0 at "index -1" → whole-front subarrays count
    int prefix = 0;
    for (int j = 0; j < a.length; j++) {
        prefix += a[j];
        int r = prefix % k;                // a[i] ≥ 0 here, so no negative-mod fix needed
        Integer i = first.get(r);
        if (i == null) first.put(r, j);    // first occurrence only — maximizes future gaps
        else if (j - i >= 2) return true;  // gap ≥ 2 ⇔ subarray length ≥ 2
    }
    return false;
}
The two-dial summary Counting subarrays → map value is a count, seed {0:1}, add lookups into ans. Longest / exists → map value is a first index, seed {0:-1}, never overwrite, compare j − firstIndex. Picking the wrong dial (or the wrong seed) is 90% of wrong answers in this family.

4 · Edge-case checklist

  • Forgetting the empty-prefix seed ({0:1} for counts, {0:-1} for indices) — misses every subarray starting at index 0. The #1 bug.
  • Update order: look up prefix − k before inserting the current prefix, or with k = 0 you'd match a subarray with itself (length 0).
  • Negative numbers: prefix sums handle them fine (that's their edge over sliding window), but Java % then goes negative — normalize with ((x % k) + k) % k.
  • Overflow: n up to 10⁵ with values up to 10⁹ → prefix sums exceed int. Use long.
  • Count vs first-index confusion: overwriting indices in LC 525/523 shortens your spans; counting in a longest-problem is meaningless.
  • Off-by-one: with the n+1-length convention, sum(i..j) = P[j+1] − P[i]. Write it in a comment before coding.
  • LC 523 specifically: length ≥ 2 means the index gap must be ≥ 2, not ≥ 1.
