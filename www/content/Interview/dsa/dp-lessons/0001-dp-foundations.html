DP Foundations

Dynamic programming is not a topic — it's one trick: never solve the same subproblem twice. Learn the 5-step framework here; every later lesson is that framework with a different state.

Mission link: DP is ~15% of Google intern questions and your self-identified gap. This is Lesson 1 of the 12-lesson DP track. Mission
Prerequisite You should be comfortable writing plain recursion (you are — the graph track's DFS was all recursion). DP adds exactly one ingredient on top: a cache. No new Java machinery until the later lessons.

1 · The one idea

DP = recursion + never solving the same subproblem twice. A problem is DP-shaped when it has overlapping subproblems (the naive recursion recomputes identical calls — fib(3) gets computed twice inside fib(5)) and optimal substructure (the best answer to the whole is built from best answers to the parts). When both hold, cache each subproblem's answer the first time and every repeat becomes an O(1) lookup: exponential collapses to polynomial.

Recognition trigger "Count the ways…", "max/min over a sequence of choices…", "can you reach…", and — the deep tell — the future depends only on a compact summary of the past (which step you're on, not how you got there). If brute force enumerates choice-trees and the same situations keep reappearing, you are in DP territory.

2 · State · Recurrence · Base case — the 5-step framework

Every DP solution in this track — 1D, grids, knapsack, strings, trees, bitmasks — is these five answers written down. Memorize the questions, not the solutions:

StepQuestionFor Climbing Stairs (LC 70)
1 · StateWhat does dp[i] mean, in one sentence?dp[i] = number of distinct ways to stand on step i
2 · RecurrenceHow does a state combine smaller states?dp[i] = dp[i-1] + dp[i-2] — arrive via a 1-step or a 2-step
3 · Base casesWhich states are known without the recurrence?dp[0] = 1, dp[1] = 1
4 · OrderIterate small→large, or memoize and let recursion sort it out?i ascending (or top-down memo — both work)
5 · AnswerWhere does the final answer live?dp[n]
Why not greedy? Greedy commits to the locally best choice and never looks back. Coins {1,3,4}, amount 6: greedy grabs the biggest coin → 4+1+1 = 3 coins, but the optimum is 3+3 = 2. The recurrence dp[a] = 1 + min(dp[a-1], dp[a-3], dp[a-4]) compares every choice at every amount, so a locally-worse pick still gets credit for the better future it enables. Greedy only works when a locally best choice is provably never wrong — rare, and you must prove it.

3 · Core template — Fibonacci, four ways

fib(n) / Climbing Stairs is the smallest problem where all four implementations are visible. The recurrence never changes — only the bookkeeping does.

Way 1 — naive recursion: O(2ⁿ)

// The recursion tree doubles every level. fib(50) ≈ 10^10 calls — hangs forever.
int fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);   // fib(n-2) recomputes everything fib(n-1) already did
}

Time O(2ⁿ) · Space O(n) stack. Draw this tree once (see the dry run below) — the repeated nodes ARE the motivation for DP.

Way 2 — top-down memoization: O(n)

Integer[] memo;                                  // null = "not computed yet" — safer than 0 as a sentinel
int fib(int n) { memo = new Integer[n + 1]; return solve(n); }

int solve(int n) {
    if (n <= 1) return n;                        // base cases (step 3)
    if (memo[n] != null) return memo[n];         // cache hit — the entire trick
    return memo[n] = solve(n - 1) + solve(n - 2);// recurrence (step 2), stored on the way out
}

Time O(n) — each state computed once. Space O(n) memo + O(n) recursion stack.

Way 3 — bottom-up table: O(n)

int fib(int n) {
    if (n <= 1) return n;
    int[] dp = new int[n + 1];                   // dp[i] = fib(i) — the state (step 1)
    dp[0] = 0; dp[1] = 1;                        // base cases
    for (int i = 2; i <= n; i++)
        dp[i] = dp[i - 1] + dp[i - 2];           // iterate small → large (step 4)
    return dp[n];                                // answer location (step 5)
}

Time O(n) · Space O(n), no recursion stack.

Way 4 — rolling variables: O(1) space

// dp[i] only reads dp[i-1] and dp[i-2] → keep just those two. This move recurs all track long.
int fib(int n) {
    if (n <= 1) return n;
    int prev2 = 0, prev1 = 1;                    // dp[i-2], dp[i-1]
    for (int i = 2; i <= n; i++) {
        int cur = prev1 + prev2;
        prev2 = prev1; prev1 = cur;              // slide the window
    }
    return prev1;
}

Time O(n) · Space O(1). This is the interview-final form for any recurrence that looks back a constant distance.

Fibonacci Number (509)

The state is dp[i] = the i-th Fibonacci number, the recurrence is dp[i] = dp[i-1] + dp[i-2], and the bases are dp[0] = 0, dp[1] = 1 — which means every snippet in §3 is the accepted submission, verbatim. Submit Way 4 (rolling variables); write the other three from a blank file anyway, because reproducing all four on demand is the drill that makes lessons 2–12 easy.

Time O(n) · Space O(1) in the rolling form.

The off-by-one that bites everyone LC 509 and LC 70 share a recurrence but not base cases: Fibonacci starts 0, 1 (a value sequence), Climbing Stairs starts 1, 1 (a count — there is exactly one way to stand still at the bottom). Copy-pasting one into the other shifts every answer by one index. Re-derive step 3 of the framework each time; never trust muscle memory on bases.

Climbing Stairs (70)

Same recurrence as Fibonacci, different meaning: dp[i] = number of ways to reach step i, and the last move was a 1-step (from i-1) or a 2-step (from i-2), so dp[i] = dp[i-1] + dp[i-2] with bases dp[0] = dp[1] = 1. All four §3 ways translate line-for-line — only the bases change. Here is Way 2 (top-down memo) for contrast; the rolling Way 4 follows.

Integer[] memo;                                  // Way 2 — top-down memo for LC 70
int climbStairs(int n) { memo = new Integer[n + 1]; return ways(n); }

int ways(int n) {
    if (n <= 1) return 1;                        // dp[0]=1, dp[1]=1 — NOT fib's 0,1
    if (memo[n] != null) return memo[n];         // cache hit
    return memo[n] = ways(n - 1) + ways(n - 2);
}

Time O(n) · Space O(n) memo + stack. And the interview-final Way 4:

int climbStairs(int n) {
    int prev2 = 1, prev1 = 1;                    // dp[0]=1 (stand at bottom), dp[1]=1
    for (int i = 2; i <= n; i++) {
        int cur = prev1 + prev2;                 // last move was a 1-step or a 2-step
        prev2 = prev1; prev1 = cur;
    }
    return prev1;
}

Time O(n) · Space O(1).

Counting DP + mod 10⁹+7 Bigger counting problems (like LC 2466 below) overflow int long before n gets interesting, and a single mod at the end is a bug — by then the value has already overflowed. Take the mod inside the recurrence, at every addition: 
final int MOD = 1_000_000_007;
int cur = (prev1 + prev2) % MOD;                 // mod EVERY addition, not just the return value
// products must widen first: int p = (int)((long)a * b % MOD);

Min Cost Climbing Stairs (746)

First mutation of the family: the sum becomes a min, plus a cost term. State: dp[i] = cheapest total cost to stand on step i. Recurrence: dp[i] = min(dp[i-1] + cost[i-1], dp[i-2] + cost[i-2]) — you pay a stair's cost when you leave it. Bases: dp[0] = dp[1] = 0, because you may start on step 0 or 1 for free. The answer lives at index n — the "top", one past the last stair.

int minCostClimbingStairs(int[] cost) {
    int n = cost.length;
    int prev2 = 0, prev1 = 0;                    // free to START on step 0 or step 1
    for (int i = 2; i <= n; i++) {               // "step n" = the top, past the last stair
        int cur = Math.min(prev1 + cost[i - 1],  // pay to leave step i-1
                           prev2 + cost[i - 2]); // or pay to leave step i-2
        prev2 = prev1; prev1 = cur;
    }
    return prev1;                                // min cost to stand on the top
}

Time O(n) · Space O(1).

Where's the answer? The two classic 746 bugs are both step-5 mistakes: returning dp[n-1] (that's the cost to stand on the last stair, not the top) and forgetting the free start (seeding dp[1] = cost[1]). If your answer is off by exactly one stair's cost, you've hit one of these.

N-th Tribonacci (1137)

Same story, wider window: the state looks back three steps instead of two — dp[i] = dp[i-1] + dp[i-2] + dp[i-3], bases T0 = 0, T1 = T2 = 1 — so the rolling form keeps three variables instead of two. This is the general rule: a recurrence looking back a constant k rolls down to k variables.

int tribonacci(int n) {
    if (n == 0) return 0;
    if (n <= 2) return 1;
    int a = 0, b = 1, c = 1;                     // T0, T1, T2 — three-wide window
    for (int i = 3; i <= n; i++) {
        int d = a + b + c;
        a = b; b = c; c = d;
    }
    return c;
}

Time O(n) · Space O(1).

Worked example — dry run

Compute fib(5) top-down with the memo. Naive recursion would expand 15 calls; memoization expands 9, and two of those (shaded) return instantly from the cache — their entire subtrees never exist. That pruning is the whole subject.

call f(5) → not cached → needs f(4), then f(3) f(4) → f(3) → f(2) → f(1)=1, f(0)=0 → memo[2]=1 f(3)'s right child f(1)=1 → memo[3]=2 f(4)'s right child f(2): memo hit → 1, no recursion → memo[4]=3 f(5)'s right child f(3): memo hit → 2, no recursion f(5) = 3 + 2 → memo[5]=5, return 5. Every state computed exactly once.

6 · Edge-case checklist

  • n = 0 / n = 1: return before touching the dp array, or size it n+1 and seed both bases — new int[n+1] with n=0 can't hold dp[1].
  • Memo sentinel: int[] initialized to 0 is a bug when 0 is a legitimate answer — use Integer[] + null, or fill with -1 only if answers are never negative.
  • Overflow: fib grows exponentially — fib(47) already overflows int. Counting problems usually ask for the answer mod 10⁹+7: take the mod inside the recurrence, every addition.
  • Recursion depth: top-down with n ≈ 10⁵ risks StackOverflowError in Java — switch to bottom-up.
  • Memo size: new Integer[n + 1], not [n] — you will index memo[n].
  • Base cases before cache check (or size the memo to include them) — solve(1) must not read memo[1] if it was never written.
