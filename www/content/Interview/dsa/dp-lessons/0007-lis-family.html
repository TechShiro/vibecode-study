Longest Increasing Subsequence & friends

Learn LIS twice — the honest O(n²) DP and the patience-sorting tails trick — then unlock a whole family of 2D problems with one move: sort one dimension, LIS the other.

Mission link: DP is ~15% of Google intern questions and your self-identified gap. This is Lesson 7 of the 12-lesson DP track. Mission

1 · The one idea

LIS has two canonical solutions and you need both. The DP view: dp[i] = length of the longest increasing subsequence ending exactly at index i — extend any earlier smaller element, O(n²). The fast view: keep an array tails where tails[k] = the smallest possible tail of any increasing subsequence of length k+1; each new element binary-searches its slot, O(n log n). The DP version generalizes (counts, reconstruction, weird predecessor rules); the tails version is the speed demon when only the length matters.

Recognition trigger "longest increasing / decreasing subsequence", "longest chain", "how many can you nest / stack / fit inside each other" (pairs, envelopes, boxes), "minimum removals to make it sorted" (= n − LIS). Any problem where you pick items in order and each must "beat" the previous one under some comparator — that comparator is the only thing that changes.

2 · State · Recurrence · Base case

PartO(n²) DP version
Statedp[i] = length of the longest increasing subsequence that ends at nums[i] (element i is mandatory — this is "ending here", like Kadane).
Recurrencedp[i] = 1 + max(dp[j]) over all j < i with nums[j] < nums[i]; if no such j, dp[i] = 1.
Base caseEvery dp[i] starts at 1 — an element alone is a subsequence of length 1.
OrderLeft → right; dp[i] only reads earlier indices.
Answermax(dp[i]) over all i — not dp[n-1]; the LIS can end anywhere.

The tails version keeps the same "smallest-tail-per-length" invariant instead of a per-index state — it's a compressed view of the same information, and it's why binary search works.

3 · Core template

Version A — O(n²) DP (generalizes to everything below)

int lengthOfLIS(int[] nums) {
    int n = nums.length;
    int[] dp = new int[n];
    Arrays.fill(dp, 1);                       // base case: each element alone = length 1
    int best = 1;
    for (int i = 1; i < n; i++) {
        for (int j = 0; j < i; j++)
            if (nums[j] < nums[i])            // strictly increasing — the ONLY line variants change
                dp[i] = Math.max(dp[i], dp[j] + 1);
        best = Math.max(best, dp[i]);         // answer = max over ALL endings
    }
    return best;
}

Time O(n²). Space O(n). To handle a different comparator (divisibility, pair chains, word predecessors) you edit exactly one line: the if.

Version B — tails + binary search, O(n log n)

int lengthOfLIS(int[] nums) {
    int[] tails = new int[nums.length];       // tails[k] = smallest tail of any inc. subseq of length k+1
    int size = 0;
    for (int x : nums) {
        int lo = 0, hi = size;                // lower bound: first index with tails[idx] >= x
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (tails[mid] < x) lo = mid + 1; else hi = mid;
        }
        tails[lo] = x;                        // replace that slot (or append when lo == size)
        if (lo == size) size++;               // x extends the longest subsequence seen so far
    }
    return size;                              // NOTE: tails is NOT an actual LIS — only its length is right
}

Time O(n log n). Space O(n). Why it works: tails is always sorted (a smaller tail for a longer length would contradict itself), so binary search is legal. Replacing tails[lo] with a smaller value never shortens anything already found — it just makes future extensions easier. Appending means x beat every tail, i.e. a strictly longer subsequence now exists.

The classic tails misconception tails is not the LIS itself. On [10,9,2,5,3,7,101,18] it ends as [2,3,7,18], which happens to be an LIS — but on [1,5,2] it ends as [1,2] while the LIS is [1,5] or [1,2]… and on [3,4,1] it ends as [1,4], which isn't even a subsequence. Only size is guaranteed correct. Need the actual sequence or a count? Use Version A.

Number of LIS (673) — lengths and counts travel together

int findNumberOfLIS(int[] nums) {
    int n = nums.length, maxLen = 0, total = 0;
    int[] len = new int[n], cnt = new int[n];
    for (int i = 0; i < n; i++) {
        len[i] = 1; cnt[i] = 1;
        for (int j = 0; j < i; j++) {
            if (nums[j] >= nums[i]) continue;
            if (len[j] + 1 > len[i]) { len[i] = len[j] + 1; cnt[i] = cnt[j]; }  // new best: REPLACE count
            else if (len[j] + 1 == len[i]) cnt[i] += cnt[j];                     // tie: ACCUMULATE count
        }
        if (len[i] > maxLen) { maxLen = len[i]; total = cnt[i]; }
        else if (len[i] == maxLen) total += cnt[i];
    }
    return total;
}

Time O(n²). Space O(n). Same skeleton as Version A, but every index now carries a second value: cnt[i] = how many distinct LIS end at i. A strictly better length replaces the count (old ways are now too short); an equal length adds counts (new, equally good ways). Tails can't do this — compression discards the per-index information counting needs.

Longest Divisible Subset (368) — sort, swap the comparator, reconstruct

List<Integer> largestDivisibleSubset(int[] nums) {
    Arrays.sort(nums);                        // sorted ⇒ divisibility chains only look backwards
    int n = nums.length, best = 0;
    int[] dp = new int[n], prev = new int[n];
    for (int i = 0; i < n; i++) {
        dp[i] = 1; prev[i] = -1;
        for (int j = 0; j < i; j++)
            if (nums[i] % nums[j] == 0 && dp[j] + 1 > dp[i]) {  // comparator swapped in
                dp[i] = dp[j] + 1; prev[i] = j;                   // remember who we extended
            }
        if (dp[i] > dp[best]) best = i;
    }
    List<Integer> res = new ArrayList<>();
    for (int i = best; i != -1; i = prev[i]) res.add(nums[i]);   // walk parents to rebuild
    return res;
}

Time O(n²). Space O(n). Two ideas stack here: sorting makes divisibility a one-directional "look backwards" relation (if nums[i] % nums[j] == 0 and j < i after sorting, the whole chain through j still divides), and prev[] records which j each i extended so you can walk the parents and output the actual subset — the reconstruction pattern the tails version can never give you.

Maximum Length of Pair Chain (646) — DP vs greedy on the same problem

A chain of pairs is an LIS where "increasing" means prev[1] < cur[0] — but unlike a plain array, pairs may be picked in any order, so you're free to sort them first. State: dp[i] = longest chain ending at pair i (after sorting by first element). Recurrence: dp[i] = 1 + max(dp[j]) over j with pairs[j][1] < pairs[i][0]; base case dp[i] = 1. That's Version A with one line swapped. But because pairs are intervals and only the length is asked, greedy wins: sort by right endpoint and always take the pair that finishes earliest — finishing early can never hurt future choices.

int findLongestChain(int[][] pairs) {
    // --- Method 1: LIS DP, O(n^2) — the transferable skill ---
    Arrays.sort(pairs, (a, b) -> a[0] - b[0]);   // sorting is legal: chain order != input order
    int n = pairs.length, best = 1;
    int[] dp = new int[n];
    Arrays.fill(dp, 1);
    for (int i = 1; i < n; i++) {
        for (int j = 0; j < i; j++)
            if (pairs[j][1] < pairs[i][0])        // the one changed line: strict gap between pairs
                dp[i] = Math.max(dp[i], dp[j] + 1);
        best = Math.max(best, dp[i]);
    }
    return best;
}

int findLongestChainGreedy(int[][] pairs) {
    // --- Method 2: greedy, O(n log n) — optimal here because pairs are intervals ---
    Arrays.sort(pairs, (a, b) -> a[1] - b[1]);   // sort by RIGHT endpoint, not left
    int count = 0, end = Integer.MIN_VALUE;
    for (int[] p : pairs)
        if (p[0] > end) {                         // strictly after the last chain's end → take it
            count++;
            end = p[1];                           // chain now ends as early as possible
        }
    return count;
}

Time O(n²) DP / O(n log n) greedy. Space O(n) / O(1). Interviews love the follow-up "can you beat O(n²)?" — the answer is greedy, not tails, because the exchange argument (an earliest-ending pair is always safe to keep) only exists for intervals. For divisibility, counts, or string predecessors, no such argument exists and DP is the only game.

The greedy sort direction Sorting by left endpoint and greedily taking pairs fails: on [[1,100],[2,3],[4,5]] it grabs [1,100] and gets chain length 1, while right-endpoint order takes [2,3] → [4,5] for length 2. Greedy interval selection is always "sort by right endpoint" — earliest finisher leaves the most room. Also note the comparator is strict: p[0] > end, because (1,2) and (2,3) do NOT chain.

Russian Doll Envelopes (354) — the sort that makes LIS legal

int maxEnvelopes(int[][] env) {
    Arrays.sort(env, (a, b) ->
        a[0] == b[0] ? b[1] - a[1]            // equal width → height DESCENDING (the trick)
                     : a[0] - b[0]);           // otherwise width ascending
    // now run tails-LIS on heights env[i][1] (Version B, strict <)
    int[] tails = new int[env.length]; int size = 0;
    for (int[] e : env) {
        int x = e[1], lo = 0, hi = size;
        while (lo < hi) { int m = (lo + hi) >>> 1; if (tails[m] < x) lo = m + 1; else hi = m; }
        tails[lo] = x; if (lo == size) size++;
    }
    return size;
}

Why the descending tiebreak? An envelope needs strictly bigger width AND height to nest. After sorting width ascending, two envelopes with equal width must never chain — by putting their heights in descending order, the height-LIS (which is strictly increasing) can pick at most one of them. Sort them ascending and (5,4),(5,7) would wrongly chain.

Longest String Chain (1048) — LIS where "smaller" = delete one character

int longestStrChain(String[] words) {
    Arrays.sort(words, (a, b) -> a.length() - b.length());   // "sort one dimension" = length
    Map<String, Integer> dp = new HashMap<>();
    int best = 1;
    for (String w : words) {
        int cur = 1;
        for (int i = 0; i < w.length(); i++) {               // generate each 1-char-deleted predecessor
            String pred = w.substring(0, i) + w.substring(i + 1);
            cur = Math.max(cur, dp.getOrDefault(pred, 0) + 1);
        }
        dp.put(w, cur);
        best = Math.max(best, cur);
    }
    return best;
}

Time O(n·L²) — generating predecessors beats comparing all pairs when n is large and words are short. Same LIS skeleton, different notion of "previous element".

Worked example — dry run

Tails-LIS (Version B) on nums = [10, 9, 2, 5, 3, 7, 101, 18]. Each element either replaces the first tail ≥ it, or appends if it beats every tail:

x=10 → tails empty → append → tails=[10], size=1 x=9 → first tail ≥ 9 is 10 (slot 0) → replace → tails=[9], size=1 x=2 → first tail ≥ 2 is 9 (slot 0) → replace → tails=[2], size=1 x=5 → no tail ≥ 5 → append → tails=[2,5], size=2 x=3 → first tail ≥ 3 is 5 (slot 1) → replace → tails=[2,3], size=2 x=7 → no tail ≥ 7 → append → tails=[2,3,7], size=3 x=101 → no tail ≥ 101 → append → tails=[2,3,7,101], size=4 x=18 → first tail ≥ 18 is 101 (slot 3) → replace → tails=[2,3,7,18], size=4 done → return size = 4

Watch what the replacements buy: after x=3, the length-2 tail drops from 5 to 3, so a future 4 could still extend to length 3. Replacing never destroys progress — it only lowers the bar for what comes next.

5 · Edge-case checklist

  • Strict vs non-decreasing: "increasing" almost always means strict (<). For non-decreasing, Version A uses <=; Version B switches lower-bound (first ≥ x) to upper-bound (first > x).
  • Answer is max(dp[i]), not dp[n-1] — the LIS can end at any index. Rite-of-passage bug.
  • Duplicates in 354/368: equal widths must not chain — that's exactly what the height-DESC tiebreak enforces. Test with [[5,4],[5,7]].
  • n = 0 or 1: return n. Both templates handle it, but check before dereferencing nums[0].
  • 673 tie handling: len[j]+1 == len[i] must add counts, and a strictly better length must overwrite the count — mixing these up double-counts.
  • Reading tails as the answer sequence: it isn't (see trap above). Reconstruction needs Version A + prev[].
  • "Minimum removals to sort" disguise: LC 1909 / "make array sorted" problems = n − LIS. Recognize the costume.
