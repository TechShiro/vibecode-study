DP on Trees

No table to fill here — the recursion is the iteration order. Each node returns a tiny tuple summarizing its subtree, and the parent just combines.

Mission link: DP is ~15% of Google intern questions and your self-identified gap. This is Lesson 10 of the 12-lesson DP track. Mission

1 · The one idea

On arrays we filled dp[i] left→right because state i depended on earlier indices. On a tree, a node's answer depends on its children's answers — so the natural fill order is postorder DFS: solve both subtrees first, then combine at the parent. The state is (node, small enum) — e.g. "best if this node is robbed" vs "best if skipped" — and the DFS returns that tuple instead of writing into a table. Memoization is free: each node is visited exactly once.

Recognition trigger A tree + "max / min / count over paths or subtrees", "place cameras / distribute coins", or a non-adjacent selection constraint (rob a node → can't rob its children). If the answer for a node is computable from a small fixed summary of each child, it's tree DP: postorder DFS returning a tuple.

2 · State · Recurrence · Base case

The 5-part framework, instantiated for House Robber III (LC 337):

  • State: dfs(node) returns int[]{rob, skip} — rob = best loot in this subtree if we rob node; skip = best if we don't.
  • Recurrence: rob = node.val + left.skip + right.skip (rob me → children must be skipped); skip = max(left.rob, left.skip) + max(right.rob, right.skip) (skip me → each child is free to choose).
  • Base case: null → {0, 0}. A missing subtree contributes nothing either way.
  • Order: postorder — recurse into children before computing the node's tuple. The call stack is the "table".
  • Answer: max(root.rob, root.skip).

3 · Core template

// LC 337 House Robber III — THE tree-DP template. State enum = {robbed, skipped}.
int rob(TreeNode root) {
    int[] r = dfs(root);
    return Math.max(r[0], r[1]);           // answer lives at the root: rob it or not
}
int[] dfs(TreeNode node) {                 // returns {rob, skip} for node's subtree
    if (node == null) return new int[]{0, 0};       // base case
    int[] L = dfs(node.left), R = dfs(node.right);  // postorder: children FIRST
    int rob  = node.val + L[1] + R[1];              // rob me → children forced to skip
    int skip = Math.max(L[0], L[1]) + Math.max(R[0], R[1]); // skip me → children choose freely
    return new int[]{rob, skip};
}

Time O(n) — each node computed once (this is the memoization; contrast the naive "rob root + grandchildren vs children" recursion, which re-solves subtrees exponentially). Space O(h) recursion stack, h = tree height. There is no bottom-up table version worth writing — postorder DFS already visits states in dependency order.

Return vs record — the one distinction that unlocks path problems For path problems, two different quantities live at every node: the best path ending at the node (straight — extendable upward, so you return it) and the best path through the node (bent left-node-right — it can't extend to the parent, so you record it in a global and never return it). Mixing these up is the #1 tree-DP bug.

Diameter (543) — the return-vs-record template

int best = 0;
int diameterOfBinaryTree(TreeNode root) { height(root); return best; }
int height(TreeNode n) {
    if (n == null) return 0;
    int l = height(n.left), r = height(n.right);   // O(n): heights computed ONCE, bottom-up
    best = Math.max(best, l + r);   // bent path THROUGH n (in edges) → RECORD globally
    return 1 + Math.max(l, r);      // straight path ENDING at n → RETURN to parent
}
The O(n²) trap Calling a separate height() for every node ("diameter = max over nodes of leftH+rightH") recomputes heights repeatedly — O(n²) on a skewed tree. Tree DP computes each height once inside the same postorder pass that updates the answer. Same subproblem, never solved twice — that's the DP.

Maximum Path Sum (124) — negatives join the party

int best = Integer.MIN_VALUE;              // NOT 0 — the whole tree can be negative
int maxPathSum(TreeNode root) { gain(root); return best; }
int gain(TreeNode n) {
    if (n == null) return 0;
    int l = Math.max(0, gain(n.left));     // a negative arm? drop it (take empty path)
    int r = Math.max(0, gain(n.right));
    best = Math.max(best, n.val + l + r);  // bent path through n → record
    return n.val + Math.max(l, r);         // straight path ending at n → return
}

Longest Univalue Path (687) — diameter with a membership test

Same skeleton as 543, but a child's arm only survives if the child's value matches the current node's. State: arm(n) returns the longest same-value path (in edges) starting at n and going straight down. Recurrence: recurse into both children first, then set each arm to childArm + 1 if child.val == n.val, else reset it to 0; record leftArm + rightArm (the bent path through n) globally and return the larger single arm. Base case: null → 0.

int best = 0;
int longestUnivaluePath(TreeNode root) { arm(root); return best; }
int arm(TreeNode n) {
    if (n == null) return 0;
    int l = arm(n.left), r = arm(n.right);   // ALWAYS recurse — a mismatching subtree may hold the answer
    int la = (n.left  != null && n.left.val  == n.val) ? l + 1 : 0;  // arm survives only on value match
    int ra = (n.right != null && n.right.val == n.val) ? r + 1 : 0;
    best = Math.max(best, la + ra);          // bent path through n → record
    return Math.max(la, ra);                 // straight arm ending at n → return
}

Time O(n), Space O(h) — one postorder pass, same as diameter.

Two classic bugs (1) Skipping the recursion into a mismatching child — wrong: the answer path may live entirely inside that subtree; you recurse everywhere and only reset the arm to 0. (2) Counting nodes instead of edges — 687's answer is in edges, so a single node scores 0.

Binary Tree Cameras (968) — a three-value state enum

// States: 0 = needs cover, 1 = covered (no camera), 2 = has camera.
int cameras = 0;
int minCameraCover(TreeNode root) {
    if (dfs(root) == 0) cameras++;         // root left uncovered → it needs its own camera
    return cameras;
}
int dfs(TreeNode n) {
    if (n == null) return 1;               // null pretends to be covered → leaves report 0
    int l = dfs(n.left), r = dfs(n.right);
    if (l == 0 || r == 0) { cameras++; return 2; } // a child needs cover → camera HERE
    if (l == 2 || r == 2) return 1;        // a child's camera watches me → covered
    return 0;                              // children fine but nobody watches me → ask parent
}

Why parents, not leaves, get cameras: a camera on a leaf covers 2 nodes; on the leaf's parent it covers up to 4. The state machine encodes exactly that greedy.

Distribute Coins (979) — return the flow, count the moves

int moves = 0;
int distributeCoins(TreeNode root) { excess(root); return moves; }
int excess(TreeNode n) {                   // (coins in subtree) − (nodes in subtree)
    if (n == null) return 0;
    int flow = excess(n.left) + excess(n.right) + n.val - 1;  // keep 1 coin for myself
    moves += Math.abs(flow);               // every surplus/deficit coin crosses my parent edge
    return flow;
}

Sum of Distances in Tree (834) — rerooting: two passes, every node gets to be root

One DFS from node 0 answers "sum of distances from 0" — but 834 wants that sum for every node, and n separate DFS runs are O(n²). Rerooting answers all n in two passes. State: size[u] = nodes in u's subtree, ans[u] = sum of distances from u. Down-pass (postorder): compute size[u] and, node by node, ans[0] — each child subtree contributes its own internal distances plus one extra edge per node in it, so ans[u] += ans[v] + size[v]. Base case: a leaf has size = 1, partial ans = 0. Up-pass (preorder): moving the root one edge from parent to child makes the size[child] nodes in the child's subtree one step closer and the other n − size[child] nodes one step farther, so the answer transfers in O(1): ans[child] = ans[parent] − size[child] + (n − size[child]) = ans[parent] + (n − 2·size[child]).

When rerooting fires The question asks for an answer with EVERY node as the root — "for each node, the sum/count/max over the whole tree" — and n is too big for n separate DFS runs. Recipe: one postorder pass for subtree facts + the root-0 answer, one preorder pass with an O(1) parent→child transfer formula. If you can write that transfer formula, the problem is done. 
int n; int[] size, ans;
List<List<Integer>> g;
int[] sumOfDistancesInTree(int n, int[][] edges) {
    this.n = n; size = new int[n]; ans = new int[n];
    g = new ArrayList<>();                        // adjacency list — 834 hands you an edge list
    for (int i = 0; i < n; i++) g.add(new ArrayList<>());
    for (int[] e : edges) { g.get(e[0]).add(e[1]); g.get(e[1]).add(e[0]); }
    down(0, -1);                                  // pass 1: size[] everywhere + ans[0] correct
    up(0, -1);                                    // pass 2: shift the root down every edge
    return ans;
}
void down(int u, int parent) {                    // postorder: subtree sizes + root-0 answer
    size[u] = 1;
    for (int v : g.get(u)) if (v != parent) {
        down(v, u);
        size[u] += size[v];
        ans[u]  += ans[v] + size[v];              // v's subtree: its distances + 1 extra edge each
    }
}
void up(int u, int parent) {                      // preorder: transfer BEFORE recursing
    for (int v : g.get(u)) if (v != parent) {
        ans[v] = ans[u] + n - 2 * size[v];        // size[v] nodes get closer, n−size[v] get farther
        up(v, u);
    }
}

Time O(n) — two linear DFS passes instead of n. Space O(n) for the adjacency list and arrays, O(h) recursion stack. This is the CP end of tree DP: know the two-pass shape and the transfer formula cold; deriving novel transfer formulas under interview pressure is beyond intern scope.

Order bugs that break rerooting In the up-pass, ans[v] must be set from ans[u] before recursing into v — preorder, the mirror of the down-pass's postorder. And after the down-pass, only ans[0] is a real answer; every other ans[u] is a partial (subtree-only) sum that the up-pass overwrites. Returning the array without the up-pass is the classic half-solution.

Worked example — dry run

House Robber III on root = [3,2,3,null,3,null,1]. Each node shows its computed {rob, skip} pair — filled bottom-up by the postorder DFS:

dfs(leaf 3): children null → {0,0}. rob = 3+0+0 = 3, skip = 0 → {3, 0} dfs(node 2): left null, right {3,0}. rob = 2 + 0(rightSkip) = 2; skip = max(3,0) = 3 → {2, 3} dfs(leaf 1): → {1, 0} dfs(node 3, right): rob = 3 + 0(leftSkip) + 0(rightSkip) = 3; skip = max(1,0) = 1 → {3, 1} dfs(root 3): rob = 3 + L.skip(3) + R.skip(1) = 7; skip = max(2,3) + max(3,1) = 3+3 = 6 → {7, 6} answer = max(7, 6) = 7 — rob the root and the two grandchildren

5 · Edge-case checklist

  • Null base case first. Decide what a missing subtree reports — {0,0} for robber, 0 for height, 1 ("covered") for cameras — and get it right before anything else.
  • Return vs record: path-through-node answers go into a global; only the extendable (straight) value is returned. Returning the bent path corrupts every ancestor.
  • Negative values (124): initialize best to Integer.MIN_VALUE, not 0, and clamp child gains with Math.max(0, ·) — an all-negative tree's answer is its largest single node.
  • Single-node tree: the combine step must degrade gracefully when both children are null.
  • Skewed trees: recursion depth = n in the worst case; for n ~ 10⁵ mention an iterative postorder (rarely required, always worth saying).
  • Don't recompute subtree facts (heights, sums) with separate helpers per node — that's the O(n²) trap. One postorder pass computes and consumes them.
