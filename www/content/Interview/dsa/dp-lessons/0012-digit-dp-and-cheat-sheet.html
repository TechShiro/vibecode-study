Digit DP & the DP Cheat Sheet

"How many integers ≤ N have property P?" — when N is 10¹⁸, you don't iterate numbers, you build their digits. Then: the one-page revision card for all twelve DP families.

Mission link: DP is ~15% of Google intern questions and your self-identified gap. This is Lesson 12 of 12 — the DP track finale. Mission

1 · The one idea

Every number ≤ N can be built digit by digit, left to right. At each position you're in one of two worlds: tight — every digit so far equals N's prefix, so this digit may go only up to N's digit — or free — you already dipped below N somewhere, so anything 0–9 is legal. Count recursively over (pos, propertyState, tight). The free world is where memoization pays: once you're free, the count depends only on (pos, state), and there are just len × states of those.

Recognition trigger "How many integers in [0, N] (or [L, R]) such that …" with N up to 10⁹–10¹⁸ — far too big to loop. Properties like "digits from a given set", "no two consecutive ones", "contains / counts a digit", "digit sum divisible by k". Range queries reduce via f(R) − f(L−1).

2 · State · Recurrence · Base case

  • State: dfs(pos, state, tight) = how many ways to complete digits pos..len−1, where state carries whatever the property needs (last digit, count so far, remainder mod k…) and tight says "still glued to N's prefix". Add a started flag when leading zeros would pollute the property.
  • Recurrence: try each digit d from 0 to limit (limit = N's digit if tight, else 9); recurse with the updated property state and tight' = tight && d == limit — you stay glued only by matching N exactly.
  • Base case: pos == len → return 1 if state satisfies the property, else 0.
  • Order: top-down memo — but cache only tight == false states. Each tight state occurs at most once per position (there's only one glued prefix), so caching it is pointless; free states repeat massively.
  • Answer: dfs(0, START, true). For [L, R]: f(R) − f(L−1).

3 · Core template

char[] s;
Integer[][] memo;                          // memo[pos][state] — for tight == false only

long countUpTo(long N) {                   // numbers in [0, N] whose digits satisfy the property
    s = Long.toString(N).toCharArray();
    memo = new Integer[s.length][STATES];
    return dfs(0, START, true);
}
int dfs(int pos, int state, boolean tight) {
    if (pos == s.length) return accept(state) ? 1 : 0;   // a full number is built — does it qualify?
    if (!tight && memo[pos][state] != null) return memo[pos][state];
    int limit = tight ? s[pos] - '0' : 9;  // glued to N? can't exceed N's digit here
    int total = 0;
    for (int d = 0; d <= limit; d++)
        total += dfs(pos + 1, next(state, d), tight && d == limit);  // stay tight only on the max digit
    if (!tight) memo[pos][state] = total;
    return total;
}

Time O(len · STATES · 10) — for N = 10¹⁸ that's 19 positions × a handful of states × 10 digits: microseconds. Space O(len · STATES). next(state, d) and accept(state) are the only parts that change between problems — the shell above never does.

The classic digit-DP bug The memo is only valid when tight == false. A tight state's answer depends on N's remaining digits — cache it without tight in the key and a later free visit reads a poisoned value (or vice versa). Either guard both the read and the write with !tight (as above), or make the memo 3-D with tight as a dimension. The one-flag guard is the standard idiom — tight states don't repeat anyway.

Numbers At Most N Given Digit Set (902)

int atMostNGivenDigitSet(String[] digits, int n) {
    char[] s = String.valueOf(n).toCharArray();
    int k = digits.length, len = s.length;
    int[] pow = new int[len + 1];          // pow[i] = k^i = free completions of i positions
    pow[0] = 1;
    for (int i = 1; i <= len; i++) pow[i] = pow[i - 1] * k;

    int count = 0;
    for (int i = 1; i < len; i++) count += pow[i];   // every SHORTER length is fully free (no leading-zero issue: set has no '0')
    for (int pos = 0; pos < len; pos++) {            // walk N's digits while tight
        boolean canStayTight = false;
        for (String d : digits) {
            if (d.charAt(0) < s[pos]) count += pow[len - pos - 1];  // drop below N here → suffix free
            if (d.charAt(0) == s[pos]) canStayTight = true;
        }
        if (!canStayTight) return count;             // glue broken — no digit matches N's
    }
    return count + 1;                                // survived every position → N itself qualifies
}

This is the digit-DP recursion unrolled: the tight spine is a single path, and every "drop below" branch contributes a closed-form k^remaining. When the free-world count has a formula, you don't even need the memo.

Practice — free-tier LeetCode

Non-negative Integers without Consecutive Ones (600) — digit DP in base 2

int findIntegers(int n) {
    int[] f = new int[32];                 // f[i] = count of i-bit FREE suffixes with no "11" (Fibonacci!)
    f[0] = 1; f[1] = 2;
    for (int i = 2; i < 32; i++) f[i] = f[i - 1] + f[i - 2];
    int count = 0, prev = 0;
    for (int i = 30; i >= 0; i--) {        // walk n's bits, high → low, staying tight
        if ((n & (1 << i)) != 0) {
            count += f[i];                 // place 0 where n has 1 → i lower bits go free
            if (prev == 1) return count;   // n's own prefix has "11" → tight path dies here
            prev = 1;
        } else prev = 0;
    }
    return count + 1;                      // n itself has no consecutive ones — count it
}

Same shell, base 2: limit comes from n's bits, and the property state is just the previous bit. The free-suffix counts turn out to be Fibonacci numbers — precompute them and the tight walk is O(32).

Practice — free-tier LeetCode

  • LC 600 · Non-negative Integers without Consecutive Ones (Hard) — the code above; watch the "glue dies when n itself contains 11" line.
  • LC 2376 · Count Special Integers (Hard) — all digits distinct: the property state grows from "previous bit" to a 10-bit mask of used digits, plus a started flag for leading zeros. Same shell, richer state.

Number of Digit One (233) — sum a quantity instead of counting

// dfs returns the TOTAL number of 1-digits across all completions — note the base case.
int dfs(int pos, int ones, boolean tight) {
    if (pos == s.length) return ones;      // each finished number contributes its own 1-count
    if (!tight && memo[pos][ones] != null) return memo[pos][ones];
    int limit = tight ? s[pos] - '0' : 9, total = 0;
    for (int d = 0; d <= limit; d++)
        total += dfs(pos + 1, ones + (d == 1 ? 1 : 0), tight && d == limit);
    if (!tight) memo[pos][ones] = total;
    return total;
}

The delta from the core template: the base case returns ones instead of 0/1, because each finished number contributes its count of 1-digits, not just its existence. The state space is still tiny — ones can only reach len, so the memo is len × len.

Practice — free-tier LeetCode

  • LC 233 · Number of Digit One (Hard, Google-reported) — the code above; the sum-a-quantity base case is the whole trick.
  • LC 1012 · Numbers With Repeated Digits (Hard) — complement counting: answer = N − (numbers with all-distinct digits); count the complement with a used-digit mask, like 2376 inside-out.

The [L, R] trick

Nothing in the state changes — you wrap the prefix counter twice. The only real content is the L = 0 edge (there is no −1 to count up to) and remembering that both calls rebuild s and the memo:

long countInRange(long L, long R) {
    return f(R) - (L == 0 ? 0 : f(L - 1));  // remove [0, L−1] so L itself stays counted
}
// f(N) = the countUpTo(N) from the core template — fresh s[] and memo per call!

Subtracting f(L) instead of f(L − 1) deletes L when it qualifies — the #1 wrong-answer on range digit-DP problems. And "shift the range to start at 0" never works: digit properties like "contains a 7" aren't shift-invariant.

Practice — free-tier LeetCode / CSES

  • LC 2719 · Count of Integers (Hard) — digit-sum in [min_sum, max_sum] over a range given as decimal strings: the f(R) − f(L−1) trick plus a mod, with L−1 done as string decrement.
  • CSES · Counting Numbers — "no two adjacent digits equal" on [a, b] up to 10¹⁸; the cleanest pure drill of this exact wrapper.

Worked example — dry run

Count numbers ≤ 234 using only digits {1, 2, 3} (LC 902 shape, k = 3). Walk N's digits keeping the tight spine; every dip below N releases a block of free completions:

shorter lengths (1 and 2 digits, no leading-zero worry): 3 + 3² = 12 pos 0, tight, limit 2: d=1 < 2 → free, 3² = 9 numbers (111..133) · d=2 = 2 → stay tight · d=3 > 2 → illegal pos 1, tight, limit 3: d=1,2 < 3 → free, 2 × 3 = 6 (211..223) · d=3 = 3 → stay tight pos 2, tight, limit 4: d=1,2,3 all ≤ 4 → 3 survivors (231, 232, 233) total = 12 + 9 + 6 + 3 = 30 sanity: 1-digit 3, 2-digit 9, 3-digit ≤ 234: 1xx = 9, 21x/22x/23x = 9 → 3+9+18 = 30 ✓

5 · Edge-case checklist

  • Leading zeros: if the property inspects actual digits (digit sets, "contains a 7"), add a started flag so a leading 0 means "number hasn't begun", not "digit 0 was used".
  • Memo vs tight: never cache tight states without including tight in the key — the safe habit is cache-only-when-free.
  • f(L−1) off-by-one: the range trick needs L−1, and L = 0 makes it −1 — special-case it.
  • long everywhere: N up to 10¹⁸ doesn't fit an int; counts can overflow too (use long, apply the modulus if asked).
  • Does 0 count? "Non-negative" (600) includes 0; "positive numbers made of set digits" (902) does not. Read the range's left end.
  • Base ≠ 10: 600 is the same template on bits — limit comes from n's binary digits.

6 · DP-optimization map

Sometimes the recurrence is right but too slow — the fix is speeding up the transition, not changing the state. The first two below are interview-real (learn them with code); the last three are Codeforces-level (learn to recognize them).

Monotonic deque — sliding-window max over dp

When it fires: the transition takes a max (or min) over a sliding window of earlier states — dp[i] = a[i] + max(dp[i−k..i−1]). Naively that inner max costs O(k) per i → O(nk) total. A deque of candidate indices, kept in decreasing dp order, answers each window-max in O(1): the front is always the current winner, and anything smaller than a newer value can never win again, so it's popped forever. This is exactly LC 239 Sliding Window Maximum, welded onto a dp array.

State: dp[i] = max sum of a valid subsequence ending at i (LC 1425: consecutive picks at most k apart). Recurrence: dp[i] = nums[i] + max(0, dp[i−k..i−1]) — the max(0, …) lets i start a fresh subsequence instead of extending a negative one. Base: the empty deque contributes 0.

int constrainedSubsetSum(int[] nums, int k) {   // LC 1425
    int n = nums.length;
    int[] dp = new int[n];
    ArrayDeque<Integer> dq = new ArrayDeque<>(); // indices; dp values decreasing front → back
    int best = Integer.MIN_VALUE;
    for (int i = 0; i < n; i++) {
        while (!dq.isEmpty() && dq.peekFirst() < i - k)
            dq.pollFirst();                       // evict indices that fell out of the window [i−k, i−1]
        int windowMax = dq.isEmpty() ? 0 : Math.max(0, dp[dq.peekFirst()]);
        dp[i] = nums[i] + windowMax;              // extend the best in-window chain, or start fresh (the 0)
        best = Math.max(best, dp[i]);
        while (!dq.isEmpty() && dp[dq.peekLast()] <= dp[i])
            dq.pollLast();                        // dominated: older AND ≤ dp[i] → can never be the max again
        dq.addLast(i);
    }
    return best;                                  // subsequence must be non-empty → best dp[i], not dp[n−1]
}

Time O(n) — each index enters and leaves the deque at most once. Space O(n) for dp (the deque holds ≤ k+1 indices). Same skeleton, min-deque instead of max: LC 1696 Jump Game VI.

Deque traps (1) Store indices, not values — you can't evict by age otherwise. (2) Evict from the front by window (< i − k), pop from the back by dominance — mixing the ends up is the classic bug. (3) In 1425 specifically, forgetting the max(0, …) forces every subsequence to chain through negatives and fails on all-negative inputs (answer should be the single largest element).

Practice — free-tier LeetCode

  • LC 239 · Sliding Window Maximum (Hard) — the deque primitive by itself, no DP; do this first.
  • LC 1425 · Constrained Subsequence Sum (Hard) — the template above; dp + window max.
  • LC 1696 · Jump Game VI (Medium) — identical shape with max score instead of subsequence sum; write it without looking.

Prefix-sum / prefix-max over dp

When it fires: the transition sums (or maxes) a contiguous range of earlier states — dp[i] = Σ dp[i−k..i−1]. Don't re-scan the range; carry a running window aggregate and update it in O(1) as i advances. Before/after on the same recurrence:

// BEFORE — O(n·k): every i re-scans its window
for (int i = 1; i <= n; i++)
    for (int j = Math.max(0, i - k); j < i; j++)
        dp[i] += dp[j];

// AFTER — O(n): maintain win = dp[i−k] + … + dp[i−1] incrementally
long win = dp[0];                          // window sum entering i = 1
for (int i = 1; i <= n; i++) {
    dp[i] = win;
    win += dp[i];                          // i joins the window for i+1
    if (i - k >= 0) win -= dp[i - k];      // i−k slides out — forget this line and win grows forever
}

Time O(n), Space O(n). For prefix-max over a window that only grows (no elements ever leave), a single running variable suffices; if elements leave, you're back to the deque above — that's how the two techniques divide the territory.

Practice — free-tier LeetCode

  • LC 837 · New 21 Game (Medium) — probabilities with dp[i] = (Σ dp[i−W..i−1]) / W; the sliding window sum is the entire solution.
  • LC 1871 · Jump Game VII (Medium) — reachable[i] = "any reachable j in [i−maxJump, i−minJump]?" — a windowed count of reachable states via prefix sums.

Codeforces-level: recognize, don't memorize

These three are beyond Google-intern interviews but standard in Div. 1/2 contests. For each, know the recurrence shape it fires on and what it buys — that's enough to look up the rest mid-practice.

  • Knuth's optimization — fires on interval DP dp[i][j] = min over k of (dp[i][k] + dp[k][j]) + cost(i, j) when the optimal split point is monotone: opt[i][j−1] ≤ opt[i][j] ≤ opt[i+1][j] (holds when cost satisfies the quadrangle inequality). Searching k only between those bounds telescopes O(n³) → O(n²). Practice: the classic Breaking Strings / Optimal BST problem (UVa 10003 "Cutting Sticks" is the same DP — LC 1547 without Knuth, then add the bound).
  • Divide & conquer optimization — fires on layered transitions dp[t][i] = min over j<i of (dp[t−1][j] + cost(j, i)) when the argmin is monotone in i. Solve each layer by recursing on (range of i, range of candidate j), splitting at the midpoint's argmin: O(k·n²) → O(k·n log n). Practice: Codeforces 321E "Ciel and Gondolas".
  • Convex hull trick (CHT) — fires when the transition is a min/max over lines: dp[i] = min over j of (mj·xi + cj), i.e. cost splits into (slope from j) × (query from i) + intercept. Maintain the lower envelope of the lines; each query is amortized O(1) (sorted slopes/queries) or O(log n) (Li Chao tree): O(n²) → O(n log n). Practice: Codeforces 319C "Kalila and Dimna in the Logging Industry".
Contest smell test If a Codeforces DP is Θ(n²) with n = 10⁵ (or Θ(n³) intervals with n = 5000), the intended solution is almost certainly one of these three. Identify which by the transition's shape: split point in an interval → Knuth; layered min with monotone argmin → D&C; lines in the cost → CHT.
