Monotonic Stack Track · Lesson 1 of 2 · next/previous greater & smaller in O(n)

The Next-Greater Family

Every "for each element, find the nearest bigger/smaller one" question looks O(n²) — a stack that stays sorted answers all of them in one pass.

Mission link: Daily Temperatures and Next Greater Element are among the most common OA warm-ups at Amazon and Google — and Lesson 2's histogram problems (a genuine hard-question staple) are built entirely on this one. This is Lesson 1 of the 2-lesson monotonic-stack track. Mission

1 · The one idea

Take Daily Temperatures: for each day, how many days until a warmer one? The naive answer scans right from every index — O(n²), and on a descending array it really does n²/2 work. Now flip the question: instead of each day searching forward for its answer, let each new day deliver answers backward. Keep a stack of days still waiting for a warmer day. When a new temperature arrives, it resolves — pops — every waiting day it beats. Colder days pile up; one hot day pays off the whole pile.

Because a day is pushed once and popped at most once, the total work is ~2n stack operations — O(n), even though one arrival may pop many items. That amortized push-once/pop-once argument is the pattern. And notice what the stack looks like between arrivals: every element that survives is smaller-or-equal below the newcomer's victims — the stack stays sorted (decreasing from bottom to top). Hence the name: monotonic stack.

Recognition trigger "Next / previous greater / smaller element", "days until a warmer temperature", "span of consecutive smaller values", histograms and skyline shapes, "remove digits to make it smallest". Any per-element question about the nearest dominating neighbor to the left or right. If your first idea is a nested scan from each index — this pattern deletes the inner loop.

2 · Core template — next greater to the right (Daily Temperatures, LC 739)

int[] dailyTemperatures(int[] t) {
    int n = t.length;
    int[] ans = new int[n];                // 0 = "no warmer day" (default)
    Deque<Integer> st = new ArrayDeque<>();// stack of INDICES; temps decreasing bottom→top
    for (int i = 0; i < n; i++) {
        while (!st.isEmpty() && t[i] > t[st.peek()]) {
            int j = st.pop();              // day j just found its answer: it's day i
            ans[j] = i - j;                // distance — possible only because we stored indices
        }
        st.push(i);                        // i now waits for ITS next-greater
    }
    return ans;                            // whatever's left on the stack keeps ans = 0
}

Time O(n) — each index pushed once, popped at most once, so the while-loop's total cost across the whole run is ≤ n pops. Space O(n) worst case (strictly decreasing input keeps everything stacked). Use Deque/ArrayDeque, not the legacy java.util.Stack.

t = [73, 74, 75, 71, 69, 72, 76], stack holds indices (shown as temps) i=0 (73): stack empty → push. st = [73] i=1 (74): 74 > 73 → pop, ans[0]=1; push. st = [74] i=2 (75): 75 > 74 → pop, ans[1]=1; push. st = [75] i=3 (71): 71 < 75 → just push. st = [75, 71] i=4 (69): push. st = [75, 71, 69] ← decreasing, the "waiting pile" i=5 (72): pops 69 (ans[4]=1) and 71 (ans[3]=2); push. st = [75, 72] i=6 (76): pops 72 (ans[5]=1) and 75 (ans[2]=4); push. st = [76] 76 never popped → ans[6] = 0. Total pushes 7, pops 6 → O(n).

The two dials: direction of monotonicity, and what you store

  • Looking for next GREATER → keep the stack DECREASING (pop while new > top). Looking for next SMALLER → keep it INCREASING (pop while new < top). Rule of thumb: the stack holds elements still waiting, so it's sorted in the direction that keeps them unresolved — you pop exactly the ones the newcomer resolves.
  • Equal elements: decide whether ties resolve. "Strictly warmer" → pop only on >, equal values stack up. In Lesson 2's LC 907, the strict/non-strict choice on each side is what prevents double-counting.
  • Store INDICES, not values, whenever the answer involves distance (739), position, or width (all of Lesson 2). Store values only when a value-keyed map is the output (496) or you compress runs (901 stores value+count pairs). Indices are the safe default — t[st.peek()] recovers the value for free; a value can't recover its index.

Case: Next Greater Element I (LC 496) — values into a map

nums1 is a subset of nums2 (all values distinct). Solve NGE once over nums2; because values are unique, a value→answer map is enough — no indices needed.

int[] nextGreaterElement(int[] nums1, int[] nums2) {
    Map<Integer, Integer> nge = new HashMap<>();
    Deque<Integer> st = new ArrayDeque<>();     // stack of VALUES — distinct, and output is by value
    for (int x : nums2) {
        while (!st.isEmpty() && x > st.peek())
            nge.put(st.pop(), x);               // x is the next greater for everything it pops
        st.push(x);
    }
    int[] ans = new int[nums1.length];
    for (int i = 0; i < nums1.length; i++)
        ans[i] = nge.getOrDefault(nums1[i], -1); // never popped → no greater → -1
    return ans;
}

Case: Next Greater Element II — circular (LC 503)

In a circular array, an element's next greater may sit behind it. Standard trick: pretend the array is laid out twice and sweep 2n steps with i % n. The second lap only resolves leftovers — don't push again, or you'd answer an element with itself's neighborhood twice. 

int[] nextGreaterElements(int[] a) {
    int n = a.length;
    int[] ans = new int[n];
    Arrays.fill(ans, -1);                       // a max element never finds a greater
    Deque<Integer> st = new ArrayDeque<>();     // indices
    for (int i = 0; i < 2 * n; i++) {
        int x = a[i % n];                       // virtual second copy of the array
        while (!st.isEmpty() && x > a[st.peek()])
            ans[st.pop()] = x;
        if (i < n) st.push(i);                  // push each index ONCE — lap 2 only resolves
    }
    return ans;
}

Case: Online Stock Span (LC 901) — streaming, compress with counts

Span = 1 + how many consecutive previous prices were ≤ today's. That's a "previous strictly greater" question in disguise — pop everything ≤ today. Since prices arrive one at a time and popped days can never matter again (today dominates them for all future queries too), store (price, span) pairs and let today absorb the spans it pops. 

class StockSpanner {
    private final Deque<int[]> st = new ArrayDeque<>(); // {price, span} — prices strictly decreasing
    public int next(int price) {
        int span = 1;                           // today itself
        while (!st.isEmpty() && st.peek()[0] <= price)
            span += st.pop()[1];                // absorb the popped run — its days are ≤ mine too
        st.push(new int[]{price, span});
        return span;
    }
}

Time amortized O(1) per next call — same push-once/pop-once argument, spread over the stream.

Case: previous smaller element (generic template)

Mirror image, and the key that unlocks Lesson 2: sweep left→right with an increasing stack. Here the answer isn't found by popping — it's whoever survives on top after the pops: everything ≥ me is popped (useless as a "previous smaller"), so the survivor is the nearest smaller one. 

int[] prevSmaller(int[] a) {                    // prevSmaller[i] = index of nearest smaller to the left, else -1
    int n = a.length;
    int[] ans = new int[n];
    Deque<Integer> st = new ArrayDeque<>();     // indices; values increasing bottom→top
    for (int i = 0; i < n; i++) {
        while (!st.isEmpty() && a[st.peek()] >= a[i])
            st.pop();                           // ≥ me can never be anyone's "previous smaller" past me
        ans[i] = st.isEmpty() ? -1 : st.peek(); // the SURVIVOR is my answer (contrast: 739 answers on pop)
        st.push(i);
    }
    return ans;
}
One template, two read-out modes Answer-on-pop (739, 496, 503): the newcomer is the popped element's answer — "next X" problems. Answer-on-peek (previous smaller, and both bounds in Lesson 2): after popping, the top of the stack is the newcomer's answer — "previous X" problems. Same loop; you just read the answer at a different moment.

4 · Edge-case checklist

  • Wrong monotonic direction — popping on < when hunting next-greater silently returns garbage. Re-derive: "who does the newcomer resolve?"
  • Strict vs non-strict comparison with duplicates: [3, 3] — does the second 3 pop the first? For "strictly warmer" no; for stock span yes (<=). Read the problem statement's tie rule.
  • Values when you needed indices: if the answer mentions distance, width, or position, store indices. LC 496 gets away with values only because they're distinct.
  • Circular arrays: 2n sweep with i % n, push only on the first lap; forgetting the push-guard duplicates entries.
  • Leftovers on the stack at the end have no next-greater — make sure your default (0, −1) is prefilled, not left as accidental garbage.
  • Empty-stack peeks: every peek/pop sits behind an isEmpty() guard (or a sentinel — Lesson 2 uses those).
  • Use ArrayDeque, not java.util.Stack (legacy, synchronized, slower) — interviewers notice.
