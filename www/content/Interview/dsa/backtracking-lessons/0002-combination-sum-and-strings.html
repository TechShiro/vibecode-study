Combination Sum & String Backtracking

Same choose→explore→unchoose skeleton, two new levers: a numeric budget that prunes branches, and strings where each "choice" is the next chunk you consume or the next character you append.

Mission link: Combination Sum and Generate Parentheses are two of the most-reported backtracking questions in big-tech OAs — and both are 15-line solutions once you see the knobs. This is Lesson 2 of the 3-lesson backtracking track. Mission

1 · The one idea

Lesson 1's template enumerated structures (subsets, permutations). This lesson adds a goal and a budget: carry the remaining target down the tree, succeed when it hits 0, and prune any branch that already overshot. The single most-tested detail: when an element may be reused, recurse with i (stay on the same candidate); when it's use-once, recurse with i + 1. For strings, nothing conceptually changes — the "path" is a StringBuilder or a list of chunks, and a choice is either "append this char" or "consume this prefix."

Recognition trigger "All combinations that sum to target," "all ways to split / partition this string," "generate all valid strings (parentheses, IPs, phone letters)." The tell: the answer is a set of sequences, and each sequence is built left-to-right by repeatedly choosing what comes next. If any prefix can be proven invalid early (sum too big, more ')' than '(', segment > 255) — that's your pruning, and pruning is where the marks are.

2 · Core template — Combination Sum (LC 39)

Distinct positive candidates, unlimited reuse, find all combinations summing to target. Sort first so one break kills every too-big sibling at once. 

List<List<Integer>> res = new ArrayList<>();

List<List<Integer>> combinationSum(int[] cand, int target) {
    Arrays.sort(cand);                    // enables the break-prune below
    backtrack(cand, 0, target, new ArrayList<>());
    return res;
}

void backtrack(int[] cand, int start, int remain, List<Integer> path) {
    if (remain == 0) {                    // budget exactly spent → record a leaf
        res.add(new ArrayList<>(path));
        return;
    }
    for (int i = start; i < cand.length; i++) {
        if (cand[i] > remain) break;      // PRUNE: sorted, so every later cand is too big too
        path.add(cand[i]);                // CHOOSE
        backtrack(cand, i, remain - cand[i], path); // EXPLORE with i (NOT i+1): reuse allowed
        path.remove(path.size() - 1);     // UNCHOOSE
    }
}

Time — branching ≤ n, depth ≤ target / min(cand), so O(ntarget/min) in the worst case; state it as "exponential in target/min, output-sensitive in practice." Space O(target/min) recursion depth.

Why i keeps it duplicate-free even with reuse Recursing with i allows [2,2,3] (stay on index 0, then move on) but still forbids revisiting earlier indices — so [3,2,2] is never built. Non-decreasing index order = one canonical ordering per combination. Reuse and dedup are handled by the same single character: i vs i + 1.

Two numeric variants, four string builders. The table is the whole lesson — the snippets show the one knob each turns.

Case: Combination Sum II — use once, duplicates in input (LC 40)

Two changes from the core, both from Lesson 1's toolkit: i + 1 (each array element used at most once) and the dedup skip (equal siblings would rebuild the same combination). 

void backtrack(int[] cand, int start, int remain, List<Integer> path) {
    if (remain == 0) { res.add(new ArrayList<>(path)); return; }
    for (int i = start; i < cand.length; i++) {
        if (cand[i] > remain) break;                          // same sorted prune
        if (i > start && cand[i] == cand[i - 1]) continue;    // dedup-skip idiom (input sorted)
        path.add(cand[i]);
        backtrack(cand, i + 1, remain - cand[i], path);       // i+1: this element is spent
        path.remove(path.size() - 1);
    }
}
39 vs 40 in one breath Reuse allowed → i, no dedup needed (candidates distinct). Use-once with duplicate values → i + 1 and sort + skip. Interviewers ask for the diff verbally — practice saying it.

Case: Generate Parentheses — constraint pruning (LC 22)

Build the string one char at a time. A prefix stays extendable-to-valid iff you've used at most n opens and never have more closes than opens. Enforce that before recursing and every leaf you reach is automatically valid — zero wasted work. 

List<String> res = new ArrayList<>();

List<String> generateParenthesis(int n) {
    bt(new StringBuilder(), 0, 0, n);
    return res;
}
void bt(StringBuilder sb, int open, int close, int n) {
    if (sb.length() == 2 * n) {           // invariants held all the way → valid leaf
        res.add(sb.toString());
        return;
    }
    if (open < n) {                       // may still open
        sb.append('(');
        bt(sb, open + 1, close, n);
        sb.deleteCharAt(sb.length() - 1); // unchoose = delete last char
    }
    if (close < open) {                   // close only what's already open — the pruning
        sb.append(')');
        bt(sb, open, close + 1, n);
        sb.deleteCharAt(sb.length() - 1);
    }
}

Time O(4ⁿ/√n) — the n-th Catalan number of leaves, each of length 2n. Space O(n) depth. Contrast: generate all 22n strings and filter = TLE; prune prefixes = pass. That contrast is Lesson 3's theme.

Case: Letter Combinations of a Phone Number (LC 17)

The simplest string builder: position idx in digits is the depth, and the choice-set is that digit's letters. Product of choice-set sizes = number of leaves. 

String[] KEYS = {"", "", "abc", "def", "ghi", "jkl", "mno", "pqrs", "tuv", "wxyz"};
List<String> res = new ArrayList<>();

List<String> letterCombinations(String digits) {
    if (digits.isEmpty()) return res;     // EDGE: "" → [] (not [""])
    bt(digits, 0, new StringBuilder());
    return res;
}
void bt(String digits, int idx, StringBuilder sb) {
    if (idx == digits.length()) { res.add(sb.toString()); return; }
    for (char c : KEYS[digits.charAt(idx) - '0'].toCharArray()) {
        sb.append(c);                     // CHOOSE a letter for this digit
        bt(digits, idx + 1, sb);
        sb.deleteCharAt(sb.length() - 1); // UNCHOOSE
    }
}

Time O(n·4ⁿ) worst case (digits 7 and 9 have 4 letters) · Space O(n).

Case: Palindrome Partitioning — choice = the next chunk (LC 131)

Mental shift: instead of choosing one character, choose where the current piece ends. From start, try every end; recurse only if s[start..end] is a palindrome. Reaching start == s.length() means the whole string was consumed by valid pieces. 

void bt(String s, int start, List<String> path) {
    if (start == s.length()) {            // consumed everything → path is a full partition
        res.add(new ArrayList<>(path));
        return;
    }
    for (int end = start; end < s.length(); end++) {
        if (!isPal(s, start, end)) continue;  // invalid chunk → prune this branch
        path.add(s.substring(start, end + 1)); // CHOOSE the chunk
        bt(s, end + 1, path);                  // EXPLORE the rest of the string
        path.remove(path.size() - 1);          // UNCHOOSE
    }
}
boolean isPal(String s, int l, int r) {
    while (l < r) if (s.charAt(l++) != s.charAt(r--)) return false;
    return true;
}

Time O(n·2ⁿ) — up to 2n−1 partitions, O(n) per copy/check. Space O(n). Follow-up interviewers love: precompute an isPal[i][j] table with DP in O(n²) so each check is O(1) — your first taste of "backtracking + DP" before Lesson 3.

Case: Restore IP Addresses (LC 93)

Same consume-a-chunk shape with harder chunk rules: exactly 4 segments, each 1–3 chars, value ≤ 255, no leading zero ("0" is fine, "01" is not). 

void bt(String s, int start, int parts, StringBuilder sb) {
    if (parts == 4) {                     // 4 segments placed…
        if (start == s.length())          // …and every char consumed → valid IP
            res.add(sb.substring(0, sb.length() - 1)); // drop the trailing '.'
        return;
    }
    // PRUNE: remaining chars must fit in the remaining segments (1–3 chars each)
    int left = s.length() - start, need = 4 - parts;
    if (left < need || left > 3 * need) return;
    for (int len = 1; len <= 3 && start + len <= s.length(); len++) {
        String seg = s.substring(start, start + len);
        if (seg.length() > 1 && seg.charAt(0) == '0') break;  // leading zero → longer is worse too
        if (Integer.parseInt(seg) > 255) break;               // too big → longer is bigger
        int mark = sb.length();
        sb.append(seg).append('.');       // CHOOSE segment + dot
        bt(s, start + len, parts + 1, sb);
        sb.setLength(mark);               // UNCHOOSE by truncating — cleaner than two deletes
    }
}

Time O(1) for the fixed problem — at most 3⁴ = 81 segment-length patterns on a ≤ 12-char string; say "constant bounded, 3^4 branches." Space O(1) beyond output.

4 · Edge-case checklist

  • i vs i + 1 is the whole difference between LC 39 and 40. Reuse → i; spent → i + 1. Never start unchanged and never i with duplicates in input unless you dedup.
  • break vs continue when pruning: break only when the array is sorted and the disqualifier is monotone (too big ⇒ all later too big). Leading-zero and >255 in LC 93 justify break because longer segments only get worse.
  • Empty string input (LC 17): "" must return [], not [""] — guard before recursing.
  • StringBuilder unchoose: either deleteCharAt(length-1) per char appended, or record mark = sb.length() and sb.setLength(mark) — the mark trick is safer when you append multi-char chunks.
  • Success ≠ "budget small", success = "budget exactly 0" / "string fully consumed". LC 93's double condition (parts == 4 AND start == length) is the classic miss.
  • Negative or zero candidates would break the prune — LC 39/40 guarantee positives; say that assumption out loud in an interview.
  • Single characters are palindromes, so LC 131 always has at least one partition — no "no answer" branch needed.
