Backtracking Track · Lesson 1 of 3 · the decision-tree template

Choose → Explore → Unchoose

Backtracking is just DFS on an imaginary tree of decisions — one template, three lines of ritual, and it generates every subset, permutation, and combination you'll ever be asked for.

Mission link: "generate all X" questions are OA staples at Amazon, Google, and Microsoft — and they're free points once the template is muscle memory. This is Lesson 1 of the 3-lesson backtracking track. Mission

1 · The one idea

You already know recursion. Backtracking is recursion with one twist: you build a partial candidate (a growing list called path) as you recurse, and you undo each addition on the way back up so the same path object can be reused for the next branch. Picture a decision tree: the root is the empty candidate, every edge is one choice ("include nums[i]"), every node is a partial answer. Backtracking is a depth-first walk of that tree. The ritual at every level is always the same three lines: choose (add to path), explore (recurse), unchoose (remove what you added).

Recognition trigger "Return all subsets / permutations / combinations / partitions / valid strings," "generate every…," or a constraint puzzle where you place items one by one and may hit dead ends. Giveaway in the constraints: n ≤ ~20 (subsets) or n ≤ ~10 (permutations) — the answer set itself is exponential, so the interviewer expects exponential time. If the question asks only for a count, a boolean, or a best value, suspect DP instead (Lesson 3 covers that boundary).

2 · Core template — Subsets (LC 78)

Given distinct nums, return every subset. At each depth we loop i from start onward, which enforces ascending index order — that's what makes [1,2] and [2,1] the same subset generated exactly once. 

List<List<Integer>> res = new ArrayList<>();

List<List<Integer>> subsets(int[] nums) {
    backtrack(nums, 0, new ArrayList<>());
    return res;
}

void backtrack(int[] nums, int start, List<Integer> path) {
    res.add(new ArrayList<>(path));       // record a COPY — every node of the tree is a subset
    for (int i = start; i < nums.length; i++) {
        path.add(nums[i]);                // CHOOSE: include nums[i]
        backtrack(nums, i + 1, path);     // EXPLORE: only indices AFTER i (no reordering, no reuse)
        path.remove(path.size() - 1);     // UNCHOOSE: undo, so the next i starts clean
    }
}

Time O(n·2ⁿ) — 2ⁿ subsets, each copied in up to O(n). Space O(n) for the recursion stack and path (output not counted).

The decision tree for nums = [1, 2, 3]

path = [] → record [ ] · loop i = 0..2 i=0: choose 1 → path [1] → record · recurse start=1   i=1: choose 2 → path [1,2] → record · recurse start=2     i=2: choose 3 → path [1,2,3] → record · recurse start=3 (loop empty) · unchoose 3   unchoose 2 → path [1] · i=2: choose 3 → [1,3] → record · unchoose 3 unchoose 1 → path [] · i=1: choose 2 → [2] … and so on
Why "unchoose" must mirror "choose" exactly path is one shared object threaded through the whole tree. Every mutation you make before recursing must be undone after, or sibling branches inherit garbage. Rule: whatever state the choose step touches (list, used[] flag, counter, grid cell), the unchoose step restores — same lines, reversed.

3 · Why the time is exponential — and how to say it

The tree has one leaf (or node) per answer, and the number of answers is combinatorial: 2ⁿ subsets, n! permutations, C(n,k) combinations. No algorithm that outputs all of them can beat that. The interview-ready phrasing: "the complexity is output-sensitive — (number of solutions) × (cost to build/copy each one)". So Subsets is O(n·2ⁿ), Permutations is O(n·n!), Combinations is O(k·C(n,k)). Auxiliary space is just the O(n) recursion depth plus path.

4 · All the cases

Five problems, one template. Only two knobs ever move: how you pick candidates (a start index vs a used[] array) and whether you dedup (sort + skip).

Case: Subsets II — duplicates in the input (LC 90)

With nums = [1,2,2], the plain template emits [1,2] twice (once per 2). Fix: sort so equal values are adjacent, then at each tree level let only the first copy of a value start a branch. 

List<List<Integer>> subsetsWithDup(int[] nums) {
    Arrays.sort(nums);                    // dedup REQUIRES sorted input
    backtrack(nums, 0, new ArrayList<>());
    return res;
}
void backtrack(int[] nums, int start, List<Integer> path) {
    res.add(new ArrayList<>(path));
    for (int i = start; i < nums.length; i++) {
        // THE dedup-skip idiom: same value as my left SIBLING at this level → identical branch, skip
        if (i > start && nums[i] == nums[i - 1]) continue;
        path.add(nums[i]);
        backtrack(nums, i + 1, path);
        path.remove(path.size() - 1);
    }
}
Why i > start, NOT i > 0 i > start skips a duplicate only when it's a sibling (same loop, same level) of an equal value already tried. When i == start, the equal value is being stacked deeper — that's how [2,2] gets generated at all. Writing i > 0 kills every stacked duplicate and silently drops answers like [2,2] and [1,2,2]. Memorize the exact form: if (i > start && a[i] == a[i-1]) continue;

Case: Permutations (LC 46)

Now [1,2] and [2,1] are different answers, so ascending order would be wrong. Drop start; at every depth consider every index not yet used. A boolean[] used is the choose/unchoose state alongside path. 

void backtrack(int[] nums, boolean[] used, List<Integer> path) {
    if (path.size() == nums.length) {     // record only COMPLETE candidates (leaves)
        res.add(new ArrayList<>(path));
        return;
    }
    for (int i = 0; i < nums.length; i++) {
        if (used[i]) continue;            // already in path
        used[i] = true;  path.add(nums[i]);          // CHOOSE (two pieces of state)
        backtrack(nums, used, path);                 // EXPLORE
        path.remove(path.size() - 1);  used[i] = false; // UNCHOOSE (both!)
    }
}

Time O(n·n!) · Space O(n).

Case: Permutations II — duplicates (LC 47)

Sort, then the permutation flavor of the skip: among equal values, force them to be picked left to right. If nums[i-1] is equal and not currently used, picking nums[i] now would recreate a branch the first copy already produced. 

for (int i = 0; i < nums.length; i++) {
    if (used[i]) continue;
    // equal to left neighbor AND that neighbor is not in the current path → duplicate branch
    if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;
    used[i] = true;  path.add(nums[i]);
    backtrack(nums, used, path);
    path.remove(path.size() - 1);  used[i] = false;
}

Case: Combinations — choose k of n (LC 77)

Subsets template with a size gate: record only when path.size() == k. Bonus: a free pruning bound — if the numbers remaining can't fill the path to size k, don't even branch. 

void backtrack(int n, int k, int start, List<Integer> path) {
    if (path.size() == k) {               // exactly k picked → record leaf
        res.add(new ArrayList<>(path));
        return;
    }
    // prune: need (k - path.size()) more numbers; last viable start is n - need + 1
    for (int i = start; i <= n - (k - path.size()) + 1; i++) {
        path.add(i);
        backtrack(n, k, i + 1, path);
        path.remove(path.size() - 1);
    }
}

Time O(k·C(n,k)) · Space O(k).

5 · Edge-case checklist

  • Record a COPY: res.add(new ArrayList<>(path)). Adding path itself stores a reference that later mutates — you end up with a result full of identical (empty) lists. #1 backtracking bug.
  • Unchoose everything you chose. If choose sets two things (path + used[i]), unchoose resets both, in any order, but never skip one.
  • Dedup requires sorting first. The skip idiom compares neighbors — unsorted input makes it silently wrong, not just slow.
  • start vs used[]: combinations/subsets (order irrelevant) → start + i + 1; permutations (order matters) → used[] over all indices. Picking the wrong one gives duplicate or missing answers.
  • path.remove(path.size() - 1), never path.remove(value): with List<Integer>, remove(int) is by index but remove(Integer) is by value — an autoboxing trap that removes the wrong element.
  • Empty input: Subsets of [] is [[]] (one empty subset) — the record-at-every-node template handles it automatically; a record-at-leaf version might not.
  • Sanity-check the count: 2ⁿ subsets, n! permutations. If n = 3 and you got 6 subsets or 8 permutations, the tree shape is wrong.
