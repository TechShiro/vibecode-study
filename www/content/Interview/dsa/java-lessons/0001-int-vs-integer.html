int vs Integer

One is a 32-bit value on the stack; the other is a heap object that can be null. Confusing them is the source of the most embarrassing interview bugs — NullPointerException on an int, and == that lies.

Mission link: these Java internals are asked directly in Google India SWE-intern interviews, and they're the source of subtle bugs that fail you on hidden test cases. Know them cold. Mission

1 · The one idea

int is a primitive — a raw 32-bit value living directly in a variable (stack / array slot). Integer is an object — a box on the heap that holds one int plus an object header and a reference. You need Integer the instant you want null ("no value"), or you want to put numbers into a generic collection (List, Map, PriorityQueue) — generics can't hold primitives. Everywhere else, prefer int: it's smaller, faster, and can never be null.

When this fires in an interview You reach for Integer the moment you write List<Integer>, Map<String,Integer>, or Deque<Integer> — generics force the wrapper. The danger zone is the boundary: every time a value crosses from a collection back into an int (int x = map.get(k);), Java silently unboxes — and if the wrapper is null, you get a runtime crash on a line that looks like pure arithmetic.

2 · Autoboxing & unboxing

Java auto-converts between the two so you rarely write the conversion yourself. Autoboxing = int → Integer (calls Integer.valueOf); unboxing = Integer → int (calls .intValue()). It's invisible — and that's exactly why it bites. 

List<Integer> list = new ArrayList<>();
list.add(5);            // autobox: 5 -> Integer.valueOf(5)
int x = list.get(0);    // unbox: Integer -> int via intValue()

Integer a = 10;         // autobox
int b = a + 1;          // unbox a, add, result is int
The NullPointerException that looks impossible Unboxing a null Integer throws NullPointerException — on a line of plain arithmetic. The classic: map.get(key) returns null for a missing key, and you unbox it straight into an int. 
Map<String,Integer> count = new HashMap<>();
int n = count.get("missing");   // get() returns null -> unbox null -> NPE!

// Fix: never unbox a value that might be absent
int safe = count.getOrDefault("missing", 0);   // stays an int, defaults to 0
Integer raw = count.get("missing");            // or keep it boxed and null-check
if (raw != null) { /* use raw */ }

3 · The == trap

For int, == compares values — always correct. For Integer, == compares object references: "are these the same box?", not "are the values equal?". To compare the numbers, use .equals() or compare unboxed ints.

The Integer cache makes it pass small tests, then fail big ones Java caches Integer objects for −128..127, so autoboxing values in that range returns the same cached object — and == happens to return true. Outside the range you get fresh objects, so == returns false. Same code, different answer depending on the value. 
Integer a = 100, b = 100;
System.out.println(a == b);        // true  — both from the -128..127 cache

Integer c = 500, d = 500;
System.out.println(c == d);        // false — two different heap objects!
System.out.println(c.equals(d));   // true  — compares values (correct)
System.out.println(c.intValue() == d.intValue()); // true — compare as int
Rule: never use == on two Integers. Use .equals() (after a null check) or compare int values.

Worked example — dry run

Code: Integer x = 500, y = 500; int a = 500, b = 500; Because 500 is outside the −128..127 cache, autoboxing x and y creates two separate heap objects at different addresses. The primitives a and b are raw values, not references. Walk each comparison:

x == y → compares object REFERENCES → @0x1A ≠ @0x2F → false x.equals(y) → compares VALUES → 500 == 500 → true a == b (primitives) → compares values directly → true if instead value = 100: Integer p = 100, q = 100; p == q → cache returns the SAME box → true (the trap!)

4 · Overflow

Both int and Integer are 32-bit. The range is Integer.MIN_VALUE = −2,147,483,648 to Integer.MAX_VALUE = 2,147,483,647. Exceed it and Java silently wraps around — no exception, just a wrong (often negative) number.

The two overflow bugs that fail hidden test cases These look correct and pass small inputs, then wrap on the large ones interviewers add on purpose. 
// (1) The infamous binary-search midpoint bug
int mid = (lo + hi) / 2;          // lo+hi can overflow when both are large
int mid = lo + (hi - lo) / 2;     // FIX: never overflows

// (2) Summing many / large values
int sum = 0;
for (int w : weights) sum += w;   // overflows if the total > 2.1e9
long sum = 0;                     // FIX: accumulate in a long
for (int w : weights) sum += w;
Whenever a sum, product, or a+b could plausibly exceed ~2.1 billion, accumulate in long (64-bit, ~9.2×10¹⁸). For the midpoint, use lo + (hi - lo) / 2.

5 · Performance: int[] vs List<Integer>

A List<Integer> stores a reference to a separate heap object for every element: more memory, worse cache locality, and boxing/unboxing on every access. An int[] is one contiguous block of raw values — several times smaller and faster. In a tight inner loop the difference is real.

 int[]List<Integer>
StorageContiguous raw valuesReferences to boxed objects
Speed / cacheFast, cache-friendlySlower, pointer-chasing + boxing
Resizable?No — fixed lengthYes — grows dynamically
Works with generics?NoYes (collections, comparators)
How to choose Use int[] for fixed-size, performance-critical work (DP tables, frequency arrays, hot loops). Use List<Integer> when the size grows dynamically or you need generics/collection APIs. When unsure on a hot path in competitive programming, default to int[].

7 · Edge-case checklist

  • Unboxing null → NullPointerException on arithmetic. Use getOrDefault or null-check before assigning to an int.
  • == on two Integers → compares references; the −128..127 cache makes it pass for small values, fail for large. Use .equals() or compare int values.
  • (lo + hi) / 2 → overflow. Use lo + (hi - lo) / 2.
  • Summing into an int → silent wraparound past 2.1e9. Accumulate in long.
  • (a - b) comparator → overflow flips the sign for far-apart values. Use Integer.compare(a, b).
  • List<Integer> in a hot loop → boxing overhead + cache misses. Prefer int[] when size is fixed.
  • Default values differ → a fresh int[] is all 0; an Integer[] / uninitialized Integer field is null.
