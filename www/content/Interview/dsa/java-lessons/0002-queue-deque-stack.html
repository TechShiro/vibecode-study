Queue, Deque & Stack

Four names, two of them contracts and two of them classes. Untangle them once and you'll never hesitate over offer vs push in a live interview again.

Mission link: graphs are ~25% of your target interviews, and every BFS/DFS needs the right container. This is Java Essentials 2 of 3. Mission

1 · The one idea

Two of these four names are interfaces (contracts that say what operations exist) and two are classes (implementations that say how). You declare a variable with the interface and construct it with a class. For 99% of interview code the answer is the same single class — ArrayDeque — wearing two different hats: a queue hat and a stack hat.

NameKindWhat it gives youWhen
Queue<E>interfaceFIFO contract: offer / poll / peekBFS frontier, level-order, any "process in arrival order"
Deque<E>interfaceDouble-ended: addFirst/addLast, pollFirst/pollLast, plus push/popStack, sliding-window deque, 0-1 BFS
ArrayDeque<E>classThe DEFAULT implementation of both Queue and DequeUse this for stack and queue. Fast, array-backed.
LinkedList<E>classAlso a Deque, but a node per element (pointer overhead)Only when you also need List indexing / it's already a list
java.util.Stacklegacy classLIFO via push/pop/peekAvoid — synchronized, slow, extends the obsolete Vector
The rule that ends the confusion Need a stack? Deque<T> st = new ArrayDeque<>(); then push / pop / peek.
Need a queue? Queue<T> q = new ArrayDeque<>(); then offer / poll / peek.
One class — ArrayDeque — answers both. You almost never type LinkedList or Stack again.

2 · Decoding Queue<int[]> q = new ArrayDeque<>();

This single line appears in nearly every grid-BFS solution. Read it piece by piece:

Left to right, one token at a time
  • Queue — the interface (the declared type). You promise only to use FIFO operations on q.
  • <int[]> — the generic element type: each item in the queue is one int array, e.g. {row, col}.
  • q — the variable name.
  • new ArrayDeque<>() — the concrete implementation you actually build. ArrayDeque implements Queue, so this is legal.
  • <> — the diamond: "same element type as the left side", so you don't repeat <int[]>.
There is NO class called ArrayQueue. The array-backed implementation of a queue is literally named ArrayDeque — a deque can do everything a queue can, so Java ships one class for both.

Why pack coordinates into an int[]? A queue slot holds one object. A grid cell is two numbers (row and column) that must travel together, so you bundle them into a single object — an int[]{r, c}. You then unpack with cell[0] and cell[1]. (A small class or int[]{r, c, dist} works too when you need to carry distance along.) 

Queue<int[]> q = new ArrayDeque<>();
q.offer(new int[]{r, c});       // enqueue one cell as a 2-element array
int[] cell = q.poll();          // dequeue it
int row = cell[0], col = cell[1]; // unpack the bundle

3 · The method cheat table

The same physical class exposes three vocabularies. Pick one per use and stay consistent — mixing push with poll on the same structure is how you confuse yourself at the whiteboard.

RoleAddRemoveLookEnd that's used
Queue (FIFO)offer(x)poll()peek()add at tail, remove at head
Stack (LIFO)push(x)pop()peek()both at head (front)
Deque (both ends)offerFirst / offerLastpollFirst / pollLastpeekFirst / peekLastwhichever you name
null vs exception on an empty container Two families do the "same" thing but disagree when the structure is empty:
  • poll(), peek(), pollFirst(), peekFirst() → return null on empty.
  • remove(), element(), pop() → throw NoSuchElementException on empty.
In interview loops you guard with while (!q.isEmpty()), so either works — but know that an unguarded pop() blows up where an unguarded poll() quietly hands you null.

Stack with ArrayDeque (the right way to do a stack)

Deque<Integer> st = new ArrayDeque<>();
st.push(10);                // = addFirst(10)
st.push(20);
int top = st.peek();        // 20, doesn't remove
int out = st.pop();         // 20, removes (throws if empty)

Queue with ArrayDeque

Queue<Integer> q = new ArrayDeque<>();
q.offer(10);                // = addLast(10)
q.offer(20);
int head = q.peek();        // 10, doesn't remove
int out  = q.poll();        // 10, removes (null if empty)

4 · When you actually need a Deque (both ends)

A plain queue or stack uses one end. A few important patterns need both ends of the same structure — that's when you declare the variable as Deque and reach for the First/Last methods.

PatternWhy a dequeKey calls
0-1 BFS0-weight edges jump to the front (same distance), 1-weight to the backofferFirst / offerLast + pollFirst
Sliding Window Maximum (LC 239)Monotonic deque of indices: drop from the back, expire from the frontpollLast (drop smaller) / pollFirst (expire) / peekFirst
 
// Monotonic deque core (Sliding Window Maximum): store INDICES, decreasing by value
Deque<Integer> dq = new ArrayDeque<>();
for (int i = 0; i < nums.length; i++) {
    while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i])
        dq.pollLast();                 // back: drop indices that can never be the max
    dq.offerLast(i);
    if (dq.peekFirst() <= i - k)
        dq.pollFirst();                // front: expire the index that left the window
    // nums[dq.peekFirst()] is the window max once i >= k - 1
}
Forward reference — PriorityQueue is a Queue too, but NOT FIFO PriorityQueue<E> also implements Queue, so it has offer / poll / peek — but it is heap-ordered, not arrival-ordered: poll() returns the smallest (or your comparator's "best") element, not the oldest. Don't reach for it when you mean a plain FIFO frontier. It gets its own lesson next.

Worked example — dry run

One ArrayDeque used as a stack (LIFO): push(1), push(2), push(3), then pop() and peek(). Boxes grow toward the right; the right end is the top (where push/pop act). Final state after the pop:

push(1) → deque [1] push(2) → deque [1,2] push(3) → deque [1,2,3] pop() → returns 3, deque [1,2] peek() → returns 2, deque unchanged [1,2] contrast — as a QUEUE: offer(1), offer(2), poll() returns 1 (FIFO) — same ArrayDeque, but it removes from the opposite end

5 · Edge-case checklist

  • Empty container: poll/peek give null; pop/remove/element throw. Guard with isEmpty() either way.
  • Don't use Stack / Vector: legacy, synchronized (lock overhead), and Stack's iteration order is bottom-to-top — surprising. Use Deque<T> = new ArrayDeque<>().
  • ArrayDeque rejects null: offer(null) / push(null) throw NullPointerException (it uses null internally to mean "empty"). LinkedList allows null elements — a rare reason to prefer it, but usually a code smell.
  • Pick one vocabulary: treat a given structure as either a stack (push/pop) or a queue (offer/poll) — never both at once.
  • Stack direction: on ArrayDeque, push adds to the FRONT and pop removes from the FRONT (LIFO). If you accidentally offer (tail) and pop (front), you've built a queue by mistake.
  • Element type is one object per slot: bundle coordinates as int[]{r, c} (or a small record/class); you can't enqueue two loose ints.
