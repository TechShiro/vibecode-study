PriorityQueue & Comparators

A PriorityQueue is a binary heap, and a Comparator is the one dial that flips it from min to max. Get that dial right and Top-K, Dijkstra, and "two heaps" all fall out.

Mission link: the heap and ordered-map idioms the graph and DP tracks lean on — so you never stall on "which way does the comparator go?" live. This is Java Essentials 3 of 3. Mission

1 · The one idea

PriorityQueue<E> in Java is a binary heap: offer and poll are O(log n), peek is O(1). By default it is a MIN-heap ordered by natural ordering, so poll() always returns the smallest element. To order it any other way — max-heap, by a field, by a tuple — you hand the constructor a Comparator. That single argument is the whole game.

Recognition trigger "k largest / smallest / most frequent / closest", "merge k sorted", "median of a stream", "minimum cost to reach", or any time you repeatedly need the current extreme of a changing set. That's a heap. And the instant you need ordered lookups — "largest key ≤ x", "next event after t", interval booking — reach for TreeMap/TreeSet, not HashMap.
The #1 bug — comparator direction (and overflow) (a, b) -> a - b means "ascending" = MIN-heap (smallest polls first). (a, b) -> b - a means "descending" = MAX-heap. Memorize: first − second = ascending = min on top. Worse, the subtraction can overflow — a - b with a = Integer.MAX_VALUE, b = -1 wraps negative and silently inverts the order. Use Integer.compare(a, b) / Long.compare, never raw subtraction, whenever values can be far apart.

2 · Min-heap, max-heap, and Comparator basics

The default constructor is a min-heap. Everything else is a comparator. Here are the four forms you'll actually type: 

PriorityQueue<Integer> min = new PriorityQueue<>();                 // MIN-heap (natural order) — poll() = smallest
PriorityQueue<Integer> max = new PriorityQueue<>((a, b) -> b - a);  // MAX-heap — but b-a can OVERFLOW
PriorityQueue<Integer> safe = new PriorityQueue<>(Comparator.reverseOrder()); // MAX-heap, overflow-proof
PriorityQueue<Integer> ok   = new PriorityQueue<>((a, b) -> Integer.compare(b, a)); // MAX-heap, explicit + safe

For objects, build the comparator declaratively — it reads like English and never overflows:

// order int[] entries by index 1 ascending, then by index 0 descending as a tiebreak
PriorityQueue<int[]> pq = new PriorityQueue<>(
    Comparator.<int[]>comparingInt(x -> x[1])      // primary key: x[1] ascending
              .thenComparing(x -> x[0], Comparator.reverseOrder())); // tiebreak: x[0] descending

PriorityQueue<int[]> maxByVal = new PriorityQueue<>(
    Comparator.comparingInt((int[] x) -> x[0]).reversed());  // .reversed() flips the whole thing
Read a heap by its top, not its order Ask one question: "what do I want sitting on top, ready to be polled/evicted?" If you want the smallest reachable, that's a min-heap; if the largest, a max-heap. The comparator just encodes "what is least." Time: offer/poll O(log n), peek O(1), build-from-collection O(n) via new PriorityQueue<>(collection) (heapify).

Worked example — dry run

Default PriorityQueue<Integer> (a min-heap). We offer(5), then offer(1), offer(3), offer(2). The heap re-orders on every insert so the smallest sits at the root; one valid resulting shape:

poll() → 1 (the root / current min comes off first) poll() → 2 (heap re-settles, next smallest rises to the root) poll() → 3 poll() → 5 — draining a min-heap yields ascending order

new PriorityQueue<>((a,b) -> b - a) would make it a MAX-heap instead (root 5, polling in descending order).

3 · Heap of int[] — the Dijkstra / Top-K workhorse

Most interview heaps don't hold bare integers — they hold small tuples packed in an int[]: {node, dist}, {value, freq}, {row, col}. The comparator orders on whichever slot is the priority. 

// min-heap on the second slot — e.g. {node, distance} for Dijkstra, pop the closest frontier node
PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> a[1] - b[1]);
pq.offer(new int[]{src, 0});
while (!pq.isEmpty()) {
    int[] cur = pq.poll();          // cur[0] = node, cur[1] = best dist so far
    int node = cur[0], d = cur[1];
    if (d > dist[node]) continue;   // stale entry — already settled with a shorter path
    for (int[] e : adj.get(node)) { // e = {neighbor, weight}
        int nd = d + e[1];
        if (nd < dist[e[0]]) {
            dist[e[0]] = nd;
            pq.offer(new int[]{e[0], nd});   // relax: push the improved distance
        }
    }
}

This is exactly the priority queue at the heart of Dijkstra — when weights matter, BFS isn't enough and this heap is the upgrade. See it in full in the graph track: Graph 07 — Weighted Shortest Paths (Dijkstra). Note a[1] - b[1] is fine here only because distances stay small; if they can approach Integer.MAX_VALUE (an "infinity" sentinel), switch to Integer.compare(a[1], b[1]).

4 · The size-k heap idiom (and why direction matters)

To find the k largest you do not use a max-heap of everything — you keep a min-heap of size k. The smallest of your k winners sits on top; when something bigger arrives, evict the top. After one pass the heap holds the k largest and its top is the kth largest. 

int findKthLargest(int[] nums, int k) {           // LC 215
    PriorityQueue<Integer> heap = new PriorityQueue<>();  // MIN-heap of size k
    for (int x : nums) {
        heap.offer(x);
        if (heap.size() > k) heap.poll();         // drop the smallest survivor
    }
    return heap.peek();                           // top of a size-k min-heap = kth largest
}

Time O(n log k), Space O(k) — beats the O(n log n) of a full sort when k ≪ n.

Direction is inverted on purpose k largest → min-heap (smallest winner on top to evict). k smallest → max-heap. It feels backwards because you hold the opposite extreme on top so the worst survivor is the one you throw away. Flip it and you'll evict your best elements and return garbage — this is the most common heap bug in interviews.

5 · TreeMap / TreeSet — when you need order, not just lookup

HashMap/HashSet give O(1) average lookup but no order. TreeMap/TreeSet are red-black trees: keys are kept sorted, every operation is O(log n), and you unlock navigation methods a hash structure can't offer.

 HashMap / HashSetTreeMap / TreeSet
BackingHash tableRed-black (balanced BST)
OrderNoneSorted by key/comparator
get / put / containsO(1) averageO(log n)
SuperpowerRaw speedfloor/ceiling/higher/lower, ranges, min/max key

The navigation methods are the reason to pay the log factor. Pin down the four directions:

TreeMap<Integer, String> map = new TreeMap<>();
map.floorKey(x);    // largest key <= x   (or null)
map.ceilingKey(x);  // smallest key >= x  (or null)
map.lowerKey(x);    // largest key <  x   (strictly less)
map.higherKey(x);   // smallest key >  x  (strictly greater)
map.firstKey();     // minimum key  (throws if empty)
map.lastKey();      // maximum key  (throws if empty)

These turn "find the booking that could collide with [start, end)" into two O(log n) probes. My Calendar I (LC 729) is the canonical use: store events keyed by start, then check the neighbors on either side. 

class MyCalendar {
    TreeMap<Integer, Integer> cal = new TreeMap<>();  // start -> end
    public boolean book(int start, int end) {
        Integer prev = cal.floorKey(start);    // event starting at/before this one
        Integer next = cal.ceilingKey(start);  // event starting at/after this one
        if (prev != null && cal.get(prev) > start) return false; // prev overruns into us
        if (next != null && end > next)            return false; // we overrun into next
        cal.put(start, end);
        return true;
    }
}
floor/ceiling = "≤ / ≥", lower/higher = "strictly < / >" The trap is the boundary: floor and ceiling include equality; lower and higher exclude it. For interval problems "can my start touch the previous end exactly?" decides whether you want floor vs lower. Decide that before you type, not after a failing test.

6 · Map idioms you should type without thinking

Three methods collapse the most common map boilerplate — adjacency builds, grouping, frequency counts:

Map<Integer, Integer> freq = new HashMap<>();

// getOrDefault — read with a fallback, no null check
int seen = freq.getOrDefault(key, 0);

// merge — frequency counting in one line: old+1, or 1 if absent
for (int x : nums) freq.merge(x, 1, Integer::sum);

// computeIfAbsent — build a list/set value, e.g. an adjacency list
Map<Integer, List<Integer>> adj = new HashMap<>();
for (int[] e : edges)
    adj.computeIfAbsent(e[0], k -> new ArrayList<>()).add(e[1]);

merge(key, 1, Integer::sum) is the idiomatic frequency counter; computeIfAbsent guarantees the container exists before you .add to it (no "get, null-check, create, put, add" dance). You'll feed both of these straight into the Top-K heap from §4 and the adjacency-list builds in the graph track.

7 · Edge-case checklist

  • Comparator backwards → the cardinal heap bug. Re-derive from "what do I want on top to evict?": k largest → min-heap, k smallest → max-heap.
  • Overflow in a subtraction comparator → (a,b) -> a - b wraps for far-apart values. Use Integer.compare/Long.compare or Comparator.comparingInt.
  • A PriorityQueue is NOT sorted → only poll order is sorted. Iterating it (for-each, toArray, toString) yields heap-internal order, not sorted order. To drain in order, poll repeatedly.
  • peek vs poll → peek reads the top without removing; poll removes and returns it. Both return null on an empty queue (no exception) — guard with isEmpty().
  • floor vs ceiling direction → floor = largest ≤ x, ceiling = smallest ≥ x; lower/higher are the strict versions. Mixing them up flips which neighbor you inspect.
  • firstKey/lastKey on an empty TreeMap → these throw NoSuchElementException; the navigation methods (floorKey etc.) return null instead. Know which is which.
