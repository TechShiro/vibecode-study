String Internals & StringBuilder

Why strings are immutable, how the JVM String Pool saves memory, and avoiding O(N²) concatenation traps.

Track goal: Master foundational data structures from 0 level. This is Lesson 4 of 5 in Arrays & Strings. Index

1 · The One Idea

In Java, String objects are immutable — once created, their character contents can never be altered. If you write: 

String s = "";
for (int i = 0; i < n; i++) {
    s += i; // CATASTROPHIC O(N^2) COMPLEXITY!
}

On every iteration, Java creates a completely new string object and copies all previous characters over ($1 + 2 + 3 + \dots + N = \mathbf{O(N^2)}$ total character copies). For $N = 100,000$, this takes minutes and exhausts heap memory! StringBuilder uses a mutable dynamic character buffer, performing additions in amortized O(1) time ($O(N)$ total).

2 · The String Constant Pool & == vs equals()

Because strings are immutable, Java caches identical string literals inside the String Constant Pool in heap memory.

  • String s1 = "hello"; String s2 = "hello"; → s1 == s2 is true because both point to the exact same pooled memory address!
  • String s3 = new String("hello"); → s1 == s3 is false because new forcibly creates a fresh object outside the pool!
  • Golden Rule: Always compare string content using s1.equals(s2), never ==!
