Heaps & PriorityQueue

A heap answers one question — "what's the current extreme?" — in O(1), forever, no matter how the data churns. Master the size-k version and every "k largest / k closest / k most frequent" problem becomes the same 6 lines.

Mission link: Top-K is one of the highest-frequency OA patterns at big tech — Amazon and Google love "k closest / k most frequent." This is Lesson 1 of the 3-lesson Top-K / Heap track. Mission

1 · The one idea

A heap is a complete binary tree (every level full, last level packed left) with one rule: each parent is ≤ its children (min-heap) or ≥ (max-heap). Nothing else is sorted — siblings can be in any order — but that one rule guarantees the root is always the minimum (or maximum). Because the tree is complete, it needs no node objects at all: it lives flat in an array, where the children of index i sit at 2i+1 and 2i+2, and its parent at (i-1)/2. Java's PriorityQueue is exactly this array.

Recognition trigger "k largest / k smallest / k most frequent / k closest", "kth largest", "merge k sorted", "median of a stream", or any loop where you repeatedly need the current best/worst of a changing set — pop the extreme, push new items, repeat. A full sort is overkill when you only ever consume the top. That's a heap.

2 · How a heap works (60-second internals)

Two moves maintain the parent-rule, both walking one root-to-leaf path (height log n):

  • Push = sift up. Append at the end of the array (next free leaf), then swap the new element with its parent while it violates the rule. O(log n).
  • Pop = sift down. Remove the root, move the last element into its place, then swap it down with its smaller child until the rule holds. O(log n).
  • Heapify — building a heap from n existing items — is O(n), not O(n log n): sift-down from the middle backwards; most nodes are near the leaves and barely move. Java: new PriorityQueue<>(collection).

Complexities to recite: peek O(1) · offer/poll O(log n) · heapify O(n) · search or remove an arbitrary element O(n) — a heap is not a search structure.

Java PriorityQueue in four lines

PriorityQueue<Integer> min = new PriorityQueue<>();                  // MIN-heap by default: poll() = smallest
PriorityQueue<Integer> max = new PriorityQueue<>(Comparator.reverseOrder()); // MAX-heap, overflow-safe
PriorityQueue<int[]> byDist = new PriorityQueue<>((a, b) -> Integer.compare(a[1], b[1])); // tuples: min by slot 1
PriorityQueue<Integer> built = new PriorityQueue<>(list);            // heapify existing items in O(n)

The classic bug — comparator direction (a, b) -> Integer.compare(a, b) = ascending = MIN-heap (smallest on top). Integer.compare(b, a) = MAX-heap. Memorize: first − second = min on top. Half of all wrong Top-K submissions are a flipped comparator: the code runs, compiles, and quietly returns the k smallest instead of k largest. Always ask out loud: "what do I want sitting on top, ready to be evicted?"

3 · Core template — the size-k min-heap keeps the k LARGEST

Here is the counterintuitive core of the whole track: to keep the k largest elements you use a MIN-heap capped at size k. Why? Think of the heap as a VIP room with k seats. When the room is full and someone new arrives, you must decide whom to throw out — and the person you throw out is the weakest occupant. A min-heap puts exactly that person at the door (peek() = smallest of the current k) for O(1) inspection and O(log k) eviction. After processing everything, the room holds the k largest, and the root is the kth largest overall. 

// Keep the k LARGEST elements of nums. Root of the heap = kth largest.
int kthLargest(int[] nums, int k) {
    PriorityQueue<Integer> heap = new PriorityQueue<>(); // MIN-heap — smallest of the "k best" on top
    for (int x : nums) {
        heap.offer(x);                // candidate enters
        if (heap.size() > k)
            heap.poll();              // room over capacity → evict the weakest (the min)
    }
    return heap.peek();               // smallest survivor = kth largest overall
}

Time O(n log k) — n offers/polls on a heap that never exceeds k+1. Space O(k). When k ≪ n this crushes the O(n log n) full sort, and it works on a stream where sorting can't.

Worked example — dry run

nums = [3, 1, 5, 2, 4], k = 2 (find the 2nd largest):

offer 3 → heap {3} (size 1 ≤ 2, no evict) offer 1 → heap {1, 3} (size 2, full) offer 5 → heap {1, 3, 5} → over capacity → poll 1 → {3, 5} offer 2 → heap {2, 3, 5} → poll 2 → {3, 5} (2 never belonged) offer 4 → heap {3, 4, 5} → poll 3 → {4, 5} survivors = the 2 largest {4, 5}; peek() = 4 = 2nd largest ✓
The symmetry — flip everything for k smallest k largest → min-heap of size k (evict the min). k smallest / closest → max-heap of size k (evict the max). The heap's polarity is always the opposite of what you're keeping, because its top is the eviction door. Say this sentence before writing any comparator in an interview.

Case: size-k MAX-heap — k smallest (the mirror image)

// Keep the k SMALLEST: max-heap, evict the largest occupant.
PriorityQueue<Integer> heap = new PriorityQueue<>(Comparator.reverseOrder());
for (int x : nums) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();   // evicts the MAX — biggest of the "k smallest" leaves
}
// heap now holds the k smallest; peek() = kth smallest. O(n log k) / O(k)

Case: Last Stone Weight — max-heap simulation (LC 1046)

No k here — this is the other heap shape: hold everything, repeatedly consume the extreme. It's the warm-up that proves you can drive a max-heap.

int lastStoneWeight(int[] stones) {
    PriorityQueue<Integer> pq = new PriorityQueue<>(Comparator.reverseOrder()); // MAX-heap
    for (int s : stones) pq.offer(s);
    while (pq.size() > 1) {
        int a = pq.poll(), b = pq.poll();   // two heaviest, a ≥ b
        if (a != b) pq.offer(a - b);        // smash: remainder goes back in
    }
    return pq.isEmpty() ? 0 : pq.peek();    // O(n log n) time, O(n) space
}

Case: heapify-then-pop-k (when is it better?)

// All n items up front, tiny k: O(n) heapify + O(k log n) pops.
PriorityQueue<Integer> pq = new PriorityQueue<>(Comparator.reverseOrder());
pq.addAll(listOfAll);                  // note: addAll = n offers, O(n log n); constructor(collection) = true O(n) heapify
int kth = 0;
for (int i = 0; i < k; i++) kth = pq.poll(); // kth largest after k pops

Rule of thumb: size-k heap when the data streams or memory is tight (O(k) space); heapify + pop when everything is in hand and k is minuscule. Both beat sorting for k ≪ n.

5 · Edge-case checklist

  • Comparator flipped — the #1 bug. Min-heap keeps k largest; max-heap keeps k smallest. Verify with a 3-element example before running.
  • k ≥ n — the heap never overflows; you keep everything. Make sure your code doesn't assume an eviction happened (e.g., LC 703's constructor may receive fewer than k initial numbers).
  • k = 1 — degenerates to a running max/min; the heap still works but mention the O(1)-variable alternative to the interviewer.
  • Duplicates — heaps handle them fine (unlike TreeSet); ties just coexist. Never "upgrade" to TreeSet without checking for duplicate keys.
  • Iterating a PriorityQueue is NOT sorted order. The array is heap-ordered, not sorted — for (int x : pq) gives arbitrary order. Only repeated poll() drains in order.
  • offer-then-poll vs peek-first: if (heap.size() < k || x > heap.peek()) {…} skips pointless pushes and is a nice micro-optimization; the plain offer-then-poll version is easier to get right live. Either is accepted.
  • a - b overflow in comparators when values span the int range — use Integer.compare (details in the Java lesson).
