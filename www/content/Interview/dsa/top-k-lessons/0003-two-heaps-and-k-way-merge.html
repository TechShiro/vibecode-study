Two Heaps & K-way Merge

Two heaps leaning against each other hold a streaming median at their seam; one min-heap of k "next candidates" zips k sorted sources into one. These are the boss-level heap shapes — and the last two you need.

Mission link: LC 295 and LC 23 are both marked Hard and both appear constantly in big-tech onsites — yet each is ~15 lines once you know the shape. This is Lesson 3 of the 3-lesson Top-K / Heap track. Mission

1 · The one idea

Two heaps: split a stream into a lower half and an upper half. A MAX-heap holds the lower half (its top = biggest small number) and a MIN-heap holds the upper half (its top = smallest big number). The median lives at the seam between the two tops — O(1) to read — provided you rebalance so the sizes never differ by more than 1. K-way merge: to merge k sorted sources, keep a min-heap of just the k current heads. Pop the global smallest, push its successor from the same source. Every element passes through a heap of size k → O(N log k) total.

Recognition trigger Two heaps: "median of a stream", "balance two halves", or greedy problems where you repeatedly want the max of one pool and the min of another (IPO). K-way merge: "merge k sorted lists/arrays", "kth smallest across sorted rows", "k pairs with smallest sums" — any time k sorted sources must be consumed in global order.

2 · Core template A — Find Median from Data Stream (LC 295)

Invariant: lo (max-heap) holds the smaller half, hi (min-heap) the larger half, lo.size() is either equal to or exactly one more than hi.size(), and every element of lo ≤ every element of hi. The safe insertion dance: always push into lo, hand its max across to hi (this guarantees the ordering invariant), then pull back if hi grew too big. 

class MedianFinder {
    private final PriorityQueue<Integer> lo =            // MAX-heap: lower half, top = its largest
        new PriorityQueue<>(Comparator.reverseOrder());
    private final PriorityQueue<Integer> hi =            // MIN-heap: upper half, top = its smallest
        new PriorityQueue<>();

    public void addNum(int num) {
        lo.offer(num);                // 1. drop into the lower half…
        hi.offer(lo.poll());          // 2. …but pass lo's max across — now every lo ≤ every hi
        if (hi.size() > lo.size())
            lo.offer(hi.poll());      // 3. rebalance: lo may equal or exceed hi by exactly 1
    }
    public double findMedian() {
        return lo.size() > hi.size()
            ? lo.peek()                          // odd count → lo's top IS the median
            : (lo.peek() + hi.peek()) / 2.0;     // even → average of the two seam values
    }
}

Time O(log n) per addNum, O(1) per findMedian · Space O(n). A sorted list gives O(n) inserts; re-sorting gives O(n log n) per query — the two heaps beat both.

Worked example — dry run

Stream: 5, 2, 8, 1

add 5 → lo{5}→hi gets 5→hi bigger→pull back → lo{5} hi{} · median 5 add 2 → lo{2,5}→pass max 5 to hi → lo{2} hi{5} · median (2+5)/2 = 3.5 add 8 → lo{2,8}→pass 8→hi{5,8} bigger→pull 5 back → lo{5,2} hi{8} · median 5 add 1 → lo{1,2,5}→pass 5→ lo{2,1} hi{5,8} · median (2+5)/2 = 3.5 invariant held every step: max(lo) ≤ min(hi), sizes differ ≤ 1, median read off the seam in O(1)
The shortcut that breaks 295 "If num < lo.peek() push to lo, else push to hi" without the pass-across step lets an element land on the wrong side (and NPEs on the first insert). The offer–pass–rebalance dance above costs one extra O(log n) move and is unconditionally correct. Follow-up they love: sliding-window median (LC 480) — same two heaps plus lazy deletion.

3 · Core template B — K-way merge: Merge k Sorted Lists (LC 23)

Don't compare all k heads each step (O(Nk)) — keep the k heads in a min-heap. Seed one node per list; each pop emits the global minimum and pushes that node's successor, so the heap always holds exactly one candidate per unfinished list. 

ListNode mergeKLists(ListNode[] lists) {
    PriorityQueue<ListNode> heap =                        // min-heap of current heads, size ≤ k
        new PriorityQueue<>((a, b) -> Integer.compare(a.val, b.val));
    for (ListNode head : lists)
        if (head != null) heap.offer(head);               // seed: skip EMPTY lists (null heads)

    ListNode dummy = new ListNode(0), tail = dummy;
    while (!heap.isEmpty()) {
        ListNode node = heap.poll();                      // global smallest of all k fronts
        tail.next = node; tail = node;                    // stitch it onto the output
        if (node.next != null) heap.offer(node.next);     // its successor becomes that list's candidate
    }
    return dummy.next;
}

Time O(N log k), N = total nodes — each node enters and leaves a size-k heap once. Space O(k). (Alternative: pairwise divide-and-conquer merging, also O(N log k), no heap.)

Case: Find K Pairs with Smallest Sums (LC 373)

See the hidden k-way merge: fixing index i in nums1 gives a sorted "virtual list" of sums nums1[i]+nums2[0], nums1[i]+nums2[1], …. Merge those lists but stop after k pops. Seed only the first (up to) k rows, and on popping (i, j) push only (i, j+1) — never (i+1, j), which is already covered by row i+1's seed. That discipline visits each cell once, no visited-set needed. 

List<List<Integer>> kSmallestPairs(int[] nums1, int[] nums2, int k) {
    PriorityQueue<int[]> heap = new PriorityQueue<>(     // {i, j}, min-heap by pair sum
        (a, b) -> Integer.compare(nums1[a[0]] + nums2[a[1]],
                                  nums1[b[0]] + nums2[b[1]]));
    for (int i = 0; i < Math.min(k, nums1.length); i++)
        heap.offer(new int[]{i, 0});                      // seed row heads: (i, 0) — at most k rows matter

    List<List<Integer>> res = new ArrayList<>();
    while (k-- > 0 && !heap.isEmpty()) {
        int[] cur = heap.poll();                          // smallest remaining sum overall
        int i = cur[0], j = cur[1];
        res.add(List.of(nums1[i], nums2[j]));
        if (j + 1 < nums2.length)
            heap.offer(new int[]{i, j + 1});              // ONLY the same-row successor → no duplicates
    }
    return res;   // O(k log k) time, O(k) space — never materialize all n·m pairs
}
Same skeleton, more problems Kth Smallest in a Sorted Matrix (LC 378) and Smallest Range Covering k Lists (LC 632) are this exact template — rows are the sorted sources, the heap holds one index-tuple per row. Recognize it and you get three Hards for one.

Case: IPO — two heaps as a greedy pump (LC 502)

Different two-heap shape: not halves of one set, but a pipeline. Projects you can't afford wait in a min-heap keyed by capital requirement; every round, unlock all now-affordable projects into a max-heap keyed by profit, then greedily take the single most profitable. Repeat k times. 

int findMaximizedCapital(int k, int w, int[] profits, int[] capital) {
    int n = profits.length;
    PriorityQueue<int[]> locked = new PriorityQueue<>(   // min-heap by required capital
        (a, b) -> Integer.compare(a[0], b[0]));
    for (int i = 0; i < n; i++) locked.offer(new int[]{capital[i], profits[i]});

    PriorityQueue<Integer> unlocked =                    // max-heap of affordable profits
        new PriorityQueue<>(Comparator.reverseOrder());

    for (int round = 0; round < k; round++) {
        while (!locked.isEmpty() && locked.peek()[0] <= w)
            unlocked.offer(locked.poll()[1]);            // everything affordable moves across (once, ever)
        if (unlocked.isEmpty()) break;                    // can't afford anything → stop early
        w += unlocked.poll();                             // greedy: bank the best available profit
    }
    return w;   // O(n log n + k log n): each project crosses the seam at most once
}

5 · Edge-case checklist

  • 295 — never peek an empty heap. The offer–pass–rebalance dance makes the first insert safe automatically; conditional-insert versions NPE on it. Median of an odd count comes from lo only if you rebalanced toward lo — be consistent.
  • 295 — integer overflow on the even median: (lo.peek() + hi.peek()) / 2.0 can overflow int before dividing when values near ±2³¹; use ((long) lo.peek() + hi.peek()) / 2.0 if constraints allow it.
  • 23 — null heads. lists may contain empty lists, or be empty entirely — skip nulls at seed time and the loop handles the rest (returns null naturally).
  • 23 — comparator on node values, not nodes: ListNode isn't Comparable; forgetting the comparator throws ClassCastException at the second offer.
  • 373 — duplicate states. Pushing both (i+1, j) and (i, j+1) per pop double-visits cells; either use a visited set or (cleaner) seed column 0 and push only (i, j+1). Also cap seeds at min(k, nums1.length) and stop when the heap empties before k pairs exist.
  • 502 — move projects across once, ever. Re-scanning the full project list each round is O(kn); the locked min-heap makes each project cross exactly once. Also: a taken project is consumed — poll it, don't peek.
  • Everywhere: heap size in Big-O is the heap's cap (k, or n/2), not n by reflex. Saying "O(N log k), the heap never exceeds k" earns explicit credit.
