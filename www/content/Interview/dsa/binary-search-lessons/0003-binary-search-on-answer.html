Binary Search on the Answer

When you can't compute the answer but you CAN check a guess — "could Koko finish at speed 6?" — binary search the guesses. This is the single most common pattern in big-tech online assessments.

Mission link: "minimize the max / maximize the min" problems dominate Amazon, Google, and TikTok OAs — most candidates try greedy or DP and time out; you'll recognize the predicate in 30 seconds. Final lesson of the 3-lesson binary search track. Mission

1 · The one idea

Stop searching the input. Search the space of possible answers. If Koko can finish the bananas eating at speed 6, she can certainly finish at 7, 8, 9… — feasibility is monotonic in the guess: F F F T T T over speeds. So write a checker feasible(guess) (usually a greedy O(n) simulation), and run Lesson 1's firstTrue over the numeric range of guesses. Cost: O(n log(range)). You never construct the answer — you corner it.

Recognition trigger The four magic phrasings: "minimize the maximum …", "maximize the minimum …", "smallest X such that ‹task› is possible", "largest X such that ‹constraint› still holds". Confirm with two tests: (1) checking one candidate answer is easy (linear greedy), and (2) feasibility can only improve as the candidate grows (or only worsen — same thing, flipped). Constraints scream it too: answer range up to 10⁹ but n only 10⁵ → they want O(n log 10⁹), not DP over values.

2 · Core template — minimize a feasible answer

Three decisions, then it's Lesson 1 verbatim: (a) the search range [lo, hi] — smallest and largest answers that could ever make sense; (b) the checker; (c) which boundary you want (minimizing a "true means doable" predicate → first true). 

// Minimize x in [lo, hi] such that feasible(x) — feasible must be monotonic F…FT…T.
int minFeasible(int lo, int hi) {         // pick lo/hi so the answer is GUARANTEED inside
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;     // ranges hit 10⁹ here — the overflow guard earns its keep
        if (feasible(mid)) hi = mid;      // mid works → try smaller, but keep mid
        else lo = mid + 1;                // mid fails → everything ≤ mid fails too
    }
    return lo;
}

boolean feasible(int x) {                 // the ONLY problem-specific part: an O(n) greedy check
    // "if the answer were x, could we do the task?" — simulate and compare to the budget
    return true;
}

Time O(n · log(hi − lo)) — one O(n) check per halving. Space O(1). To maximize instead (feasibility looks like T…TF…F): find the first false, return lo − 1 — the Sqrt(x) move from Lesson 1. No second template.

Choosing lo and hi is half the problem lo = smallest answer that isn't automatically absurd; hi = an answer that certainly works. Koko: lo = 1 banana/hr, hi = max pile (faster never helps — one pile per hour is the floor). Shipping: lo = heaviest single package (a smaller capacity can't ship it at all), hi = sum of all weights (ship everything in one day). Tight bounds aren't about speed — log is forgiving — they're about the checker never seeing a nonsense input like capacity 0.

Case: Koko Eating Bananas (LC 875)

Minimum eating speed k so all piles are gone within h hours. A pile of p bananas takes ⌈p / k⌉ hours (one pile per hour max). More speed → fewer hours → feasibility is monotonic. Textbook instance.

int minEatingSpeed(int[] piles, int h) {
    int lo = 1, hi = 0;
    for (int p : piles) hi = Math.max(hi, p); // speed beyond max pile buys nothing
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (hours(piles, mid) <= h) hi = mid; // fast enough → try slower
        else lo = mid + 1;
    }
    return lo;
}
long hours(int[] piles, int k) {
    long total = 0;
    for (int p : piles) total += (p + k - 1) / k; // ceil division without doubles
    return total;                         // long: 10⁴ piles × 10⁹ each at k=1 overflows int
}

Time O(n log max(piles)). Memorize (p + k - 1) / k for ceiling division — Math.ceil on doubles is a precision bug waiting for a 10⁹ input.

Case: Capacity to Ship Packages in D Days (LC 1011)

Minimum ship capacity to deliver in order within D days. Checker: greedily pack packages into the current day until the next one would overflow, then start a new day. Bigger capacity → fewer days → monotonic.

int shipWithinDays(int[] weights, int days) {
    int lo = 0, hi = 0;
    for (int w : weights) { lo = Math.max(lo, w); hi += w; } // [heaviest item, total weight]
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (daysNeeded(weights, mid) <= days) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
int daysNeeded(int[] weights, int cap) {
    int days = 1, load = 0;               // day 1 exists even before the first package
    for (int w : weights) {
        if (load + w > cap) { days++; load = 0; } // close the day, open a new one
        load += w;                        // w always fits alone: cap ≥ max weight by our lo
    }
    return days;
}

Case: Split Array Largest Sum (LC 410)

Split an array into k contiguous parts minimizing the largest part-sum. Sounds like interval DP (and an O(n²k) DP exists — that's the trap). Reframe: "is there a split whose largest part ≤ cap?" Greedily cut whenever adding the next number would exceed cap; count parts. That is exactly LC 1011's checker with "days" renamed "parts". Minimize-the-maximum ≡ first feasible cap.

int splitArray(int[] nums, int k) {
    int lo = 0; long hi = 0;
    for (int x : nums) { lo = Math.max(lo, x); hi += x; }
    while (lo < hi) {
        long mid = lo + (hi - lo) / 2;
        if (parts(nums, mid) <= k) hi = mid;  // few enough parts → cap is feasible → try smaller
        else lo = (int) mid + 1;
    }
    return lo;
}
int parts(int[] nums, long cap) {
    int count = 1; long sum = 0;
    for (int x : nums) {
        if (sum + x > cap) { count++; sum = 0; } // greedy cut = fewest possible parts for this cap
        sum += x;
    }
    return count;
}
Why the greedy checker is trustworthy For a fixed cap, stretching every part as far as it can go clearly minimizes the number of parts. If even the greedy (minimum) count exceeds k, no split under this cap uses ≤ k parts. And fewer parts than k is fine — split any part further; the max only shrinks. That two-sentence argument is the proof interviewers want to hear.

Case: Minimum Days to Make m Bouquets (LC 1482)

Flower i blooms on day bloomDay[i]; a bouquet needs k adjacent bloomed flowers; make m bouquets in minimum days. The guess is a day: waiting longer only blooms more flowers, so feasibility is monotonic in the day. Checker: scan once, counting runs of adjacent bloomed flowers.

int minDays(int[] bloomDay, int m, int k) {
    if ((long) m * k > bloomDay.length) return -1; // not enough flowers EVER → bail before searching
    int lo = 1, hi = 0;
    for (int d : bloomDay) hi = Math.max(hi, d);   // by day max(bloomDay), everything is bloomed
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canMake(bloomDay, m, k, mid)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
boolean canMake(int[] bloomDay, int m, int k, int day) {
    int bouquets = 0, run = 0;
    for (int d : bloomDay) {
        if (d <= day) {                   // bloomed by 'day' → extends the adjacent run
            if (++run == k) { bouquets++; run = 0; } // harvest and restart the run
        } else run = 0;                   // unbloomed flower breaks adjacency
    }
    return bouquets >= m;
}

The lesson inside the lesson: the answer axis doesn't have to be a speed or a size — time itself binary-searches whenever "wait longer" only helps.

4 · Edge-case checklist

  • Impossible inputs first. LC 1482's m·k > n → return −1 before the loop. A binary search can only pick from candidates you gave it; it cannot invent "no answer."
  • lo must be the smallest sane answer. Capacity below max(weights) or speed 0 makes the checker lie or divide by zero. Guard the range, not the checker.
  • Overflow, twice. The midpoint (range up to 10⁹) and the checker's accumulators (long total in Koko, long sum in 410, (long) m * k in 1482).
  • Ceil division: (p + k - 1) / k. Never Math.ceil((double) p / k) — doubles lose integer precision past 2⁵³ and earlier than you think in intermediate math.
  • Minimize vs maximize. Minimize + "true = doable" → first true. Maximize + "true = still OK" (T…TF…F) → first false, minus one. Write the F/T picture in a comment before coding.
  • The checker must be exactly monotonic. If a larger guess could ever flip feasible → infeasible, the pattern is invalid. State the one-line monotonicity argument out loud in interviews — it's part of the expected answer.
  • Checker is greedy — justify it. "Greedy gives the minimum count for this cap, so if greedy fails, everything fails" (LC 410/1011). One sentence, big signal.
