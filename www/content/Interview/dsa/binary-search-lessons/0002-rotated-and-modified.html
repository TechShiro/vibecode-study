Rotated & Modified Binary Search

Rotated arrays, peaks, and 2D matrices aren't sorted — but at every midpoint you can still answer "which side is the target on?" in O(1). That question is all binary search ever needed.

Mission link: Search in Rotated Sorted Array (LC 33) is a top-20 all-time interview question at Meta/Amazon/Google — this lesson is that question plus its whole family. Lesson 2 of the 3-lesson binary search track. Mission

1 · The one idea

Lesson 1 needed a monotonic predicate. These arrays aren't monotonic — a rotated array goes up, cliffs down, goes up again. But binary search never needed sorted; it needed: at each mid, decide in O(1) which half can't contain the answer, and throw it away. In a rotated array, one half of any split is always perfectly sorted — check its endpoints to decide if the target is inside it. For finding the rotation point or a peak, comparing nums[mid] against a fixed anchor (nums[hi], or its neighbor nums[mid+1]) recovers a genuine F…FT…T predicate, and Lesson 1's template applies verbatim.

Recognition trigger "Rotated sorted array," "find the pivot/minimum," "find a peak," "search a sorted 2D matrix," or any array that is piecewise sorted with O(log n) demanded. The interview move: don't hunt for a global order — ask "standing at mid, what O(1) comparison tells me which half to discard?" If duplicates are allowed (LC 81/154), expect the follow-up "what happens to your complexity?" (answer: worst-case O(n)).

2 · Core template — find the rotation point (LC 153)

Find Minimum in Rotated Sorted Array is the family's core because it IS Lesson 1's template with predicate p(i) = nums[i] <= nums[hi] ("i is in the right-hand sorted run"). Elements in the left run are all > the last element; elements in the right run are all ≤ it — F…FT…T, and the first T is the minimum. 

// LC 153: min of a rotated sorted array with DISTINCT values.
int findMin(int[] nums) {
    int lo = 0, hi = nums.length - 1;    // nums[hi] is the anchor; answer guaranteed in [lo, hi]
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] <= nums[hi]) hi = mid; // mid is in the right sorted run → min is mid or left of it
        else lo = mid + 1;               // mid in left run (> nums[hi]) → min is strictly right
    }
    return nums[lo];                     // lo = first index of the right run = the minimum
}

Time O(log n). Space O(1). Note the anchor is nums[hi], not nums[lo] — comparing to nums[lo] breaks when the array isn't rotated at all (fully sorted input), because then everything is ≥ nums[lo] and the predicate isn't F…FT…T.

Worked example — dry run

findMin([4,5,6,7,0,1,2]). Anchor nums[6] = 2. Predicate nums[i] ≤ 2: F F F F T T T.

lo=0, hi=6 — anchor nums[6]=2 mid=3 → nums[3]=7 ≤ 2? F → min is right of the cliff → lo=4 lo=4, hi=6 → mid=5 → nums[5]=1 ≤ 2? T → hi=5 (mid could be the min) lo=4, hi=5 → mid=4 → nums[4]=0 ≤ 2? T → hi=4 lo=4 == hi=4 → nums[4] = 0 ✓

Case: Search in Rotated Sorted Array (LC 33)

Target search has no single monotonic predicate over the whole array, so this one keeps the classic lo <= hi loop and decides per step: whichever half of [lo, hi] is sorted (at least one always is), check if the target lies between its endpoints. If yes, search it; otherwise the target — if it exists — must be in the messy half. 

int search(int[] nums, int target) {
    int lo = 0, hi = nums.length - 1;
    while (lo <= hi) {                   // classic loop: we may find target AT mid and return early
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] == target) return mid;
        if (nums[lo] <= nums[mid]) {     // left half [lo..mid] is sorted (note <= : 1-element half)
            if (nums[lo] <= target && target < nums[mid])
                hi = mid - 1;            // target inside the sorted left half
            else lo = mid + 1;           // else it can only be in the right half
        } else {                         // otherwise the right half [mid..hi] is sorted
            if (nums[mid] < target && target <= nums[hi])
                lo = mid + 1;            // target inside the sorted right half
            else hi = mid - 1;
        }
    }
    return -1;
}
The <= in nums[lo] <= nums[mid] is load-bearing When lo == mid (a two-element range), the "half" [lo..mid] is a single element — sorted by definition. Writing strict < misclassifies it as the unsorted side and sends the search the wrong way. This is the #1 wrong-answer on LC 33.

Case: … with duplicates (LC 81)

Duplicates can make nums[lo] == nums[mid] == nums[hi] (e.g. [1,1,1,0,1]) — then neither half is provably sorted. The only safe move: shed one known-useless element from each end and retry. That single degenerate branch drops the worst case to O(n); everything else is LC 33.

boolean search(int[] nums, int target) {
    int lo = 0, hi = nums.length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] == target) return true;
        if (nums[lo] == nums[mid] && nums[mid] == nums[hi]) {
            lo++; hi--;                  // can't tell which side is sorted → shrink both ends
        } else if (nums[lo] <= nums[mid]) {
            if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
            else lo = mid + 1;
        } else {
            if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
            else hi = mid - 1;
        }
    }
    return false;
}

Same idea fixes LC 154 (min with duplicates): in the core template, when nums[mid] == nums[hi] you can't place mid in either run, but nums[hi] has a duplicate surviving at mid, so hi-- is safe. Average O(log n), worst O(n) — say that unprompted in the interview.

Case: Find Peak Element (LC 162)

Not sorted at all — yet nums[mid] > nums[mid+1] is a valid firstTrue predicate. If the slope at mid is downhill, a peak exists at mid or to the left; if uphill, the climb must top out somewhere to the right (the array's edges are −∞, so an ascent can't run off the end). The first "downhill" index is a peak.

int findPeakElement(int[] nums) {
    int lo = 0, hi = nums.length - 1;    // hi = n-1: mid+1 must stay in bounds; a peak always exists
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] > nums[mid + 1]) hi = mid; // downhill → a peak is at mid or before
        else lo = mid + 1;               // uphill → strictly bigger value ahead → peak is right
    }
    return lo;                           // first downhill index = a peak
}

This generalizes: whenever you can point in a direction that must contain an answer, you can binary search — sortedness is optional.

Case: Search a 2D Matrix (LC 74)

Each row sorted, and each row's first element > previous row's last: reading row-by-row gives one sorted list of length m·n. Don't flatten it — index into it. Cell k lives at matrix[k / cols][k % cols]. Then it's literally LC 704.

boolean searchMatrix(int[][] matrix, int target) {
    int rows = matrix.length, cols = matrix[0].length;
    int lo = 0, hi = rows * cols;        // virtual sorted array of length rows·cols
    while (lo < hi) {                    // firstTrue: nums[k] >= target
        int mid = lo + (hi - lo) / 2;
        if (matrix[mid / cols][mid % cols] >= target) hi = mid;
        else lo = mid + 1;
    }
    return lo < rows * cols && matrix[lo / cols][lo % cols] == target;
}

Time O(log (m·n)). Don't confuse with LC 240 (rows and columns sorted independently, no row-to-row guarantee) — that one is the staircase walk from the top-right corner, not binary search.

Boss problem: Median of Two Sorted Arrays (LC 4) — the partition sketch

Stretch goal; know the idea even if you never code it live. You don't search for a value — you search for how many elements the smaller array contributes to the left half of the merged order. Take i elements from A and j = (m+n+1)/2 − i from B, so left and right halves have equal size by construction. The partition is correct when the left half's maxima don't exceed the right half's minima: A[i−1] ≤ B[j] and B[j−1] ≤ A[i]. And here's the monotonic predicate: as i grows, A[i−1] rises while B[j] falls, so "A[i−1] > B[j] (i too big)" flips exactly once. Binary search i over [0, m] on the smaller array: O(log min(m, n)). 

// The decision inside the loop — the rest is Lesson 1 plumbing + edge sentinels:
int i = lo + (hi - lo) / 2, j = (m + n + 1) / 2 - i;
// use -∞ for A[-1]/B[-1] and +∞ for A[m]/B[n]
if (A[i - 1] > B[j])      hi = i - 1;  // A gave too many → shrink i
else if (B[j - 1] > A[i]) lo = i + 1;  // A gave too few → grow i
else { /* found: median = max(left maxes), or avg with min(right mins) if m+n even */ }

4 · Edge-case checklist

  • Not-rotated input (rotation by 0 or by n): [1,2,3,4,5] must still work. This is exactly why LC 153 anchors on nums[hi], and why LC 33 must handle "whole range already sorted."
  • Two-element ranges. mid == lo there; any < vs <= slip (sorted-half test, membership test) shows up only on these. Hand-trace [3,1] before submitting.
  • Duplicates change the contract. LC 81/154 are average O(log n), worst O(n) — the equal-ends shrink is unavoidable (adversarial input: all 1s with one 0 hidden anywhere).
  • LC 162 needs hi = n − 1, not n — the predicate reads nums[mid + 1]. Off-the-end reads are the classic peak-finding crash.
  • Membership tests are half-open: in LC 33, nums[lo] <= target < nums[mid] — mid itself was already checked, so keep it out of both halves or you'll bounce between them.
  • LC 74 vs LC 240: confirm the "row starts after previous row ends" guarantee before flattening. Without it the virtual array isn't sorted and the answer is a different algorithm.
  • Single-element array: loops with lo < hi return it untouched; loops with lo <= hi must check it. Both templates handle n = 1 — but only if hi was initialized consistently with the loop style.
