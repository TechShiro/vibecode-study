Overlapping Intervals — Merge & Insert

Sort by start, sweep once, and every "do these ranges collide?" question collapses into a single comparison: cur.start <= prev.end.

Mission link: intervals show up constantly in big-tech OAs — calendars, bookings, CPU jobs are all interval problems in costume. This is Lesson 1 of the 2-lesson intervals track. Mission

1 · The one idea

An interval [start, end] is a range on a number line. Unsorted, any pair might overlap and you're stuck with O(n²) pairwise checks. But sort by start and overlaps can only happen between neighbors in the sweep: as you walk left to right, the current interval either overlaps the last merged one (cur.start <= prev.end — it begins before the previous one has finished) or it starts a fresh block. One sort, one linear sweep, one comparison. That's the whole pattern.

Recognition trigger The input is pairs [start, end] — meetings, bookings, ranges, tasks with start/finish times — and the question says "merge", "overlap", "conflict", "insert", "intersection", or "can you attend all". If ranges are involved, your first reflex is: sort by start, then sweep. (Lesson 2 covers the cases where you sort by end instead.)

2 · Core template — Merge Intervals (LC 56)

Sort by start. Keep a list of merged blocks. For each interval: if it starts at or before the end of the last block, they overlap — extend that block's end (with max, because a later interval can be nested inside an earlier one). Otherwise open a new block. 

int[][] merge(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0])); // sort by START
    List<int[]> out = new ArrayList<>();
    for (int[] cur : intervals) {
        if (!out.isEmpty() && cur[0] <= out.get(out.size() - 1)[1]) {
            // overlap: cur begins before (or exactly when) the last block ends
            int[] prev = out.get(out.size() - 1);
            prev[1] = Math.max(prev[1], cur[1]);   // max, NOT cur[1] — cur may be nested
        } else {
            out.add(cur);                          // gap → start a new block
        }
    }
    return out.toArray(new int[0][]);
}

Time O(n log n) — the sort dominates; the sweep is O(n). Space O(n) for the output (O(log n) for the sort itself).

Worked example — dry run

Input [[1,3],[8,10],[2,6],[15,18]]. After sorting by start: [1,3],[2,6],[8,10],[15,18].

out = [] → add [1,3]. out = [[1,3]] [2,6]: 2 <= 3 → overlap. prev.end = max(3,6) = 6. out = [[1,6]] [8,10]: 8 > 6 → gap. out = [[1,6], [8,10]] [15,18]: 15 > 10 → gap. out = [[1,6],[8,10],[15,18]] answer: [[1,6],[8,10],[15,18]]
The touching-endpoints trap: is [1,2] vs [2,3] an overlap? It depends on the problem — read the statement. In Merge Intervals (56), yes: [1,2],[2,3] merge into [1,3], so the test is cur.start <= prev.end. In Meeting Rooms (252), no: a meeting ending at 2 and one starting at 2 do not conflict, so the conflict test is the strict cur.start < prev.end. Flipping <= vs < is the #1 wrong-answer in this pattern — decide it consciously for every problem.

Case: Insert Interval (LC 57)

The list is already sorted and disjoint, so don't re-sort — sweep in three phases: (1) copy intervals that end before the new one starts; (2) absorb every interval that overlaps the new one into it; (3) copy the rest. Phase 2's condition is "starts before newInterval ends" — the mirrored overlap test. 

int[][] insert(int[][] intervals, int[] newInterval) {
    List<int[]> out = new ArrayList<>();
    int i = 0, n = intervals.length;
    while (i < n && intervals[i][1] < newInterval[0])   // phase 1: entirely before — ends before new starts
        out.add(intervals[i++]);
    while (i < n && intervals[i][0] <= newInterval[1]) { // phase 2: overlaps — starts before new ends
        newInterval[0] = Math.min(newInterval[0], intervals[i][0]);
        newInterval[1] = Math.max(newInterval[1], intervals[i][1]);
        i++;                                             // newInterval swallows it and grows
    }
    out.add(newInterval);                                // place the (possibly grown) new interval once
    while (i < n) out.add(intervals[i++]);               // phase 3: entirely after
    return out.toArray(new int[0][]);
}

Time O(n), Space O(n). If an interviewer asks "can you beat re-sorting?", this three-phase sweep is the answer they want.

Case: Interval List Intersections (LC 986) — two pointers

Two sorted disjoint lists; return every pairwise intersection. Any candidate intersection is [max(a.start, b.start), min(a.end, b.end)] — real only if start <= end. Then advance the pointer of whichever interval ends first: it can't intersect anything further. 

int[][] intervalIntersection(int[][] A, int[][] B) {
    List<int[]> out = new ArrayList<>();
    int i = 0, j = 0;
    while (i < A.length && j < B.length) {
        int lo = Math.max(A[i][0], B[j][0]);   // later start
        int hi = Math.min(A[i][1], B[j][1]);   // earlier end
        if (lo <= hi) out.add(new int[]{lo, hi}); // closed intervals: lo == hi is a 1-point intersection
        if (A[i][1] < B[j][1]) i++;            // whoever ends first is exhausted — advance it
        else j++;
    }
    return out.toArray(new int[0][]);
}

Time O(m + n), Space O(1) beyond output. No sort needed — the inputs come sorted.

Case: Meeting Rooms (LC 252) — can one person attend all?

Sort by start; if any meeting starts strictly before the previous one ends, there's a conflict. Note the strict < — back-to-back meetings are fine.

boolean canAttendMeetings(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
    for (int i = 1; i < intervals.length; i++)
        if (intervals[i][0] < intervals[i - 1][1]) // STRICT: start == prev end is OK (back-to-back)
            return false;
    return true;
}

Time O(n log n), Space O(1).

Why sorting by start makes the sweep sound Once sorted, cur.start >= prev.start for every later interval. So if cur doesn't reach back to the current block (cur.start > blockEnd), nothing after it can either — every later start is even bigger. That's why one linear pass finds every merge: the sort makes "no overlap with the last block" imply "no overlap with anything before it."

4 · Edge-case checklist

  • <= vs <. Merging treats touching as overlapping ([1,2],[2,3] → [1,3]); meeting-conflict treats touching as fine. Decide per problem, out loud.
  • Nested intervals. [1,10],[2,3]: extend with Math.max(prev.end, cur.end), never blindly cur.end — the classic silent bug.
  • Empty / single-element input. 0 intervals → return empty; 1 interval → return it. For LC 57, intervals may be empty — the three-phase code handles it, but check yours does.
  • Insert at the extremes (LC 57). newInterval entirely before everything, entirely after everything, or swallowing the whole list — all three must work.
  • Comparator overflow. Use Integer.compare(a[0], b[0]), not a[0] - b[0] — subtraction overflows on values near ±2·10⁹.
  • Don't sort what's already sorted. LC 57 and LC 986 give sorted input; re-sorting is wasted work and signals you didn't read the statement.
  • Single-point intersections (LC 986). Closed intervals mean [2,2] is a valid intersection — the test is lo <= hi, not lo < hi.
