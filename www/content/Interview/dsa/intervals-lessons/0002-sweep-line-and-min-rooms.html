Sweep Line & Minimum Rooms

"How many rooms?" is really "what's the maximum number of intervals alive at one instant?" — answer it with a heap of end times or a +1/−1 event sweep. Then learn when to sort by end instead.

Mission link: Meeting Rooms II is one of the most-asked interval questions at big tech, and the sort-by-end greedy behind 435/452 is a classic OA problem. Lesson 2 of 2 in the intervals track. Mission

1 · The one idea

Lesson 1 merged intervals into blocks. This lesson asks two new questions. (1) Peak concurrency: how many intervals overlap at the busiest instant? Track it either by reusing rooms (a min-heap of end times) or by sweeping time and counting +1 at every start and −1 at every end. (2) Maximum selection: how many disjoint intervals can you keep? Sort by end and greedily take whatever finishes earliest — finishing early leaves the most room for the rest.

Recognition trigger "Minimum number of rooms / platforms / servers / resources" → peak concurrency → heap or event sweep. "Maximum meetings you can attend / minimum intervals to remove / minimum arrows" → selection → sort by end + greedy. "Common free time / gaps" → merge everything (Lesson 1), then read the gaps.

2 · Two cores — Meeting Rooms II (LC 253)

Know both solutions; interviewers routinely ask for the second after you give the first.

Core A — min-heap of end times

Sort meetings by start. The heap holds the end time of every meeting currently running — one entry per occupied room. For each meeting: if the room that frees up earliest (heap top) is done by our start, reuse it (pop); either way, push our end time. The heap's maximum size is the answer. 

int minMeetingRooms(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0])); // by START
    PriorityQueue<Integer> ends = new PriorityQueue<>();  // min-heap of end times = occupied rooms
    for (int[] m : intervals) {
        if (!ends.isEmpty() && ends.peek() <= m[0])
            ends.poll();               // earliest-freeing room is free by our start → reuse it
        ends.offer(m[1]);              // occupy a room (reused or brand new) until m[1]
    }
    return ends.size();                // rooms never shrink below the peak — heap size IS the answer
}

Time O(n log n). Space O(n) for the heap.

Why checking only the heap top is enough The top is the room that frees earliest. If even that one isn't free by our start (peek() > start), no room is — we genuinely need a new one. And note peek() <= m[0]: a meeting ending at 10 frees the room for a 10:00 start (the touching rule from Lesson 1, decided consciously).

Core B — chronological event sweep (+1 / −1)

Forget which meeting is which. Turn every interval into two events — (start, +1) and (end, −1) — sort all events by time, and sweep, tracking a running count. The maximum count is the answer. This view generalizes to "max concurrent logins", "min platforms", calendar booking (LC 731/732), and anything shaped like peak load. 

int minMeetingRooms(int[][] intervals) {
    int n = intervals.length;
    int[] starts = new int[n], ends = new int[n];
    for (int i = 0; i < n; i++) { starts[i] = intervals[i][0]; ends[i] = intervals[i][1]; }
    Arrays.sort(starts);
    Arrays.sort(ends);                 // two sorted timelines instead of explicit (time, ±1) pairs
    int rooms = 0, peak = 0, e = 0;
    for (int s = 0; s < n; s++) {
        while (e < n && ends[e] <= starts[s]) { rooms--; e++; } // release EVERY room freed by this start (tie: end first)
        rooms++;                       // this meeting takes a room
        peak = Math.max(peak, rooms);
    }
    return peak;
}

Time O(n log n). Space O(n).

The tie-break IS the touching rule When an end and a start share the same timestamp, process the end first (the ends[e] <= starts[s] above does exactly that). Otherwise [1,10],[10,20] counts as 2 simultaneous rooms — off by one. If a problem ever says touching does conflict, flip to <. The tie-break in an event sweep is where the <=/< decision from Lesson 1 lives.

Worked example — dry run (Core B)

Meetings [[0,30],[5,10],[15,20]] → starts [0,5,15], ends [10,20,30].

start 0: no end ≤ 0 → rooms = 1, peak = 1 start 5: earliest end 10 > 5 → no release → rooms = 2, peak = 2 start 15: end 10 ≤ 15 → release one → rooms 2→1, then take → rooms = 2, peak stays 2 answer: 2 rooms — [0,30] overlaps each of the others, but [5,10] and [15,20] share a room

Case: Non-overlapping Intervals (LC 435) — sort-by-end greedy

"Minimum removals so none overlap" = n minus "maximum you can keep." Sort by end; keep an interval iff it starts at or after the last kept end (touching is fine here). 

int eraseOverlapIntervals(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1])); // by END — greedy selection
    int kept = 0, lastEnd = Integer.MIN_VALUE;
    for (int[] cur : intervals) {
        if (cur[0] >= lastEnd) {       // no overlap with last kept ([1,2],[2,3] compatible)
            kept++;
            lastEnd = cur[1];          // earliest possible end → most room for the rest
        }                              // else: overlaps → this one is removed (skip it)
    }
    return intervals.length - kept;    // removals = total − max keepable
}

Time O(n log n), Space O(1).

Case: Minimum Number of Arrows (LC 452)

Identical greedy skeleton, opposite touching rule: balloons are closed ranges, so an arrow at x bursts every balloon whose start <= x. Shoot each arrow at the end of the first unburst balloon. 

int findMinArrowShots(int[][] points) {
    Arrays.sort(points, (a, b) -> Integer.compare(a[1], b[1])); // Integer.compare — coords hit ±2³¹−1, a[1]-b[1] overflows
    int arrows = 0;
    long arrowPos = Long.MIN_VALUE;    // sentinel below every possible coordinate
    for (int[] b : points) {
        if (b[0] > arrowPos) {         // current arrow misses this balloon (STRICT: start == arrowPos still bursts)
            arrows++;
            arrowPos = b[1];           // new arrow at this balloon's end — bursts the max of what follows
        }
    }
    return arrows;
}

Time O(n log n), Space O(1). Compare with 435: the only differences are the comparison direction on ties and what you count.

Case: Employee Free Time (LC 759)

Every employee has sorted disjoint intervals; find gaps common to all. Flatten every schedule into one list, run the Lesson-1 merge, then the free time is exactly the space between consecutive merged blocks. 

// LC 759 uses class Interval { int start, end; }
List<Interval> employeeFreeTime(List<List<Interval>> schedule) {
    List<Interval> all = new ArrayList<>();
    for (List<Interval> emp : schedule) all.addAll(emp);   // flatten — whose meeting it is doesn't matter
    all.sort((a, b) -> Integer.compare(a.start, b.start)); // Lesson-1 merge begins
    List<Interval> free = new ArrayList<>();
    int busyEnd = all.get(0).end;
    for (Interval cur : all) {
        if (cur.start > busyEnd) {     // a real gap between merged busy blocks
            free.add(new Interval(busyEnd, cur.start));
            busyEnd = cur.end;
        } else {
            busyEnd = Math.max(busyEnd, cur.end); // still busy — extend the block (max: nesting!)
        }
    }
    return free;                       // gaps before the first / after the last block are unbounded — excluded
}

Time O(N log N) for N total intervals (a k-way-merge heap gets O(N log k) if asked to optimize). Space O(N).

5 · Edge-case checklist

  • Event-sweep tie-break. End before start at equal timestamps (rooms), unless the problem says touching conflicts. Getting this backwards inflates the peak by exactly 1 — a maddening off-by-one.
  • 435 vs 452 touching rule is opposite. 435 keeps [1,2],[2,3] (compatible, >=); 452's arrow at 2 bursts both (overlap, strict > to start a new arrow).
  • Overflow. LC 452 coordinates span the full int range: a[1] - b[1] in a comparator overflows. Always Integer.compare.
  • Count what's asked. 435 asks for removals (n − kept), not the kept count. Easy to return the wrong number after solving the hard part.
  • Heap answer = final size, not a running max poll count. In Core A the heap only grows past the peak, never shrinks below it, since we pop at most one per push.
  • 759's unbounded ends. Free time before the first meeting and after the last is infinite — don't emit it.
  • One meeting / empty input. One meeting → 1 room, 0 removals, 1 arrow. Sanity-check your loop bounds and sentinel initialization against it.
