Scheduling & Intervals

One sorting decision — by end, not by start — turns "which meetings do I keep?" from a combinatorial nightmare into a single sweep. This is greedy's most famous provably-optimal win.

Mission link: interval scheduling is the single most re-skinned OA problem in India — "maximum non-clashing deliveries" (Flipkart), "minimum servers" (PhonePe), "driver shift overlap" (Uber) are all this lesson. Lesson 2 of the 3-lesson greedy track. Mission

1 · The one idea

When you must select as many non-overlapping intervals as possible, sort by end time and always keep the interval that finishes earliest. Why is that safe? Exchange argument: take any optimal schedule; its first meeting can be swapped for the earliest-finishing meeting overall, because finishing earlier can only leave more room for everything after — never less. Repeat down the schedule and you land exactly on the greedy answer. Ending early is pure upside; starting early promises nothing (a meeting that starts at 9:00 and ends at 18:00 blocks your whole day).

Recognition trigger Intervals / meetings / jobs / balloons with a start and end, and a question that is one of: "maximum you can keep" or "minimum you must remove" (same problem — sort by end, count keeps), "minimum resources to serve all" (rooms/servers — sweep the timeline), or "minimum actions covering overlaps" (arrows). The word "non-overlapping" plus a min/max count is a near-certain sort-by-end greedy.

2 · Core template — sort by end, keep what fits

// LC 435 Non-overlapping Intervals: minimum removals so none overlap.
// Equivalent question: keep the MAXIMUM set of non-overlapping intervals.
int eraseOverlapIntervals(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1])); // sort by END
    int kept = 0;
    int lastEnd = Integer.MIN_VALUE;     // finish time of the last kept interval
    for (int[] iv : intervals) {
        if (iv[0] >= lastEnd) {          // starts after last kept ends → compatible
            kept++;
            lastEnd = iv[1];             // COMMIT to the earliest-finishing choice
        }                                // else: overlaps → this one is a removal
    }
    return intervals.length - kept;      // removals = total − max kept
}

Time O(n log n) for the sort, O(n) sweep. Space O(1) beyond sorting. Note the comparator: Integer.compare(a[1], b[1]), not subtraction — a[1] - b[1] can overflow on large coordinates.

Sort by START vs sort by END — the decision rule Merging or covering intervals (LC 56 Merge Intervals, insert, union length)? Sort by start — you're gluing everything together and need to encounter each interval's left edge in order. Selecting a maximum compatible subset, or minimizing removals/arrows? Sort by end — you're choosing winners, and the earliest finisher is the provably safe pick. One mnemonic: merge looks left (starts), select looks right (ends). Sorting LC 435 by start is the classic wrong answer: [1,100] would get kept first and force out [2,3],[4,5],[6,7].

Case: Minimum Arrows to Burst Balloons (LC 452)

Balloons are intervals on the x-axis; one vertical arrow pops every balloon it passes through. Minimum arrows = group balloons that share a common point. Greedy: sort by end; shoot the first arrow at the first balloon's end (the latest position that still hits it, maximizing how many later balloons it can catch); any balloon starting at or before that position is already popped. 

int findMinArrowShots(int[][] points) {
    Arrays.sort(points, (a, b) -> Integer.compare(a[1], b[1])); // by end; compare() avoids overflow
    int arrows = 1;
    int arrowAt = points[0][1];          // shoot at the earliest end
    for (int[] p : points) {
        if (p[0] > arrowAt) {            // starts strictly after the arrow → not hit
            arrows++;
            arrowAt = p[1];              // new arrow at this balloon's end
        }
    }
    return arrows;
}

Spot the family resemblance: LC 435 asks how many intervals you can keep pairwise-disjoint; LC 452 asks how many disjoint groups the intervals form. Same sort, same sweep — only the comparison flips from >= (touching is OK to keep) to > (touching balloons share the arrow).

Case: Meeting Rooms II (LC 253) — min resources, not selection

"Minimum rooms so every meeting runs" is a different question: you can't drop meetings, so sort-by-end selection doesn't apply. Sweep meetings by start time, keeping a min-heap of end times of rooms in use. If the next meeting starts at or after the earliest-ending room frees up, reuse that room (pop); otherwise open a new one (push). The heap's peak size is the answer — it equals the maximum number of meetings overlapping at any instant. 

int minMeetingRooms(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0])); // by START: process chronologically
    PriorityQueue<Integer> ends = new PriorityQueue<>();           // min-heap of room end times
    for (int[] iv : intervals) {
        if (!ends.isEmpty() && ends.peek() <= iv[0])
            ends.poll();                 // earliest room is free by now → reuse it
        ends.offer(iv[1]);               // this meeting occupies a room until iv[1]
    }
    return ends.size();                  // rooms simultaneously needed at the peak
}

Time O(n log n). Space O(n) for the heap. An equivalent event-sweep exists (sort all starts and ends separately, +1 on start, −1 on end, track the max) — mention it if the interviewer asks for an alternative.

Case: Task Scheduler (LC 621) — greedy on the bottleneck

Tasks A–Z, identical tasks need a cooldown of n slots between runs; minimize total time. Greedy insight: the most frequent task is the bottleneck. Lay out its maxFreq occurrences first — that creates maxFreq − 1 gaps, each n slots wide — then pour every other task into the gaps (always filling from the currently-most-frequent, which is why this is greedy). Two regimes: 

int leastInterval(char[] tasks, int n) {
    int[] freq = new int[26];
    for (char t : tasks) freq[t - 'A']++;
    int maxFreq = 0, tiedForMax = 0;
    for (int f : freq) {
        if (f > maxFreq) { maxFreq = f; tiedForMax = 1; }
        else if (f == maxFreq) tiedForMax++;
    }
    // frame: (maxFreq-1) blocks of size (n+1), plus one final row of the tied-for-max tasks
    int framed = (maxFreq - 1) * (n + 1) + tiedForMax;
    return Math.max(framed, tasks.length); // if gaps overflow, tasks.length wins (no idle at all)
}
tasks = A A A B B C, n = 2 → freq A=3, B=2, C=1; maxFreq=3, ties=1 frame from A: A _ _ A _ _ A → (3−1)×(2+1) + 1 = 7 slots fill gaps most-frequent-first: A B C A B idle A → length 7 ✓ if there were many distinct tasks, the gaps overflow and the answer is just tasks.length

Time O(n) over tasks (the 26-way scan is constant). Space O(1). The Math.max(..., tasks.length) is the line everyone forgets: with enough task variety there is never an idle slot, and the frame formula would undercount.

4 · Edge-case checklist

  • Touching intervals. [1,2] and [2,3]: NOT overlapping in LC 435 (iv[0] >= lastEnd keeps both) but the balloons DO share an arrow in LC 452 (p[0] > arrowAt starts a new one). Read the problem's definition of overlap every time.
  • Comparator overflow. LC 452 has coordinates near ±2³¹ — a[1] - b[1] overflows. Always Integer.compare.
  • Empty input. LC 452's points[0][1] assumes at least one balloon; guard or rely on constraints.
  • Selection vs coverage. "Keep the most / remove the fewest" → sort by end. "Serve them all with fewest resources" → heap/event sweep. Confusing these gives a clean-compiling wrong answer.
  • Heap reuse condition. LC 253: a room ending exactly at the new start IS free — ends.peek() <= iv[0], not <.
  • LC 621 with n = 0. The frame formula gives maxFreq−1+ties which can undercount; Math.max with tasks.length rescues it (answer is simply tasks.length).
