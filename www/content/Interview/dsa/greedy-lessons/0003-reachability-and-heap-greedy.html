Reachability & Heap Greedy

Two final greedy engines: a running frontier that answers "can I get there / how fast", and a heap that re-sorts the world after every choice. Plus the track cheat sheet.

Mission link: Jump Game and Gas Station are stock Uber/PhonePe OA questions, and heap-greedy (merge costs, capital scheduling) is a Goldman favorite. Lesson 3 of 3 in the greedy track. Mission

1 · The one idea

Some greedies don't sort at all. Reachability greedy sweeps once, maintaining the furthest index reachable so far — a frontier that only grows; a position is winnable iff the frontier never falls behind you (you saw this shape in Partition Labels). And when the "best next choice" changes after every pick — cheapest two sticks, most profitable affordable project — a one-time sort isn't enough: heap greedy keeps candidates in a PriorityQueue so the current best is always on top, at O(log n) per commit.

Recognition trigger Reachability: "can you reach the end", "minimum jumps/steps", "starting point that survives a circuit" — an array where each element extends how far you can go. Heap greedy: "repeatedly combine/pick the two smallest", "at each step choose the best available under a constraint" — the candidate pool changes as you commit, so the best must be re-computed cheaply. If you catch yourself wanting to re-sort inside a loop, that's the heap trigger.

2 · Core template — the furthest-reach sweep

// LC 55 Jump Game: nums[i] = max jump length from i. Can you reach the last index?
boolean canJump(int[] nums) {
    int reach = 0;                       // furthest index reachable so far
    for (int i = 0; i < nums.length; i++) {
        if (i > reach) return false;     // gap: frontier fell behind → stuck forever
        reach = Math.max(reach, i + nums[i]); // greedy: extend the frontier
        if (reach >= nums.length - 1) return true;
    }
    return true;                         // loop ended → last index was within reach
}

Time O(n), Space O(1). Why safe? The frontier is the max over all reachable positions — it doesn't matter which jumps you take, only how far the best of them extends. No choice is ever "wasted", so tracking the max loses nothing. (The DP version is O(n²); this is the poster child for "greedy beats DP when a monotone frontier summarizes the state.")

Case: Jump Game II (LC 45) — fewest jumps via two frontiers

Think BFS on the array: everything reachable in ≤ k jumps is a contiguous window. Sweep with curEnd (the far edge of the current jump's window) and farthest (best reach seen inside it). When i hits curEnd, you must jump — and the greedy-safe landing is whatever gave farthest. 

int jump(int[] nums) {
    int jumps = 0, curEnd = 0, farthest = 0;
    for (int i = 0; i < nums.length - 1; i++) {   // note: stop BEFORE the last index
        farthest = Math.max(farthest, i + nums[i]);
        if (i == curEnd) {               // exhausted this jump's window → commit a jump
            jumps++;
            curEnd = farthest;           // next window = best reach found
        }
    }
    return jumps;
}

Time O(n), Space O(1). Looping to nums.length - 1 matters: including the last index can count a phantom extra jump when you land exactly on it.

Case: Gas Station (LC 134) — the restart argument

Circular route; gain[i] = gas[i] - cost[i]. If total gain < 0, no start works. Otherwise sweep with a running tank; whenever the tank drops below zero at station i, restart from i + 1. Why can you skip every station in the failed stretch? Because you arrived at each of them with tank ≥ 0 — starting at one of them means starting with an empty tank, i.e. with less or equal fuel than the run that already failed. None of them can succeed, so jumping straight past the failure point is safe. 

int canCompleteCircuit(int[] gas, int[] cost) {
    int total = 0, tank = 0, start = 0;
    for (int i = 0; i < gas.length; i++) {
        int gain = gas[i] - cost[i];
        total += gain;
        tank  += gain;
        if (tank < 0) {                  // stranded before i+1
            start = i + 1;               // restart PAST the failure — no stretch station can win
            tank = 0;
        }
    }
    return total >= 0 ? start : -1;      // total gain ≥ 0 guarantees the surviving start works
}

Time O(n), Space O(1). The two-part proof (restart-skip + "total ≥ 0 ⇒ the last surviving start completes the circle") is a beloved interview follow-up — rehearse it.

Case: Minimum Cost to Connect Sticks (LC 1167) — heap greedy / Huffman's idea

Connecting sticks of lengths a and b costs a + b; minimize total cost to connect all. Every early merge's weight is re-paid in each later merge that includes it — so the smallest sticks should be merged first (they get counted the most times). This is exactly Huffman coding: frequent symbols get short codes; light sticks get merged deep. 

int connectSticks(int[] sticks) {
    PriorityQueue<Integer> pq = new PriorityQueue<>(); // min-heap: smallest on top
    for (int s : sticks) pq.offer(s);
    int cost = 0;
    while (pq.size() > 1) {
        int merged = pq.poll() + pq.poll();  // greedy: ALWAYS the two smallest
        cost += merged;
        pq.offer(merged);                    // the new stick competes with the rest
    }
    return cost;
}

Time O(n log n), Space O(n). Exchange argument: if an optimal merge tree ever combines a non-smallest pair first, swapping in the two smallest sticks at that depth can only reduce (or keep) the total weighted cost. Note why a one-time sort fails: the merged stick's size is new data that must be re-ranked — hence the heap.

Case: IPO (LC 502) — two-constraint heap greedy (sketch)

Pick at most k projects; each needs capital[i] upfront and pays profits[i]; maximize final capital. Two moving parts → two orderings: sort projects by capital, and keep a max-heap of profits for the ones you can currently afford. Each round: unlock all newly-affordable projects into the heap, then greedily take the top profit (safe — profit adds directly to capital, so the biggest affordable profit can never hurt). 

int findMaximizedCapital(int k, int w, int[] profits, int[] capital) {
    int n = profits.length;
    int[][] proj = new int[n][2];
    for (int i = 0; i < n; i++) proj[i] = new int[]{capital[i], profits[i]};
    Arrays.sort(proj, (a, b) -> Integer.compare(a[0], b[0])); // by capital needed
    PriorityQueue<Integer> best = new PriorityQueue<>((a, b) -> b - a); // max-heap of profits
    int i = 0;
    while (k-- > 0) {
        while (i < n && proj[i][0] <= w) best.offer(proj[i++][1]); // unlock affordable
        if (best.isEmpty()) break;       // nothing affordable → stop early
        w += best.poll();                // take the richest unlocked project
    }
    return w;
}

Time O(n log n + k log n), Space O(n). The shape to remember: sort by the gating constraint, heap by the objective.

5 · Edge-case checklist

  • LC 55: single-element array is trivially true; zeros are only fatal if the frontier lands exactly on them with nothing beyond.
  • LC 45: loop bound is nums.length - 1; guaranteed-reachable per constraints, so no gap check needed there.
  • LC 134: answer is unique when it exists (constraint says so); return -1 only via the total-gain check, never mid-loop.
  • Heap direction. Sticks want a min-heap, IPO profits a max-heap — flipping the comparator is the most common heap-greedy bug. In Java, max-heap = new PriorityQueue<>(Collections.reverseOrder()).
  • Overflow. Merge costs and running capital can exceed int on big inputs — reach for long in OAs even when LC constraints don't force it.
  • Heap with one element (LC 1167 single stick): cost 0; the size() > 1 guard already handles it.
  • IPO with zero affordable projects: break out instead of polling an empty heap.
