Greedy Track · Lesson 1 of 3 · what greedy is, and when to trust it

Greedy Foundations

Take the best-looking option right now, never look back — a strategy that is usually wrong, occasionally provably perfect, and worth a fortune in OAs when you know which is which.

Mission link: Indian big-tech OAs (Flipkart, PhonePe, Uber, Goldman) are greedy-heavy — short problems where the whole game is spotting the safe greedy choice fast. This is Lesson 1 of the 3-lesson greedy track. Mission

1 · The one idea

A greedy algorithm builds a solution one step at a time, and at each step commits to the choice that looks best right now — no backtracking, no "what if". That makes it blazingly simple and fast (usually one sort plus one linear sweep), but also dangerous: a locally best choice can lock you out of the globally best answer. So greedy comes with a rule you must never break: a greedy choice is only valid if you can argue it's safe. The standard argument is the exchange argument: take any optimal solution that disagrees with your greedy choice, swap in the greedy choice, and show the result is no worse. If every disagreement can be exchanged away, greedy is optimal.

Recognition trigger "Minimum / maximum number of…", "can you…", "assign / schedule / distribute", one pass over sorted data, and — crucially — a one-line reason why committing early can't hurt. If the problem has interacting choices where an early pick changes the value of later options in complicated ways, that's DP territory, not greedy. In an OA: if the constraint is n ≤ 10⁵ and the answer is a single count or boolean, greedy (or greedy + sort) is the first thing to try — after a 10-second safety check.

2 · Core template — sort, then sweep

Most interview greedies share one shape: sort by the dimension that makes the greedy choice safe, then sweep once, committing at each element. Here it is on Assign Cookies (LC 455): give each child the smallest cookie that satisfies them, so big cookies stay available for greedy kids. 

// LC 455 Assign Cookies: g[i] = child i's greed, s[j] = cookie j's size.
// Greedy: sort both; satisfy the easiest child with the smallest workable cookie.
int findContentChildren(int[] g, int[] s) {
    Arrays.sort(g);                      // 1. SORT by the safety dimension
    Arrays.sort(s);
    int child = 0;
    for (int cookie = 0; cookie < s.length && child < g.length; cookie++)
        if (s[cookie] >= g[child])       // 2. SWEEP: commit when the local choice works
            child++;                     // this child is done — never revisit
    return child;
}

Time O(n log n + m log m) — the sorts dominate; the sweep is linear. Space O(1) beyond sorting.

The exchange argument, on this exact problem Suppose an optimal solution gives the easiest child a bigger cookie than the smallest one that fits. Swap the two cookies: the easy child is still satisfied (their cookie only shrank to something that still fits), and the other child got a cookie that's at least as big — so still satisfied. Same number of happy children, but now it agrees with greedy. Repeat for every disagreement ⇒ greedy is optimal. That's the whole proof pattern: swap, show no-worse, repeat. Practice saying it in two sentences — interviewers at Uber and Goldman explicitly ask "why does greedy work here?"

Case: Can Place Flowers (LC 605) — greedy without sorting

Sweep left to right; plant in every plot whose left and right neighbors are empty. Safe because planting as early (as left) as possible never blocks more future plots than skipping would — an early plant "uses up" the leftmost available space, leaving the maximum room to its right. 

boolean canPlaceFlowers(int[] bed, int n) {
    for (int i = 0; i < bed.length && n > 0; i++) {
        boolean leftOk  = (i == 0) || bed[i - 1] == 0;             // edge counts as empty
        boolean rightOk = (i == bed.length - 1) || bed[i + 1] == 0;
        if (bed[i] == 0 && leftOk && rightOk) {
            bed[i] = 1;                  // COMMIT: plant greedily, never reconsider
            n--;
        }
    }
    return n <= 0;                       // n == 0 also fine when loop ends early
}

Case: Partition Labels (LC 763) — the running-frontier greedy

Split a string into the most parts so each letter appears in only one part. Precompute each letter's last occurrence. Sweep, extending the current partition's required end to the farthest last-index seen; the moment you reach that frontier, everything inside is self-contained — cut. This "extend a frontier, close when you catch it" shape returns in Jump Game II (Lesson 3). 

List<Integer> partitionLabels(String s) {
    int[] last = new int[26];
    for (int i = 0; i < s.length(); i++) last[s.charAt(i) - 'a'] = i;
    List<Integer> sizes = new ArrayList<>();
    int end = 0, start = 0;
    for (int i = 0; i < s.length(); i++) {
        end = Math.max(end, last[s.charAt(i) - 'a']); // frontier: partition must reach here
        if (i == end) {                  // caught the frontier → safe to cut
            sizes.add(i - start + 1);
            start = i + 1;
        }
    }
    return sizes;
}

Time O(n), Space O(1) — the 26-slot array is constant.

Case: Lemonade Change (LC 860) — greedy inside a simulation

Customers pay $5, $10, or $20 for a $5 drink; can you always make change? The greedy bit: for a $20, prefer giving $10 + $5 over three $5s, because $5 bills are strictly more flexible (they're the only way to change a $10). Spend the least-flexible currency first. 

boolean lemonadeChange(int[] bills) {
    int fives = 0, tens = 0;
    for (int b : bills) {
        if (b == 5) fives++;
        else if (b == 10) {              // needs exactly one $5
            if (fives == 0) return false;
            fives--; tens++;
        } else {                         // $20: prefer 10+5 — hoard the flexible $5s
            if (tens > 0 && fives > 0) { tens--; fives--; }
            else if (fives >= 3) fives -= 3;
            else return false;
        }
    }
    return true;
}

Case: where greedy FAILS — coin change with coins {1, 3, 4}

Fewest coins to make 6. Greedy ("always take the biggest coin that fits") grabs 4, then can't use 4 or 3, so takes 1 + 1: three coins. Optimal is 3 + 3: two coins.

target 6, coins {1, 3, 4} greedy: take 4 → remaining 2 → take 1, take 1 → coins used = 3 optimal: take 3 → remaining 3 → take 3 → coins used = 2 greedy's early commit to 4 locked out the 3+3 split — no exchange argument can save it

Why does the exchange argument break? Swapping the 4 for a 3 leaves remainder 3 vs remainder 2 — the swap changes the value of the subproblem, so you can't argue "no worse". When an early choice reshapes what later choices are worth, you need DP: try every coin at each amount and take the min. 

// LC 322-style DP — correct for ANY coin system. dp[a] = fewest coins for amount a.
int coinChange(int[] coins, int amount) {
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, amount + 1);         // "infinity" sentinel
    dp[0] = 0;
    for (int a = 1; a <= amount; a++)
        for (int c : coins)
            if (c <= a)
                dp[a] = Math.min(dp[a], dp[a - c] + 1); // consider EVERY coin — no early commit
    return dp[amount] > amount ? -1 : dp[amount];
}

Time O(amount × coins), Space O(amount) — the price of not trusting greedy.

The "prove it or don't trust it" habit Greedy works for {1, 5, 10, 25} (US coins) and fails for {1, 3, 4} — the same algorithm, correctness decided by the input structure. So never submit a greedy on vibes. Before coding, spend 10 seconds on either (a) a two-sentence exchange argument, or (b) hunting for a small counterexample (3–5 elements is usually enough). If you find neither, write the brute force / DP. A wrong greedy that passes samples and fails hidden tests is the classic OA point-killer.

4 · Edge-case checklist

  • Empty / single-element input. Greedy sweeps usually handle these for free, but check: LC 605 with a length-1 bed, LC 455 with no cookies.
  • Boundary neighbors. In LC 605, index 0 has no left neighbor and the last index no right — treat "off the edge" as empty (i == 0 || bed[i-1] == 0).
  • Sorted by the wrong key. The sort dimension is the proof. Sorting cookies descending in LC 455 wastes big cookies on easy kids — same code shape, wrong answer.
  • Ties and equal values. Make sure your commit condition is >= vs > deliberately: a cookie of size exactly g[child] does satisfy.
  • Mutating the input (LC 605 plants into bed). Fine in OAs; mention it in interviews and offer a no-mutation variant if asked.
  • Greedy correctness is per-problem, not per-pattern. Re-verify the safety argument every time the constraints shift (e.g., coin systems, weighted versions).
