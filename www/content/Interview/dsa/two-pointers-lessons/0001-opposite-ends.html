Opposite-Ends Two Pointers

Start one pointer at each end, move them toward each other under a rule, and a brute-force O(n²) pair scan collapses into a single O(n) pass.

Mission link: two pointers is the single most common array pattern in big-tech OAs — it hides inside 3Sum, Container With Most Water, and dozens of "find a pair" questions. This is Lesson 1 of the 3-lesson Two Pointers track. Mission

1 · The one idea

You already know the naive way to find a pair in an array: two nested loops, try every (i, j), O(n²). The two-pointer insight is that when the data has structure — it's sorted, or it's symmetric like a palindrome — you don't need to try every pair. Put left at index 0 and right at the last index. At each step, the structure tells you which pointer is provably useless to keep: move that one inward. Each step eliminates at least one candidate forever, so after at most n steps the pointers meet. You've examined n positions instead of n²/2 pairs.

Recognition trigger The array is sorted (or sortable, or symmetric) AND you're asked about a pair / two things interacting: "two numbers that sum to target," "is it a palindrome," "two lines forming a container," "water trapped between walls." If a nested loop over pairs is the naive answer and the data is ordered, opposite-ends pointers is almost always the intended O(n) solution.

2 · Core template — Two Sum II (LC 167)

Sorted array, find two numbers summing to target. Naive: for each i, scan the rest — O(n²). Better naive: for each i, binary-search for target − a[i] — O(n log n). The two-pointer version beats both. The key question at every step: what does the current sum tell me? If a[l] + a[r] is too small, then a[l] paired with anything at or left of r is also too small (the array is sorted, so a[r] was its best shot) — a[l] can never be part of the answer, discard it with l++. Symmetrically, too big means a[r] is dead: r--. 

// LC 167: sorted 1-indexed array, exactly one solution guaranteed.
int[] twoSum(int[] a, int target) {
    int l = 0, r = a.length - 1;         // one pointer per end
    while (l < r) {                      // strictly <: a pair needs two DIFFERENT indices
        int sum = a[l] + a[r];
        if (sum == target) return new int[]{l + 1, r + 1}; // problem wants 1-indexed
        if (sum < target) l++;           // sum too small → a[l] is exhausted: even a[r] couldn't save it
        else r--;                        // sum too big → a[r] is exhausted: even a[l] couldn't save it
    }
    return new int[]{-1, -1};            // unreachable here (solution guaranteed)
}

Time O(n) — every step retires one index for good. Space O(1) — two ints. Compare: nested loops O(n²), hash map O(n) time but O(n) space. Sorted input is what buys you O(1) space.

Worked example — dry run

a = [2, 7, 11, 15], target = 18:

l=0(2) r=3(15) sum=17 < 18 → 2 can't do better than 15; drop it → l++ l=1(7) r=3(15) sum=22 > 18 → 15 can't do better than 7; drop it → r-- l=1(7) r=2(11) sum=18 = target → return [2, 3] (1-indexed) 3 steps, not 6 pairs — each comparison permanently eliminated one index
The elimination argument — say it out loud in interviews Every opposite-ends solution rests on one sentence: "when I move a pointer, I've proven that index can't appear in any better answer." If you can state why the discarded index is dead, your solution is correct; if you can't, you probably have a counterexample. This argument is what makes Container With Most Water below click.

Case: Valid Palindrome (LC 125)

Same skeleton, different rule: instead of a sum, compare characters for equality and bail on mismatch. The wrinkle is the input is dirty — skip anything that isn't a letter or digit, and compare case-insensitively. 

boolean isPalindrome(String s) {
    int l = 0, r = s.length() - 1;
    while (l < r) {
        while (l < r && !Character.isLetterOrDigit(s.charAt(l))) l++; // skip junk; keep l < r guard!
        while (l < r && !Character.isLetterOrDigit(s.charAt(r))) r--;
        if (Character.toLowerCase(s.charAt(l)) != Character.toLowerCase(s.charAt(r)))
            return false;                // mirror positions disagree → not a palindrome
        l++; r--;                        // both matched → both move inward
    }
    return true;                         // pointers crossed with no mismatch
}

Time O(n), Space O(1). Naive alternative — build a cleaned string and compare with its reverse — is also O(n) time but O(n) space; interviewers ask for the in-place version.

Case: Container With Most Water (LC 11) — "move the worse side"

Heights h[]; pick two lines so the container holds the most water: area = min(h[l], h[r]) × (r − l). Naive is all pairs, O(n²). Two pointers works, but the movement rule changes: there's no target to compare against. Instead, ask which pointer is hopeless. Moving either pointer inward shrinks the width — so the only way a future pair beats the current one is with a taller minimum. The shorter line is the bottleneck: keep it, and every future container it forms is capped at its height with less width — strictly worse. So the shorter line is dead. Discard it. 

int maxArea(int[] h) {
    int l = 0, r = h.length - 1, best = 0;
    while (l < r) {
        int area = Math.min(h[l], h[r]) * (r - l);
        best = Math.max(best, area);     // no target → track the best seen
        if (h[l] < h[r]) l++;            // shorter side is the bottleneck → it can NEVER do better; drop it
        else r--;                        // ties: either move is safe (that min height is maxed out)
    }
    return best;
}

Time O(n), Space O(1). The proof is the elimination argument: when we drop h[l] (the shorter), every unexplored pair containing l has area ≤ h[l] × (smaller width) < current area — none of them can be the answer, so skipping them is safe.

Case: Trapping Rain Water (LC 42) — two-pointer version

Water above position i is min(maxLeft, maxRight) − h[i]: the shorter of the tallest walls on each side sets the water level. The O(n)/O(n) solution precomputes two max arrays. The two-pointer version drops to O(1) space by noticing you don't need both maxes exactly — only the smaller one, and you can know which is smaller without full information. Keep running maxes maxL, maxR from each end. If maxL < maxR, then for position l the true left max is exactly maxL (we've seen everything left of it) and the true right max is ≥ maxR > maxL — so the water level at l is decided by maxL alone. Settle it, move on. 

int trap(int[] h) {
    int l = 0, r = h.length - 1;
    int maxL = 0, maxR = 0, water = 0;   // tallest wall seen so far from each end
    while (l < r) {
        maxL = Math.max(maxL, h[l]);
        maxR = Math.max(maxR, h[r]);
        if (maxL < maxR) {               // left's ceiling is the binding one — right side can only be taller
            water += maxL - h[l];        // safe to settle position l NOW (≥ 0: maxL includes h[l])
            l++;
        } else {
            water += maxR - h[r];        // symmetric: right's ceiling decides position r
            r--;
        }
    }
    return water;
}

Time O(n), Space O(1) — versus O(n) extra space for the prefix-max version. Same complexity as the monotonic-stack variant, but far less code.

The classic wrong instinct In LC 11 and 42 people move the pointer "on the taller side" or "the one that looks promising." Wrong way around — you always retire the weaker side, because the weak side is the one whose fate is already sealed. The tall side might still pair with something even taller; the short side never improves.

4 · Edge-case checklist

  • while (l < r), not <= — pair problems need two distinct indices; l == r would pair an element with itself.
  • Empty / single-element input — the loop body never runs; make sure your default return (true for palindrome, 0 for area) is right.
  • Inner skip loops need the l < r guard too (LC 125) — a string of pure punctuation like ".,!" will run a pointer off the end otherwise.
  • Duplicates — the core template returns the first valid pair; if you must enumerate all pairs (3Sum, Lesson 3), you'll need dedup skips.
  • Ties in "move the worse side" — when h[l] == h[r] either move is safe; don't overthink it, just pick one branch consistently.
  • 1-indexed answers (LC 167) — read the output format before submitting; off-by-one here is a free wrong answer.
  • Overflow — a[l] + a[r] of two ints near 2³¹ overflows; use long if constraints allow values that large.
