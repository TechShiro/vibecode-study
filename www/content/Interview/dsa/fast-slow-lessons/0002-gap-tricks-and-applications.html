Fast & Slow — Gap Tricks & Applications

The same two-pointer race, redeployed: an array that secretly contains a cycle, palindromes checked in O(1) space, and a fixed-gap trick that deletes the nth-from-end in one pass.

Mission link: Find the Duplicate Number (LC 287) is a famous "aha" interview question — the O(1)-space answer is Lesson 1's cycle trick wearing an array costume. This is Lesson 2 of the 2-lesson Fast & Slow track. Mission

1 · The one idea

Fast & slow is really about the gap two pointers maintain. A growing gap (speeds 1 and 2) detects cycles and finds midpoints. A fixed gap (same speed, head start of n) finds "nth from the end" in one pass. And the structure doesn't have to be a linked list: any deterministic "next" — including i → nums[i] over an array — is a linked list in disguise, so Floyd's machinery transfers wholesale.

Recognition trigger "Find the duplicate without modifying the array and in O(1) space," "is the list a palindrome (O(1) space)," "remove the nth node from the end in one pass," "reorder / fold the list." Constraints that outlaw HashSets, sorting, or a second pass are the tell — they force pointer gymnastics.

2 · Core — the array-as-linked-list reduction (LC 287)

nums has n+1 integers, each in 1..n, one value duplicated. Read index i as a node whose next pointer is nums[i]. Values in 1..n mean every arrow lands at a valid index, and starting from index 0 (which no arrow returns to, since values are ≥ 1) the walk enters a ρ-shape: a tail, then a loop. Two arrows entering one node is exactly a duplicated value — so the duplicate is the cycle entrance, and LC 142's two-phase algorithm reads it off without touching the array. 

int findDuplicate(int[] nums) {
    int slow = nums[0], fast = nums[nums[0]];    // take 1 and 2 steps from "node" 0
    while (slow != fast) {                       // phase 1: collide inside the cycle
        slow = nums[slow];                       // slow = slow.next
        fast = nums[nums[fast]];                 // fast = fast.next.next
    }
    slow = 0;                                    // phase 2: reset to head (index 0)
    while (slow != fast) {
        slow = nums[slow];                       // both at speed 1 now
        fast = nums[fast];
    }
    return slow;                                 // cycle entrance = the duplicated value
}

Time O(n), Space O(1), array untouched — the only approach that satisfies all of LC 287's constraints at once (sorting mutates, HashSet costs O(n) space, binary-search-on-value works but is O(n log n)).

nums = [1, 3, 4, 2, 2]  →  arrows: 0→1, 1→3, 2→4, 3→2, 4→2 walk from 0: 0 → 1 → 3 → 2 → 4 → 2 → 4 → … (tail 0→1→3, loop 2→4→2) two arrows enter node 2 (from 3 and from 4) — because the VALUE 2 appears twice cycle entrance = 2 = the duplicate ✓

Case: Palindrome Linked List (LC 234)

O(1) space forces surgery: find the middle (Lesson 1), reverse the second half in place (the flip-loop from Reversal Lesson 1), then walk the two halves in lockstep comparing values. The first-middle guard (fast.next != null && fast.next.next != null) keeps the extra node in the front half for odd lengths. 

boolean isPalindrome(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast.next != null && fast.next.next != null) { // slow → FIRST middle
        slow = slow.next;
        fast = fast.next.next;
    }
    ListNode second = slow.next;
    slow.next = null;                        // sever the halves
    ListNode prev = null;                    // reverse the back half (Reversal Lesson 1)
    while (second != null) {
        ListNode next = second.next;
        second.next = prev;
        prev = second;
        second = next;
    }
    ListNode p1 = head, p2 = prev;           // compare front half vs reversed back half
    while (p2 != null) {                     // back half is ≤ front half in length
        if (p1.val != p2.val) return false;
        p1 = p1.next;
        p2 = p2.next;
    }
    return true;                             // (interview bonus: re-reverse to restore the list)
}

Time O(n), Space O(1). For odd length the middle node stays in the front half and is never compared — correct, since it matches itself. Mentioning "I could re-reverse to restore the input" earns points.

Case: Reorder List (LC 143) — same skeleton, different phase 3

Identical setup to LC 234 — find mid, sever, reverse back half — but phase 3 zip-merges instead of comparing: a₁→aₙ→a₂→aₙ₋₁…. Full code and dry run live in Reversal Lesson 2; here, notice the shared skeleton. Once you own "mid + reverse," two LeetCode problems differ by only their last loop:

Case: Remove Nth Node From End (LC 19) — the fixed gap

Different trick, same family: both pointers move at speed 1, but lead starts n + 1 steps ahead of trail (the +1 lands trail before the victim, from the dummy). When lead hits null, the gap guarantees trail.next is the nth from the end. One pass, no length count. 

ListNode removeNthFromEnd(ListNode head, int n) {
    ListNode dummy = new ListNode(0);
    dummy.next = head;                       // dummy: the head itself might be deleted
    ListNode lead = dummy, trail = dummy;
    for (int i = 0; i < n + 1; i++) lead = lead.next; // open a gap of n+1
    while (lead != null) {                   // slide the whole gap to the end
        lead = lead.next;
        trail = trail.next;
    }
    trail.next = trail.next.next;            // trail is just before the victim → unlink it
    return dummy.next;
}

Time O(n) single pass, Space O(1). Deleting the head (n = length) is exactly why the dummy exists: trail stays on dummy and dummy.next skips the old head.

4 · Edge-case checklist

  • LC 287 starting points: start the walk conceptually at index 0 — it's outside the cycle since no value equals 0. Initializing slow = nums[0], fast = nums[nums[0]] is "already moved once/twice," which lets the while (slow != fast) guard work without a do-while.
  • Don't modify, don't allocate (LC 287): the problem explicitly bans sorting and O(n) space; if you reach for a HashSet, expect the follow-up. Floyd's is the intended answer.
  • First vs second middle: cutting problems (234/143) want the first middle guard so the front half keeps the odd node. Re-check the guard on a 4-node dry run.
  • Sever before reversing (234/143): forgetting slow.next = null leaves a cycle and the final loop never terminates.
  • Compare on p2 != null (LC 234): the reversed back half is the shorter (or equal) half; driving on p1 overruns for odd lengths.
  • Gap size n + 1, from dummy (LC 19): a gap of n lands trail ON the victim; n + 1 lands it just before. And with n = list length, only the dummy start keeps trail valid.
  • Restore-the-input bonus (LC 234): real interviews sometimes require leaving the list intact — re-run the flip-loop on the back half and re-attach.

5 · Check yourself

In LC 287, why is the duplicated value guaranteed to be the entrance of the cycle in the i → nums[i] graph?
In LC 19 you open a gap of exactly n (not n + 1) starting from the dummy. When lead hits null, where is trail?
