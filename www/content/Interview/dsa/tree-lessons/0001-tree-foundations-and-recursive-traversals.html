Tree Foundations & Recursive Traversals

A tree is a recursive shape, so recursion isn't a trick here — it's the native language. Learn the three visit orders and, more importantly, what each one is for.

Mission link: trees are the single most common data structure in big-tech OAs and phone screens — nearly every tree question is one of six shapes, and this track covers all six. Lesson 1 of 6. Mission

1 · The one idea

A binary tree is defined by itself: a node holds a value and two smaller binary trees (left, right), and the empty tree is null. Because the definition is recursive, almost every tree algorithm is three lines: handle null, recurse left, recurse right — and the only real decision is when you process the current node relative to those two recursive calls. Before (pre-order), between (in-order), or after (post-order). That single choice of visit order determines what information is available when you touch a node, and therefore what you can compute. 

// The node class every LeetCode tree problem hands you. Memorize it.
public class TreeNode {
    int val;
    TreeNode left;
    TreeNode right;
    TreeNode(int val) { this.val = val; }
}
Recognition trigger The input type is TreeNode root — that alone fires this pattern. Then ask: do I need nodes in a specific order (traverse/print/collect/kth), or a value computed from subtrees (height/sum/validate)? Order questions are this lesson; compute-from-children is Lesson 3. If the word BST appears with "sorted" or "kth smallest", think in-order immediately.

2 · Core template

Here's the naive-first framing: to visit every node you could try loops, but a tree has no single "next" pointer — each node forks two ways, so a loop can't remember where to come back to. Recursion solves that: the call stack remembers for you. One function, three placements of "visit": 

// The one recursive skeleton — the ONLY difference between the three
// traversals is WHERE the visit line sits. Time O(n), Space O(h) call stack
// (h = height: log n balanced, n for a stick-shaped tree).
void traverse(TreeNode node, List<Integer> out) {
    if (node == null) return;          // base case: empty tree, nothing to do

    out.add(node.val);                 // ← HERE = PRE-order  (root, left, right)  LC 144
    traverse(node.left, out);
    // out.add(node.val);              ← HERE = IN-order   (left, root, right)  LC 94
    traverse(node.right, out);
    // out.add(node.val);              ← HERE = POST-order (left, right, root)  LC 145
}

Time O(n) — every node visited exactly once. Space O(h) for the recursion stack, which is O(log n) if balanced but O(n) worst case on a degenerate (linked-list-shaped) tree.

Worked example — dry run

In-order on this tree. Watch how each node "waits" until its entire left subtree finishes:

inorder(4): first recurse left into 2 — 4 waits on the stack inorder(2): recurse left into 1 — 2 waits too inorder(1): left is null → visit 1 → right is null → return back in inorder(2): left done → visit 2 → recurse right into 3 → visit 3 back in inorder(4): left subtree done → visit 4 → recurse right into 6 inorder(6): left is 5 → visit 5 → then visit 6 output: [1, 2, 3, 4, 5, 6] — sorted, because this tree is a BST
The BST superpower — in-order is sorted In a Binary Search Tree, everything in the left subtree is smaller and everything in the right is larger. In-order visits left → node → right, so the output is ascending sorted order, for free. This one fact solves Kth Smallest (LC 230), Validate BST (LC 98), and inorder-successor problems — all in Lesson 5.

3 · All the cases

Same skeleton, three problems — plus the real payoff: knowing which order to reach for in later problems.

CaseProblemWhat changes
Pre-order traversalLC 144Visit before both recursions. Root comes first.
In-order traversalLC 94Visit between the recursions. Sorted for BSTs.
Post-order traversalLC 145Visit after both recursions. Children finish before parent.

What each order is FOR (this is the interview intuition)

OrderWhen node is visitedUse it when…Canonical uses
Pre (root, L, R)Before you know anything about the childrenYou pass info down: copy/serialize a tree, the root must be identified firstSerialize (297), Construct from preorder (105), path building

Case: Preorder Traversal (LC 144)

List<Integer> preorderTraversal(TreeNode root) {
    List<Integer> out = new ArrayList<>();
    pre(root, out);
    return out;
}
void pre(TreeNode n, List<Integer> out) {
    if (n == null) return;
    out.add(n.val);                    // root FIRST — its identity leads
    pre(n.left, out);
    pre(n.right, out);
}

Case: Inorder Traversal (LC 94)

void in(TreeNode n, List<Integer> out) {
    if (n == null) return;
    in(n.left, out);
    out.add(n.val);                    // root in the MIDDLE — sorted for a BST
    in(n.right, out);
}

Case: Postorder Traversal (LC 145)

void post(TreeNode n, List<Integer> out) {
    if (n == null) return;
    post(n.left, out);
    post(n.right, out);
    out.add(n.val);                    // root LAST — children's results are ready
}
The mental-model bug: trying to trace every call Don't simulate the whole call stack in your head — you'll drown on any tree bigger than five nodes. Instead use the recursive leap of faith: assume traverse(n.left) already correctly handles the entire left subtree (it does — it's the same function on a smaller input, and the null base case grounds it). Your only job is to get one node's logic and the base case right.

Reading LeetCode's tree notation

LeetCode prints trees as level-order arrays with nulls: [4,2,6,1,3,5] is the tree in the diagram above; [1,null,2] is a root whose only child is a right child. The judge builds the TreeNode for you — you never parse this — but you must read it fluently to debug failing tests. Two rules: values fill top-to-bottom, left-to-right, and a null means "no child here" (its own children are simply omitted, not written as more nulls).

4 · Edge-case checklist

  • root == null — the empty tree. Every recursive function's first line. Forgetting it = instant NullPointerException.
  • Single node — both children null; all three orders output just [root.val]. Good 10-second sanity check.
  • Skewed tree (every node has only one child) — recursion depth hits n, not log n. Java's default stack handles ~10⁴–10⁵ frames; deeper needs the iterative version (Lesson 2).
  • Don't confuse "visit" with "recurse". You always recurse left-then-right in all three orders; only the position of the visit line moves.
  • Helper vs. return-value style. Passing a List accumulator down (as above) is simplest; building and merging sublists allocates O(n²) in the worst case.
  • In-order sorted ⟺ BST only holds with strict inequalities — duplicates break "strictly sorted". Watch problem constraints.
