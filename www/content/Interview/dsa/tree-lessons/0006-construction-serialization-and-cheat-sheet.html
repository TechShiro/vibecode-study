Construction, Serialization & the Cheat Sheet

Traversals in reverse: instead of tree → sequence, rebuild sequence → tree. One insight powers all of it — preorder tells you WHO the root is, inorder tells you WHERE the split is.

Mission link: Construct from Traversals (105) and Serialize/Deserialize (297) are Meta and Amazon regulars, and 297 is the classic "design" tree question. This closes the tree track — cheat sheet at the bottom. Lesson 6 of 6. Mission

1 · The one idea

Every construction problem is the same two questions asked recursively: which element is the root? and which elements belong to its left subtree vs its right? Preorder (and postorder) answer the first — the root is the first (resp. last) element. Inorder answers the second — everything left of the root's position is the left subtree, everything right is the right subtree. Serialization is the same game made easy: by recording the nulls, one preorder string alone pins down the tree, no second traversal needed.

Recognition trigger "Construct / build the tree from…", "serialize / deserialize", "encode to a string and back". Also fires when a problem hands you two traversal arrays, or asks you to transmit/store a tree. Route: two arrays → root-and-split recursion; string round-trip → preorder with explicit null markers.

2 · Core template

Core A — Construct from Preorder + Inorder (LC 105)

Naive version: take preorder[0] as root, scan inorder to find it, copy subarrays, recurse — O(n²) from the scans and copies. Two standard upgrades: a HashMap from value → inorder index kills the scan, and index ranges instead of copied arrays kill the copying. A single advancing pre pointer replaces subarray arithmetic entirely — preorder hands out roots in exactly the order the recursion asks for them (root, then all of left, then all of right). 

// Time O(n) — each node built once, O(1) map lookup. Space O(n) map + O(h) stack.
Map<Integer, Integer> idx = new HashMap<>();  // value → its inorder position
int pre = 0;                                   // next unused preorder element

TreeNode buildTree(int[] preorder, int[] inorder) {
    for (int i = 0; i < inorder.length; i++) idx.put(inorder[i], i);
    return build(preorder, 0, inorder.length - 1);
}
TreeNode build(int[] preorder, int inLo, int inHi) {
    if (inLo > inHi) return null;              // this inorder range is empty → no subtree
    int rootVal = preorder[pre++];             // preorder ALWAYS knows the next root
    TreeNode root = new TreeNode(rootVal);
    int mid = idx.get(rootVal);                // inorder splits: [inLo..mid-1] | [mid+1..inHi]
    root.left  = build(preorder, inLo, mid - 1);  // MUST build left first — preorder order
    root.right = build(preorder, mid + 1, inHi);
    return root;
}

Worked example — dry run

preorder = [3, 9, 20, 15, 7], inorder = [9, 3, 15, 20, 7] pre=0 → root 3; inorder index 1 → left gets [9], right gets [15, 20, 7] pre=1 → root 9 (left subtree); its inorder range is just [9] → both children null pre=2 → root 20 (right subtree); splits [15] | [7] pre=3 → 15, pre=4 → 7 — done tree: 3 / (9, 20), 20 / (15, 7) ✓

Core B — Serialize / Deserialize (LC 297)

Why can one traversal rebuild the tree here when LC 105 needed two? Because we write the nulls. With every null recorded, preorder becomes unambiguous: read a token — if it's # the subtree is empty, otherwise it's a root and the next tokens are its left then right subtrees. Encoder and decoder are mirror images. 

// Preorder with null markers. Time O(n) both ways, Space O(n).
String serialize(TreeNode root) {
    StringBuilder sb = new StringBuilder();
    ser(root, sb);
    return sb.toString();                  // e.g. "1,2,#,#,3,4,#,#,#,"
}
void ser(TreeNode n, StringBuilder sb) {
    if (n == null) { sb.append("#,"); return; }  // null marker — the crucial part
    sb.append(n.val).append(',');          // root first (preorder)
    ser(n.left, sb);
    ser(n.right, sb);
}

int pos = 0;                               // shared cursor over the token stream
TreeNode deserialize(String data) {
    pos = 0;
    return des(data.split(","));
}
TreeNode des(String[] t) {
    String tok = t[pos++];                 // consume exactly one token per call
    if (tok.equals("#")) return null;      // empty subtree
    TreeNode n = new TreeNode(Integer.parseInt(tok));
    n.left  = des(t);                      // tokens arrive in preorder —
    n.right = des(t);                      // left subtree's tokens come first
    return n;
}
Why LC 105 needs inorder but LC 297 doesn't Plain preorder without nulls is ambiguous — [1,2] could be a left child or a right child. LC 105 resolves the ambiguity with a second traversal (inorder gives the split); LC 297 resolves it by recording nulls (every subtree boundary is explicit). Two solutions to the same information problem — say this in the interview.

Case: Construct from Inorder + Postorder (LC 106)

Mirror image of Core A. Postorder is (left, right, root), so read it backwards: the last element is the root, and walking backwards yields root, then the right subtree's roots, then the left's. So the pointer starts at the end and you must recurse right before left. 

Map<Integer, Integer> idx = new HashMap<>();
int post;                                      // cursor starts at the END

TreeNode buildTree(int[] inorder, int[] postorder) {
    for (int i = 0; i < inorder.length; i++) idx.put(inorder[i], i);
    post = postorder.length - 1;
    return build(postorder, 0, inorder.length - 1);
}
TreeNode build(int[] postorder, int inLo, int inHi) {
    if (inLo > inHi) return null;
    TreeNode root = new TreeNode(postorder[post--]);  // take from the back
    int mid = idx.get(root.val);
    root.right = build(postorder, mid + 1, inHi); // ★ RIGHT first — reversed postorder
    root.left  = build(postorder, inLo, mid - 1); // is (root, right, left)
    return root;
}

Case: Vertical Order Traversal (LC 987) — brief

Different flavor: assign each node a coordinate — root at column 0, left child col−1, right child col+1, row = depth — then group by column, sorting each group by (row, then value) per the problem's tie rule. A TreeMap<col, list> plus one DFS does it; know the shape more than the boilerplate. 

TreeMap<Integer, List<int[]>> cols = new TreeMap<>();  // col → [(row, val)…], keys sorted

List<List<Integer>> verticalTraversal(TreeNode root) {
    dfs(root, 0, 0);
    List<List<Integer>> out = new ArrayList<>();
    for (List<int[]> col : cols.values()) {
        col.sort((a, b) -> a[0] != b[0] ? a[0] - b[0] : a[1] - b[1]); // row, then value
        List<Integer> vals = new ArrayList<>();
        for (int[] p : col) vals.add(p[1]);
        out.add(vals);
    }
    return out;
}
void dfs(TreeNode n, int col, int row) {
    if (n == null) return;
    cols.computeIfAbsent(col, k -> new ArrayList<>()).add(new int[]{row, n.val});
    dfs(n.left,  col - 1, row + 1);           // left = one column west, one row down
    dfs(n.right, col + 1, row + 1);
}

Time O(n log n) from sorting. Note LC 314 (Vertical Order, the premium sibling) wants BFS order within a column instead of the sort rule — read the tie-break rules carefully.

4 · Edge-case checklist

  • LC 105/106 assume unique values — the value→index map is only valid then. With duplicates you'd need pure index bookkeeping.
  • LC 106: right before left, cursor from the back. Recursing left first with a back-cursor builds a scrambled tree — the signature bug.
  • Serialize negative numbers — split on a delimiter, never parse character by character (-12 is one token).
  • Null markers are load-bearing — dropping them (or the trailing ones) makes the preorder string ambiguous and the decoder misalign.
  • Deserialize shares one cursor — a field or a queue of tokens. Passing a plain int index down doesn't work: Java is pass-by-value, so child consumption wouldn't advance the parent's index.
  • Empty tree round-trip — serialize(null) must produce something ("#,") that deserializes back to null.
  • Vertical order tie rules differ between LC 314 (BFS order) and LC 987 (sort by row, then value) — mixing them fails hidden tests.
