1 · Bipartite check (2-coloring)

A graph is bipartite if you can split its nodes into two sets with every edge going between the sets — never within one. Equivalent test: try to 2-color it (color a node, force every neighbor the opposite color). The instant you must color a node the same as a neighbor, you've found a conflict. The deep fact: a graph is bipartite ⟺ it has no odd-length cycle.

Recognition trigger "Split into two groups / two teams", "can we 2-color", "no two adjacent X share a Y", "is this a valid bipartition". LC 785 (Is Graph Bipartite?) and LC 886 (Possible Bipartition — build edges from the "dislikes" list, then it's literally 785). 
// LC 785: color[] holds 0 / 1, -1 = uncolored. BFS 2-coloring.
boolean isBipartite(int[][] graph) {
    int n = graph.length;
    int[] color = new int[n];
    Arrays.fill(color, -1);
    for (int s = 0; s < n; s++) {        // graph may be DISCONNECTED — start everywhere
        if (color[s] != -1) continue;
        color[s] = 0;
        Queue<Integer> q = new ArrayDeque<>();
        q.offer(s);
        while (!q.isEmpty()) {
            int u = q.poll();
            for (int v : graph[u]) {
                if (color[v] == -1) {
                    color[v] = color[u] ^ 1;  // flip 0<->1
                    q.offer(v);
                } else if (color[v] == color[u]) {
                    return false;             // same color across an edge = odd cycle
                }
            }
        }
    }
    return true;
}

Time O(V + E) — each vertex/edge touched once. Space O(V) for the color array and queue. DFS works identically: recurse, coloring each neighbor the flipped color, return false on a clash.

Worked example — dry run

Input: an undirected 4-cycle, nodes 0..3, edges {0,1},{1,2},{2,3},{3,0}. Color the start node A, then BFS-flip each neighbor. Because it's an even cycle, no edge ever joins two same-colored nodes → bipartite = true:

color[0]=A, enqueue 0 pop 0 → neighbors 1, 3 uncolored → color[1]=B, color[3]=B, enqueue both pop 1 → neighbor 2 uncolored → color[2]=A, enqueue 2 pop 3 → neighbor 2 already A (≠ 3's B) → ok pop 2 → neighbors 1, 3 already colored and consistent → queue empty no same-colored edge ever found → return true (bipartite)

Note: an odd cycle (e.g. a triangle 0-1-2-0) would force two adjacent nodes to share a color → not bipartite.

2 · Bridges & Articulation Points (Tarjan low-link)

A bridge is an edge whose removal disconnects the graph (a single point of failure in a network). An articulation point is the vertex version. Tarjan finds all of them in one DFS using two timestamps per node: disc[u] (when DFS first reached u) and low[u] (the earliest disc reachable from u's subtree, including via one back-edge). The key test: edge (u, v) is a bridge when low[v] > disc[u] — v's subtree has no back-edge that climbs above u, so cutting the edge strands it.

Recognition trigger — Google favorite LC 1192 Critical Connections in a Network is a frequently-reported Google question and is exactly "find all bridges." Trigger words: "critical connection", "single point of failure", "edge whose removal disconnects", "servers / network resilience". If you memorize one thing in this lesson, make it this DFS. 
// LC 1192: return every bridge. Undirected graph, nodes 0..n-1.
int timer = 0;
List<List<Integer>> criticalConnections(int n, List<List<Integer>> connections) {
    List<List<Integer>> adj = new ArrayList<>();
    for (int i = 0; i < n; i++) adj.add(new ArrayList<>());
    for (List<Integer> e : connections) {
        adj.get(e.get(0)).add(e.get(1));
        adj.get(e.get(1)).add(e.get(0));   // undirected → both ways
    }
    int[] disc = new int[n], low = new int[n];
    Arrays.fill(disc, -1);                 // -1 = unvisited
    List<List<Integer>> bridges = new ArrayList<>();
    for (int i = 0; i < n; i++)
        if (disc[i] == -1) dfs(i, -1, adj, disc, low, bridges); // disconnected-safe
    return bridges;
}
void dfs(int u, int parent, List<List<Integer>> adj,
         int[] disc, int[] low, List<List<Integer>> bridges) {
    disc[u] = low[u] = timer++;
    for (int v : adj.get(u)) {
        if (v == parent) continue;         // don't bounce straight back along the same edge
        if (disc[v] == -1) {               // tree edge → recurse
            dfs(v, u, adj, disc, low, bridges);
            low[u] = Math.min(low[u], low[v]);
            if (low[v] > disc[u])          // no way back above u → bridge
                bridges.add(Arrays.asList(u, v));
        } else {                           // back edge → tighten low with disc[v]
            low[u] = Math.min(low[u], disc[v]);
        }
    }
}

Time O(V + E) — one DFS, each edge inspected twice. Space O(V) for disc/low plus O(V) recursion.

Variant: articulation points — same DFS, two changes

An articulation point is the vertex single-point-of-failure. Same disc/low DFS, but (1) the test loosens to low[v] >= disc[u] — equality now counts, because a back-edge reaching u itself still dies when u is deleted — and (2) the root is a special case: it has no ancestor to climb back to, so it's an articulation point iff it has ≥ 2 DFS children. 

// Same skeleton as the bridge DFS — only the marking logic differs.
void dfsAP(int u, int parent, List<List<Integer>> adj,
           int[] disc, int[] low, boolean[] isArt) {
    disc[u] = low[u] = timer++;
    int children = 0;                       // DFS-tree children, for the root rule
    for (int v : adj.get(u)) {
        if (v == parent) continue;
        if (disc[v] == -1) {
            children++;
            dfsAP(v, u, adj, disc, low, isArt);
            low[u] = Math.min(low[u], low[v]);
            if (parent != -1 && low[v] >= disc[u]) // >= not > : reaching u itself isn't enough
                isArt[u] = true;
        } else {
            low[u] = Math.min(low[u], disc[v]);
        }
    }
    if (parent == -1 && children >= 2) isArt[u] = true; // root rule: ≥2 subtrees fall apart
}
Bridge vs articulation — the one-character bug Bridges use low[v] > disc[u], articulation points use low[v] >= disc[u]. Mixing them up passes small tests and fails on graphs where a back-edge lands exactly on u. And only the articulation version needs the root special case — a root edge can still be a bridge via the normal test.

  • LC 1568 · Minimum Number of Days to Disconnect Island (Hard) — the answer is always 0, 1, or 2: it's 1 exactly when the island has an articulation point (or a single cell). Turns the grid into an articulation-point recognition exercise.

3 · Strongly Connected Components (Kosaraju)

In a directed graph, a strongly connected component (SCC) is a maximal set of nodes where every node can reach every other node (a "mutual reachability" cluster). Collapse each SCC to a point and the graph becomes a DAG — the standard pre-step for harder directed problems. Kosaraju finds all SCCs with two passes of DFS: (1) DFS the original graph, pushing nodes onto a stack in finish order; (2) DFS the transpose (all edges reversed) in reverse-finish order — each tree in that second pass is one SCC.

Recognition trigger (awareness-level) "Mutually reachable", "cycles in a directed graph grouped together", "condense the graph". Rare in intern interviews — recognize the term and the 2-pass idea; you're unlikely to be asked to code it from scratch under time pressure. 
// Kosaraju: count SCCs of a directed graph (nodes 0..n-1).
int countSCC(int n, List<List<Integer>> adj) {
    boolean[] seen = new boolean[n];
    Deque<Integer> stack = new ArrayDeque<>();
    for (int i = 0; i < n; i++)
        if (!seen[i]) fill(i, adj, seen, stack);   // pass 1: push in finish order

    List<List<Integer>> rev = new ArrayList<>();    // build transpose graph
    for (int i = 0; i < n; i++) rev.add(new ArrayList<>());
    for (int u = 0; u < n; u++)
        for (int v : adj.get(u)) rev.get(v).add(u);

    Arrays.fill(seen, false);
    int scc = 0;
    while (!stack.isEmpty()) {
        int u = stack.pop();
        if (!seen[u]) { scc++; mark(u, rev, seen); } // pass 2: each DFS tree = one SCC
    }
    return scc;
}
void fill(int u, List<List<Integer>> adj, boolean[] seen, Deque<Integer> stack) {
    seen[u] = true;
    for (int v : adj.get(u)) if (!seen[v]) fill(v, adj, seen, stack);
    stack.push(u);                                   // push AFTER children finish
}
void mark(int u, List<List<Integer>> rev, boolean[] seen) {
    seen[u] = true;
    for (int v : rev.get(u)) if (!seen[v]) mark(v, rev, seen);
}

Time O(V + E) — two linear DFS passes plus an O(V + E) transpose build. Space O(V + E) for the reversed graph. Tarjan's SCC does it in a single pass with one stack and the same disc/low idea from §2 — handy to mention, but Kosaraju is easier to recall.

Practice (free-tier LeetCode has no pure SCC problem — the honest drill set is one LC problem SCC thinking cracks open, plus the CP classics):

  • LC 2360 · Longest Cycle in a Graph (Hard) — every node has ≤ 1 outgoing edge (a functional graph), so each SCC of size ≥ 2 is a cycle; the answer is the largest one. Solve it with the SCC lens first, then notice the one-out-edge structure lets a timestamped walk do it in O(n).
  • CSES 1682 · Flight Routes Check — "is the whole graph ONE strongly connected component?" Kosaraju shortcut: DFS from node 1 in the graph and in the transpose; if both reach everything, yes.
  • CSES 1683 · Planets and Kingdoms — label every node with its SCC id: the countSCC template above with a comp[] array instead of a counter.

4 · Eulerian path (Hierholzer)

An Eulerian path uses every edge exactly once (contrast: a Hamiltonian path visits every vertex once — NP-hard). Hierholzer's algorithm builds it greedily: walk edges, deleting each as you use it; when you get stuck, you've completed a sub-cycle — splice it in. The neat trick is a post-order DFS that appends a node to the answer only once it's exhausted, then reverses.

Recognition trigger (awareness-level) "Use every ticket / edge exactly once", "reconstruct the itinerary", "trace the route covering all roads". LC 332 Reconstruct Itinerary is the canonical one — and it wants the lexicographically smallest route, so visit neighbors in sorted order. 
// LC 332: all tickets used once, lexically smallest itinerary, starting at "JFK".
Map<String, PriorityQueue<String>> adj = new HashMap<>();
LinkedList<String> route = new LinkedList<>();
List<String> findItinerary(List<List<String>> tickets) {
    for (List<String> t : tickets)              // min-heap = lexical order for free
        adj.computeIfAbsent(t.get(0), k -> new PriorityQueue<>()).add(t.get(1));
    dfs("JFK");
    return route;                               // already in correct order after addFirst
}
void dfs(String u) {
    PriorityQueue<String> pq = adj.get(u);
    while (pq != null && !pq.isEmpty())
        dfs(pq.poll());                         // consume the edge, recurse
    route.addFirst(u);                          // prepend when u is exhausted (post-order)
}

Time O(E log E) — every edge is consumed once, and the per-edge work is a heap poll/insert (the log E comes from sorting neighbors lexically). Space O(E) for the adjacency heaps and the route. Without the lexical requirement it's a clean O(V + E).

Practice — free-tier LeetCode

  • LC 332 · Reconstruct Itinerary (Hard) — the template verbatim: PriorityQueue adjacency for lexical order, post-order addFirst.
  • LC 2097 · Valid Arrangement of Pairs (Hard) — the same Hierholzer on pairs [start, end]: find the start node (out-degree − in-degree = 1, else any node), walk every pair once. No lexical requirement, so plain lists + an index pointer keep it O(V + E).
  • LC 753 · Cracking the Safe (Hard, stretch) — the de Bruijn sequence: nodes are (n−1)-digit states, edges are digits; an Eulerian circuit through all edges is the shortest master string.

5 · All-pairs shortest path (Floyd-Warshall)

When you need the shortest distance between every pair of nodes on a small, possibly weighted graph, Floyd-Warshall is the three-line DP. Read it as: "for each intermediate node k, can routing through k make any pair (i, j) cheaper?" The loop order is the whole trick — k must be the outermost loop.

Recognition trigger (awareness-level) "Shortest path between all pairs", "smallest number of cities reachable within a threshold", and a small V (≤ a few hundred). LC 1334 Find the City With the Smallest Number of Neighbors at a Threshold Distance is the textbook case. 
// LC 1334: dist[i][j] = shortest i->j. Seed with INF, 0 on the diagonal, edge weights.
int[][] floydWarshall(int n, int[][] edges) {
    int[][] dist = new int[n][n];
    for (int[] row : dist) Arrays.fill(row, 1_000_000); // "infinity" that won't overflow on add
    for (int i = 0; i < n; i++) dist[i][i] = 0;
    for (int[] e : edges) {                  // undirected weighted edge {u, v, w}
        dist[e[0]][e[1]] = e[2];
        dist[e[1]][e[0]] = e[2];
    }
    for (int k = 0; k < n; k++)              // intermediate node — MUST be outermost
        for (int i = 0; i < n; i++)
            for (int j = 0; j < n; j++)
                if (dist[i][k] + dist[k][j] < dist[i][j])
                    dist[i][j] = dist[i][k] + dist[k][j];
    return dist;
}

Time O(V³) — the triple loop. Space O(V²) for the matrix. That cubic cost caps it at roughly V ≤ 400–500; beyond that, run Dijkstra (Lesson 07) from each source instead. It also handles negative edges (no negative cycles).

Practice — free-tier LeetCode

  • LC 1334 · Find the City With the Smallest Number of Neighbors at a Threshold Distance (Medium) — already solved (Lesson 07 ladder) — re-solve from a blank file if the triple loop isn't automatic yet.
  • LC 2976 · Minimum Cost to Convert String I (Medium) — the graph is just 26 letter-nodes with conversion-cost edges; Floyd-Warshall the 26×26 matrix, then sum dist[src[i]][tgt[i]] per position. The cleanest "small V hiding inside a string problem" drill.
  • LC 2642 · Design Graph With Shortest Path Calculator (Hard) — n ≤ 100 with many queries and edge insertions: maintain the all-pairs matrix and relax it through each new edge in O(V²) instead of re-running everything.

6 · Edge-case checklist

  • Disconnected graphs (all of these): bipartite check, bridges, and SCC must loop over every node and launch from each unvisited one — a single start misses whole components.
  • Bipartite on a disconnected graph: color each component independently; one component being bipartite doesn't excuse the others.
  • Bridges — the parent edge: skip the immediate parent, but beware parallel edges (two edges between the same pair) — those are never bridges, so skipping by parent id rather than parent node matters. Self-loops contribute nothing to low and are never bridges.
  • Eulerian — lexical order: LC 332 wants the smallest route, so neighbors must come out sorted (a PriorityQueue or pre-sorted list). Also: prepend (addFirst) in post-order, or you'll get the route reversed.
  • Eulerian existence: a path exists only if 0 or 2 vertices have odd degree (undirected); LC 332 guarantees one exists, but real problems may not.
  • Floyd-Warshall feasibility: O(V³) is fine at V = 100 (10⁶ ops), painful at V = 1000 (10⁹). Check the constraint before committing to it — otherwise reach for Dijkstra-per-source.
  • Floyd-Warshall overflow: use an "infinity" like 10⁶, not Integer.MAX_VALUE, so dist[i][k] + dist[k][j] doesn't overflow.
