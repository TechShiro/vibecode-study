Minimum Spanning Tree (Kruskal & Prim)

Connect every node into one network for the least total cost. Two greedy builds — sort edges (Kruskal) or grow a tree (Prim) — and the same family of "minimum cost to connect" interview problems falls out.

Mission link: Graphs are ~25% of Google intern questions, and "minimum cost to connect all points" is a verified Google favorite. This is Lesson 8 of the 9-lesson graph track. Mission
Prerequisite — two earlier lessons power this one Kruskal is just sort + Union-Find from Graph Lesson 06 (Union-Find / DSU), and Prim is BFS with a min-heap using PriorityQueue from Java Lesson 03: PriorityQueue & Comparators. If either is rusty, skim it first — MST adds almost no new machinery.

1 · The one idea

A spanning tree of a connected, undirected graph picks a subset of edges that touches all V nodes using exactly V − 1 edges and forms no cycle. A minimum spanning tree (MST) is the spanning tree whose edge weights sum to the smallest possible total. There are two greedy ways to build one, and both are provably optimal:

  • Kruskal — sort all edges ascending, then walk them cheapest-first and add an edge iff it joins two different components (otherwise it would close a cycle). Component membership is tracked with Union-Find.
  • Prim — grow one tree from an arbitrary start node; repeatedly take the cheapest edge crossing from the tree to a node not yet in it, via a min-heap.

Both stop the instant they have added V − 1 edges. Either greedy choice is safe because of the cut property: across any partition of the nodes, the lightest crossing edge is always in some MST.

Recognition trigger "Minimum cost to connect all points / cities / houses / nodes", "make the whole network reachable as cheaply as possible", "lay cable/road/pipe so everything is linked." The signal is connect everything once, minimize total weight, no shortest-path-between-two-nodes involved. If the question instead asks the cheapest path from A to B, that is Dijkstra (Lesson 07), not MST — though the two share machinery, as the Prim cases below show.

2 · Core template — Kruskal (sort edges + DSU)

Kruskal needs an edge list {u, v, w}, sorted by weight. The Union-Find structure answers "are u and v already connected?" in near-O(1); if not, we union them and take the edge. 

// Returns total MST weight, or -1 if the graph is disconnected.
int kruskal(int n, int[][] edges) {       // edges[i] = {u, v, w}
    Arrays.sort(edges, (a, b) -> Integer.compare(a[2], b[2])); // cheapest first
    DSU dsu = new DSU(n);
    long total = 0;                        // long: summed weights can overflow int
    int used = 0;                          // edges added so far
    for (int[] e : edges) {
        if (dsu.union(e[0], e[1])) {       // union returns false if already same set
            total += e[2];
            if (++used == n - 1) break;    // V-1 edges → tree complete, stop early
        }
    }
    return used == n - 1 ? (int) total : -1; // fewer than V-1 → disconnected
}

// Union-Find with path compression + union by size (from Lesson 06).
class DSU {
    int[] parent, size;
    DSU(int n) {
        parent = new int[n];
        size = new int[n];
        for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }
    }
    int find(int x) {
        while (parent[x] != x) { parent[x] = parent[parent[x]]; x = parent[x]; }
        return x;
    }
    boolean union(int a, int b) {
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;        // same component → adding edge makes a cycle
        if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
        parent[rb] = ra;
        size[ra] += size[rb];
        return true;
    }
}

Time O(E log E) dominated by the sort (the DSU work is near-O(E·α) ≈ O(E)). Space O(V) for the DSU arrays (the edge list is the input).

3 · Core template — Prim (PriorityQueue + visited[])

Prim treats MST like a BFS that always expands the cheapest frontier edge. Start from any node, push its edges into a min-heap keyed by weight, and repeatedly pop the lightest edge to an un-visited node. This wants an adjacency list of int[]{neighbor, weight}. 

// adj.get(u) = list of {neighbor, weight}. Returns MST weight or -1 if disconnected.
int prim(int n, List<List<int[]>> adj) {
    boolean[] inTree = new boolean[n];     // node already absorbed into the tree?
    PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(a[1], b[1]));
    pq.offer(new int[]{0, 0});             // {node, edgeWeight}; start node has cost 0
    long total = 0;
    int count = 0;                         // nodes pulled into the tree
    while (!pq.isEmpty() && count < n) {
        int[] top = pq.poll();             // cheapest crossing edge
        int u = top[0], w = top[1];
        if (inTree[u]) continue;           // stale heap entry — skip (key trick)
        inTree[u] = true;                  // absorb u now
        total += w;
        count++;
        for (int[] nei : adj.get(u)) {     // add u's edges to the frontier
            if (!inTree[nei[0]]) pq.offer(new int[]{nei[0], nei[1]});
        }
    }
    return count == n ? (int) total : -1;  // didn't reach all n → disconnected
}

Time O(E log V) — each edge can be pushed once and every pop/push is O(log V). Space O(V + E) for the heap and adjacency list.

The "lazy Prim" skip is the crux We push a node every time we see a cheaper-looking edge and never decrease-key. So the heap holds stale entries. The if (inTree[u]) continue; line discards any popped edge whose endpoint is already in the tree — without it you'd double-count weight. Mark inTree at pop time (when the edge is committed), not at push time. This mirrors the Dijkstra "skip outdated" pattern from Lesson 07.

4 · Kruskal vs Prim — which to reach for

 KruskalPrim
Core machineSort edges + Union-FindMin-heap grown from one node
Input it likesEdge list — given edges[][] directlyAdjacency list — already built / easy to build
Best whenSparse (E ≈ V): few edges to sortDense (E ≈ V²): heap beats sorting V² edges
ComplexityO(E log E)O(E log V)
BonusEdges arrive pre-sorted → near-linear; easy to reason aboutStreams the tree outward; pairs with a dist[]/eager variant

Rule of thumb: given raw edges or a sparse graph → Kruskal; given/needing an adjacency list or a dense graph → Prim. Both are correct everywhere; this is about which fits the input with least code. Since E log E = E log V²= 2E log V, the asymptotics tie on dense graphs — the constant factor and input shape decide.

Case: Min Cost to Connect All Points (LC 1584) — build the complete graph, both ways

No edges are given, just points. The graph is implicit: every pair of points is an edge whose weight is their Manhattan distance |x1−x2| + |y1−y2|. That's n(n−1)/2 edges, so O(n²). Code it both ways — interviewers love asking for the other one.

Kruskal way — materialize all pair edges, sort, union:

int minCostConnectPoints(int[][] points) {
    int n = points.length;
    List<int[]> edges = new ArrayList<>();   // build the complete graph: O(n^2) edges
    for (int i = 0; i < n; i++)
        for (int j = i + 1; j < n; j++) {
            int w = Math.abs(points[i][0] - points[j][0])
                  + Math.abs(points[i][1] - points[j][1]); // Manhattan distance
            edges.add(new int[]{i, j, w});
        }
    edges.sort((a, b) -> Integer.compare(a[2], b[2]));
    DSU dsu = new DSU(n);
    long total = 0;
    int used = 0;
    for (int[] e : edges) {
        if (dsu.union(e[0], e[1])) {
            total += e[2];
            if (++used == n - 1) break;     // connected all points
        }
    }
    return (int) total;                     // always connectable (complete graph)
}

Prim way — never build the edge list; generate a node's edges at absorb time. The graph is complete, so "the neighbors of u" is simply every un-absorbed point:

int minCostConnectPoints(int[][] points) {  // lazy Prim on the implicit graph
    int n = points.length;
    boolean[] inTree = new boolean[n];
    PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(a[1], b[1]));
    pq.offer(new int[]{0, 0});               // {point index, edge weight}
    int total = 0, count = 0;
    while (count < n) {
        int[] top = pq.poll();
        int u = top[0], w = top[1];
        if (inTree[u]) continue;             // stale entry — same skip as the template
        inTree[u] = true; total += w; count++;
        for (int v = 0; v < n; v++)          // implicit edges: u ↔ every other point
            if (!inTree[v])
                pq.offer(new int[]{v, Math.abs(points[u][0] - points[v][0])
                                    + Math.abs(points[u][1] - points[v][1])});
    }
    return total;
}
Why Prim is often preferred here On a complete graph E = O(n²), so Kruskal's sort is O(n² log n) and you must store all n² edges. Prim (above) never builds the edge list — O(n² log n) time but only O(n)-ish extra state. And a dense-Prim with a plain int[] minDist array (no heap at all) runs in O(n²), the textbook optimum for this problem. Mention this trade-off if the interviewer pushes on scale.

Kruskal case 1: Edge Length Limited Paths (LC 1697) — the offline trick

For each query {u, v, limit}: does a path exist using only edges strictly lighter than limit? Answering queries one-by-one rebuilds the DSU every time. The offline trick: sort the queries by limit too. Then as limits rise, the DSU only ever grows — each edge is unioned exactly once across all queries. 

// Main logic. Sort edges by weight; sort query INDICES by limit (answers must
// come back in original order, so sort indices, not the queries themselves).
Arrays.sort(edgeList, (a, b) -> Integer.compare(a[2], b[2]));
Integer[] qi = /* 0..q-1 sorted by queries[i][2] ascending */;
DSU dsu = new DSU(n);
int e = 0;
for (int idx : qi) {
    int u = queries[idx][0], v = queries[idx][1], limit = queries[idx][2];
    while (e < edgeList.length && edgeList[e][2] < limit) {  // absorb all edges below limit
        dsu.union(edgeList[e][0], edgeList[e][1]);           // Kruskal's exact inner loop
        e++;
    }
    ans[idx] = dsu.find(u) == dsu.find(v);   // one find answers the query
}

O((E + Q) log(E + Q)) for the sorts; the merge itself is near-linear. This is Kruskal's loop reused as a query engine — no tree is ever built.

Kruskal case 2: Remove Max Edges, Keep Graph Fully Traversable (LC 1579) — two DSUs

Edges are typed: 1 = Alice only, 2 = Bob only, 3 = both. Remove as many as possible while both can still reach everything. Greedy insight (same as Kruskal's cycle rejection): process the most valuable edges first — type-3 (shared) before type-specific — and an edge is removable exactly when union returns false in every DSU it applies to. 

// Main logic. Two independent DSUs; count redundant edges.
DSU alice = new DSU(n + 1), bob = new DSU(n + 1);  // nodes 1..n
int removed = 0, aliceUsed = 0, bobUsed = 0;
for (int[] e : edges) if (e[0] == 3) {              // pass 1: shared edges first
    if (alice.union(e[1], e[2])) { bob.union(e[1], e[2]); aliceUsed++; bobUsed++; }
    else removed++;                                 // cycle for both → safe to drop
}
for (int[] e : edges) {                             // pass 2: type-specific edges
    if (e[0] == 1) { if (alice.union(e[1], e[2])) aliceUsed++; else removed++; }
    if (e[0] == 2) { if (bob.union(e[1], e[2]))   bobUsed++;   else removed++; }
}
return (aliceUsed == n - 1 && bobUsed == n - 1) ? removed : -1; // V-1 check, twice

Note the ending: the familiar used == n − 1 spanning check, applied to both DSUs. If either falls short, the graph was never fully traversable → -1.

Prim case 1: Find the Safest Path in a Grid (LC 2812) — max-heap bottleneck

Each cell's "safeness" is its distance to the nearest thief; a path's safeness is the minimum cell safeness along it. Maximize that from top-left to bottom-right. Two phases: (1) multi-source BFS from all thieves to fill safe[r][c]; (2) the Prim template with the comparator flipped to a max-heap and the key = worst safeness so far. 

// Phase 2 main logic — Prim shape, max-heap, min-key. safe[][] from BFS.
PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(b[0], a[0])); // MAX-heap
pq.offer(new int[]{safe[0][0], 0, 0});      // {pathSafeness, r, c}
boolean[][] seen = new boolean[n][n];
while (!pq.isEmpty()) {
    int[] t = pq.poll();
    int s = t[0], r = t[1], c = t[2];
    if (seen[r][c]) continue;               // same stale-skip as lazy Prim
    seen[r][c] = true;
    if (r == n - 1 && c == n - 1) return s; // first pop of target = best bottleneck
    for (int[] d : DIRS) {                   // 4 neighbors
        int nr = r + d[0], nc = c + d[1];
        if (inBounds && !seen[nr][nc])
            pq.offer(new int[]{Math.min(s, safe[nr][nc]), nr, nc}); // key = worst cell so far
    }
}
The reusable lesson — bottleneck keys When a path is scored by its worst (or best-of-worst) edge/cell instead of a total, keep the Prim/Dijkstra shape and swap only the key: Math.min(...) or Math.max(...) instead of +, and flip the heap direction to match. The greedy pop-order argument still holds — that's the cut property doing the work.

Prim case 2: Network Delay Time (LC 743) — same machinery, sum key

Signal from node k reaches everyone — how long until the last node hears it? This is formally Dijkstra (Lesson 07), but look at the code: it is line-for-line the §3 Prim template. Heap, visited, stale-skip at pop. The only difference is the key — Prim pushes the edge weight, Dijkstra pushes the accumulated path sum. Internalize that one-line delta and you own both algorithms. 

// Main logic — compare each line to §3. adj.get(u) = list of {neighbor, weight}.
PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(a[1], b[1]));
pq.offer(new int[]{k, 0});                   // start at k, elapsed time 0
boolean[] visited = new boolean[n + 1];
int ans = 0, count = 0;
while (!pq.isEmpty()) {
    int[] top = pq.poll();
    int u = top[0], d = top[1];
    if (visited[u]) continue;                // identical stale-skip
    visited[u] = true; ans = Math.max(ans, d); count++;
    for (int[] nei : adj.get(u))
        if (!visited[nei[0]])
            pq.offer(new int[]{nei[0], d + nei[1]}); // ← the ONLY delta: d + w, not w
}
return count == n ? ans : -1;                // same reach-all check as Prim

Stretch case: Critical and Pseudo-Critical MST Edges (LC 1489) — Kruskal as a subroutine

Hard, but the logic is just three runs of the same Kruskal you already have. Compute the base MST weight, then test each edge: 

// Main logic — kruskal(n, edges, forcedEdge, bannedEdge) returns MST weight.
int base = kruskal(n, edges, -1, -1);       // normal run: the reference weight
for (int i = 0; i < edges.length; i++) {
    if (kruskal(n, edges, -1, i) > base)    // ban edge i: weight rises (or graph splits,
        critical.add(i);                    //   treat as ∞) → edge is CRITICAL
    else if (kruskal(n, edges, i, -1) == base) // force edge i in first: weight unchanged
        pseudo.add(i);                      //   → PSEUDO-critical (in some MST, not all)
}

The modified kruskal is the §2 template with two tweaks: if forcedEdge ≥ 0, union it and add its weight before the sorted loop; if an edge index equals bannedEdge, skip it. Total cost O(E² log E) — fine for LC constraints.

6 · Edge-case checklist

  • Disconnected graph ⇒ no spanning tree. If you add fewer than V − 1 edges (Kruskal) or absorb fewer than V nodes (Prim), there is no MST — return -1 (or per spec). Always check the count at the end. LC 1579 applies this check twice, once per DSU.
  • Honor the V−1 stop condition. Break as soon as used == V − 1; running past it wastes time and, in Prim, risks adding stale heavy edges if your skip check is wrong.
  • Parallel edges are fine. Multiple edges between the same pair just sit in the list; the union/visited check keeps only the cheapest that actually joins components. No dedup needed.
  • Self-loops (u == v) are harmless — union(u,u) returns false / both ends are inTree — but never useful in an MST; ignore them.
  • Overflow on summed weights. With up to ~10⁵ edges of weight up to ~10⁶, the total exceeds int. Accumulate in a long, cast at the end (the templates do this).
  • Indexing. If nodes are labelled 1..n (LC 1579, LC 743), size the DSU / arrays n + 1 and ignore index 0; on grids (LC 2812), either flatten (r, c) to r * cols + c or keep 2-D seen[][]. Off-by-one here is the classic silent bug.
  • Prim: mark inTree at pop, skip stale entries. Marking at push (or forgetting the skip) double-counts weight. See the §3 callout.
  • Strict vs non-strict limits. LC 1697 requires edges strictly less than the query limit — <, not <=, in the merge loop. Read the comparison in the problem statement, don't assume.
  • Answers in original order. Offline tricks (LC 1697) sort a copy of the query indices, never the answer array — write results back via the original index.
